### PROBLEM

Current main still computes a continuous speed-driven `localPlayer.squashX/squashY` every movement update, but the production PNG avatar renderer in `engine-ab.js` does not consume those values at all. The effect only exists in the older procedural `engine-a.js::renderAvatar()` path, which is bypassed when `assets/hero.PNG` is loaded successfully.

This is simultaneously dead runtime work and a future implementation trap. The user explicitly wants body lean, weight, bob and a larger lateral avatar. A tempting shortcut would be to reconnect the existing squash/stretch values to the PNG. But the legacy transform was designed around the procedural avatar centered on `p.x,p.y`, not around the PNG's explicit foot root at `p.y+10`. Applying non-uniform scale/rotation around the old center can move the visible feet relative to the world contact point and create exactly the floating/foot-slip effect we are trying to remove.

The existing signal is also driven by speed magnitude, not acceleration/reversal/contact semantics. At sustained full movement it tends toward a permanently widened/shortened body instead of a transient anticipation/weight response.

### CONFIRMED_IN_GEMINI

At current `main` baseline `4db45b9849b1a6e02ff1262eb67ad1c4af42168a`, visible title `Kelo World — V6.13`:

1. `engine-a.js` initializes the local player with `squashX:1` and `squashY:1`.
2. Every `updateMovement(dt)` computes current speed and exponentially drives:
   - `squashX -> 1 + (currentSpeed / CONFIG.speed) * 0.08`
   - `squashY -> 1 - (currentSpeed / CONFIG.speed) * 0.06`
   with response constant `15` via `1-exp(-15*dt)`.
3. Current `engine-ac.js` forces `CONFIG.movementType='DIRECT'` and sets `CONFIG.speed` to the current speed-cap function before calling the base movement. Under open-ground direct movement, `currentSpeed / CONFIG.speed` is therefore approximately processed input magnitude.
4. At full input the legacy target deformation is approximately `scaleX=1.08`, `scaleY=0.94`; at 0.5 processed magnitude it is approximately `1.04 x 0.97`.
5. Base `engine-a.js::renderAvatar()` applies that deformation only for the self actor above 10 px/s. It translates to `p.x,p.y`, rotates into the movement direction, applies non-uniform scale, rotates back, then draws the procedural body. Thus the transform origin is the physics/player center, not the PNG foot root.
6. `engine-ab.js` is the effective PNG renderer when the sheet is loaded. It never reads `p.squashX` or `p.squashY` and never calls the base renderer on the successful PNG path. It draws the lateral PNG at about 48 x 81 world px with `footY = p.y + 10`.
7. Therefore the squash/stretch calculation currently has no visible effect on the production PNG hero in the normal loaded-asset path.
8. If the legacy full-speed Y scale 0.94 were naively applied around `p.y`, the foot root offset `+10` would itself transform toward roughly `+9.4` in a pure horizontal orientation, shifting visible contact by about 0.6 world px before camera/zoom. More importantly, the sprite top/body envelope would also change around the wrong pivot. This number is a geometric prediction, not a measured LIVE artifact because production does not currently apply the scale.
9. If the same 1.08/0.94 scale were applied to the current side rectangle itself, nominal 48 x 81 becomes about 51.84 x 76.14 before any rotation/sampling. That is a 4.86 px vertical-height change at full input. With a center-style pivot, part of that change necessarily affects the feet unless an explicit foot-root compensation is added.
10. `engine-v.js` is intentionally empty and says scale was absorbed into `engine-ab` draw size, so there is no separate current presentation-transform owner that safely mediates visual deformation around the feet.
11. The production PNG renderer currently mirrors LEFT and draws RIGHT from the same lateral row; any body deformation applied in world axes must be checked for mirror symmetry and not accidentally bias one direction.
12. `ENGINE_MAP.md` is still stale: it labels `engine-m.js` as hero owner while current PNG rendering is in `engine-ab.js`. Do not follow that ownership row blindly.
13. No Grok feedback newer than GC-20260831-003 exists, so there is no measured implementation evidence that body squash/lean has already been validated in current V6.13.
14. Recent V6.13 changes are primarily Gardens composition/visual-direction work; the movement/render snippets above were re-read from current main and not assumed from older rounds.

### EXTERNAL_EVIDENCE

1. Godot's current `Sprite2D` documentation exposes `centered` and `offset` explicitly and notes that sprite placement relative to its transform matters, including pixel-art deformation when centered between pixels. This supports treating the visual pivot/offset as an explicit presentation contract rather than implicitly scaling around the physics center. Source: https://docs.godotengine.org/en/4.6/classes/class_sprite2d.html
2. Unity root-motion documentation distinguishes a stable body/root transform from foot/IK goals. Kelo does not use Mecanim root motion, but the transferable principle is that body deformation and ground contact should be expressed relative to a stable root instead of allowing arbitrary sprite scaling to move the contact point. Source: https://docs.unity3d.com/kr/2022.3/Manual/RootMotion.html
3. A confirmed Godot GitHub issue documents pixel instability when rotation and float motion interact under pixel-perfect rendering. This is counterevidence against adding arbitrary continuous rotation/shear to Kelo's current nearest-neighbor Canvas2D sprite before screen-space sampling is benchmarked. Source: https://github.com/godotengine/godot/issues/57221
4. Another Godot issue documents visible sprite pixel stretching artifacts at non-integer display scale near collisions. It does not prove Kelo has the same bug, but it reinforces that dynamic non-uniform scale plus fractional output scaling can create artifacts in pixel-art-like rendering. Source: https://github.com/godotengine/godot/issues/54974
5. Community 2D animation practice repeatedly recommends placing the graphics pivot at the feet (or compensating position) when squash/stretch must preserve ground contact, and keeping visual graphics separate from the collider/physics object. One concrete Unity2D thread describes center-pivot Y scaling lifting the feet and solving it by pivot/offset separation. Source: https://www.reddit.com/r/Unity2D/comments/gk60ao
6. Community evidence also supports squash/stretch as useful game feel when subtle, but includes counterevidence that excessive continuous squash looks cartoony or distracting. A January 2026 Godot discussion specifically praises the effect while recommending reducing its amplitude when it becomes too prominent. Source: https://www.reddit.com/r/godot/comments/1qgyvut/squash_and_stretch_and_skew/
7. A recent open-source 2D procedural controller separates the physics collider from a visual puppet and uses squash/stretch/limb motion on the presentation layer. It is not a normative engine standard, but it is a concrete architecture example aligned with the foot-root separation already proposed for Kelo. Source: https://github.com/cristhiandrm/2D-Procedural-Hyper-Motion-Controller

### HYPOTHESIS

Kelo will feel more premium if visual body deformation is treated as a foot-rooted presentation effect, not as a legacy physics-adjacent scale signal. The existing `squashX/squashY` should first be classified as dead/legacy for the production PNG path. If a subtle premium body response is desired, derive a new presentation signal from locomotion transitions/reversal/contact state and apply it around an explicit `footRoot`, while leaving `p.x/p.y`, collider radius 20, collision resolution and camera unchanged.

For lateral locomotion, a better first candidate than permanent speed squash is a very small transient response:
- launch/start: slight forward lean/stretch that decays quickly;
- sustained travel: return close to 1.0 scale rather than remain 1.08/0.94 forever;
- hard reversal: short opposite anticipation/settle response keyed to direction change/velocity sign change;
- stop/blocked: settle to neutral/contact pose without changing the foot root;
- any vertical bob remains a sprite/body offset above the foot root; contact shadow remains on the root.

This is a hypothesis until the current 4-frame source and sampling pipeline are tested. The final 8+8 atlas may encode much of this in art and require less procedural deformation.

### RISKS

1. The current 4-frame atlas may not tolerate extra scale/rotation without looking rubbery; a future authored 8+8 atlas could make procedural deformation unnecessary.
2. Continuous rotation/shear on nearest-neighbor pixel-art-like sprites can generate shimmer at fractional camera/zoom/DPR.
3. A transient lean driven from poorly filtered acceleration can vary with dt/refresh and reintroduce 60/90/120 Hz inconsistency.
4. Foot-root compensation can be mathematically correct while visual silhouette still looks wrong because source-frame alpha bounds/pivots vary; atlas audit remains necessary.
5. Reversal deformation can mask, rather than solve, a bad contact-frame transition. Foot planting/reversal phase must remain independently measurable.
6. Removing legacy squash computation too early could alter the procedural fallback if `hero.PNG` fails to load; cleanup needs a fallback-path test.
