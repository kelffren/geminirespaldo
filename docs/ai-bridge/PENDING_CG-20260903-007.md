### PROBLEM

The production hero PNG path does not render `assets/hero.PNG` directly. `engine-ab.js` first copies the entire image into an offscreen canvas, reads every RGBA pixel, and sets alpha to zero whenever all three RGB channels are greater than 232. That rule is global and position-blind: it does not distinguish white background connected to the outside of a frame from intentional near-white pixels inside Kelo's body, eyes, jewelry, metal highlights, clothing, specular edges, or other authored detail.

At the current small destination size, any accidental holes or clipped bright detail may be visually subtle. The user's next objective explicitly includes making the avatar materially larger. Increasing destination size will make each surviving/removed source feature occupy more screen area, so transparency preprocessing must be audited before avatar scale is judged. Otherwise a scale experiment can incorrectly conclude that the source art is low-quality when the loader itself is deleting part of it.

This is separate from previously researched non-integer scaling/subpixel judder: even perfect sampling cannot recover pixels whose alpha was zeroed before `drawImage()`.

### CONFIRMED_IN_GEMINI

At current `main` baseline `4d4203036181922a215122e4745a271f0482049a`, visible title `Kelo World — V6.12`:

1. `index.html` loads `engine-ab.js?v=149` after `engine-m.js`; current `ENGINE_MAP.md` is stale and still labels `engine-m.js` as hero owner even though `engine-ab.js` overrides `renderAvatar()` with the production PNG path.
2. `engine-ab.js` creates a new offscreen canvas matching `raw.width/raw.height`, draws the complete `assets/hero.PNG` into it, then calls `getImageData(0,0,c.width,c.height)`.
3. It loops through every pixel and executes `if (r > 232 && g > 232 && b > 232) alpha = 0`.
4. No spatial mask, connected-component test, frame-border flood fill, alpha-matte analysis, or exception for interior highlights exists in that preprocessing.
5. After this destructive preprocessing, the modified pixels are written back with `putImageData()` and this processed canvas becomes the source for every hero/NPC `drawImage()` using the PNG renderer.
6. `engine-ab.js` sets `ctx.imageSmoothingEnabled=false` for sprite drawing. This affects scaling interpolation, but it does not restore pixels already made transparent.
7. The renderer crops each 4x4 cell further by about 5% horizontally and 4% vertically before scaling it to the current destination body size (side width 48 world px, non-side width 54; destination height derived from sheet cell aspect ratio).
8. Therefore there are two independent quality transforms before the character reaches the screen: source crop + global near-white transparency key, followed by nearest-neighbor scaling.
9. `engine-l.js` separately applies a HiDPI backing store up to DPR 3, so source-detail loss from the alpha key can remain visible on high-density screens; higher DPR increases display sampling capacity but cannot recreate deleted source detail.
10. The binary `assets/hero.PNG` is present at current main with blob SHA `8319a9046f5dd874f44d1f420d227fa97a005490`.
11. This connector/runtime could confirm the current blob identity but could not decode the binary PNG in this research pass. Therefore this entry does NOT claim how many intentional bright pixels are actually being deleted. That is the benchmark to run.
12. No Grok feedback newer than GC-20260831-003 exists, so there is no implementation evidence closing this asset-preprocessing question.

### EXTERNAL_EVIDENCE

1. MDN documents `getImageData()` as direct access to underlying pixel data and `putImageData()` as writing that modified data back. The current loop therefore permanently changes alpha in the processed hero source used for rendering; this is not merely a display filter.
2. MDN documents `imageSmoothingEnabled=false` as a way to preserve hard pixels during image scaling. It controls interpolation only; it does not make a color-key operation semantically safe.
3. A concrete chroma-key bug report in CasparCG describes bright white/yellow details such as teeth, metal zips, eyes and bright clothing being incorrectly keyed out. This is the same failure class as a position-blind brightness key, although it is external evidence, not proof that Kelo's atlas contains those colors.
4. Aseprite issue discussions around sprite transparency show that source spritesheets often require deliberate background/alpha handling; changing background colors to transparency can affect interior sprite pixels when the background color also appears inside the art.
5. A current sprite-processing project (`sprite-lab`) explicitly uses background-connected detection plus alpha matting to avoid destroying internal highlights and to reduce white/grey edge halos. It is an implementation example, not an authority, but it demonstrates a safer class of preprocessing than global RGB thresholding.
6. A May 2026 community thread on AI-generated spritesheets reports white fringe/halo cleanup as a recurring problem and recommends selecting connected transparent/background regions and then carefully growing/color-to-alpha rather than indiscriminately deleting every white-ish pixel.
7. Counterevidence: if `hero.PNG` was intentionally generated with a pure/near-pure white matte and contains no desired pixels above the threshold, the current simple key can be perfectly adequate and cheaper than a more complex preprocessing pipeline. Do not replace it solely because the algorithm looks crude.
8. Counterevidence: making the avatar larger can actually expose more of the original source detail because the destination draw uses more screen pixels. If the alpha mask is already clean, larger scale may improve perceived detail rather than harm it. The purpose of this experiment is to isolate alpha-mask quality from scaling quality.

### HYPOTHESIS

Before selecting an avatar scale such as 1.15x, 1.25x or 1.30x, Kelo World should measure whether the global near-white key removes pixels that are not part of the exterior matte. If it does, replacing only the preprocessing mask — while keeping the same source atlas, same movement, same destination size, same filtering and same collider — should preserve more intentional detail and produce a cleaner large-avatar preview.

The safest candidates are:

A — BASELINE_GLOBAL_KEY
- Current rule: every pixel with R,G,B > 232 becomes fully transparent.

B — PER_CELL_EDGE_CONNECTED_KEY
- Divide the atlas into the same 4x4 cells used by the renderer.
- Build the same near-white candidate mask, but only remove candidate pixels connected to the outer border of each cell through an agreed neighborhood.
- Bright candidate islands fully enclosed inside the foreground survive.
- This is a diagnostic/candidate, not automatically the final art pipeline.

C — AUTHORED_ALPHA_ASSET
- Export a hero atlas with final transparency authored into the PNG and remove runtime color keying entirely.
- This is conceptually strongest if the art source can be regenerated cleanly, but it should only replace the current path after identical-frame visual comparison and load/memory testing.

D — MATTE/DECONTAMINATION PASS
- If B preserves interior highlights but leaves pale fringe at silhouette edges, test a narrowly scoped edge-matte/decontamination algorithm offline or at asset-build time rather than increasing the global brightness threshold.

### DO_NOT_ASSUME

- Do not assume every near-white pixel is background.
- Do not assume every non-border-connected near-white pixel is intentional foreground; holes between limbs/clothing can be real background islands. The metric is a warning signal that requires contact-sheet inspection.
- Do not raise/lower the `232` threshold blindly.
- Do not change collider radius 20 to match a larger sprite.
- Do not change camera, stride cadence, reversal, gait thresholds, shadow, aura, nameplate or depth during this mask experiment.
- Do not enable bilinear smoothing merely to hide edge artifacts; that can mask the alpha problem while softening the sprite.
- Do not claim the atlas currently has deleted eyes/highlights until binary measurement or rendered comparison proves it.
- Do not replace the asset with a new artistic interpretation in the same experiment; preserve content so mask quality can be isolated.

### RISKS

- Edge-connected flood fill can preserve unwanted white islands that are genuinely background holes enclosed by the silhouette; contact-sheet review remains necessary.
- 8-neighbor connectivity can leak through diagonal anti-aliased paths differently from 4-neighbor connectivity; benchmark both before choosing.
- A soft matte/decontamination algorithm can create semi-transparent edges that look worse with nearest-neighbor pixel-art presentation.
- Runtime per-pixel connected-component work may add startup cost and allocations on mobile; authored alpha at asset-build time may be preferable if the source pipeline allows it.
- Larger avatars increase the perceptual visibility of every mask/pivot/frame inconsistency; a cleaner alpha mask does not solve stride, reversal, depth or subpixel issues already tracked separately.
- The current source could already be perfectly compatible with the global key. In that case changing it is needless complexity and should be rejected.
