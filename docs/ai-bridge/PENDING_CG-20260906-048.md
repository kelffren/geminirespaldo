### PROBLEM
The LIVE lateral/vertical facing classifier and the lateral-reversal classifier do not use the same directional boundary, and neither has directional hysteresis. Near the diagonal boundary an analog joystick can therefore make the rendered hero alternate between lateral row 2 and vertical rows even when the player is holding an effectively steady diagonal intent. In addition, there is an angular band where the renderer classifies movement as lateral but reversal telemetry classifies it as non-horizontal, so the current reversal audit can miss visually lateral reversals.

### CONFIRMED_IN_GEMINI
Current `main` at the start of this round is `b3d8ce6ed6c3550fb4c46d5fe331d20c4d48bb2f`.

`index.html` still loads `engine-ab.js` before `engine-ac.js`, and the live movement/render contract remains `engine-ac.js` gait/facing state -> `engine-ab.js` hero renderer.

In `engine-ac.js::updateVisualMotion()`:

- lateral reversal intent uses `Math.abs(intentX) >= Math.abs(intentY)`;
- rendered facing uses `Math.abs(v.dx) * 1.15 >= Math.abs(v.dy)`;
- `v.face` is rewritten immediately on every update whenever the classifier changes;
- there is no facing hold time, angular hysteresis band, or previous-axis preference at the diagonal boundary.

The reversal threshold is therefore 45 degrees from the horizontal axis. The rendered-side threshold is `|dy/dx| <= 1.15`, or about `atan(1.15) = 48.99 degrees`. This leaves an approximately 3.99-degree band (45.00–48.99 degrees from horizontal) where the hero is rendered with the lateral sprite row but `horizontalIntentSign` is zero, so a left/right sign change in this visually lateral band is not counted as a lateral reversal.

`engine-ab.js` consumes `v.face` directly through `motionOf()`/`faceOf()` and maps `left/right` to spritesheet row 2, `down` to row 0, and `up` to row 3. Therefore any `v.face` churn across the threshold is a real row change, not audit-only state.

`engine-a.js::processInput()` produces continuous analog `normX/normY` from the touch joystick after radial deadzone processing. It does not quantize direction to cardinal sectors, so small pointer/hand changes near the boundary can feed continuously varying angles to the classifier. Keyboard exact diagonals are less exposed because normalized x/y are equal and deterministically classify as lateral under both current inequalities.

There is also duplicated directional responsibility: `engine-ac.js` computes and publishes `v.face`, while `engine-ab.js::faceOf()` retains a fallback classifier using the same 1.15 side bias. Do not refactor this duplication until a measured directional contract is selected.

### EXTERNAL_EVIDENCE
- Unity's official 2D Blend Tree documentation treats velocity X/Y as a two-parameter directional space and distinguishes directional blending as a first-class locomotion problem. This supports deriving animation direction from a coherent 2D directional contract rather than unrelated thresholds in separate systems: https://docs.unity3d.com/Manual/BlendTree-2DBlending.html
- Godot's official controller documentation notes that joystick inputs need deadzone handling because real analog devices produce drift/noise; the deadzone must reject noise without discarding intentional input: https://docs.godotengine.org/en/latest/tutorials/inputs/controllers_gamepads_joysticks.html
- Community evidence shows analog axes commonly produce arbitrary intermediate values rather than exact cardinal values, and diagonal animation/flip logic can fail when it assumes exact or overly sharp directional boundaries. Recent Godot example: https://www.reddit.com/r/godot/comments/1ui2yag/hello_im_new_to_godot_and_programing_and_i_have/
- Another community case documents awkward animation state transitions while a physical joystick passes through intermediate values during direction changes, motivating transition-state/hysteresis treatment rather than interpreting one sample as a new stable state: https://www.reddit.com/r/gamedev/comments/18ti5bn/how_to_avoid_going_into_the_idle_state_when/

Counterevidence: a crisp cardinal threshold is not inherently wrong. For keyboard or deliberately snappy four-direction art, immediate switching can be desirable. Adding too much hysteresis can make Kelo visibly keep a sideways pose while the player is clearly moving vertically. The issue to prove is repeated/chattering boundary crossings and inconsistent classifier ownership, not simply that the current threshold is sharp.

### HYPOTHESIS
A single authored direction classifier, shared by facing and reversal logic, with a small angular hysteresis around the lateral/vertical boundary will reduce diagonal row popping and make reversal telemetry cover every visually lateral reversal without changing physics, speed, collision, stride phase, or input latency.

A likely design is stateful axis preference rather than smoothing the movement vector itself: keep the current horizontal/vertical facing axis until the incoming direction crosses a stricter exit boundary, then switch. This preserves DIRECT physics and raw joystick responsiveness while stabilizing only presentation classification.

### PROPOSED_CHANGE
Do not change production yet.

Create a QA-only directional classifier, for example `classifyVisualDirection(dx, dy, previousFace)` or equivalent, and make both:
1. `v.face` selection; and
2. `horizontalIntentSign` / lateral reversal classification
consume the same axis decision.

Candidate A: current single threshold, instrumented only.
Candidate B: unified current 1.15 threshold with no hysteresis (tests whether mismatch alone matters).
Candidate C: unified threshold plus a small hysteresis band/previous-axis preference. Exact enter/exit ratios must be selected by benchmark; do not hard-code the suggested values from this research as production truth.

Do not low-pass/filter `input.normX/normY` for this experiment. That would change input feel and confound the result. Stabilize animation-facing classification only.

### DO_NOT_ASSUME
- Do not assume every diagonal should use a lateral sprite. The current art only has cardinal presentation rows and the authored preference needs visual evaluation.
- Do not assume 1.15 is the correct final side bias merely because both `engine-ac.js` and fallback `engine-ab.js` use it.
- Do not assume hysteresis is beneficial until row-churn is reproduced with actual touch traces or deterministic noisy-angle traces.
- Do not change movement vectors, speed, collider, camera, stride cadence, footRoot, or avatar scale in the same experiment.
- Do not delete the fallback direction logic in `engine-ab.js` until baseline/change/same-trace evidence shows which owner should remain.

### RISKS
- Excess hysteresis can create sticky/wrong-facing diagonals.
- A previous-axis preference can make the same instantaneous vector display differently depending on history; this is intentional only if the visual stability benefit is measurable.
- Unifying reversal classification with rendered facing may change audit counters without changing gameplay; tests must distinguish telemetry changes from actual player behavior.
- If the sprite art itself makes the 49° lateral preference look bad, the correct result may be to alter the base directional boundary rather than add hysteresis.
- Future true 8-direction sprites would change this design; keep the classifier contract isolated so it can be replaced rather than embedded across wrappers.
