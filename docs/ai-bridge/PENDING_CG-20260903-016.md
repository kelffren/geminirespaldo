### PROBLEM
The previous round established that `renderAvatar()` can be called 1/2/3 times for the same actor in a single RAF because Plaza/Gardens depth compositing redraws actors. Even if legacy locomotion mutation is moved out of render, the current late `armor-aura.js` wrapper means each `renderAvatar()` call also redraws semi-transparent back/front aura passes. Therefore render-count remains observable: the same Armor Aura can become substantially more opaque/bright merely because the actor is inside a landmark's depth-composite region. This is especially undesirable during lateral movement across a fountain/landmark because brightness can change as a spatial side-effect unrelated to gameplay or aura rank.

There is a second scale-related coupling in the same VFX wrapper: aura ring/body glow/particle reach are derived from `p.radius || 20`, i.e. the physical collider radius. The current user priority is to enlarge the visual avatar while preserving collider=20. If the body becomes 1.15x–1.25x but Aura remains collider-sized, the aura-to-body composition changes even when physics correctly stays unchanged.

### CONFIRMED_IN_GEMINI
Current `main` load order in `index.html` is: `engine-ab.js` (visible PNG renderer) -> ... -> `plaza-depth.js` -> `gardens-landmark.js` -> ... -> `armor-aura.js`. Because Plaza/Gardens call the global `renderAvatar` at execution time, those depth redraws invoke the later Aura wrapper.

`engine-c.js` already performs the normal actor draw once during the base world pass. `plaza-depth.js` then calls `base()`, enters its world transform, draws `back`, calls `renderAvatar()` for each overlapping actor, draws `front`, and calls `renderAvatar()` again for actors whose `y > baseY`. `gardens-landmark.js` uses the same back -> actor -> front -> optional front-actor redraw pattern.

`armor-aura.js::install()` wraps the final avatar path as:
`renderBack(ctx,p); base(p,isSelf); renderFront(ctx,p);`
so every depth redraw repeats semitransparent ring, body glow and particles.

The Aura alpha values make this non-neutral under source-over compositing. Example at rank 9: ring alpha is `min(.16 + 9*.045, .58) = .565`. If the same ring pixels are drawn repeatedly over the same destination, idealized effective alpha is `1-(1-a)^n`: one draw=.565, two=.811, three=.918. Body glow rank-9 alpha is `.035 + 9*.012 = .143`; one=.143, two=.266, three=.371. Exact screen pixels vary because ring halves/particles and other passes differ, but repeated draws cannot be assumed visually identical to one draw.

The wrapper also sizes most Aura geometry from physical radius: ring rx uses `(p.radius||20)*(1.05+rank*.075)*pulse`; body glow uses `(p.radius||20)*(1.35+rank*.07+...)`; particle orbit/rise uses `(p.radius||20)`. `engine-ab.js` independently renders the hero at roughly 48x81 world px laterally while collider remains radius 20. A future 1.25x body (~60x101 world px) would not automatically enlarge Aura geometry.

Code ownership/redundancy scan: this is not a request to refactor every wrapper. The relevant responsibility duplication is that actor presentation is split across body (`engine-ab`), aura (`armor-aura`) and landmark-specific redraw orchestration (`plaza-depth`, `gardens-landmark`). Current multipass composition assumes `renderAvatar()` is safe to repeat, but semi-transparent VFX violate that assumption even if animation state becomes pure.

### EXTERNAL_EVIDENCE
Official Godot 2D particle documentation explicitly separates particle local/global coordinate behavior and visibility bounds from the emitter, reinforcing that VFX need their own presentation-space contract rather than inheriting physics geometry by default: https://docs.godotengine.org/en/latest/tutorials/2d/particle_systems_2d.html

Godot issue #98764 documents a real low-resolution-game/high-resolution-UI setup where particle behavior becomes visibly jittery when transform snapping is inherited from a rendering context, illustrating the broader risk of letting unrelated presentation transforms leak into VFX behavior: https://github.com/godotengine/godot/issues/98764

Godot issue #104423 documents particles being unintentionally affected by physics interpolation and recommends separating that behavior; again, not the same Kelo bug, but relevant evidence that particle/VFX presentation should not implicitly inherit unrelated simulation/render policies: https://github.com/godotengine/godot/issues/104423

Counterevidence: simple Canvas2D games can intentionally redraw an actor and all attached VFX together if the redraw replaces previous pixels or is rendered to isolated compositing surfaces. Kelo currently does not clear an isolated actor surface between repeated depth calls; the extra Aura calls source-over onto the same frame, so that counterexample does not make the current calls neutral. Also, keeping aura radius tied to the collider can be an intentional gameplay readability choice, so visual-scale decoupling must be measured rather than assumed.

### HYPOTHESIS
For the current Canvas2D architecture, actor presentation should be split conceptually into at least:
1. actor body/name/depth content that may legitimately be redrawn for occlusion composition;
2. ground/contact VFX with explicit depth policy;
3. additive/semitransparent aura/particles that should normally contribute once per final visible actor per RAF, or be composited through an isolated actor layer that is itself reused without accumulating alpha.

A minimal fix may not require a renderer rewrite. If instrumentation confirms intensity drift, the safest candidate is to make depth passes capable of redrawing BODY_ONLY while the Aura is emitted once in a stable VFX pass. Separately, future avatar scaling should introduce an explicit visual presentation scale/envelope input for Aura instead of changing collider radius.

### PROPOSED_CHANGE
Do not implement production changes before baseline measurements.

Candidate A — BASELINE: keep current global `renderAvatar()` calls and record Aura invocation count/intensity across depth zones.

Candidate B — BODY_ONLY_DEPTH_REDRAW: preserve all existing physics/depth decisions, but depth-composite redraws call a body-only presentation function or suppress Aura during corrective actor redraws. Aura renders exactly once in the normal actor/VFX pass. Do not change collider, world trace, camera, gait or network state.

Candidate C — ISOLATED_ACTOR_COMPOSITE: render actor body+AURA once into an isolated compositing surface/snapshot and reuse that result in depth composition. This can preserve aura-body integration but is architecturally larger and should be DEFERRED unless B cannot preserve correct front/back aura ordering.

Scale follow-up, only after redraw policy is stable: add a visual scale/envelope input such as `presentationScale`/`visualBounds` for VFX sizing while leaving `radius=20` as physics-only. Benchmark 1.00x/1.15x/1.25x; do not derive visual scale by mutating collider radius.

### DO_NOT_ASSUME

Do not refactor all renderer wrappers before measuring.

### RISKS
Suppressing Aura from all depth redraws could put ring/particles on the wrong side of an occluder; B must define which Aura components belong ground/back/front rather than blindly drawing everything last.
An isolated actor surface may increase memory/bandwidth and complicate pixel-perfect sampling.
Freezing Aura phase is test-only; production animation must remain time-based.
A larger visual Aura may create clutter with 25–50 actors even if one actor looks better.
Any new presentationScale must not leak into collisions, social tap radius, network position or gameplay hit tests.
