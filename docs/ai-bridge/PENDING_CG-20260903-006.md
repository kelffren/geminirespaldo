### PROBLEM

Current mobile input has two different activation thresholds after the raw radial deadzone. `processInput()` begins producing a non-zero normalized movement vector immediately outside `CONFIG.joystickDeadzone`, but `engine-ac.js::gaitFrom()` continues classifying the hero as `idle` until processed magnitude reaches `GAIT_IDLE_MAX=0.03`. Because physical DIRECT movement consumes the non-zero input vector regardless of gait, there is a narrow but real touch band in which Kelo moves physically while the local visual locomotion system is still IDLE. At the current joystick radius/deadzone this corresponds to roughly 2.06 CSS pixels of additional radial thumb travel beyond the raw deadzone and physical speeds up to ~3.3 world px/s.

This is distinct from the previously researched 0.12 px/update stride-credit issue: here the contradiction exists even before stride advancement. The physical movement policy and the gait activation policy disagree about whether Kelo has started locomoting.

### CONFIRMED_IN_GEMINI

At current live `main` baseline `6660f453b32abdd7f84dcdf8b031188bb1bf5a5f`, visible title `Kelo World — V6.12`:

1. `engine-ac.js` currently overrides `CONFIG.joystickRadius=72`, `CONFIG.joystickDeadzone=0.045`, `CONFIG.joystickCurve='LINEAR'`, and `CONFIG.movementType='DIRECT'`.
2. `engine-a.js::processInput()` computes a radial raw distance in CSS client coordinates. If `dist < radius*deadzone` it outputs zero; otherwise it linearly remaps the remaining radius with `mag=(min(dist,maxR)-deadR)/(maxR-deadR)` and emits `input.normX/Y = unitDirection * mag`.
3. With radius 72 and deadzone 0.045, `deadR = 3.24 CSS px`.
4. `engine-ac.js::gaitFrom(mag)` returns `idle` while `mag < 0.03`, `walk` for magnitudes below 0.70 after that, and `run` from 0.70 upward.
5. The raw radius that maps to processed magnitude 0.03 is `deadR + 0.03*(72-deadR) = 3.24 + 2.0628 = 5.3028 CSS px`, or ~7.365% of the virtual stick radius.
6. Therefore the radial interval from approximately 3.24 px to 5.30 px is physically active according to `processInput()` but visually IDLE according to `gaitFrom()`.
7. For all magnitudes in that interval, `speedFor(mag)` returns `WALK_SPEED=110`; DIRECT base movement therefore requests physical speed `mag*110`, approaching 3.3 world px/s just below the visual gait threshold.
8. `engine-ac.js::updateVisualMotion()` defines `hasIntent = gait !== 'idle'`, so this sub-0.03 band is not considered visual intent even though `input.normX/Y` is non-zero.
9. The same function only treats movement as physically moving if per-update world displacement exceeds 0.12 px or velocity exceeds 16 px/s. The micro-movement band's speed is <=3.3 px/s, far below the velocity fallback.
10. At 60 Hz, 3.3 px/s produces only ~0.055 world px/update; at 90 Hz ~0.0367; at 120 Hz ~0.0275. All are below the existing 0.12 per-update displacement threshold. Thus the visual motion state can settle to `on=false` while world position continues changing.
11. `engine-ab.js` renders frame column 0 whenever local `_visualMotion.on` is false. Therefore the production hero can remain on its idle column while physics creeps.
12. `engine-ah.js` does not cancel this mismatch. Its `hasMoveInput()` returns true whenever `input.touchActive` is true, so holding a live touch slightly outside deadzone does not invoke its hard-stop path. DIRECT movement has already set the requested low velocity.
13. Keyboard input does not traverse this analog magnitude band: cardinal or normalized diagonal keyboard input has magnitude 1. The issue is therefore primarily mobile/touch (and any future analog source using the same processed vector).
14. The global CSS/runtime currently supplies pointer client coordinates directly to the virtual joystick, so the 3.24/5.30 quantities are CSS-pixel thumb distances, not DPR backing-store pixels.
15. Current `ENGINE_MAP.md` is stale (V5.15/v66 and outdated hero ownership). Current `engine-ab.js` remains the effective production PNG renderer after load, and `engine-ac.js` remains the local `_visualMotion` producer.
16. No Grok feedback newer than GC-20260831-003 exists, so this mismatch has not been closed by implementation evidence.

### EXTERNAL_EVIDENCE

1. Unity Input System documentation describes stick deadzones as a Vector2 magnitude processor: input below `min` is output as zero, input above the upper threshold is normalized, and the accepted range is re-normalized. This supports using a coherent activation contract rather than allowing separate hidden movement and animation thresholds to disagree.
2. Unity's InputSettings documentation notes that physical sticks are often wobbly and that deadzones are specifically intended to filter unwanted small input near center; it also notes the active range is re-normalized after deadzoning.
3. Community reports across controller/game-development forums repeatedly describe the perceptual failure mode of characters slowly drifting while visually idle or after light stick input. These reports are anecdotal, not proof of Kelo's runtime appearance, but they support treating low-speed unintended motion as highly noticeable game-feel debt.
4. A March 2026 Godot community thread shows a near-zero residual joystick component breaking directional animation selection; the accepted advice is to use the engine's deadzone rather than testing for exact zero. This is relevant to keeping movement and animation activation thresholds semantically aligned.
5. Counterevidence: enlarging the deadzone indiscriminately can make input feel sluggish and reduce fine analog control. Therefore the proposal is not simply to increase `joystickDeadzone` from 4.5% to 7.4% and ship it. The relevant experiment is to align locomotion activation while preserving as much continuous post-deadzone range as possible.

### HYPOTHESIS

Kelo's mobile lateral movement will feel more planted if there is one explicit locomotion activation contract: when the presentation says IDLE, physical travel caused by the movement stick should also be zero; once physical travel starts, presentation should have enough signal to leave IDLE consistently.

Three candidates should be compared rather than assuming the fix:

A — BASELINE_DUAL_THRESHOLD
- Keep current 4.5% raw deadzone and separate 0.03 gait threshold.
- Expected to preserve the confirmed physical-IDLE band.

B — SINGLE_ACTIVATION_REMAP
- Keep the raw 4.5% hardware/touch-noise deadzone.
- Treat processed magnitude <=0.03 as no locomotion for both physics and presentation.
- Re-normalize the remaining processed range 0.03..1 back to 0..1 before deriving target speed/gait so maximum reach and most analog range are preserved.
- Do not implement by simply increasing the raw deadzone unless measurements show they are behaviorally equivalent for thumb feel.

C — VISUAL_START_AT_ANY_PROCESSED_INPUT
- Leave physics exactly as baseline but classify any meaningful processed magnitude >epsilon as locomotion intent.
- This removes semantic disagreement but may make tiny thumb jitter trigger WALK and will still interact badly with the unresolved per-update stride-credit threshold. It is useful as countercandidate, not the preferred result.

Candidate B is currently the cleaner hypothesis because it enforces `IDLE => zero stick-driven travel` without requiring the walk animation to respond to near-zero noise, but it must be measured for start latency/fine-control loss.

### RISKS

- Re-normalizing 0.03..1 can slightly steepen the low-end response curve; this may make initial WALK acceleration feel less delicate even while removing creep.
- Increasing only the raw deadzone can reduce fine thumb control and make the virtual stick feel unresponsive.
- Starting animation at every tiny non-zero magnitude can expose touch jitter, produce WALK flicker, and interact poorly with current distance-credit thresholds.
- Real fingers have larger positional noise than a synthetic sweep, so a numerically clean threshold still needs mobile touch validation.
- The current virtual stick has no explicit start/stop hysteresis; after activation is unified, a narrow stateful hysteresis may prove useful, but do not add it until baseline chatter is measured.
- Existing integer sprite snapping and 0.12 distance gating can make very-low-speed visible motion look more quantized than its world trace; those are separate known variables and must be logged, not silently changed.
