### PROBLEM
Kelo's local-player gait and the generic appearance renderer both classify movement direction with the same instantaneous rule: horizontal/side wins when `abs(dx) * 1.15 >= abs(dy)`. There is no directional hysteresis or minimum hold around the side↔vertical sector boundary. The boundary is therefore approximately `atan(1.15) = 48.99°` from horizontal. Near that angle, tiny analog/touch-vector changes can swap the rendered row between side and up/down while world movement remains smooth. This is a presentation discontinuity, not a physics problem, and it becomes more obvious as the avatar gets larger.

The current LIVE hero harness verifies that diagonal movement contains both X and Y displacement, but it does not assert which face/row is chosen, how often it changes, or whether mobile and desktop resolve an equivalent diagonal consistently. This leaves a gap exactly in the user's current priority: premium lateral/diagonal motion, reversals and future larger character scale.

### EXTERNAL_EVIDENCE
- Godot's official controller documentation explains that analog axes do not reliably return exactly zero and recommends a circular deadzone for 2D vector input. This supports treating analog/touch input as noisy continuous data rather than assuming exact stable thresholds. https://docs.godotengine.org/en/latest/tutorials/inputs/controllers_gamepads_joysticks.html
- Godot's `Input.get_vector()` documentation specifically describes a circular deadzone and normalized vector handling for joystick/WASD movement. Kelo already approximates the normalized-vector part; the remaining issue here is presentation sector switching, not magnitude normalization. https://docs.godotengine.org/en/4.2/classes/class_input.html
- A current open-source analog-stick driver (`wdtamagi/zmk-driver-analog-stick`) exposes configurable threshold **and hysteresis** specifically when converting an analog stick into 4/8 directional states. This is directly analogous to Kelo converting a continuous vector into four animation-facing states: one threshold chooses a state, hysteresis prevents chatter around the boundary. https://github.com/wdtamagi/zmk-driver-analog-stick
- Community evidence from r/gamedev documents an adjacent joystick state problem: during a direction reversal the stick crosses intermediate values and can briefly enter an unwanted animation state. Recommended fixes include considering motion state/velocity or an explicit turnaround state rather than mapping every instantaneous input sample directly to animation. https://www.reddit.com/r/gamedev/comments/18ti5bn/
- Counterevidence: adding dedicated 8-direction art can make diagonal presentation more faithful, but it multiplies animation/export/shadow workload substantially. A recent r/gamedev account of an 8-direction hand-drawn game reports the combinatorial cost of N/NE/E/SE/S/SW/W/NW and notes even mirrored directions can require lighting/shadow corrections. Kelo should first prove that stable 4-direction sector selection is insufficient before expanding art scope. https://www.reddit.com/r/gamedev/comments/1twgjqx/

### HYPOTHESIS
H1 — A small presentation-only hysteresis band around the side↔vertical facing boundary will reduce sprite-row chatter during noisy or slowly rotating diagonal touch input without changing movement, velocity, collision or camera traces.

H2 — Facing hysteresis should use the previous **presentation face** as state. It should not modify `input.normX/Y` or physics. The player's world trajectory remains fully analog; only the animation row waits for a decisive angular crossing.

H3 — The same facing-sector helper should eventually serve both `engine-ac.js` local visual motion and `character-appearance.js` generic actors, because both currently duplicate the same 1.15 ratio. Do not refactor ownership before A/B proof; first instrument both paths with identical metrics.

H4 — The existing 1.15 side bias is not necessarily wrong. The experiment should compare the current ~49° nominal boundary with stateful bands around it rather than replacing it with an assumed 45° rule.

H5 — Fixing sector stability before 1.20x scale is important because larger sprites make a whole-row switch visually more conspicuous; scale is an amplifier, not the root cause.

### PROPOSED_CHANGE
Do not change production locomotion in this research pass. Add measurement first, then a feature-flagged presentation candidate.

1. Add facing telemetry to the local `_visualMotion` audit: previous face, candidate raw face, committed face, face transition count, side↔vertical transition count, and time/distance since last committed face change.
2. Extend the hero harness with controlled angular sweeps and noisy diagonal traces instead of only keyboard `D+S`.
3. Candidate helper concept: `resolveFacingWithHysteresis(previousFace, dx, dy, params)`. It returns one of `left/right/up/down` and never changes the underlying vector.
4. Keep initial facing acquisition compatible with the current `1.15` rule. Once a side or vertical state is established, require a larger angular margin to leave it.
5. Benchmark small hysteresis bands first, e.g. ±3°, ±5°, ±7° around the current ~49° side/vertical boundary. Do not pick a final band by intuition.
6. Horizontal sign reversal (right↔left) remains immediate when the vector is decisively lateral; do not use side↔vertical hysteresis to delay left/right reversal. The user's control must remain responsive.
7. Generic bots/peers should later consume the same presentation-sector policy, but keep that rollout separate from CG-024 distance-driven gait so one experiment changes one variable.
8. Keep avatar scale 1.15, crop, per-frame foot-pivot candidate, cadence, `CONFIG.speed`, joystick deadzone/radius/curve, collider, camera and zoom unchanged during this A/B.

### DO_NOT_ASSUME
- Do not increase the joystick deadzone to solve an animation-facing problem. That would trade visual stability for worse control responsiveness.
- Do not clamp movement to 4 or 8 directions. World movement should remain continuous analog.
- Do not add diagonal sprite rows before proving stable four-direction sectors are visually insufficient.
- Do not apply smoothing to `input.normX/Y` in this experiment; that would alter physics/camera and contaminate the A/B.
- Do not delay direct right↔left reversals. Hysteresis is only for the side↔vertical boundary.
- Do not assume 45° is the correct art boundary. Current code intentionally biases side to ~49°; measure candidate boundaries against actual sprite readability and foot planting.
- Do not combine this with 1.20x scale, pivot migration, distance-driven generic gait or network interpolation changes.

- console/network failures: 0.

### RISKS
- Too much hysteresis can make the sprite look like it is facing sideways after movement has become visibly vertical. This is why angular bands must be benchmarked, not guessed.
- Too little hysteresis will not stop row chatter on touch input.
- A four-direction art set may still look awkward at true diagonals even with perfect sector stability. If that remains after hysteresis + foot anchoring, then dedicated diagonal poses/rows become an art question, not an input bug.
- `engine-ac.js` and `character-appearance.js` currently duplicate facing logic. Implementing separate hysteresis independently would deepen architectural debt; after proof, move the pure policy to one shared presentation helper.
- If tests inject vectors by mutating `input.normX/Y` after `processInput()`, timing/order can invalidate the result. The harness needs a deterministic hook at the same stage normal input reaches gait processing.
