### PROBLEM
The live PNG hero path in engine-ab.js replaces renderAvatar when hero.PNG is available. The legacy renderAvatar in engine-a.js draws a grounding ellipse before drawing the fallback body, but the live engine-ab.js path draws the sprite and nameplate without drawing that grounding ellipse. At the same time engine-ab.js exports layout.shadowAnchorX/Y at the footRoot, while Armor Aura computes footRootY but draws its ring at p.y + physicsRadius * 0.72. This creates two separate ground-anchor concepts and means rank-0 heroes can have no explicit ground-contact shadow in the live PNG path.

### CONFIRMED_IN_GEMINI
- main was re-read at commit 2ebe11066a8c7a28cfbc39338bbef270de9b92dd; index.html declares Kelo World V6.52 and loads engine-a.js before engine-ab.js, then later src/systems/armor-aura.js.
- engine-a.js::renderAvatar draws an ellipse at (p.x, p.y + 14) with radii p.radius*0.9 and p.radius*0.45 before drawing the legacy procedural body.
- engine-ab.js captures const _av = renderAvatar, but when hero.PNG is loaded successfully it does NOT call _av. It draws only the processed sprite and then the nameplate. Therefore the legacy ellipse is not part of the successful PNG path.
- engine-ab.js::presentationOf exports footRootY = p.y + 10 and shadowAnchorY = footRootY. This shadowAnchor is not consumed inside the live engine-ab.js renderer itself.
- src/systems/armor-aura.js uses KELO_AVATAR_PRESENTATION, including footRootY in visualMetrics(), but drawRing() positions the ellipse at p.y + physicsRadius*0.72. With the default radius 20 this is p.y + 14, i.e. 4 world px below the declared footRoot/shadowAnchor at p.y + 10.
- Armor Aura returns immediately for rank <= 0, so its ring is not a universal grounding cue.
- The current layout already separates physicsRoot, footRoot, depthRoot, shadowAnchor and nameplateAnchor, so a dedicated ground-local shadow can be introduced without changing collider or sprite scale if measurements support it.
- Redundancy/ownership: engine-a.js still owns a legacy visual shadow; engine-ab.js owns the live PNG actor presentation and separately exposes shadowAnchor; armor-aura.js has a third ellipse placement rule. These are duplicated ground-contact responsibilities, but no refactor is proposed until the visual baseline is measured.

### EXTERNAL_EVIDENCE
- Unity 2D Sprite tooling explicitly supports sprite pivots/custom pivots, reinforcing the general practice of using a semantic pivot rather than assuming the center of the graphic rectangle for actor grounding.
- Unity SpriteAlignment documents BottomCenter and Custom pivot alignment, relevant to foot-root anchoring.
- Community top-down 2D practice commonly keeps the ground shadow as a separate object/layer from animated character motion; a Godot discussion recommends moving/animating the character branch independently while leaving the shadow at the ground position during vertical character motion.
- A separate Godot report documents visible sprite/shadow jitter despite them sharing a parent, showing that apparently coupled sprite/shadow layers can still diverge perceptually under camera/scaling conditions and should be measured in screen space.
- GitHub Godot rendering issues #71074, #35606 and docs issue #7774 document pixel-art/camera smoothing jitter and the sensitivity of subpixel transforms/pixel snapping. This is counterevidence against simply adding a highly dynamic or independently rounded shadow transform.
- Counterevidence: a grounding ellipse is not automatically an improvement. The live sprite may already contain enough painted contact information, and a generic oval can look cheap or conflict with authored lighting. Candidate must be judged visually and by temporal stability.

### HYPOTHESIS
A restrained, ground-local contact shadow whose center is derived from KELO_AVATAR_PRESENTATION.shadowAnchor and whose rendering is independent of BODY_LOCAL gait/lean/bob will improve lateral movement grounding, especially as avatarVisualScale rises from 1.15 toward 1.20. A single canonical ground anchor should also reduce future divergence between normal shadow, aura ring, depth and foot-root systems. However, the visual benefit is unproven and a naive shadow can introduce shimmer, excess darkness or double-grounding.

### PROPOSED_CHANGE
Do not change production yet. Benchmark four presentation-only variants:
A) current live PNG baseline: no explicit normal contact shadow; Aura unchanged.
B) diagnostic legacy-equivalent ellipse reintroduced under the PNG hero at the current legacy center p.y+14.
C) foot-root shadow: same restrained ellipse concept centered exactly on layout.shadowAnchorX/Y (currently p.y+10), with dimensions derived from visualWidth or collider radius but never changing collider/physics.
D) foot-root shadow plus Aura alignment: normal shadow at shadowAnchor and Aura ring center expressed relative to the same canonical ground anchor. Candidate D is architectural control only; do not ship unless Aura visuals remain correct at all ranks.

For any future BODY_LOCAL lean/bob/squash, keep shadow under GROUND_LOCAL and do not inherit sprite rotation/bob. Do not couple contact shadow opacity/position to animation frame until per-frame support-foot evidence exists.

### DO_NOT_ASSUME
- Do not assume the old p.y+14 ellipse was visually correct merely because it existed first.
- Do not assume shadowAnchor=p.y+10 is the true visible sole contact for every lateral frame; CG-068 already identified per-frame opaque-bottom data as a measurement prerequisite.
- Do not assume Aura ring should exactly overlap the normal contact shadow; it may deliberately encircle a wider magical footprint.
- Do not change p.radius, collider, world position, camera, stride cadence or sprite scale in this experiment.
- Do not add body-relative bob/rotation to the shadow.
- Do not refactor legacy renderAvatar ownership before baseline/change/same-trace remeasurement.

### EXPERIMENT
Use the same deterministic avatar/world trace for A/B/C/D. Test local hero rank 0 first so Aura cannot mask the shadow result, then ranks 3, 7 and 9. Traces: idle; RIGHT 0.25/0.50/1.00; LEFT equivalents; walk->run; run->walk; release; RIGHT->LEFT reversal; 45-degree diagonals; repeated short taps; full-stick against a collider; pass behind/in front of an occluder if a deterministic fixture is available. Repeat at avatar scale 1.15 baseline and QA-only 1.20, without touching the collider. Repeat 60/90/120 Hz and at minimum 390x844 DPR2 and 1280x720 DPR1. Capture frame-by-frame screen-space coordinates for physicsRoot, footRoot, shadow center, visible support centroid, aura center, depthRoot and sprite bounds. Use the exact same input trace and camera trace for all candidates.

### RISKS
- Generic ellipse can make premium art look cheaper or over-dark.
- Separate integer rounding of sprite and shadow can create 1px relative shimmer; if used, both should derive screen placement from the same world transform/rounding policy.
- Scaling shadow from collider radius may underrepresent a visually enlarged 1.20 avatar; scaling from visualWidth may make shadow too large for narrow side poses. Benchmark both dimensions rather than assume.
- Aura ring currently uses p.y+14 semantics; moving it to footRoot without visual review can make high-rank aura look too high.
- Multiple late render wrappers may affect draw order; verify the final wrapped renderAvatar, not only engine-ab.js in isolation.
- Any per-frame support-foot anchoring can itself jitter if contact inference changes frame to frame. Keep canonical ground anchor stable unless data proves otherwise.
