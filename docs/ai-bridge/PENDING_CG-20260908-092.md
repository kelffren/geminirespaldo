### PROBLEM
The live PNG hero now has a semantic `nameplateAnchor`, but the actual text is still painted inside `engine-ab`'s avatar middleware. `visual-integration` is a higher-priority KeloAvatar middleware and applies BODY_LOCAL offset/rotation/non-uniform scale around the foot pivot before calling `next()`. Therefore the body transform also applies to the hero nameplate. This already matters for active transform animation clips and becomes a direct blocker for adding locomotion lean/squash/bob cleanly or enlarging the avatar while preserving UI readability.

### CONFIRMED_IN_GEMINI
Current `main` is Foundation V3. `KeloAvatar` sorts middleware by descending priority and explicitly documents that larger priority is an outer layer. `visual-integration:actor-fx-transform` registers at priority 400, saves the Canvas context, applies transform offset + rotation + scale around the semantic foot pivot, then calls `next()`. `engine-ab:production-hero` registers at priority 100 and inside that call draws the PNG and then `fillText(p.name || 'Kelo', round(layout.nameplateAnchorX), round(layout.nameplateAnchorY))`. Canvas text therefore inherits the current BODY_LOCAL matrix.

The problem is not only theoretical. `visual-manifests.js` currently defines `cast_magic_01` with scale/rotation keyframes including roughly (0.96,1.04,-0.035rad,-1Y) and (1.07,0.96,+0.045rad,+2X). With the lateral hero's current nameplate approximately ~99 world px above the foot pivot (about 93 px visual height + 6 px gap), the latter keyframe can move the nameplate anchor by roughly +6.3 world px horizontally and +4 world px vertically relative to an untransformed overlay, while rotating the glyphs ~2.58 degrees and non-uniformly scaling them. At an effective zoom of 1.45 that horizontal displacement is roughly 9 CSS px. Exact runtime values must be measured rather than assumed.

The same architecture would make any future locomotion micro-lean/squash affect the nameplate every step. This is specifically relevant to CG-083: BODY_LOCAL deformation should not silently become NAMEPLATE_LOCAL deformation.

### EXTERNAL_EVIDENCE
MDN documents that the current Canvas 2D transformation matrix is applied when painting text as well as shapes, and that rotate()/scale()/translate() modify that matrix. Therefore a `fillText()` executed inside the current transformed context is rotated/scaled by design, not by browser accident:
- https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D
- https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/rotate
- https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/scale

Unity's World Space UI documentation explicitly separates the problem of placing UI in the world from its chosen scale/orientation; a world-space UI may be freely rotated/scaled, which is useful for diegetic surfaces but not automatically desirable for a readable player nameplate:
- https://docs.unity3d.com/cn/2018.3/Manual/HOWTO-UIWorldSpace.html

Community evidence is mixed and is useful as counterevidence. In a Unity2D top-down discussion, a developer reports that health/name UI rotating with characters is undesirable and the suggested solution is to billboard/stabilize it. Conversely, Unreal community discussion notes that world-space nameplates can intentionally participate in world occlusion, while screen-space nameplates often require explicit occlusion checks. This means Kelo should not blindly move nameplates to screen UI; it should separate BODY_LOCAL transform from WORLD/NAMEPLATE positioning while deciding occlusion policy independently.
- https://www.reddit.com/r/Unity2D/comments/y2j3lf/
- https://www.reddit.com/r/unrealengine/comments/1klz0mf/

### HYPOTHESIS
Kelo's nameplate should normally follow the actor's semantic head/nameplate anchor and camera/world transform, but should not inherit transient BODY_LOCAL rotation or non-uniform squash/stretch. Avatar visual scale may change the anchor height, but font orientation and glyph aspect ratio should remain stable. A tiny vertical BODY_LOCAL offset could be debatable for a fully diegetic label, so this must be benchmarked rather than hard-coded as doctrine.

### PROPOSED_CHANGE
Do not patch `engine-ab` by applying the inverse KeloAnimation matrix; that would duplicate ownership and couple the renderer back to the animation system.

Benchmark an explicit composition split instead:
A. Baseline: current priority-400 BODY_LOCAL transform contains sprite + nameplate.
B. Stable nameplate lane: body/actor FX remain inside BODY_LOCAL; nameplate is painted after the BODY_LOCAL transform is restored, using `KELO_AVATAR_PRESENTATION.nameplateAnchor` transformed only by the normal world/camera matrix.
C. Optional anchored-offset variant: if fully stable B feels visually detached during strong authored actions, test a small position-only offset derived from the body transform while still forcing rotation=0 and glyph scaleX=scaleY=1.

Implementation architecture must reuse `KeloAvatar`; do not introduce a direct `renderAvatar` wrapper. Prefer a named overlay/post-body composition extension or another owner-supported lane rather than adding special inverse-matrix knowledge to `engine-ab`. Before changing owner APIs, prove B is visually preferable and does not break prop occlusion/redraw paths from CG-091.

### DO_NOT_ASSUME
- Do not assume every world-space nameplate must be screen-space UI.
- Do not assume the current transformed behavior is perceptually bad without reproducing an active transform clip.
- Do not assume locomotion lean has already been implemented; it has not.
- Do not assume visual avatar scale should scale the 11 px font. Increasing 1.15x -> 1.20x should first move the anchor with the taller body while keeping font readability stable unless a separate UI scale rule is justified.
- Do not refactor KeloAvatar middleware blindly. Baseline -> isolated candidate -> same trace -> measurement.

### RISKS

- Moving the label outside BODY_LOCAL may change occlusion semantics; nameplate occlusion must be decided separately from body depth.
- Stabilizing position too aggressively can make the label feel disconnected from strong jumps/reactions.
- Creating a new global wrapper would regress Foundation ownership and is not acceptable.
