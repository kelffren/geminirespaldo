### PROBLEM
The live camera computes its dead-zone thresholds as `screenW * CONFIG.deadXRatio` and `screenH * CONFIG.deadYRatio`, then compares those values directly against WORLD-space player/camera deltas. The final world is later rendered by `engine-c.js` with `ctx.scale(CONFIG.zoom, CONFIG.zoom)`. Because the dead-zone sizes are not divided by zoom, the intended screen-space dead-zone fraction grows with zoom. `lookAheadDist` is likewise a world-space offset, so its visible screen-space magnitude grows with zoom. The result can make lateral camera composition and apparent avatar screen position materially different between mobile and desktop even with identical world motion.

### CONFIRMED_IN_GEMINI
Current `main` at the research start is `45354099b8a6d7a405a2987146e2a017e726715d` (`V6.52 drop modal lock scripts; force unlock movement`). `index.html` declares Kelo World V6.52 and loads `engine-a.js`, `engine-h.js`, `engine-z.js`, `engine-ab.js`, then `engine-ac.js`; no later camera owner was found in the inspected locomotion/render path.

`engine-a.js::updateCamera(dt)` uses:
- `deadW = screenW * CONFIG.deadXRatio`
- `deadH = screenH * CONFIG.deadYRatio`
- `deltaX = (localPlayer.x + camera.lookOffsetX) - camera.targetX`
- `deltaY = (localPlayer.y + camera.lookOffsetY) - camera.targetY`
The quantities being subtracted are world coordinates/world offsets, so `deadW/deadH` are effectively treated as world units.

`engine-c.js::render()` later applies `ctx.scale(z,z)` around the screen centre before translating by `camera.x/y`, with `z = CONFIG.zoom || 1`. Therefore a world-space dead-zone width of `D` appears as approximately `D*z` CSS pixels on screen.

`engine-z.js::applyZoom()` currently computes `z = screenW / (targetTiles * TILE)`, clamps zoom to `[1.05, 1.45]`, and clamps `CONFIG.lookAheadDist` from the initial 60 to 36 when it is above 40.

Using the current defaults (`deadXRatio = 0.10`, `deadYRatio = 0.08`) and `TILE=32`:
- 390px mobile: targetTiles=11 -> z≈390/(11*32)=1.108. Horizontal dead zone is 39 WORLD px -> ≈43.2 CSS px -> ≈11.1% of viewport width, not 10%.
- 1280px desktop: targetTiles=14 -> raw z≈2.857 -> clamped z=1.45. Horizontal dead zone is 128 WORLD px -> ≈185.6 CSS px -> ≈14.5% of viewport width.
- Current look-ahead after `engine-z` is 36 WORLD px, which appears as ≈39.9 CSS px at z≈1.108 and ≈52.2 CSS px at z=1.45.

Thus the same configured camera ratios do not represent the same screen-space composition across current zooms. DPR is not the cause of this specific mismatch; it exists in CSS/world units before backing-store DPR.

The current `scripts/live-hero-audit.mjs` measures hero motion/presentation but does not record camera.x/y, camera target, look offsets, zoom-normalized dead-zone sizes, avatar screen-space displacement from centre, or reversal camera overshoot. It therefore cannot currently reject this mismatch.

### EXTERNAL_EVIDENCE
Official Godot Camera2D documentation separates relative camera offset from position smoothing and exposes camera limits/dead-zone-style framing as camera-space concepts; see Camera2D docs: https://docs.godotengine.org/en/4.6/classes/class_camera2d.html

Official Unity Cinemachine documentation describes dead zones/soft zones as regions of the CAMERA FRAME and lookahead as prediction based on target motion. It also warns that lookahead can amplify noisy target motion and should be smoothed/reduced when it creates jitter. See:
- https://docs.unity3d.com/Packages/com.unity.cinemachine@2.6/manual/CinemachineUsing.html
- https://docs.unity3d.com/Packages/com.unity.cinemachine@2.6/manual/CinemachineBodyFramingTransposer.html

Godot's interpolation documentation recommends exponential, delta-aware smoothing (`1-exp(-speed*delta)`) for frame-rate-independent following; Kelo already uses this form for camera damping, so the issue here is not the damping formula itself but unit consistency/composition: https://docs.godotengine.org/en/4.4/tutorials/math/interpolation.html

Community counterevidence: dynamic/look-ahead framing is subjective and some top-down games intentionally keep asymmetric/speed-dependent framing; a fixed screen fraction is not universally required. Relevant discussion: https://www.reddit.com/r/gamedesign/comments/105ec6f/ and velocity-based look-ahead examples such as https://www.reddit.com/r/godot/comments/18638s4/. Therefore do not normalize camera units merely because the math differs; benchmark perceived stability/readability first.

### HYPOTHESIS
For Kelo World's current orthographic/pixel-art camera, normalizing camera dead-zone and look-ahead contracts to a declared coordinate space will make lateral motion feel more consistent between mobile/desktop and across zoom changes. The most conservative candidate is to preserve the current mobile feel as the reference and express dead-zone/look-ahead in screen-space CSS pixels (or normalized viewport fractions), converting to world units by dividing by the active zoom before `updateCamera` uses them.

A second hypothesis is that look-ahead should eventually use RESOLVED player motion (or a blend of intent and resolved motion) rather than raw input so collision-blocked intent does not dominate framing. Do not combine that with the unit-normalization experiment yet; isolate variables.

### DO_NOT_ASSUME
- Do not assume 10% is the aesthetically correct dead-zone fraction; it is simply the configured intent implied by `deadXRatio=0.10`.
- Do not assume desktop should feel exactly identical to mobile; larger viewports may benefit from deliberately different framing. If so, encode that difference explicitly in a camera profile rather than getting it accidentally through zoom multiplication.
- Do not assume look-ahead should be zero when blocked; that is a separate intent-vs-resolved-motion experiment.
- Do not infer success from world traces alone; this is a screen-space composition problem.
- Do not change `CONFIG.zoom` or DPR in the same candidate.

### RISKS
- Normalizing to a strict viewport fraction may make desktop feel too camera-active because the current accidental larger dead zone may actually feel comfortable on a wide monitor.
- Converting look-ahead to stable CSS pixels can reduce desktop forward visibility; a deliberate desktop profile may be preferable.
- Camera edge clamps can dominate measurements near world boundaries; separate central-world traces from edge traces.
- Pixel rounding (`CONFIG.roundPixels=true`) and zoom can create screen-space quantization; measure it but do not change it in this experiment.
- Frequent late wrappers exist in the project. Re-check current `main` and camera ownership immediately before implementation.
