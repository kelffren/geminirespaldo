### PROBLEM
Current `engine-a.js::updateMovement(dt)` continuously computes `localPlayer.squashX` and `localPlayer.squashY` from current speed with exponential smoothing, but the live PNG hero renderer in `engine-ab.js` draws a fixed-width/fixed-height sprite from `KELO_AVATAR_PRESENTATION`; it does not consume those squash values. This leaves a movement-responsive deformation signal in the core with no confirmed live visual effect.

At the same time, a newer late visual architecture already supports presentation-only `scaleX`, `scaleY`, `rotation`, and offsets around a semantic foot pivot: `src/visuals/animation-system.js` samples transform clips and `src/visuals/visual-integration.js` applies them around `KeloAnchors.get(actor,'foot')` before invoking the final `renderAvatar`. Locomotion currently does not appear to use that channel. Creating another movement wrapper for lean/squash would duplicate an existing transform responsibility.

### CONFIRMED_IN_GEMINI
- Current `main` round-start head: `591629319e5799ff361485eec3b9771de5e8670f`; `index.html` declares `Kelo World — V6.53`.
- `engine-a.js` initializes `localPlayer.squashX=1`, `squashY=1` and on every movement update computes approximately:
  - `squashX -> 1 + (currentSpeed/CONFIG.speed)*0.08`
  - `squashY -> 1 - (currentSpeed/CONFIG.speed)*0.06`
  using exponential smoothing `1-exp(-15*dt)`.
- With DIRECT movement the ratio is driven by actual current velocity relative to the current speed cap. At full stick this trends toward roughly 1.08 X / 0.94 Y; low analog magnitudes trend much closer to 1/1.
- `engine-ab.js` is the live PNG hero owner. `presentationOf()` derives fixed `visualWidth/visualHeight` from base size and `AVATAR_VISUAL_SCALE=1.15`, then `renderAvatar()` draws the selected source frame at that width/height around `footRootY`. In the live PNG path reviewed this round, no `p.squashX`/`p.squashY` is applied.
- `src/systems/armor-aura.js` wraps `renderAvatar` but also does not consume `squashX/squashY`; it sizes effects from radius + avatar presentation scale.
- `src/visuals/animation-system.js` already owns generic actor transform clips and exposes sampled `scaleX`, `scaleY`, `rotation`, `offsetX`, `offsetY`. It derives semantic anchors from `KELO_AVATAR_PRESENTATION`, including `foot`.
- `src/visuals/visual-integration.js` is loaded very late and wraps the final `renderAvatar`; when a transform exists it translates to the foot pivot, rotates/scales, translates back, then renders actor back FX -> avatar -> front FX. This is exactly the architectural location where presentation-only lean/squash can be tested without modifying collider/world motion.
- `src/visuals/visual-manifests.js` currently defines action transform clips (`cast_magic_01`, `cast_self_01`) but no locomotion transform clip. Therefore the locomotion channel exists in the controller priority table but is not yet used by current manifests for the normal lateral gait.
- `engine-ac.js` remains the owner of movement-derived visual state (`stridePhase`, gait, resolved distance, facing). It is a better signal source for any locomotion transform than adding another independent wall-clock oscillator.
- `ENGINE_MAP.md` remains stale in top-level version metadata, but explicitly says loaded code wins; it still identifies `engine-ac.js` as gait owner and `engine-ab.js` as visible hero owner.

### EXTERNAL_EVIDENCE
1. Godot's 2D documentation makes pivot location explicit: rotation/scaling behavior depends on the chosen pivot. That supports Kelo's existing foot-root transform architecture rather than center-scaling the full sprite.
   https://docs.godotengine.org/en/4.5/tutorials/2d/introduction_to_2d.html
2. Godot `Transform2D` documentation confirms scale/rotation/skew are one transform basis and that skew/distortion is a direct consequence of manipulating that basis. This supports treating lean/squash as a presentation transform with one clear owner.
   https://docs.godotengine.org/en/stable/classes/class_transform2d.html
3. Aseprite issue #1357 argues for per-frame/root pivots specifically for humanoids, alignment, sorting and attachments, with the point between the feet as a common root. This aligns with Kelo's exported `footRoot` and argues against deforming around the sprite center.
   https://github.com/aseprite/aseprite/issues/1357
4. Counterevidence/risk: Godot issue #57221 shows that combining non-integer motion and sprite rotation can create visible pixel jitter even when either operation alone is stable. Kelo already uses nearest-neighbor, fractional zoom and subpixel world motion, so runtime lean by arbitrary rotation is not automatically safe.
   https://github.com/godotengine/godot/issues/57221
5. Additional rendering risk: Godot proposal #6995 documents nearest-neighbor jitter under smooth/fractional motion, while current Kelo uses nearest-neighbor and non-integer zoom. Any transform test must therefore measure temporal silhouette/shimmer, not just perceived liveliness.
   https://github.com/godotengine/godot-proposals/issues/6995
6. Community evidence is mixed rather than universally pro-squash: a 2026 Godot thread shows squash/stretch/skew can make a 2D character feel much more alive without extra frames, but commenters also specifically warn that excessive squash looks wrong. This supports a very small measured effect, not the current theoretical 8%/6% deformation by default.
   https://www.reddit.com/r/godot/comments/1qgyvut/
7. Community foot-pivot evidence: a GameDev discussion on feet sinking during animation points to center pivots/height changes as a cause and recommends separating display sprite/pivot from hitbox. This is consistent with Kelo's physics-vs-presentation separation.
   https://www.reddit.com/r/gamedev/comments/v5p29e/

### HYPOTHESIS
The existing `squashX/squashY` calculations are legacy/dead presentation state in the current live PNG path. The right experiment is not to revive them inside `engine-ab.js` or add another render wrapper. Instead, if subtle lateral body deformation improves weight, feed a bounded locomotion transform through the already-existing foot-pivot visual transform architecture, driven by `engine-ac` movement state and tested against the current no-transform baseline.

A second hypothesis is that pure nonuniform squash at the current theoretical full-stick amplitude (about +8% X / -6% Y) is too strong for Kelo's authored pixel sprite and could damage silhouette/foot readability. A smaller body-local deformation or no deformation may win.

### RISKS
- Nonuniform scaling can distort pixel proportions and make the hero look rubbery, especially at 1.20x or fractional zoom.
- Rotation can amplify nearest-neighbor jitter under fractional motion/zoom.
- Transforming the whole wrapped actor may also transform front/back actor FX; that can be correct for body-attached FX but wrong for ground-local effects if layer ownership is not respected.
- Action transform clips have higher priority than locomotion; adding locomotion through the same controller must preserve channel arbitration and avoid pops when action/reaction clips take over then release.
- A core-state cleanup could break hidden legacy/fallback renderers even if the live PNG path ignores the values; removal requires explicit consumer trace.
