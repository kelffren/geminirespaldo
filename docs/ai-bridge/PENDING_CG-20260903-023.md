### PROBLEM

The current hero is simulated at floating-point world coordinates, but the production PNG renderer rounds the hero destination to whole world pixels before the final camera/zoom transform. Separately, the HiDPI layer advertises a physical-pixel-compatible zoom strategy, but a later-loaded zoom owner replaces it with viewport-derived zoom values that are usually non-integer in physical-pixel space. This creates a mixed sampling contract: world-space actor snapping plus fractional camera/physical scaling.

For lateral movement, especially at slow speed and high refresh rate, this can produce repeated rendered positions followed by jumps even when physical movement is continuous. Removing rounding blindly may trade judder for mixels/shimmer. The correct choice must therefore be measured in final screen/backing-pixel space, not inferred from world coordinates alone.

### CONFIRMED_IN_GEMINI

At base commit `41a9663fc23b1e56878457c642e903c3b2b08d0e`:

1. `engine-a.js` integrates `localPlayer.x/y` with floating-point `vx * dt` / `vy * dt`; camera follow also uses exponential float interpolation (`camera.x += (targetX-camera.x)*(1-exp(-dampX*dt))`, same for Y). There is no integer quantization in the simulation state.
2. `engine-ab.js` draws the production hero PNG using `Math.round(p.x - dw/2)` and `Math.round(footY - dh)` as the destination origin. The nameplate position is also rounded. Thus the body presentation is quantized to 1 world-pixel increments before the world transform.
3. `engine-c.js` renders the world with `translate(screen center) -> scale(CONFIG.zoom) -> translate(-camera.x,-camera.y)`. Camera coordinates remain fractional.
4. `engine-h.js` sets HiDPI backing size using DPR (capped at 3), disables image smoothing, sets `CONFIG.roundPixels=true`, and defines `pixelPerfectZoom(target)` so `(zoom * DPR)` is an integer physical scale.
5. `engine-z.js` loads later than `engine-h.js` and overwrites `CONFIG.zoom` using `screenW/(targetTiles*32)` clamped to 1.05..1.45. It does not preserve `pixelPerfectZoom` or consult DPR.
6. Therefore the final runtime zoom is commonly not a whole physical-pixel scale. Examples from current formulas, before LIVE measurement: viewport 390 CSS px -> zoom ~1.108; 430 -> ~1.222; 768/1440 cases can clamp to 1.45. At DPR 3 these correspond to physical scales ~3.324, ~3.665 and 4.35, not integers.
7. Because hero X is rounded in world space, a single quantization step projects to `zoom` CSS pixels. At current zoom bounds that is approximately 1.05..1.45 CSS px per world-pixel step, or ~1.05..4.35 backing pixels depending on DPR 1..3. This is a derived consequence, not yet a measured visual defect.
8. `CONFIG.roundPixels=true` is currently not an end-to-end contract: `engine-c.js` does not consult it when composing the camera transform, while `engine-ab.js` hard-rounds the actor regardless of the flag.
9. Code-responsibility scan: pixel-grid policy is split across `engine-h` (DPR + intended physicalScale), `engine-z` (final zoom), `engine-c` (world transform), and `engine-ab` (actor-only world rounding). This is duplicated/fragmented responsibility, but no refactor should occur before an A/B trace.

### EXTERNAL_EVIDENCE

1. MDN documents `imageSmoothingEnabled=false` as the standard way to retain hard pixels when enlarging pixel art. This supports keeping nearest-neighbor-style sampling, but it does not guarantee temporal smoothness or a coherent pixel grid when transforms are fractional.
2. Phaser's documented `roundPixels` behavior explicitly draws textured game objects at integer positions, and its camera follow documentation warns that sub-pixel jitter can be reduced with rounding but can still be broken by non-integer camera zoom. This is directly analogous to Kelo's current conflict between integer world placement and fractional final zoom.
3. A 2026 PixiJS fix/issue area around `roundPixels` and anchor offsets shows that pixel rounding has to account for the actual transformed/anchored render position; rounding only one component can still be wrong.
4. Community reports are contradictory in a useful way: some pixel-art projects eliminate blur by rounding draw coordinates; others report that rounding the actor while a camera moves fractionally produces staircase judder, especially diagonally/at low speed, and recommend preserving fractional simulation then resolving snapping coherently at the final render grid.
5. Recent community discussions also note that snapping in world space is not equivalent to snapping in screen space once zoom is non-1.0; a world-unit step can map to a fractional number of screen pixels.

### HYPOTHESIS

The current lateral feel can be improved without touching physics by establishing one coherent presentation-space sampling policy. The likely best candidate for modern phone/desktop screens is not simply `Math.round(worldX)`. A screen/backing-pixel-aware placement policy may preserve sharp edges while reducing irregular lateral steps, especially with fractional camera motion and DPR > 1.

However, strict authored pixel art may look better with integer physical scaling even if motion is slightly more stepped. Therefore both temporal smoothness and sprite fidelity must decide the result.

### PROPOSED_CHANGE

Do not refactor or ship yet. Instrument first, then compare the same trace:

**A — BASELINE_WORLD_ROUND**
- Current behavior: hero destination rounded to whole world pixels; current `engine-z` zoom.

**B — FLOAT_ACTOR_DESTINATION**
- Keep simulation/camera unchanged.
- Draw hero at floating destination coordinates.
- Keep `imageSmoothingEnabled=false`.
- Purpose: isolate how much judder comes from actor-only world rounding; reject if edge shimmer/mixels become worse.

**C — FINAL_PHYSICAL_PIXEL_SNAP**
- Keep actor and camera state as floats.
- Compute the hero's final projected screen/backing-pixel anchor after camera + zoom + DPR.
- Snap that final anchor to the physical-pixel grid (1 backing pixel), then map only the presentation offset back for drawing.
- Do not modify `p.x/p.y`, collision, stridePhase, or camera state.
- Foot root should be the anchor candidate, not arbitrary top-left, so future avatar scaling keeps feet stable.

**D — DPR-COMPATIBLE_ZOOM + FINAL SNAP**
- As an experiment only, quantize final zoom so `zoom * DPR` is integral or belongs to a deliberately allowed scale set, then use final-grid snapping.
- This may alter field of view and is therefore not a first production recommendation.

**E — DEFERRED HIGHER-RES/SEPARATE PRESENTATION SURFACE**
- Only if A/B/C/D cannot jointly preserve crisp sprites and smooth camera-relative motion. Do not introduce WebGL/WebGPU or a second render surface from this finding alone.

### DO_NOT_ASSUME

- Do not assume `Math.round()` is inherently wrong; for strict pixel art it can be the correct visual policy.
- Do not assume removing rounding fixes jitter; fractional zoom can convert that into shimmering/mixels.
- Do not force integer zoom globally without measuring camera framing and mobile field of view.
- Do not change physical `p.x/p.y`, `radius`, collision or stride to solve a presentation sampling problem.
- Do not combine this benchmark with CG-020 stride-credit fixes, CG-019 dead-zone changes, CG-021 reversal physics, or CG-022 visual-bounds changes. Use an identical world trace and change one presentation variable at a time.
- Do not treat `CONFIG.roundPixels=true` as proof the final runtime is pixel-perfect; current live owners do not implement one shared policy.

### EXPERIMENT

1. Record current HEAD, viewport, devicePixelRatio, `CONFIG.zoom`, backing-store size, camera.x/y and hero p.x/y each render.
2. Freeze animation frame/stride first so pose changes cannot contaminate temporal pixel comparisons.
3. Use a clear open-world patch and run constant horizontal RIGHT then LEFT movement at processed magnitudes 0.05, 0.10, 0.30, 0.60 and 1.00 for at least 4 seconds each.
4. Repeat diagonal RIGHT+UP and LEFT+UP because X/Y quantization can alternate visibly.
5. Run A, B and C with exactly the same recorded simulation/camera trace. D only after those are measured.
6. Test CSS viewports 390x844, 430x932, 768x1024 and 1440x900 with DPR-equivalent 1, 2 and 3 where harness allows.
7. Repeat presentation at 60/90/120 Hz-equivalent cadence or real high-refresh device when available.
8. Capture a small ROI around feet/body every frame and calculate projected anchor displacement, repeated-position frames, jump sizes and pixel-diff area.
9. Repeat winning policy at visual scale 1.00x, 1.15x and 1.25x without changing collider or camera trace.
10. Run a stationary-camera counter-test and a moving-camera test. A policy that only works with camera frozen is not acceptable.

### RISKS

- Float destinations with smoothing disabled can create uneven nearest-neighbor texel widths under fractional scaling.
- Physical-pixel snapping may still show judder if the backing pixel is large relative to perceived motion at DPR 1.
- Quantizing zoom can alter field of view and invalidate camera-composition tuning.
- At DPR 3, backing-pixel smoothness can look excellent while CPU/GPU fill cost remains high; this experiment must not be mistaken for a DPR performance endorsement.
- Future 1.25x avatar scaling can make sampling artifacts easier to see, so the winner at 1.00x must be re-tested after scale.
- Text/nameplates and semitransparent Aura may require a different sampling policy from the opaque sprite; do not force one snap rule onto all render layers.
