### PROBLEM
The current lateral gait correctly advances stride from actual resolved world distance, but its moving/on decision can remain true from input intent or requested velocity even when collision resolution produces essentially zero displacement. In that blocked state, stride phase no longer advances yet the current authored frame is retained. If the player reaches a wall in frame 0/1/3 and keeps holding LEFT/RIGHT into it, Kelo can potentially hold that unsupported mid-stride pose indefinitely instead of resolving to a planted/contact pose. This is a different state from release-stop: the input is still active, requested velocity is still high, but actual displacement is blocked.

### CONFIRMED_IN_GEMINI
1. `engine-a.js` LIVE movement is `DIRECT` after engine-ac configuration. Each update assigns `localPlayer.vx = input.normX * CONFIG.speed` and `vy` from intent before collision resolution.
2. Movement then applies X and Y position independently and resolves penetrations against obstacles by pushing the actor back. The collision path does not rewrite `localPlayer.vx/vy` to the resolved/real velocity after a blocked axis.
3. `engine-ac.js` computes `dist = hypot(p.x-lastX, p.y-lastY)` after movement and `spd = hypot(p.vx,p.vy)`. `physicallyMoving = dist > 0.12 || spd > 16`; `hasIntent = gait !== idle`.
4. Therefore while pressing into a wall, `hasIntent` remains true and/or `spd > 16` can remain true even when collision resolution makes `dist <= 0.12`. This keeps `v.on = true`.
5. Stride phase advances only when `lastStepDistancePx > 0`, so in a fully blocked hold phase does not advance. The code only resets to `PLANT_PHASE/PLANT_FRAME` when `!v.on`.
6. Resulting state is possible by code: `v.on === true`, requested speed nonzero, resolved distance ~0, frame retained indefinitely. If the retained frame is not the authored support/plant frame 2, the avatar can visually freeze in an unsupported stride pose while pushing the wall.
7. This is not a request to change physics responsiveness or collider behavior. The issue is presentation state classification: requested velocity/intent and resolved motion are different signals around collision.
8. Ownership scan: `engine-a.js` owns legacy physics/collision application; `engine-ac.js` owns gait/stride presentation through `KeloMovement`. No new wrapper/manager is justified.

### EXTERNAL_EVIDENCE
- Godot CharacterBody2D explicitly separates requested `velocity` from `get_real_velocity()` and `get_position_delta()`: the latter report movement that actually occurred after `move_and_slide()`. This is a direct precedent for distinguishing intent/requested motion from resolved motion in presentation logic: https://docs.godotengine.org/en/latest/classes/class_characterbody2d.html
- Godot's CharacterBody2D tutorial explains that collision response recalculates movement/velocity and that top-down `move_and_slide()` should reflect slowdown/slide after contact rather than treating the requested vector as identical to resolved motion: https://docs.godotengine.org/en/stable/tutorials/physics/using_character_body_2d.html
- Godot issue #75428 is useful counterevidence: even mature engines can have edge cases where reported velocity after wall/floor contact does not reflect the expected blocked component. This is why Kelo should measure position delta directly rather than trusting velocity alone for planted-state decisions: https://github.com/godotengine/godot/issues/75428
- Community discussion also distinguishes stored/requested velocity from `get_real_velocity()` when wall contact changes actual body motion: https://www.reddit.com/r/godot/comments/1garw7g/

### HYPOTHESIS
A collision-aware visual state based on resolved displacement, not requested velocity alone, will make wall contact feel more planted without changing gameplay. When strong movement intent persists but resolved displacement stays below a threshold for a short distance/time window, the lateral animation should settle to an authored contact/plant pose (or a dedicated push pose later) instead of freezing whichever stride frame happened to touch the wall. When sliding tangentially along a wall, cadence should continue from the actual tangential distance rather than incorrectly planting.

### PROPOSED_CHANGE
Do not modify production blindly. Benchmark these policies:
A. Baseline: current `hasIntent || spd>16` keeps visual motion ON; zero resolved distance freezes current frame.
B. Resolved-motion plant: preserve input/physics unchanged, but when intent is active and resolved distance remains <= MIN_VISUAL_MOVE_PX for a small measured window, mark presentation as `blockedPlant` and settle to PLANT_FRAME while preserving face from intent.
C. Axis-aware blocked plant: only plant when the intended dominant axis is actually blocked and tangential resolved movement is negligible. If diagonal input slides along a wall, continue phase from real tangential distance.
D. Dedicated authored push/contact pose only if B/C visibly improve grounding but the normal plant frame looks wrong under sustained input. Do not create new art before B/C prove need.

Keep current release-stop logic independent. Do not set gameplay vx/vy to zero merely for animation. Do not change collision radius, movement speed, joystick, camera, or stride-cycle constants in this pass.

### DO_NOT_ASSUME
- Do not treat `p.vx/p.vy` as resolved velocity under the current engine-a collision path.
- Do not classify every low-distance frame as blocked; very low-speed walk, frame quantization, or normal subpixel motion can produce tiny deltas.
- Do not plant while the character is successfully sliding along a wall; actual tangential travel should continue driving stride.
- Do not alter collision response to satisfy presentation.
- Do not add a second movement owner or wrapper.
- Do not assume PLANT_FRAME=2 is visually correct for sustained push until captured; it is only the current authored plant contract.

### EXPERIMENT
Create a deterministic obstacle reproduction using an existing vertical wall/AABB. For LEFT and RIGHT separately:
1. Approach wall at walk magnitude 0.48, threshold 0.70, and max 1.00.
2. Record the exact frame/phase at first collision.
3. Continue holding directly into the wall for 0.5 s, 1 s and 2 s.
4. Repeat with diagonal input at 15°, 30° and 45° into the wall so the actor can slide tangentially.
5. Repeat release after blocked hold and immediate reversal away from wall.
6. Test at 60/90/120 Hz and 390x844 DPR2, 844x390 DPR2, 1280x720 DPR1.

Instrumentation per update/render: requested input vector, requested vx/vy, pre-collision proposed delta, post-collision x/y, resolved dx/dy/dist, collision pushX/pushY or blocked-axis evidence where accessible, visual `on`, face, gait, stridePhase, frame, blocked duration, and rendered frame.

### RISKS
1. A naive timeout can plant during legitimate very-slow movement or temporary subpixel stalls. Prefer resolved-distance plus collision/blocked-axis evidence if cheaply available.
2. Snapping directly to frame 2 can itself create a visible pose jump. If so, test phase-aware shortest transition or a dedicated contact pose only after measuring the jump.
3. Diagonal wall slide is the main false-positive risk. Use actual resolved tangential distance as the deciding signal.
4. Collision pushes can produce tiny corrective deltas that look like motion numerically. Threshold should be benchmarked in CSS/world terms, not guessed.
5. If future server-authoritative movement changes vx semantics, keep the presentation contract defined around resolved displacement rather than specific legacy velocity fields.
