### PROBLEM
The current production hero and generic appearance renderers expose a semantic foot/shadow anchor but no longer preserve the legacy contact shadow that visually planted the primitive avatar to the floor. Reintroducing a shadow naively inside renderAvatar would create a second problem: Kelo's prop-occlusion system can intentionally call renderAvatar again in the same frame, so an embedded shadow can be overdrawn/darkened or appear on the wrong depth layer. Before increasing avatar scale to 1.20x or adding vertical/horizontal bob, grounding must become a separate once-per-actor layer tied to the world footRoot.

### CONFIRMED_IN_GEMINI
1. Current main was re-read at BASE_COMMIT 950f0536c9944367c1b9aeca7125f1fafd401652. The newest commit removes a Plaza fountain asset; engine-a.js, engine-c.js, engine-ab.js, engine-ac.js and character-appearance.js retain the locomotion/render contracts inspected here.
2. engine-a.js legacy renderAvatar draws a contact ellipse before the primitive actor: center=(p.x,p.y+14), rx=p.radius*0.9, ry=p.radius*0.45, alpha via rgba(0,0,0,0.4).
3. engine-ab.js replaces renderAvatar when hero.PNG is ready. It draws the processed hero sprite and nameplate but does not call the legacy renderer in the successful sprite path, so the legacy contact ellipse is not preserved there. engine-ab nevertheless exposes shadowAnchorX/shadowAnchorY in KELO_AVATAR_PRESENTATION, equal to the semantic footRoot.
4. src/characters/character-appearance.js also replaces the renderer for non-legacy appearances such as bot_crimson_v1 and draws the sprite + nameplate without a contact shadow. It uses per-frame foot anchors correctly but does not consume shadowAnchor.
5. engine-c.js already has an explicit render order: world/groundFX -> belowActor -> drawPreActors -> actors -> worldFX -> drawPostActors -> foregroundFX. This gives Kelo a natural place for grounding that is outside the sprite body renderer.
6. src/environment/generic-props.js uses occlusion mode actor-base-y-redraw-v1 to call renderAvatar(actor, ...) again for overlapping actors in front of selected props. Therefore putting a semi-transparent shadow inside renderAvatar can draw the same shadow twice in one frame, making it darker and potentially placing it above a foreground prop.
7. src/visuals/visual-system.js defines a belowActor world layer, but the current API draws generic world FX there; it does not perform a once-per-visible-actor grounding pass.
8. scripts/live-hero-audit.mjs validates visual scale, footRoot, collider, lateral/reversal/release/diagonal movement and aura scale, but it has no assertion that a contact shadow exists, is anchored to footRoot, is drawn once, or remains stable through occlusion redraws.
9. engine-ac.js remains distance-driven and should not be changed for this experiment. The proposed grounding layer is presentation-only.

### EXTERNAL_EVIDENCE
- Godot's official 2D lights/shadows documentation separates shadow casting/occluders from sprite rendering and drawing order; this supports treating shadows as a layer concern rather than embedding them inseparably in the body sprite.
- Unity's current 2D Shadow Caster documentation likewise treats shadow shape/casting as a rendering component separate from sprite gameplay physics.
- r/gamedev community discussion consistently identifies a simple circular/blob shadow under a 2D character as the cheapest/common grounding solution; another HD-2D discussion specifically notes that a shadow disconnected from the foot makes a sprite read as floating.
- Godot GitHub issues #74265, #78964, #105110 and #111463 document real ordering/self-shadow complications with more physically dynamic 2D shadow systems. Counterevidence: dynamic light-cast shadows can look richer and may be desirable later, but they add ordering/occluder complexity that is unnecessary for solving Kelo's immediate contact-grounding problem.
- Community counterevidence also notes that sprite-cast/projected shadows can expose the flatness of billboarded/HD-2D characters. This argues for a restrained contact blob first, not a full silhouette projection.

### HYPOTHESIS
A subtle, stable contact shadow rendered exactly once per visible actor at the semantic footRoot will improve lateral grounding and make a future 1.20x avatar feel more planted without modifying collision, stride, camera or physics. The shadow should stay on the ground while any later body bob/lean offsets move only the sprite. It should not be emitted from renderAvatar because renderAvatar is not guaranteed to execute exactly once per actor per frame.

### PROPOSED_CHANGE
Do not ship a shadow change yet. First add an audit-only grounding pass and compare three candidates:
A. Legacy-radius blob: preserve the old footprint proportions from engine-a.js, but center it on layout.shadowAnchor/footRoot.
B. Presentation-width blob: derive width from truthful appearance/presentation bounds after CG-026 instrumentation, with a conservative fixed aspect ratio.
C. Authored appearance metadata: optional shadowWidth/shadowHeight/shadowOffset/alpha per appearance, with fallback to B.

Architectural requirement for all candidates:
- collect the actors that the primary actor pass will draw;
- render their contact shadows once before body sprites, preferably in one batched Canvas2D path/fill when style is identical;
- never render the contact shadow from renderAvatar itself;
- keep shadow world position at footRoot/shadowAnchor, independent of frame pivot, stride phase, bob, lean or sprite visual scale transform;
- cull with the same actor visibility envelope used for normal rendering;
- let body re-render/occlusion passes redraw body/nameplate only, not grounding.

A possible API shape is KeloCharacterGrounding.drawAll(ctx, actors) called immediately before the primary actor draw pass, or an equivalent actor-aware belowActor hook. Do not overload generic transient KeloFX unless the grounding lifetime/once-per-frame semantics are explicit.

### DO_NOT_ASSUME
- Do not assume a larger sprite needs a proportionally larger collision radius.
- Do not assume the shadow should scale exactly 1.15 -> 1.20 with the body; feet/contact footprint may need a smaller change.
- Do not animate the shadow vertically with body bob. It represents floor contact.
- Do not infer shadow position from frame top/bottom after per-frame cropping; use the semantic footRoot/source foot-pivot contract.
- Do not add blur filters, Canvas shadowBlur, dynamic light occluders or per-pixel silhouette projection in the first experiment.
- Do not put shadow drawing into renderAvatar until duplicate redraw behavior is eliminated or shadow emission is provably idempotent.
- Do not claim the current live hero visibly lacks grounding until a LIVE screenshot/audit confirms the code-path result; the code confirms the legacy ellipse is bypassed, not the user's subjective perception.

### RISKS
- Adding the blob inside renderAvatar is deceptively simple but can double-darken under prop actor redraws.
- Using tight per-frame visible bounds for shadow width can make the shadow pulse with every pose; use a stable appearance envelope or authored footprint instead.
- A shadow that is too dark/large can read as a hole or UI ring and reduce HD-2D quality.
- A shadow that follows visual bob defeats grounding and reintroduces floating.
- Full dynamic 2D shadows add occluder/order/self-shadow complexity and are not justified until the simple contact-shadow baseline is measured.
- If 32 actors are common, unbatched alpha ellipses can create unnecessary state changes/overdraw; benchmark before choosing the implementation.
