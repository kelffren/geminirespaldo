### PROBLEM
Current `main` has an analog walk/run progression for touch but not for desktop keyboard. `engine-a.js::processInput()` converts any non-zero WASD/arrow combination to a normalized unit vector (`input.normX/Y = k / hypot(kx,ky)`). Therefore cardinal and diagonal keyboard movement both have processed magnitude exactly 1. `engine-ac.js::gaitFrom()` classifies any magnitude >= 0.70 as `run`, so ordinary desktop WASD skips the entire walk region and immediately enters run. Touch input, by contrast, maps joystick displacement through deadzone-remapped magnitude 0..1, so it can produce idle -> walk -> run continuously. This means the current desktop audit is not testing the same gait space as mobile, and the requested idle↔walk↔run polish cannot currently be evaluated on keyboard from normal user input.

### CONFIRMED_IN_GEMINI
1. Current `main` at the start of this round is `bbb3319581b11bccf3d5e24d2c01d0ac4df64519`; its head commit only appended CG-031 bridge research, not locomotion code.
2. `index.html` is currently `Kelo World — V6.33` and loads `engine-a.js?v=149`, `engine-ab.js?v=240`, `character-appearance.js?v=2`, and `engine-ac.js?v=222`. `ENGINE_MAP.md` is older (V6.16 audit), so live load order/code wins.
3. `engine-a.js::processInput()` builds digital `kx/ky` from WASD/arrows and, whenever either is non-zero, normalizes the vector by its length. Thus D = (1,0), A = (-1,0), D+S = (1/sqrt(2),1/sqrt(2)); every keyboard combination has `hypot(normX,normY)=1`.
4. Touch does not use that digital normalization path. It computes joystick distance, removes the deadzone, remaps the remaining radius to a magnitude in [0,1], then multiplies the unit direction by that magnitude. With the current `engine-ac.js` overrides (`joystickRadius=72`, `joystickDeadzone=0.045`, LINEAR), touch can occupy the full analog magnitude continuum.
5. `engine-ac.js` defines `GAIT_IDLE_MAX=0.03` and `GAIT_RUN_START=0.70`; `gaitFrom(1)` is always `run`. There is no keyboard-specific walk modifier or keyboard magnitude state in the searched current code.
6. At magnitude 1, `speedFor(1)` returns `MAX_SPEED = 178 + (1-0.74)*28 = 185.28`, and target speed is magnitude * cap, so keyboard immediately requests ~185.28 world px/s under DIRECT movement.
7. `MOV-CADENCE-V2` already removed the prior hard 50->90 px stride-length discontinuity at the walk/run boundary: the run cycle starts at 50 px at magnitude 0.70 and grows continuously toward 90 px at magnitude 1. The remaining issue in this entry is input-source coverage/transition semantics, not that old cadence jump.
8. `scripts/live-hero-audit.mjs` drives both its mobile and desktop contexts with `page.keyboard.down('d'/'a'/'s')`. Even the `isMobile:true, hasTouch:true` context uses keyboard events for the dynamic trace. Therefore the current 'mobile' gait audit also exercises magnitude 1/run rather than the real analog touch walk band.
9. No new relevant Grok response exists after `GC-20260831-003`, so there is no implementation evidence that already adds keyboard gait selection or analog-touch gait coverage.

### EXTERNAL_EVIDENCE
- MDN documents browser keyboard input as discrete `keydown`/`keyup` key interactions; modifiers are boolean states. This matches Kelo's current key-state implementation and provides no ordinary key-pressure magnitude: https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent
- MDN documents `Gamepad.axes` as floating-point values from -1.0 to 1.0, illustrating the continuous axis model that analog controls can provide and digital keys normally cannot: https://developer.mozilla.org/en-US/docs/Web/API/Gamepad/axes
- PCSX2 issue #12500 describes the same practical constraint when mapping keyboard to analog controls: standard keyboard input is effectively full-off/full-on, motivating a separate pressure/range modifier instead of pretending digital keys provide native analog magnitude: https://github.com/PCSX2/pcsx2/issues/12500
- A GameDev community discussion recommends explicit sprint/walk modifiers or toggles for mouse+keyboard because keyboard movement is binary while controller movement can represent 0..1 magnitude. It also provides useful counterevidence: artificial keyboard acceleration can feel laggy, so Kelo should not introduce a ramp solely to imitate a stick without measuring responsiveness: https://www.reddit.com/r/gamedev/comments/z679sx/
- Community feedback around games that quantize analog movement into only slow/fast thresholds reports immersion/control loss from abrupt walk↔run switching. This is not proof of the best Kelo policy, but it reinforces preserving genuine analog progression on touch rather than degrading it to keyboard-like states: https://www.reddit.com/r/oblivion/comments/1k6id8c/movement_speed_with_analog_stick_issue/

### HYPOTHESIS
Part of the desktop lateral movement feeling harsher than mobile is not necessarily a sprite defect: desktop normal input has no natural walk band and therefore transitions from idle directly to the fastest run state. More importantly, current QA cannot compare idle->walk->run across mobile and desktop because its mobile context is still controlled with keyboard events. Before tuning run lean, bob, transition timing, or 1.20x scale, Kelo needs source-aware gait traces and an explicit decision about keyboard walk/run semantics.

A secondary hypothesis is that we should NOT automatically emulate analog stick pressure by slowly ramping keyboard magnitude. DIRECT movement was deliberately chosen, and a forced ramp can trade visual softness for input latency. The correct keyboard policy may instead be an explicit walk/run modifier/toggle, or preserving full-speed WASD while treating walk as an accessibility/exploration mode.

### RISKS
- Adding a keyboard ramp can make the game feel mushy and undo the deliberate DIRECT control choice.
- A walk modifier may conflict with future combat/sprint/targeting bindings, so key assignment is a product/input-map decision rather than a hardcoded research conclusion.
- If the mobile audit continues using keyboard events, future gait tuning can accidentally optimize for desktop behavior while being reported as mobile evidence.
- Making desktop and touch physically identical is not necessarily desirable; input-source parity should mean equivalent intent and quality, not identical hardware semantics.
- Any later 1.20x avatar scale will magnify abrupt gait-state transitions, so this input-source gap should be measured before using scale A/B screenshots to judge locomotion polish.
