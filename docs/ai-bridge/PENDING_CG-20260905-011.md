### PROBLEM
The 1.15x visual-only avatar scale and Armor Aura visual-radius follow-up are present on current main, and the static mobile/desktop hero gate verifies scale/collider/foot-root invariants. However, the gate did not yet exercise the enlarged avatar through the user's highest-priority locomotion cases: RIGHT motion, immediate RIGHT->LEFT reversal, release/plant and diagonal movement. A static PASS therefore could not establish that the 1.15x presentation remains invariant while locomotion state changes.

- `engine-ac.js` remains gait owner: processed input magnitude drives gait/speed, stride phase advances from actual world distance, MOV-STOP-V2 resets release to visual frame 0, and `reversalAccidentalIdleCount` is exposed in `KELO_MOVEMENT_AUDIT`.

### EXTERNAL_EVIDENCE
- MDN `requestAnimationFrame()` documentation warns that animation progress must be time-based because callback frequency generally follows display refresh rate and high-refresh 120/144 Hz displays are common. This supports keeping locomotion validation focused on world-distance/state invariants rather than assuming render-frame counts.
- MDN `imageSmoothingEnabled` documents that disabling smoothing preserves pixel sharpness when images are enlarged, supporting the current Canvas2D scale path while not proving temporal stability.
- Community counterevidence from recent pixel-art/game-dev reports shows cardinal movement can look acceptable while diagonal/subpixel movement jitters even with fixed timestep, interpolation and point filtering. Therefore static crispness is insufficient evidence for dynamic quality.

### HYPOTHESIS
A short deterministic dynamic trace inside the existing LIVE hero gate can close the largest objective part of the 1.15x experiment without changing gameplay. If RIGHT, immediate LEFT reversal, release and diagonal motion all preserve visualScale/collider/footRoot invariants, do not introduce accidental idle, and settle to planted frame 0, then the 1.15x scale is materially safer to KEEP while visual/shimmer/depth inspection continues separately.

### PROPOSED_CHANGE
Implemented on main in commit `3c70555f67b767fc7b4882ea16d1202e8f785e33` (`test: add dynamic lateral hero trace to live audit`).

The existing `scripts/live-hero-audit.mjs` now:
- waits for `KELO_MOVEMENT_AUDIT`;
- samples baseline, RIGHT, immediate LEFT reversal, release, diagonal down-right and final release;
- uses short 220ms movement holds to stay near spawn and minimize environment-collision interference;
- asserts at every sample that visualScale remains 1.15, colliderRadius remains `player.radius`, and footRoot remains exactly +10Y from physicsRoot;
- requires positive RIGHT motion, positive LEFT reversal motion and two-axis diagonal motion;
- requires `reversalAccidentalIdleCount` not to increase;
- requires both releases to settle with `visualOn=false` and `visualFrame=0`;
- records release-count delta and movement distances into `hero-live-audit.json`;
- adds post-dynamic-trace mobile/desktop screenshots.

No production movement, sprite, camera, collider, scale or aura code changed in this increment.

### DO_NOT_ASSUME
- A passing headless keyboard trace does not prove physical touch joystick quality; touch remains a separate path.
- A passing DPR1/DPR2 trace does not prove 90/120 Hz temporal smoothness; Playwright headless timing is not a high-refresh-display benchmark.
- `visualFrame=0` is the current MOV-STOP-V2 planted convention, not proof that authored frame 0 is the best biological/contact pose. Contact-frame semantics still need source/visual evidence.
- Short movement near spawn reduces collision interference but is not a complete depth/occlusion route through fountain/buildings/props.
- Do not increase to 1.25x until the 1.15x dynamic gate and visual depth/shimmer checks are accepted.

- `rightDistancePx` > 8
- `reversalDistancePx` > 8
- `abs(diagonalDxPx)` > 4

- `reversalAccidentalIdleDelta = 0`

- release/final release `visualFrame=0`
- dynamic `visualScale = 1.15` at every sample
- dynamic `colliderRadius == player.radius` at every sample
- dynamic `footRootY - physicsRootY = 10` and X drift 0 at every sample
- browser console/request/HTTP errors = 0
- screenshots available for both mobile and desktop
- later temporal benchmark: frame-time P50/P95/P99 and screen-space jitter at 60/90/120 Hz where real hardware/browser measurement is available.

### RISKS
- Synthetic keyboard input in a mobile-emulated browser validates movement-state invariants, not touchscreen ergonomics/latency.
- A nearby obstacle could reduce one movement leg; short holds make this less likely but a failure must be inspected rather than automatically blamed on 1.15x.
- Release settling after 140ms depends on the current hard-stop/MOV-STOP behavior. If timing changes intentionally, the gate threshold should be updated together with documented rationale.
- This adds several hundred milliseconds per viewport to LIVE QA but no runtime production cost.
- It still does not quantify visual shimmer or high-refresh frame pacing.
