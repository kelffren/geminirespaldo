### PROBLEM

Current actor identity rendering has no single stable presentation contract. `engine-c.js` wraps the then-current `renderAvatar()` to add the local player's title (`Caballero`), but `engine-ab.js` loads later and replaces `renderAvatar()`. While the PNG is not ready, `engine-ab` delegates to its captured previous renderer; once `hero.PNG` is ready it draws the production sprite and name itself and does not call that captured renderer. Therefore the title wrapper can be present during fallback/loading and absent in the stable PNG path. At the same time, the player name is drawn inside the world transform with a hard-coded `11px` font and a Y position tied directly to current sprite draw height. Landmark depth wrappers then re-call `renderAvatar()`, so identity text inherits actor world zoom, actor depth/occlusion, and duplicate redraw behavior.

This becomes a first-order problem before scaling Kelo to 1.15x/1.25x: body scale, name readability, title visibility, landmark occlusion, crowd overlap and collider size are currently not independent contracts.

### CONFIRMED_IN_GEMINI

At base commit `2f6423ae0185620fc99ef7dc95ec502d56e003ca` / V6.20:

1. `index.html` loads `engine-c.js` before `engine-ab.js`.
2. `engine-c.js` captures the previous `renderAvatar` in `_renderAvatar`, calls it, then draws the local title with `ctx.font='9px sans-serif'` at `p.y - p.radius - 18`.
3. `engine-ab.js` later captures the then-current renderer as `_av`, then replaces `renderAvatar` again.
4. In `engine-ab.renderAvatar`, the fallback path is `if (!ok || !p || !sheet) return _av(p,isSelf)`, so the old wrapper/title can execute before the PNG is ready or when sprite rendering falls back.
5. In the production PNG path, `engine-ab` does not call `_av`; it draws the sprite directly and then draws only `p.name || 'Kelo'` with `ctx.font='bold 11px sans-serif'`. Therefore `engine-c`'s local title is bypassed once `ok && sheet` is true.
6. The production name Y is `footY - dh - 6`, where side draw width is 48, non-side width is 54 and `dh` is derived from the current atlas aspect ratio. Identity position is therefore coupled to sprite geometry, not to a separate visual envelope/nameplate anchor.
7. `engine-c.render()` establishes the world transform (`translate center -> scale(CONFIG.zoom) -> translate(-camera)`) before avatars are rendered. Canvas text is therefore world-scaled along with the avatar.
8. With an 11px world-space font, final CSS-space text height is approximately 11*zoom before rasterization details. At zoom 1.05-1.45 this is ~11.55-15.95 CSS px. The same player name therefore changes apparent size with camera zoom.
9. `plaza-depth.js` re-calls `renderAvatar()` for actors near the fountain during back/actor/front composition and can call it again for actors in front. Because the label lives inside `renderAvatar`, the name is also redrawn and inherits the same landmark depth decision.
10. `plaza-depth.js` still uses collider radius for overlap and `actor.y` for depth; CG-20260903-022 already covers that body/depth-root issue. This entry does not repeat that proposal; it isolates identity/nameplate ownership.
11. `engine-ac.js` does not own name/title presentation and should not be expanded to do so; its current responsibility is movement/gait/stride.
12. `ENGINE_MAP.md` is stale relative to the inspected main: it says audit base V6.16 while current `index.html` is V6.20. Code wins where the map conflicts.

### EXTERNAL_EVIDENCE

1. MDN Canvas2D `scale()` documents that scaling changes the size of canvas units, so text painted under the same current transform is scaled too. Source: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/scale
2. MDN `measureText()` provides `TextMetrics` including measured width, allowing nameplate layout/overlap metrics instead of assuming every name occupies the same width. Source: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/measureText
3. MDN `fillText()` supports an optional maximum width, confirming Canvas2D can constrain long labels without changing world physics. Source: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/fillText
4. A real Minecraft/Pehkui bug report documents player nameplates being affected by multiple independent scales, causing labels to clip into small characters or move far above large ones. This is not Kelo's engine, but it is direct counterexample evidence against deriving identity transforms from multiple unrelated scale owners. Source: https://github.com/Virtuoel/Pehkui/issues/364
5. A nameplate issue from KuiNameplates documents zoomed-out labels blocking other important icons, showing that zoom-dependent label footprint can become a readability/occlusion problem. Source: https://github.com/kesava-wow/kuinameplates2/issues/284
6. A current community discussion on Unreal nameplates describes the tradeoff: world-space labels can blur/move with the world and be naturally occluded, while screen-space labels remain sharp but require explicit occlusion/distance policy. Source: https://www.reddit.com/r/unrealengine/comments/1klz0mf
7. Counterevidence: keeping labels in world space can be desirable because they stay diegetically anchored and naturally respect world occlusion. The proposal is therefore not "move all text to UI"; it is to benchmark a stable identity layer and choose an explicit policy.

### HYPOTHESIS

Kelo will scale more cleanly if actor identity becomes a separate, render-pure presentation layer derived from a stable head/visual-envelope anchor rather than being embedded inside body rendering. The body may remain world-space and depth-occluded, while name/title text can use a deliberate policy: either world-space with a clamped font/spacing contract or screen-space projection with explicit visibility/occlusion rules. For the first experiment, no physics, movement, camera or landmark-depth behavior should change.

The minimum expected benefit is deterministic identity: the same name/title set must remain present before and after `hero.PNG` becomes ready, and repeated body redraws must not multiply or unpredictably occlude the identity layer.

### PROPOSED_CHANGE

**P1 — Instrument current identity behavior before changing it**
- Record whether `name` and `title` were drawn for each actor and from which wrapper/path.
- Record draw count per actor per RAF and whether identity changes when `hero.PNG` flips from fallback to production.
- Freeze movement/camera for the load transition test so only renderer ownership changes.

**P2 — Define one actor presentation metric contract**
- Reuse/extend the CG-022 presentation metrics concept, but keep identity fields separate from physics.
- Candidate fields: `footRoot`, `visualTopY`, `visualBounds`, `nameAnchorWorld`, `presentationScale`, `identityVisible`.
- Do not derive title position from `p.radius` and name position from unrelated `dh` in different wrappers.

**P3 — Give name/title one owner**
- Candidate architecture: body renderer returns/uses presentation metrics; a dedicated identity pass draws name + optional title exactly once per visible actor after the intended world-depth body composition.
- Remove neither old wrapper until baseline proves which outputs must be preserved.
- Repeated body redraws for fountain/Gardens must not create additional identity contributions.

**P4 — Benchmark two explicit label spaces**
- B1: world-space anchor but font size/offset clamped to an intentional visible range.
- B2: project `nameAnchorWorld` to screen space and draw identity after restoring the world transform, with explicit occlusion/visibility policy.
- Do not assume B2 wins. World-space may look more integrated; screen-space may be more readable.

**P5 — Long-name/crowd safety**
- Use `measureText()` instrumentation to record actual label widths.
- Test representative short/medium/long names and 1/10/25/50 visible actors.
- Candidate policies only after measurement: max width, truncation, priority for local/targeted actors, vertical separation, distance fade/cull. Do not add all of them blindly.

**P6 — Larger avatar scale matrix**
- After identity is deterministic at 1.00x, rerun at body presentationScale 1.15 and 1.25 with collider fixed at 20.
- Name/title visual size should not accidentally grow 1.25x merely because body size grows unless A/B evidence prefers that.
- Anchor gap above the visual silhouette should remain stable in screen pixels or a deliberately chosen world-space contract.

### DO_NOT_ASSUME

- Do not treat `engine-c` title disappearance as a user-visible bug until the load/fallback transition is reproduced; the code path is confirmed, visibility severity is not.
- Do not move identity to DOM/HTML merely because it is UI-like; Canvas2D can render a separate screen-space pass without DOM churn.
- Do not make nameplates ignore all world occlusion automatically; that can expose actors through walls/landmarks and increase clutter.
- Do not scale collider radius with the body or nameplate.
- Do not couple nameplate font size directly to avatar presentationScale in the first test.
- Do not refactor `engine-c` + `engine-ab` + depth wrappers wholesale. Baseline -> one ownership change -> same trace -> re-measure.
- Do not use the current stale ENGINE_MAP as authority where V6.20 code disagrees.

### RISKS

- Screen-space labels can reveal actors that the world should hide unless occlusion is modeled explicitly.
- World-space labels can become too small/large or blurry as zoom changes.
- Long-name collision avoidance can become O(n^2) if implemented naively for crowds; benchmark before adding pairwise layout.
- A dedicated identity pass changes layer ordering; screenshots must verify that labels do not cover menus, important VFX or architecture incorrectly.
- Removing the old title wrapper without preserving intended local title semantics can silently lose product information.
- Larger avatars may increase head/top overlap with nearby actors even if identity rendering itself is fixed.
