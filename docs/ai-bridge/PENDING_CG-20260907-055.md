### PROBLEM
The current stop path solves one real problem — it no longer leaves the hero frozen indefinitely in an arbitrary walk pose — but the default MOV_STOP_V2 path can replace that failure mode with a different one: an immediate discrete pose snap on the first update where movement ceases.

The LIVE audit waits 140 ms after key release and then verifies only that the final state is planted. It does not sample the first render/update after release, does not record the pre-release frame-to-post-release frame delta, and does not measure visible support-foot displacement. A visually abrupt stop can therefore pass the current audit.

### CONFIRMED_IN_GEMINI
At BASE_COMMIT 0c99dc2418a674752fbccbaffbca9301b41da649:

1. `engine-ac.js` declares `DEFAULT_PLANT_FRAME = 2`, `PLANT_PHASE = 0.5`, `VISUAL_STOP_HOLD_SEC = 0.075`, and defaults `MOV_STOP_V2` to enabled unless `?movStopV2=0`.
2. `updateVisualMotion()` computes `hasIntent = gait !== 'idle'` and `physicallyMoving = dist > 0.12 || spd > 16`.
3. When neither is true and MOV_STOP_V2 is enabled, it immediately sets `v.stopElapsed = VISUAL_STOP_HOLD_SEC`, `v.on = false`, `unsupportedPoseFreezeMs = 0`, and `releaseToStablePlantMs = 0`.
4. Later in the same function, `!v.on` immediately resets `stridePhase = PLANT_PHASE`, `strideDistancePx = 0`, and `frame = PLANT_FRAME`.
5. Therefore a release from frame 0, 1, or 3 can become frame 2 in one update. The code records `lastReleaseFromFrame/Phase`, but does not measure or constrain this transition jump.
6. With `CONFIG.movementType='DIRECT'`, the wrapped core movement in `engine-a.js` sets velocity directly from input. On a processed zero-input update, velocity becomes zero before `updateVisualMotion()` runs, so the immediate stop branch can be reached without a physical deceleration tail.
7. `engine-ah.js`, loaded after `engine-ac.js`, wraps `updateMovement()` again and hard-zeros `vx/vy` whenever no movement input exists. Under the current DIRECT path this is partly redundant ownership and should not be refactored blindly, but it confirms stop responsibility is split across wrappers.
8. `scripts/live-hero-audit.mjs` holds RIGHT/LEFT, releases the key, waits 140 ms, then calls `assertPlantedRelease()`. That assertion checks final `visualOn=false`, `visualFrame===plantFrame`, `stridePhase===plantPhase`, and zero retained stride distance, but never observes the first post-release transition.
9. `engine-ab.js` consumes `v.frame` directly as the source column. Therefore a one-update `frame N -> frame 2` change is an actual spritesheet pose switch, not merely telemetry.

Relevant redundancy/ownership observation: `VISUAL_STOP_HOLD_SEC` remains meaningful for the legacy `MOV_STOP_V2=false` branch, but the default V2 branch writes the hold duration and disables visual motion immediately, so it is not currently a visible settling window. Stop behavior is distributed between `engine-ac.js`, the core DIRECT movement in `engine-a.js`, and the later `engine-ah.js` hard-stop wrapper.

### EXTERNAL_EVIDENCE
- Unity Animator transitions explicitly support exit time, transition duration, and destination time offset. This is evidence that production animation systems treat the timing and phase of state transitions as first-class data rather than assuming an arbitrary immediate frame replacement is always visually correct: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animations.AnimatorStateTransition.html
- Unity `Animator.CrossFade` preserves the idea of a controlled transition duration and normalized destination offset: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animator.CrossFade.html
- Godot AnimationTree documents Immediate, Sync, and At End transition modes; Sync specifically switches states while seeking the new state to the previous playback position, again showing that continuity/phase is a separate design choice: https://docs.godotengine.org/en/4.x/tutorials/animation/animation_tree.html
- Community counterexample: a 2024 Godot discussion reports visible flicker/abrupt switching when releasing walk input at certain animation phases. The author tried waiting for frame progress >0.9, but reported that this harmed responsiveness. This is useful counterevidence against simply forcing every stop to wait until the end of a cycle: https://www.reddit.com/r/godot/comments/1dhb02v/
- A 2026 gamedev discussion about animated-sprite foot sliding reinforces matching visual foot travel/cadence to world travel, while also showing that extra animation constraints can be over-engineered if the perceptual artifact is already negligible: https://www.reddit.com/r/godot/comments/1rxgqwb/

### HYPOTHESIS
The current immediate `frame -> PLANT_FRAME` reset can produce a perceptible stop-pop, especially during lateral motion when release happens on a frame whose visible support geometry differs materially from frame 2. The artifact is likely easier to see after increasing avatar scale to 1.20x.

A very short, phase-aware visual settle that does not change physics could look more planted than both alternatives: (a) freezing an arbitrary walk frame or (b) snapping instantly to one globally chosen plant frame.

This is not yet proven. The four authored lateral frames may already be similar enough at the feet that the immediate snap is visually negligible. Measure before changing.

### PROPOSED_CHANGE
Do not change production yet.

Candidate A — baseline instrumentation only:
- sample the exact last moving render/update and the first 1–4 post-release renders;
- record `lastReleaseFromFrame`, first post-release frame, support centroid/bottom-band position in screen/device pixels, and elapsed milliseconds;
- preserve the current MOV_STOP_V2 behavior.

Candidate B — only if A confirms a visible discontinuity:
- keep physics stop immediate;
- keep `footRoot`, collider, camera and world position unchanged;
- add a purely visual settle state lasting at most a small bounded window (initial search range 30–80 ms, not a committed value);
- choose the settle behavior from measured authored support geometry, not from intuition. Possibilities to benchmark include: nearest compatible plant/contact frame, a single intermediate frame, or a phase-aware mapping into the authored plant pose.

Candidate C — if any settle delay feels laggy or introduces foot skating:
- keep the immediate stop but choose a release plant frame dynamically from the lateral contact metrics rather than forcing frame 2 for every phase.

Do not introduce sprite cross-fading as the first solution; alpha blending between discrete pixel-art frames may blur the hero and confound the filtering/raster work already under investigation.

### DO_NOT_ASSUME
- Do not assume `PLANT_FRAME=2` is wrong. It may be the best authored idle/contact frame.
- Do not assume waiting until a gait cycle completes is acceptable; that can make controls feel visually delayed.
- Do not change physics deceleration, joystick response, camera, collider, gait cadence, zoom, avatar scale, filtering, shadow or footRoot in the same experiment.
- Do not delete `engine-ah.js` or `VISUAL_STOP_HOLD_SEC` merely because responsibilities overlap; first prove behavior and consumers.
- Do not call the issue fixed because a final 140 ms snapshot is planted.

### EXPERIMENT
Baseline -> candidate -> identical trace -> re-measure.

1. Extend the hero harness with a deterministic release sampler that captures the last moving sample and every animation/update sample for at least the first 100 ms after release.
2. Force release from each lateral source frame 0, 1, 2, 3. Do not rely on arbitrary 220 ms timing; steer `stridePhase`/trace or wait until each exact frame is observed before keyup.
3. Run RIGHT->release and LEFT->release separately; mirrored LEFT may change visible support displacement even with the same source frame.
4. Repeat magnitudes 0.50 and 1.00, plus a run-threshold case near 0.70 if analog injection is available.
5. Repeat mobile 390x844 DPR2 and desktop 1280x720 DPR1; add desktop DPR2 when available.
6. Where feasible, replay equivalent traces at 60/90/120 Hz or deterministic dt equivalents.
7. For each sample, project the authored lateral `supportCentroidX`, lowest opaque Y/bottom band, footRoot, and sprite destination rect to screen/device coordinates.
8. Baseline metrics first. Only if the stop-pop is measurable/perceptible, test Candidate B and/or C with exactly the same trace.
9. Re-run with 1.20x only after a stop-transition candidate wins at 1.15x.

### DECIDING_METRICS
Primary:
- `releaseFrameJumpMax` and distribution by source frame.
- `releaseSupportJumpP95CssPx` / `releaseSupportJumpP95DevicePx`.
- `releaseBodyBottomVsFootRootJumpP95CssPx`.
- `releasePoseDiscontinuityFirstFrameCount`.
- `releaseToStablePlantMs` measured from actual sampled frames, not hardcoded telemetry.
- `releaseVisibleSlideDistancePx` after physics has already stopped.

Control/quality:
- input-to-physics-stop latency must not increase.
- `worldTraceDelta = 0`.
- `cameraTraceDelta = 0`.
- `colliderDelta = 0`.
- `footRootDelta = 0`.
- `depthRootDelta = 0`.
- no extra idle/walk/run classifier changes.
- no new raster shimmer beyond baseline.

Initial decision targets are experimental, not requirements: aim for first-frame support/body discontinuity below roughly 0.5 CSS px if achievable without visible slide, and keep visual settle under the shortest duration that observers cannot perceive as lag. If baseline is already below perceptual noise, reject the extra state and keep current code.

### RISKS
- A settle window can create foot skating after the physics body has stopped.
- Waiting for a particular authored frame can increase perceived input latency even if physics is immediate.
- Dynamic plant-frame selection can look inconsistent if different frames have materially different torso silhouettes.
- More state in `engine-ac.js` can duplicate responsibilities with `engine-ah.js` and future animation-system work.
- Measuring only source frame indices is insufficient; mirror direction and support geometry matter.
- 1.20x can amplify an artifact that is negligible at 1.15x, so scale must be a later validation dimension, not part of the first code change.
