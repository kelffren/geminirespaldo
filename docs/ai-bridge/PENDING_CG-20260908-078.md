### PROBLEM
Kelo currently has no deliberate body bob in the live PNG locomotion path. This is not merely an unimplemented polish feature: `engine-ah.js` explicitly documents that an older bob was removed because it moved both shadow and sprite and made the character appear to float. That previous failure mode does not prove that all bob is harmful; it proves that bob must not translate the ground/contact root. The current renderer already exposes a stable `footRoot`, `depthRoot`, and `shadowAnchor`, while gait already exposes a distance-driven `stridePhase`. This gives the architecture needed to test a body-only, contact-aware bob without changing physics or ground anchoring.

### CONFIRMED_IN_GEMINI
1. Current main at research start: `d84f02be1a9e3fd19da98e91858eb451e37992c0`; `index.html` declares Kelo World V6.52 and loads `engine-ab.js` before `engine-ac.js`, with `engine-ah.js` later.
2. `engine-ah.js` states: `Solo freno al soltar. El bob visual se quito: movia sombra+sprite y flotaba.` Therefore the prior bob failure is explicitly recorded in live code.
3. `engine-ac.js` is the live gait owner and already computes distance-driven `stridePhase`, `strideDistancePx`, gait (`idle/walk/run`), current frame, and face. The phase is not render-count driven.
4. `engine-ab.js` exposes `KELO_AVATAR_PRESENTATION` with separate `physicsRoot`, `footRoot`, `depthRoot`, `shadowAnchor`, visual bounds, and nameplate anchor. The current PNG draw destination is based on the fixed foot root; there is no explicit vertical/horizontal body bob term in the live draw path.
5. `src/characters/character-appearance.js` preserves an older per-frame foot-anchor concept (`footX[]`, `footY[]`) for the retired/non-default appearance path, reinforcing that foot-relative placement is an existing repo concept rather than a new abstraction invented for this proposal.
6. `engine-a.js` still computes speed-dependent `squashX/squashY`, but the live PNG renderer does not consume those values. This is presentation state living in core physics/movement code and should not be reused blindly for bob.
7. No Grok feedback newer than `GC-20260831-003` exists in `GROK_TO_CHATGPT.md`; no implementation evidence currently closes this bob question.

### EXTERNAL_EVIDENCE
- Unity's current Root Motion documentation describes a Feet-based root transform option where root Y follows the lowest foot across frames specifically to keep blending around the feet and prevent floating during transitions. This supports keeping the presentation root/contact reference at the feet while allowing the body pose to vary above it.
- Godot's current AnimationTree documentation provides cyclic synchronization modes specifically to keep locomotion phases aligned across animations. This supports deriving any secondary body motion from the already distance-driven gait phase rather than from an independent timer.
- Meta's avatar locomotion documentation uses explicit `LeftFootPlanted`/`RightFootPlanted` curves for foot planting, demonstrating that body motion and contact state should be coordinated rather than applying generic sine-wave bob independent of support.
- Community counterevidence: head/body bob is frequently reported as uncomfortable or visually distracting when amplitude is high, when it continues during weak/blocked motion, or when transitions reset phase. A Godot head-bob report also shows snapping when switching locomotion/idle states, with blending/phase handling needed to remove it. Therefore a generic always-on sinusoid is not justified.

### HYPOTHESIS
A small BODY_LOCAL offset derived from the existing stride phase can add weight and locomotion energy without reintroducing floating if and only if:
- `footRoot`, `shadowAnchor`, `depthRoot`, collider, and physics position remain unchanged;
- amplitude is small and gait-dependent;
- the bob is phase-locked to the same distance-driven cycle that selects frames;
- release converges to exactly zero body offset without a snap;
- blocked/collision motion cannot continue full-amplitude bob merely because velocity/input remains high;
- horizontal sway is tested separately from vertical bob rather than bundled into one transform.

### PROPOSED_CHANGE
Do not implement directly in production yet. Add a QA-only presentation experiment with four candidates:

A — BASELINE: current PNG renderer, no body bob/sway.

B — TIMER_SINE_CONTROL: a deliberately naive time-based sine bob (diagnostic only). This is expected to expose phase drift across different speeds/Hz and should not ship.

C — PHASE_VERTICAL_BODY_LOCAL: compute a small vertical body offset from `stridePhase`, applied only to the destination sprite/body branch while leaving `footRoot/shadow/depth/nameplate policy` independently measurable. Start with conservative amplitude, e.g. walk <= 0.8 CSS px apparent and run <= 1.3 CSS px apparent after zoom, but tune from device measurements rather than hardcoding these as production values.

D — PHASE_VERTICAL_PLUS_HORIZONTAL: same as C plus very small lateral sway tied to support phase, only if C first proves stable. Horizontal amplitude should remain lower than vertical and must not move the contact root.

Architecturally, expose a presentation-only transform such as `bodyOffsetX/bodyOffsetY` owned by the gait/presentation layer, not by physics. `engine-ab.js` would consume that transform for the sprite draw only. Ground-local effects remain anchored to `footRoot/shadowAnchor/depthRoot`.

### DO_NOT_ASSUME
- Do not assume 'more bob = more premium'. Zero bob may remain best for this authored sprite.
- Do not assume a sine wave is correct; authored frame geometry may already encode vertical mass motion.
- Do not drive bob from `Date.now()` or render count.
- Do not use `localPlayer.squashX/Y` as a proxy for gait phase.
- Do not move `p.x/p.y`, collider, camera target, footRoot, shadow, aura ground ring, or depth root.
- Do not allow body bob while the actor is blocked with near-zero resolved displacement unless a separate push animation is intentionally authored.
- Do not combine bob, lean, squash, scale 1.20x, and camera changes in one benchmark.

### RISKS
- The authored four-frame lateral sequence may already contain enough implied vertical body motion; extra procedural bob can double-count motion.
- Nearest-neighbor rendering plus fractional zoom may turn subpixel body offsets into temporal shimmer even at tiny amplitudes.
- Tying offset to raw `stridePhase` can create a visible discontinuity when MOV-STOP-V2 snaps phase to `PLANT_PHASE`; the presentation offset must settle independently or choose a function whose plant-phase offset is exactly zero.
- A body-only vertical offset can reveal that the current visible support pixel is not actually aligned to `footRoot` for every frame; CG-068 contact metrics remain a prerequisite for interpreting failures.
- Horizontal sway may look like collision/camera jitter and should not be tested until vertical-only C is stable.
- Nameplate policy is unresolved: leaving it ground-local may visually increase body/nameplate spacing during bob, while moving it body-local can make text jitter. Measure both; do not assume.
