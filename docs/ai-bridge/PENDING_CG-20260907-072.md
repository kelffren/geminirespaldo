PROBLEM
The current distance-driven gait is conceptually frame-rate independent, but `engine-ac.js::updateVisualMotion()` only credits a movement step when the displacement from the immediately preceding update exceeds `MIN_VISUAL_MOVE_PX = 0.12`. Deltas at or below that threshold are discarded rather than accumulated. Because `engine-a.js` advances world position with `vx * dt`, the same continuous low-speed movement produces smaller per-update deltas at higher update/refresh rates. Therefore a slow lateral input can move Kelo physically while `stridePhase` receives zero distance at 120 Hz, even though the same world speed advances the animation at 60 Hz. This is a different failure mode from CG-069 cadence-at-run-speed: it affects the low-speed floor and creates refresh-rate-dependent walk/idle appearance.

CONFIRMED_IN_GEMINI
- Current `main` at research start is `4fc5c720da6746637544e2fa33897303ffcf73d1`, title Kelo World V6.43. Current code was re-read; no assumption was carried over from older rounds.
- `engine-ac.js` sets `MIN_VISUAL_MOVE_PX = 0.12` and computes `dist = hypot(p.x-v.lastX, p.y-v.lastY)` every movement update.
- `v.lastStepDistancePx = dist > MIN_VISUAL_MOVE_PX ? dist : 0`; only when `v.lastStepDistancePx > 0` does `strideDistancePx` and `stridePhase` advance. Sub-threshold deltas are not placed in a remainder/accumulator; `v.lastX/Y` are still updated at the end of the call, so discarded distance is permanently lost for gait purposes.
- `engine-ac.js` forces `CONFIG.movementType='DIRECT'`. For input magnitudes <= `SPEED_BLEND_START=0.48`, `speedFor()` returns `WALK_SPEED=110`, while target speed is `mag * speedCap`; thus unobstructed slow motion is approximately `110 * mag` world px/s.
- `engine-a.js::updateMovement(dt)` sets direct velocity from input and updates world position via `localPlayer.x += vx*dt` and `y += vy*dt` before collision resolution. Thus per-update displacement scales with dt.
- The practical threshold speed implied by 0.12 px/update is approximately 7.2 world px/s at 60 Hz, 10.8 at 90 Hz and 14.4 at 120 Hz. With the 110 px/s low-speed cap, that corresponds to processed magnitudes of about 0.065, 0.098 and 0.131 respectively.
- `GAIT_IDLE_MAX=0.03`, so there is a real input band above gait-idle where physical movement can be nonzero but visual stride can receive no distance. At 120 Hz the theoretical band is roughly processedMag 0.03..0.131 in unobstructed low-speed motion; at 60 Hz it is roughly 0.03..0.065. Exact boundaries depend on actual dt, collisions and update scheduling and must be measured.
- `engine-ab.js` consumes `_visualMotion.frame`; if stride phase is frozen while world position moves, the PNG body can translate laterally with a planted authored frame, reading as glide/ice rather than a slow walk.
- Current `publishAudit()` exposes `lastStepDistancePx`, `strideDistancePx`, `stridePhase` and frame, but does not expose discarded sub-threshold distance, accumulated remainder, update Hz, or physical-distance-vs-credited-gait-distance ratio.
- `character-appearance.js` contains another legacy/delegated movement heuristic using the same `>0.12` displacement cutoff, but current default player delegates to the engine-ab renderer. This duplication reinforces that 0.12 is a historical per-update heuristic, not a proven time/distance invariant. Do not refactor both systems in this experiment.

EXTERNAL_EVIDENCE
- MDN `requestAnimationFrame()` documentation explicitly notes that callback frequency generally follows display refresh rate (60/75/120/144 Hz are common) and warns that per-frame animation progress must account for elapsed time to avoid high-refresh-rate dependence: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame
- Godot's stable physics interpolation documentation separates fixed physics ticks from rendered frames because displays/rendering can run at different rates; this is direct evidence that update-frequency assumptions should not leak into motion presentation thresholds: https://docs.godotengine.org/en/stable/tutorials/physics/interpolation/physics_interpolation_introduction.html
- Unity's `Time.deltaTime` documentation states the same principle: per-frame changes should be expressed in units per second rather than units per frame when behavior must be frame-rate independent: https://docs.unity3d.com/ScriptReference/Time-deltaTime.html
- GitHub counterexample/evidence: Godot issue #86634 documents 2D character/camera jitter whose manifestation changes with movement/render conditions, reinforcing that visually smooth motion must be evaluated across the full camera/update pipeline rather than inferred from FPS alone: https://github.com/godotengine/godot/issues/86634
- Community evidence on top-down sprite locomotion repeatedly identifies mismatch between world distance and visible step distance as foot sliding; practical advice is to couple animation to travelled distance rather than an arbitrary frame count: https://www.reddit.com/r/gamedev/comments/o9esl6/ and https://www.reddit.com/r/gamedev/comments/wofi7p/
- Counterevidence: a small minimum displacement threshold can be useful as noise suppression near idle, collision correction and floating-point jitter. The proposal is NOT to remove all thresholding blindly; it is to make the credited-distance rule invariant to update rate and preserve a deliberate noise floor.

HYPOTHESIS
The current 0.12-per-update discard causes a measurable refresh-rate-dependent low-speed glide band. Replacing permanent discard with a small distance accumulator/remainder, or with a threshold expressed in speed/time terms, can preserve idle noise suppression while making the same world trace produce the same stride progression at 60/90/120 Hz. The best candidate should credit only resolved world displacement, so blocked-wall jitter is not accumulated into fake steps.

PROPOSED_CHANGE
Do not change production first. Add QA telemetry and compare:
A) baseline: current `dist > 0.12 ? dist : 0` permanent discard;
B) accumulated-distance gate: add each resolved world delta to a small `pendingStrideDistancePx`; when the accumulator exceeds a deliberate noise floor, transfer the accumulated distance into stride progression and reset/subtract the threshold. The accumulator must be cleared on true idle/teleport/reset and must not convert collision pushback oscillation into steps;
C) speed/time gate: decide whether motion is visually creditable from resolved speed over a short time window, then credit the full resolved distance instead of testing each frame independently;
D) zero-threshold control only for diagnosis, not a production recommendation, to reveal the maximum possible frame-rate invariance and the amount of noise the 0.12 cutoff was hiding.
Keep `worldTrace`, speed mapping, collider, camera, stride cycle length, authored frames and avatar scale unchanged. Do not combine with CG-069 run cadence, CG-068 per-frame pivots, CG-070 facing hysteresis, CG-071 body transforms, subpixel draw changes or 1.20x scale.

DO_NOT_ASSUME
- Do not assume the browser update loop is exactly 60/90/120 Hz; log actual dt/update cadence.
- Do not simply set `MIN_VISUAL_MOVE_PX=0`; the existing threshold may suppress legitimate collision/subpixel noise.
- Do not use raw `vx/vy` alone to advance stride. Collisions can leave velocity nonzero while resolved displacement is near zero.
- Do not accumulate teleport/dash/quick-travel displacement into normal walking stride without an explicit reset/teleport rule.
- Do not let candidate B accumulate forever while input is idle; stale remainder could cause a delayed first-step pop on next movement.
- Do not refactor duplicated movement heuristics in `character-appearance.js` in the same patch.

RISKS
- Accumulating tiny resolved deltas can expose camera/collision/subpixel noise that the historical threshold hid.
- Remainder handling can cause a delayed frame transition immediately after release/restart if not cleared under explicit state rules.
- A speed-window candidate can add perceptual latency if smoothing is too long.
- Testing only keyboard is insufficient because full keyboard magnitude bypasses this low-speed region; touch/virtual-stick magnitudes are the primary reproduction path.
- Emulated refresh rate may not perfectly reproduce mobile compositor scheduling, so real-device 120 Hz validation remains desirable before claiming verified.
- The source sprite has only four lateral frames, so fixing low-speed distance accounting may reveal cadence/coarseness that was previously masked; that is a separate art/cadence decision, not reason to retain frame-rate dependence.
