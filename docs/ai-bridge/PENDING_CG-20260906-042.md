### PROBLEM
The current lateral locomotion pipeline has one authored four-frame lateral sequence for both `walk` and `run`. `engine-ac.js` changes gait semantics and the world-distance represented by one loop, but `engine-ab.js` still selects the same row 2 and the same 4 columns for both gaits. Under MOV-CADENCE-V2, the cycle is 50 world px below run and grows linearly from 50 px at processed magnitude 0.70 to 90 px at 1.00. That means the same visible poses are asked to represent up to 80% more world translation per loop without a different run pose, longer visual leg reach, or per-gait contact geometry. This can create foot sliding even when normalized stride phase itself is continuous.

A second internal clue is present in `src/characters/character-appearance.js`: for the same `assets/hero.PNG`, row 2 has per-frame right-facing foot-anchor X metrics `[145,135,121,113]` with Y `[384,384,384,384]`. The live default player delegates to `engine-ab.js`, which does not use any per-frame foot anchor; it centers every cropped frame on the same `p.x`. Those metrics are not authoritative proof of the correct support foot, because they belong to a retired bot appearance definition, but they demonstrate that frame-local anchor variation for this exact source asset is already known elsewhere in the repo and is currently ignored by the live hero path.

### EXTERNAL_EVIDENCE
- Unity Blend Tree documentation states that locomotion clips blend best when corresponding foot-contact moments occur at the same normalized times (for example left-foot and right-foot contacts aligned at the same phase). This supports treating support/contact phase as an explicit invariant rather than only varying arbitrary playback distance.
- Godot AnimationTree cyclic sync modes explicitly keep locomotion cycle phases aligned while adapting cycle duration, and its discrete-carry mode preserves playback position across frame-by-frame animation changes. This supports phase continuity but does not by itself guarantee that world translation matches visible stride reach.
- A PubMed running biomechanics study reports that humans increase running speed using a combination of stride length and stride frequency; another study found self-selected stride frequency increased with running speed. This is counterevidence to a presentation model where nearly all speed increase is represented only by a much longer virtual stride while cadence and pose set remain almost unchanged.
- A practical r/gamedev foot-sliding discussion repeatedly converges on matching movement speed to the distance represented by the animation/gait; one high-voted answer describes measuring the distance traveled between foot placement and lift and deriving animation speed from that measurement. Community evidence is not authoritative, but it matches the engine-level hypothesis.
- Counterevidence: a run can legitimately use longer strides without a dramatic cadence increase, and stylized four-frame sprites can intentionally exaggerate stride distance. Therefore 50→90 px is not automatically wrong; the deciding evidence must be measured screen-space support-foot slip from the actual `hero.PNG`.

### HYPOTHESIS
The current lateral animation can look increasingly like skating as processed magnitude approaches 1.0 because the same four source poses translate 80% farther per loop while their visual leg reach/contact geometry is unchanged. A smaller but potentially independent contributor is static body-centering of each source frame instead of a measured frame-local contact anchor. The 1.20x avatar scale may make the character easier to read but will not fundamentally repair either mismatch.

### EXPERIMENT
1. Baseline current main with one fixed lateral trajectory in open ground.
2. Execute processed magnitudes 0.50, 0.69, 0.70, 0.80, 0.90, 1.00 for enough distance to cover at least 6 complete cycles each.
3. Repeat at effective 60/90/120 Hz or deterministic simulated update cadences; world trajectory must remain the same for the same magnitude/time.
4. Record on every animation-frame transition: world X, screen X, gait, stridePhase, source frame, cycleWorldPx, source support/contact X, transformed support/contact screen X, and whether that contact is classified planted/swing.
5. Compute `plantedFootSlipPx` as screen/world displacement of the same validated contact point while it should be in stance. Also compute `translationPerQuarterCyclePx` and `cycleFrequencyHz`.
6. Repeat baseline at 1.20x QA-only with identical physics; do not change cycle curve.
7. If baseline proves slip, test one variable at a time: (B) per-frame anchor compensation first; then (C) calibrated cycle-distance curve if needed. Re-run the exact same trace.
8. Negative controls: idle must show zero anchor creep; reversal must preserve physical/footRoot continuity; diagonal test must not introduce new row thrashing.

Suggested acceptance target for a presentation-only fix: materially lower p95 stance slip than baseline with no world/camera/collision trace changes and no new >1 px contact jump introduced at reversal. Do not lock a universal numerical threshold until the baseline is captured because the sprite is stylized and nearest-neighbor scaled.

### RISKS
- Bottom-band centroid is not automatically the true planted foot; trousers/shoes/transparency may make automated contact inference ambiguous.
- Per-frame anchor correction can create torso jitter if it locks the wrong foot or over-corrects swing frames.
- Reducing cycleWorldPx too aggressively can make legs look like they churn while the body moves slowly.
- Increasing cadence to match speed may worsen readability with only four frames, especially at 120 Hz displays where the renderer is smooth but sprite poses remain discrete.
- A separate run row/asset would improve expressiveness but adds asset memory/authoring complexity and should not be introduced until the current four-frame limit is proven to be the bottleneck.
