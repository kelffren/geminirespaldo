### PROBLEM
The production hero is deliberately rendered with nearest-neighbor sampling and integer-rounded world destination coordinates, while the world/camera is then scaled by a late zoom value that is usually fractional in CSS space and frequently fractional in physical-device-pixel space. The repo also contains an earlier DPR-aware `pixelPerfectZoom()` policy in `engine-h.js`, but later engines overwrite that policy. This creates two independent quantization decisions—world-coordinate rounding for the hero and continuous late zoom for the scene—without a single owner defining how authored sprite pixels should map to physical pixels during lateral motion.

This matters directly for the current user priority. At 1.15x/1.25x presentation scale, small edge cadence differences and one-frame stalls become more visible. At 90/120 Hz, a physical world step can be below one world pixel per render; because `engine-ab.js` rounds the destination world coordinate before the global zoom transform, the visible sprite may alternate between zero- and one-world-pixel jumps instead of following the float simulation continuously.

### CONFIRMED_IN_GEMINI
1. `index.html` declares `image-rendering: pixelated; image-rendering: crisp-edges` on `#game-canvas` and currently loads `engine-h.js` before `engine-t.js`, then `engine-z.js`, then `engine-ab.js`.
2. `engine-h.js` explicitly defines `pixelPerfectZoom(target)` as `round(target * DPR) / DPR`, sets `CONFIG.roundPixels = true`, uses a HiDPI backing canvas (`canvas.width = CSS width * DPR`, `ctx.setTransform(DPR, ...)`) and disables `ctx.imageSmoothingEnabled`.
3. `engine-t.js`, loaded later, caps the current zoom to <=1.05.
4. `engine-z.js`, loaded later still, replaces zoom with `screenW / (targetTiles * 32)` clamped to 1.05..1.45. It does not call `pixelPerfectZoom()`. Therefore `engine-h` is not the final owner of default zoom despite exposing `KELO_HD_RENDER.mode='hidpi-pixel-perfect-v1'`.
5. Representative current `engine-z` target values are approximately: 390 CSS px -> z=1.10795; 430 -> z=1.22159; >=~650 may clamp to z=1.45. With DPR 3, these produce physical world-unit scales ~3.32386, 3.66477 and 4.35 device px per world unit respectively, not integer scales.
6. `engine-c.js` applies the global transform `translate(screen center) -> scale(CONFIG.zoom) -> translate(-camera)` before rendering the hero.
7. `engine-ab.js` disables image smoothing and draws the current hero frame at `Math.round(p.x - dw/2)` and `Math.round(footY - dh)`, i.e. it quantizes the hero's destination in WORLD coordinates before the later camera/zoom transform reaches the backing store. Nameplate x/y are rounded similarly.
8. `engine-a.js` keeps simulation position as floats; movement is not integer-quantized. `engine-ac.js` currently uses WALK_SPEED=110 and a float distance-based stride phase. Therefore rendering can quantize position while gait continues to advance from float world distance.
9. `CONFIG.roundPixels` is set by `engine-h.js`, but in the reviewed hero path the actual rounding behavior comes from explicit `Math.round()` calls in `engine-ab.js`; the flag does not define a shared projection/snapping contract there.
10. Ownership is redundant/fragmented: `engine-h` describes DPR/pixel-perfect zoom, `engine-t` mutates zoom, `engine-z` owns the latest automatic zoom, `engine-c` owns scene transform, and `engine-ab` independently rounds hero world coordinates.

### EXTERNAL_EVIDENCE
- MDN `CanvasRenderingContext2D.imageSmoothingEnabled`: disabling smoothing preserves hard pixel-art edges when images are scaled, but it does not by itself define position snapping or guarantee uniform physical pixel sizes. https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
- MDN `CanvasRenderingContext2D.scale()`: scaling transforms the canvas coordinate unit itself; non-integer scales therefore map a logical unit to a fractional number of output pixels. https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/scale
- MDN `Crisp pixel art look with image-rendering`: explicitly warns that when CSS pixels and device pixels do not align, some authored pixels can become larger than others and the result can look uneven; it also warns about non-integer image->canvas scale factors. https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look
- MDN `image-rendering`: `pixelated` chooses nearest-neighbor/similar behavior around an integer multiple and then may interpolate to the final arbitrary size; it is not a proof that arbitrary DPR/zoom combinations are visually identical. https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/image-rendering
- Community counterevidence: pixel-art developers report that strict whole-pixel snapping can itself create stair-stepping/jitter during diagonal or slow movement, and some deliberately allow subpixel presentation for smoother motion. Example discussion: https://www.reddit.com/r/godot/comments/1hspdkd/ . Therefore "make every scale/position integer" must NOT be assumed to be the premium answer.
- Recent community reports continue to identify a real trade-off between strict pixel snapping and smooth free movement/camera interpolation at higher refresh rates; this supports an A/B benchmark rather than a stylistic assumption.

### HYPOTHESIS
The current combination of float simulation + distance-based gait + integer WORLD-coordinate hero draw + fractional global zoom can create visible lateral micro-stutter/uneven pixel cadence that varies by viewport, DPR, camera offset and refresh rate. The problem may become more obvious at 1.15x/1.25x hero scale because silhouette pixels are larger and movement edge cadence is easier to see.

A single explicit PRESENTATION projection contract may outperform the current mixed policy. Candidate contracts include: current world rounding; no destination rounding with nearest-neighbor sampling; device-pixel projection snapping after camera+zoom; or a deliberately DPR-quantized zoom. The correct result is empirical and may vary by art scale.

### PROPOSED_CHANGE
Do NOT refactor zoom/render ownership yet. First instrument and benchmark.

A — `WORLD_ROUND_BASELINE`
Keep current production exactly: `Math.round(world destination)`, `imageSmoothingEnabled=false`, current late `engine-z` zoom.

B — `FLOAT_WORLD_NEAREST`
For the hero only, keep world destination as float while leaving sampling disabled. Do not change physics, camera, gait or zoom. This tests whether current world rounding is causing 90/120-Hz hold/jump cadence.

C — `DEVICE_PIXEL_PROJECTED_SNAP`
Experimental presentation-only helper. Compute the hero's desired screen/device position using the same camera+zoom+DPR transform, snap the FOOT ROOT or sprite destination to the nearest device pixel, then convert the correction back to world units for draw. Do not mutate `p.x/p.y`, collider or camera. The goal is to snap in the coordinate space that actually becomes pixels, not prematurely in world space.

D — `DPR_QUANTIZED_ZOOM_DIAGNOSTIC`
Use the existing `engine-h` idea only as a diagnostic: compare the current target zoom against a nearby DPR-quantized zoom. Reject this candidate if the field-of-view change is materially worse, especially on DPR3 mobile where nearest integer physical scaling can produce a large zoom jump. Do not impose integer zoom globally merely for purity.

E — `PRESENTATION_SCALE_1.15_1.25`
Only after A/B/C have a winner at 1.00x, rerun the same projection contract with the proposed larger body while preserving footRoot and collider.

If C wins, centralize only the measured projection math in a tiny presentation helper. Do not merge camera, movement, avatar and zoom modules blindly.

### DO_NOT_ASSUME
- Do not assume `imageSmoothingEnabled=false` guarantees pixel-perfect physical output under arbitrary zoom/DPR.
- Do not assume integer WORLD positions are better than float positions for a smoothly moving camera.
- Do not assume DPR-quantized zoom is acceptable; on some DPR/viewports the nearest scale changes field of view substantially.
- Do not change simulation coordinates, collider, stride phase, movement speed or networking coordinates to solve a presentation issue.
- Do not revive legacy renderers.
- Do not delete `engine-h`, `engine-t` or `engine-z` based only on apparent ownership overlap. Baseline -> variant -> same trace -> measurement first.
- Do not update validated visual memory unless one policy wins LIVE browser/mobile comparison.

### EXPERIMENT
Use deterministic movement traces with fixed starting player/camera coordinates and capture actual rendered hero screen position once per RAF.

Traces:
1. idle -> RIGHT WALK for 2 s -> release
2. idle -> RIGHT RUN for 2 s -> release
3. LEFT mirror
4. 45-degree diagonal
5. RIGHT run -> hard LEFT reversal
6. slow analog magnitudes around 0.20 / 0.35 / 0.50 where per-frame visual displacement is smallest

Run A/B/C at 60, 90 and 120 Hz equivalent RAF capture where environment permits; do not fake browser refresh as proof if only synthetic stepping is available. Test CSS viewports 390x844, 430x932, 768x1024 and 1440x900. Record DPR 1/2/3 where available/emulatable, but distinguish emulated DPR from a real device.

For every RAF record:
- float player world x/y
- camera x/y
- CONFIG.zoom
- DPR
- desired unsnapped screen foot-root x/y
- actual snapped/drawn screen foot-root x/y
- device-pixel coordinate of the foot root
- frame/stridePhase/gait

Visually capture a tight ROI around the hero and compare silhouette stability while moving past a high-contrast vertical background edge. Repeat with body 1.00x first, then 1.15x/1.25x only for the best candidates.

### DECIDING_METRICS
Primary:
- `heroScreenStepCssPxStdDevAtConstantVelocity` — lower unevenness is better, but zero-step/large-step alternation must be counted separately.
- `zeroScreenStepFrameRatePct` at constant nonzero velocity.
- `heroDevicePixelFractionAbsP95` — distance from nearest device-pixel coordinate for foot root/body anchor.
- `silhouetteEdgeChangeVariancePerMeter` — proxy for edge shimmer under identical movement.
- `footRootScreenJitterCssPxP95` after removing expected constant-velocity trend.
- `frameHoldPatternPeriod` — detect repeated 0/1/2-pixel cadence caused by quantization.
- `sameTraceVisualCadenceDiff60vs90vs120`.

Scale quality:
- `authoredPixelNonUniformityPct` in a captured ROI (how often equivalent source clusters render at differing physical widths/heights).
- `heroRoiSharpEdgeRatio` or equivalent nearest-edge metric.
- subjective side-by-side rating for silhouette crispness at 1.00x/1.15x/1.25x.

Performance:
- `frameMsP95/P99`, `fpsP5`, and per-actor draw cost for 1/10/25/50 actors if any projection helper adds per-draw math.

Hard invariants:
- `worldTraceDeltaPx = 0`
- `collisionOutcomeDiffCount = 0`
- `stridePhaseDelta = 0` for the same simulation trace
- `cameraTraceDeltaPx = 0` for A/B/C
- networking state unchanged

### RISKS
- FLOAT_WORLD_NEAREST may trade motion cadence for edge shimmer because nearest-neighbor sampling from fractional destination positions can make source pixels alternate coverage.
- DEVICE_PIXEL_PROJECTED_SNAP can make the hero move differently from the background if only the actor is snapped while the camera/world remains fractional; this relative mismatch must be measured, not ignored.
- Strict DPR-quantized zoom may materially alter field of view and mobile composition. It is diagnostic, not the default recommendation.
- Snapping footRoot independently from body dimensions can introduce a one-device-pixel silhouette asymmetry after left/right mirroring unless the full transform is handled consistently.
- Enlarging the avatar can amplify every artifact without changing the root cause.
- Centralizing all zoom/rendering now would be a blind refactor; ownership cleanup should follow a measured winner.
