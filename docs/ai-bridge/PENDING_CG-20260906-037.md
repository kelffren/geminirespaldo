### PROBLEM
The current gait owner chooses one of four facing rows from a single instantaneous dominance test: `abs(dx) * 1.15 >= abs(dy)` means lateral, otherwise vertical. There is no hysteresis, angular hold band, or face-transition telemetry. A direction close to that boundary can therefore alternate lateral↔vertical when tiny changes in joystick angle, achieved displacement, collision resolution, or update timing move the vector across the threshold.

This matters directly to premium lateral motion: a stable diagonal gesture can preserve world trajectory and stride phase yet still pop between a side silhouette and an up/down silhouette. At 1.20x the row switch would become more visible, so facing stability should be benchmarked before scale rollout or secondary-motion polish.

### CONFIRMED_IN_GEMINI
1. Current `main` was re-read at `4ac08501acd54b864fdc51d3c5c529a9149a490a`; the newest commit before this entry is the append for CG-036. No Grok response exists beyond `GC-20260831-003`.
2. `index.html` declares Kelo World V6.33 and loads `engine-ab.js` before `engine-ac.js`; `engine-ac.js` remains the live gait/facing producer for the local hero.
3. `engine-ac.js::updateVisualMotion()` stores achieved `dx/dy` when `dist > 0.12`, otherwise falls back to commanded velocity when `spd > 16`, otherwise input intent.
4. When visual motion is on, it computes `side = abs(v.dx) * 1.15 >= abs(v.dy)` and immediately sets face to right/left or down/up. There is no previous-face-dependent threshold and no minimum dwell time.
5. The current side/vertical boundary is `abs(y/x) = 1.15`, approximately 48.99 degrees from the horizontal axis. A vector just below that angle uses the lateral row; a vector just above it uses up/down.
6. `engine-ab.js` maps `up` to sprite row 3, `down` to row 0, and both `left/right` to row 2 (left mirrored). Crossing the facing boundary therefore changes the source row, not merely a metadata label.
7. `engine-a.js` processes touch as a continuous analog vector; real joystick X/Y can vary fractionally around a constant intended direction. Keyboard diagonals are normalized exactly and therefore are a poor stress test for analog boundary behavior.
8. `engine-a.js` resolves collisions after X movement and again after Y movement. `engine-ac.js` preferentially uses achieved per-update displacement when it exceeds the visual epsilon, so near obstacles the facing vector can legitimately differ from raw input and can move across the same dominance threshold.
9. `scripts/live-hero-audit.mjs` currently tests one digital D+S diagonal sample only. It does not sweep analog angle, inject small angular noise, count facing transitions, or inspect source-row changes.
10. `src/characters/character-appearance.js` duplicates the same `abs(mx) * 1.15 >= abs(my)` face-selection rule for non-delegated appearances. This is a real duplicated policy; a future fix in only one owner risks behavior drift.

### EXTERNAL_EVIDENCE
- Godot's official AnimationTree documentation treats 2D direction as a two-parameter animation space and provides Discrete / Discrete Carry modes for frame-by-frame 2D animation rather than requiring a single hard cardinal switch: https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html
- Godot's `AnimationNodeBlendSpace2D` documentation explicitly describes a 2D Vector2-controlled animation space and `BLEND_MODE_DISCRETE_CARRY`, which keeps playback position when changing the selected discrete animation: https://docs.godotengine.org/en/stable/classes/class_animationnodeblendspace2d.html
- Unity's official BlendTree API describes `SimpleDirectional2D` as intended for motions such as forward/back/left/right driven by two directional parameters; this is evidence that directional animation selection is normally treated as a 2D presentation problem rather than four unrelated instantaneous booleans: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animations.BlendTreeType.html
- A Godot community report describes the practical diagonal case where a four-direction BlendSpace switches inconsistently around values such as `(1,1)` and recommends keeping a separate animation-direction variable rather than blindly using movement vector every frame: https://www.reddit.com/r/godot/comments/w6t154/
- A June 2026 Godot joystick discussion shows the relevant source of analog variability: joystick axes commonly produce values such as `-0.89` and `0.99`, unlike digital keyboard values exactly at -1/0/1: https://www.reddit.com/r/godot/comments/1ui2yag/
- Counterevidence: achieved-motion facing can be desirable while sliding along a wall; if diagonal input becomes purely vertical achieved movement, switching to vertical may correctly communicate the actual path. The proposal therefore does not force facing from raw intent.
- Counterevidence: temporal smoothing/EMA can add visible input lag during genuine direction changes. Prefer a small Schmitt-trigger/hysteresis band first because it suppresses boundary chatter without continuously delaying the direction signal.

### HYPOTHESIS
Part of the perceived diagonal/lateral roughness is row thrashing near the ~49-degree boundary. Keeping the current achieved-motion semantics but adding a small previous-face-aware angular hysteresis band will reduce accidental lateral↔vertical row changes while preserving immediate LEFT↔RIGHT reversals and genuine large direction changes.

### EXPERIMENT
Baseline A — unobstructed analog sweep:
1. Use fixed processed magnitude 0.85 so gait remains run and only direction changes.
2. Sweep direction angle 40→58 degrees over 2 seconds, then 58→40 over 2 seconds.
3. Record angle, vector source, face, source sprite row, stridePhase, world position and every horizontal↔vertical axis transition.

Baseline B — boundary noise:
4. Hold nominal 49° for 3 seconds and inject deterministic alternating perturbations of ±0.5°, then ±1°, then ±2° at identical update schedules.
5. Repeat at effective 60/90/120 Hz or record actual dt if the harness cannot force exact refresh.

Baseline C — collision/slide:
6. Drive a diagonal vector along a wall so one component is partially/fully constrained. Record raw input, commanded velocity, achieved displacement and selected face-axis.

Candidate D — hysteresis:
7. Replay exactly the same deterministic vectors and world trajectories with only face-axis selection changed.
8. Preserve stride phase/frame and world/camera/collider traces.
9. Verify immediate right↔left reversal is not delayed when the axis is already horizontal.

Acceptance target for Candidate A:
- zero repeated horizontal↔vertical chatter while angle remains inside the hysteresis hold band;
- exactly one intended axis change per monotonic sweep in each direction, unless collision semantics clearly justify another;
- no measurable delay for LEFT↔RIGHT reversal within the horizontal axis;
- no world/camera/collider/footRoot change;
- same stridePhase for the same traveled distance;
- stable behavior across 60/90/120-Hz update schedules.

### RISKS
- Too-wide hysteresis can make Kelo visually face sideways while moving noticeably vertical, or vice versa.
- Too-narrow hysteresis will not suppress real analog noise.
- A collision can make achieved motion cross the axis boundary for a valid reason. The benchmark must distinguish one intentional switch from repeated chatter.
- Duplicated face-selection logic exists in `engine-ac.js`, `engine-ab.js` fallback logic, and `character-appearance.js`; applying inconsistent thresholds would worsen architectural drift.
- If the asset's up/down rows differ strongly in silhouette/foot anchors from the lateral row, even one correct axis transition may still need a future transition pose. That is separate art/animation research after axis stability is proven.
