### PROBLEM
The current MOV-CADENCE-V2 correctly removes the old abrupt 50→90 world-pixel cycle-distance jump at the walk/run boundary, but its replacement continuously grows the cycle distance from 50 to 90 world px from input magnitude 0.70→1.00. At the same time physical target speed rises. Because the LIVE Character Appearance renderer does not switch to a separate run clip or wider run poses and instead keeps consuming the same four lateral source columns, this makes the identical four-pose cycle become slower in time while Kelo moves faster through the world. The code is therefore creating an increasingly long virtual stride that is not visibly authored by a different run animation.

### CONFIRMED_IN_GEMINI
At BASE_COMMIT, engine-ac.js defines WALK_CYCLE_WORLD_PX=50, RUN_CYCLE_WORLD_PX=90, GAIT_RUN_START=0.70 and MOV-CADENCE-V2. For run, cycleWorldPxFor() linearly interpolates 50→90 as processed magnitude goes 0.70→1.00. speedFor() simultaneously smoothsteps WALK_SPEED=110 toward MAX_SPEED=185.28. updateVisualMotion() advances stridePhase by resolved distance / cycleWorldPx and selects one of four frames with floor(stridePhase*4). Character Appearance uses those same four frame columns for LEFT and RIGHT; it has independent directional rows and per-frame foot anchors, but no separate walk-vs-run frame set or run-specific stride-amplitude artwork.

Using the exact current formulas, representative steady-state values are approximately:
- mag 0.48: speed 110.00, cycle 50.00, 2.20 cycles/s, 8.80 frame changes/s equivalent.
- mag 0.70: speed 139.02, cycle 50.00, 2.78 cycles/s, 11.12 frame changes/s equivalent (~89.9 ms per pose).
- mag 0.75: speed 149.81, cycle 56.67, 2.64 cycles/s, 10.57 frame changes/s.
- mag 0.80: speed 160.44, cycle 63.33, 2.53 cycles/s, 10.13 frame changes/s.
- mag 0.90: speed 178.00, cycle 76.67, 2.32 cycles/s, 9.29 frame changes/s.
- mag 1.00: speed 185.28, cycle 90.00, 2.06 cycles/s, 8.23 frame changes/s equivalent (~121.4 ms per pose).
Thus from mag 0.70→1.00 physical speed rises ~33.3% while the identical four-pose cycle frequency falls ~26.0%, and its represented world distance rises 80% (50→90 px). This is code-level confirmation of a speed/cadence inversion, not yet confirmation of a visible defect.

Ownership scan: engine-ac.js already owns gait, speed, cycle distance, stride phase and visual frame; Character Appearance only consumes the resulting frame. No new movement wrapper/manager is justified for this experiment.

### EXTERNAL_EVIDENCE
Official Epic documentation describes Stride Warping as dynamically changing foot spacing/stride length to match capsule movement speed, and its Distance Matching utility states that cyclic walk/jog animations typically adjust play rate so animation speed matches in-game movement speed. This establishes the key principle: speed differences must be represented by cadence/play-rate, visible stride amplitude, or both rather than silently drifting apart.

Community evidence is consistent: GameDev/Unreal discussions repeatedly diagnose foot sliding when translation speed and the implied step speed differ, and recommend matching animation playback to movement speed or using stride warping/root motion. A top-down 2D discussion specifically notes that if the character moves farther during a step than the animation visually implies, sliding becomes obvious; it also recommends different animations for different speed ranges when needed.

GitHub/community tooling around locomotion likewise treats root/character speed versus observed foot motion, stride length and cadence as explicit quantities to validate rather than assuming a fixed clip remains correct at all speeds.

Counterevidence: cadence does not have to rise monotonically with world speed. Realistic running can gain speed through longer stride as well as cadence, and a deliberately authored longer run stride can legitimately use fewer cycles per second. Therefore the 50→90 policy is not inherently wrong. The mismatch is specifically suspicious here because the LIVE 2D renderer reuses the same four lateral poses and does not visibly widen the stride as the virtual cycle distance grows 80%.

### HYPOTHESIS
For the current four-frame lateral artwork, the 50→90 MOV-CADENCE-V2 ramp likely makes high-speed RIGHT/LEFT movement look more floaty/glide-like than a cadence profile that preserves or modestly increases temporal step frequency. A moderate virtual-stride endpoint around 60–70 world px may look more grounded than 90 while avoiding an excessively fast four-frame loop. This is a hypothesis only; the current 90 px endpoint must remain if blinded captures and foot-contact metrics prefer it.

### PROPOSED_CHANGE
Do not change production blindly. Add an experiment-only cadence endpoint/profile parameter inside the existing KeloMovement consumer in engine-ac.js and compare the current endpoint 90 against at least 60, 65 and 70 while keeping exactly the same movement physics, input mapping, collision response, camera, renderer, source frames and scale. Do not create another animation manager or movement wrapper.

If the current four poses cannot support the required speed range without either rapid cycling or visual sliding, the correct long-term solution is an authored run gait (or additional run poses) rather than forcing an extreme virtual stride into the walk artwork. In that future case, expose/consume an explicit gait contract rather than duplicating gait decisions in Character Appearance.

### RISKS

Adding a separate run clip later increases asset/memory complexity and must not be assumed necessary until this benchmark fails to find a satisfactory cadence with current art.
