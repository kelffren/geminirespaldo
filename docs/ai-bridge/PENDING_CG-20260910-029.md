## PROBLEM
El dodge PvP declaraba 112 px / 160 ms pero el runtime LIVE reproducible en Chromium móvil y escritorio desplazaba 0 px. `startDodge()` sí creaba `localPlayer._dash`, pero `dash.time` permanecía congelado en 0.16 y el actor nunca avanzaba.

## CONFIRMATION_IN_GEMINI
- `src/systems/pvp-world.js` crea `_dash` con `distance:112`, `duration:.16` y bloquea input normal durante `state.dodge`.
- `src/abilities/kelo-ability-boot.js` es el owner real que consume `_dash` y actualiza posición desde su hook `KeloSimulation`.
- Ese runtime puede dormir su hook mediante lifecycle/performance cuando no existe trabajo.
- El módulo se cargaba en contexto social, quedaba dormido, y la entrada posterior a PvP no ejecutaba `wakeRuntime()`. Un hook deshabilitado no podía observar por sí mismo el nuevo lifecycle PvP.
- Baseline LIVE: móvil y escritorio `start=(2790,720)`, `end=(2790,720)`, distancia 0 px, `_dash.time=.16` congelado, collisions `[]`, page errors `[]`.

## EVIDENCE
Evidencia principal de esta ronda es el runtime exacto de `main`, Playwright Chromium y CI del repositorio; no se necesitó extrapolar un patrón externo para localizar la causa.

## DISCOVERED_FOLLOWUP_GAP
El experimento también reveló una deuda de paridad NO corregida en esta ronda:

1. Cliente genérico de dash usa trayectoria lineal durante 160 ms.
2. Servidor PvP usa cubic-out `1-(1-k)^3`.
3. Ambos terminan exactamente a 112 px (endpoint delta 0), pero la máxima diferencia temporal de trayectoria es ~43.1019 px alrededor de 66.67 ms.
4. First step 60 Hz: cliente ~11.67 px vs server ~31.48 px; 90 Hz: 7.78 vs 21.75; 120 Hz: 5.83 vs 16.60.
5. Cliente conserva `state.dodge` / input movement lock durante recovery adicional de 150 ms; server actualmente deja de bloquear por `_pvpDash` al llegar al endpoint, por lo que existe `postDashControlDeltaMs=150`.

Esto NO invalida al winner funcional, pero sí impide declarar paridad completa cliente/servidor.

## RISKS
- Mantener KeloAbilities simulation awake durante PvP añade el coste intencional del owner que ya debe actualizar dashes/casts/projectiles en combate; no crea un loop adicional.
- El próximo cambio de easing debe evitar alterar indiscriminadamente Wind Dash/Shadow Step u otros `_dash`; preferir contrato data-driven/per-dash y misma semántica client/server.
- El recovery cliente vs server debe decidirse como una sola regla compartida antes de modificarlo, para evitar rubberband/control disagreement.
