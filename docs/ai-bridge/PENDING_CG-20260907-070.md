PROBLEM
The live facing selector in engine-ac.js chooses lateral vs vertical every update from an instantaneous ratio: `side = Math.abs(v.dx) * 1.15 >= Math.abs(v.dy)`. There is no directional hysteresis or dwell. The boundary is about atan(1.15)=49 degrees from the horizontal. Near that boundary, small vector changes can flip the rendered row/facing even while world movement remains smooth. On keyboard, exact diagonals (|x|=|y|) are always classified as lateral because of the 1.15 bias. This can make diagonal movement read as sideways strafing and can make touch diagonals visually chatter between lateral and vertical poses.

CONFIRMED_IN_GEMINI
- `engine-ac.js::updateVisualMotion()` derives facing from `v.dx/v.dy` on every update and uses `Math.abs(v.dx) * 1.15 >= Math.abs(v.dy)` with no remembered facing-sector threshold.
- `v.dx/v.dy` are refreshed from actual world delta when `dist > MIN_VISUAL_MOVE_PX`, otherwise velocity when speed >16, otherwise raw processed input when there is intent. Therefore the source feeding direction classification can change among world delta, velocity and input around small movements/collisions.
- `engine-a.js::processInput()` normalizes keyboard diagonals to equal X/Y and touch preserves the current joystick angle after radial deadzone processing. There is no angular filtering/hysteresis in input.
- The current movement mode is DIRECT via engine-ac.js, so for unobstructed touch movement the physics vector follows the input direction immediately; a render-facing oscillation can occur without requiring a physics oscillation.
- `index.html` live title is Kelo World V6.41 and loads `engine-ab.js?v=240` then `character-appearance.js?v=2` then `engine-ac.js?v=222`; current code, not the older ENGINE_MAP audit snapshot, is authority.
- Existing reversal telemetry tracks horizontal sign reversals but does not count lateral<->vertical facing toggles near diagonal sector boundaries.

EXTERNAL_EVIDENCE
- Unity documents 2D Simple Directional blending specifically for directional motions driven by two parameters, showing that directional presentation is normally treated as a 2D directional state/blend problem rather than four unrelated hard thresholds: https://docs.unity3d.com/ja/2021.3/Manual/BlendTree-2DBlending.html
- Godot issue #81975 documents joystick-axis input flicker when the stick is wiggled around directional thresholds, confirming that analog axis noise/variation can create repeated state transitions if a direction gate has no stabilizing policy: https://github.com/godotengine/godot/issues/81975
- Godot issue #103360 documents analog stick rebound producing false opposite inputs when thresholds are too permissive, reinforcing the broader principle that raw analog threshold crossings are not always stable semantic intent: https://github.com/godotengine/godot/issues/103360
- Counterevidence: mirroring/quantizing a 4-direction sprite by dominant axis is standard and very cheap; if measured sector toggles are rare and visually harmless, adding stateful hysteresis would be unnecessary and could delay legitimate direction changes.

HYPOTHESIS
The current instantaneous 49-degree lateral/vertical boundary creates unnecessary facing-sector chatter for touch trajectories near the diagonal boundary and biases exact keyboard diagonals to lateral. A small angular hysteresis around the existing boundary should reduce visual row flips while preserving physical movement, stride phase, and responsive intentional turns.

PROPOSED_CHANGE
Do not modify production first. Add QA telemetry for facing-sector transitions and benchmark three candidates:
A) baseline current one-threshold classifier (~49 degrees from horizontal);
B) same center bias but stateful angular hysteresis, initially test approximately 4 degrees on each side of the current boundary (for example remain lateral until >53 degrees, remain vertical until <45 degrees); exact values must be selected by measurement, not assumed;
C) dominant-axis neutral boundary around 45 degrees with smaller hysteresis, only as counterfactual to determine whether the current 1.15 lateral bias itself improves or harms authored 4-direction readability.
Hysteresis must affect presentation facing only. Do not filter, rotate or delay the physics/input vector.

DO_NOT_ASSUME
- Do not assume every diagonal should use a diagonal sprite; Kelo currently has four authored directional rows and may intentionally prefer lateral poses for 45-degree travel.
- Do not assume the 1.15 bias is wrong; it may have been chosen to keep lateral movement visually stable.
- Do not mix this experiment with native LEFT row selection, per-frame foot pivots, cadence changes, DPR, hero 1.20x scaling, bob, lean, shadow or camera changes.
- Do not add time-based debounce before measuring angular hysteresis; fixed millisecond dwell can add visible input-to-facing latency and behave differently at 60/90/120 Hz.

EXPERIMENT
Create a deterministic direction sweep at constant magnitude and constant speed. Sweep joystick/input angle slowly through 35, 40, 44, 46, 48, 49, 50, 52, 54, 58 and 65 degrees from horizontal, then reverse the sweep. Add a noisy boundary trace centered around 49 degrees with deterministic perturbations such as +/-1, +/-2 and +/-4 degrees. Hold each segment long enough for multiple stride frames. Run both right/down and right/up quadrants, then mirrored left quadrants. Run keyboard W+D, S+D, W+A, S+A as exact 45-degree controls. Repeat at 60/90/120 Hz if harness control is available and at mobile 390x844 DPR2 plus desktop 1280x720 DPR1.
Log per update/render: input angle, motion-delta angle, velocity angle, chosen direction source, current face, prior face, face-sector transition count, milliseconds since last face-sector transition, stridePhase, sourceFrame, world position and actual speed.

Candidate B should materially reduce near-boundary toggles (target >=70% reduction as a starting benchmark) while adding no physics latency and keeping intentional facing-change P95 latency below one normal render interval plus the angular crossing requirement. Reject it if users must move the stick noticeably farther than expected to change facing or if diagonal readability worsens.
Required invariants: `worldTraceDelta=0`, `actualSpeedDelta=0`, `colliderDelta=0`, `cameraTraceDelta=0`, `stridePhaseDelta=0` except normal frame presentation mapping, and no added allocations in the hot path after initialization.

RISKS
- Too much hysteresis can make Kelo look like he keeps facing sideways while clearly moving vertically.
- Because current direction source can fall back among displacement, velocity and input, hysteresis may mask rather than reveal a source-consistency problem; telemetry must distinguish source switches.
- Exact keyboard diagonals are deterministic and may intentionally be lateral; changing that policy could regress desktop feel even if touch improves.
- A four-direction sheet inherently has a discontinuity around sector boundaries. Hysteresis reduces chatter but cannot create true diagonal poses.

Do not implement production hysteresis unless the same-trace benchmark demonstrates a clear visual stability win without physics/input changes.
