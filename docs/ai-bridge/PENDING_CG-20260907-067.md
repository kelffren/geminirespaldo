### PROBLEM
The live renderer is intentionally HiDPI and nearest-neighbor, but mobile performance caps the canvas backing-store DPR independently from the physical device DPR. On common high-DPI phones this can create a second, non-integer upscale of the entire canvas after Kelo has already been sampled into the backing store. That means a future avatar increase from 1.15x to 1.20x must not be judged only by source sprite dimensions: whole-canvas backing-store-to-device scaling may be the sharper or noisier link.

### CONFIRMED_IN_GEMINI
- `index.html` styles `#game-canvas` with `image-rendering:pixelated` and `image-rendering:crisp-edges`.
- `engine-h.js::activeDpr()` uses `min(window.devicePixelRatio, dprCap)`, sets `canvas.width/height = CSS size * activeDpr`, restores CSS width/height to viewport CSS pixels, and sets `ctx.setTransform(dpr,...)` plus `imageSmoothingEnabled=false`.
- `src/environment/mobile-performance-contract.js` caps ordinary mobile at DPR 2, low-memory mobile at 1.5, and desktop at 3. Mobile canvas budget is 1.5 MP (0.9 MP low-memory).
- Therefore an ordinary mobile device reporting physical DPR 3 is rendered into a DPR-2 backing store, which the browser must display across a DPR-3 physical surface: final backing-store-to-device scale = 3/2 = 1.5x. A low-memory DPR-3 device using cap 1.5 instead produces a 2x final scale.
- `engine-ab.js` separately forces `ctx.imageSmoothingEnabled=false` around `drawImage(hero...)`; lateral presentation is currently 48 base world px wide and scale 1.15 (55 world px after rounding). The proposed 1.20x QA scale would be about 58 world px wide, without changing collider/physics by design.
- `engine-z.js` then applies zoom 1.05..1.45. At the current Playwright mobile viewport 390x844, target zoom is about 390/(11*32)=1.108.
- `scripts/live-hero-audit.mjs` currently tests mobile with `deviceScaleFactor:2`, exactly matching the ordinary mobile cap. It therefore cannot expose the DPR3->cap2->1.5x final upscale path.
- `hero.PNG` is present as a 2,134,082-byte asset; `engine-ab.js` derives the real runtime frame dimensions from the loaded raster and records them in `KELO_HERO_SPRITE_AUDIT`. Do not assume static 256x384 source-frame dimensions unless the live audit reports them.

### EXTERNAL_EVIDENCE
- MDN `Window.devicePixelRatio` explicitly recommends scaling canvas backing resolution by devicePixelRatio for sharper Retina/high-DPI output and notes modern mobile devices often report DPR >2: https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio
- MDN Canvas optimization guidance likewise sizes the backing canvas from CSS size * DPR and scales the context accordingly: https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas
- MDN's crisp pixel-art guide warns that `image-rendering: pixelated` with non-integer mapping between CSS and device pixels can produce uneven pixel widths/edges; browser/page zoom can trigger the same class of problem: https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look
- MDN confirms `CanvasRenderingContext2D.imageSmoothingEnabled=false` disables smoothing for scaled images, which preserves hard pixels but does not make arbitrary non-integer scale ratios mathematically uniform: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
- W3C/CSSWG issue #5837 documents distortion concerns when pixelated nearest-neighbor scaling is far from an integer scale, especially around 150%: https://github.com/w3c/csswg-drafts/issues/5837
- Counterevidence: rendering at full physical DPR 3 is not automatically acceptable. Kelo's mobile performance contract deliberately limits canvas megapixels and decoded memory; 390x844 at DPR3 alone is ~2.96 MP and exceeds the current ordinary-mobile 1.5 MP canvas budget. Quality cannot be fixed by blindly removing the cap.

### HYPOTHESIS
On DPR3 phones, current cap2 may save fill-rate/memory but introduce visible non-uniform nearest-neighbor post-scaling (1.5x) that can show as uneven edges or temporal shimmer during lateral motion. A DPR-aware cap selection that stays within the same or lower pixel budget but makes physicalDpr/renderDpr an integer (for example DPR3 -> renderDpr1.5 -> final 2x) may produce more stable pixel cadence, though it may lose fine detail because the backing store is lower resolution. Separately, 1.20x may remain source-resolution-safe on mobile because it is still likely downsampling a high-resolution authored frame, but this must be computed from the live audit's actual `frameWidth/frameHeight`, not assumed.

### PROPOSED_CHANGE
Do not change production yet. Extend the live hero audit to model and capture the two-stage scale chain:
1. physical device DPR;
2. active/render DPR after cap;
3. CSS-to-device final scale = physicalDpr / activeDpr;
4. world zoom;
5. actual hero source crop dimensions from live audit;
6. destination hero size in backing pixels and physical device pixels.
Then A/B the current DPR policy against a QA-only integer-final-scale policy that never exceeds the current DPR/canvas-pixel budget. Keep `AVATAR_VISUAL_SCALE`, collider, movement, camera, zoom and smoothing policy identical during this DPR experiment. In a separate trace, compare 1.15x vs 1.20x under the winning DPR policy.

### DO_NOT_ASSUME
- Do not assume DPR3 full-resolution is viable just because it is sharper; it violates the current mobile pixel budget at 390x844.
- Do not assume DPR1.5 is better than DPR2 on DPR3; lower backing resolution may erase facial/limb detail even if its final upscale is integer.
- Do not assume `image-rendering:pixelated` and `imageSmoothingEnabled=false` solve non-integer sampling artifacts.
- Do not change filtering and avatar scale in the same candidate.
- Do not change collider, footRoot, depthRoot, camera, world speed or gait to compensate for a render-quality issue.
- Do not hardcode 256x384 as the real frame size; use live `sheetWidth/frameWidth/frameHeight` from `KELO_HERO_SPRITE_AUDIT`.

### RISKS
- Integer-final-scale rendering at a lower backing DPR may look steadier but softer/coarser.
- A full DPR3 buffer can exceed the mobile canvas budget and hurt FPS, memory and thermal behavior.
- Browser implementations of `pixelated`/`crisp-edges` differ, so Chrome-only screenshots are not universal proof.
- A prettier idle screenshot may hide temporal shimmer; decision must include moving traces.
- The current `Math.round()` hero destination position (CG-20260907-062) can confound edge-jitter measurements; first hold that behavior identical across candidates and report it as a fixed confounder rather than fixing both at once.
