### PROBLEM
GC-20260909-004 correctly separated combat aim-facing from locomotion-facing: move RIGHT while aiming UP now preserves `_face=up` for combat and Character Appearance intentionally renders the UP row. However, the locomotion frame index still advances from actual resolved movement distance. With the current single full-body four-direction hero sheet, this means a player can travel laterally RIGHT while visibly cycling the authored UP walk row. That is semantically a strafe, but Kelo has no authored forward/back/strafe locomotion basis relative to aim; it is reusing a forward-facing directional walk cycle for orthogonal travel. The gameplay aim fix is correct, but presentation can therefore look like sideways sliding or moonwalking during PvP strafing. This is a NEW consequence of current main after GC-004 and should not be solved by merging aim-facing back into movement-facing.

### EXTERNAL_EVIDENCE
- Unity's official 2D Blend Tree documentation explicitly treats strafing and forward velocity as separate 2D animation parameters; its example uses velocityX for strafing and velocityZ for forward speed. This supports modeling locomotion relative to facing rather than assuming one world-direction row can represent every move/aim combination: https://docs.unity3d.com/cn/2018.3/Manual/BlendTree-2DBlending.html
- Unity's current SimpleDirectional2D API describes distinct motions such as walk forward, walk backward, walk left and walk right, and separately aim up/down/left/right. This supports the distinction between aim direction and locomotion direction without implying Kelo needs Unity-style blending: https://docs.unity3d.com/cn/6000.0/ScriptReference/Animations.BlendTreeType.SimpleDirectional2D.html
- A community/GitHub counterexample shows some 2D projects intentionally restrict movement to one axis/direction at a time because their sprite content cannot represent combined directions. That demonstrates the asset limitation is real, but Kelo should NOT adopt that restriction because free movement is a PvP requirement: https://github.com/syarul/tstl-2d-sprite-demo
- Godot/GitHub rendering reports show pixel-perfect sprites can exhibit additional jitter from subpixel/camera interactions. Therefore a visual strafe test must compare actor-relative feet/body motion and not attribute every screen-space artifact to row selection: https://github.com/godotengine/godot/issues/35606
- Counterevidence: a full-body sprite facing aim while translating sideways is not automatically wrong; many games intentionally show strafing this way. The issue exists only if the authored UP/DOWN/LEFT/RIGHT walk cycles visibly imply travel in their facing direction and therefore create support-foot slip when used orthogonally. Measure before changing.

### HYPOTHESIS
Kelo's new aim-facing separation is gameplay-correct but presentation-incomplete. The current four-direction full-body sheet lacks an explicit relative locomotion semantic, so orthogonal/opposed move-vs-aim combinations may look less planted than same-direction travel. The correct next step is to measure move-vs-aim angular mismatch and visible support-foot slip, then choose the smallest presentation policy that preserves aim readability without reintroducing movement-driven attack-facing.

A likely short-term improvement, if baseline confirms the problem, is NOT to discard combat aim-facing. First test whether combat-facing should dominate the body only during recent/active aim or attack commitment, while ordinary PvP locomotion outside an aim-activity window uses locomotion-facing. `pvp-world.js` already tracks `lastAimActivity`; the renderer currently ignores freshness and treats combat mode itself as permanent aim authority. This can reduce persistent sideways-sliding after aim input goes stale while preserving correct facing during actual attacks.

Long-term, if active strafing itself still looks wrong, the asset/presentation contract likely needs explicit `forward/back/strafeLeft/strafeRight` clips or a modular lower-body locomotion layer. A single full-body four-row sheet cannot perfectly express independent aim and travel vectors in all combinations.

### PROPOSED_CHANGE
Do not change production from research alone. Benchmark in this order:

A. Baseline current behavior. Build a deterministic matrix of movement direction versus aim direction in PvP while preserving current GC-004 logic. Measure same-direction, 90° strafe, and 180° backpedal cases.

B. Telemetry-only classification. Compute the signed angle between resolved locomotion vector and aim vector and classify `forward`, `strafe-left`, `strafe-right`, `backward`, `idle`. Publish this as presentation telemetry only; do not alter physics, aim, hit geometry, speed, stride or server state.

C. Aim-freshness presentation policy, only if baseline shows stale-aim sliding is a major contributor. During active attack/cast or recent meaningful aim input, keep combat aim-facing exactly as now. After an evidence-based inactivity window, allow locomotion-facing to drive the idle/walk row while retaining the stored gameplay aim vector. Reuse `lastAimActivity`/existing PvP state if safely exposed; do not duplicate an aim timer inside Character Appearance.

D. If active 90° strafing remains visually poor, benchmark authored strafe assets or a lower-body locomotion layer as a CONTENT/PRESENTATION capability. Keep aim upper-body/attack direction authoritative. Do not fake it by rotating the current PNG or restricting movement to four directions.

E. Do not attempt 1.20x scale in the same experiment. Once a winning strafe policy exists, rerun the identical matrix at 1.20x because larger avatars amplify foot-slide and row mismatch.

### RISKS
- Falling back to locomotion-facing too soon can make the body turn away from the attack cursor immediately before an attack and reduce PvP readability.
- Falling back too late leaves the current sliding issue unchanged.
- Mouse users generate frequent aim updates, while touch/controller may have different aim cadence; one hardcoded timeout may not generalize.
- Full-body authored strafe assets multiply content/QA and need per-frame foot anchors, visual bounds, equipment compatibility and future 1.20x validation.
- Lower-body/upper-body modular animation would be more scalable but is a larger capability and should not be created until the four-row limitation is objectively demonstrated.
