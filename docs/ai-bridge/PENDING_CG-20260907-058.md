### PROBLEM
The lateral gait is distance-driven, which is the correct direction for refresh-rate independence, but `engine-ac.js` applies `MIN_VISUAL_MOVE_PX = 0.12` to each individual update and then immediately overwrites `v.lastX/v.lastY`. Any displacement smaller than 0.12 world px in that update is discarded rather than accumulated. Because the main loop is requestAnimationFrame-driven, higher refresh rates create smaller per-update displacements. The result is a refresh-rate-dependent low-speed band where Kelo physically moves but `stridePhase` and the lateral source frame do not advance.

### CONFIRMED_IN_GEMINI
Current `main` at `ae0df96f5d496872aff791db9af1184b61d26978` loads `engine-ac.js?v=222`; `engine-ac.js` is still the live gait owner after `engine-ab.js`.

`engine-b.js` owns the live RAF loop:

```js
let lastTime = performance.now();
function gameLoop(currentTime) {
  const dt = Math.min((currentTime - lastTime) / 1000, 0.1);
  lastTime = currentTime;
  processInput(); updateMovement(dt); updateCamera(dt); updateSimulation(dt); render();
  requestAnimationFrame(gameLoop);
}
```

`engine-ac.js` defines:

```js
const MIN_VISUAL_MOVE_PX = 0.12;
...
const dx = p.x - v.lastX;
const dy = p.y - v.lastY;
const dist = Math.hypot(dx, dy);
...
v.lastStepDistancePx = dist > MIN_VISUAL_MOVE_PX ? dist : 0;
...
if (v.on && v.lastStepDistancePx > 0) {
  v.strideDistancePx += v.lastStepDistancePx;
  v.stridePhase = (v.stridePhase + v.lastStepDistancePx / v.cycleWorldPx) % 1;
  v.frame = Math.floor(v.stridePhase * 4) % 4;
}
...
v.lastX = p.x;
v.lastY = p.y;
```

Therefore a 0.10 px step is not carried into the next frame; it is lost from gait accounting.

For low input magnitudes (`mag <= 0.48`), `speedFor(mag)` returns 110 world px/s and DIRECT movement produces approximately `speed = 110 * mag`.

The minimum physical speed that yields a per-frame displacement above 0.12 px is therefore approximately:

- 60 Hz: 0.12 * 60 = 7.2 px/s => processed magnitude ~0.0655.
- 90 Hz: 10.8 px/s => processed magnitude ~0.0982.
- 120 Hz: 14.4 px/s => processed magnitude ~0.1309.

With the current 72 px joystick radius and 0.045 deadzone, those processed magnitudes correspond approximately to raw thumb radii from origin of:

- 60 Hz: 7.74 px.
- 90 Hz: 9.99 px.
- 120 Hz: 12.24 px.

So there is a real mathematical band in which the avatar moves in world space while the lateral animation remains on one pose, and that band gets materially larger at high refresh rate.

This is separate from the already-known collision-recovery contamination in CG-20260907-056: here even clean free-space locomotion can lose gait distance.

### EXTERNAL_EVIDENCE
1. MDN `requestAnimationFrame()` states that callback frequency generally follows display refresh rate and explicitly calls out 60, 75, 120 and 144 Hz. It warns that animation progression must use elapsed time or equivalent timing so behavior does not change on high-refresh displays: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame
2. Gaffer on Games, `Fix Your Timestep!`, explains that when time/distance is accumulated across variable render frames, the remainder must be carried forward rather than thrown away; the accumulator pattern exists specifically so high-rate frames do not lose partial progress: https://gafferongames.com/post/fix_your_timestep/
3. WHATWG issue #5025 documents that modern devices increasingly use 90/120/144 Hz and that browser RAF behavior can vary across high-refresh hardware, reinforcing that code should not encode behavior in per-frame thresholds: https://github.com/whatwg/html/issues/5025
4. W3C HTML issue #375 discusses detecting dropped/skipped RAF frames and refresh-rate variability for games: https://github.com/w3c/html/issues/375
5. Community counterexamples around pixel/subpixel movement show that discarding or snapping fractional movement can create jitter or rate-dependent motion, while retaining subpixel remainders is a common solution. Example: https://www.reddit.com/r/gamedev/comments/1l2u8eg

Counterevidence: the current 0.12 threshold likely exists to prevent tiny collision/camera/subpixel noise from advancing the gait. Removing the threshold outright could reintroduce idle foot twitch or make collision recovery noise advance frames. Therefore the recommendation is not `MIN_VISUAL_MOVE_PX = 0`; it is to preserve the anti-noise threshold while accumulating legitimate locomotor distance until it exceeds the threshold.

### HYPOTHESIS
If legitimate free-space locomotor displacement is accumulated in a residual bucket instead of discarded every frame, then the same joystick magnitude and same world distance will produce materially closer stride-phase/frame traces at 60/90/120 Hz, especially between processed magnitude ~0.065 and ~0.131, without increasing idle jitter.

### PROPOSED_CHANGE
Do not refactor the loop or convert physics to fixed timestep in this experiment.

First add QA telemetry to prove the loss:

- `rawFrameDistancePx`
- `discardedBelowThresholdDistancePx`
- `cumulativeDiscardedBelowThresholdDistancePx`
- `gaitResidualDistancePx`
- `strideConsumedDistancePx`
- `processedMag`
- `rafDtMs`

Candidate A: current baseline.

Candidate B: add a residual accumulator owned by visual gait. Legitimate locomotor distance below 0.12 px is added to `gaitResidualDistancePx`; only when residual + current legitimate distance exceeds the threshold is that accumulated distance consumed into `strideDistancePx/stridePhase`. Reset residual on true idle/release and on teleports/warps; do not let collision depenetration from CG-20260907-056 enter this bucket once that separation exists.

Pseudo-contract, not implementation-ready code:

```js
residual += legitimateLocomotorDist;
if (residual >= MIN_VISUAL_MOVE_PX) {
  const consumed = residual;
  residual = 0;
  advanceStride(consumed);
}
```

A more stable variant may consume fixed threshold quanta and retain the remainder rather than draining the entire bucket. Benchmark both before choosing.

### RISKS
- Accumulating all movement blindly can include collision depenetration, teleports or clamp corrections; integrate with the locomotor-distance separation from CG-20260907-056 rather than hiding that problem.
- Draining the whole residual bucket at once can create a small periodic pose jump at very low speed. Consuming threshold quanta and retaining remainder may be smoother.
- A visually animated gait at extremely tiny joystick magnitudes may look busier than the current planted pose. If so, the product decision may be to define an explicit visual locomotion minimum in world-speed units, not a per-frame pixel threshold.
- Synthetic 60/90/120 stepping proves rate dependence in logic but does not replace real mobile Safari/Chrome high-refresh verification.
