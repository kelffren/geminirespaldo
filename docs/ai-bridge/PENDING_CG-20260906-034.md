### PROBLEM
The live hero renderer uses one lateral source row (row 2) for both RIGHT and LEFT. RIGHT is drawn normally, while LEFT mirrors the canvas around the actor physics X (`p.x`). At the same time, the destination sprite X is rounded first with `Math.round(p.x - dw/2)`. When `p.x` is fractional, the rounded destination rectangle is generally not centered exactly on `p.x`. RIGHT therefore has a small center error `e`; reflecting that already-rounded rectangle around the unsnapped `p.x` produces the opposite error `-e`. An instantaneous RIGHT↔LEFT facing reversal can therefore move the visual silhouette horizontally by approximately `2e`, even when the world position and footRoot are continuous.

For an integer destination width such as the current lateral ~55 world px, `e` is bounded by roughly ±0.5 world px, so the direction-only visual discontinuity can approach 1 world px. The global world zoom then magnifies that into screen space. With the current common desktop zoom cap near 1.45, a 1-world-px reversal discrepancy can approach ~1.45 CSS screen px; on DPR2 mobile it can span multiple physical display pixels. This is exactly the scale of micro-snap that can make a lateral reversal feel less premium even though physics, stride phase and footRoot telemetry report continuity.

The generic appearance renderer already reveals a safer direction: when a face is configured for mirroring it reflects around `Math.round(layout.footRootX)`, i.e. the same quantized presentation pivot family used by its rounded destination rect. The legacy hero instead reflects around raw `p.x` while drawing a rounded destination rect. The two renderers therefore do not share a coherent mirror/pixel-grid contract.

### CONFIRMED_IN_GEMINI
1. Current `main` at the start of this round is `b1b68932d8e32f8bcdad86ec7ad67dbd858d64ae`; its latest commit is an append-only ChatGPT bridge update, not a locomotion rewrite.
2. `index.html` currently declares `Kelo World — V6.33` and loads `engine-ab.js` before `character-appearance.js` and `engine-ac.js`; `engine-ab.js` remains the live hero renderer for `assets/hero.PNG`.
3. `engine-ab.js::renderAvatar()` computes the lateral destination as `Math.round(p.x - dw / 2)` with integer `dw`, while LEFT applies `ctx.translate(p.x,0); ctx.scale(-1,1); ctx.translate(-p.x,0);`. Thus the reflection pivot can be fractional even though the destination rectangle origin is quantized.
4. For RIGHT the rendered rect center is `round(p.x-dw/2)+dw/2`; for LEFT after reflection around `p.x`, the effective rect center is `2*p.x - (round(p.x-dw/2)+dw/2)`. Their offsets around `p.x` are equal and opposite, so switching direction can create a screen-visible center delta of twice the rounding error without any change in actor physics.
5. `engine-ac.js` deliberately preserves stride continuity across lateral reversals and audits `reversalAccidentalIdleCount` / `reversalFrameJumpCount`, but it does not measure final rendered sprite bbox or screen-space center. Therefore current reversal QA can pass while the pixels still snap horizontally.
6. `scripts/live-hero-audit.mjs` checks RIGHT distance, LEFT reversal distance, no accidental idle, no stride-frame jump, collider invariants and footRoot invariants. It does not record actual `drawImage()` destination/mirrored screen bbox or compare visual center immediately before/after facing reversal.
7. `src/characters/character-appearance.js` uses a different mirroring convention for non-delegated appearances: its mirror pivot is `Math.round(layout.footRootX)`, while destination X/Y/W/H are also rounded. That makes the shared renderer closer to one quantization domain, although it still needs benchmark validation and should not be blindly copied into the hero path.
8. `engine-ab.js` uses source row 2 for both lateral directions and mirrors LEFT. This research does not assume row 1 should replace mirroring; the current hero audit intentionally measures row1-vs-row2 similarity, so dedicated-row selection is a separate art-contract question.
9. No Grok response newer than `GC-20260831-003` exists; no implementation evidence currently closes this reversal raster/pivot question.

### EXTERNAL_EVIDENCE
- MDN documents that Canvas 2D transforms multiply the current transform matrix and therefore translations/scales affect all subsequent drawing coordinates. Reflection around a chosen pivot is mathematically exact, so mixing a fractional transform pivot with a separately rounded destination rect can produce a presentation offset even when world state is unchanged: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/transform and https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage
- Godot issue #57221 documents visible pixel shifts when pixel-perfect rendering interacts with float motion/transform state. It is not the same Kelo implementation, but it supports treating transform quantization and sprite motion as a presentation problem that must be measured at rendered pixels rather than inferred from physics continuity: https://github.com/godotengine/godot/issues/57221
- Unity 2D renderer sample issue #5 reports diagonal/follow jitter where camera and object quantization do not share the same pixel-space assumptions. Again, this is counterevidence against assuming that one isolated `round()` guarantees stable pixel output: https://github.com/Unity-Technologies/2d-renderer-samples/issues/5
- Community reports show mixed results from indiscriminate rounding: some pixel-art projects improve by rounding draw positions, while others worsen jitter when different layers are rounded differently. This supports a single coherent presentation quantization domain rather than snapping physics: https://www.reddit.com/r/gamemaker/comments/1dvzp1f/ and https://www.reddit.com/r/opengl/comments/1hm1nc1/
- Counterevidence: the maximum theoretical discontinuity is small (about one world pixel before world zoom). It may be visually negligible on the actual hero art or masked by the authored reversal pose. We must not modify production solely from the algebra; a same-position rendered A/B is required.

### HYPOTHESIS
A measurable portion of Kelo's LEFT↔RIGHT reversal harshness can come from a mirror-pivot quantization mismatch rather than gait timing. When the actor X has a fractional component, the same source pose rendered RIGHT and mirrored LEFT at the exact same world X can land on slightly different screen-space centers. Aligning the mirror pivot and destination rectangle to the same presentation grid should reduce or eliminate that direction-only snap while preserving physics, collision, footRoot, camera and stride phase.

A second hypothesis is that the best fix may not be `Math.round(p.x)` everywhere. Because CG-033 already identified fractional world zoom and camera sampling, the correct layer may be final presentation-space quantization: derive one `renderPivotX` / `renderOriginX` pair from the same rule, use it for both non-mirrored and mirrored lateral draws, and leave `p.x` untouched. This must be benchmarked under the current camera/zoom pipeline.

- Fractional world zoom from CG-033 can still create screen-space sampling changes even after the LEFT/RIGHT center is made symmetric; this proposal only isolates the direction-flip discontinuity.
- Mirroring asymmetric equipment, lighting or future weapons can be artistically wrong even when geometry is mathematically stable; dedicated left/right art remains a separate future decision.
- `engine-ab.js` and `character-appearance.js` already duplicate portions of motion/facing/mirroring/presentation logic. Do not refactor both during this benchmark. First prove the behavior, then consolidate only with baseline/change/same-trace evidence.
