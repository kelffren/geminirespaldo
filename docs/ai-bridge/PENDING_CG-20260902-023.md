### PROBLEM
The production PNG avatar is positioned with `Math.round(...)` in world coordinates before camera/zoom transforms are applied. This can discard real sub-world-pixel lateral motion from presentation even while physics remains continuous. Because the later camera transform can scale one world unit to 1.05–1.45 CSS pixels, a one-world-pixel presentation step can become a visibly larger screen-space step. The risk is strongest during slow analog WALK and high-refresh operation, exactly where Kelo is supposed to look planted and premium.

This is separate from CG-021. CG-021 concerns stride-distance loss caused by the update-side `0.12 px` gate. CG-023 concerns raster presentation of the body after a valid world position already exists.

### CONFIRMED_IN_GEMINI

1. `index.html` is currently `Kelo World — V6.05` and loads the production hero override from `engine-ab.js?v=149`, `engine-ac.js?v=220`, the HiDPI/plaza wrapper from `engine-l.js?v=222`, and zoom from `engine-z.js?v=94`.

2. `engine-ab.js` positions the production sprite destination with:
   - `Math.round(p.x - dw / 2)`
   - `Math.round(footY - dh)`
   and positions the name with `Math.round(p.x)` / `Math.round(footY - dh - 6)`.
   Therefore sprite-body and nameplate world positions are quantized independently to integer world units before any later zoom transform.

3. `engine-a.js` keeps physics positions as floating-point values (`localPlayer.x += vx*dt`, `localPlayer.y += vy*dt`). `CONFIG.roundPixels` currently defaults to `false`; that switch only affects the base camera `camX/camY` path and does not disable the unconditional `Math.round` inside the production hero renderer.

4. `engine-l.js::applyHiDPI()` sets a DPR transform (`ctx.setTransform(dpr,0,0,dpr,0,0)`) and disables image smoothing. The canvas backing store can therefore be 1–3× CSS resolution while world-space hero coordinates are still integer-snapped before camera/zoom composition.

5. `engine-z.js` clamps `CONFIG.zoom` to 1.05–1.45. In any zoomed world pass, one integer world-coordinate presentation step corresponds to approximately 1.05–1.45 CSS px, or about 3.15–4.35 physical device pixels at DPR 3.

6. For a representative slow WALK magnitude 0.08 under the current movement model, physical speed is about 8.8 world px/s. If presentation is integer-snapped, a new horizontal integer position becomes available only about every `1/8.8 = 113.6 ms` in a frozen-camera trace. At zoom 1.45 that implies hold-then-jump presentation of about 1.45 CSS px rather than continuous ~0.073 CSS px steps at 120 Hz. At magnitude 0.20 (~22 world px/s), the integer-position cadence is still only about once every 45.5 ms.

7. `index.html` also applies `image-rendering: pixelated` / `crisp-edges` to the canvas and `engine-ab.js` disables Canvas image smoothing for the sprite. Kelo therefore currently has multiple simultaneous sampling/snap policies: CSS pixelated canvas presentation, HiDPI backing-store scaling, world-space integer sprite placement, nearest-style draw sampling, and variable camera zoom.

8. `ENGINE_MAP.md` remains stale: it names `engine-m.js` as hero sprite owner, but the live `index.html` loads `engine-ab.js` later and `engine-ab.js` overrides `renderAvatar`. Treat current runtime code, not the map label, as authority for this experiment.

### EXTERNAL_EVIDENCE
- MDN documents that `CanvasRenderingContext2D.drawImage()` accepts destination coordinates (`dx`, `dy`) in the current canvas coordinate system; it does not require integer destination coordinates. This means floating destination coordinates are a supported baseline candidate rather than an invalid Canvas use.
- MDN documents that `CanvasRenderingContext2D.scale()` changes the size of a canvas unit. Thus a one-world-unit snap made before a 1.45× camera scale becomes a 1.45 CSS-pixel screen displacement.
- MDN documents that `imageSmoothingEnabled=false` controls interpolation when images are scaled; it is not itself a position-rounding requirement.
- Current PixiJS documentation exposes `roundPixels` as an explicit optional rendering choice (`0` no rounding, `1` nearest-pixel rounding), supporting the architectural point that position rounding is a policy to benchmark, not a universal requirement.
- PixiJS issue #5748 and #6676 provide counterevidence that nearest sampling, integer positioning, scaling, DPR/platform behavior, and atlas padding can interact in non-obvious ways; integer coordinates alone do not guarantee artifact-free output across browsers/devices.
- Community reports in Godot/GameMaker/Raylib repeatedly show a trade-off: subpixel motion can shimmer, while aggressive rounding can produce low-speed judder. These reports are anecdotal, not proof for Kelo, and are included specifically to justify an A/B/C measurement rather than assuming either policy is correct.

### HYPOTHESIS
The current unconditional world-space `Math.round` in `engine-ab.js` is likely contributing measurable low-speed lateral judder, especially at 90/120 Hz and zoom >1, because it collapses many valid physics updates into identical presentation coordinates and then emits a larger integer-world jump.

A better policy may be either:
A. allow the hero to use floating world destination coordinates while preserving nearest image sampling; or
B. snap the final composed foot/body position to the physical device-pixel grid after camera + zoom + DPR are known, instead of snapping to one whole world unit before projection.

This is NOT yet a recommendation to remove all rounding. Pixel-art sharpness may regress under floating placement, and a transform-aware screen/device-pixel snap may outperform both the current policy and fully floating rendering.

### PROPOSED_CHANGE
No production change in this research round.

Benchmark three isolated presentation policies behind a narrow test flag or harness override:

A — CURRENT_WORLD_ROUND
- Keep current `Math.round(p.x - dw/2)` / `Math.round(footY-dh)`.

B — FLOAT_WORLD
- Pass floating destination x/y to `drawImage`.
- Do not change physics, stride, camera, zoom, `imageSmoothingEnabled`, sprite dimensions, collider, or nameplate policy in the same test.

C — FINAL_DEVICE_PIXEL_SNAP
- Compute the intended world-space sprite/foot position continuously.
- Project through the actual current CTM/camera/zoom/DPR.
- Snap the final screen position to the nearest physical device pixel (not nearest world unit), then map the correction back consistently for drawing.
- Body, mirror pivot and nameplate must use the same chosen presentation anchor; do not independently round each element.

Do not choose B or C by visual intuition alone.

### DO_NOT_ASSUME
- Do not assume `imageSmoothingEnabled=false` requires integer world coordinates.
- Do not assume floating draw coordinates will be sharper; nearest sampling at fractional transforms can shimmer.
- Do not assume integer rounding is universally better for pixel art; Kelo's production hero is a large source sprite aggressively downscaled into ~48×81 world px and then scaled again by camera zoom/DPR.
- Do not change `CONFIG.roundPixels`, camera damping/dead-zone, zoom policy, avatar scale, aspect ratio, sprite atlas, stride cadence, foot planting, or fountain compositor in this experiment.
- Do not use the current multiple-pass fountain case as the primary deciding trace until CG-022 is instrumented; use an open area first so duplicate actor passes do not contaminate the result.
- Do not claim a visible bug from code math alone. Measure actual screen position and capture visual evidence.

### RISKS
- FLOAT_WORLD may trade coarse judder for edge shimmer with nearest sampling, especially at fractional zoom.
- FINAL_DEVICE_PIXEL_SNAP can be implemented incorrectly if DPR and current CTM are confused; snapping CSS pixels instead of device pixels can still produce uneven physical-pixel motion.
- Independent snapping of body, mirror pivot, nameplate or shadow would create relative jitter; presentation components must share a semantic root.
- Existing duplicate/multi-pass actor rendering near the fountain can make any sampling policy look worse or better unpredictably; isolate open-area baseline first.
- A larger avatar may make both quantization and sampling artifacts easier to see, so current-scale winner must be revalidated before SCL-002.
- Browser differences, especially iOS Safari and non-integer DPR, may change the winner. Desktop Chrome alone is insufficient.
