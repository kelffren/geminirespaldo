### PROBLEM
The production hero renderer performs full-sheet color-key transparency conversion in the browser after the PNG has already loaded and can already be rendered. `engine-ab.js` first assigns `sheet = raw` and `ok = true`, then schedules `knockWhite()` through `requestIdleCallback(..., {timeout:900})` (or `setTimeout`). `knockWhite()` creates another full-size canvas, draws the entire source sheet, calls `getImageData()` for the entire image, scans every RGBA pixel in JavaScript, sets alpha to zero for RGB values >232 on all channels, calls `putImageData()`, and finally replaces `sheet` with the processed canvas.

This creates two separate concerns relevant to current movement/scale work:
1. performance: an unpredictable full-image readback + JS scan + writeback happens on the main thread after boot, potentially during active movement on busy mobile devices when the 900 ms timeout fires;
2. presentation continuity: the renderer can use the original PNG for early frames and then hot-swap to the processed canvas later, so the same pose may change its edge/background alpha treatment during play.

### CONFIRMED_IN_GEMINI
At base commit `d543b2bc...` and V6.23:
- `index.html` preloads `assets/hero.PNG` and loads `engine-ab.js?v=240` before `engine-ac.js?v=220`; later `armor-aura.js` wraps the final `renderAvatar` but does not replace the hero sheet preprocessing path.
- `assets/hero.PNG` is present as one 2,134,082-byte repository asset (blob `8319a904...`).
- `engine-ab.js::raw.onload` calls `useRawSheet()` immediately, which sets `sheet=raw`, derives `FW/FH` from runtime image dimensions, and sets `ok=true`.
- The same onload then schedules `knockWhite()` with `requestIdleCallback(later,{timeout:900})`, falling back to `setTimeout(later,0)` where requestIdleCallback is absent.
- `knockWhite()` allocates a new canvas at `raw.width × raw.height`, requests a 2D context with `{willReadFrequently:true}`, draws the full PNG, retrieves the full canvas with `getImageData`, loops `for (let i=0; i<d.length; i+=4)`, zeros alpha for pixels where R/G/B are all >232, then `putImageData()` and assigns `sheet=c`.
- `renderAvatar()` uses whichever object `sheet` currently references. There is no generation/version flag, no transition fence, no measurement around the swap, and no assertion that raw and processed visual output are identical except for intended background pixels.
- `src/systems/performance-governor.js` measures frame EMA and has `registerTexture`, but current `engine-ab.js` neither registers raw/canvas hero texture memory nor reports the preprocessing duration/transient allocation. Its governor therefore cannot currently explain a one-time hero preprocessing spike.
- Current movement gait and stride in `engine-ac.js` are independent of this preprocessing, so this can be benchmarked while preserving the exact world trace, collider, stridePhase and camera trace.

### EXTERNAL_EVIDENCE
1. MDN `CanvasRenderingContext2D.getImageData()` documents that the default `rgba-unorm8` representation uses a `Uint8ClampedArray`, i.e. four 8-bit components per pixel. A full-sheet read therefore materializes width×height×4 bytes of pixel data in addition to the canvas backing store and decoded source representation. Source: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/getImageData
2. MDN `requestIdleCallback()` explicitly says that if a timeout expires, the callback is queued even if doing so risks a negative performance impact. Kelo sets a 900 ms timeout, so “scheduled idle” is not evidence that the full scan cannot land during animation/input. Source: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback
3. MDN Background Tasks guidance warns idle tasks not to overrun the available budget and notes that timeout-forced work can create lag or animation stutter. Kelo's callback does not inspect `deadline.timeRemaining()` or chunk work; it performs the whole read/scan/write in one callback. Source: https://developer.mozilla.org/en-US/docs/Web/API/Background_Tasks_API
4. WHATWG issue #5614 introduced `willReadFrequently` specifically as a hint for canvases that are read frequently with `getImageData`; this supports Kelo's hint syntactically but is counterevidence against treating that flag as the main fix because Kelo performs one large preprocessing pass, not a sustained repeated-read workload. Source: https://github.com/whatwg/html/issues/5614
5. Konva issue #293 documents severe cross-browser slowdown around `getImageData()` on large canvases/high-memory scenes, with behavior differing by browser. It is not proof Kelo hitches, but it supports benchmarking on mobile browsers instead of assuming desktop behavior. Source: https://github.com/konvajs/konva/issues/293
6. Reddit reports around large-image `getImageData()` show inconsistent browser/device behavior, including cases where large backing images dominate cost. This is community evidence only, not authoritative performance data, and reinforces the need for Kelo-specific traces. Source: https://www.reddit.com/r/firefox/comments/jdbw0s/why_is_getimagedata_so_slow_in_this_case/

### HYPOTHESIS
If the intended transparent hero can be authored/preprocessed once as an asset (or if `hero.PNG` already has acceptable alpha and the runtime white-key pass is unnecessary), removing the full-sheet runtime read/scan/write and texture hot-swap will improve boot/movement frame stability on weaker mobile hardware and make sprite sampling/scaling experiments more deterministic.

A secondary hypothesis is that the threshold `(R>232 && G>232 && B>232)` may erase legitimate near-white highlights inside armor/clothing, and that the effect becomes more visible at 1.15x/1.25x. This is NOT confirmed; it must be checked by comparing pixel masks and screenshots.

### PROPOSED_CHANGE
Do not refactor production blindly. Benchmark these variants with the same hero and trace:

A — BASELINE_RUNTIME_KEY
- current behavior: raw hero renders immediately, full-sheet `knockWhite()` later, then `sheet` hot-swaps.

B — PREPROCESSED_ASSET
- create an offline/export-time transparent hero asset using the exact current >232 RGB rule first, so the visual delta is controlled;
- load only that asset in runtime;
- no `getImageData`, per-pixel JS loop, `putImageData`, or sheet hot-swap;
- preserve rows/columns/frame source geometry exactly.

C — RAW_NO_KEY_DIAGNOSTIC
- diagnostic only if raw alpha/background is already acceptable;
- skip runtime `knockWhite()` and compare output to baseline after preprocessing.

Do not combine this experiment with presentationScale, smoothing, zoom, stride, footRoot, depth or atlas-redesign changes.

If B wins, a later cleanup can delete the runtime color-key path and register the hero texture with `KELO_PERF.registerTexture`. Do not perform that deletion until same-trace and screenshot evidence exists.

### DO_NOT_ASSUME
- Do not assume `requestIdleCallback` makes the current pass free; the 900 ms timeout can force it onto the event loop when no idle budget is available.
- Do not assume `{willReadFrequently:true}` solves the one-time full-sheet scan; it is mainly a repeated-read optimization hint.
- Do not assume the PNG runtime dimensions from the fallback `FW=256/FH=384`; log `raw.naturalWidth/raw.naturalHeight` first.
- Do not assume compressed file size (2.13 MB) equals decoded or transient memory.
- Do not assume the >232 white-key threshold removes only background; compare masks for legitimate white highlights.
- Do not change collider, camera, movement, stride cadence, presentation scale, zoom or filtering in this benchmark.
- Do not call this a fixed performance problem without a measured baseline and after trace.

### RISKS
- Offline preprocessing with the current threshold can permanently bake a bad mask if near-white costume highlights are being removed; first reproduce the exact baseline rule and inspect the result.
- If the raw PNG intentionally contains a white matte around antialiased edges, merely zeroing bright pixels can leave fringe colors; a properly authored alpha asset may require art cleanup rather than only reproducing the threshold.
- A second asset can accidentally drift in frame dimensions/padding and break foot alignment; preserve exact sheet geometry in B.
- Browser memory APIs are incomplete; do not present estimates as measured RAM/VRAM.
- Removing the runtime canvas may change how nearest-neighbor sampling behaves if source pixel content or alpha differs. Compare screenshots before combining with CG-20260904-005 scale/filter work.
- The performance governor currently does not account for the hero's raw/processed texture copies, so its `textureMB` is not a valid deciding metric for this experiment until instrumentation is added.
