### PROBLEM
V6.18 changed hero loading so `assets/hero.PNG` is used immediately, then `engine-ab.js` asynchronously creates a second full-size canvas, reads all pixels, and sets alpha=0 for every pixel whose R/G/B are all >232. When that work completes it replaces the global `sheet` reference with the processed canvas. This creates two distinct visual representations of the same hero during one page session: raw PNG first, threshold-keyed canvas later. The key is color-only and global; it does not know whether a near-white pixel is background, an intentional highlight/detail inside the character, or antialiased edge color. Before increasing avatar size, Kelo needs one deterministic source sprite with verified alpha/fidelity.

### CONFIRMED_IN_GEMINI
At current `main` baseline `63a3732df74c24c4fb30e411084166a58b61f465`, visible title `Kelo World — V6.18`:

1. `index.html` preloads `assets/hero.PNG` with `fetchpriority="high"` and loads `engine-ab.js?v=240`.
2. Commit `1cae269ac06712760ce8405c2907ee64a4c5b7d6` explicitly changed `engine-ab.js` from processing before first use to `useRawSheet()` immediately and `knockWhite()` later.
3. `raw.onload` now calls `useRawSheet()`, making `sheet=raw` and `ok=true` before background cleanup.
4. The later callback is scheduled via `requestIdleCallback(later,{timeout:900})` when available, otherwise `setTimeout(later,0)`.
5. `knockWhite()` allocates a canvas at `raw.width × raw.height`, draws the whole sheet, calls `getImageData()` over the whole sheet, loops every RGBA pixel, and sets alpha to zero whenever `R>232 && G>232 && B>232`; it then `putImageData()`s the result and assigns `sheet=c`.
6. Therefore a render before the callback can sample the raw PNG while the next render after the callback can sample the processed canvas without any locomotion/state transition.
7. The threshold test ignores source alpha, connectedness to the background, frame cell, semantic sprite region, and neighboring pixels. Any intentional near-white opaque pixel meeting the threshold is made fully transparent.
8. The visible renderer keeps `imageSmoothingEnabled=false`, so any removed/high-contrast pixels can become more obvious when the body is enlarged with nearest-neighbor sampling.
9. `engine-ab.js` currently carries several responsibilities in one file: hero asset load/preprocess, legacy non-local movement detection, face/frame selection, sprite draw/mirroring, and nameplate drawing. This is a responsibility-density observation, not a refactor request.
10. I could not directly inspect `assets/hero.PNG` pixel values in this run because the available GitHub text connector rejects binary file payloads and the sandbox has no direct GitHub network access. Therefore the number/location of pixels affected by `>232` is NOT confirmed and must be measured before changing production.
11. `engine-ac.js` remains unchanged in the relevant locomotion path: stride is still distance-driven and frame selection still uses four equal phase quarters. This entry does not alter cadence, stop, reversal, collider, or camera semantics.
12. The V6.18 preload/cache commit (`9ef01410fe832fc46db13c080a868481cf56cdcd`) improves early discovery of the hero resource, but preload does not remove the later raw→processed representation swap inside `engine-ab.js`.

### EXTERNAL_EVIDENCE
1. MDN documents that PNG has full alpha-transparency support across major browsers. A production sprite can therefore carry authored transparency directly rather than requiring a color-threshold key at runtime when the asset pipeline can provide correct alpha. https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Image_types
2. MDN documents `imageSmoothingEnabled=false` as the way to retain hard pixel edges when enlarging pixel art. That makes source-pixel correctness more important: threshold mistakes are not blurred away during upscale. https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
3. MDN documents that `getImageData()` reads full pixel data and that `willReadFrequently` is a context hint associated with software acceleration/readback behavior. Kelo only does this once per load, so this is not automatically a performance bug, but it is real full-sheet CPU/readback work and extra temporary memory that should be measured on mobile. https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/getImageData and https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/getContextAttributes
4. MDN marks `requestIdleCallback()` as limited-availability/non-Baseline. Kelo's fallback is `setTimeout(...,0)`, so the timing of the raw→processed swap is browser-dependent by design. https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback
5. web.dev's July 2026 preload guidance supports preloading critical images with `fetchpriority="high"`; the new V6.18 preload itself is directionally sound for discoverability, but it is orthogonal to pixel preprocessing correctness. https://web.dev/articles/preload-responsive-images
6. Community sprite workflows warn that chroma-key/background colors must not also appear in the sprite itself; otherwise those sprite pixels become transparent. Example discussion: https://www.reddit.com/r/RPGMaker/comments/172q5pc/ . A recent 2026 game-art discussion also notes that thresholding a flattened matte can leave or damage antialiased edge pixels and recommends authored alpha/defringing instead of naïve replacement: https://www.reddit.com/r/aigamedev/comments/1veb525/
7. Counterevidence: if `hero.PNG` genuinely contains a pure/near-white matte and no intended near-white character pixels, the current threshold may be visually acceptable and the one-time processing cost may be negligible. This must be decided from the actual asset and same-snapshot screenshots, not from theory.

### HYPOTHESIS
The premium path is likely to be a single deterministic hero atlas with final alpha authored/precomputed before runtime. If runtime cleanup must remain temporarily, it should not allow the player to see one source representation and then silently switch to another, and the cleanup mask should be proven not to delete intended character pixels. Larger 1.15x/1.25x rendering will amplify holes, edge chatter and silhouette changes caused by source-alpha mistakes.

### PROPOSED_CHANGE
P0 — Do not change production yet. First obtain/export the actual hero PNG pixel data in a benchmark environment and quantify what `knockWhite()` changes.

P1 — Create an asset audit script/harness that computes: source dimensions, source alpha histogram, count of pixels satisfying the >232 threshold, how many of those are already transparent, connected-to-border vs interior near-white pixels, per-frame affected-pixel counts, and bounding boxes of changed pixels.

P2 — Capture deterministic same-pose screenshots immediately after raw sheet readiness and after `knockWhite()` completion with movement/camera frozen. Produce a pixel-diff mask and classify whether changes are background-only, edge cleanup, or destruction of visible character detail.

P3 — Candidate A baseline: current raw→idle threshold swap.

P4 — Candidate B deterministic processed-before-visible: only if runtime thresholding is proven visually correct, keep hero fallback/procedural visible until processing completes, then switch once. This removes raw→processed hero popping but can delay PNG availability; benchmark startup latency.

P5 — Candidate C preferred asset pipeline: export a final `hero` atlas with authored alpha, remove `getImageData/putImageData` runtime cleanup entirely, and render the same immutable source from first visible PNG frame onward. Preserve the same frame grid and visual dimensions for the first comparison.

P6 — If a matte must be keyed programmatically, do not assume a global RGB threshold is sufficient. Evaluate border-connected background selection plus edge/defringe handling offline, then save the result as an asset. Do not add a per-frame runtime chroma-key algorithm.

P7 — Only after a deterministic alpha source wins at current size, repeat the exact same sprite at 1.15x and 1.25x under nearest-neighbor and the current camera/DPR matrix from earlier research.

P8 — Defer any architectural split of `engine-ab.js` until baseline/change measurements exist. A future clean separation could be asset preparation, presentation-state selection, body draw and nameplate draw, but no blind refactor is proposed here.

### DO_NOT_ASSUME
- Do not assume every RGB>232 pixel is background.
- Do not assume the raw PNG is already visually correct; inspect alpha/matte first.
- Do not assume the processed version is better merely because background white disappears.
- Do not judge threshold correctness only on a dark Plaza background; test light and dark scene regions.
- Do not combine this A/B with gait cadence, subpixel snapping, shadow, bob, lean, reversal, depth-envelope or collider changes.
- Do not lower source resolution to save preprocessing cost before measuring quality at 1.15x/1.25x.
- Do not migrate to WebGL/WebGPU for this issue; it is primarily an asset/presentation determinism problem.

### RISKS
- An offline-alpha replacement can accidentally alter crop/padding or frame dimensions; lock sheet dimensions and per-cell registration for the first A/B.
- Waiting for processed-before-visible can regress perceived startup if preprocessing is slow, so it is only a transitional candidate, not automatically the final architecture.
- Border-connected keying can fail if the matte has gaps or if white background is enclosed by sprite geometry; asset inspection must decide.
- Nearest-neighbor scaling at non-integer projected scale can still shimmer even with perfect alpha; that remains CG-20260903-010 scope.
- Browser scheduling differences can make the swap hard to reproduce if tests do not log which sheet representation rendered each frame.
- The inability of this ChatGPT run to read binary asset bytes means pixel-severity claims would be speculative until Grok/CI performs the audit.
