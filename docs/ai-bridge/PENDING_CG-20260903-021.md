### PROBLEM
Current V6.18 no longer uses the eased physical reversal described by older reversal research. `engine-ac.js` now explicitly sets `CONFIG.movementType = 'DIRECT'`. With DIRECT movement, `engine-a.js::updateMovement()` assigns `localPlayer.vx/velocity` directly from the current processed input target every update. A steady full RIGHT command followed immediately by full LEFT can therefore change horizontal velocity from approximately +185.28 px/s to -185.28 px/s in one logical update, with no physical zero-cross interval or braking phase.

This is responsive, but it removes the short physical turn window that previous contact-aware reversal hypotheses expected to use for a planted turn. `engine-ac.js::updateVisualMotion()` runs after movement and derives direction from the new post-movement displacement first, so the sprite can also flip/mirror in that same update. The current four-frame side row has no explicit turn/contact state. With a larger avatar, stronger arm swing, lean, shadow anchoring and more leg detail, an instantaneous 370.56 px/s signed velocity delta plus same-update mirror can look weightless even when input latency is excellent.

The goal is not to reintroduce slippery movement. The new question is narrower: can Kelo keep instant RELEASE/STOP responsiveness while giving hard LEFT↔RIGHT reversals a very short, measurable turn/braking contract, or is a presentation-only plant visually sufficient?

### CONFIRMED_IN_GEMINI
At live `main` base `646c07db98aba2c9a55146e680320f2692673cdc`:

1. `index.html` declares `Kelo World — V6.18` and loads `engine-ab.js?v=240`, `engine-ac.js?v=220`, then later `engine-ah.js?v=94`.
2. `engine-ac.js` currently sets `WALK_SPEED=110`, `RUN_SPEED=178`, `MAX_SPEED = 178 + (1-0.74)*28 = 185.28 px/s`, `GAIT_RUN_START=0.70`, `joystickDeadzone=0.045`, `joystickCurve='LINEAR'`, `joystickRadius=72`, and critically `CONFIG.movementType='DIRECT'`.
3. The same file also writes `CONFIG.accelDecay=32` and `CONFIG.decelDecay=18`, but those values are not used by `engine-a.js::updateMovement()` while movementType is DIRECT. This is a concrete dead-configuration/redundancy signal: the variables look active but are bypassed by the chosen branch.
4. `engine-a.js::updateMovement(dt)` computes `targetVx=input.normX*CONFIG.speed` / `targetVy=...`. In DIRECT mode it performs `localPlayer.vx=targetVx; localPlayer.vy=targetVy` with no interpolation before integrating position.
5. Keyboard cardinal input is normalized to magnitude 1. Therefore current full keyboard RUN uses the current maximum speed cap and a direct RIGHT→LEFT switch can assign +185.28→-185.28 px/s in one call. Signed delta magnitude is 370.56 px/s. This is a code-derived value, not a runtime measured acceleration.
6. `engine-ac.js` wraps `updateMovement`, chooses gait/speed before the base call, then calls `updateVisualMotion()` after the position has already moved. In an unobstructed hard reversal, the post-movement `dx` already has the new sign, so visual facing can flip in the same logical update.
7. The current reversal therefore does not have a physical zero-cross event for presentation to synchronize against. Older calculations that predicted several updates of braking before sign change are no longer compatible with current main.
8. Git history confirms the behavior changed intentionally in commit `8c2dc8975da4d64b4c62d5125891345c53fd3c96`, message `Softer joystick: linear curve, smaller deadzone, direct move`. Its patch added `CONFIG.movementType='DIRECT'` plus the current joystick settings and speed increases.
9. Immediately before that commit (`130b35a430366095a44344c82bb096d08c9c99cc`), `engine-ac.js` did not override movementType, so base `engine-a.js` remained on its MICRO_ACC path. Research written against the earlier acceleration path must therefore be revalidated rather than reused.
10. `engine-ah.js` still wraps updateMovement and hard-zeros velocity when there is no move input. Under current DIRECT movement, a normal release already targets zero in the base movement function, so this wrapper is largely redundant for ordinary release. It remains loaded and should not be removed blindly because edge cases/touch/build-mode behavior must be traced first.
11. `engine-ac.js` preserves `stridePhase` across active movement/reversal and the renderer mirrors the side row for LEFT. There is still no authored reversal/contact metadata.
12. `ENGINE_MAP.md` correctly identifies `engine-a.js` as base movement owner, `engine-ac.js` as gait/speed support and `engine-ah.js` as hard-stop support, but it does not currently call out that DIRECT bypasses the configured accel/decel constants.

### EXTERNAL_EVIDENCE
1. Epic/Unreal's current `UCharacterMovementComponent::CalcVelocity` documentation explicitly models velocity updates with separate friction, acceleration/deceleration and `BrakingDeceleration`, demonstrating that responsive character controllers commonly treat requested acceleration and braking as tunable movement semantics rather than forcing every direction change to be an instantaneous velocity assignment. Source: Epic Developer Community, `UCharacterMovementComponent::CalcVelocity`.
2. Epic also exposes separate braking friction specifically for slowing a character to a stop, supporting an asymmetric contract where release braking and change-of-direction behavior can be tuned independently instead of sharing one global smoothing rule. Source: Epic `bUseSeparateBrakingFriction` / `BrakingFriction` docs.
3. The open-source Unity `LocomotionSystem` by Rune Skovbo Johansen explicitly discusses fast opposite-direction changes where movement direction can change faster than facing and treats locomotion presentation as the layer that makes that behavior believable. It also emphasizes matching native animation speed/foot motion to world speed. This supports measuring physics and presentation separately rather than assuming one must own the entire effect.
4. A recent Godot physics issue (#101052) shows a useful counterexample: directly assigning character velocity each frame does not guarantee visually/physically simple outcomes once collisions participate. Kelo's reversal benchmark therefore must include open space and collision/corner traces before changing controller semantics.
5. Community counterevidence is strong: game developers frequently prefer immediate directional response and report that inertia/coasting can make controls feel worse for games that demand precision. A July 2026 r/gamedev discussion specifically contrasts unwanted release inertia with games that stop when input stops. Therefore the proposal must preserve release stop and reject any candidate that feels slippery.
6. Another community pattern for Sonic-like/high-momentum controllers uses stronger deceleration specifically while velocity and requested direction have opposite signs, then accelerates into the new direction. This is not authoritative and does not prescribe Kelo's constants, but it is evidence for testing reversal-specific rather than universal smoothing.

### HYPOTHESIS
A tiny reversal-specific physical bridge may produce a more premium planted LEFT↔RIGHT turn without sacrificing the user's current responsive release behavior. The strongest candidate is NOT to switch the entire controller back to generic MICRO_ACC. Instead, keep start and release policy effectively direct, detect an established opposite-sign lateral reversal, and allow velocity to cross zero over a very short bounded interval before accelerating into the new side.

Candidate analytical reference only: the already-configured but currently bypassed `accelDecay=32` would have a first-order continuous half-life of ln(2)/32 ≈ 21.7 ms toward an opposite target. That is a useful benchmark reference, not a recommended shipping constant. A 20–40 ms physical reversal bridge is short enough to test while still clearly different from a one-update sign flip.

A second viable possibility is that physics should remain completely DIRECT and the needed weight can be achieved presentation-only (contact pose, lean reversal, arm-swing reversal, shadow/foot anchoring). This is safer for control feel but risks backward-skating if the sprite intentionally holds the old side while world movement has already reversed. The A/B experiment must decide.

### PROPOSED_CHANGE
Do not modify production blindly. Reproduce current main first.

**A — BASELINE_DIRECT**
- Keep current V6.18 exactly as-is.
- Instrument opposite-direction intent, pre/post velocity, position delta, facing, stride phase/frame and camera response.
- Establish whether reversal visually reads as weightless/pop at current scale before changing anything.

**B — PRESENTATION_ONLY_REVERSAL**
- Keep physics/world trace byte-for-byte equivalent to A.
- Add only an auditable presentation state around same-update LEFT↔RIGHT flip.
- Test a contact/lean bridge only after current atlas frames are classified.
- Hard rejection criterion: if sprite faces/leans against actual travel for a visible interval and creates moonwalk/backward-skate, reject B.

**C — REVERSAL_ONLY_VELOCITY_BRIDGE**
- Preserve DIRECT response for idle→move and preserve immediate release stop.
- Only when horizontal intent is strongly opposite established horizontal travel, move `vx` toward the opposite target through a short deterministic zero-cross instead of assigning the new sign immediately.
- Do not add universal release coast.
- Start with a parameterized harness flag, not a hard-coded production constant.
- Test reference zero-cross targets near ~16, 24, 32, 40 and 50 ms; do not assume the existing `accelDecay=32` is optimal.
- Keep vertical component and diagonals explicitly measured; do not accidentally distort diagonal speed normalization.

**D — GLOBAL_MICRO_ACC CONTROL**
- As a comparison only, temporarily test existing MICRO_ACC branch using the already-configured 32/18 values while `engine-ah` remains in place.
- This helps determine whether existing machinery already produces desirable turn weight, but do NOT ship it merely because it is simpler. It changes acceleration from rest as well as reversal and can alter control feel beyond the intended scope.

**E — CLEANUP ONLY AFTER WINNER**
- If DIRECT remains the chosen production mode, either remove/deprecate misleading unused accel/decel assignments in `engine-ac.js` or document that they are inactive/reference-only.
- If a reversal-specific bridge wins, give it a clearly named owner/config; do not overload generic accelDecay with two semantics.
- Re-evaluate whether `engine-ah` still has a unique job after the controller contract is finalized. No blind wrapper deletion.

### DO_NOT_ASSUME
- Do not assume physical inertia is automatically more premium. Precision/control may win.
- Do not make release coast. Current immediate stop is a valuable responsiveness invariant unless the user explicitly changes that goal.
- Do not make a turn animation block input.
- Do not use render-frame counts for a reversal timer.
- Do not force frame 0 as a plant before the current atlas contacts are verified.
- Do not enlarge collider radius 20.
- Do not combine reversal physics with camera-deadzone, stride-threshold CG-020, sprite scale, subpixel sampling or aura/depth fixes in the same A/B.
- Do not reuse old ~40–50 ms zero-cross predictions from pre-DIRECT builds as current behavior; they are obsolete on V6.18.
- Do not remove `engine-ah` simply because DIRECT makes its ordinary-release action redundant; first trace touch-active deadzone, build mode, UI focus and any wrappers that depend on the post-call zeroing.

### EXPERIMENT
Baseline → one candidate → same trace → re-measure.

**Trace R1 — cardinal hard reversal**
1. Open collision-free flat area; freeze camera for the first visual capture.
2. Hold RIGHT until stable full speed.
3. Switch to full LEFT on a known logical update with no neutral interval.
4. Hold until stable LEFT, then mirror LEFT→RIGHT.
5. Repeat 30 times each direction.
6. Run deterministic dt sequences equivalent to 60/90/120 Hz where harness permits; log actual update cadence rather than assuming display Hz equals simulation Hz.

**Trace R2 — walk/analog reversal**
Repeat at processed magnitudes 0.30, 0.60, 0.699, 0.80 and 1.00 so WALK and RUN behavior are both covered. Include actual touch hardware later if synthetic analog passes.

**Trace R3 — release invariant**
At the same magnitudes, release to neutral instead of reversing. Any candidate C must preserve current release-to-zero response within one logical update/tolerance and must not add coast distance.

**Trace R4 — diagonal reversal**
RIGHT+UP→LEFT+UP, RIGHT+DOWN→LEFT+DOWN and mirrored cases. Confirm magnitude normalization, direction-family behavior and vertical trajectory are not unintentionally altered.

**Trace R5 — collision/corner**
Repeat a lateral reversal while sliding along a representative wall and near a corner. Because `engine-a.js` resolves X/Y collisions separately, ensure a reversal bridge does not create extra penetration/push artifacts.

**Trace R6 — presentation capture**
For A/B/C, crop the hero from 120 ms before to 160 ms after reversal. Record stride phase, rendered column, mirror state and any identifiable planted foot. Repeat current scale first; only after a winner test 1.15x and 1.25x.

Decision rule:
- Reject any candidate that adds noticeable release inertia, collision regressions or directional input lag.
- Prefer C over A only if it materially reduces reversal pop/weightlessness and the added reversal latency/distance remains below a measured perceptual cost.

### RISKS
- Even 20–40 ms of physical turn bridge can feel worse in PvP or tight obstacle navigation; moving-video preference and control metrics matter more than theoretical realism.
- Presentation-only planting can create moonwalk because current DIRECT physics already travels the new direction immediately.
- A generic MICRO_ACC toggle changes start acceleration too, so it is not an isolated test of reversal and can lead to the wrong conclusion.
- Axis-specific reversal handling can distort diagonals if vector magnitude is not re-normalized/limited carefully.
- Collision response may interact with a short velocity bridge differently near walls/corners; open-space success is insufficient.
- Current 4-frame atlas may not have a usable plant pose; a physics improvement cannot compensate for missing artwork indefinitely.
- CG-20260903-020's destructive 0.12px stride gate remains unresolved and can contaminate low-speed animation measurements. Log raw/credited stride distance and avoid using very-low-speed animation results as sole evidence.
- Larger sprites will magnify a mirror/pose discontinuity, but scale must not be changed until the current-size movement candidate is chosen.
