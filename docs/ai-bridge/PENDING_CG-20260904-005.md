### PROBLEM

The user wants the hero visually larger (candidate 1.15x/1.25x) while preserving premium lateral motion, crispness and mobile/desktop performance. Current runtime draws the same large 4x4 source sheet into a small world-space destination, disables image smoothing, and then applies a later world zoom that is often fractional. Before creating a larger asset or changing filtering, we need to separate three questions: source resolution sufficiency, destination-area render cost, and resampling quality.

### CONFIRMED_IN_GEMINI

At base commit `b8fcfbfb...`:

1. `index.html` declares `Kelo World — V6.22`, preloads `assets/hero.PNG`, loads `engine-ab.js?v=240`, `engine-ac.js?v=220`, and later loads `performance-governor.js`.
2. `engine-ab.js` treats the hero as a 4-column x 4-row sheet. It initializes frame dimensions to `FW=256`, `FH=384`, then on load derives `FW=raw.width/4`, `FH=raw.height/4`. The current asset blob is `8319a904...` and GitHub reports file size `2,134,082` bytes. The connector could not decode the binary image dimensions in this run, so exact current PNG dimensions MUST be captured at runtime (`raw.naturalWidth/Height`) before relying on the 256x384 initial defaults.
3. Current lateral destination width is `dw=48`; vertical width is `54`; destination height is `round(54*(FH/FW))`. The source crop removes ~5% per horizontal side and ~4% per vertical side before drawing.
4. `engine-ab.js` explicitly sets `ctx.imageSmoothingEnabled=false` during hero draw.
5. `engine-c.js` subsequently renders the world under `ctx.scale(CONFIG.zoom, CONFIG.zoom)`.
6. `engine-z.js` is the late zoom writer and sets zoom from viewport width, clamped to `1.05..1.45`. Therefore final projected scale is often fractional.
7. `engine-h.js` has an earlier DPR-aware `pixelPerfectZoom()` policy, but `engine-z.js` overwrites the final zoom. `engine-h.js` still creates a HiDPI backing store up to DPR 3 and globally disables smoothing.
8. Increasing only hero destination `dw/dh` does NOT create a second hero texture and does NOT increase the decoded source texture dimensions. The source-sheet memory is therefore invariant with presentation scale. What grows is the number of destination/backing pixels touched by each actor draw. A 1.25x width+height change increases destination area by 1.25^2 = 1.5625 (56.25%) per hero draw before considering overdraw/depth wrappers.
9. The current performance governor can report FPS/frameMs and register texture dimensions, but `engine-ab.js` does not currently register `hero.PNG` with `KELO_PERF.registerTexture`, nor does it expose source dimensions/presentation scale in its audit surface.
10. The current hero draw still has filtering/scale ownership spread across `engine-ab` (source crop + destination size + per-draw smoothing), `engine-c` (world transform), `engine-h` (DPR/backing store + pixel-perfect intent) and `engine-z` (final zoom). Do not refactor all four in one experiment.

### EXTERNAL_EVIDENCE

1. MDN `CanvasRenderingContext2D.imageSmoothingEnabled` documents that disabling smoothing preserves hard pixels when scaled, especially for pixel art, but it does not claim that arbitrary non-integer resampling or large downscales are visually optimal: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
2. MDN `CanvasRenderingContext2D.scale()` confirms that canvas transforms multiply the final size of drawing units, so the hero destination draw is subsequently rescaled again by the world zoom: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/scale
3. CSSWG issue #5837 documents distortion with nearest-neighbor/pixelated rendering at non-integer scale factors (example 150%), supporting a benchmark rather than assuming `smoothing=false` + fractional zoom is automatically pixel-perfect: https://github.com/w3c/csswg-drafts/issues/5837
4. Community reports show the countervailing tradeoff: integer/point scaling gives crisp static pixel art, while non-integer movement/camera projection can create jitter/uneven pixel widths; solving one by indiscriminate smoothing can make the image softer. Example: https://www.reddit.com/r/gamedev/comments/1i36sr3/

### HYPOTHESIS

The present hero sheet likely has enough source resolution to make Kelo 1.15x or 1.25x larger without needing a higher-resolution runtime texture. In fact, if the source frame is substantially larger than the current 48x~81 destination, a modestly larger destination reduces the downscale ratio and may reveal more authored detail. The main quality risk is not source exhaustion but the current two-stage scale chain: large source -> small nearest-neighbor destination -> fractional world zoom/DPR projection. The main performance risk is destination fill/overdraw, especially when depth wrappers redraw actors, not texture memory growth.

A pre-baked presentation atlas at the chosen world-space size may eventually outperform repeated high-resolution runtime downsampling and produce more deterministic pixels, but that should be tested only after choosing the winning visual scale/filter policy.

### RISKS

- Actor redraw wrappers can make the scale cost look worse than the nominal 56.25% area increase; measure actual `heroDrawCountPerRAF` rather than multiplying one draw by actor count blindly.
- Browser Canvas2D rasterization cost is implementation/hardware dependent, so desktop measurements do not replace mobile measurements.
- Smoothing=true may score better on some edge-difference metrics while looking softer; include a human visual gate for sprite character/style.
- Offline pre-baking can accidentally change alpha, palette or foot alignment if done before the presentation contract is finalized.
- If the hero sheet contains anti-aliased/high-resolution art rather than strict pixel art, nearest-neighbor downsampling may alias fine details differently at 48, 55 and 60 world px; that is exactly what this benchmark should expose.
