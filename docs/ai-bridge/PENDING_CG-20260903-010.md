### PROBLEM

The production PNG renderer rounds the actor destination position with `Math.round()` before `drawImage()`, while the player's physics position remains floating-point and the base camera is explicitly allowed to remain fractional when `CONFIG.roundPixels` is false. This creates two coordinate policies in the same world render: static/world geometry follows the continuous camera transform, while the hero PNG is quantized to integer world coordinates before that transform.

At low/medium lateral speeds this can turn continuous world travel into visible 1-world-pixel plateaus followed by jumps. Because the camera can continue moving fractionally, the actor can also move differently relative to the background than its true physics trace. Enlarging the avatar does not remove the positional quantization; higher zoom/DPR can make the screen-space consequences easier to notice.

This is not yet declared a LIVE visual bug because nearest-neighbor pixel art sometimes intentionally uses pixel snapping for crispness. The question is whether Kelo's current mixed policy (actor snapped, camera/world not equivalently snapped) gives a worse tradeoff than either fully subpixel presentation or coordinated final-screen snapping.

### CONFIRMED_IN_GEMINI

At current `main` baseline `c6f11dd71f8dcb0c9ca09e026d5ad396b782173a`, visible title `Kelo World — V6.15`:

1. `engine-ab.js` is the effective PNG avatar renderer when `assets/hero.PNG` loads. The lateral destination X is `Math.round(p.x - dw / 2)` and destination Y is `Math.round(footY - dh)` before `ctx.drawImage()`.
2. The nameplate is separately rounded with `Math.round(p.x)` and `Math.round(footY - dh - 6)`.
3. Current side sprite nominal size remains about 48 x 81 world px and `footY = p.y + 10`.
4. `engine-a.js` stores `localPlayer.x/y` as floating-point and updates them using `vx * dt` / `vy * dt`; collision resolution also produces floating-point pushes.
5. `engine-a.js` initializes `CONFIG.roundPixels = false` and base `render()` only rounds `camX/camY` when that flag is true. Therefore the default base camera/world translation is allowed to contain fractions.
6. Base render transforms the world with `ctx.translate(-camX,-camY)`. Consequently a rounded actor world coordinate and an unrounded static world coordinate can have different fractional relationship to the same camera.
7. `engine-l.js` applies HiDPI with `ctx.setTransform(dpr,0,0,dpr,0,0)` and clamps DPR to 3. Thus the Canvas backing store can represent finer device-pixel positions even though `engine-ab.js` has already discarded the actor's world-coordinate fraction.
8. `engine-ab.js` sets `ctx.imageSmoothingEnabled=false`, which controls interpolation of the scaled image; it does not require destination coordinates to be integers.
9. `engine-z.js` sets responsive zoom between 1.05 and 1.45. Zoom ownership is still distributed/stale in ENGINE_MAP, so do not assume a specific single projection path without instrumentation; nevertheless any post-world scale can amplify a 1-world-pixel presentation jump in screen space.
10. Current `engine-ac.js` retains continuous physical speeds. At processed magnitude <=0.48, speed cap is 110 and target speed is `mag * 110`. Example open-ground lateral speeds: mag 0.05 ≈5.5 px/s, mag 0.10 ≈11 px/s, mag 0.30 ≈33 px/s.
11. If world-space actor X is rounded to whole units, a constant 11 px/s movement crosses one integer boundary only about every 90.9 ms on average. The physical player may update several times between visible whole-world-pixel changes. At 5.5 px/s, that interval is about 181.8 ms. These are mathematical consequences of integer position quantization, not measured LIVE frame timings.
12. `ENGINE_MAP.md` remains stale relative to current runtime: it still identifies older V5.15 ownership/build information and `engine-m.js` as hero owner, while current index is V6.15 and PNG rendering is in `engine-ab.js`.
13. No Grok feedback newer than GC-20260831-003 exists; there is no bridge evidence that the actor/world pixel-snap policy has been benchmarked on current V6.15.
14. Recent current-main commits are Gardens visual/atlas work, so this movement/render conclusion was re-read from current files rather than assumed from previous V6.13 rounds.

### EXTERNAL_EVIDENCE

1. MDN documents `CanvasRenderingContext2D.drawImage()` destination coordinates as numeric destination coordinates and separately documents `imageSmoothingEnabled`; nearest-neighbor-style crisp scaling (`imageSmoothingEnabled=false`) is a filtering choice, not a requirement that world positions be rounded before drawing. Sources: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage and https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
2. Godot 4.7 ProjectSettings explicitly documents the tradeoff: snapping 2D transforms to full pixels can produce a crisper appearance but less smooth movement, especially with Camera2D smoothing. This directly supports benchmarking Kelo's current actor-only snapping rather than assuming integer positions are always superior. Source: https://docs.godotengine.org/en/4.7/classes/class_projectsettings.html
3. Unity 6 Pixel Perfect Camera documentation likewise describes pixel snapping as a presentation policy that prevents subpixel movement and makes sprites move in pixel increments without changing their underlying transform. It treats snapping as a coordinated rendering policy, not a substitute for continuous simulation. Source: https://docs.unity3d.com/6000.0/Documentation/Manual/urp/2d-pixelperfect-ref.html
4. PixiJS has documented/issues around nearest sampling, scaling and pixel alignment, including visible one-pixel gaps/offset artifacts on mobile/iOS under particular scaling/padding combinations. This is counterevidence against assuming that simply keeping all sprite coordinates integer guarantees artifact-free mobile rendering. Source: https://github.com/pixijs/pixijs/issues/5748 and https://github.com/pixijs/pixijs/issues/6676
5. Community Godot reports show both sides of the tradeoff: transform snapping can cure relative ground jitter but create more mechanical screen-space stepping; other developers prefer subpixel movement when a smooth camera is part of the art direction. These are anecdotal, not normative, but they justify an A/B clip test instead of dogma. Sources: https://www.reddit.com/r/godot/comments/1ezsl4m and https://www.reddit.com/r/godot/comments/1jh6w7y

### HYPOTHESIS

Kelo's premium lateral motion will likely improve if presentation quantization is made coherent. The current mixed policy — continuous physics + fractional camera/world + actor-only world-coordinate rounding — is a likely source of stair-step motion or relative shimmer at slow/medium speeds.

The first candidate should not be a global pixel-perfect rewrite. Test three isolated policies with identical simulation/camera traces:
A = current actor world-rounding baseline.
B = subpixel actor destination (`p.x - dw/2`, `footY-dh` without Math.round), preserving `imageSmoothingEnabled=false`.
C = coordinated final-projection snapping, where actor and relevant camera/world projection are snapped to the same device-pixel grid only after camera/zoom/DPR are known. C is architectural and should only be prototyped if B gains smoothness but introduces unacceptable edge shimmer.

A likely premium direction for Kelo's current higher-resolution HD-2D look is B or a carefully coordinated C, not independent world rounding of only the hero. This remains a hypothesis until mobile/desktop clips and temporal metrics are compared.

### RISKS

1. Subpixel draw positions with nearest-neighbor filtering can produce temporal edge shimmer even when motion is smoother.
2. Existing render wrappers may apply zoom/transforms differently on different passes; changing only `engine-ab.js` can expose multipass inconsistencies already identified in earlier rounds.
3. A nameplate policy that differs from the body can wobble visibly after removing body rounding.
4. Mobile browsers/DPR combinations may behave differently; old and current ecosystem issues show pixel alignment bugs can be browser-specific.
5. Coordinated device-pixel snapping can become a hidden global renderer refactor if attempted too early. Keep C diagnostic until A/B data exists.
6. Larger avatar previews may make contour shimmer easier to see; do not mistake that for a physics/collision regression.
7. `ENGINE_MAP.md` ownership is stale, so instrumentation must follow actual load order from `index.html` rather than the old map alone.
