### PROBLEM
CG-083 correctly identified the existing foot-pivot transform path as the right place to test locomotion lean/squash instead of adding another renderer wrapper. Current main reveals a more specific ownership problem inside that path: `src/visuals/visual-integration.js` applies the sampled transform to the Canvas 2D context, then renders `actorBackFX`, calls the entire final `renderAvatar()`, renders `actorFrontFX`, and only then restores the context. The live PNG `renderAvatar()` in `engine-ab.js` draws both the body sprite and the nameplate. Therefore any transform clip—existing action transforms today, or a future locomotion lean/squash/bob—also transforms the nameplate. Actor FX on both sides inherit the same transform too, regardless of whether a particular FX should be BODY_LOCAL or GROUND_LOCAL. This is a semantic-layer problem, not a physics problem.

### CONFIRMED_IN_GEMINI
- Current main inspected for this entry is `3a08ee5357d24b0aa731e86c941c088c53ecd928`; `index.html` declares Kelo World V6.53 and loads `engine-ab.js` before the visual stack, with `src/visuals/visual-integration.js?v=2` near the end of the page. Thus the final bridge wraps the already-installed PNG avatar renderer.
- `engine-ab.js` live PNG renderer draws the sprite, restores its local left-facing mirror transform, then separately calls `ctx.fillText(...)` for the nameplate inside the same `renderAvatar()` function. The nameplate anchor comes from the foot-root presentation contract, but the text draw is still inside the outer caller's current transformation matrix.
- `src/visuals/visual-integration.js::installActorBridge()` saves the context, applies animation offset, translates to semantic `foot` pivot, applies rotation and scale, translates back, renders `actorBackFX`, calls `base(actor,isSelf)`, renders `actorFrontFX`, and only after all of that calls `g.restore()`. Therefore the base avatar—including its `fillText()` nameplate—is under the body transform.
- `src/visuals/animation-system.js` confirms transform clips can provide `scaleX`, `scaleY`, `rotation`, `offsetX`, and `offsetY`, and the semantic `foot` anchor is derived from `KELO_AVATAR_PRESENTATION` when available.
- `src/visuals/visual-manifests.js` already contains real transform clips (`cast_magic_01`, `cast_self_01`). `cast_magic_01` reaches roughly scaleX 0.96/scaleY 1.04 with -0.035 rad rotation and later scaleX 1.07/scaleY 0.96 with +0.045 rad rotation. So transform leakage is not merely hypothetical future locomotion code; the current generic action path is capable of rotating/scaling the nameplate today whenever that clip is active.
- The same wrapper renders both `actorBackFX` and `actorFrontFX` under the transform. Some ACTOR-space FX (head/hand/body attachments) may correctly want BODY_LOCAL inheritance, but a future ground contact effect, shadow, aura, or foot ring should not automatically lean/squash with the torso.
- This extends rather than repeats CG-083: CG-083 established transform ownership should reuse the existing foot-pivot system; CG-085 establishes that the existing boundary is too broad for locomotion because it also owns overlay text and all actor FX.

### EXTERNAL_EVIDENCE
- MDN Canvas 2D documents that the current transformation matrix applies to painting text as well as shapes. `scale()`, `rotate()`, and `translate()` alter the coordinate system for subsequent draws, so a `fillText()` called before restore inherits those transforms. This directly matches Gemini's wrapper behavior: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D and https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/scale
- MDN also documents `setTransform()`/reset semantics, supporting an explicit transform boundary rather than counter-scaling text heuristically: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/setTransform
- Godot issue #78394 documents that GUI/Control nodes such as Label have distinct rendering/sorting behavior from Node2D world objects, illustrating why UI-like overlays need deliberate ownership rather than assuming they behave like body sprites: https://github.com/godotengine/godot/issues/78394
- Godot issue #93003 shows 2D origin plus negative scale can produce transform instability/flicker in a real engine. It is not evidence that Gemini has the same bug, but it is counterevidence against adding more nested scale/flip transforms without measuring temporal stability: https://github.com/godotengine/godot/issues/93003
- Community evidence: a Godot user reported labels becoming flipped because an ancestor character node carried negative scale, and the fix was to stop inheriting that visual flip at the label level. This is directly analogous to keeping Kelo's nameplate out of character-facing/body transforms: https://www.reddit.com/r/godot/comments/16kbvg9/
- Counterevidence: world-space labels can intentionally scale with the world/camera, and community examples use labels as children when that behavior is desired. Therefore the goal is NOT to make Kelo's nameplate pure screen-space UI; it should still follow world position/camera zoom. The narrower requirement is that BODY_LOCAL lean/squash/flip must not distort its glyphs.

### HYPOTHESIS
Split avatar presentation into semantic transform domains while preserving one final integration owner: GROUND_LOCAL for shadow/ground rings/depth contact; BODY_LOCAL for PNG body plus body-attached FX and future locomotion lean/squash/bob; OVERLAY_LOCAL for nameplate and similar readable overlays. OVERLAY_LOCAL should follow the actor/nameplate anchor and global camera/world transform, but should not inherit BODY_LOCAL rotation, non-uniform scale, mirror, or body bob unless explicitly authored. This should allow premium micro-lean/squash without making text wobble, stretch or rotate.

### PROPOSED_CHANGE
Do not modify production before baseline measurement. Preferred implementation shape if the benchmark confirms leakage is visible/relevant:
1. Refactor the live avatar renderer into an explicit body draw and overlay draw (for example `renderAvatarBody()` + `renderAvatarOverlay()` behind the existing public `renderAvatar()` compatibility boundary), rather than installing another generic wrapper.
2. In `visual-integration.js`, save context; apply BODY_LOCAL transform around semantic foot pivot; render body-attached back FX + avatar body + body-attached front FX; restore BODY_LOCAL transform; then render overlay/nameplate from its semantic anchor with only the normal world/camera transform.
3. Classify FX by transform space, not merely front/back layer. Existing head/hand/center actor FX may remain BODY_LOCAL; future shadow/aura/ground ring must be GROUND_LOCAL. Do not infer ground/body ownership only from `actorBackFX` vs `actorFrontFX`.
4. Preserve the public `renderAvatar(actor,isSelf)` entry point for plaza/depth callers and remote actors until call-site audit proves a safer migration. Avoid wrapper proliferation.
5. Do not add locomotion lean/squash in the same production commit that changes the render boundary. First prove the layer split preserves baseline pixels when transform is identity; then test a QA-only micro-transform using the same trace.

### DO_NOT_ASSUME
- Do not assume the current nameplate distortion is visually severe merely because code proves transform inheritance; measure the real action clip and future QA locomotion transform.
- Do not move the nameplate to DOM/UI screen space by default. It should remain world-anchored unless a separate design decision says otherwise.
- Do not counter-rotate/counter-scale the text inside the transformed context as the first solution; nested inverse transforms increase complexity and can create rounding/jitter problems.
- Do not classify every actor FX as BODY_LOCAL. Ground-contact FX need a separate semantic domain.
- Do not change physicsRoot, collider, footRoot, depthRoot, stride phase, movement speed, camera, or avatar scale in the layer-ownership benchmark.
- Do not add a second `renderAvatar` wrapper solely for nameplates; consolidate responsibility around the existing final visual bridge.

### RISKS
Splitting body/overlay drawing can alter depth/redraw order if callers assume `renderAvatar()` is atomic. Plaza-depth or other prop redraws could duplicate overlays if the compatibility boundary is designed poorly. Anchoring the nameplate to pre-transform visualTop may produce an inconsistent gap when the body stretches/leans; anchoring to fully transformed bounds can introduce small positional motion even though glyph orientation is stable. The correct position policy must be benchmarked separately from glyph transform policy. BODY_LOCAL actor FX must remain aligned with head/hand sockets after the split, while ground-local FX must not inherit body lean. Extra save/restore calls are cheap in principle but still require frame-time measurement on mobile.
