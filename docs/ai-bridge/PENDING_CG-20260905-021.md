### PROBLEM
CG-20260905-020 correctly identified that current reversal metrics do not prove foot-support continuity and that the late `engine-z.js` zoom owner can reintroduce fractional physical scaling. This round refines those hypotheses against the newest `main` and finds a more direct grounding problem.

First, a single global integer-physical-scale zoom is too coarse to be the primary cross-device candidate. With current `engine-z.js` framing, a 390 CSS-px mobile viewport uses `390/(11*32)=1.10795` zoom. At DPR2 or DPR3, rounding `zoom*dpr` to the nearest integer yields zoom 1.0, changing visible horizontal world coverage from exactly 11 tiles to about 12.19 tiles (+10.8%). On a 1280px DPR1 desktop, `engine-z` clamps to 1.45; nearest integer physical scale would be 1.0, changing visible coverage from about 27.59 tiles to 40 tiles (+45%). That is not a clean sampling A/B because camera composition changes dramatically.

Second, `main` advanced during this research to `da699ea84f245ff1351f1f192a02177a89a1f46d`, adding `src/characters/character-appearance.js`. The new crimson bot renderer has explicit per-frame source foot anchors and maps each frame's source foot coordinate onto the shared world `footRoot`. The player hero renderer in `engine-ab.js`, by contrast, already measures each lateral frame's `lowestOpaqueY` and `supportCentroidX` but uses those values only for audit. Its actual draw still anchors the cropped destination rectangle to one fixed bottom coordinate. Therefore the semantic `footRoot` can be stable while the visible sole/contact pixels shift from frame to frame because source-frame transparent padding/contact geometry differs. That is now a higher-value foot-planting hypothesis than adding an arbitrary reversal hold.

### EXTERNAL_EVIDENCE
- MDN `requestAnimationFrame()` states callback frequency generally follows display refresh (including common 60/75/120/144 Hz cases) and warns animation progress must use timestamps/elapsed time so high-refresh displays do not accelerate animation. This supports preserving Kelo's distance/dt-driven stride rather than frame-count cadence: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame
- MDN `imageSmoothingEnabled` confirms disabling smoothing preserves sharp pixel edges for scaled pixel art, especially enlargement, but it does not establish that a heavily downscaled sprite at arbitrary camera/zoom sampling will be temporally stable: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
- MDN `createImageBitmap()` exposes deterministic resize dimensions plus `resizeQuality` including `pixelated`, making a canonical-size preprocessed sprite/frame atlas a testable browser-native alternative if runtime downscaling remains visually unstable: https://developer.mozilla.org/en-US/docs/Web/API/Window/createImageBitmap
- Godot issue #86634 reports player/screen jitter with Camera2D smoothing and fractional scaling; godot-docs #7774 aggregates many pixel-perfect smoothing/jitter cases. These do not prove Kelo has the same bug, but they support measuring camera/render sampling rather than assuming animation art is solely responsible: https://github.com/godotengine/godot/issues/86634 and https://github.com/godotengine/godot-docs/issues/7774
- Counterevidence is important: community reports and engine issues show broad pixel/transform snapping can make smooth/diagonal motion look choppy or create different jitter modes. Therefore do not globally snap player/camera merely to remove static pixel instability. One recent r/godot report describes jitter even with integer viewport scaling/nearest filtering, reinforcing that integer stretch alone is not a universal cure.

### HYPOTHESIS
H1 — The player hero's highest-value current grounding defect is likely source-frame contact drift: its logical foot root is stable, but the renderer does not map a per-frame visible foot/sole anchor onto that root. Applying a validated per-frame player foot anchor, using the new bot renderer's architecture as the model, can improve planted lateral motion and transitions without touching physics, camera or collider.

H2 — `supportCentroidX`/`lowestOpaqueY` are useful measurements but not automatically valid authored anchors. The bottom-band centroid is a silhouette proxy, not anatomical identification of the weight-bearing foot. Use these measurements to instrument/error-detect and seed candidate anchors, then visually validate the four lateral frames before committing anchor metadata.

H3 — CG-20260905-020's global integer-physical zoom candidate should be DEFERRED as the primary fix, not because fractional sampling is proven harmless, but because the nearest integer choices cause unacceptable field-of-view changes on common contexts. Measure final screen-space sampling first; if needed, test a residual/screen-space composition approach or per-sprite canonical preprocessing that preserves current world framing.

H4 — If visible shimmer remains after contact anchoring, a canonical presentation-size/pre-scaled hero atlas may reduce heavy downscale instability more cleanly than altering global camera zoom. This is experimental and must be A/B tested because pre-resampling can also lose useful detail.

### RISKS
- A mathematically stable anchor can still look wrong if the chosen source pixel is not the actual support foot. Visual frame review is mandatory.
- Horizontal support motion is part of natural walking; eliminating all X movement would make gait robotic. The target is removal of unexplained contact teleport, not a permanently centered foot.
- Per-frame anchor metadata can become stale if the spritesheet changes; it should live with appearance data/versioning and be audited against asset dimensions.
- The new appearance wrapper plus `engine-ab` creates overlapping rendering responsibility. Reusing the bot's anchor transform is desirable, but a large renderer consolidation now would obscure the locomotion experiment.
- Canonical pre-resizing can trade temporal stability for lost detail; test rather than assume.
- Camera/fractional sampling can remain a secondary contributor after foot anchoring. Deferring global integer zoom is not declaring the camera solved.
- Adding DPR3/desktop-DPR2 test contexts increases audit time but is justified before 1.20x scale decisions.
