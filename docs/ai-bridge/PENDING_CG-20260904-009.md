### PROBLEM
Current production movement exposes acceleration/deceleration constants but does not actually use them in the live local-player path. `engine-ac.js` forces `CONFIG.movementType = 'DIRECT'`, while `engine-a.js::updateMovement(dt)` only applies `accelDecay/decelDecay` in its non-DIRECT branch. Later, `engine-ah.js` wraps the already-wrapped movement function and hard-zeros velocity again whenever it detects no movement input. The result is an ownership mismatch: the code advertises/tunes acceleration and braking, but the production path is effectively immediate target velocity while input exists and immediate zero on release. For premium lateral feel this matters because start/stop/reversal response is currently controlled almost entirely by stick magnitude and gait presentation, not by a measured acceleration/braking envelope.

### CONFIRMED_IN_GEMINI
1. Current `main` baseline is `5b2b6ad0ab59bfc4c74948c497d05ff2fcff0883`; `index.html` declares `Kelo World — V6.23` and loads `engine-a.js`, later `engine-ac.js`, then later `engine-ah.js`.
2. `engine-a.js` initializes `CONFIG.movementType = 'MICRO_ACC'`, `accelDecay = 18.0`, `decelDecay = 35.0`, and contains two movement branches:
   - DIRECT: `localPlayer.vx = targetVx; localPlayer.vy = targetVy;`
   - non-DIRECT: exponential convergence using `factor = 1 - exp(-decay*dt)` with accel/decel decay.
3. `engine-ac.js` overwrites the live config with `CONFIG.movementType = 'DIRECT'`, `CONFIG.accelDecay = 32`, `CONFIG.decelDecay = 18`, but because movementType is DIRECT those two decay values are not consumed by `engine-a.js` for local-player velocity convergence.
4. `engine-ac.js` independently computes speed cap and gait from processed stick magnitude, wraps `updateMovement(dt)`, calls the prior movement function, then updates distance-driven `_visualMotion`.
5. `engine-ah.js` loads after `engine-ac.js`, captures the current wrapped `updateMovement`, calls it, and then if `hasMoveInput()` is false sets `localPlayer.vx = 0`, `localPlayer.vy = 0`, `input.normX = 0`, `input.normY = 0`.
6. Under the current DIRECT branch, release already produces target velocity zero in `engine-a.js`; therefore the velocity-zero part of `engine-ah.js` is redundant for ordinary local movement unless another wrapper or edge case reintroduces velocity after the core call.
7. This means the production local-player start and stop envelope is not currently governed by the configured `accelDecay/decelDecay` constants. Any apparent easing is coming from input magnitude changes, visual gait/stop-hold, camera damping, or other presentation behavior—not physical velocity convergence from those constants.
8. `engine-ab.js` renders the hero from the resulting displacement/visual state and does not itself smooth physical velocity. Thus a start/stop policy change can be benchmarked while holding sprite atlas, collider, camera trace capture and render ownership constant.
9. This is a redundancy/responsibility finding: `movementType`, `accelDecay`, `decelDecay` and `engine-ah` currently describe overlapping or dormant policies. Do not refactor them blindly; first benchmark exact traces.

### EXTERNAL_EVIDENCE
- Godot's official 2D movement overview shows direct velocity assignment (`velocity = input_direction * speed`) as a legitimate baseline for responsive top-down controls. This is important contraevidence: DIRECT is not inherently wrong and should not be replaced just because smoothing exists. https://docs.godotengine.org/en/4.1/tutorials/2d/2d_movement.html
- Godot's CharacterBody documentation emphasizes applying movement with a timestep-aware physics update; Kelo already integrates position with `velocity * dt`, so any proposed acceleration/braking experiment should remain dt-based rather than frame-count based. https://docs.godotengine.org/en/4.7/tutorials/physics/using_character_body_2d.html
- Unity's current `Mathf.SmoothDamp`/`Vector2.SmoothDamp` documentation describes spring-damper-like convergence toward a target over `deltaTime` without overshoot. This supports benchmarking a controlled non-instant response, but not blindly adopting Unity's exact function or long smooth times. https://docs.unity3d.com/ja/current/ScriptReference/Mathf.SmoothDamp.html and https://docs.unity3d.com/kr/2022.3/ScriptReference/Vector2.SmoothDamp.html
- A current Godot issue reproduction for top-down CharacterBody2D includes `move_toward(velocity, 0, SPEED)` when directional input is absent, demonstrating that explicit deceleration-to-zero is a common live pattern, though its exact feel is project-specific. https://github.com/godotengine/godot/issues/108137
- Community evidence is mixed, which is useful here: developers use acceleration/friction to create weight, but repeatedly warn that too much acceleration makes top-down controls feel slippery. Example discussion: https://www.reddit.com/r/pico8/comments/vlk9gn

### HYPOTHESIS
For Kelo World, the best premium lateral feel is likely not a long inertial glide and not the current fully discontinuous start/stop. A short, asymmetric velocity envelope may work better: very fast attack to preserve input responsiveness, stronger but still nonzero braking on release, and a special hard-reversal policy that changes facing/pose immediately while physical velocity crosses zero over a very short bounded interval. This should be evaluated separately for keyboard and analog touch. If any smoothing adds measurable control lag or foot sliding, DIRECT should remain the winner.

Candidate C — SHORT_EXPONENTIAL_ENVELOPE:
- Temporarily use the existing dt-based exponential branch in `engine-a.js` with a deliberately fast attack and short release.
- Start with diagnostic time constants derived from decay values, not arbitrary frame counts. Candidate decay sweep: accel 24/32/48 s^-1 and decel 32/48/64 s^-1.

Candidate D — ASYMMETRIC_START_STOP:
- Preserve near-instant start (DIRECT or very high accel decay) but apply only a tiny dt-based release envelope.
- Candidate release target: reach <=10% of pre-release speed in roughly 40/60/80 ms.
- Compare whether this adds planted weight without visible skating.

Candidate E — REVERSAL_AWARE:
- Visual facing/intent reverses immediately, but physical lateral velocity transitions through zero over a bounded interval.
- Candidate zero-crossing target: approximately 30/50/70 ms at full-speed RIGHT→LEFT.
- This is diagnostic only and must be compared against CG-20260903-021 reversal findings; do not supersede that work without current measurements.

### DO_NOT_ASSUME
- Do not assume acceleration always improves feel; DIRECT is a valid and often preferred top-down control scheme.
- Do not enable the old `MICRO_ACC` preset wholesale; it also carries other historical deadzone/damping/look-ahead values and would confound the experiment.
- Do not tune gait cycle, atlas frames, camera, collider, footRoot, zoom or nameplate in the same A/B trace.
- Do not use frame-count acceleration/deceleration; all candidates must be dt-based and compared at 60/90/120 Hz.
- Do not allow smoothing to create post-release collision drift that changes gameplay outcome.
- Do not treat `engine-ah` as removable merely because it looks redundant under DIRECT; first trace whether Café/modal/network/other wrappers can leave velocity nonzero before/after it.
- Do not combine with 1.15x/1.25x avatar scale until a physical envelope winner is chosen at 1.00x.

### RISKS
- Any nonzero braking distance can change collision timing near walls/doors and therefore must be tested in open field first, then near colliders.
- Analog touch already has magnitude variation; adding physical smoothing can double-smooth the control path and increase perceived latency.
- A release envelope can fight the current `VISUAL_STOP_HOLD_SEC` policy and create feet that keep animating or freeze inconsistently; evaluate them separately before combining changes.
- Hard reversal smoothing can conflict with immediate facing changes and produce a body visually facing LEFT while still drifting RIGHT. If used, visual and physical reversal semantics must be logged explicitly.
- `engine-ah` may exist to protect obscure modal/Café edge cases; removing it before dependency tracing could reintroduce post-modal drift.
- Exponential decay constants are refresh-independent only when evaluated from real dt; clamped or irregular dt can still change observed traces and should be included in stress testing.
