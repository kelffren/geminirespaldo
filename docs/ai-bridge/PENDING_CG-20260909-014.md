### PROBLEM
Kelo's current local-player gait correctly advances `stridePhase` from resolved world distance, which removes direct render-count dependence. However the authored hero still has only four discrete locomotion columns, and `engine-ac.js` converts the continuous phase to a pose with `Math.floor(stridePhase * 4) % 4`. `character-appearance.js` then consumes `motion.frame` directly. Therefore a visual pose transition can only become visible on a movement-update/render opportunity; it cannot occur at the exact continuous crossing time between those opportunities. The round needs to determine whether this discrete scheduling produces perceptible LEFT/RIGHT cadence irregularity at 60 Hz compared with 90/120 Hz, especially after scaling the avatar to 1.20x.

This is not a repeat of CG-005 pixel-phase, CG-006 idle->start, CG-013 anchor registration, or the distance-cadence work already in MOV-CADENCE-V2. Those investigated position quantization, transition semantics, anchors, and cycle-distance continuity. This round isolates POSE DWELL TIMING across refresh/update cadences.

### EXTERNAL_EVIDENCE
Official MDN `Window.requestAnimationFrame()` documentation (updated 2026-08-21) states callbacks generally track display refresh rate and explicitly lists 60, 75, 120 and 144 Hz as common. MDN warns animation progression must use elapsed time/timestamps or it will run faster on high-refresh displays. This supports Kelo's existing dt/distance-based progression but also establishes that presentation opportunities differ materially by refresh rate.

MDN's WebXR rendering guide similarly explains that browser frame callbacks may run at 60/90/120 Hz depending on the display and that dropped/uneven frames reduce smoothness. It reinforces measuring frame-period variation rather than assuming 60 Hz.

Godot issue #103229 (`SpringBoneSimulator3D Behaviour is tied to Framerate`) is confirmed and demonstrates that apparently visual/animation behavior can materially change with frame rate if scheduling/progression is not genuinely independent. Kelo's stride progression is better than that case because it is distance-driven, but the issue is useful counterevidence against declaring refresh-rate neutrality from code inspection alone.

Godot issue #104046 documents a one-frame delay in Animation Playback Track behavior, reinforcing that a single display/update boundary can be visually observable even when the underlying animation state is otherwise correct.

Community evidence is mixed and should not be treated as engine truth. Reddit Godot threads on 60 vs 120/144 Hz repeatedly report visible 2D sprite jitter when physics/update cadence and display cadence differ; recommended fixes vary between delta-correct movement, interpolation, or matching physics ticks. A July 2026 thread also showed apparent sprite jitter caused by restarting animation every update, illustrating why cadence debugging must separate state resets from true refresh/update quantization. Kelo does NOT currently restart the local stride animation each frame, so that particular failure mode is counterevidence, not a diagnosis.

Counterevidence: a four-frame authored locomotion sequence is intentionally discrete. Perfectly equal continuous-time frame dwell is not automatically necessary for good pixel/HD-2D animation, and adding interpolation/crossfade can create ghosting, soften silhouettes, or damage authored foot-contact clarity. `character-appearance.js` intentionally renders the hero with `imageSmoothingEnabled=false`. Therefore higher temporal smoothness is not automatically higher visual quality.

### HYPOTHESIS
The current MOV-CADENCE-V2 is probably correct at the continuous stride level, but at 60 Hz the 4-pose lateral animation may show a measurable alternating dwell pattern of up to one movement-update/display quantum (~16.7 ms if update cadence is refresh-coupled). Because the fastest nominal pose dwell near the walk/run boundary is only ~90 ms, a one-quantum variation can be ~18% of pose duration and may be perceptible as an uneven lateral rhythm, particularly with the larger avatar.

A second hypothesis is that this will NOT be perceptually important once anchor registration (CG-013) and pixel-phase behavior (CG-005) are controlled. If blinded video comparison cannot distinguish 60 from 120 after controlling those variables, no cadence rewrite should be made.
