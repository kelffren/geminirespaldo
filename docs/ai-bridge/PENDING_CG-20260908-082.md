### PROBLEM
CG-20260908-081 used `speedCap` as if it were physical analog speed. Current `engine-a.js` DIRECT movement instead uses `targetV = input.norm * CONFIG.speed`, and current `engine-ac.js` publishes the same relation as `targetSpeed = processedMag * speedCap`. Therefore the prior ~26% run-cadence-drop conclusion was based on the wrong speed quantity and must not be used for implementation decisions.

With corrected target speeds, the present 50->90 world-pixel cycle mapping is approximately monotonic in temporal cadence across most of the analog range: cadence rises from ~1.06 cycles/s at mag 0.48 to ~2.09 at mag 0.90, then falls only ~1.5% to ~2.06 at full stick. The large inversion claimed in CG-081 is not supported by current code math.

A separate, newly exposed issue is more plausible: after idle/release, MOV-PLANT-V1 seeds `stridePhase` exactly at plant frame 2 (`0.5`). Since four rendered frames quantize phase by quarters, the sprite cannot change from frame 2 to frame 3 until another 0.25 cycle of resolved world distance has accumulated. At slow analog movement that can mean hundreds of milliseconds where the character physically moves while the lateral sprite remains on the same planted pose.

### HYPOTHESIS
The current cadence mapping itself is much healthier than CG-081 stated. The higher-value remaining issue is startup quantization: at low analog speeds Kelo may slide for a perceptible distance/time before the first pose change because the plant phase starts at the beginning of frame-2's quarter-cycle bucket. A small presentation-only startup phase policy may improve responsiveness without changing physics, collider, camera, cycle distance, release plant frame, or steady-state cadence.

### PROPOSED_CHANGE
Do not alter production until baseline capture.

A — BASELINE: current planted start at phase 0.5; first visible transition after 0.25 cycle.

B — STATIC WITHIN-FRAME PHASE PRELOAD (QA only): on an idle->moving rising edge, keep the rendered initial frame 2 but seed the hidden phase later inside frame 2 (for example 0.625). This halves distance/time to frame 3 without a visible frame jump at t=0. Release still returns to canonical 0.5.

C — SPEED-AWARE STARTUP PHASE (QA only): choose an invisible within-frame seed so first visible frame change is capped near a tested maximum latency while remaining inside frame 2. Do not use a second timer to advance ongoing gait; distance remains authoritative after the seed.

D — AUTHORED START FRAME/SEQUENCE: if contact geometry shows frame 2 is a poor first-step pose, compare `plantFrame=0` baseline and/or an authored first-step sequence. Only consider after measuring `lateralContactFrames`; do not assume frame 0 is better.

Preferred minimal path if baseline defect is real: B before C/D because it preserves the same visible initial plant frame, same steady-state distance-driven cycle and no new runtime wrapper.

### RISKS
- Shortening a contact-pose hold can make low-speed walking look nervous or reduce perceived weight.
- A phase preload can shift subsequent foot-contact timing; support-centroid evidence must be compared, not just transition latency.
- Speed-aware seeding adds state/complexity and could become frame-rate dependent if implemented with timers instead of a one-time phase offset.
- Reversal and release work from earlier CG entries can regress if startup state is not isolated to an idle->moving rising edge.
- Four frames may simply be insufficient for premium very-slow walk; if so, the right answer could be authored art rather than more code.
