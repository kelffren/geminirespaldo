### PROBLEM
Kelo's current lateral camera computes a dead-zone threshold from CSS viewport dimensions (`screenW * deadXRatio`, `screenH * deadYRatio`) but compares those thresholds directly against world-space deltas (`localPlayer + lookOffset - camera.target`). The final production renderer then applies `CONFIG.zoom` around the world. This mixes coordinate spaces: the nominal `deadXRatio`/`deadYRatio` no longer describes one stable screen-space fraction across zoom/device classes. Because `engine-z.js` derives/clamps zoom from viewport width, mobile and desktop can begin lateral camera follow at noticeably different projected offsets even with the same movement trace.

### CONFIRMED_IN_GEMINI
- Current `main` at the base commit declares `Kelo World — V6.18` and loads `engine-a.js`, `engine-c.js`, `engine-h.js`, `engine-z.js`, `engine-ab.js`, `engine-ac.js` in that order before later wrappers.
- `engine-a.js::updateCamera(dt)` computes `deadW = screenW * CONFIG.deadXRatio` and `deadH = screenH * CONFIG.deadYRatio`, then compares world-space `deltaX/deltaY` against those values. Camera damping and look-ahead use exponential `dt` forms, which is a positive frame-rate-independent property and should be preserved.
- `engine-a.js` defaults are `deadXRatio=0.10`, `deadYRatio=0.08`, `lookAheadDist=60`, `lookAheadDecay=4`, `dampX=8`, `dampY=8`.
- `engine-z.js` later computes zoom as `screenW/(targetTiles*32)`, with 11 target tiles below 500 CSS px and 14 otherwise, clamped to 1.05..1.45; it also clamps `lookAheadDist` to 36 when it was above 40.
- `engine-c.js` is the final world renderer in this chain and explicitly applies `ctx.translate(screenW/2, screenH/2); ctx.scale(z,z); ctx.translate(-camera.x,-camera.y)`. Therefore camera/player differences are world units and become CSS-screen displacement after multiplication by zoom.
- Derived current examples (not live measurements): at 390px width zoom is about 1.108, so the nominal horizontal threshold projects to about 43.2 CSS px = 11.08% of viewport width; at 430px it projects to about 52.5px = 12.22%; at 768px and 1440px zoom clamps to 1.45, so the threshold projects to 14.5% of width. The configured ratio is 10%, but the visible ratio becomes approximately `deadXRatio * zoom`.
- `lookAheadDist=36` is world-space, so its screen-space contribution also varies with zoom: roughly 39.9 CSS px at 390px, 44.0px at 430px, and 52.2px at zoom 1.45.
- Secondary architecture observation: `engine-h.js` sets `CONFIG.roundPixels=true`, but the later `engine-c.js` render override does not consult that flag when applying the camera transform. The old `engine-a.js` renderer does consult it, so `roundPixels` is not a reliable switch for the current final renderer. Do not use that flag as evidence that current camera projection is snapped.

### EXTERNAL_EVIDENCE
- Godot Camera2D exposes drag margins as relative screen margins; e.g. a margin value is defined relative to the screen edge. This supports keeping a camera comfort zone in a clearly defined screen/view coordinate contract rather than accidentally mixing viewport and world units: https://docs.godotengine.org/en/latest/classes/class_camera2d.html
- Phaser Camera `setDeadzone(width,height)` defines a camera-follow rectangle in pixels centered on the camera midpoint, and Phaser separately defines camera zoom as the scale of world presentation. This is another example of treating the dead zone as an explicit camera/view-space concept: https://docs.phaser.io/api-documentation/class/cameras-scene2d-camera and https://docs.phaser.io/phaser/concepts/cameras
- Community reports around zoom/camera transforms repeatedly show bugs when screen/view coordinates are used without applying the camera transform. This is supporting evidence for explicit coordinate-space conversions, not proof of this exact Kelo bug: https://www.reddit.com/r/godot/comments/17zne6k/
- Counterevidence: a world-space dead zone can be a deliberate design choice, especially if the goal is to preserve a fixed number of world units before camera motion. Therefore the current code is not automatically wrong merely because values change on screen. The issue is that the variables are named/configured as screen ratios while their runtime semantics are world-space thresholds multiplied by zoom. The experiment must decide which feel the product wants.

### HYPOTHESIS
For Kelo World's premium lateral feel, the camera comfort zone should have one explicit coordinate-space contract. The strongest candidate is screen-normalized dead-zone semantics: compute the desired CSS-screen margin from viewport ratio, convert it to world units using current zoom before comparing with world-space deltas, while keeping look-ahead and damping separately tunable. This should make left/right follow onset more consistent between mobile and desktop and across Zoom HD choices without changing player physics.

A secondary hypothesis is that look-ahead should also be specified in either screen-space pixels/ratio or world-space units deliberately, rather than inheriting screen-size differences indirectly. Do not change both dead-zone and look-ahead in the first A/B; isolate them.

### PROPOSED_CHANGE
Do not change production immediately. Instrument the current camera and compare:

A — BASELINE_MIXED_SPACE
- Preserve current `deadW = screenW*deadXRatio`, `deadH = screenH*deadYRatio` world comparison.

B — SCREEN_CONTRACT_DEADZONE
- Preserve `deadXRatio/deadYRatio` as viewport fractions.
- Convert to world before comparison: candidate `deadWorldX = (screenW*deadXRatio)/zoom`, `deadWorldY = (screenH*deadYRatio)/zoom`.
- Do not change movement physics, gait, lookAheadDist, lookAheadDecay, dampX/dampY, collider, renderer or avatar size.

C — DEFERRED_LOOKAHEAD_NORMALIZATION
- Only after A/B choose a dead-zone contract, test whether look-ahead should remain 36 world px or become a screen-space target converted by zoom. This is deliberately separate to avoid confounding two camera variables.

Also treat `roundPixels` as a separate renderer/sampling investigation. Do not alter snapping as part of this camera-dead-zone test.

### DO_NOT_ASSUME
- Do not assume screen-space dead-zone is automatically better; measure subjective/quantitative lateral feel on both phone-sized and desktop viewports.
- Do not change `dampX/dampY` to compensate during the first experiment.
- Do not change `lookAheadDist` in A/B.
- Do not change player velocity, DIRECT movement, collider radius, stride, sprite scale, foot root or collision code.
- Do not use `CONFIG.roundPixels=true` as proof that the production camera is pixel-snapped; final `engine-c.js` projection currently ignores that flag.
- Do not refactor the camera wrappers before baseline traces exist.

### EXPERIMENT
Use a deterministic open-ground trace with no collisions and a frozen initial camera/player relation.

Viewports:
- 390x844
- 430x932
- 768x1024
- 1440x900

For each viewport record the actual `CONFIG.zoom` after all wrappers.

Traces, mirrored LEFT and RIGHT:
1. idle 500ms
2. WALK at stable input magnitude 0.60 for 2s
3. idle 500ms
4. RUN at magnitude 1.00 for 2s
5. hard reversal to opposite direction for 1s
6. idle

Run A and B with identical input/world traces at 60, 90 and 120Hz update profiles where the harness can control/observe them.

Record every update:
- player world X/Y
- camera target X/Y
- camera actual X/Y
- lookOffset X/Y
- zoom
- dead threshold in world units
- projected player-to-camera offset in CSS px
- first update where camera.targetX begins changing after movement onset/reversal

Then repeat the winning camera contract at avatar presentation scale 1.00x and simulated 1.25x without changing physics, only to verify that a larger body does not create a new perceived framing problem.

### RISKS
- A screen-normalized dead zone may feel too active on large desktop viewports even if mathematically consistent; player preference beats mathematical neatness.
- Converting dead zone by zoom while leaving 36-world-px look-ahead untouched may expose that look-ahead itself needs a separate contract. That is expected and should not be fixed in the same patch.
- Camera changes can amplify nearest-neighbor shimmer even when physics is unchanged, especially because current final renderer does not honor the old `roundPixels` flag. Sampling/snap must remain a separate measured axis.
- A larger avatar may make the same center framing feel tighter even with identical camera math; do not compensate by changing collider or physics root.
