### PROBLEM
Kelo still needs premium lateral secondary motion (body lean, restrained bob, impact/weight cues), but the current runtime contains a misleading legacy mechanism: engine-a.js continuously computes localPlayer.squashX/squashY from speed, while the modern hero sprite renderer in engine-ab.js and the generic appearance renderer do not consume those values. Re-enabling the old transform blindly would also rotate/scale around the old primitive actor center rather than the semantic footRoot established by the modern presentation contract, risking visible foot drift and breaking the grounding work from CG-021/023/027.

### CONFIRMED_IN_GEMINI
- Current main was re-read; the latest commit inspected changed grass audit workflow only, not locomotion owners.
- engine-a.js updateMovement still updates squashX toward 1 + speedRatio*0.08 and squashY toward 1 - speedRatio*0.06 with exponential smoothing.
- engine-a.js legacy renderAvatar consumes squashX/squashY only in the primitive fallback path, rotating into movement direction, scaling around p.x/p.y, then rotating back.
- engine-ab.js replaces renderAvatar for the loaded hero.PNG path and does not use squashX/squashY.
- src/characters/character-appearance.js also ignores squashX/squashY.
- engine-ac.js already exposes stridePhase, frame, gait, actual movement distance and plant state; these are better candidate drivers for authored visual secondary motion than raw render-frame count.
- modern presentation already exposes footRoot/shadowAnchor, so a body-only transform can be defined relative to that fixed ground point without changing collider or physics root.
- scripts/live-hero-audit.mjs currently checks movement, release, reversal, diagonal, collider and footRoot but does not measure any body secondary-motion transform or verify that the visual pivot remains fixed while such a transform runs.

### EXTERNAL_EVIDENCE
- MDN Canvas 2D documents that rotate() operates around the current canvas origin; changing the rotation center requires translate() to the intended pivot and translating back. This directly supports using footRoot as the explicit transform origin instead of actor center. Source: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/rotate
- MDN Canvas transform documentation confirms translate/rotate/scale can be composed in the current transform matrix and isolated with save/restore. Source: https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Transformations
- Pixel-art walk-cycle critique repeatedly emphasizes that weight improves when torso/head vertical motion is synchronized with contact/passing poses, while arbitrary or linear bobbing can look floaty or stiff. Examples: https://www.reddit.com/r/PixelArt/comments/1850443 and https://www.reddit.com/r/PixelArt/comments/18haaqz
- Counterevidence: pixel-art communities also report that excessive bob/squash, inconsistent timing, or moving grounded contact points introduces jitter/weightlessness. Therefore secondary motion should be subtle, phase-authored and benchmarked rather than automatically derived from speed.

### HYPOTHESIS
A small presentation-only transform hierarchy anchored at footRoot can add premium weight without touching physics: ground anchor stays fixed; body transform may apply a few CSS/world pixels of vertical offset and at most a very small lateral lean/rotation based on stride phase and gait. Using stridePhase/contact frames instead of continuous speed-only squash should align motion with foot contacts and remain deterministic across 60/90/120 Hz. The old squashX/squashY path should not be revived as-is.

### PROPOSED_CHANGE
Do not refactor production yet. First add an experimental pure helper (or audit-only calculation) that returns body presentation offsets from {gait, stridePhase, frame, face, speedRatio}. Contract:
1. footRoot, collider, physics root, camera and shadow anchor remain unchanged.
2. body transform origin is footRoot (translate to footRoot -> optional rotate/scale/translate body -> draw -> restore).
3. Start with translation-only A/B before any rotation: lateral walk bob candidate <= 1.0 CSS px at 1.15x; run <= 1.5 CSS px. No horizontal body offset initially.
4. If translation-only passes, test lean separately at 0.5°, 1.0°, 1.5° max, signed by lateral direction and eased by gait/phase. Never rotate the shadow or nameplate with the body.
5. Keep imageSmoothingEnabled=false. Do not alter source frame timing, stride distance, physics speed or camera in the same experiment.
6. Treat legacy squashX/squashY as compatibility state until fallback usage is audited; do not delete it blindly.

### DO_NOT_ASSUME
- Do not assume the existing four-frame hero art lacks its own authored bob; measure visible torso/head Y per frame first or a runtime bob may double the motion.
- Do not assume more motion is better. A zero-motion baseline may win.
- Do not drive bob from requestAnimationFrame count.
- Do not scale/rotate around p.x/p.y if footRoot is the grounding contract.
- Do not include shadow, collider, aura, nameplate or depthRoot inside the body transform.
- Do not remove squashX/squashY until every fallback/legacy consumer has been confirmed.

- visual verdict must be screenshot/video A/B, not metrics alone

### RISKS
- Existing sprite frames may already encode torso bob, so runtime bob can double it.
- Small Canvas rotations can make pixel art look softer or shimmer even with smoothing disabled because the transformed grid is no longer axis-aligned; translation-only may be the superior final choice.
- A transform applied inside renderAvatar can be duplicated during depth re-draws; body transform must be idempotent per draw, while the contact shadow remains once-per-actor ground-layer work per CG-027.
- Global scale/rotation can accidentally include aura/nameplate if wrapper order is wrong.
- Removing legacy squash calculations prematurely could break fallback primitive rendering.
