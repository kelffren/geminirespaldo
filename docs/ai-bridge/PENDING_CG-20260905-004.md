### PROBLEM
The new `KELO_HERO_SPRITE_AUDIT` instrumentation is useful, but one field currently has incorrect semantics. `engine-ab.js` increments `affected` for every RGB>232 pixel regardless of alpha, then assigns `sheetMutationAfterIdle = affected > 0`. A fully transparent source pixel can retain RGB values above 232 while alpha is already 0; setting its alpha to 0 again does not mutate visible pixel data. Therefore `sheetMutationAfterIdle` can become true even when the knockout pass changed no previously visible pixel. That false positive could send the next round toward removing/changing `knockWhite()` without evidence of an actual visible mutation.

There is a second measurement gap: the live Playwright harness does not read `window.KELO_HERO_SPRITE_AUDIT`, so the runtime values introduced by CG-003 are still not captured by CI/LIVE evidence. This is now the smallest blocker before deciding crop/knockout/LEFT/contact-frame work.

### EXTERNAL_EVIDENCE
- MDN documents that `getImageData()` returns the raw underlying RGBA pixel data and that `putImageData()` writes that data back. This supports defining a mutation according to a before/after RGBA change rather than merely matching an RGB predicate.
- MDN documents that `imageSmoothingEnabled=false` controls smoothing of scaled image drawing; it does not change the semantics of the source alpha mutation being audited here.
- CSSWG issue #5837 documents that non-integer pixel-art scaling can distort output even when pixelated/nearest rendering is requested. This remains counterevidence against assuming that fixing preprocessing alone will solve lateral shimmer or future 1.15x scaling quality.
- Reddit/Godot community reports repeatedly show that pixel-art jitter can persist from camera/subpixel/scale interactions even when nearest filtering and snapping are enabled. Community evidence is not proof for Kelo World, but it reinforces keeping preprocessing correctness separate from camera/scale conclusions.

### HYPOTHESIS
If `sheetMutationAfterIdle` is redefined to mean an actual change to previously visible alpha (`affectedOpaque > 0`) and the LIVE harness captures the full hero audit after preprocessing, we can turn CG-003 from instrumentation-only into an evidence-producing benchmark without altering gameplay or rendering output. That will let the next round choose one visual change from measured data instead of assumptions.

### PROPOSED_CHANGE
One measurement-only increment, no visual refactor:

1. In `engine-ab.js`, change only the audit semantic from:
   `sheetMutationAfterIdle = affected > 0`
   to a visible-mutation definition such as:
   `sheetMutationAfterIdle = affectedOpaque > 0`.
   Prefer renaming/adding a clearer field such as `visibleAlphaMutationAfterIdle` if backward compatibility with the existing audit field matters; do not silently change meaning if downstream tooling already depends on it.
2. In the LIVE Playwright harness, wait until `KELO_HERO_SPRITE_AUDIT.processed === true` or a bounded timeout expires, then persist the audit object in a JSON report.
3. Assert only measurement invariants: `loaded`, `processed`, `error===null`, frame grid dimensions valid, 16 crop buckets, finite `preprocessMs`. Do NOT assert that affected/cropped counts must be zero until source evidence is known.
4. Optionally persist `KELO_MOVEMENT_AUDIT` before/after the existing rightward keyboard trace so this same harness can later host LEFT/reversal measurements, but do not change movement logic in this commit.
5. Keep renderer output, crop, knockout threshold, direction rows, collider, footRoot, gait, camera and scale unchanged.

No refactor of `engine-ab.js` responsibilities is justified in this measurement pass. The unused `side` local in `renderAvatar` and other small cleanup can be documented but should not be mixed into the benchmark change.

### DO_NOT_ASSUME
- Do not treat near-white transparent pixels as a visible sprite mutation.
- Do not conclude `knockWhite()` is harmful solely because `affectedOpaque > 0`; those opaque pixels may intentionally be white background and still require visual classification.
- Do not conclude the crop is wrong solely because `croppedOpaquePixelCount > 0`; edge pixels could be authored padding/background or could be important silhouette pixels.
- Do not infer row 1=LEFT or contact-frame semantics from pixel counts.
- Do not change 1.00x avatar scale in this round.
- Do not change camera/zoom to fix jitter based on preprocessing results.

### RISKS
- Changing the meaning of an existing audit field could confuse any unseen consumer; adding a new explicitly named field may be safer than silently redefining the old one.
- Waiting for idle preprocess in Playwright must use a bounded timeout because `requestIdleCallback` scheduling can vary by browser/load.
- The current crop audit is a source-pixel diagnostic around a fractional `padX/padY`; exact Canvas sampling at fractional source rectangles may still require visual confirmation and should not be overinterpreted as an exact rendered-pixel loss map.
- Instrumentation can establish whether visible alpha changed, but it cannot classify whether those pixels were intended sprite detail or background.
- Fractional DPR/zoom/avatar scaling remains a separate jitter risk; do not conflate successful preprocessing measurement with solved lateral motion quality.
