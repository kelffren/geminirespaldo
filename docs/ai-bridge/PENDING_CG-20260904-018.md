### PROBLEM
The current local-player stop transition is time-based but pose-agnostic: after physical movement/input ends, `_visualMotion.on` remains true for `VISUAL_STOP_HOLD_SEC = 0.075`. During that hold, stride phase and frame no longer advance because there is no world-distance step, so whatever walk/run column was active at release is frozen for up to ~75 ms; only after the hold expires does the code reset `stridePhase=0`, `strideDistancePx=0`, `frame=0`. If the released frame is a passing/airborne-looking pose, Kelo can be physically stopped while visually frozen mid-stride, then snap to column 0. Separately, `engine-ab.js` keeps a legacy fallback path for avatars without `_visualMotion`: it uses `_walkHold = 10` decremented per render call and wall-clock `Date.now()/130` frame selection, so its stop latency is refresh-dependent and its gait is not distance-driven.

### CONFIRMED_IN_GEMINI
- Current `main` declares Kelo World V6.23 and loads `engine-ab.js` before `engine-ac.js`, then `engine-ah.js`; `engine-ac` therefore owns `_visualMotion` for the local player while `engine-ab` consumes it.
- `engine-ac.js` defines `VISUAL_STOP_HOLD_SEC = 0.075` and `MIN_VISUAL_MOVE_PX = 0.12`.
- In `updateVisualMotion`, when there is neither intent nor physical motion, `stopElapsed += dt` and `v.on = v.stopElapsed < 0.075`.
- While that 75 ms hold is active and `lastStepDistancePx == 0`, no stride phase/frame update occurs; the previous `v.frame` is retained.
- Once `v.on` becomes false, the code immediately resets `stridePhase=0`, `strideDistancePx=0`, and `frame=0`.
- `engine-ab.js::stepCol` returns frame 0 whenever `m.on` is false, so idle presentation is hard-mapped to atlas column 0 for the last facing row.
- `engine-ab.js::legacyMovingOf` has a second stop-hold policy: `_walkHold=10`, decremented once per renderer invocation, not by elapsed seconds. At one draw per refresh this is about 167 ms at 60 Hz, 111 ms at 90 Hz, and 83 ms at 120 Hz.
- The same fallback uses `Math.floor(Date.now()/130)%4` (~7.69 atlas-frame changes/s) rather than distance-driven stride; it therefore has different cadence semantics from local `_visualMotion`.
- `engine-ah.js` hard-stops velocity after the movement wrapper if there is no move input; under current DIRECT movement this does not advance a settling pose and does not solve the visual freeze-to-idle transition.
- `engine-a.js` updates simulated-player world positions using dt, so their physical motion is time-based while their fallback visual stop hold is render-count based.

### EXTERNAL_EVIDENCE
- Godot AnimationTree documents explicit transition policies: Immediate, Sync (switch while seeking destination to the old playback position), and At End. This supports treating locomotion-to-idle as a transition policy rather than an arbitrary global delay. https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html
- Unity Animator transitions expose normalized Exit Time and transition duration, showing that transitions can be keyed to animation phase rather than simply waiting a fixed number of milliseconds. https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animations.AnimatorStateTransition-exitTime.html
- Godot issue #52518 documents visible multi-frame freezes/delays around animation transitions, demonstrating that even a few stale frames can be perceptually obvious in motion. https://github.com/godotengine/godot/issues/52518
- Godot issue #104046 documents one-frame animation playback delay and a workaround that explicitly resets animation/frame on the same rendered frame to avoid flashing. https://github.com/godotengine/godot/issues/104046
- Reddit r/godot discussion “Sprite Timing and/or Abrupt Sprite Animation Switches” describes walk→idle flicker when releasing input at different points in the cycle and notes that simply waiting until late frame progress can harm fluidity. This is useful counterevidence against a naive “always wait to cycle end” policy. https://www.reddit.com/r/godot/comments/1dhb02v/
- Reddit r/gamedev discussion on a dedicated stop-walking animation recommends a separate stop state with exit timing, but also illustrates the state-machine complexity this can create. Kelo currently has only four authored locomotion frames, so do not assume a new stop animation exists. https://www.reddit.com/r/gamedev/comments/dgicuj/

### HYPOTHESIS
The current 75 ms pose-agnostic hold is likely less premium than a contact-aware or nearest-safe-idle transition because it can freeze a visibly unsupported stride pose while world velocity is already zero. However, immediately forcing frame 0 may also create a worse pop. The best low-complexity solution is likely to preserve facing and choose a stop policy from actual atlas semantics: either (A) immediate idle if column 0 is a compatible planted pose, or (B) a very short phase-aware settle to the nearest authored planted/contact column, bounded tightly enough that controls remain visually responsive. The 10-render-frame legacy hold should not remain refresh-dependent if that fallback is still reachable for visible actors.

### PROPOSED_CHANGE
Do not add new art or change physics yet. First instrument and classify the four real lateral atlas columns. Then benchmark four local stop policies with identical world traces:
1. CURRENT_75MS_FREEZE — current production behavior.
2. IMMEDIATE_IDLE — keep last facing but set idle/contact column immediately on confirmed physical stop.
3. NEAREST_CONTACT_SETTLE — if atlas inspection identifies one or more planted/contact columns, allow at most one short visual-only progression to the nearest safe contact pose, with a hard maximum around 50–80 ms; no world drift.
4. PHASE_WINDOW_IDLE — switch immediately when already near a safe contact phase, otherwise bounded settle; never wait a whole cycle.
For the fallback path, first instrument reachability. If visible actors use it, replace `_walkHold` render-count semantics with elapsed-time semantics and prefer the same stop policy contract where possible. Do not merge local and remote motion systems blindly because simulated/network actors may need interpolation-specific handling.

### DO_NOT_ASSUME
- Do not assume atlas column 0 is the best idle/contact pose solely because code currently uses it.
- Do not assume a dedicated stop animation exists; inspect `hero.PNG` first.
- Do not wait to the end of an entire cycle after input release; that can add unacceptable latency and community evidence specifically warns that phase-gated fixes can hurt fluidity.
- Do not change collider, velocity, camera, or network position to make a visual settle happen.
- Do not reset facing to down on idle; preserve the last stable facing.
- Do not delete `legacyMovingOf` until its runtime reachability is measured for simulated/network/fallback actors.
- Do not refactor wrappers before baseline trace → isolated visual change → same trace → re-measurement.

### EXPERIMENT
1. Capture the four lateral columns of `hero.PNG` at native nearest-neighbor scale and classify each as contact/planted, passing, recoil, airborne/ambiguous, with uncertainty.
2. Instrument on every input release: `releaseTime`, `physicalStopTime`, `frameAtRelease`, `phaseAtRelease`, `frameShownDuringHold`, `idleSwitchTime`, and facing.

5. Repeat at 60/90/120 Hz and 1.00x visual scale. Only the winning policy progresses to 1.15x and 1.25x.
6. For simulated/fallback actors, force a deterministic move→stop trace and compare `_walkHold=10` across 60/90/120 Hz; count actual duration and frame changes. Instrument how often production calls `legacyMovingOf` for visible actors.
7. Keep camera, collision, world movement, stride distance and zoom unchanged throughout.

### RISKS
- Immediate frame 0 may pop harder than the current hold if column 0 is not a compatible planted pose for every direction.
- A phase-aware settle can feel like input latency if it lasts too long; this is presentation-only and must be tightly bounded.
- Moving a visual frame after physical stop can look like moonwalking if the authored frame itself implies translation; only contact-compatible progression should be considered.
- Converting the fallback from render-count to time-based behavior could alter simulated/network actor visuals; measure reachability and actor classes first.
- If frame semantics differ by facing row, one global contact-column table may be wrong; classify lateral first and extend only after evidence.
- Scaling the avatar magnifies any stop-pop or unsupported frozen pose, so scale testing must happen after the 1.00x policy is selected.
