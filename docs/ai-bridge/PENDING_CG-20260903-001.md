### PROBLEM

V6.10 expands the authored world with `gardens-landmark.js`, but the new landmark does not merely add art. It independently wraps the global `render()` function and reproduces almost the same back→actor→front→actor composition pattern already present in `plaza-depth.js`. `plaza-nature.js` is another global `render()` wrapper that redraws actors in front of tree props. All three systems independently collect actors, derive overlap from `actor.radius || 20`, establish their own camera+zoom transform, and may call `renderAvatar()` again after the base scene has already drawn actors.

This creates two cumulative risks as more districts/landmarks are authored:

1. **Correctness / scale risk** — new occluders continue using the physics collider as a proxy for visible-body overlap, so avatar enlargement can reopen torso/head occlusion errors already identified for plaza trees/fountain.
2. **Render scalability risk** — every new authored landmark wrapper adds per-frame JS/state/draw work even when the landmark is nowhere near the viewport. The current three wrappers already form a nested global render chain. If this pattern is copied to every district, cost and ownership ambiguity grow with world content instead of with visible content.

This round is not claiming that current V6.10 FPS is bad. It identifies a new structural growth path that must be benchmarked before avatar scale, more depth props, aura, shadows and additional HD-2D landmarks multiply the same work.

### CONFIRMED_IN_GEMINI

Baseline inspected: current `main` commit `65978edf697ead953d9ad9d22de1d4fa12a1206c`, visible title `Kelo World — V6.10`.

1. `index.html` loads `plaza-nature.js` first, later `plaza-depth.js`, and then `gardens-landmark.js`. Each file captures the current global `render` and replaces it with another wrapper, so the runtime is a nested render chain rather than one central depth compositor.
2. `src/environment/plaza-nature.js` does `const _render=render; render=function(){ _render(); drawNature(); }`.
3. `src/environment/plaza-depth.js` does `const base=window.render; ... window.render=layered` and `layered()` begins by calling `base()`.
4. `src/environment/gardens-landmark.js` does `const base=window.render; window.render=function(){ base(); ... }`. Because it loads after plaza-depth, its `base()` includes the prior wrappers.
5. `plaza-nature.js::drawNature()` establishes its own `screen center -> scale(CONFIG.zoom) -> -camera` transform every render and unconditionally iterates all four plaza nature props with `P.forEach(prop=>drawProp(...))` whenever the atlas is ready. There is no viewport-intersection test before those four `drawImage()` calls.
6. `plaza-depth.js::layered()` establishes the same general camera/zoom transform and calls `drawBack()` and `drawFront()` every render when the two images are loaded. There is no viewport-intersection gate around the fountain pair before these draw calls.
7. `gardens-landmark.js` establishes the same general camera/zoom transform and calls `drawBack()` plus `drawFront()` every render when ready. There is no viewport-intersection gate around the east fountain landmark before these draw calls.
8. Therefore these three current environment wrappers alone issue a baseline of up to **8 static image draw calls per render** when ready — 4 plaza nature props + 2 plaza fountain layers + 2 gardens landmark layers — even if the camera is in another district. This is a source-code count, not a measured GPU/raster cost; browser clipping may reduce some downstream work.
9. Each wrapper also executes actor collection/filter logic each render. `plaza-depth.js` and `gardens-landmark.js` sort the near actors by Y independently.
10. `plaza-nature.js::overlapActor`, `plaza-depth.js::overlapsFountain`, and `gardens-landmark.js::overlaps` all use `actor.radius || 20` as the overlap extent for deciding whether an actor needs a foreground/depth redraw.
11. The new gardens landmark therefore reintroduces the same domain mismatch previously identified in CG-20260902-018: the ~20 px physics radius is not a scale-safe representation of the full visible avatar envelope.
12. `gardens-landmark.js` repeats the same actor gathering pattern as `plaza-depth.js`: local player + simulated players + optional PvP rival, then filter/sort, render actors between back/front, then redraw actors classified in front.
13. `plaza-depth.js` and `gardens-landmark.js` both call `renderAvatar()` inside their compositor after `base()` has already rendered the scene. This keeps CG-20260902-022 relevant to new world content: near an occluder the avatar/body/nameplate/VFX wrappers can be rasterized multiple times unless ownership is explicitly excluded in the base pass.
14. `plaza-nature.js` can also call `renderAvatar()` again for an actor classified in front of a tree.
15. Because `engine-ab.js::renderAvatar()` includes the nameplate in the same function, every environment-triggered actor redraw can also redraw the nameplate unless a later wrapper suppresses or separates it.
16. The three environment files duplicate responsibilities that should at minimum have one explicit contract: actor enumeration, semantic depth root, visible-overlap envelope, camera projection, sorting, background/front layering and audit draw counts.
17. `gardens-landmark.js` is compressed into a very large one-line source file. This is not a runtime bug by itself, but combined with duplicated wrapper logic it makes responsibility diffing/auditing harder than necessary.
18. `ENGINE_MAP.md` is still stale: it predates V6.10, the gardens compositor and the current effective hero renderer ownership. Current code is the authority for this round.
19. `tile-registry.js` already contains a `styles.propDepth` contract and explicit `baseY` metadata for props. The repository therefore has a metadata location that could eventually feed a shared compositor instead of each landmark inventing a new render wrapper, but no such migration is assumed safe yet.
20. No production file was modified in this research round. The baseline must be measured before any compositor/refactor change.

### EXTERNAL_EVIDENCE

1. **PixiJS current official Scene Graph / Container guidance** treats render order as a scene hierarchy problem and supports explicit child ordering / `zIndex` within a container. This is evidence for central ownership of render ordering rather than an indefinitely growing chain of unrelated global render wrappers. Pixi also cautions that sortable children should be used sparingly because sorting can be expensive; therefore this is not an argument to sort the entire Kelo world every frame. Source: https://pixijs.com/8.x/guides/components/scene-objects/container
2. **PixiJS current official CullerPlugin guidance** says culling is particularly useful for large camera-driven scenes and skips rendering objects outside screen bounds. It also makes the important tradeoff explicit: culling adds CPU bounds-check work, so it should be applied where offscreen render savings justify it. Source: https://pixijs.com/8.x/guides/components/application/culler-plugin
3. **PixiJS official scene-object guidance** distinguishes local/global bounds and allows custom bounds areas to avoid repeated expensive bounds measurement. This supports a stable explicit visual/depth envelope for Kelo and authored props rather than using the physics collider as the visual overlap shape. Source: https://pixijs.com/8.x/guides/components/scene-objects
4. **MDN Canvas 2D documentation** confirms `save()`/`restore()` preserve/restore the current transform and drawing state. Each independent environment wrapper is therefore establishing a separate state/transform scope by design. This is correct locally, but the number of scopes/calls should be measured as wrappers accumulate. Source: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D
5. **GitHub issue evidence:** Godot issue #85871 documents a confirmed 2D performance collapse when much more of a huge TileMap becomes visible while zoomed out. It is not the same engine and does not prove Kelo has that bug, but it reinforces that visible-content volume/culling strategy matters in expanding 2D worlds. Source: https://github.com/godotengine/godot/issues/85871
6. **GitHub issue evidence for depth complexity:** Godot issue #72322 shows that large top-down sprites can produce incorrect Y-sort behavior when relying on simple tile/origin assumptions. This supports keeping semantic base/foot Y and visual bounds explicit for tall/avatar-scaled content. Source: https://github.com/godotengine/godot/issues/72322
7. **Community evidence:** a r/gamedev top-down Y-sort discussion recommends keeping static layers separate and sorting/merging only dynamic objects that actually need depth interaction, rather than treating every static object as a fully dynamic sort participant. Source: https://www.reddit.com/r/gamedev/comments/vqz82b/
8. **Community performance evidence:** Canvas 2D developers report `drawImage()` becoming a dominant cost when many calls are issued each frame, even when using spritesheets. This is anecdotal and hardware/workload-specific, so it supports measuring draw counts rather than assuming eight extra calls are currently material. Source: https://www.reddit.com/r/gamedev/comments/lr0unn/
9. **Counterevidence:** eight static `drawImage()` calls are small compared with thousands of tile draws, and browsers can clip offscreen content internally. A generic culling layer or global sort could cost more CPU than it saves at today's scene size. Therefore do not refactor solely because the wrapper pattern looks inelegant; benchmark wrapper/draw cost and growth first.
10. **Counterevidence:** a back→actor→front pair is a legitimate simple solution for one isolated tall prop. The problem identified here is not that layered composition is wrong; it is that the same global-render/actor-overlap machinery is now being independently duplicated as authored world content grows.

### HYPOTHESIS

Kelo World should preserve layered back/actor/front composition, but render ownership should eventually become **content-driven and viewport-scoped** rather than **wrapper-driven and global**.

The likely scalable contract is:

- one authoritative world projection per render;
- one actor enumeration per relevant depth pass;
- stable `footRoot/sortY` for actor depth;
- stable `visualEnvelope` for overlap eligibility, independent from collider radius;
- authored occluders registered as metadata (`bounds`, `baseY`, back/front draw callbacks or source regions);
- viewport/expanded-camera culling before invoking offscreen static landmark draw callbacks;
- sort only the small visible set of actors/occluders that actually require dynamic interleaving;
- nameplates/HUD handled separately from world-depth body redraw.

However, implementing a scene graph/compositor now without baseline traces would violate the user's no-blind-refactor rule. First prove how many wrappers/draws execute, how much time they cost, and whether base-vs-local actor CTMs are still inconsistent.

### RISKS

- Adding bounds checks for a tiny scene can cost more CPU than simply issuing a few clipped draw calls.
- Culling too tightly can make large sprites pop because transparent/visual extents exceed logical landmark bounds; use conservative authored bounds/padding.
- A shared compositor can accidentally change painter's order, especially with multiple overlapping tall props. Migrate only one landmark first.
- A visual envelope that is too broad can trigger unnecessary redraws; too narrow can recreate torso/head occlusion misses.
- Sorting all registered static objects every frame would be a regression; static metadata should remain preordered where possible and only visible dynamic interactions should be merged/sorted.
- Separating nameplates from body depth is desirable but is a separate UI/presentation migration and should not be bundled into P1/P3.
- Aura/equipment wrappers around `renderAvatar()` can make duplicate logical actor calls more expensive than the body alone; measure current wrapper expansion rather than estimating it.
- Current global render wrappers may rely on load order. Replacing one wrapper can expose implicit assumptions from later wrappers, so runtime wrapper identity/chain logging is mandatory before edits.
