### PROBLEM
The production PNG renderer gives LEFT/RIGHT a destination width of 48 px but computes destination height from a 54 px reference width (`dh = round(54 * FH/FW)`). The source frame is cropped proportionally by 5% per side horizontally and 4% per side vertically. This creates a lateral destination rectangle that is materially narrower than an aspect-preserving transform of the cropped source. Before scaling Kelo to 1.15x-1.25x or judging stride/arm swing/lean, distinguish authored lateral silhouette from renderer-introduced horizontal compression.

### CONFIRMED_IN_GEMINI
- Revalidated current `main` after it changed during this research pass: head `0145358a5b8e7f0af547313580db9055f7c46897` already contains the separate MOV-CADENCE-V2 experiment from CG-20260904-021. This entry does not modify or invalidate that cadence experiment.
- `index.html` still declares V6.23 and loads `engine-ab.js` as the live PNG hero renderer, then `engine-ac.js` as gait/visual-motion owner.
- `engine-ab.js` derives `FW = raw.width/4`, `FH = raw.height/4`; source crop uses `padX=max(2,FW*0.05)` and `padY=max(2,FH*0.04)`.
- Destination width is `48` for LEFT/RIGHT and `54` for UP/DOWN. Destination height is always `round(54*(FH/FW))`, including lateral frames.
- For normal atlas dimensions where proportional padding wins over the 2px minimum, crop size is approximately `0.90*FW` by `0.92*FH`.
- An aspect-preserving destination width at the current height is therefore approximately `54*(0.90/0.92)=52.83`, i.e. about 53 px before integer rounding.
- Current lateral 48 px gives X/Y scale ratio `(48/(0.90FW)) / ((54FH/FW)/(0.92FH)) ≈ 0.909`: about 9.1% horizontal compression relative to vertical scale.
- Front/back 54 px at the same height has ratio about 1.022, roughly 2.2% horizontal expansion relative to the cropped source aspect.
- LEFT mirrors the same side row as RIGHT; the compression is symmetric and affects every lateral frame used by walk/run/reversal.
- The new cadence-v2 code in `engine-ac.js` changes stride distance only; it does not change `engine-ab.js` destination geometry, so this aspect issue remains independent.

### EXTERNAL_EVIDENCE
- MDN Canvas2D `drawImage()` documents source crop and destination width/height independently; when destination aspect differs from source-crop aspect the image is scaled non-uniformly. https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage
- MDN `scale()` likewise defines horizontal and vertical scale factors independently. Nearest-neighbor sampling does not make unequal X/Y geometry aspect-preserving. https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/scale
- Pixel-art community guidance consistently treats consistent pixel scale and avoiding stretch as separate from filtering; nearest filtering can keep hard edges while still producing visually distorted geometry, especially at non-integer scaling. Practical example: https://www.reddit.com/r/godot/comments/1aqfrs8/
- Counterevidence: a side-view authored silhouette may legitimately be narrower than front/back, and opaque pixels can have direction-specific transparent padding. Therefore crop-aspect preservation is a benchmark candidate, not a proven final art rule.

### HYPOTHESIS
Part of Kelo's lateral motion reading as less premium may come from renderer-introduced horizontal compression: shoulder width, arm swing, leg separation and contact poses are squeezed by roughly 9% relative to an aspect-preserving transform of the cropped side frame. Enlarging the character would enlarge the same distortion. A width around 53 px may preserve source geometry better, but actual opaque alpha bounds and same-trace screenshots must decide.
