### PROBLEM
The live touch pipeline has two different activation thresholds for locomotion and visual gait. `processInput()` starts publishing a non-zero normalized vector immediately after the radial joystick deadzone. `engine-ac.js::gaitFrom()` still returns `idle` until processed magnitude reaches 0.03. With DIRECT movement, the core physics continues to move during that interval, but `updateVisualMotion()` treats `gait === 'idle'` as no visual intent. At these magnitudes the physical speed is also far below its `spd > 16` fallback, so `_visualMotion.on` can remain false while world position changes. This creates a small but real annulus where Kelo can drift with a planted/idle sprite.

This is distinct from CG-20260907-058. Preserving sub-0.12 px stride distance with a residual accumulator does not fix this lower-magnitude case because the visual state is disabled before stride consumption matters.

### CONFIRMED_IN_GEMINI
Current `main` audited at `a42e860a9794e4ce9706c8d22eaeba1169e203a3`.

`engine-ac.js` currently sets:
- `GAIT_IDLE_MAX = 0.03`
- `WALK_SPEED = 110`
- DIRECT movement via `CONFIG.movementType = 'DIRECT'`
- `hasIntent = gait !== 'idle'`
- `physicallyMoving = dist > 0.12 || spd > 16`

`engine-a.js::processInput()` uses a circular touch deadzone, then re-normalizes the remaining radius continuously from zero:
- `joystickRadius = 72` from `engine-ac.js`
- `joystickDeadzone = 0.045`
- dead radius = `72 * 0.045 = 3.24 CSS px`
- outside that radius, processed magnitude grows continuously as `(dist - deadR) / (72 - deadR)`.

The point where processed magnitude reaches the visual gait threshold 0.03 is approximately:
`3.24 + 0.03 * (72 - 3.24) = 5.3028 CSS px`.

Therefore the annulus from about 3.24 px to 5.30 px of thumb displacement can publish `0 < processedMag < 0.03`.

At those magnitudes `speedFor()` returns 110, so core target speed is `processedMag * 110`, reaching up to about 3.3 world px/s immediately below the gait threshold. That movement is legitimate physics under the current contract.

But in `engine-ac.js`, `gaitFrom(mag)` is still `idle`, so `hasIntent` is false. At <=3.3 world px/s, `spd > 16` is also false. The visual state can therefore settle to `v.on=false`, plant frame/plant phase, even though `localPlayer.x/y` continues to change.

`engine-ah.js` does not cancel this. Its late hard-stop only zeros velocity when `hasMoveInput()` is false; while a touch remains active it returns true even at tiny analog magnitudes.

This also means CG-20260907-058 alone is insufficient below 0.03 processed magnitude: a gait residual accumulator would preserve distance, but the animation owner still classifies the character as visually idle.

### EXTERNAL_EVIDENCE
Official Unity Input System documentation describes stick deadzones as a way to eliminate small unintended control noise and notes that values below the minimum are clamped to zero; Unity's documented default lower deadzone is 0.125 for stick controls. This does not imply Kelo should use 0.125, but it supports treating near-center analog noise as an input-policy decision rather than allowing it to leak accidentally into physics.

Official Godot documentation recommends a circular deadzone for 2D movement vectors and states the design tradeoff directly: the deadzone should be high enough to ignore drift/noise but low enough not to ignore intentional player input.

Community evidence is consistent with the perceptual failure mode: developers repeatedly report that animation/movement speed mismatches read as gliding, and recent joystick discussions show tiny non-zero vectors breaking idle/directional animation when neutral input is not filtered. Counterevidence is equally important: increasing a deadzone too far can make controls feel sluggish, so simply enlarging the physical deadzone is not assumed correct.

Sources reviewed:
- Unity Input System `StickDeadzone` / `defaultDeadzoneMin` documentation.
- Godot `Input.get_vector()` / controller deadzone documentation.
- Reddit r/godot/r/gamedev discussions on animation-speed mismatch, joystick neutral noise and deadzone tradeoffs.

### HYPOTHESIS
The 0.03 gait-idle threshold and the physical joystick activation threshold are expressing two different policies accidentally. The premium result should have one explicit near-center contract: either input in this range is intentional locomotion and the visual gait must represent it, or it is noise and physics should not move. Keeping "physics moves but visuals are idle" is the worst of the three outcomes.

For a 72 px virtual stick, aligning the physical threshold with the current visual 0.03 threshold would correspond to an effective raw radius of about 5.30 px, or ~7.36% of stick radius. That value is only a benchmark candidate, not a recommendation.

### PROPOSED_CHANGE
Do not edit production before baseline measurement. Benchmark three policies with the same touch traces:

A — BASELINE: current 4.5% radial deadzone + gait idle below processed 0.03.

B — SHARED LOCOMOTION DEADZONE: treat processed magnitude below 0.03 as zero for BOTH physics and gait, then re-normalize above the threshold so full-stick still reaches 1.0. This removes the drift annulus but changes low-speed physical precision and must be measured.

C — VISUAL FOLLOWS REAL LOCOMOTION: keep physics exactly unchanged, but replace `hasIntent = gait !== 'idle'` with a separately named locomotion-active signal derived from real non-zero processed intent / legitimate locomotor displacement; combine with the residual-distance concept from CG-20260907-058 so very slow intentional movement advances stride proportionally instead of gliding. This preserves precision but risks tiny foot animation under thumb tremor.

Do not combine B and C in one production patch. They answer different product questions.

If real touch traces show that the 3.24–5.30 px band is overwhelmingly noise, prefer B. If users can intentionally hold stable useful movement there, prefer C. A fourth option (stateful enter/exit hysteresis near center) is worth testing only if traces repeatedly chatter across the boundary.

### RISKS
- Raising the physical activation threshold can make delicate movement feel less precise, especially on small phones.
- Letting visuals activate for every non-zero normalized input can animate feet under hand tremor while world motion is nearly imperceptible.
- Re-normalizing above a larger deadzone changes the response curve even if max speed is unchanged.
- Near-center hysteresis can introduce asymmetric feel if implemented against raw X/Y instead of radial magnitude.
- Fixing visual activation without CG-20260907-058 residual accounting may leave high-refresh displays with visually frozen micro-movement anyway.
- 1.20x avatar scale will make any glide/foot twitch more visible, so scale testing should happen after this contract is settled.
