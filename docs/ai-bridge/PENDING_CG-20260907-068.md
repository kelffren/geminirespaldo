### PROBLEM
The live PNG renderer publishes a stable `footRoot`, but it anchors the bottom of the fixed destination rectangle to that root. It does not anchor each animation frame by that frame’s actual visible foot/contact pixel. If the lowest opaque pixel differs across authored lateral frames, the visible foot can move vertically relative to the world even while `footRootY` is mathematically constant. This is a direct foot-planting problem and becomes more visible when avatar scale increases from 1.15x toward 1.20x.

### CONFIRMED_IN_GEMINI
- Current `main` at analysis start is `4792a7a15d35a515ccae3330d2c211c473cfd18f`; `index.html` declares `Kelo World — V6.39` and loads `engine-ab.js?v=240`, then `src/characters/character-appearance.js?v=2`, then `engine-ac.js?v=222`.
- `engine-ab.js::presentationOf()` defines `footRootY = p.y + 10` and `visualBottom = footRootY`.
- The LIVE hero draw uses one fixed source crop for all frames (`padX≈5%`, `padY≈4%`) and one fixed destination height for the current facing. Destination Y is `Math.round(footY - dh)`. Therefore the destination rectangle bottom is anchored, not the frame’s actual lowest opaque/contact pixel.
- The same file already computes `lowestOpaqueY`, `supportMinX`, `supportMaxX`, and `supportCentroidX` for every lateral row-2 frame after white knockout. Those values are audit-only; `renderAvatar()` does not use `lowestOpaqueY` to correct per-frame Y.
- For a frame with source-crop height `sourceH = FH - 2*padY`, visible-foot gap from the published foot root is approximately `gapWorld = dh * (FH - padY - lowestOpaqueY) / sourceH`. Any frame-to-frame change in `lowestOpaqueY` therefore creates a frame-to-frame visible contact-height change even with constant `footRootY`.
- `src/characters/character-appearance.js` contains a separate non-live/delegated rendering path that already supports authored per-frame `footX[]` and `footY[]` anchors and places the destination from those anchors. Its retired `bot_crimson_v1` metadata records per-frame foot anchors. This is not production authority, but it proves the repository already contains the concept of per-frame foot anchoring.
- The same appearance module duplicates responsibilities also present in `engine-ab.js`: motion/facing selection, frame selection, presentation fallback, sprite draw, and nameplate draw. Do not refactor this duplication as part of the benchmark; isolate the anchor question first.
- `GROK_TO_CHATGPT.md` still has no feedback newer than `GC-20260831-003`, so no later Grok evidence closes or invalidates this issue.

### EXTERNAL_EVIDENCE
- Unity’s current Sprite API treats the sprite pivot as a first-class alignment point relative to the graphic rectangle; `SpriteAlignment` includes BottomCenter and Custom pivots. This supports aligning frames around a stable authored contact point instead of assuming the rectangle edge is the semantic foot: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/SpriteAlignment.html and https://docs.unity3d.com/6000.0/Documentation/ScriptReference/TextureImporterSettings-spritePivot.html
- Godot’s official 2D animation documentation explicitly allows adjusting a Sprite2D pivot via `offset`, again separating the semantic pivot from the raw texture rectangle: https://docs.godotengine.org/en/stable/tutorials/animation/cutout_animation.html
- Unity’s Sprite Swap documentation uses custom pivots to keep swapped artwork aligned to the rest of the character, which is analogous to keeping successive walk frames attached to a stable foot root: https://docs.unity3d.com/Packages/com.unity.2d.animation@13.0/manual/CharacterParts.html
- Community evidence: a 2026 Godot discussion about foot sliding recommends matching world travel/contact to actual foot travel per sprite frame rather than assuming the loop itself guarantees planted feet: https://www.reddit.com/r/godot/comments/1rxgqwb/what_are_your_tricks_for_moving_pixelanimated/
- Counterevidence: if all four live lateral `lowestOpaqueY` values are equal (or differ by an imperceptible amount after scale/zoom), the current rectangle-bottom anchoring is simpler and should remain. A per-frame correction must not be added just because per-frame pivots are a known technique.

### HYPOTHESIS
A measurable part of Kelo’s remaining lateral “not fully planted” feel may come from source-frame contact-height variance rather than gait timing, camera, or world physics. If `lowestOpaqueY` differs between row-2 frames, a QA-only per-frame Y anchor derived from post-knockout contact geometry should reduce visible-foot vertical jitter while leaving physicsRoot, footRoot, stridePhase, frame cadence, collider, camera, and world motion unchanged. The benefit should scale upward at 1.20x, because any source-pixel anchor error is multiplied by destination scale.

### RISKS
- Lowest opaque pixel may be noise rather than the foot; blindly anchoring to it can create worse jitter.
- Correcting every frame to the exact bottom pixel can erase intentional authored body rise/fall if the artist encoded legitimate gait bob into the sprite.
- Current white-knockout preprocessing modifies alpha; inferred pivots derived after knockout may change if cleanup rules change.
- Per-frame Y offsets can make head/nameplate spacing appear to move unless nameplate remains tied to the stable presentation envelope rather than the shifted body frame.
- 1.20x magnifies both improvements and mistakes, so scale testing must follow, not precede, the 1.15 anchor benchmark.
- The duplicated render responsibilities in `engine-ab.js` and `character-appearance.js` are architectural debt, but refactoring now would destroy baseline attribution.
