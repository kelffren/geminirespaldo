### PROBLEM
The LIVE modern avatar has already been given a semantic ground-contact contract (`footRoot`, `depthRoot`, `shadowAnchor`) specifically suitable for a premium planted character, but the actual modern Character Appearance path currently renders no contact/blob shadow. The old `engine-w` base renderer still contains an ellipse shadow under the legacy pixel hero. However, `KeloAvatar` middleware is short-circuitable: when `character-appearance:custom-sprite` at priority 200 successfully renders the modern `hero.PNG`, it does not call `next()`, so the `engine-w` base renderer—and therefore its shadow—does not run. This means the current modern hero can lose a cheap but useful ground-contact cue exactly while the user is prioritizing foot planting, lateral weight, reversal clarity, and increasing visual scale to 1.20x.

A naïve fix is risky: drawing a shadow inside any `renderAvatar()` middleware may make that shadow redraw during prop-occlusion actor redraws (CG-003), potentially painting a ground shadow above a foreground prop. The research goal is therefore not merely “add an ellipse”; it is to identify the correct owner/layer so one grounded shadow is drawn at the semantic shadow anchor during the normal actor pass without altering physics, camera, depth authority, or producing duplicate shadows on occlusion redraw.

### CONFIRMED_IN_GEMINI
Current `main` at BASE_COMMIT:
- `index.html` is Kelo World V6.54 and loads `engine-w.js`, `engine-ab.js`, `src/characters/character-appearance.js`, then the modern Visual System and later Character Customization.
- `engine-w.js::drawHero()` draws a legacy contact/blob shadow with Canvas2D before the pixel body: `ctx.ellipse(x, y + 18, 14, 5, ...)` with `rgba(0,0,0,0.4)`.
- `engine-ab.js::presentationOf()` publishes `footRootX/Y`, `depthRootX/Y`, and `shadowAnchorX/Y`, with shadow anchor currently equal to foot root. This is already the correct semantic place to hang a grounding cue rather than deriving it from `actor.radius`.
- `src/core/avatar-render-system.js` dispatches middleware in descending priority and reaches the base renderer only if the middleware chain calls `next()`.
- `src/characters/character-appearance.js` registers `character-appearance:custom-sprite` at priority 200. On a valid ready modern appearance it draws `runtime.source` and returns without calling `next()`. Therefore the `engine-w` base renderer (including its ellipse shadow) is not drawn for the modern hero path.
- `character-appearance.js` already computes each authored frame around per-frame foot anchors and a semantic `layout.footRootX/Y`, so the modern renderer already knows where the ground-contact point is.
- `src/characters/character-customization.js` registers modular layers at priority 250 and calls `next()` between its back/front sections; therefore the modern full-body appearance at priority 200 remains the terminal renderer for the default base body. Any future contact-shadow placement must remain compatible with this layered path.
- `engine-c.js` invokes `KeloVisualSystem.renderWorldLayer('belowActor', ctx)` before actor rendering, then calls `renderAvatar()` for actors. This is semantically attractive for contact shadows because a below-actor world layer cannot accidentally cover the actor body. However, current `KeloVisualSystem.renderWorldLayer()` only forwards to KeloFX/KeloProjectileVisuals; it does not expose a general arbitrary world-layer registration API.
- `src/systems/performance-governor.js` already measures frame P50/P95/P99, long animation frames, weighted scene pressure, particles/FX, and mobile quality profiles, so the cost of any grounding-shadow candidate can be measured rather than assumed.
- Current code therefore has an architectural asymmetry: the semantic `shadowAnchor` exists, a legacy shadow visual exists, and a `belowActor` render location exists, but no modern reusable consumer joins those three pieces.

### EXTERNAL_EVIDENCE
- Unity 6 URP 2D documentation treats a Shadow Caster 2D as a separate rendering concern with its own shape/properties, rather than requiring the collider to define the visual shadow. This supports keeping Kelo's shadow grounded in presentation data rather than `actor.radius`.
- Godot's 2D lights/shadows documentation similarly models shadow casters/occluders as rendering objects distinct from gameplay collision. Again, visual shadow geometry is not required to equal physics geometry.
- Community practice for simple 2D/2.5D characters commonly uses a separate blob/contact shadow located at the bottom/feet of the character; when airborne, that shadow can remain on the ground and change opacity/scale rather than following the body. This supports Kelo's existing `shadowAnchor=footRoot` as the right baseline contract.
- A Godot community blob-shadow implementation reports good performance for simple character blob shadows and contrasts it with heavier screen-space decal techniques. This is not proof for Kelo/Canvas2D, but supports benchmarking a very cheap ellipse/small sprite before considering dynamic-light shadow systems.
- PixiJS performance guidance (not Kelo's renderer, but relevant Web render evidence) notes that simple graphics can be cheap while complex/rebuilt graphics and excessive transparency can become costly; sprites are the fastest common render path and batching/order matter. For Kelo this argues for benchmarking both a Canvas ellipse and a tiny pre-rendered shadow sprite if actor counts grow, rather than assuming either is universally faster.
- Counterevidence: a contact/blob shadow is not automatically an upgrade. If too dark, too wide, detached from the authored feet, or redrawn above props, it can make a top-down sprite look like it is floating on a sticker. In a heavily stylized scene, no shadow can be cleaner. The candidate must win screenshots/video and performance measurements.

### HYPOTHESIS
A subtle contact shadow anchored to `KELO_AVATAR_PRESENTATION.shadowAnchor` will improve perceived lateral grounding, stop/reversal readability, and make the larger 1.20x avatar feel less floaty—provided the shadow remains stable in world space while body pose transforms/bob occur and is rendered exactly once in a true below-actor layer. The highest-value architectural solution is likely to extend an existing visual owner with a reusable below-actor actor-ground decoration hook, rather than adding another engine or putting shadow math inside physics/collision. However, because the current Visual System lacks an arbitrary world-layer registration hook, that capability must be benchmarked against a smaller local solution before adoption.

### PROPOSED_CHANGE
Do NOT modify production before baseline screenshots/traces. Compare isolated candidates:

A) BASELINE — modern Character Appearance with no additional contact shadow.

B) LOCAL APPEARANCE CONTROL — draw one subtle ellipse directly in `character-appearance.js` immediately before the modern sprite at `layout.shadowAnchor || layout.footRoot`. This is the smallest causal visual test and proves whether a contact shadow improves the current hero. It is NOT the preferred final architecture because `renderAvatar()` redraws may duplicate the shadow and because modular/full-body paths could diverge.

C) AVATAR MIDDLEWARE CONTROL — register one outer KeloAvatar middleware above Character Customization/Appearance that draws the shadow before `next()`. This centralizes actor appearance variants better than B, but explicitly test occlusion redraws: if Generic Props calls `renderAvatar()` again, the shadow may be redrawn above foreground props. Reject C if duplicate/incorrect layering occurs.

D) EXISTING VISUAL-OWNER EXTENSION (preferred only if B proves visual value and C exposes redraw problems) — extend `KeloVisualSystem` with a minimal reusable registration capability for existing world layers, e.g. owner-registered callbacks for `belowActor`, then implement one `actor-grounding-shadow` consumer that enumerates visible actors once in the normal pre-actor pass and draws at `shadowAnchor`. This is a new capability inside an existing owner, not a new engine. It should be designed for future reusable ground markers/selection rings/target circles, but do not add those features now. Preserve current KeloFX/projectile behavior unchanged.

E) PRE-RENDERED SHADOW SPRITE — if ellipse/path cost or visual softness is worse on mobile, compare a tiny pre-rendered transparent PNG/atlas sprite drawn at the same anchor. Do not use filters/blur per actor in the baseline candidate.

Initial visual tuning ranges to benchmark, not final constants: horizontal radius around 20–35% of current visualWidth, vertical radius around 4–8% of visualHeight, alpha ~0.15–0.30. Size should be derived from presentation/appearance scale rather than collider radius so 1.15x→1.20x can be tuned deliberately. Shadow position should remain tied to `shadowAnchor`/footRoot, not torso bob offsets.

### DO_NOT_ASSUME
- Do not assume the old `engine-w` ellipse dimensions (14x5 at y+18) are correct for the 93px modern hero or for 1.20x.
- Do not increase `actor.radius` to fit the shadow.
- Do not derive the contact shadow from nameplate or visual top bounds.
- Do not put locomotion bob/root offset into the shadow anchor; grounded shadow should remain at the ground contact unless the actor is intentionally airborne.
- Do not use dynamic 2D lights, blur filters, normal maps, WebGL/WebGPU migration, or per-pixel shadow casters for this first test.
- Do not add another renderer manager if KeloVisualSystem/KeloAvatar can own the capability cleanly.
- Do not accept a middleware implementation until prop-occlusion redraw is tested.
- Do not bundle this with 1.20x, cadence, hysteresis, or camera changes; test current scale first, then repeat the winner at 1.20x.

### RISKS
- Rendering the shadow inside `renderAvatar()` can duplicate it during Generic Props actor redraw and place a ground cue over foreground geometry.
- If Character Customization/full-body override paths short-circuit differently, a local Character Appearance shadow can disappear or duplicate depending on outfit mode.
- A shadow sized from collider radius will become proportionally too small as the avatar moves to 1.20x; size must be presentation-driven if visual scale is the intent.
- A shadow transformed with body bob/offset will undermine foot planting by visibly moving the ground contact itself (see CG-20260909-002).
- Too much alpha/width can visually flatten HD-2D depth and dirty the plaza, especially with existing environment shadows/lighting.
- A new arbitrary Visual System callback API is architectural surface area; only add it after the simple B proof shows enough visual benefit to justify reusable ownership.
- Pre-rendered shadow textures add asset/atlas/memory management; do not choose them solely on theory.
