### PROBLEM
The live local-player presentation chooses one of four facing rows from the latest displacement/velocity vector using a single hard boundary: `abs(dx) * 1.15 >= abs(dy)`. There is no directional hysteresis or minimum dwell. Near that diagonal boundary, small analog-stick noise or small collision-induced changes in displacement direction can alternate the selected row between side and vertical while world motion remains nearly unchanged. Because the side row is also the premium left/right presentation priority, row chatter can read as a pop/flicker exactly during diagonal lateral movement.

### CONFIRMED_IN_GEMINI
- `engine-a.js::processInput()` normalizes keyboard diagonals but passes continuous analog touch direction from the joystick after radial deadzone processing. There is no angular deadband/hysteresis after the radial deadzone.
- `engine-ac.js::updateVisualMotion()` updates `v.dx/v.dy` from actual displacement when distance exceeds `MIN_VISUAL_MOVE_PX`; otherwise it falls back to velocity or input. It then classifies facing every update using `const side = Math.abs(v.dx) * 1.15 >= Math.abs(v.dy)` and immediately writes `v.face` / `p._face`.
- The boundary is equivalent to `abs(dy/dx) <= 1.15` for side-facing, i.e. about 48.99 degrees from the horizontal axis. A vector that moves back and forth by only a few degrees around ~49 degrees can therefore switch rows repeatedly.
- `engine-ab.js` consumes `m.face` directly and maps `left/right` to sprite row 2, `down` to row 0 and `up` to row 3. Thus a facing switch changes the source row of `hero.PNG` immediately; there is no crossfade because this is frame-by-frame pixel art.
- Keyboard 45-degree diagonals are deterministically classified as side-facing (`1.15 * |x| >= |y|`), so the main risk is analog/touch direction, collisions, or other small displacement-angle perturbations near the threshold, not ordinary WASD diagonals.
- This is separate from radial joystick deadzone, stride timing, WALK/RUN thresholds and physical speed. Those systems can remain unchanged while facing selection is benchmarked.

### EXTERNAL_EVIDENCE
- Godot documents discrete 2D animation selection as a valid mode for frame-by-frame animation and also provides a Carry mode that preserves playback position while switching discrete animations. This supports treating direction selection and stride phase as separable concerns rather than resetting gait on every row switch: https://docs.godotengine.org/en/stable/classes/class_animationnodeblendspace2d.html
- Godot's 8-way movement documentation normalizes the input vector before applying speed, consistent with Gemini's keyboard handling; this means direction-sector logic is a presentation decision, not a reason to alter physical diagonal speed: https://docs.godotengine.org/en/stable/tutorials/2d/2d_movement.html
- Community reports describe visible sprite flicker when direction angles oscillate at boundaries between discrete facing sectors. One GameMaker discussion specifically reports rapid switching when the angle sits on a border between directional intervals: https://www.reddit.com/r/gamemaker/comments/g6k4ki/
- A recent 2D directional-animation guide explicitly recommends directional hysteresis when raw analog input repeatedly crosses a sector boundary. Treat this as supporting community guidance, not authoritative engine documentation: https://www.framesprite.com/guides/godot-4-eight-direction-animation-blendspace2d
- Counterevidence: a hard threshold is simpler, deterministic and can be completely adequate if measured touch/displacement angles do not chatter around the boundary. Do not add state merely because hysteresis is common.

### HYPOTHESIS
A small presentation-only angular hysteresis around the existing ~49-degree side/vertical boundary will reduce row chatter during diagonal touch movement and collision perturbations without changing world trajectory, speed, collider, stride distance, or input latency. The currently selected facing should remain until the competing sector wins by a small margin. The stride phase should continue uninterrupted when facing changes.

### PROPOSED_CHANGE
Do not refactor movement ownership yet. First instrument facing transitions. If chatter is reproduced, test a tiny stateful selector inside the visual-motion layer only:
1. Keep the existing sector center/bias as baseline.
2. Add separate enter/exit boundaries around the current ratio rather than one shared threshold. Example diagnostic sweep only, not final constants: side-enter ratio 1.20 / side-exit ratio 1.10, plus narrower alternatives.
3. Preserve immediate sign reversal within the same axis (`right -> left` or `down -> up`) when the dominant component truly changes sign; do not let hysteresis make hard reversals feel delayed.
4. Do not reset `stridePhase` when the facing row changes.
5. Do not touch `input.normX/normY`, movement speed, collision, camera or joystick radial deadzone.
6. Keep `engine-ab.js` renderer read-only with respect to facing; facing ownership should stay in presentation update, not renderer.

### DO_NOT_ASSUME
- Do not assume analog row chatter is currently visible until captured or logged.
- Do not assume the example 1.20/1.10 ratios are correct production values.
- Do not convert the game to eight-direction sprites; current asset contract is four directions and left is mirrored from the right row.
- Do not smooth physical input just to stabilize animation direction.
- Do not add a time delay that makes a real hard reversal visually late.
- Do not reset walk/run cycle phase on direction changes unless evidence proves the authored atlas requires it.

### RISKS
- Too much hysteresis can make the character appear to face sideways while movement is visibly vertical, or vice versa.
- A generic time dwell can make hard reversals feel laggy.
- Using intended input instead of actual displacement may stabilize the row but become visually wrong while sliding along collision geometry.
- Using only actual displacement can inherit one-frame collision-resolution angle spikes. Instrument vector-source transitions before choosing ownership.
- Larger avatars amplify any wrong-row pop, so a value acceptable at 1.00x may fail at 1.25x.
- Do not duplicate the direction classifier in `engine-ab.js`; two owners would create future drift.
