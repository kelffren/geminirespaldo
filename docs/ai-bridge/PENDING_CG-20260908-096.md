### PROBLEM
The LIVE locomotion pipeline distinguishes resolved world displacement from requested velocity only partially. `engine-a.js` computes `localPlayer.vx/vy` from input, integrates position, then collision resolution pushes position back out of AABBs without modifying the velocity components. `engine-ac.js` correctly advances stride from resolved world distance, but its `physicallyMoving`/visual-on decision also treats `speed > 16` as movement. Therefore, when the player holds directly into a blocking wall, the actor can have near-zero resolved displacement while `localPlayer.vx/vy` remains large. In that state `v.on` remains true, stride receives zero distance, and the normal plant reset (`!v.on`) never runs. The visible sprite can therefore freeze indefinitely on whichever authored lateral frame happened to be active when the wall became fully blocking. This is not foot skating, but it is also not deliberate foot planting: a random mid-stride pose can be held for arbitrarily long while the player pushes the wall.

### CONFIRMED_IN_GEMINI
- Current main at research time: `0f83bb5e574796c89873d9b4ab8d4068b3dbc4ad`.
- `index.html` remains Kelo World V6.53 and loads Foundation `KeloMovement`, then `engine-ac.js?v=223`, then `engine-ah.js?v=95` in the LIVE runtime.
- `ENGINE_MAP.md` identifies `engine-a.js` as LIVE legacy movement physics owner, `KeloMovement` as the only movement extension owner, `engine-ac.js` as gait/speed/stride support, and `engine-ah.js` as release-brake support. No new wrapper should be created.
- In `engine-a.js`, DIRECT movement sets `localPlayer.vx=targetVx` and `localPlayer.vy=targetVy`. Position is then integrated per axis. If a collision occurs, the collision resolver's push vector is added back to `localPlayer.x/y`, but `localPlayer.vx/vy` are not projected, zeroed, or otherwise changed by the collision response.
- `engine-ac.js` computes `dist = hypot(p.x-v.lastX, p.y-v.lastY)` after movement/collision resolution, and `spd = hypot(p.vx,p.vy)`.
- It defines `physicallyMoving = dist > MIN_VISUAL_MOVE_PX || spd > 16`.
- If `hasIntent || physicallyMoving`, it forces `v.on=true` and `v.stopElapsed=0`.
- When `dist <= MIN_VISUAL_MOVE_PX && spd > 16`, it updates visual direction from `p.vx/p.vy`, so facing can remain correctly aimed into the wall.
- But `v.lastStepDistancePx = dist > MIN_VISUAL_MOVE_PX ? dist : 0`, and stride advances only when `v.on && v.lastStepDistancePx > 0`.
- The plant/reset branch runs only when `!v.on`, setting `stridePhase=PLANT_PHASE` and `frame=PLANT_FRAME`.
- Consequently, with sustained wall input: desired/requested velocity may remain high, resolved distance may be ~0, `v.on` remains true, stride does not advance, and the current frame can remain frozen indefinitely.
- `engine-ah.js` does not fix this while input remains held. It only zeroes velocity/norm input when `hasMoveInput()` is false.
- Current `unsupportedPoseFreezeMs` telemetry does not detect this wall-block freeze under MOV_STOP_V2 because that metric is tied to the release path; while pushing a wall `v.on` remains true and the release state is never entered.
- The previous CG-086 low-speed finding is relevant: any blocked-state solution must not simply reuse the per-callback `MIN_VISUAL_MOVE_PX` threshold as the only source of truth, because that threshold can discard legitimate slow movement at high refresh rates.

### EXTERNAL_EVIDENCE
1. Godot's current CharacterBody2D API explicitly distinguishes requested `velocity` from `get_real_velocity()` and `get_position_delta()`. The docs state that `get_real_velocity()` returns the actual motion produced by the last movement/collision step, whereas `velocity` represents requested velocity. This is directly analogous to Kelo's distinction between `localPlayer.vx/vy` and resolved `p.x/y` delta.
2. Godot's `move_and_slide()` documentation also states that collision response modifies velocity. Kelo's manual AABB correction currently changes position without modifying `localPlayer.vx/vy`, so consumers must not assume that velocity is post-collision actual motion.
3. Godot issue #75428 documents a one-frame collision case where velocity incorrectly remained nonzero while the body was not actually moving; the reporter specifically observed an ugly run/idle animation flicker because animation was driven by that misleading velocity. This is strong counterevidence against using requested/non-resolved velocity as the sole visual locomotion truth near collisions.
4. A r/godot discussion about stopping walking animation at walls recommends tying animation to player velocity rather than raw input. For Kelo, the important refinement is that `localPlayer.vx/vy` is still pre/post-intent velocity after collision correction, so the safer equivalent is resolved displacement/real velocity, not raw input or requested velocity.
5. Counterevidence: many games intentionally keep a push/strain animation active while the player holds against a wall. Therefore 'blocked = idle immediately' is not a universal rule. A deliberate blocked pose can be better than idle. The defect here is specifically that Kelo can hold an arbitrary walk-cycle frame, not that it continues acknowledging input.

### HYPOTHESIS
Kelo will feel more planted if collision-blocked locomotion is treated as a distinct resolved-motion state instead of inheriting the last arbitrary stride frame. When sustained input produces negligible resolved motion, the presentation should settle after a short, measured grace period to a deliberate support pose (initially the existing PLANT_FRAME as the cheapest candidate) while retaining facing/intention. Diagonal wall sliding must continue to animate from the actual tangential world distance. The state should be driven by resolved motion accumulated in a refresh-rate-independent way, not merely by instantaneous requested velocity or a per-frame epsilon.

### PROPOSED_CHANGE
No production change yet.

Candidate A — BASELINE: preserve current behavior and instrument wall-block intervals.

Candidate B — RESOLVED-MOTION BLOCK SETTLE: keep `hasIntent` and facing from input/requested motion, but detect sustained blocked locomotion using resolved displacement/real velocity. If intent remains non-idle while accumulated resolved travel remains below a tiny spatial budget for a short grace period (QA starting range 60–120 ms), settle stride/frame to the existing PLANT_FRAME without changing physics or input. As soon as resolved movement resumes, stride continues from a defined restart policy. Do not use raw `dist <= 0.12` per callback as the sole blocker detector; integrate/accumulate distance so 60/90/120 Hz behave equivalently.

Candidate C — AUTHORED BLOCKED/PUSH POSE: only if B proves visually better but PLANT_FRAME looks too passive. Add a data-driven blocked pose/clip later, using the same resolved-motion state. Do not create this asset/system before B establishes that the state transition itself is useful.

Candidate D — COLLISION-RESPONSE VELOCITY: project/zero velocity components when collision resolution blocks an axis so `localPlayer.vx/vy` better matches post-collision motion. This is architecturally broader and can change gameplay/camera/online semantics, so it should not be the first experiment. Prefer presentation-only B unless evidence shows physics velocity must be corrected globally.

### DO_NOT_ASSUME
- Do not assume `localPlayer.vx/vy` equals actual post-collision velocity in current Kelo; it does not on the confirmed manual collision path.
- Do not immediately force idle on every collision; sliding diagonally along a wall should still walk/run based on tangential resolved travel.
- Do not use the existing per-frame 0.12 px threshold as the sole blocked-state detector; CG-086 already shows refresh-rate-dependent distance loss at low speeds.
- Do not reset facing when blocked. Input direction can remain useful for visual orientation and future push animations.
- Do not alter collider size, collision geometry, speed map, camera, stride cycle length, avatar scale, or sprite assets in the same experiment.
- Do not implement Candidate D before proving that a presentation-only state cannot solve the visual problem.
- Do not add another `updateMovement` wrapper. Use current `KeloMovement` hooks/owners.
- Do not rewrite or delete `GROK_TO_CHATGPT.md` history.

### RISKS
- Settling too quickly can make brief wall brushes visually pop to plant; grace/hysteresis must be measured.
- Settling based on a per-frame epsilon will reintroduce the 60/90/120 Hz problem already identified in CG-086.
- Treating any collision as 'blocked' would incorrectly stop stride during legitimate wall sliding.
- Resetting phase on wall exit can create a visible cadence jump; preserving arbitrary phase can reintroduce poor support-foot continuity. This needs A/B measurement.
- A future authored push pose could become another hardcoded special case if not data-driven; defer it until the state proves useful.
- Altering physics velocity (Candidate D) could affect camera look-ahead, abilities, networking prediction, knockback, or other systems that currently read `localPlayer.vx/vy`.
