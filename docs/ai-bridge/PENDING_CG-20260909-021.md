### PROBLEM
Current main correctly keeps locomotion, aim and melee timing in separate owners, and the opener `sword_light_basic` already restores full movement during recovery. However, the same combo data still applies recovery movement scales of 0.80 on `sword_light_follow` and 0.64 on `sword_light_finisher`. This means repeated basic attacking becomes progressively more movement-committed even after the active hit window has ended. That may be deliberate finisher identity, but it is not yet measured against the user's desired Drakantos-like action-combat feel. The next gap is therefore not “movement is locked while attacking” globally; it is whether the current phase-specific slowdown is stronger or longer than necessary for light-basic continuity.

### CONFIRMED_IN_GEMINI
Current LIVE `src/systems/pvp-world.js` installs exactly one KeloMovement before-hook `pvp-world:movement-scale`. During combat it computes `s = dodge ? 0 : basicAttack ? KeloMeleeEngine.movementScaleFor(profile, phase) : 1`, multiplies input.normX/normY by `s`, then legacy/Foundation movement resolves normally. There is no second PvP movement engine.

`KeloMeleeEngine.movementScaleFor()` is a pure profile helper and clamps phase values to [0,1]. Therefore the slowdown is data-driven and shared cleanly with the combat timeline rather than hardcoded per attack in PvPWorld.

Current melee profile timings/scales:
- sword_light_basic: windup 0.085s @ 0.86, active 0.075s @ 0.48, recovery 0.180s @ 1.00.
- sword_light_follow: windup 0.070s @ 0.90, active 0.070s @ 0.52, recovery 0.170s @ 0.80.
- sword_light_finisher: windup 0.110s @ 0.76, active 0.085s @ 0.34, recovery 0.260s @ 0.64.
- sword_heavy_charge: windup 0.120s @ 0.58, active 0.090s @ 0.25, recovery 0.340s @ 0.55.

Time-weighted normal-movement equivalence across each attack timeline (ignoring hit-stop/status/actual collisions) is approximately:
- light opener: 0.2891 / 0.340 = 85.0% average movement.
- light follow: 0.2354 / 0.310 = 75.9% average movement.
- light finisher: 0.2789 / 0.455 = 61.3% average movement.
- heavy charge release attack: 0.2791 / 0.550 = 50.7% average movement.

The opener profile version explicitly documents `light-recovery-mobility`, and its audit exports `basicRecoveryMovementScale:1`, so full opener recovery mobility is an intentional recent improvement. Follow and finisher were not normalized with it.

`canAttack()` still prevents a new melee attack while `state.basicAttack` exists, while the 125 ms combat input buffer can preserve a press near the end of recovery. This is relevant to continuous basic feel but is a separate hypothesis from movement scale and should not be changed in the same pass.

Main changed substantially immediately before this research via Performance Foundation merge `88d7b6ddb1d3ffd849ed4ef7ab70575c001d994f`; current `index.html` V6.54 now lazy-loads Combat/Effects/Status/Melee through `KeloRuntimeBootstrap.ensure()`. Research therefore used the current lazy runtime, not prior load-order assumptions.

### EXTERNAL_EVIDENCE
Drakantos publicly reworked its earlier tile-based movement because players perceived lag and clunkiness; the developers said the new free movement made control smoother and more fluid. Community discussion around the same rework specifically called out basic attacks that required stopping movement as feeling bad, and another commenter emphasized the importance of the feel of continuously attacking. By May 2026 community reports described the newer version as free movement + full action combat, although diagonal animation remained imperfect.

This supports testing whether light-basic recovery unnecessarily suppresses locomotion, but it does NOT prove every attack should allow 100% movement. Counterevidence from action-melee systems shows that deliberate movement commitment during active/heavy phases can improve attack weight and positioning. Therefore opener/follow/finisher/heavy should not be flattened to one scale by assumption.

### HYPOTHESIS
H1: The opener is already close to the desired mobility contract; its recovery=1 should remain baseline.
H2: `sword_light_follow` recovery=0.80 may create a measurable “sticky” tail after a nominally light hit that is not needed for hit readability.
H3: `sword_light_finisher` recovery=0.64 may be justified by finisher identity and stronger knockback/stagger; changing it without a same-trace comparison could reduce weight.
H4: If browser traces show the perceived lock comes primarily from active-phase slowdown rather than recovery, changing recovery would be the wrong fix.
H5: Do not touch heavy charge in the same experiment; it is intentionally high-commitment content and provides useful counterexample/control.

### PROPOSED_CHANGE
Do not modify production yet. First extend an existing PvP/melee audit path with deterministic move+attack traces. If the baseline proves excessive post-hit suppression on the LIGHT FOLLOW only, test one data-only candidate: `sword_light_follow.movementScale.recovery: 0.80 -> 1.00`, leaving windup, active, finisher, heavy, physics, shared movement profile and server authority unchanged.

If follow recovery=1 produces no meaningful improvement or makes the combo visually slide, reject it. Only after that result should finisher recovery be considered separately.

### DO_NOT_ASSUME
- Do not assume Drakantos has 100% locomotion during all attack phases; public evidence supports free/action movement, not exact movement multipliers.
- Do not remove active-phase commitment just because recovery mobility is being tested.
- Do not change attack timing and movement scale simultaneously.
- Do not alter `KeloMovementProfile`, collision, dodge distance, hit geometry, aim-facing or network transport.
- Do not create a combat-movement manager; PvPWorld + KeloMeleeProfiles already own the required contract.
- Do not treat input-buffer behavior as the same bug; benchmark it separately if movement-scale tests pass but basic chaining still feels sticky.

### EXPERIMENT
Build one deterministic trace that runs identical RIGHT, LEFT and 45-degree movement while executing each combo step at magnitudes 0.48, 0.70 and 1.00, at dt=1/60, 1/90 and 1/120.

For every simulation sample record:
- attack id/profile and phase;
- phase elapsed/remaining;
- raw input vector before PvP movement scaling;
- movement scale selected;
- scaled input vector entering movement;
- requested velocity;
- resolved displacement;
- actual world speed;
- visual stride phase/frame;
- movement face and attack/aim face;
- collision/status multiplier if present.

Baseline A = current profiles.
Candidate B = only `sword_light_follow.recovery = 1.0`.
Heavy charge remains untouched as commitment control.

Repeat an unobstructed trace and a wall-slide trace. Add an aim-orthogonal case (move RIGHT + aim UP) to guarantee attack-facing independence is unchanged.

### DECIDING_METRICS
Primary:
- recoveryRequestedSpeedRatioToFreeMoveP50/P95
- recoveryResolvedSpeedRatioToFreeMoveP50/P95
- postActiveMovementSuppressionAreaPx (integral of free-speed minus actual requested speed from active-end to attack-end)
- activeEndToFullMovementMs
- comboStepMovementContinuityP95
- moveAimAngularIndependenceErrorDeg

Regression invariants:
- world trace outside candidate recovery window = identical
- collision result diff count = 0 outside expected extra displacement during candidate recovery
- attack active timestamp delta = 0
- hit geometry/damage/cooldown/resource delta = 0
- stride phase must continue from resolved distance, not requested velocity
- client/server canonical base movement profile delta = 0
- aim/attack direction delta = 0

Suggested decision gate for follow recovery candidate:
Keep only if `activeEndToFullMovementMs` materially decreases (expected ~170 ms -> first post-active update) and user-visible/trace locomotion continuity improves, while no attack timing, hit, aim, collision-contract or stride discontinuity regression appears. Do not promote based only on a larger displacement number.

### RISKS
- Full recovery movement may visually look like skating if the melee animation still communicates planted commitment; browser capture is required before calling it superior.
- Extra movement during 170 ms recovery changes final world position, so online server movement validation must use the same phase movement semantics or reconcile correctly. The base speed profile remains shared, but attack-phase modifiers must be checked server-side before implementation.
- Wall/corner cases may gain extra lateral escape distance; test collision traces.
- Flattening finisher/heavy movement would reduce attack identity and is explicitly out of scope.
- Performance Foundation changed load order to lazy combat modules; audits must call `KeloRuntimeBootstrap.ensure()` or load the same module set explicitly instead of assuming melee is booted at page load.
