### PROBLEM
CG-20260905-001 established that the live 4x4 hero renderer still has unknown directional/contact semantics. Current main has since closed Environment Asset Contract v2, but `assets/hero.PNG` is not one of that contract's 11 production PNG entries. The character therefore still has critical presentation semantics embedded as hard-coded runtime assumptions in `engine-ab.js`: 4x4 sheet shape, direction-row mapping, LEFT mirroring, heuristic source cropping, foot-root offset, destination size, and a client-side near-white knockout pass.

This blocks clean verification of foot planting and makes 1.15x/1.25x scale experiments less trustworthy: we can scale the destination rectangle, but we do not yet have machine-readable authored pivot/contact/crop/mirroring semantics to prove that the result preserves feet, silhouettes and intended pixels.

### CONFIRMED_IN_GEMINI
- Research base is current `main` commit `79ab7b7fbe8db90af4fc2d6538b74f3d1a24a777`; `index.html` declares Kelo World V6.23.
- Environment Asset Contract v2 is now validated and covers 11 production environment PNG entries with dimensions, alpha/sampling, frames, anchors, visual bounds, footprint/collider, ownership, layers, occlusion, cache and fallback metadata.
- `src/environment/art-asset-manifest.json` does NOT contain `assets/hero.PNG`. This is appropriate to notice rather than blindly inserting the actor into an environment layer manifest: the manifest's formal phases are environment phases and actors sit between pre/post actor passes.
- `engine-ab.js` loads `assets/hero.PNG` directly with no query-version cache key. `index.html` also preloads the same unversioned `assets/hero.PNG`, unlike many environment assets whose query cache version is validated.
- `engine-ab.js` assumes `COLS=4` and derives four rows by `FH=raw.height/4`; row semantics remain hard coded (`down=0`, `up=3`, lateral=2, LEFT mirrored), leaving row 1 unused.
- The renderer crops every source frame heuristically by about 5% horizontally and 4% vertically before drawing. There is no machine-readable per-frame source rectangle/pivot contract proving that this crop excludes only empty/background padding.
- After the raw sprite has already become drawable, `engine-ab.js` schedules `knockWhite()` using `requestIdleCallback` (timeout 900 ms) or `setTimeout`. That pass draws the entire sheet into a temporary canvas, calls `getImageData`, and sets alpha=0 for every pixel whose RGB channels are each >232. This is a one-time load path, not a per-frame cost, but it can mutate the visible sprite after initial display and can remove legitimate near-white art if such pixels exist.
- The white-knockout pass currently has no audit counters for how many opaque pixels are removed, no alpha/background contract, and no visual proof that the source actually requires this operation.
- `engine-ab.js` already exposes a useful actor presentation contract (`physicsRoot`, collider, `footRoot`, depth root, shadow anchor, visual bounds, nameplate anchor), so a character sprite metadata contract can extend this separation without touching physics.
- `engine-ac.js` continues to advance stride by actual world distance and MOV-STOP-V2 still resets release to frame 0; this round does not change that behavior.
- `engine-ah.js` still performs hard stop only and intentionally does not reintroduce the old combined sprite/shadow bob.
- `armor-aura.js` still sizes aura effects from `p.radius`, confirming that collider and visual-body scale remain conflated in at least one downstream visual system; do not solve that in the same commit as the sprite-contract audit.
- No new Grok locomotion response exists beyond GC-20260831-003.

### EXTERNAL_EVIDENCE
- Aseprite's official slice format supports explicit bounds and a pivot representing the central/base location of a sprite, and those slice/pivot values can be exported in sprite-sheet JSON. This is directly relevant to replacing guessed crop/pivot rules with authored metadata.
- Aseprite's official CLI can emit sprite-sheet JSON including slices and pivots, and sprite-sheet export can select frames by tags. If an authored `.aseprite` source exists, frame tags/slices are preferable evidence to reverse-engineering semantics from PNG rows. The project does not need to depend on Aseprite at runtime.
- The W3C CSSWG has an open issue documenting that nearest/pixelated scaling at non-integer factors can distort pixel art. This reinforces the need to measure 1.15x/1.25x in the full DPR×zoom×avatar-scale pipeline rather than assuming nearest-neighbour guarantees clean pixels.
- Community pixel-art reports show cardinal motion can appear smooth while diagonal/non-integer motion jitters even with fixed timestep, point filtering and integer render targets. This is counterevidence against treating a character contract as a complete jitter solution: camera/zoom/frame-pacing work remains separate.

References reviewed: Aseprite official Slices docs; Aseprite official CLI and sprite-sheet docs; W3C CSSWG issue #5837 on pixelated non-integer scaling; recent r/gamedev/raylib/Godot pixel-art jitter discussions as community counterevidence.

### HYPOTHESIS
The next high-value structural step is a minimal CHARACTER sprite contract plus offline/CI diagnostics, not another runtime visual effect. It should describe the current hero intentionally and measure unknowns rather than invent them.

A character-specific contract can make row/frame/pivot/crop/mirroring/cache assumptions explicit and allow CG-20260905-001's contact/LEFT audit to become reproducible. In particular, measuring the existing white-knockout and heuristic crop against the source pixels may uncover a hidden quality regression: intended near-white highlights or silhouette pixels could currently be removed/cropped, and scaling the sprite would only magnify that damage.

Do NOT place the hero blindly into the environment manifest if that would incorrectly model an actor as an environment asset. Prefer a small actor/character metadata file or an explicitly actor-aware extension chosen by Grok after architecture review.

### PROPOSED_CHANGE
Do not change production rendering first. Add a metadata + diagnostic layer with no visual behavior change:

1. Define one minimal character contract for Kelo hero, location chosen to fit repo architecture (for example `src/characters/hero-sprite-contract.json`, not mandated).
2. Record only proven/current facts and explicit UNKNOWNs: id/path, sheet dimensions, 4x4 grid, sampling, current direction policy, current mirror policy, current crop policy, foot-root policy, current display dimensions, cache policy, and optional semantic fields for direction tags/contact/pivots that may remain UNKNOWN until CG-001 is measured.
3. Add an offline/CI diagnostic that reads the PNG and emits per-cell measurements without modifying runtime:
   - actual sheet/frame dimensions;
   - alpha coverage and near-white pixel counts;
   - non-transparent/non-background bounding box per frame;
   - pixels that current 5%/4% crop would remove;
   - pixels that `knockWhite()` would turn transparent, including how many were originally opaque;
   - row 1 vs row 2 pixel-difference and horizontally mirrored similarity as diagnostic evidence only;
   - bottom-most opaque-pixel distribution / silhouette baseline by frame as a hint for foot-anchor consistency, not automatic semantic CONTACT labeling.
4. Expose a cache/version rule for `hero.PNG` so future A/B sprite replacements cannot be confused with a stale browser copy. Keep preload and runtime source URL consistent.
5. Only if measurement proves `knockWhite()` is unnecessary or destructive should a later one-change commit remove/replace it. Only if crop removes authored pixels should a later one-change commit alter source rectangles.
6. Keep scale 1.00x during this diagnostic. The 1.15x/1.25x A/B happens only after the source/pivot contract is trustworthy.

### DO_NOT_ASSUME
- Do not assume the PNG has a white background merely because `knockWhite()` exists.
- Do not assume every RGB>232 pixel is background; legitimate clothing, eye, highlight or effect pixels may be near-white.
- Do not infer CONTACT/plant semantics solely from the bottom-most opaque pixel or silhouette bounding box.
- Do not assume row 1 is LEFT; CG-001 still requires evidence.
- Do not assume a distinct Aseprite source file exists in the repo. Use authored tags/slices if available; otherwise keep the contract independent of Aseprite.
- Do not conflate the actor contract with Environment Asset Contract v2 unless the formal layer/ownership model is extended deliberately.
- Do not change collider radius 20, movement speed, camera, physics, gait, economy, combat or networking in this experiment.

### RISKS
- This can become over-engineered if generalized into a huge character factory. Keep v1 minimal and Kelo-specific enough to solve current unknowns.
- Pixel statistics cannot identify semantic foot contact by themselves. They are evidence for crop/pivot consistency, not animation meaning.
- Removing white knockout without inspecting the source can expose a background; retaining it without measurement can erase intended highlights.
- Adding a query version to the hero URL is behaviorally low risk but can affect preload/runtime URL deduplication if the two URLs diverge; they must match exactly.
- A one-time `getImageData` pass is not evidence of a steady-state FPS problem. Optimize it only if measurement shows load-time cost/pop or visual damage.
- Non-integer avatar scaling can still distort nearest-neighbour pixels even after metadata is correct; that remains a later A/B, not solved by this contract.
