### PROBLEM

Kelo World maps continuous 2D movement onto only four visible facing rows. The current local-player visual controller decides lateral versus vertical facing from a single instantaneous ratio test on every movement update. There is no hysteresis, dwell, previous-facing preference band or semantic diagonal policy around the boundary. Touch/joystick vectors are continuous floats, so a nearly unchanged diagonal trajectory can cross that boundary repeatedly because of small finger/axis variation. That can produce abrupt row changes (right/left walk row <-> up/down row) while physical speed and direction remain perceptually steady. This is especially relevant to the user's current goal: make left/right motion look planted and premium before scaling the avatar.

### CONFIRMED_IN_GEMINI

Current `main` at the base commit loads `engine-ab.js?v=240` and `engine-ac.js?v=220`; `index.html` declares Kelo World V6.21.

`engine-a.js::processInput()` normalizes keyboard diagonals and produces continuous radial touch input:
- keyboard diagonal: `(±1/sqrt(2), ±1/sqrt(2))`;
- touch: `input.normX=(dx/dist)*mag`, `input.normY=(dy/dist)*mag` after a circular radial deadzone.

`engine-ac.js::updateVisualMotion()` updates `v.dx/v.dy` from actual displacement, velocity, or intent and classifies facing on every active update with:

`const side = Math.abs(v.dx) * 1.15 >= Math.abs(v.dy);`

then `right/left` if side, otherwise `down/up`.

There is no previous-face hysteresis or minimum angular persistence around that comparison.

The ratio boundary is `|dy/dx| = 1.15`, equivalent to about 48.99 degrees from the horizontal axis. Therefore each horizontal/lateral sector spans about 97.98 degrees total while each vertical sector spans about 82.02 degrees. This is a deliberate-looking lateral bias, not an equal 45-degree quadrant split, but the code does not document why 1.15 is the chosen value.

An exact keyboard diagonal has `|dx|=|dy|`, therefore `|dx|*1.15 >= |dy|` is always true: all exact WASD diagonals resolve to LEFT/RIGHT presentation, not UP/DOWN. Touch can occupy any angle and can repeatedly cross ~48.99 degrees.

`engine-ab.js` consumes `p._visualMotion.face` and selects row `2` for both left/right (left is mirrored), row `3` for up and row `0` for down. Thus crossing the threshold is not a subtle parameter change: it selects a different spritesheet row. `engine-ab.js` also contains another 1.15 ratio classifier in `faceOf()`, but for a local player with `_visualMotion` the `m.face` supplied by `engine-ac.js` wins first. The duplicate classifier is therefore a responsibility/debt signal rather than the current local facing authority.

No new Grok feedback exists after GC-20260831-003, so no later measured diagonal/facing decision supersedes this finding.

### EXTERNAL_EVIDENCE

Godot's official `Input.get_vector()` documentation treats joystick/WASD input as a continuous vector with length capped at 1 and a circular deadzone. That supports Kelo's radial input model, but it does not solve presentation-state switching at cardinal boundaries by itself.

Godot issue #81975 documents real joystick-axis flicker when a direction-like action is derived directly from a noisy/wiggled analog axis, demonstrating that analog values around thresholds can repeatedly cross state boundaries. Godot issue #103360 documents another threshold problem: analog-stick rebound can briefly cross a low deadzone and generate unintended opposite inputs. These are not the same Kelo bug, but they are direct evidence that instantaneous threshold decisions on analog axes need careful stability policy.

A recent July 2026 r/godot discussion describes the exact art-direction problem relevant here: when transitioning from a cardinal direction into a diagonal, the desired four-direction sprite can preserve the prior cardinal animation instead of immediately selecting whichever axis happens to win a new comparison. Another community thread on abrupt directional animation switching notes visible flicker between walk-direction animations; other 8-direction discussions report one-frame direction snaps caused by slightly different input-release timing and use a short buffer/previous-direction memory to stabilize presentation.

Counterevidence: instantaneous dominant-axis selection is common, cheap and deterministic. With a keyboard it may be preferable because exact diagonals are stable values and no analog noise exists. Adding hysteresis that is too wide can make the sprite visibly face RIGHT while the player is already traveling mostly UP, which would be worse than the current behavior. Therefore this is not a recommendation to add smoothing blindly.

### HYPOTHESIS

The lateral animation will look more premium on touch if facing classification becomes a presentation state with a small angular hysteresis band around the existing ~49-degree boundary, while physical movement remains completely unchanged. The likely best policy is not time smoothing of the movement vector; it is state-aware cardinal selection: retain the current visible cardinal direction inside a narrow diagonal ambiguity band and switch only after the competing axis wins clearly.

A narrow band should reduce lateral<->vertical row popping during near-diagonal touch travel without increasing input latency or changing world trajectory. Keyboard exact diagonals can retain the current lateral preference unless product testing shows another policy feels better.

### PROPOSED_CHANGE

Do not modify production before baseline measurement.

A — BASELINE_SINGLE_BOUNDARY
- Keep current `abs(dx)*1.15 >= abs(dy)` classification.
- Instrument face switches and input/travel angle.

B — STATEFUL_ANGULAR_HYSTERESIS
- Preserve the current ~49-degree neutral boundary as the center.
- When currently lateral, do not switch vertical until the travel angle exceeds a tested exit boundary beyond the center.
- When currently vertical, do not switch lateral until travel angle falls below a tested enter boundary below the center.
- Benchmark total hysteresis widths of approximately 4, 8 and 12 degrees rather than hard-coding one by intuition.
- Do not filter or rotate the actual movement vector.

C — PREVIOUS_CARDINAL_DIAGONAL_POLICY
- As a comparison, when both axes are materially active and neither dominates strongly, retain the last cardinal face until one axis clearly dominates.
- This is conceptually similar to B but can be expressed directly in component ratios and may be easier to maintain without atan2.

D — EIGHT_DIRECTION_ATLAS
- DEFERRED. Adding authored diagonals may ultimately look best, but it multiplies art/content requirements and should not be used to hide instability in the four-direction state machine.

Architecture note: if a helper is introduced later, one function should own cardinal presentation selection. Do not keep live copies of the 1.15 rule in both `engine-ac.js` and `engine-ab.js`. First trace remote/legacy use before deleting any fallback.

5. Repeat with natural noisy touch paths if the harness can capture/replay them.
6. Keyboard controls: W+D, W+A, S+D, S+A must be tested separately because exact 45-degree diagonals are stable and currently lateral-biased.
7. Compare A versus B widths ~4/8/12 degrees and C using identical vector traces.
8. Repeat at 60/90/120 Hz-equivalent presentation/update conditions after confirming actual update cadence.
9. Re-enable normal camera and repeat the winner.
10. After a facing policy wins at 1.00x avatar size, repeat at 1.15x and 1.25x; a larger sprite will make row pops more visible.

Suggested traces also include: RIGHT -> shallow up-right -> RIGHT; UP -> shallow up-right -> UP; sustained 45-degree diagonal; circular joystick sweep; hard RIGHT -> LEFT reversal; RIGHT+UP -> LEFT+UP reversal.

### RISKS

- Too much hysteresis can make facing semantically wrong during true diagonal-to-cardinal turns.
- A time-based hold instead of angle/state hysteresis could make 60/90/120 Hz behavior harder to reason about and can add input lag.
- If `v.dx/v.dy` is contaminated by collision resolution near walls, a facing classifier based on actual displacement may still jump even with hysteresis; test open ground first, then walls as a separate counter-test.
- Exact keyboard diagonal preference is an art/product choice. Changing it can make desktop feel different even if touch improves.
- Future 8-direction sprites would change this policy, so keep the classifier data-driven/small rather than embedding it into renderer code.
