### PROBLEM
The local visual stride is distance-based, but `engine-ac.js` credits stride only when the distance moved in the current update exceeds `MIN_VISUAL_MOVE_PX = 0.12`. Because `lastX/lastY` are updated every call even when the distance is rejected, sub-threshold movement is discarded rather than accumulated. At sufficiently slow lateral movement, the body can move through the world while `stridePhase` does not advance; if update cadence differs across 60/90/120Hz displays, the boundary at which this occurs can also differ.

### CONFIRMED_IN_GEMINI
- `engine-ac.js` sets `MIN_VISUAL_MOVE_PX = 0.12`.
- `updateVisualMotion()` computes `dist = hypot(p.x-v.lastX,p.y-v.lastY)` every call.
- It sets `v.lastStepDistancePx = dist > MIN_VISUAL_MOVE_PX ? dist : 0`.
- Stride advances only when `v.on && v.lastStepDistancePx > 0`.
- Regardless of whether distance was credited, the function ends by writing `v.lastX = p.x; v.lastY = p.y`; therefore rejected sub-threshold distance is not accumulated into a later stride step.
- Movement itself remains continuous in `engine-a.js`: player position advances by `vx*dt` / `vy*dt` and is not quantized to 0.12px.
- With current WALK speed cap 110 px/s, target physical speed is approximately `mag*110` below the blend start. Therefore, under one update per display refresh as a test model, the per-update displacement is ~0.092px at 60Hz for mag 0.05, ~0.061px at 90Hz and ~0.046px at 120Hz; all are rejected. For mag 0.10 it is ~0.183px at 60Hz, ~0.122px at 90Hz and ~0.092px at 120Hz, meaning the same input magnitude could credit stride at 60/90Hz but not at 120Hz. These are derived boundary calculations, not live measurements of actual update cadence.
- `engine-ab.js` consumes the resulting `visual.frame` directly for the visible PNG, so a stalled `stridePhase` is visible as a held animation pose even while the player position continues moving.

### EXTERNAL_EVIDENCE
- MDN documents that `requestAnimationFrame()` callback frequency generally follows display refresh rate and explicitly warns that animation progress must account for elapsed time to avoid high-refresh-rate differences: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame
- A current GitHub issue in `SardineFish/raindrop-fx` reports the same general failure class: animation speed tied to an assumed per-frame delta changes on fast-refresh displays: https://github.com/SardineFish/raindrop-fx/issues/17
- Community pixel-art discussions note that float world motion plus frame-rate-independent timing is normal, while presentation can still snap/quantize separately; the key is not to discard real movement solely because each individual frame displacement is small: https://www.reddit.com/r/GameDevelopment/comments/sb9351/pixelperfect_jitterfree_animation/
- Counterevidence: a small movement threshold can be useful to suppress collision jitter/noise and avoid twitching animation while nominally idle. Therefore the threshold should not simply be deleted unless an accumulation/noise test shows a better contract.

### HYPOTHESIS
The current threshold should be applied to accumulated visual travel or to motion-state/noise qualification, not used as a destructive per-update distance gate. A tiny remainder accumulator can preserve every real world pixel traveled while still ignoring true jitter. This should make slow LEFT/RIGHT stride progression independent of update cadence without changing physics, input, collider, camera, gait thresholds, or total cycle distance.

### PROPOSED_CHANGE
Do not change production before measurement.
A. BASELINE: current destructive per-update gate.
B. ACCUMULATED_DISTANCE: accumulate raw `dist` into `pendingStrideDistance`; only publish/consume once a noise threshold is crossed, carrying the whole accumulated amount into `stridePhase` instead of discarding earlier sub-threshold travel.
C. SPEED/INTENT_GATE: advance stride from all real distance whenever movement state is valid (`hasIntent` or trusted physical speed), using the 0.12 threshold only to decide whether a single displacement is reliable for facing/noise, not whether distance exists.
Prefer B first because it preserves the existing jitter guard with minimal semantic change.

### DO_NOT_ASSUME
- Do not assume the main loop is exactly one simulation update per display refresh; instrument actual update cadence first.
- Do not change the physical movement integrator, joystick deadzone, gait thresholds, cycle distances, camera, collision, or renderer in the same experiment.
- Do not remove the threshold globally until collision-adjacent jitter traces are tested.
- Do not count intended zero-input settling as stride distance.
- Do not use render-count-based accumulation.

### EXPERIMENT
1. Instrument `updateVisualMotion()` and actual simulation cadence: `updateDtMs`, `updatesPerSecond`, `rawDist`, `creditedDist`, `discardedDist`, `pendingStrideDistance`, `stridePhase`, `frame`, `actualSpeed`.
2. In open terrain with frozen camera, hold pure RIGHT then pure LEFT at processed magnitudes 0.04, 0.05, 0.075, 0.10, 0.15, 0.30 for at least 4 seconds each.
3. Repeat under 60/90/120Hz conditions or controlled scheduler profiles that reproduce those update cadences; verify actual updates rather than assuming display Hz.
4. Compare A vs B using the exact same input/time trace. Total world distance and physics trace must match.
5. Run a collision-adjacent idle/jitter trace against a wall and after release to ensure B does not animate from tiny collision corrections.
6. Repeat winning candidate on diagonal slow movement and LEFT↔RIGHT reversal.

### DECIDING_METRICS
- `visualDistanceCreditRatio = creditedStrideDistance / actualWorldDistance` during valid movement: target 0.98–1.02 after startup/stop exclusions.
- `visualDistanceCreditRatioSpreadAcross60_90_120`: target <= 2 percentage points.
- `stridePhaseDeltaAfterSameWorldDistanceAcrossHz`: target <= 0.01 cycles.
- `movingWorldWhileStrideFrozenMsP95`: target near 0 during sustained valid movement above gait idle threshold.
- `discardedValidMovementPxPerSecond`: target near 0.
- `idleCollisionJitterStrideAdvancePx`: target 0 or no worse than baseline.
- `frameTransitionCountPer50WorldPx` for WALK: stable across Hz.
- `worldTraceDiffPx`, `cameraTraceDiffPx`, `collisionOutcomeDiffCount`: target 0 vs baseline.

### RISKS
- Naive accumulation could turn tiny collision corrections into delayed animation pops; reset/qualification rules matter.
- If the actual game loop uses a fixed simulation timestep independent of display refresh, the cross-Hz severity may be lower than the derived examples, but the destructive-distance-loss bug still exists for any per-update displacement below 0.12px.
- At very low joystick magnitudes just above `GAIT_IDLE_MAX`, extremely slow walking may be artistically undesirable even if mathematically correct; that is a separate gait/input design question and should not be hidden by accidental distance loss.
- Fixing stride credit may expose the already-known uniform 25% pose dwell issue from CG-20260903-017; evaluate them separately.
