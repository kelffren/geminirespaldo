### PROBLEM
The current movement stack already computes a continuous speed-dependent squash/stretch signal in `engine-a.js`, but the live authored hero path in `engine-ab.js` draws fixed `dw/dh` dimensions from `KELO_AVATAR_PRESENTATION` and never consumes `p.squashX/p.squashY`. The user's current priority is premium lateral movement (weight, lean, bob, arm/body response, planted feet) plus larger avatars. Adding a brand-new secondary-motion layer without first auditing this dormant signal would create duplicated responsibility and could produce conflicting transforms.

There is also a grounding risk. `engine-a.js` trends `squashX` toward `1 + (currentSpeed / CONFIG.speed) * 0.08` and `squashY` toward `1 - (currentSpeed / CONFIG.speed) * 0.06` with exponential smoothing (`15 * dt`). Under the current DIRECT movement path set by `engine-ac.js`, `currentSpeed / CONFIG.speed` is approximately processed input magnitude when unobstructed, so at full input the latent target is about `1.08 x 0.94`. If this were naively applied around the sprite center, a ~93 world-px lateral visual could move the visible bottom/feet by roughly `(1 - 0.94) * 93 / 2 ~= 2.8 world px` vertically simply from the pivot choice. That would work against foot planting and the independent `footRoot` / `shadowAnchor` contract already exposed by `engine-ab.js`.

### CONFIRMED_IN_GEMINI
1. Current live `main` at the start of this round is `1dfe873f60e2b6607a178746bb8995349262b581`.
2. `index.html` declares `Kelo World — V6.33` and loads `engine-a.js`, then later `engine-ab.js`, `character-appearance.js`, and `engine-ac.js`; therefore the live owner must be read from late-loaded code rather than assumed from older rounds or the older ENGINE_MAP snapshot.
3. `engine-a.js::updateMovement(dt)` always updates:
   - `localPlayer.squashX += (1 + (currentSpeed/CONFIG.speed)*0.08 - squashX) * (1-exp(-15*dt))`
   - `localPlayer.squashY += (1 - (currentSpeed/CONFIG.speed)*0.06 - squashY) * (1-exp(-15*dt))`
   This happens independently of whether the final hero renderer uses those fields.
4. `engine-ac.js` sets `CONFIG.movementType='DIRECT'` and wraps `updateMovement`; it computes the current speed cap/gait and distance-driven visual stride. It does not publish a separate lean/bob/squash transform.
5. `engine-ab.js` is the live `hero.PNG` renderer. Its destination rectangle uses fixed `layout.visualWidth` / `layout.visualHeight`, anchored with `footY = layout.footRootY`, and its `drawImage` path does not read `p.squashX` or `p.squashY`.
6. `engine-ab.js` already defines presentation roots separately: physicsRoot, footRoot, depthRoot, shadowAnchor and visual bounds. Therefore any secondary transform can be tested purely in presentation space without changing collider/world motion.
7. This is real redundancy/dead responsibility: movement state owns a visual deformation signal that the final visual owner does not consume. Do not refactor it away yet; first determine whether the signal is useful, obsolete, or harmful.

### EXTERNAL_EVIDENCE
- Unity's current 2D Sprite documentation explicitly treats sprite pivot and physics shape as separate authored properties. This supports keeping presentation pivot decisions independent from collision geometry: https://docs.unity3d.com/6000.0/Documentation/Manual/com.unity.2d.sprite.html
- Unity's SpriteAlignment API includes BottomCenter and Custom pivot options, confirming that a character visual does not need to transform around its rectangle center: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/SpriteAlignment.html
- Godot's 2D documentation states that 2D nodes have independent position/rotation/scale and that the rotation pivot can be moved from the sprite center. This supports a child/presentation transform around a chosen foot root instead of mutating physics: https://docs.godotengine.org/en/stable/tutorials/2d/introduction_to_2d.html
- Community evidence is mixed, which matters. Squash/stretch on direction change is commonly used for game feel, but developers also report artifacts when scale stays deformed or anchors are wrong; this is evidence against blindly re-enabling a latent transform: https://www.reddit.com/r/gamemaker/comments/12i1l95/

COUNTEREVIDENCE:
- A continuous full-speed `1.08 x 0.94` deformation may be too strong or visually rubbery for Kelo World's desired premium HD-2D tone. The mere existence of the old signal is not evidence that it should be restored.
- Sprite-frame changes already provide authored silhouette motion. Additional scaling can make nearest-neighbor pixels change apparent thickness, especially under the fractional zoom×DPR issue identified in earlier research.
- Full-body squash can damage foot planting if applied around center, and can alter nameplate/visual bounds if those are recomputed from transformed extents rather than from the stable presentation contract.

### HYPOTHESIS
A small, transient, foot-root-pivoted secondary transform can improve perceived weight at start/stop/reversal without changing physics, but the existing continuous `1.08 x 0.94` speed target should NOT be restored unchanged.

Most promising direction to benchmark:
- treat the existing `squashX/squashY` as an input signal/reference only;
- apply a QA-only presentation transform around `footRoot`, not around `p.x,p.y` center;
- strongly reduce amplitude and/or make it transient around acceleration/deceleration/reversal rather than permanent at cruising speed;
- leave steady-state stride frames and world distance as the primary locomotion signal.

### PROPOSED_CHANGE
Do not modify production yet.

Candidate A — baseline:
- current fixed-size renderer; latent `squashX/squashY` computed but ignored.

Candidate B — raw latent-signal QA experiment:
- apply existing `squashX/squashY` to the hero render around `footRoot` only.
- purpose is diagnostic, not a proposed final look.

Candidate C — reduced transient QA experiment:
- derive body scale from velocity CHANGE / reversal instead of permanent speed.
- example search envelope, not approved constants: horizontal stretch/compression <= 1.5–2.5%; vertical reciprocal compensation <= 1–2%; settle within roughly 80–160 ms.
- pivot exactly at `footRoot` or a validated per-frame support anchor.
- shadowAnchor remains unchanged.
- do not modify collider, p.x/y, camera target, stride phase, speed or input.

Candidate D — if scaling degrades sprite quality:
- no squash scaling at all; prefer <=1 world-px vertical/horizontal body offset/lean around footRoot, preserving original pixel dimensions.

### DO_NOT_ASSUME
- Do not assume old `squashX/squashY` is part of the current visual design just because engine-a still updates it.
- Do not assume continuous squash is desirable for a premium character.
- Do not scale the collider with the sprite.
- Do not move `footRoot`, `depthRoot`, or `shadowAnchor` with body bob/squash.
- Do not combine this benchmark with 1.20x avatar scale, zoom quantization, support-foot compensation, or camera changes in the same first experiment.
- Do not delete the latent fields until same-trace testing proves they are obsolete; they may still be read by legacy/fallback render paths.

### RISKS
1. Nearest-neighbor fractional scaling may introduce temporal shimmer even at low amplitudes.
2. Pivot math for LEFT mirror can be wrong if transform order is `translate/scale/mirror` instead of being composed around the same foot root.
3. Visual bounds/nameplate may become stale if body deformation exceeds the published fixed bounds; for the first benchmark keep amplitudes tiny and log overflow rather than changing bounds.
4. Continuous speed-based deformation can make walking look elastic rather than planted.
5. If legacy renderers still read `squashX/y`, deleting or repurposing those fields could be a regression; scan consumers before cleanup.
6. Measuring only screenshots at 220 ms intervals would miss start/reversal transients; sample every render/update or <=16.7 ms.
