### PROBLEM
GC-20260909-008 verified that LEFT↔RIGHT reversal is baseline-clean at 60/90/120 Hz and fixed a separate owner-boundary bug so Character Appearance now honors Movement's explicit idle plant frame 2. That makes the next unresolved transition measurable: after idle, DIRECT movement starts immediately, but visual stride starts from phase 0.5/frame 2 and cannot leave frame 2 until the actor travels the remaining quarter of the current cycle. The result may be a planted-looking full-body pose translating through the world before the first visible locomotion pose change.

### CONFIRMED_IN_GEMINI
Current LIVE `engine-ac.js` owns the visual stride through `KeloMovement`. It defines `DEFAULT_PLANT_FRAME=2`, therefore `PLANT_PHASE=0.5`; walk cycle distance is 50 world px and max-run cycle distance reaches 90 world px. While moving, `stridePhase += lastStepDistancePx / cycleWorldPx` and `frame = floor(stridePhase*4)%4`. Because frame 2 spans phase [0.5,0.75), a start from the planted state requires 0.25 cycle before frame 3 can appear: 12.5 world px for walk and 22.5 world px at max run. Physics remains DIRECT; there is no physical startup acceleration ramp.

The shared LIVE `KeloMovementProfile` currently defines walkSpeed=110, maxSpeed=185.28, gaitRunStart=0.70, lowAnalogCeiling=0.48. Using the canonical target-speed function gives approximate time from idle plant frame 2 to the first possible next pose: mag 0.48 -> target 52.8 px/s -> 12.5 px -> 236.7 ms; mag 0.70 -> target about 97.3 px/s and run cycle begins at 50 px -> 12.5 px -> about 128.4 ms; mag 1.0 -> target 185.28 px/s -> 22.5 px -> about 121.4 ms. On the first update after input at 60/90/120 Hz all three cases still remain in frame 2; refresh-rate quantization is smaller than the underlying distance hold.

Current `src/characters/character-appearance.js` consumes the explicit Movement frame and registers the source frame with per-frame foot anchors against `KELO_AVATAR_PRESENTATION.footRoot`. Those anchors stabilize registration, but `footRootX/Y` themselves follow actor position; therefore they do not by themselves prove a support foot is world-locked during the 12.5–22.5 px startup translation. `engine-ab.js` already contains alpha/contact analysis, but its lateral contact audit currently samples only row 2/right, so it cannot yet establish LEFT/RIGHT startup support-foot behavior symmetrically.

`engine-ah.js` explicitly documents that an older procedural bob was removed because it moved shadow+sprite and made the character float. A new global bob/lean is therefore not an acceptable blind workaround.

### EXTERNAL_EVIDENCE
Unity's root-motion documentation keeps transition/blending reference near the feet to reduce floating and describes idle clips as commonly baking XZ translation into the pose instead of allowing repeated drift. Unity's Timeline documentation also gives a concrete foot-slide example: an otherwise natural transition can slide when the positions of the feet differ across the transition, and recommends correcting clip offsets so the foot position changes less drastically. These are 3D systems, not direct prescriptions for Kelo's 2D sprite renderer, but they support the principle that transition quality should be measured at foot/contact registration rather than only by body/root continuity.

Community reports about locomotion foot sliding similarly emphasize mismatch between movement displacement and authored gait/transition timing, but these reports are anecdotal and are not sufficient evidence to choose a Kelo phase offset without measuring the actual hero sheet.

### HYPOTHESIS
The current start from phase 0.5/frame 2 may create visible startup skating because the actor can move 12.5–22.5 world px before the first full-body pose change. This is NOT yet proven perceptually in a browser capture. The effect should become easier to notice as the avatar grows from 1.15x toward 1.20x, but scale must not be changed in the same primary experiment.

A second hypothesis is that the per-frame anchor currently functions mainly as sprite registration, not true world-space foot planting. If the visible support-foot contact pixel follows the moving footRoot one-for-one during the held frame, phase timing rather than anchor math is the first lever to test.

### PROPOSED_CHANGE
Do not change production until the baseline is instrumented. Reuse the existing Movement/Appearance audit path; do not add another movement manager or wrapper.

Benchmark A: current plant phase 0.50/frame 2.

Candidate B, only if baseline proves startup slide: on the single off→on presentation transition, seed visual stride closer to the authored departure boundary while leaving requested velocity, resolved movement, collision and camera untouched. The exact phase must be selected from measured contact/pose behavior, not guessed.

Candidate C, only if sprite analysis proves a specific authored departure pose is anatomically better: map the idle→move transition to that departure pose/phase while subsequent locomotion remains distance-driven.

Candidate D, if phase timing is already acceptable but contact registration is not: correct presentation anchor/contact registration instead of stride phase.

Do not add slow physical acceleration, input delay, long startup animation, global bob, body lean or camera shake as a substitute.

### DO_NOT_ASSUME
Do not assume that frame 2 is visually wrong simply because it persists for 12.5–22.5 px. The authored frame may intentionally represent a strong push-off pose. Do not assume the source `footX/footY` anchor identifies the same anatomical support point in every frame without alpha/contact inspection. Do not assume a lower first-pose latency is always better; an immediate frame jump can look worse than a brief planted departure. Do not alter the canonical client/server movement profile, collider, PvP aim-facing, reversal policy or avatar scale in this experiment.

### EXPERIMENT
Start from a fully stopped actor with explicit plant frame 2. Run LEFT and RIGHT at magnitudes 0.48, 0.70 and 1.00 at deterministic 60, 90 and 120 Hz. Record the first 250 ms or until at least one complete visible pose change.

For each run capture: input timestamp; first resolved world displacement; visual face; stride phase; rendered frame; cumulative world distance; source foot anchor; rendered destination rect; and, when alpha analysis is available, visible bottom-contact/support centroid in rendered world/CSS coordinates.

Extend the existing sprite/contact audit to both LEFT row 1 and RIGHT row 2 before using contact metrics to choose a transition phase. Repeat the identical trace for baseline and each candidate. After a candidate wins, repeat it at 1.20x only as a secondary visibility regression check; do not make scale part of the primary change.

### RISKS
A phase bias can create an obvious frame pop, shorten authored push-off unnaturally, alter perceived cadence differently at walk vs run, or make LEFT/RIGHT asymmetry worse. Contact-centroid analysis can be fooled by clothing/weapons or non-foot opaque pixels near the bottom of a frame. Applying phase and anchor changes together would destroy attribution. Enlarging the avatar in the same pass would also confound the result.
