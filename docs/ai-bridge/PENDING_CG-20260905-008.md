### EXTERNAL_EVIDENCE
- Canvas 2D `drawImage()` supports destination scaling, and `imageSmoothingEnabled=false` is the standard browser mechanism for keeping enlarged pixel-art edges crisp rather than interpolated.
- Counterevidence: nearest-neighbour filtering does not guarantee temporally stable pixel art under every non-integer DPR/zoom/scale combination. Community reports and pixel-art engine issues document residual jitter/shimmer from fractional screen-space motion even when point/nearest filtering is enabled.
- Therefore 1.15x is an A/B candidate, not proof that the result is automatically more premium. Temporal movement, camera and high-refresh behavior still require observation/measurement.

### HYPOTHESIS
Increasing only the hero destination presentation to 1.15x, anchored to the same foot root, should improve visual presence while keeping physics and world-space interaction unchanged. Moving the nameplate upward with the enlarged visual bounds should preserve basic legibility. Because draw dimensions are rounded to integer world pixels and smoothing remains disabled, this is a lower-risk first scale increment than jumping directly to 1.25x.

### RISKS
- 1.15x is a non-integer conceptual scale even though destination dimensions are rounded; DPR x camera zoom can still produce fractional physical sampling and temporal shimmer.
- Enlarging only the body can make the current `p.radius`-based Armor Aura look undersized, especially high ranks.
- Enlarged visual bounds may enter front-occlusion regions sooner while depth ordering still uses the same foot root. That is usually the desired feet-based depth model, but it needs screenshot/trace validation around fountain/architecture/props.
- The nameplate moves upward with the body and may collide with HUD/NPC labels in dense scenes.
- The hero asset itself still has unresolved crop/knockWhite and row/contact semantics; enlarging it can magnify source-quality defects even when geometry is correct.
- The first LIVE run exposed a workflow race: a push-triggered audit can start before Pages finishes deploying the same commit. The rerun passed the hero step after propagation. The workflow should eventually wait for/verify deployed revision rather than relying on timing.
