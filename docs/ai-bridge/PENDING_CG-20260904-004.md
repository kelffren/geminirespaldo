### PROBLEM

The current distance-driven gait has a hard WALK→RUN mode switch at processed input magnitude 0.70. The physical speed curve remains continuous across that threshold, but the visual distance per animation cycle jumps from 50 world px to 90 world px in one update. Because stride phase increments as `distance / cyclePx`, crossing into RUN can make the visible leg cycle substantially slower at almost the same physical speed. On analog touch input hovering around 0.70, this can also alternate the cadence between two incompatible rates even when world velocity changes only slightly.

### CONFIRMED_IN_GEMINI

At current `main` base commit `9fe171e...`, `engine-ac.js` defines:

- `GAIT_RUN_START = 0.70`
- `WALK_CYCLE_WORLD_PX = 50`
- `RUN_CYCLE_WORLD_PX = 90`
- `gaitFrom(mag)` returns `walk` for `mag < 0.70` and `run` otherwise.
- `speedFor(mag)` is continuous: below/above 0.70 it uses the same smooth `speedCap` curve; `engine-a.js` then sets DIRECT velocity from `input.norm * CONFIG.speed`.
- `updateVisualMotion()` preserves the existing `stridePhase`, but for every credited step chooses `cyclePx = gait === 'run' ? 90 : 50` and advances `stridePhase += distance/cyclePx`.
- `engine-ab.js` maps `stridePhase` to one of four atlas columns. There is no separate WALK row and RUN row; both gaits reuse the same four columns. The only cadence difference is therefore the distance denominator.

Derived from the current formulas, not a live measurement:

- At processed magnitude 0.699, target speed is about 97.03 world px/s. WALK cadence is ~97.03/50 = 1.94 cycles/s (~7.76 atlas-frame advances/s for four columns).
- At processed magnitude 0.700, target speed is about 97.32 world px/s. RUN cadence becomes ~97.32/90 = 1.08 cycles/s (~4.33 atlas-frame advances/s).

So an input increase of 0.001 and a physical-speed increase of only ~0.30% can reduce visual cycle frequency by roughly 44%. This is a code-derived discontinuity and should be measured visually before implementation changes.

### EXTERNAL_EVIDENCE

Official Unreal Engine Animation Locomotion/Distance Matching documentation explicitly describes driving animation by distance or adjusting cycle play rate to match in-game movement speed so feet do not slide when character speed changes. Unreal's `Set Playrate to Match Speed` documentation says cyclic walk/jog animations typically adjust play rate to match current movement speed, while Distance Matching exists to align poses with actual travelled distance.

Godot's long-running BlendSpace synchronization issues provide relevant caution: when locomotion animations with different durations/cycle timing are switched or blended without compatible normalized phase, visible footstep timing can become unsynchronized. A 2024 Godot issue for discrete BlendSpace2D notes cardinal pixel-art locomotion can restart/lose synchronized footstep timing during directional transitions, and a 2026 Godot documentation update added explicit cyclic synchronization support for BlendSpaces.

Community evidence from Unreal/gamedev repeatedly identifies the visible symptom as foot sliding/skating when animation cadence and actual movement speed disagree; practitioners commonly measure the ground distance represented by a foot-contact cycle and tune animation rate to that distance rather than choosing cycle speed independently.

Counterevidence: walk and run do not have to share one cadence function. A run can legitimately have a longer world distance per cycle because stride length increases. A discrete 50→90 px step may even be visually correct if the four reused source poses are authored such that the run stride is nearly twice the walk stride. Therefore do not replace the constants just because the derived cadence is discontinuous; first inspect the actual lateral poses and benchmark threshold crossings.

### HYPOTHESIS

The premium lateral feel will improve if world-distance-per-cycle changes continuously, or at least with hysteresis/phase-safe transition, through the walk→run blend region instead of switching instantly from 50 to 90 at magnitude 0.70. Because the current asset reuses the same four lateral columns for walk and run, a continuous `cycleWorldPx` derived from processed magnitude is a low-complexity candidate. However, if the atlas visually encodes distinct walk/run semantics despite sharing columns, an authored two-gait cadence map may be preferable.

### PROPOSED_CHANGE

Do not modify production before baseline traces and source-pose classification.

Benchmark these candidates using the same recorded input/world traces:

A — BASELINE_HARD_CYCLE_SWITCH
- Current `50 px` WALK / `90 px` RUN threshold at `mag=0.70`.

B — CONTINUOUS_CYCLE_DISTANCE
- Keep gait labels for UI/state, but compute the cycle denominator continuously over a bounded blend interval, e.g. candidate region around the existing speed blend/run threshold.
- Example concept only: `cycleWorldPx = lerp(50, 90, runBlend)` where `runBlend` is monotonic and continuous. Do not hardcode this exact formula until traces are reviewed.

C — HYSTERETIC_GAIT_CYCLE
- Keep discrete 50/90 cycle lengths but add a small WALK→RUN / RUN→WALK hysteresis band so analog input around 0.70 cannot flip cadence every update.
- This addresses threshold thrash but not the one-time cadence discontinuity, so it is a control candidate rather than the preferred architecture.

D — SPEED-MATCHED_CADENCE_MAP
- Derive world distance per cycle from measured source pose/contact semantics and desired foot-contact cadence rather than magnitude label alone.
- Use only if the actual atlas can support a meaningful walk/run cadence map.

For B/D, preserve normalized stride phase through gait changes. Do not reset phase or column solely because gait label changes.

### RISKS

- Continuously interpolating 50→90 may still be artistically wrong if the source pose sequence has a preferred authored cadence.
- Hysteresis can hide threshold chatter but leave a large one-time cadence jump.
- Making run cadence simply faster can produce tiny frantic legs if the four source columns do not visually support running.
- If CG-020 drops small per-update distances, near-threshold cadence measurements can be contaminated at some update rates.
- Collisions can reduce actual distance while intent remains high; cadence should continue to follow credited world travel rather than target speed to avoid foot skating into walls.
- Enlarging the avatar will make cadence mismatch and foot slip more visible but should not be part of the first causal test.
