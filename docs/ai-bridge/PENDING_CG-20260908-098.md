### PROBLEM
The current avatar presentation contract already exposes `shadowAnchorX/Y` at the semantic foot root, but the modern LIVE `player_hero_v1` render path does not visibly consume that anchor or draw a contact shadow. `engine-w.js` still draws a legacy ellipse shadow, but `character-appearance:custom-sprite` (priority 200) renders the production appearance and does not call `next()` once ready, so the lower legacy base renderer and its shadow are bypassed. `engine-ab:production-hero` (priority 100) likewise draws the sprite/nameplate but no shadow. This can reduce perceived foot planting and weight, especially during LEFT/RIGHT movement, reversals, blocked states, and at proposed 1.20x avatar scale.

### CONFIRMED_IN_GEMINI
- `engine-ab.js` publishes `KELO_AVATAR_PRESENTATION` with `footRoot`, `depthRoot`, and `shadowAnchor`, all sharing the semantic foot root (`p.y + 10`).
- `src/characters/character-appearance.js` is LIVE, default player appearance is `player_hero_v1`, middleware priority is 200, and successful rendering ends without calling `next()`.
- `src/core/avatar-render-system.js` dispatches middleware in descending priority; lower middleware/base renderers only execute when the current middleware calls `next()`.
- `engine-w.js` base renderer is the confirmed location that draws `ctx.ellipse(x, y + 18, 14, 5, ...)` as a contact shadow.
- `engine-ab.js` modern production hero renderer has no contact-shadow draw.
- `engine-c.js` renders `belowActor` world FX before actors, but current code inspected does not provide an avatar contact-shadow owner there.
- Therefore, after `player_hero_v1` is ready, the player can render through the modern appearance path while bypassing the only confirmed avatar contact shadow.

### EXTERNAL_EVIDENCE
Unity 2D documentation supports using a sprite Pivot as the semantic world-space sort point instead of the visual center, reinforcing foot/pivot-based presentation for tall 2D sprites. Godot/community practice for top-down characters commonly keeps the ground shadow separate from body-local vertical/animation transforms so the shadow remains attached to the ground rather than following the animated sprite. Reddit examples specifically recommend separating the shadow from the animated CharacterSprite branch and keeping it with the ground/root movement. Counterevidence: a contact shadow is stylistic, not mandatory; some pixel-art games intentionally omit it, and an oversized/soft ellipse can make a character look like it is floating or standing on a sticker. Therefore this must be benchmarked visually, not assumed.

### HYPOTHESIS
A subtle, foot-root-anchored contact shadow rendered independently of BODY_LOCAL lean/bob will improve perceived lateral weight and foot planting more than adding extra body bob alone, particularly at 1.20x. The shadow should remain ground-anchored while body-local animation may rotate/scale/offset the sprite. It may need mild width/opacity modulation by gait phase, but phase modulation should only be explored after a static baseline proves beneficial.

### PROPOSED_CHANGE
Do not restore the legacy renderer or duplicate avatar composition. Add/extend one presentation-level contact-shadow capability that consumes `KELO_AVATAR_PRESENTATION.shadowAnchor` and is rendered once per actor before the body. Prefer an existing owner/hook (`KeloAvatar` middleware or the existing visual layer architecture) rather than a new render wrapper. Candidate A: current no-shadow baseline. Candidate B: static ellipse/contact blob at shadowAnchor, width derived from visual footprint but capped independently from collider. Candidate C: B plus tiny stride-conditioned width/alpha modulation only if B wins and C adds measurable quality. The shadow must not inherit BODY_LOCAL lean/squash/bob; it may follow world translation and camera only.

### DO_NOT_ASSUME
- Do not assume the lack of shadow is automatically a bug; it may be an intentional art direction.
- Do not re-enable `engine-w` under the modern sprite merely to recover its ellipse; that would duplicate body/nameplate rendering.
- Do not derive shadow size directly from collider radius if avatar scale changes; collider and visual footprint are separate contracts.
- Do not let contact shadow participate in collision, depth authority, networking, or gameplay.
- Do not add per-frame allocations, blur filters, large compositing surfaces, or expensive Canvas shadowBlur on mobile without measurement.
- Re-check current `main` before implementation because avatar composition is actively changing.

### RISKS
- A shadow that is too wide/dark can look like a decal or blob and reduce premium quality.
- If drawn in the wrong middleware layer it can be transformed by BODY_LOCAL lean/bob, defeating grounding.
- If generic prop occlusion redraws the avatar, the shadow could be drawn twice unless composition ownership is explicit.
- If every NPC receives a large translucent ellipse, overdraw can become noticeable on low-end mobile; measure before scaling to crowds.
- Future jumping/mounting systems may require shadow separation from body height; this proposal should remain ground-root based rather than hardcoded to current hero geometry.
