### PROBLEM
Current local locomotion advances a continuous distance-driven `stridePhase`, then maps it to the four lateral sprite columns with `floor(stridePhase*4)%4`. That makes every source pose occupy exactly 25% of the gait cycle distance. The code has no per-pose cadence/dwell weights and no semantic contact markers. Even after WALK/RUN cycle-distance discontinuity, reversal and stop are solved, this equal-quarter mapping can still make a planted/contact pose disappear too quickly or a passing/extreme pose linger too long if the four authored drawings are not naturally spaced at equal gait phase.

This round does NOT claim that unequal timing is automatically better. The current atlas must first be classified. The new finding is narrower: Kelo's runtime currently cannot express non-uniform pose cadence at all.

### CONFIRMED_IN_GEMINI
At current `main` baseline `12021a0fe98550c7c9c82cd3bf64beb6a39d01ac`, visible title `Kelo World — V6.17`:

1. `engine-ac.js` advances local stride from actual world distance, not render count: `stridePhase = (stridePhase + lastStepDistancePx/cyclePx)%1`.
2. `engine-ac.js` then selects `frame = floor(stridePhase*4)%4`.
3. Therefore frame boundaries are fixed at normalized phase 0.00, 0.25, 0.50 and 0.75; each frame owns exactly one quarter of world-cycle distance.
4. WALK currently uses `WALK_CYCLE_WORLD_PX=50`, so each displayed column owns 12.5 world px of nominal cycle travel.
5. RUN currently uses `RUN_CYCLE_WORLD_PX=90`, so each column owns 22.5 world px.
6. With the current speed curve, illustrative code-derived dwell times are: WALK mag=.30 (~33 px/s) ≈379 ms per column; WALK mag=.699 (~97.03 px/s) ≈129 ms per column; RUN mag=.70 (~97.32 px/s) ≈231 ms per column; RUN mag=1 (~185.28 px/s) ≈121 ms per column. These are analytical consequences, not live display measurements.
7. `engine-ab.js` consumes that integer frame directly. RIGHT and LEFT use the same row 2, with LEFT mirrored; there is no secondary timing table in the renderer.
8. Current code has no metadata such as `contact`, `passing`, `down`, `up`, `leftPlant`, `rightPlant`, or per-frame relative duration.
9. This is distinct from CG-20260903-008: that entry concerns the WALK→RUN 50→90 cycle-distance jump. Even with a continuous cycle-distance blend, equal 25% pose partitioning would remain.
10. This is distinct from CG-20260903-012/013: those concern stop settlement and reversal/contact identity. This entry concerns steady-state pose cadence within a cycle.
11. Collider remains radius 20 and no physics/camera change is required to test cadence mapping.
12. `ENGINE_MAP.md` is now materially improved and correctly identifies `engine-ac.js` as gait/stride owner and `engine-ab.js + hero.PNG` as visible hero renderer; current code remains the final authority.

### EXTERNAL_EVIDENCE
1. Godot's current `SpriteFrames` API explicitly supports a relative duration per individual frame; a frame duration of 2 is displayed twice as long as duration 1. This establishes that mature 2D sprite runtimes treat per-frame timing as an independent animation parameter rather than requiring equal dwell. Source: https://docs.godotengine.org/en/latest/classes/class_spriteframes.html
2. Phaser's current animation documentation likewise supports per-frame `duration` values in addition to a global frame rate. Source: https://docs.phaser.io/phaser/concepts/animations
3. Unreal Engine's current Sync Marker documentation explains that locomotion blending often needs semantic markers such as foot contacts when stride lengths or step counts differ. Kelo does not need Unreal's animation stack, but the relevant principle is that normalized phase alone is not always the correct semantic clock. Source: https://dev.epicgames.com/documentation/unreal-engine/animation-sync-groups-in-unreal-engine
4. Godot issue #86058 is a concrete bug report about a per-frame duration being ignored on the first loop, showing that individual frame dwell is meaningful enough to have correctness tests in a production 2D engine. Source: https://github.com/godotengine/godot/issues/86058
5. Pixel-art community feedback repeatedly focuses on contact/passing timing and foot arcs, not only raw frame count. Example: https://www.reddit.com/r/PixelArt/comments/1cr808n/
6. Counterevidence: simple four-frame walks are commonly authored for equal timing and can look excellent. A r/gamedev discussion specifically notes four key poses can be enough; more or uneven timing is not automatically superior. Source: https://www.reddit.com/r/gamedev/comments/o7iefe/
7. Counterevidence: if hero.PNG's four lateral cells were authored at equal phase intervals, adding non-uniform dwell could worsen the cycle. Therefore atlas semantics and same-trace video must decide.

### HYPOTHESIS
A premium planted feel may require separating continuous stride phase from pose sampling. Keep distance-driven phase, but map phase to authored pose intervals rather than hard-coded equal quarters. If the current atlas contains recognizable contact/passing semantics, a small cadence map could hold contact poses slightly longer and transit through passing/extreme poses differently while preserving exactly the same world trace and cycle distance. If the current four frames are already equal-phase or too ambiguous, retain uniform mapping and defer cadence work to a richer WALK/RUN atlas.
