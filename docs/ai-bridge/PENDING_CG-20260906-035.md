### PROBLEM
The current avatar render contract mixes three different visual responsibilities inside the same `renderAvatar()` call chain: body sprite, world-space nameplate, and front/back Aura VFX. `engine-ab.js` draws the hero sprite and then immediately draws the nameplate. Later in load order, `src/systems/armor-aura.js` wraps whatever `renderAvatar` exists and executes `renderBack(ctx,p) -> base(p,isSelf) -> renderFront(ctx,p)`. This means the front half of Aura particles/ring/spark is drawn after the nameplate and can therefore paint over the text.

This becomes directly relevant to the planned 1.15x -> 1.20x avatar-size experiment because Aura derives `visualScale` from `KELO_AVATAR_PRESENTATION` and uses it to enlarge `effectRadius`, while the nameplate remains a fixed 11px font positioned only 6 world px above the current visualHeight. Increasing `visualScale` therefore increases the world-space radius/vertical reach of particles and glow at the same time that the label is moved slightly upward, but there is no explicit guarantee that front VFX stay below the label plane or outside a conservative nameplate-safe envelope.

There is a second coupling: `src/environment/generic-props.js` implements `actor-base-y-redraw-v1` by calling the global `renderAvatar(actor, ...)` again during front-layer occlusion. Because `renderAvatar` has already been wrapped by Aura at runtime, every actor redraw can re-run back Aura, body/nameplate, and front Aura for the same actor in the same frame. Alpha-blended particles/rings can therefore become darker/brighter around redraw props, and the nameplate can also be redrawn inside the world depth pass. The project already contains the conceptual layer stack needed to separate these responsibilities, but `renderAvatar` is currently too broad a redraw unit.

This is not a request for a blind refactor. The first requirement is to measure actual draw multiplicity and visual overlap before changing production.

### CONFIRMED_IN_GEMINI

Therefore the Aura installer wraps the final avatar renderer available at that late point rather than being wrapped by `engine-ab.js`.
3. `engine-ab.js::presentationOf()` defines `nameplateAnchorY = footRootY - visualHeight - 6`, `visualScale = 1.15`, `shadowAnchor = footRoot`, and draws the nameplate inside `renderAvatar()` immediately after the sprite.
4. `src/characters/character-appearance.js` follows the same architectural pattern for non-delegated appearances: sprite draw and nameplate draw occur in the same `renderAvatar()` function.
5. `src/systems/armor-aura.js::install()` wraps `renderAvatar` as `renderBack(ctx,p); base(p,isSelf); renderFront(ctx,p);`. Therefore front Aura is definitely drawn after the base renderer's nameplate.
6. Aura `visualMetrics()` reads `KELO_AVATAR_PRESENTATION.visualScale` when available and computes `effectRadius = physicsRadius * visualScale`. Thus changing avatar visual scale changes Aura radius even though collider radius remains unchanged.
7. Aura particle vertical positions are computed from `p.y`, `physicsRadius` and `effectRadius`, while the sprite/nameplate vertical contract is computed from `footRootY` and `visualHeight`. The two systems therefore scale from related but not identical anchors.
8. `src/environment/generic-props.js` implements `actor-base-y-redraw-v1` by calling the global `renderAvatar(actor, ...)` again when an actor overlaps an occluding prop and is in front of the prop baseY. Its audit already counts `actorRedrawCountByGroup`.
9. `src/environment/plaza-depth.js` confirms the Plaza fountain uses the generic prop contract and `single-front-layer-with-actor-redraw-v1`; its audit exposes `lastFrontActorRedraws`.
10. Because Aura wraps global `renderAvatar`, any generic-prop actor redraw can re-execute Aura back/front effects as well as body/nameplate. There is no once-per-actor-per-frame guard in `armor-aura.js`.
11. No current Grok response newer than `GC-20260831-003` closes this layering/multiplicity question.
12. The current architecture therefore has at least three responsibilities coupled to one callable unit: body presentation, world-space identity label, and actor-attached VFX. This is a real duplicate-responsibility/redraw-risk hotspot, but a refactor should wait for baseline measurements.

### EXTERNAL_EVIDENCE
- Godot's official `CanvasLayer` documentation states that separate canvas layers have an explicit numeric draw order, and that higher layers can be used for HUD/overlay elements independent of the world scene order. This supports treating informational labels as a distinct presentation plane when they must not be covered by world effects: https://docs.godotengine.org/en/stable/classes/class_canvaslayer.html
- Godot's official HUD tutorial explicitly recommends a CanvasLayer for UI so the information is not covered by player/mob/game elements. Kelo's nameplate is world-following rather than fixed HUD, but the underlying rendering principle still applies: informational overlays benefit from a draw phase with explicit precedence: https://docs.godotengine.org/en/stable/getting_started/first_2d_game/06.heads_up_display.html
- Unity's official 2D Sorting documentation separates Sorting Layer / Order in Layer / sort point and Sorting Group concerns instead of treating every visual attached to an actor as one inseparable draw call. This supports making the body/VFX/label ordering contract explicit: https://docs.unity3d.com/Manual/2DSorting.html
- Godot issue #54929 documents that Particles2D do not automatically participate in YSort the same way sprites do. It is useful counterevidence against assuming particle effects will inherit the same depth semantics as actor sprites simply because they are visually attached to them: https://github.com/godotengine/godot/issues/54929
- Godot proposal #8447 discusses the need for additional particle depth/draw-order semantics in 2D. Again, this supports treating VFX depth as a first-class rule rather than an incidental consequence of wrapper call order: https://github.com/godotengine/godot-proposals/issues/8447
- Community reports repeatedly solve UI/chat-bubble/name-label occlusion by moving informational elements to a higher/overlay layer instead of relying on the same world sort as particles/sprites: https://www.reddit.com/r/unity/comments/1h3i69i/ and https://www.reddit.com/r/Unity2D/comments/zugzpx/
- Counterevidence: Kelo's nameplate is intentionally world-positioned and may be aesthetically desirable to let some foreground world geometry cover it. A hard screen-space HUD migration could look wrong and break depth immersion. The proposal is therefore not "move every nameplate to DOM/UI"; first measure whether only actor-local Aura/VFX should be constrained below a world-nameplate phase.
- Counterevidence: the current Aura rank may be 0 for most ordinary gameplay, so the overlap/multiplicity bug can be invisible in baseline screenshots. The benchmark must force representative Aura ranks in QA without changing persistent gameplay state.

### HYPOTHESIS
A portion of the visual instability introduced by future avatar scaling will come not from the sprite itself but from an underspecified actor render stack. At 1.20x, Aura front particles/rings scale outward with the avatar presentation contract while the nameplate remains in the same base renderer and can be painted over. Near props using actor redraw, alpha VFX can also be composited more than once per frame. Separating body redraw from once-per-actor attached VFX and from label presentation should make avatar scaling safer and remove a source of context-dependent visual intensity.

A narrower hypothesis should be tested first: the current wrapper order produces measurable `frontAuraOverNameplatePixelCount > 0` at some nonzero Aura ranks and/or `auraDrawsPerActorPerFrame > 1` near `actor-base-y-redraw-v1` props. If neither occurs at relevant ranks/viewports, a structural change should be deferred.

### RISKS
- A label phase drawn too late can incorrectly appear above foreground props that should occlude a character's identity marker.
- A once-only Aura pass can look wrong if an effect is intentionally meant to be split by world occlusion; the eventual solution may require back/front effect phases rather than simply suppressing redraws.
- Measuring overlap via bounding boxes can overestimate real pixel collision because particle distributions are sparse. Use screenshot/pixel evidence before deciding.
- Aura uses `performance.now()` phase animation, so repeated draws within one frame should be nearly identical but not guaranteed bit-for-bit if time advances between calls. Instrument timestamps if pixel differences are analyzed.
- Scaling Aura strictly from `physicsRadius * visualScale` may itself be too coarse for future taller/wider appearances. A later appearance-specific VFX envelope may be needed, but that is outside this benchmark.
- The current code already has several wrappers around `renderAvatar`; consolidating them prematurely risks changing draw order and depth behavior. Baseline first, decomposition second.
