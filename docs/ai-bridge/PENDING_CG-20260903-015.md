RESPONDS_TO: user priority on premium lateral movement, 60/90/120 Hz consistency, larger avatars, depth/occlusion and avoiding duplicated responsibilities

### PROBLEM

The local player now has update-side distance-driven locomotion state in `engine-ac.js`, but actors without `_visualMotion` still fall back to `legacyMovingOf()` inside `engine-ab.js::renderAvatar()`. That fallback mutates `_lx`, `_ly`, `_walkHold`, `_mdx` and `_mdy` while drawing. `renderAvatar()` is not guaranteed to run once per actor per RAF: Plaza and Gardens depth wrappers deliberately redraw actors one or two extra times to composite front/back layers, and later systems wrap the final renderer again.

Therefore a non-local actor's animation-on/off tail can depend on how many times it is drawn, where it stands relative to a landmark, and monitor refresh rate. This is a presentation-state ownership problem, not a request to refactor the whole renderer.

### CONFIRMED_IN_GEMINI

At base commit `e1fcc4135a79c643fcf898a4a0f7a810213a7650`:

1. `ENGINE_MAP.md` was refreshed for V6.16 and now correctly identifies `engine-ac.js` as gait/stride owner for local movement and `engine-ab.js + assets/hero.PNG` as the visible hero renderer.
2. `engine-ac.js` creates `_visualMotion` only for the local player through the `updateMovement(dt)` wrapper. Its stride state advances from actual world distance and is update-side.
3. `engine-ab.js::motionOf(p)` uses `_visualMotion` when present. Otherwise it calls `legacyMovingOf(p)` from inside `renderAvatar()`.
4. `legacyMovingOf()` mutates actor state during rendering: `_lx`, `_ly`, `_walkHold`, `_mdx`, `_mdy`.
5. `_walkHold` is set to `10` when movement/velocity/target-distance is detected and decremented by exactly `1` on each subsequent render call that does not re-arm it. It is not dt-based.
6. Fallback animation column uses `Date.now()/130`, which is time-based; the problematic part identified here is primarily the mutable movement hold/direction sampling inside render, not the clock expression itself.
7. `engine-net.js` creates remote peers without `_visualMotion`; it interpolates their x/y in `updateSimulation(dt)` and then draws them through `renderAvatar()`. Therefore online peers use the render-time legacy fallback today.
8. The two built-in `simulatedPlayers` also have no `_visualMotion` in their initial state, so they use the same fallback unless another runtime path assigns one.
9. `src/environment/plaza-depth.js` calls `base()` first, then for nearby local/simulated/PvP actors calls `renderAvatar()` once in the back→actor→front composite and a second time if the actor is in front of the front layer. A nearby non-local actor can therefore be drawn up to two additional times in the same RAF beyond its normal base-world draw.
10. `src/environment/gardens-landmark.js` uses the same basic pattern: `base()`, one actor redraw for overlap, then another redraw for actors classified in front.
11. `src/systems/armor-aura.js` wraps `renderAvatar()` and calls its base once per invocation. It does not itself solve update ownership; every depth-triggered avatar invocation still passes through the mutable fallback.
12. No production movement, renderer, collider, camera or networking code was changed in this research pass.

Derived timing consequence if `_walkHold=10` is allowed to count down without being re-armed:
- 1 render call/actor/RAF: about 167 ms at 60 Hz, 111 ms at 90 Hz, 83 ms at 120 Hz.
- 2 calls/actor/RAF: about 83 ms at 60 Hz, 56 ms at 90 Hz, 42 ms at 120 Hz.
- 3 calls/actor/RAF: about 67 ms at 60 Hz, 44 ms at 90 Hz, 33 ms at 120 Hz (ceil(10/3) RAFs).

These values are mathematical consequences of the per-render counter, not LIVE measurements. Re-arming via target distance can lengthen some cases; the experiment must capture the real state trace.

### EXTERNAL_EVIDENCE

1. Phaser's Scene lifecycle explicitly orders UPDATE/POST_UPDATE before PRE_RENDER/RENDER. This is strong precedent for advancing gameplay/animation state in update and treating render as the later presentation stage.
2. PixiJS v8 documents the same frame structure: ticker callbacks/user logic execute first, then scene transforms/culling, then rendering. Its examples place animation mutation in ticker/update callbacks rather than inside draw traversal.
3. PixiJS also registers app rendering at a low ticker priority, after normal/high-priority update work. This is useful precedent for Kelo's desired ownership split without requiring Kelo to adopt Pixi.
4. A recent GitHub issue in anime.js (#1178) describes the exact class of clock bug relevant here: when multiple canvases each call the same animation engine update, animations can be ticked multiple times per frame. Kelo's mechanism differs, but the failure mode is analogous: visual traversal count must not accidentally become animation tick count.
5. /r/gameenginedevs discussion on separate Update/Render notes the debugging and timing advantage of keeping `Render()` from changing object state, while also providing counterevidence that small engines can combine update/render if the call contract is strictly once-per-step.
6. Counterevidence: mutating presentation state during render is not intrinsically broken when rendering is guaranteed exactly once per actor per frame and the render cadence itself is the intended clock. Kelo no longer has that guarantee because depth compositing intentionally re-invokes `renderAvatar()`.

### HYPOTHESIS

Making non-local locomotion presentation state advance exactly once per simulation/update step, while keeping `renderAvatar()` observational/pure with respect to actor locomotion state, will remove depth-location and refresh-rate dependence from the fallback walk/idle tail. This should also make future larger avatars and more complex occlusion passes safer because adding another redraw will no longer alter locomotion state.

### PROPOSED_CHANGE

Do not refactor all animation systems immediately. First instrument the current behavior.

Candidate A — BASELINE_RENDER_MUTATION
- Current `legacyMovingOf()` inside `renderAvatar()`.

Candidate B — UPDATE_SIDE_LEGACY_VISUAL_STATE
- Extract the legacy movement detection/hold into a narrow updater that receives actor + dt/position delta and runs once per update for actors without authored `_visualMotion`.
- `renderAvatar()` reads the resulting presentation snapshot only; it must not decrement counters or overwrite last-sampled positions.
- Convert the 10-render hold to an explicit time budget only after baseline timing is measured. If preserving the old 60 Hz feel is desired, 10 frames corresponds to about 166.7 ms, but that value is a benchmark reference, not a pre-approved constant.
- Remote peers should be sampled after `engine-net.js` interpolation for that update.
- Simulated/PvP actors should be sampled after their simulation positions update.

Candidate C — FULL_SHARED_DISTANCE_STRIDE
- Future option only if B proves insufficient: reuse the distance-driven stride contract from `engine-ac.js` for all actors, with network gait as metadata but visible stride phase derived from actual interpolated screen/world travel.
- Do not jump to C in this round; it changes more semantics and may need network-specific treatment.

Architecture target:
`simulation/interpolation update -> actor presentation snapshot -> zero-or-many renderAvatar draws`

not:
`simulation -> renderAvatar draw #1 mutates locomotion -> draw #2 mutates it again -> draw #3 mutates it again`.

### DO_NOT_ASSUME

- Do not assume every non-local actor currently shows a visible bug; measure it.
- Do not change local player's already distance-driven `_visualMotion` in the same experiment.
- Do not change collider radius 20, movement speed, camera, zoom, network send cadence or depth rules.
- Do not remove Plaza/Gardens redraws merely to hide this issue; those redraws exist for occlusion correctness.
- Do not convert every presentation timer in the repo in one refactor.
- Do not assume 166.7 ms is the ideal walk-tail duration; it is only the approximate current 60 Hz/one-draw legacy reference.
- Do not tie the fix to avatar scaling. The fix should be scale-neutral.

### RISKS

1. Moving sampling out of render changes the moment `_lx/_ly` are initialized; first-frame behavior must be measured rather than assumed.
2. Network peers interpolate in `engine-net.js`'s `updateSimulation` wrapper loaded after `engine-ac.js`; ownership/order must ensure visual sampling happens after interpolation, not before.
3. Simulated actors and remote peers have different sources of intent (`targetX/Y` vs server `_gait`). One helper may need narrow adapters instead of a single over-generalized abstraction.
4. A time-based hold can preserve refresh-rate consistency but still feel visually wrong; timing should be tuned only after same-trace comparison.
5. A shared all-actor stride system could accidentally animate blocked or network-stalled actors. That is why Candidate C is deferred until B is measured.
6. Extra instrumentation itself can perturb frame time; keep audit logging aggregated/in-memory during benchmarks.
7. `renderAvatar()` is wrapped by aura and called from multiple environment compositors. Any attempted purity check must inspect the final runtime chain, not only `engine-ab.js` in isolation.
