### PROBLEM
The local player now has a good distance-driven stride contract in `engine-ac.js`, but the shared appearance renderer still falls back to a wall-clock animation (`performance.now()/130`) for actors that do not carry `_visualMotion`. That means social bots, future moving PvP masters and current network peers can animate at the same frame cadence while travelling at different visible speeds. This is the classic foot-sliding failure mode and would become more obvious as characters are enlarged. The future online ability architecture adds a second risk: a server-authoritative swap/teleport can create a large positional discontinuity; if client presentation treats that displacement as ordinary locomotion, it can advance stride wildly or interpolate/glide through a teleport.

### CONFIRMED_IN_GEMINI
- Current live `main` was rechecked at `55de7f13dea482abc9ba4ba12251ce77bdc83caa`; the latest commit is a LIVE world-audit alignment, not a locomotion rewrite.
- `ENGINE_MAP.md` remains stale relative to current code (it still documents V6.16 / 2026-09-03), so current `index.html` and loaded code are treated as authority. `index.html` is V6.24 and loads `engine-ab.js`, then `character-appearance.js?v=2`, then `engine-ac.js`, and later `engine-net.js`.
- Local-player stride in `engine-ac.js` advances from actual world distance: `stridePhase += lastStepDistancePx / cycleWorldPx`, with walk cycle 50px and run cycle blended toward 90px. This is independent of render-frame count and should be preserved.
- `character-appearance.js::frameColumn()` uses `_visualMotion.frame` when available, but otherwise chooses the frame with `Math.floor((performance.now()+phase*23)/130) % columns`. The fallback animation therefore has a fixed ~520ms four-frame cycle regardless of actor speed.
- Legacy social bots in `engine-a.js` move at ~80 world px/s. At the current 4 x 130ms fallback cycle, they travel ~41.6 world px per animation cycle. Any actor moving at a different speed still receives the same 520ms visual cycle, so distance-per-cycle changes with speed.
- Current network peers in `engine-net.js` do not receive `_visualMotion`; `upsert()` stores server `face/gait`, then the update wrapper interpolates `p.x/p.y` toward `targetX/targetY` with `min(1,12*dt)`. Their visible transform is smoothed client-side, but their generic sprite frame remains wall-clock-driven.
- `engine-net.js` sends the local pose roughly every 0.1s (`sendAcc > 0.1`) and remote peers are interpolated between those pose targets. A distance-driven presentation phase can therefore use the actual interpolated displacement the viewer sees without changing server authority.
- `master-bot-pipelines.js` already separates social and PvP master pipelines and marks the PvP master server-ready. The current training master is stationary, so it does not expose this cadence bug today; future moving PvP AI will unless visual motion is generalized.
- Current `character-appearance.js` also owns the non-player motion fallback and frame timing. Together with `engine-ac.js`, this means gait timing responsibility is duplicated: one path is distance-matched, the other wall-clock-matched.
- `player_hero_v1` still delegates to the legacy renderer, so this round does NOT change the player renderer or the crop-local pivot work from CG-20260905-023.

### EXTERNAL_EVIDENCE
- Epic Games documents foot sliding as a planting problem and uses measured foot speed to determine when feet should remain planted. Although Kelo is 2D and does not need IK, the underlying rule is directly relevant: visible foot contact should follow motion evidence, not an unrelated wall clock. https://dev.epicgames.com/documentation/en-us/unreal-engine/fix-foot-sliding-with-ik-retargeter-in-unreal-engine
- Unity Netcode documents client-side transform interpolation as a smoothing layer between authoritative state updates. This supports deriving presentation from the interpolated visual trajectory while keeping authority on the server. https://docs-multiplayer.unity3d.com/netcode/2.0.0/learn/clientside_interpolation/
- Gaffer On Games describes snapshot streams around 10Hz plus interpolation and the latency tradeoff. Kelo currently sends poses at roughly this cadence, so animation should not assume packet cadence equals animation cadence. https://www.gafferongames.com/post/snapshot_compression/
- Aseprite slice pivots are authored in local coordinates and exportable to JSON. This still supports the separate CG-023 foot-anchor contract; distance matching and pivot anchoring solve different parts of grounding. https://www.aseprite.org/api/slice
- Community counterevidence is consistent: developers often fix sliding by matching animation rate to movement speed or root motion, but more frames alone do not solve a speed mismatch. Example: https://www.reddit.com/r/gamedev/comments/wofi7p/
- Community pixel-art feedback similarly notes that a planted foot should visually stay in place while the body advances; this supports measuring distance per contact/cycle instead of increasing bob or frame count first. Example: https://www.reddit.com/r/PixelArt/comments/1hgne5y/

### HYPOTHESIS
H1 — A generic actor visual-motion adapter that advances stride from actual rendered/interpolated world distance will reduce foot sliding for social bots and network peers without changing physics, server authority or local-player gait.

H2 — The client should derive animation phase from the trajectory it actually presents (post-interpolation position), while authoritative network state supplies pose intent/face/gait and explicit discontinuity semantics. Replicating an animation frame every network tick is unnecessary and would couple visual cadence to packet cadence.

H3 — Teleports, swaps, respawns and hard corrections require an explicit motion discontinuity (`motionEpoch`, `teleport/snap` result, or equivalent). On discontinuity, presentation must reset its previous-position accumulator/stride state instead of counting the jump as locomotion. For actual teleport semantics, network transform interpolation must snap/rebase rather than visually lerp through the world.

H4 — This motion contract should be solved before increasing generic characters to larger presentation scales. Larger sprites make foot sliding and orientation/cadence mismatch more visible, but visual scale itself should remain a separate A/B after grounding.

### PROPOSED_CHANGE
Do not alter production movement in this research pass. First add measurement and a feature-flagged candidate for non-local actors only.

1. Introduce a small presentation-only visual-motion state per actor, conceptually `{lastX,lastY,stridePhase,strideDistancePx,cycleWorldPx,frame,face,gait,motionEpoch}`. Keep the existing local-player `_visualMotion` from `engine-ac.js` as the authoritative local presentation path.
2. For bots/peers without local-player `_visualMotion`, accumulate actual displayed displacement each update and advance phase by `distance / cycleWorldPx`. Do not use `performance.now()` for gait frame when measurable displacement exists.
3. Resolve walk/run cycle distance from a shared movement/appearance contract. Start by benchmarking the existing local values (walk 50px, run toward 90px); do not assume those exact distances fit the crimson art.
4. Keep face/gait intent supplied by the actor/network when available, but derive frame phase locally from displayed distance. A remote peer should not need frame replication at 10Hz.
5. Add explicit discontinuity handling to the future network/ability contract. Swap/teleport/respawn/server correction must be able to increment a `motionEpoch` or mark `snap=true`; the visual-motion adapter resets `lastX/lastY` and phase history on that event. Network transform code should not lerp ordinary locomotion and teleport with the same policy.
6. Keep `player_hero_v1.delegateToLegacyHero=true`, visual scale 1.15, crop/pivots, camera, collider, zoom and aura unchanged during this experiment.
7. Do not merge this with the CG-023 shared foot-pivot renderer migration. First prove cadence parity; then combine only after both isolated candidates pass.

### DO_NOT_ASSUME

- Do not infer animation phase from server packet count or a fixed 130ms frame clock for moving actors.
- Do not send animation frame numbers every pose packet unless a later benchmark proves a real need.
- Do not count teleport/swap displacement as stride distance.
- Do not visually interpolate an authoritative teleport as if it were normal locomotion.

Phase C — network/discontinuity harness:

- Compare current wall-clock gait vs distance-matched gait.
- Candidate teleport event must reset presentation motion immediately and must not add the teleport distance to stride. If testing network snap/rebase, do that as a separate candidate from cadence matching.

### DECIDING_METRICS
- `worldTraceDeltaPx = 0` and `collisionOutcomeDiffCount = 0` between baseline and presentation-only cadence candidate.
- `distancePerVisualCyclePx`: stable for a given appearance/gait across 60/90/120Hz and across 40/80/110/178/200 px/s; target variance <= 5% once an appearance-specific cycle distance is chosen.
- `footSlipDuringPlantCssPx` / contact-anchor screen drift during planted portions: lower than wall-clock baseline.
- `frameRateRefreshVariance`: logical cycle distance and frame sequence must not depend on refresh rate.
- `remoteJitterFrameBacktrackCount`: 0 or lower than baseline under synthetic packet jitter.
- `teleportStrideInjectedPx = 0` after discontinuity reset.
- `teleportWalkFramesAfterSnap = 0` for an authoritative instantaneous teleport candidate.
- `networkPayloadDeltaBytes = 0` for the distance-derived frame candidate (no frame replication required).
- `frameTimeP95 <= +5%` versus baseline; visual-motion update should be allocation-free in steady state.
- browser console/network failures: 0.

### RISKS
- Deriving phase from interpolated distance means a heavily smoothed remote actor animates to the movement the viewer actually sees, which is desirable visually but may lag authoritative velocity; document this as presentation behavior, not simulation truth.
- Packet corrections can create small backward deltas. Without correction/discontinuity semantics they may cause phase jitter or face flips; audit them explicitly.
- If the appearance's authored stride length is unknown, a distance-driven system can still slide, just consistently. It needs an appearance-specific calibrated cycle distance or contact metadata.
- A teleport threshold inferred only from distance can misclassify very fast legitimate movement. Prefer explicit authority/event semantics for swaps/teleports when online abilities are wired.
- Generic motion-state ownership could become another wrapper. Keep it presentation-only and define one owner before broad migration.
