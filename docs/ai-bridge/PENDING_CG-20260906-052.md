### PROBLEM
The live camera update mixes CSS viewport dimensions (`screenW/screenH`) with world-space camera coordinates without compensating for `CONFIG.zoom`. The renderer later scales the world by `CONFIG.zoom`. As a result, the effective camera dead zone in screen pixels and the camera's edge clamp both change with zoom. Since current `engine-z.js` selects materially different zooms on mobile and desktop, the same lateral movement trace can produce different camera composition and follow feel even when physics and gait are identical.

This matters directly to the user's current priority: a premium lateral walk/run can still feel floaty or delayed if the character is allowed to drift across a much larger fraction of the desktop screen before camera target correction than on mobile. It also complicates judging 1.15x vs 1.20x avatar scale because screen composition is not currently normalized across viewport/zoom profiles.

### CONFIRMED_IN_GEMINI
Current `main` at base commit `49121332ee286faf3f992f403d114ea00c4ad8fa` still declares `Kelo World — V6.33` in `index.html`. Load order keeps `engine-a.js` as core camera owner, `engine-c.js` as the world transform owner, `engine-h.js` as HiDPI/pixel-perfect support, and `engine-z.js` as the late zoom override.

`engine-a.js::updateCamera(dt)` currently computes:
- `deadW = screenW * CONFIG.deadXRatio`
- `deadH = screenH * CONFIG.deadYRatio`
- camera target deltas in world coordinates (`localPlayer.x/y`, `camera.targetX/Y`, `lookOffsetX/Y`)
- world-edge clamp with `halfW = screenW / 2`, `halfH = screenH / 2`
- final camera clamp to `[halfW, worldWidth-halfW]` and `[halfH, worldHeight-halfH]`.

Those `screenW/screenH` values are CSS viewport dimensions, while `camera.x/y`, player position and world extents are world units.

`engine-c.js` renders the world using:
`translate(screen center) -> scale(CONFIG.zoom) -> translate(-camera)`.
It also implements `screenToWorld()` correctly as `(screen - screenCenter) / zoom + camera`, which confirms that one world unit maps to `CONFIG.zoom` CSS pixels during world rendering.

`engine-z.js`, loaded after `engine-h.js`, sets final zoom from viewport width:
- mobile `<500px`: `screenW / (11*32)`, clamp 1.05–1.45;
- desktop: `screenW / (14*32)`, clamp 1.05–1.45.
For the existing audit profiles this yields approximately:
- 390px mobile: `zoom = 390/352 = 1.1079545`;
- 1280px desktop: clamped `zoom = 1.45`.

With the core defaults `deadXRatio=0.10`, `deadYRatio=0.08`, the current horizontal dead zone becomes, on screen:
- 390px mobile: 39 world px * 1.10795 = ~43.2 CSS px = ~11.08% of screen width;
- 1280px desktop: 128 world px * 1.45 = 185.6 CSS px = 14.5% of screen width.
Thus a nominal 10% horizontal dead-zone ratio becomes ~31% larger as a fraction of screen width on the desktop profile than on the mobile profile.

The vertical nominal 8% ratio similarly renders as ~8.86% of screen height on mobile vs 11.6% on desktop.

The edge clamp is also geometrically inconsistent with zoom. The visible half-width in world units should be `screenW/(2*zoom)` if the goal is to prevent showing outside the world. Current code uses `screenW/2`.
Examples:
- 1280 desktop @1.45: current halfW=640 world px; visible half-world width is ~441.38; camera is over-clamped by ~198.62 world px at each horizontal edge.
- 390 mobile @1.10795: current halfW=195; visible half-world width is ~176.0; over-clamp is ~19 world px per horizontal edge.
- 720px desktop height @1.45: current halfH=360 vs visible ~248.28, ~111.72 world px excess vertical clamp.
- 844px mobile height @1.10795: current halfH=422 vs visible ~380.88, ~41.12 world px excess vertical clamp.

`engine-z.js` also caps `CONFIG.lookAheadDist` to 36 world px. This becomes ~39.9 CSS px on the 390 mobile profile but 52.2 CSS px on desktop. Unlike the dead-zone/clamp mismatch, this may be intentional because look-ahead can reasonably be authored in world units; it should be measured, not automatically converted.

`ENGINE_MAP.md` already marks zoom ownership as `NEEDS_AUDIT`, while camera ownership remains in `engine-a.js`. This is therefore another concrete cross-owner contract problem rather than a reason for a broad refactor.

### EXTERNAL_EVIDENCE
Official Godot 4.6 `Camera2D` documentation describes drag margins as relative to the screen: values from 0 to 1 represent where in the screen frame camera dragging begins. It separately defines camera zoom as changing how much world area the viewport covers. This supports keeping screen-composition margins invariant under zoom rather than allowing a nominal screen ratio to scale again with camera zoom.
Source: https://docs.godotengine.org/en/4.6/classes/class_camera2d.html

Official Unity Cinemachine documentation describes the Dead Zone and Soft Zone as regions of the camera frame/screen, with Screen X/Y expressed as normalized screen positions. This is the same conceptual separation: composition zones are screen-space controls, while world target motion is separate.
Source: https://docs.unity3d.com/Packages/com.unity.cinemachine@2.6/manual/CinemachineUsing.html

Godot proposal issue #14137 demonstrates the zoom geometry explicitly when deriving visible camera extents: viewport size must be divided by camera zoom to obtain the world-space area actually visible. That directly matches Kelo World's render transform and shows why `screenW/2` is not the correct world half-extent when zoom != 1.
Source: https://github.com/godotengine/godot-proposals/issues/14137

Godot docs issue #7774 collects multiple Camera2D jitter cases and notes that smoothing/dead-zone behavior interacts with tiny camera movement. This is relevant counterevidence against making a blind mathematical change without replaying the same trace: a geometrically correct dead zone can still expose or suppress camera jitter depending on damping and sampling.
Source: https://github.com/godotengine/godot-docs/issues/7774

Community evidence is mixed rather than authoritative: developers commonly report that camera composition can feel wrong after zoom/resolution changes unless screen-space framing is recalculated; conversely, overly aggressive dead-zone normalization can make cameras feel too active. Treat community reports as motivation for A/B measurement, not proof of the exact Kelo constants.

### HYPOTHESIS
Kelo World's camera should separate world-space follow coordinates from screen-space composition constraints.

For a camera whose renderer maps world delta to CSS pixels via `delta * zoom`:
1. a desired dead-zone fraction of the screen should be converted to world units as `(screen dimension * ratio) / zoom` before comparison with world-space player/camera positions;
2. the world-edge clamp should use visible half-extents `screenW/(2*zoom)` and `screenH/(2*zoom)`;
3. look-ahead should remain world-space initially unless measurements show that its perceived screen offset must be normalized too.

This should make lateral camera onset and edge behavior more consistent between mobile and desktop without changing player physics, gait, stride phase, collider, footRoot or avatar visual scale.

4. Record every update/render: player world X, camera X/targetX, lookOffsetX, zoom, player screen X, dead-zone current/candidate bounds, camera velocity.

8. Repeat the camera trace at 60/90/120-equivalent update/render cadences where practical; damping should remain exponential/dt-based and results should converge rather than depend materially on sample rate.

### RISKS
- Reducing the effective world-space dead zone at high zoom means the desktop camera may begin following sooner than today; mathematically consistent does not automatically mean aesthetically better.
- Correcting edge clamps exposes more of the world near boundaries. If environment art/streaming intentionally relied on the old oversized clamp to hide unfinished edges, Candidate B may reveal content gaps; that would be important evidence, not a reason to silently retain incorrect geometry.
- Existing world/chunk culling may also make assumptions about camera extents. Edge correction should therefore inspect world renderer culling before production implementation if baseline shows new regions becoming visible.
- Damping plus a smaller world-space dead zone can surface subpixel camera motion/jitter. Measure raster stability together with CG-045 rather than treating geometry alone as sufficient.
- A 1.20x avatar may need composition tuning after camera normalization, but sprite size must not be used to redefine physics or visible world extents.
