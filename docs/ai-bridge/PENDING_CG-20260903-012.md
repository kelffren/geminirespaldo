### PROBLEM
Current voluntary stop behavior does not settle a lateral stride onto a known planted-foot/neutral pose. When input becomes idle, `engine-ac.js` keeps `_visualMotion.on` true for `VISUAL_STOP_HOLD_SEC = 0.075`; during that interval no stride distance is added, so the exact currently displayed locomotion frame freezes. As soon as the 75 ms hold expires, the code unconditionally sets `stridePhase = 0`, `strideDistancePx = 0`, and `frame = 0`.

Therefore a RIGHT/LEFT WALK or RUN can stop at any stride phase, visibly hold that arbitrary pose briefly, then snap to atlas column 0. If the release occurs on column 1/2/3, the stop transition can contain a one-frame pose discontinuity unrelated to world motion or a known foot-contact marker. If release occurs on column 0, no column pop occurs. The severity depends on the actual silhouettes/contact semantics of the current atlas and must be measured visually before changing production.

This is not the same as CG-20260903-004. That entry concerns sustained input while physically BLOCKED by collision. This entry concerns deliberate input release in free space.

### CONFIRMED_IN_GEMINI
At current `main` HEAD `b3e5878f125a588c28ef2e17127e125e60da89a4` / `index.html` title `Kelo World — V6.16`:

1. `engine-ac.js` defines `VISUAL_STOP_HOLD_SEC = 0.075` and initializes `stopElapsed` to that value.
2. `gaitFrom(mag)` returns `idle` below `GAIT_IDLE_MAX = 0.03`.
3. `updateVisualMotion()` computes world-space `dist` from the actor's current position versus `lastX/lastY` and defines `hasIntent = gait !== 'idle'`.
4. On normal free-space release under `DIRECT` movement, processed input becomes zero, base `engine-a.js::updateMovement()` sets `vx/vy` to zero immediately, and the next visual update typically has `dist≈0`, `spd≈0`, `hasIntent=false`.
5. In that case `stopElapsed += dt` and `v.on = v.stopElapsed < 0.075`. While `v.on` remains true, no new `lastStepDistancePx` is added because distance is below the 0.12 threshold; `stridePhase` and `frame` therefore remain frozen at the last moving values.
6. Once `v.on` becomes false, `engine-ac.js` unconditionally executes `v.stridePhase = 0; v.strideDistancePx = 0; v.frame = 0`.
7. `engine-ab.js` directly uses `m.frame % 4` as the source column for actors with `_visualMotion`. Therefore this reset reaches the production PNG directly.
8. `engine-ab.js` uses the same lateral atlas row for RIGHT and mirrored LEFT, so the same stop-phase rule applies to both lateral directions.
9. The current code does not expose authored per-frame foot-contact metadata, `lastPlantedFoot`, stop-animation selection, or a contact-aware neutral frame.
10. Because the hold is time-based rather than render-count-based, its duration is broadly refresh-rate independent, but the actual transition is quantized to update cadence. Nominally 75 ms corresponds to about 4.5 frames at 60 Hz, 6.75 at 90 Hz, and 9 frames at 120 Hz; the threshold is crossed on the first update where accumulated stop time is no longer `< 0.075`, so observed frame count can differ by one because of discrete stepping/floating-point timing.
11. The resulting visual discontinuity is phase-dependent: release while `frame=0` produces no column jump; release while `frame=1/2/3` eventually jumps to column 0 even though world position is already stationary.
12. `engine-ah.js` still wraps `updateMovement()` after `engine-ac.js` in script load order and hard-zeros velocity when there is no movement input. Under current `DIRECT` movement this is mostly redundant for voluntary release, but it confirms stop semantics are split across multiple movement wrappers. Do not refactor them as part of this narrow visual experiment.
13. `ENGINE_MAP.md` remains stale (V5.15/v66 and hero owner `engine-m.js`) while current runtime title is V6.16 and production PNG override is in `engine-ab.js`; source code remains authority for this round.

### EXTERNAL_EVIDENCE
1. Epic's Unreal Engine Animation Sync Groups documentation says walk/run cycles should synchronize foot placement, and marker-based syncing is specifically useful when stride lengths differ and when blending non-looping starts/stops. This supports tracking left/right foot-contact phase rather than snapping every stop to an arbitrary universal frame. Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/animation-sync-groups-in-unreal-engine
2. Epic's Distance Matching documentation describes driving animation pose/playback by movement distance and includes stopping as a use case for reducing foot sliding. The API documentation for `DistanceMatchToTarget` explicitly describes selecting animation time from remaining distance to stop, while noting that this approach does not automatically preserve the previous jog phase. That caveat is important counterevidence: distance matching alone does not solve phase continuity. Sources: https://dev.epicgames.com/documentation/en-us/unreal-engine/distance-matching-in-unreal-engine and https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/AnimationLocomotionLibraryRuntim-/UAnimDistanceMatchingLibrary/DistanceMatchToT-
3. Unity Animator transitions expose normalized `exitTime`, allowing a transition to occur at a chosen phase in a loop rather than at an arbitrary instant. Kelo World should not copy Unity's state machine, but the precedent supports making locomotion→idle phase-aware when visual continuity matters. Source: https://docs.unity3d.com/6000.0/ScriptReference/Animations.AnimatorStateTransition-exitTime.html
4. Godot issue #52518 documents user-visible one/few-frame animation transition delays/freezes even with zero xfade, showing that short transition timing defects can be visually salient and should be inspected frame-by-frame rather than dismissed because they last only a few frames. Source: https://github.com/godotengine/godot/issues/52518
5. Godot issue #93136 documents state/blend changes not restarting at the expected animation phase, reinforcing that phase/reset semantics during transitions can create visible wrong-frame behavior. Source: https://github.com/godotengine/godot/issues/93136
6. Community reports on run→idle foot sliding describe exactly the perceptual symptom of a foot moving into the idle placement after locomotion stops; another Unreal community discussion recommends selecting left-foot/right-foot stop animations from contact markers when available. These are implementation anecdotes, not authoritative requirements, but they support testing contact-aware stops. Sources: https://www.reddit.com/r/Unity3D/comments/1jbo0kz and https://www.reddit.com/r/UnrealEngine5/comments/1l0slks
7. Counterevidence: responsiveness matters. Waiting for an entire gait cycle or forcing the character to continue world motion until a foot-contact phase would make controls feel laggy and is not proposed. The physics/world stop should remain immediate; only presentation settling is under test.

### HYPOTHESIS
The current 75 ms arbitrary-frame freeze followed by unconditional column-0 reset is a low-cost implementation of stop hysteresis, but it is not a true planted stop. A premium lateral presentation should stop physics immediately while settling the visual pose toward a known contact/neutral state using phase information, without advancing world position, delaying input responsiveness, or replaying a long stop animation.

The likely architecture is to add explicit presentation semantics such as `contactClass` / `lastPlantedFoot` / `stopPose`, derived from the authored atlas or future walk/run atlas. On release, visual locomotion can enter a short `settling` state that either (A) immediately chooses the nearest valid planted/contact pose, or (B) uses a tiny bounded transition only if measured to look better. The correct contact columns must be discovered from the actual atlas first; do not assume columns 0/2 are foot contacts.

### PROPOSED_CHANGE
P0 — Instrument before production change.
- Extend movement audit/test harness with release-time `stridePhase`, `frame`, `gait`, `stopElapsed`, world position, foot/contact classification (once authored/diagnosed), and the exact first idle frame shown.
- Add a deterministic way to trigger release near requested stride phases 0.00/0.25/0.50/0.75.

P1 — Audit lateral frame semantics.
- Create/inspect a 4-frame contact sheet for the production lateral row(s).
- Classify each frame as candidate `left_contact`, `passing`, `right_contact`, `passing/other`, or `unknown` using visible sole/foot position.
- Do not infer contact solely from column index.

P2 — A/B/C presentation-only stop policies with identical world trace.
A BASELINE: current 75 ms arbitrary-frame hold -> frame 0 reset.
B NEAREST_CONTACT_SNAP: on voluntary stop, freeze world immediately and choose the nearest authored contact/neutral frame from current phase in the first presentation update. This tests whether removing the 75 ms arbitrary hold is already better.
C SHORT_CONTACT_SETTLE: world stops immediately; presentation keeps current facing and moves to the nearest valid contact/neutral pose within a small bounded window (candidate <= 80 ms), with no stride/world advancement. Exact interpolation/frame policy depends on atlas semantics and should not be invented before P1.

P3 — Preserve phase across WALK↔RUN separately.
- Do not reset stride phase merely because gait changes; CG-20260903-008 already handles cadence discontinuity. This entry should only change voluntary movement→idle settlement after that cadence contract is understood.

P4 — Future authored atlas contract.
- If a richer WALK/RUN atlas is produced, include explicit marker metadata per direction/gait for `left_plant`, `right_plant`, neutral/idle, and optional start/stop poses.
- Use the same semantic markers for LEFT/RIGHT mirrored art only if mirror symmetry is deliberately accepted; if true LEFT artwork is later activated, validate matching contact timing.

P5 — Only after measurement, consolidate stop ownership if useful.
- `engine-ac.js` and `engine-ah.js` both participate in stop behavior via nested `updateMovement` wrappers. Do not refactor first. Once the visual stop policy is validated with identical traces, consider one explicit movement/presentation owner to reduce duplicated responsibilities.

### DO_NOT_ASSUME
- Do not assume frame 0 is a planted or neutral pose.
- Do not assume frames 0 and 2 are left/right contacts until the atlas is visually inspected.
- Do not move physics/world position after release merely to finish an animation.
- Do not add input latency or wait for an entire gait cycle before stopping.
- Do not change collider, camera, joystick thresholds, WALK/RUN cycle distance, subpixel snap, avatar scale, or depth logic in the first A/B.
- Do not combine this with BLOCKED stop behavior; sustained collision input is a separate state and may need a different settle policy.
- Do not add a procedural bob/lean/squash while evaluating stop-pose continuity; it would confound the frame transition.
- Do not call a contact-aware stop better until same-trace video/pixel/foot-root metrics support it.

### RISKS
- With only four current lateral frames, no column may be a convincing idle/contact pose. In that case the correct answer may be `DEFERRED until atlas`, not procedural complexity.
- Snapping immediately to a contact frame can itself pop more than the current 75 ms hold. That is why B and C both need same-trace visual comparison.
- A short settle that advances animation phase without world motion can look like treadmill motion. Candidate C must move only toward a bounded settle pose and must not continue cycling.
- Mirrored LEFT may invert which visual foot appears planted. Contact metadata must define semantic foot side carefully or use screen-side contact labels where appropriate.
- At 60 Hz, a 75–80 ms window is only a handful of displayed frames, so temporal quantization can dominate. Compare actual frame sequences, not just timestamps.
- Future larger avatars make any silhouette pop more visible, but changing scale in the first test would confound the diagnosis.
