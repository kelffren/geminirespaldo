### PROBLEM
The lateral visual-stride owner advances `stridePhase` from resolved world distance, which is the correct high-level contract, but it first applies `MIN_VISUAL_MOVE_PX = 0.12` to each individual render/update displacement. At the end of every update it still moves `v.lastX/v.lastY` to the current player position. Therefore any real displacement smaller than 0.12 world px in one frame is permanently discarded rather than accumulated. At low analog joystick magnitudes the player can move through the world while `lastStepDistancePx` remains zero and the lateral sprite stays on one frame. Because requestAnimationFrame frequency follows the display refresh rate, the world speed required to exceed 0.12 px in one callback is higher at 90/120Hz than at 60Hz. This makes micro-walk animation behavior device/refresh-rate dependent even though physics itself is dt-based.

### CONFIRMED_IN_GEMINI
1. Current main baseline for this entry is d5b5145c57a5ceb994ab211db45584fe8a36d8e6; index.html declares Kelo World V6.53.
2. engine-ac.js defines `MIN_VISUAL_MOVE_PX = 0.12`. In `updateVisualMotion`, it computes `dist = hypot(p.x-v.lastX,p.y-v.lastY)`, then publishes `v.lastStepDistancePx = dist > MIN_VISUAL_MOVE_PX ? dist : 0`.
3. `stridePhase` advances only when `v.on && v.lastStepDistancePx > 0`; otherwise a moving sample below the threshold contributes zero distance to stride.
4. At the end of every call, `v.lastX = p.x; v.lastY = p.y` regardless of whether `dist` passed the threshold. Thus sub-0.12 displacement is not retained for a later cumulative sample.
5. `hasIntent = gait !== 'idle'`, and gait becomes non-idle above processed magnitude 0.03. Therefore visual state can be `on=true` while `lastStepDistancePx=0` and the frame does not progress.
6. For touch, engine-ac sets CONFIG.joystickRadius=72 and CONFIG.joystickDeadzone=0.045; engine-a maps raw radial distance linearly after the dead zone. The raw distance needed merely to leave gait idle is about 5.30 px from joystick origin: 3.24 px dead radius + 0.03*(72-3.24).
7. In the low-magnitude range (`mag <= 0.48`), speed cap is 110 px/s and DIRECT physics gives approximately `actualSpeed = mag*110`. A per-frame 0.12 px threshold corresponds to ~7.2 px/s at 60Hz, 10.8 px/s at 90Hz and 14.4 px/s at 120Hz. Converted to processed magnitude these are ~0.0655, ~0.0982 and ~0.1309.
8. With the current 72px joystick geometry, those processed magnitudes correspond to raw thumb displacements of ~7.74 px (10.75% of radius) at 60Hz, ~9.99 px (13.88%) at 90Hz and ~12.24 px (17.00%) at 120Hz. Between the ~5.30px gait-on threshold and those refresh-specific values, Kelo can move physically while the stride frame can remain frozen indefinitely under perfectly steady input.
9. Even above those exact thresholds, variable frame pacing can make some callbacks contribute distance and other callbacks discard it, creating quantized cadence at slow speed rather than a smooth distance-driven phase.
10. `physicallyMoving` using `spd > 16` does not repair this: it affects whether the visual is on and which direction vector is used, but stride distance is still set to zero whenever the current render displacement is <=0.12.
11. `scripts/live-hero-audit.mjs` currently drives keyboard cardinal/diagonal traces. Keyboard normalizes to magnitude 1, so the live audit never exercises the analog micro-walk band where this defect exists, and it does not compare 60/90/120Hz low-speed cadence.
12. This is distinct from CG-082 startup-phase latency: CG-082 concerns how long the authored plant frame lasts after starting; CG-086 concerns actual resolved distance being discarded every callback, which can freeze steady-state micro-walk and changes with refresh rate.

### EXTERNAL_EVIDENCE
- MDN documents that requestAnimationFrame callback frequency generally matches display refresh rate and explicitly notes common 60Hz plus 75/120/144Hz displays. It warns that animation progress must use elapsed time rather than frame count to avoid high-refresh differences. Kelo's world movement uses dt, but the 0.12 world-px gate is currently applied per callback, so its effective velocity threshold is still refresh dependent.
- Godot's current Idle and Physics Processing documentation states that per-frame processing frequency varies across devices and time, and delta should be used for frame-rate-independent calculations. The relevant principle here is not that Kelo needs a Godot-style fixed physics loop; it is that a spatial epsilon intended to reject noise should not silently become a velocity threshold via per-frame reset.
- Unity's Time.deltaTime documentation makes the same distinction between per-second and per-frame quantities: movement values need time normalization for frame-rate independence.
- Counterevidence from Godot issues and community reports: blindly eliminating all spatial quantization/pixel constraints can expose subpixel jitter and camera/sprite shimmer. Therefore the proposed first candidate preserves a small spatial epsilon as an accumulated sampling threshold instead of simply setting MIN_VISUAL_MOVE_PX to zero.

### HYPOTHESIS
Keep distance-driven gait, but make the 0.12 px threshold spatial/cumulative rather than per-render. Maintain a stride sampling anchor that is updated only after cumulative resolved displacement from that anchor reaches the epsilon. This should preserve the noise filter while ensuring real slow movement eventually advances stride identically at 60/90/120Hz. The physics trace, input mapping, cycleWorldPx, facing rules, collider and camera should remain unchanged.

### PROPOSED_CHANGE
QA A baseline: current per-render `dist > 0.12` gate with `lastX/lastY` reset every callback.
QA B preferred: add a dedicated stride sampling anchor, e.g. `strideSampleX/strideSampleY`, initialized to the player position. Compute `cumulativeStrideDisplacement = hypot(p.x-strideSampleX,p.y-strideSampleY)`. Only when this reaches MIN_VISUAL_MOVE_PX publish that cumulative displacement to stride and move the sampling anchor to the current player position. Keep the existing immediate per-frame dx/dy path for facing/direction if needed. Reset the stride sampling anchor on stable idle/release/teleport so stale subthreshold distance cannot leak into a new movement episode.
QA C diagnostic only: remove the 0.12 stride gate and advance stride from every positive resolved `dist`. Compare against B to determine whether the epsilon is actually protecting against collision/subpixel noise. Do not default to C.
QA D: if cumulative Euclidean displacement around a tight sub-epsilon reversal produces measurable phase error, accumulate a signed/projected displacement along current locomotion intent instead; only pursue after B measurement.

### RISKS
- A cumulative Euclidean anchor can count a small curved path differently than sum-of-frame path length. At a 0.12px threshold that error should be tiny, but measure reversals rather than assume.
- If collision resolution produces a slow monotonic positional creep while blocked, B would eventually animate despite the wall; the blocked-collider trace is mandatory.
- Making micro-walk frames finally advance may reveal that four authored lateral frames are insufficient at ultra-low cadence; that would be an art/cadence limitation, not a reason to discard real world distance again.
- Any frame-rate test must distinguish actual display/rAF cadence from Playwright timer scheduling; log real callback dt.
