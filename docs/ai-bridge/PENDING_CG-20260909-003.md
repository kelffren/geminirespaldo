### PROBLEM
Kelo World intentionally wants a larger visual avatar while preserving the physical collider. That separation is architecturally correct, but the LIVE Generic Props occlusion system still decides whether a prop/actor overlap exists from `actor.x/y` plus `actor.radius`, and its clip rectangle is also sized from `actor.radius`. As visual size grows, visible parts of the sprite can overlap a prop while the collider-sized gate says there is no overlap, or the actor redraw/clip can cover only a small physical-radius region instead of the enlarged visual silhouette. This is especially relevant to the planned 1.20x avatar scale.

### CONFIRMED_IN_GEMINI
At current `main` base commit 4599b335c4f3cb46cb7abd7b40647d10be7a3dc2:

1. `engine-ab.js` defines `KELO_AVATAR_PRESENTATION` with separate semantic visual bounds (`visualLeft/Top/Right/Bottom`) and collider radius. At current 1.15 scale the side visual contract is about 55 world px wide and 93 world px tall, anchored at `footRootY = actor.y + 10`.
2. `src/characters/character-appearance.js` consumes that presentation contract and renders the LIVE player around `footRoot` with per-frame authored foot anchors. Therefore visual extent is intentionally independent of `actor.radius`.
3. `src/environment/generic-props.js` defines `overlaps(actor,b)` as an AABB derived solely from `actor.radius`: `actor.x +/- r`, `actor.y +/- r`.
4. In `actor-base-y-clip-v1`, after the radius overlap gate passes, the clip region is also radius-derived: `r = max(22,(actor.radius||20)+clipPadding)` and `rect(actor.x-r, actor.y-r*1.8, r*2, r*2.5)`.
5. In `actor-base-y-redraw-v1`, the same radius-based `overlaps(actor,bounds)` decides whether `renderAvatar(...)` is invoked. Thus the redraw gate does not use the larger visual rectangle even though the avatar owner exposes one.
6. `src/environment/prop-contract.js` currently uses these modes for real LIVE content: plaza nature uses `actor-base-y-clip-v1`; the Justice fountain uses `actor-base-y-redraw-v1` with a large visual bounds rectangle.
7. `src/environment/plaza-depth.js` reports the fountain depth mode as `single-front-layer-with-actor-redraw-v1`, confirming the redraw path is part of the active plaza-depth contract.
8. No proposal in this entry changes the collider, physics, collision response or depth root. The issue is presentation-space overlap/clip ownership.

### EXTERNAL_EVIDENCE
Official Unity Sprite Renderer / 2D sorting documentation separates render sorting from physical colliders and allows sprite sorting to use the Sprite pivot in world space. The transferable point is that visual ordering/occlusion should use render-space anchors/bounds rather than assuming collider geometry describes sprite extent.

Official Godot `VisibleOnScreenNotifier2D` represents visibility as a rectangular region and explicitly uses render culling against that region. This supports treating presentation visibility/overlap as its own rectangle rather than deriving it from collision radius.

PixiJS 8 culling documentation similarly describes culling from renderer/global screen bounds, with an explicit custom `cullArea` when default bounds are unsuitable. This reinforces the distinction between visual bounds and unrelated physics bounds.

Community counterexample: developers sometimes deliberately use oversized conservative AABBs to avoid missed rendering/culling when visual bounds are dynamic. That can be viable here too, but only if measured because an excessively large bound increases redraw/overdraw work.

Counterevidence: radius-based overlap may be adequate for props whose important occlusion region is concentrated around the feet, and the current 1.15x avatar may visually hide the miss. Therefore this is not proof of a current visible bug in every scene; it is a confirmed contract mismatch that must be reproduced before changing production.

### HYPOTHESIS
For presentation-only prop occlusion, Kelo will scale more safely if overlap/redraw gates consume the avatar presentation rectangle (or a conservative union derived from it) while depth ordering continues to use `depthRootY`/actor base semantics and physics continues to use the collider. This should prevent enlarged visible pixels from escaping occlusion without changing movement or collisions.

### PROPOSED_CHANGE
Do not refactor blindly. First instrument the current paths.

A — baseline: keep radius-based overlap and radius-based clip exactly as today.

B — visual-overlap gate only: replace only the boolean overlap gate for avatar/prop occlusion with bounds from `KELO_AVATAR_PRESENTATION.get(actor, face)`, converted to `{x,y,w,h}`. Keep the existing clip region and redraw mechanism unchanged. This isolates whether missed redraws are caused by the gate.

C — visual-overlap gate + visual clip: if B proves missed pixels but the clip still truncates the enlarged sprite, derive the clip from a conservative presentation rectangle plus small padding. Do not use exact per-frame alpha bounds in runtime unless measurement proves necessary; prefer a stable per-face or union bound to avoid breathing/flicker.

D — conservative union optimization: if calculating full presentation bounds per actor/prop is too expensive or causes unstable geometry, cache a small union bound per appearance/face/scale and reuse it.

Preserve `actor.y`/`depthRootY` as the depth-order signal unless a separate benchmark proves it wrong. Do not enlarge `actor.radius` to solve a visual issue.

### DO_NOT_ASSUME
- Do not assume the collider should match the visible sprite.
- Do not assume every prop should use the full visual rectangle for occlusion; some footprint-oriented props may intentionally care only about the actor base.
- Do not change physics, collision radius, movement speed, camera, stride or avatar scale in the A/B comparison.
- Do not combine this benchmark with nameplate changes, contact-shadow work or cadence changes.
- Do not use per-frame alpha scanning inside the render loop.
- Do not replace the Generic Props owner or add another occlusion manager.
- Do not treat a larger overlap AABB as free: measure extra redraws and frame cost.

### RISKS
- A larger visual AABB can trigger more `renderAvatar()` redraws around large props, increasing overdraw on mobile.
- `renderAvatar()` middleware may include nameplates/equipment/FX; repeated redraws can duplicate presentation layers if ownership is not redraw-safe. Preserve and measure the previously identified redraw-count risk.
- Using exact per-face/frame bounds may make the occlusion gate change when the direction/frame changes, creating flicker at prop edges. A conservative union can be visually more stable.
- Visual bounds in `engine-ab.js` are semantic, not measured alpha bounds. If CG-099 later proves they under/overestimate the LIVE appearance, fix/calibrate the presentation contract first rather than baking compensating magic numbers into Generic Props.
- Increasing scale to 1.20x magnifies the mismatch and may expose additional nameplate/shadow issues; keep those outside this experiment.
