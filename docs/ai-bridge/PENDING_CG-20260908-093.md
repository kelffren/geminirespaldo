### PROBLEM
Character Creator V2 now renders modular back/front layers through KeloAvatar middleware priority 250. That middleware calls drawSectionWithActorTransform(), which explicitly samples KeloAnimation and applies offset/foot-pivot rotation/scale before drawing each modular section. However visual-integration is a higher-priority KeloAvatar middleware (400), therefore it is outermost and already applies the same KeloAnimation transform to the Canvas context before calling next(). The modular middleware executes inside that already-transformed context and then applies the actor transform again. The base hero rendered deeper in the chain receives only the outer transform. This can make modular clothing/equipment separate from or overreact relative to the body during cast transforms, and would become more visible if locomotion micro-lean/squash/bob is added.

### CONFIRMED_IN_GEMINI
- KeloAvatar sorts middleware priority descending and documents that higher priority is the outer layer.
- visual-integration registers `visual-integration:actor-fx-transform` at priority 400. It saves ctx, applies KeloAnimation offset + foot-pivot rotation + scale, renders back FX, calls `next()`, renders front FX, then restores ctx.
- CharacterCustomization registers `character-customization:modular-layers` at priority 250. Before/after `next()` it calls `drawSectionWithActorTransform()`.
- `drawSectionWithActorTransform()` independently calls `KeloAnimation.sampleTransform(actor)` and applies the same offset + foot-pivot rotation + scale to ctx before drawing modular layers.
- Therefore in the current middleware ordering, modular layers are drawn under outer transform T and then inner transform T again (effective composition approximately T*T), while the base hero is drawn under T once.
- visual-manifests already contains real non-identity action transforms. At cast_magic_01 keyframe t=0.52: scaleX 1.07, scaleY 0.96, rotation 0.045 rad, offsetX 2. Ignoring translation/pivot cross-terms, double application implies roughly 1.1449 X scale, 0.9216 Y scale and 0.09 rad (~5.16 degrees) rotation for modular layers versus 1.07/0.96/~2.58 degrees for the body.
- This is newly relevant because ENGINE_MAP now declares Character Creator V2 LIVE and KeloCharacterCustomization middleware priority 250 as part of the current Foundation runtime.

### EXTERNAL_EVIDENCE
- MDN Canvas transform documentation: transformations multiply the current transformation matrix; nested rotate/scale/translate operations compose rather than replace the parent transform. `save()` stores the current transform and `restore()` returns to that saved state, so saving inside an already-transformed parent does not reset to identity.
- MDN `getTransform()` exposes the currently applied DOMMatrix and is suitable for proving the matrix entering the modular middleware and the matrix immediately before its draw calls.
- Godot/Unity community discussions on parent-child 2D transforms show the normal rule: children inherit parent transforms unless explicitly made top-level/unparented. This supports one transform owner for a composed actor, not repeated application of the same parent transform by each child layer.
- Counterevidence: local per-layer transforms are legitimate when intentionally additive (for example cloth sway or weapon recoil). Therefore removing the second transform blindly would be wrong if it encodes a distinct local animation. Current code does not distinguish a local layer transform; it samples the same actor-level KeloAnimation transform.

### HYPOTHESIS
The modular Character Creator layers currently over-transform relative to the hero during any non-identity KeloAnimation action. This may be invisible with the default legacy body/outfit when no modular source-backed items are active, but becomes visible with real clothing/equipment and will worsen if continuous locomotion lean/squash/bob is introduced. A single owner of BODY_LOCAL actor transform should transform base body + modular layers + BODY_LOCAL actor FX exactly once.

### PROPOSED_CHANGE
Do not refactor blindly. First prove the matrix duplication with instrumentation. If confirmed visually and numerically, candidate B is to remove actor-level KeloAnimation sampling/application from `drawSectionWithActorTransform()` and let priority-400 visual-integration own BODY_LOCAL transform for the entire nested avatar composition. Preserve per-item `visual.rotation`, per-face offsets and per-item scale inside `drawVisualEntry()`; those are legitimate local transforms. If CharacterCustomization must also work when visual-integration is absent, prefer an explicit composition contract/metadata indicating whether BODY_LOCAL transform is already active rather than silently applying it twice. Do not add another renderAvatar wrapper.

### DO_NOT_ASSUME
- Do not assume every current character preset has source-backed modular layers active.
- Do not assume the double matrix is perceptible without a real equipped modular asset.
- Do not remove item-local rotation/offset/scale; the suspected duplication concerns the actor-level KeloAnimation transform only.
- Do not change physics, collider, camera, gait, stride, avatar visual scale or nameplate behavior in this experiment.
- Re-read current main before implementation because Character Creator V2 is actively changing.

### RISKS
- Removing the inner actor transform without understanding middleware context could make modular layers fail in a test/runtime path where priority-400 visual-integration is not installed.
- Some modular equipment may intentionally need independent local motion; that should be represented as a separate local transform, not by duplicating the full actor transform.
- Back/front layering and UP-facing weapon occlusion could regress if composition order is altered rather than only transform ownership.
- A future nameplate-isolation change from CG-092 must not accidentally move modular BODY_LOCAL layers into world/UI space.
