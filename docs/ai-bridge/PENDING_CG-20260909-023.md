### PROBLEM
CG-022's client/server cast-movement mismatch is still present on current main. This pass narrows the architectural cause: `abilityData.action` is canonical shared DATA, but the actual windup→active→recovery phase machine is implemented privately inside `server/pvp-authority.js`. The client ability runtime does not consume `def.action` for timeline progression at all, and `KeloPvPWorld` has no predicted cast phase state. Therefore simply adding a client movementScale check would require duplicating phase/timing semantics or inventing ad-hoc timers.

### CONFIRMED_IN_GEMINI
1. HEAD at research start and immediately before the research write was `f6c5525753692f93a38af8ad72f7baf7a29ce37b`; concurrent Map Forge work was unrelated to PvP movement.
2. `index.html` LIVE runtime is V6.54 and now loads `KeloRuntimeBootstrap` early; Combat/Effects/Status/Melee are lazy first-use. `ENGINE_MAP.md` still describes V6.53/old late bootstrap in places, so runtime wins.
3. `src/systems/pvp-world.js::movementHook()` still computes action scale only from dodge/basic melee, then status multiplier. No ability cast state participates.
4. `castArmed()` still calls `KeloAbilities.engine.predict()` online / `.cast()` offline, clears `armedSlot`, sends the intent, and does not retain windup/active/recovery state.
5. `src/abilities/kelo-ability-boot.js` owns validation, delivery, cooldowns, effects, projectiles, dash/blink, and emits `ABILITY_CAST`, but inspection of the LIVE source found no `def.action` consumption for actor locomotion or phase simulation.
6. `src/abilities/abilityData.js` defines every action as canonical `{windup, active, recovery, movementScale}` and is consumed by both browser and Node/server.
7. `server/pvp-authority.js` privately normalizes `def.action` through `actionOf(def)`, creates `_pvpCast`, applies current cast movementScale before requested-velocity displacement, then advances windup→active→recovery after movement each fixed 1/60 step.
8. Server step ordering matters: on a fixed step, current phase movementScale is applied first; phase time is incremented and boundary transition happens afterward. Any client helper that transitions before applying that frame's movement can be off by one simulation step even with identical durations.
9. Melee already has the pattern we want conceptually: a shared owner (`KeloMeleeEngine`) exposes phase-related semantics consumed by client and server. Ability action timing lacks an equivalent pure/shared primitive.

Counterevidence: action-combat responsiveness does not mean casts should all have movementScale=1. Deliberate commitment remains valid. The defect is duplicated/absent timeline semantics, not the existence of slowdown.

### HYPOTHESIS
H1: The smallest robust fix is not another timer inside `KeloPvPWorld`; it is one PURE shared ability-action timeline primitive that both client prediction and server authority consume.
H2: Because `abilityData.js` is explicitly data-only (`NO ejecutar gameplay`), placing simulation state advancement directly inside that data owner risks violating its contract. A tiny pure browser+Node contract adjacent to Ability Data is safer than adding phase logic to CharacterAppearance/PvPWorld/server independently.
H3: The primitive should normalize action data, resolve current movementScale for a phase, and advance a phase deterministically with explicit ordering matching server fixed-step semantics. It must not own DOM, movement, damage, cooldowns, VFX, network transport, or player state.
H4: `KeloAbilities` should own the predicted local cast instance/lifecycle because Ability runtime already owns cast execution; `KeloPvPWorld` should only consume a published current cast movement scale in its existing movement hook.
H5: Server authority should keep ownership of authoritative cast state, but call the same pure phase helper instead of its private `actionOf` + transition logic.

### PROPOSED_CHANGE
First implement a parity audit before production behavior changes. If confirmed, introduce one minimal shared ability-action contract (name/location chosen by Grok only after Foundation audit), usable from browser and CommonJS/Node, analogous in spirit to shared melee semantics.

Minimum pure API shape to evaluate:
- normalize(def.action) -> canonical finite nonnegative windup/active/recovery + movementScale contract
- movementScaleFor(action, phase) -> scalar [0,1], supporting current scalar and future per-phase object form
- advance(state, dt) -> next phase/time/completed with EXACT server ordering defined and tested

Then:
1. `KeloAbilities` creates/publishes predicted cast lifecycle only after a valid local/predicted cast is accepted.
2. Existing `pvp-world:movement-scale` consumes the predicted cast's published movement scale and combines it with melee/dodge/status using server-equivalent ordering.
3. `server/pvp-authority.js` replaces private phase normalization/transition duplication with the same pure helper while preserving authority.
4. No ability values are retuned in this pass.
5. Mobility delivery (dash/blink/swap) remains owned by existing delivery contracts; ordinary locomotion scale must not double-transform the mobility path.

### DO_NOT_ASSUME
- Do not put timeline simulation into `abilityData.js` unless its data-only contract is deliberately changed and documented.
- Do not create an AbilityMovementManager or second KeloMovement wrapper.
- Do not use `setTimeout`, `armedSlot`, animation state or VFX state as cast authority.
- Do not change windup/active/recovery/movementScale values while fixing parity.
- Do not alter collider, camera, stride, base movement profile, damage or hit resolution.
- Do not transition client phase before movement if server applies movement for the old phase then advances afterward.
- Do not assume current immediate local ability delivery timing is correct; it may be a second mismatch, but keep it separate unless the parity audit proves inseparable.

### RISKS
- A helper that is pure but sampled directly from variable browser dt can still cross boundaries differently than a 60 Hz server. The audit must distinguish presentation sampling from canonical simulation stepping.
- Changing server timeline code and client prediction in one pass can hide a regression if both are wrong the same way; preserve an explicit pre-change server reference trace in the test fixture.
- Immediate local delivery in `KeloAbilities.predict()` currently occurs without consuming action windup; after movement parity this may become visually inconsistent (effect appears immediately while movement remains in windup). Record it, but do not silently broaden scope.
- Lazy runtime boot means tests must call the real first-use bootstrap path where integration behavior depends on Combat/Effects/Melee availability.
