### PROBLEM
The local player now has distance-driven visual locomotion in `engine-ac.js`, but actors without `_visualMotion` still fall back to `engine-ab.js::legacyMovingOf()` + `stepCol()`. That fallback mixes two clocks: movement hold is counted in render calls (`_walkHold = 10`, then decremented per call) while frame selection uses `Math.floor(Date.now()/130)%4`. This means remote/simulated/legacy actors do not share the local player's distance-matched stride contract, and the visible stop duration can vary with refresh rate and with repeated `renderAvatar()` calls from authored depth compositors.

### CONFIRMED_IN_GEMINI
1. `engine-ac.js` updates only `localPlayer` through its `updateMovement` wrapper and publishes `_visualMotion` with distance-derived `stridePhase` / `frame`.
2. `engine-ab.js::motionOf(p)` uses `p._visualMotion` when present; otherwise it calls `legacyMovingOf(p)`.
3. `legacyMovingOf(p)` sets `_walkHold = 10` whenever `dist > 0.12`, `spd > 16`, or `toTarget > 14`; otherwise it decrements `_walkHold` by exactly 1. No `dt` is used.
4. `stepCol()` uses the authoritative `_visualMotion.frame` when available, but the legacy path selects `Math.floor(Date.now()/130)%4`, giving a fixed ~7.69 atlas frame advances/s independent of actor world speed.
5. `engine-net.js` interpolates peers every `updateSimulation(dt)` toward server targets, but does not build `_visualMotion` for them. It sends local pose at >0.1 s intervals and renders peers via `renderAvatar(peers[id], false)`, therefore network peers use the legacy renderer path.
6. `src/environment/plaza-depth.js` and `src/environment/gardens-landmark.js` can call `renderAvatar()` once for the actor pass and again for actors in front of the front layer. Because `legacyMovingOf()` mutates `_lx/_ly/_walkHold` inside rendering, a single RAF can consume multiple hold counts around those landmarks.
7. The local path does not have this specific render-count mutation because its `_visualMotion` is updated in movement, not in `renderAvatar()`.

Derived timing from the confirmed code, not yet LIVE-measured: if a legacy actor receives exactly one `renderAvatar()` call per RAF, a 10-call hold lasts ~166.7 ms at 60 Hz, ~111.1 ms at 90 Hz, and ~83.3 ms at 120 Hz. Two renderer invocations per RAF approximately halve those durations. These numbers are theoretical until same-trace browser measurement is performed.

### EXTERNAL_EVIDENCE
- WHATWG issue #5025 documents that modern devices increasingly run at 90/120/144 Hz and that animation scheduling assumptions tied to display cadence are not portable across devices: https://github.com/whatwg/html/issues/5025
- Svelte issue #10717 is a concrete cross-refresh-rate bug report where an animation produced visibly different behavior on 60 Hz vs 120 Hz because its update behavior was refresh-dependent: https://github.com/sveltejs/svelte/issues/10717
- Community locomotion practice consistently recommends matching animation cadence to actual movement distance/speed to prevent foot sliding rather than playing a fixed cycle regardless of travel speed: https://www.reddit.com/r/gamedev/comments/wofi7p and https://www.reddit.com/r/gamedev/comments/o9esl6
- Contraevidence: a wall-clock animation such as `Date.now()/130` is itself refresh-rate-independent for frame selection and is cheap/deterministic. The problem is not the use of wall time alone; it is that cadence is disconnected from world distance and that stop/hold state is mutated by render count.

### HYPOTHESIS
A unified presentation-motion contract for every rendered actor will make lateral movement more planted and consistent across local, simulated and network characters. The smallest high-value fix is likely not a refactor of networking or physics, but moving legacy motion bookkeeping out of `renderAvatar()` and deriving visual phase from actor displacement/time once per simulation update or once per actor snapshot. Remote peers can initially use displacement-derived stride with the same presentation constants as local motion, while preserving their existing network interpolation and physics semantics.

### PROPOSED_CHANGE
Benchmark before production changes.

Candidate A — BASELINE_LEGACY:
- Keep current `_walkHold` render-count state and `Date.now()/130` frame cycling.

Candidate B — DT_HOLD_ONLY:
- Preserve wall-clock frame cadence temporarily, but replace render-count `_walkHold` with seconds (`stopElapsed`/holdSec) updated outside rendering once per simulation update.
- Goal: isolate refresh/depth-redraw dependence from cadence mismatch.

Candidate C — DISTANCE_PHASE_REMOTE:
- Build a non-authoritative presentation state for actors lacking `_visualMotion`, updated outside `renderAvatar()` from actual interpolated displacement.
- Advance `stridePhase` from distance, not wall clock; derive `frame` from phase.
- Keep network interpolation, server target cadence, collider, world trace and server messages unchanged.
- Use the same local WALK/RUN cycle constants initially only as a benchmark control; do not assume they are correct for peer gait until measured.

Candidate D — UNIFIED_PRESENTATION_HELPER:
- Only if C validates: extract a small pure-ish helper that consumes `(actor, dx, dy, dt, gait)` and returns presentation motion for both local and remote actors.
- Do not refactor ownership blindly; first verify identical local trace and visual phase against current `engine-ac.js`.

Also remove motion-state mutation from `renderAvatar()` only after a validated replacement exists. Rendering should ideally read presentation state, not advance/decrement it.

### DO_NOT_ASSUME
- Do not assume network peers actually exhibit visible skating before LIVE measurement.
- Do not assume local WALK/RUN cycle distances are automatically correct for network peers; peer gait may arrive from the server at coarse cadence.
- Do not assume every `renderAvatar()` call occurs exactly once per RAF; authored depth wrappers explicitly prove otherwise near Plaza/Gardens.
- Do not change `engine-net.js` transport cadence, server protocol, interpolation constant, collider, camera, local movement, or atlas in the first experiment.
- Do not delete `legacyMovingOf()` until simulated actors, PvP rival and remote peers are all mapped to a replacement path.

### RISKS
- Creating per-actor presentation objects for many peers can add allocations/GC if implemented naively; reuse fields/objects and benchmark 1/10/25/50 actors.
- Server gait is coarse and may disagree briefly with interpolated displacement; distance should be the visual phase authority while gait remains a style/cycle selection hint unless measurements show otherwise.
- If phase resets when new network snapshots arrive, the cure can create new foot pops. Presentation phase must persist across target updates.
- If authored depth wrappers continue rerendering bodies multiple times, any shadow/Aura/nameplate work must also remain read-only/idempotent per RAF to avoid alpha accumulation or state mutation.
- Unifying local and remote motion too early could accidentally perturb the already-improved local path. Start by fixing legacy/peer state ownership independently.
