PROBLEM
The live lateral camera mixes screen-space quantities with world-space camera math after a late zoom is applied. `updateCamera()` builds `deadW/deadH` from `screenW/screenH`, compares those values directly against world-coordinate deltas, clamps camera center with `screenW/2` and `screenH/2` as world extents, and uses `lookAheadDist` in world units. Later render transforms the world by `CONFIG.zoom`. Because `engine-z.js` owns the late zoom and allows roughly 1.05-1.45, the apparent dead zone, look-ahead and world-edge framing vary with zoom/device even with the same movement trace. Separately, the core game loop uses one variable-timestep simulation update per requestAnimationFrame with dt capped at 100 ms and no fixed-step accumulator/render interpolation.

CONFIRMED_IN_GEMINI
1. Current main is d0a4234378d0b7848bd134be364719ac6a811a89 and index declares V6.53.
2. `engine-b.js::gameLoop` computes `dt = min((currentTime-lastTime)/1000, 0.1)` and runs processInput -> updateMovement(dt) -> updateCamera(dt) -> updateSimulation(dt) -> render() once per rAF. No fixed-step accumulator or render interpolation is present in that owner.
3. `engine-a.js::updateCamera` uses exponential dt-aware smoothing (`1-exp(-k*dt)`), which is a positive frame-rate-independent property for ideal frame pacing.
4. The same function computes `deadW=screenW*deadXRatio`, `deadH=screenH*deadYRatio` and compares those values directly to world-space deltas. It clamps with `halfW=screenW/2`, `halfH=screenH/2`, also without dividing by zoom.
5. `engine-c.js` renders with `scale(CONFIG.zoom, CONFIG.zoom)` around screen center.
6. `engine-z.js`, loaded later than the earlier zoom owners, sets `CONFIG.zoom = clamp(screenW/(targetTiles*32), 1.05, 1.45)` and caps lookAheadDist to 36 world px.
7. Example consequences from current formulas: at 390 CSS px width, zoom ~= 390/(11*32)=1.108, so a nominal 10%-width horizontal dead zone becomes ~11.08% of screen after scaling. At zoom 1.45 it becomes ~14.5%. A 36-world-px lookahead appears ~39.9 CSS px at zoom 1.108 but ~52.2 CSS px at zoom 1.45.
8. More seriously, camera edge clamp uses screenW/2 world px rather than screenW/(2*zoom). At 390px and zoom~1.108 this is about 19 world px too conservative per horizontal side. At 1280px and zoom 1.45, it is about 199 world px too conservative. This can make the camera stop following much earlier near world boundaries on desktop/high zoom.
9. `src/systems/performance-governor.js` already records frame p50/p95/p99/worst, >33/>50/>100/>=120ms and LoAFs, but targets 60 FPS globally; it does not currently classify camera/player screen-space phase error by refresh rate.

EXTERNAL_EVIDENCE
- MDN documents that requestAnimationFrame normally follows the display refresh rate and explicitly names 60, 75, 120 and 144 Hz; it recommends advancing animation from the callback timestamp rather than frame count. The current Kelo loop does use the timestamp/dt, which is good.
- Unity Cinemachine's current Position Composer describes dead zones as regions of the camera frame/screen composition, with size expressed relative to screen dimensions. That supports treating Kelo's intended dead-zone contract consistently in screen space and converting it to world space through zoom before world-coordinate comparisons.
- Godot Camera2D documentation treats zoom as changing the viewport framing, and current Camera2D APIs separate drag margins, smoothing and limits. Multiple Godot GitHub issues document visible jitter when camera smoothing, pixel snapping, and subpixel movement interact.
- Counterevidence: switching blindly to a fixed timestep is not automatically superior for this codebase. Kelo currently updates movement and camera together in the same rAF using dt-aware smoothing; this avoids the classic mismatch of physics at one cadence and camera at another. A fixed step without render interpolation could make 90/120Hz presentation less smooth.

HYPOTHESIS
The highest-value camera correction is not a fixed-timestep rewrite. First make camera composition zoom-aware while preserving the exact player/world trace: convert desired screen-space dead-zone and visible viewport half-extents into world units (`screenPx/zoom`) before world comparisons/clamps, and decide explicitly whether look-ahead is authored in screen px or world px. This should make lateral framing materially more consistent between common phone widths and desktop while leaving physics untouched. Only after that baseline should variable-step vs fixed-step/interpolation be benchmarked under induced frame irregularity.
