### PROBLEM
The live hero already separates physics bounds from presentation bounds, but generic prop occlusion still decides actor overlap and front/back redraw eligibility from `actor.x`, `actor.y`, and `actor.radius`. This means a visual-only avatar scale increase can enlarge the visible sprite without enlarging the occlusion candidate area. A character can therefore visibly overlap a prop while the prop system still considers the actor non-overlapping, or switch depth based on physics-root `actor.y` instead of the hero's explicit `depthRootY/footRootY`. This is particularly relevant before raising the hero from 1.15x to 1.20x.

### CONFIRMED_IN_GEMINI
- Current `main` inspected for this pass is `a40b78421eb752dcf2b6973d01b3d89623c71ef8`; the newest commits are iPhone fullscreen/orientation UI changes, not hero/prop depth fixes.
- `index.html` remains Kelo World V6.53 and loads `engine-ab.js?v=240`, then later `src/environment/plaza-depth.js?v=219`; Foundation declares `KeloAvatar` as the avatar-render owner and `KELO_GENERIC_PROPS` as the data-driven prop renderer.
- `engine-ab.js` defines `AVATAR_VISUAL_SCALE=1.15` and publishes `KELO_AVATAR_PRESENTATION.get()`. The presentation exposes `visualLeft`, `visualTop`, `visualRight`, `visualBottom`, `footRootX/Y`, `depthRootX/Y`, `shadowAnchorX/Y`, and `nameplateAnchorX/Y`. These visual bounds are deliberately separate from `colliderRadius`.
- `src/environment/generic-props.js::overlaps(actor,b)` ignores that presentation contract. It constructs a square candidate from `actor.x/y` and `actor.radius||20`.
- In `actor-base-y-clip-v1`, the same file checks `actor.y >= p.occlusion.baseY`; in `actor-base-y-redraw-v1` it checks `actor.y <= p.occlusion.baseY`. Thus depth gating uses physics-root Y rather than the explicit hero `depthRootY`/`footRootY`.
- The redraw path can call `renderAvatar()` again after a prop front layer. Therefore any future contact shadow/aura/body-local effects must not be accidentally duplicated or moved into the wrong depth group.
- `src/environment/plaza-depth.js` reports fountain depth from `localPlayer.y > baseY`, again using physics-root Y rather than the avatar presentation depth root.
- Increasing 1.15x to 1.20x enlarges the lateral visual width/height while collider radius remains unchanged by design, making a collider-based occlusion candidate relatively less representative of the visible silhouette.

### EXTERNAL_EVIDENCE
- Godot's official CanvasItem/Y-sort documentation says higher Y positions render in front of lower Y positions; the sort key is a chosen node position, which in character scenes is commonly authored at the ground/feet rather than inferred from visual height. https://docs.godotengine.org/en/stable/classes/class_canvasitem.html
- Unity's official 2D sorting documentation exposes a Sprite Sort Point (Center or Pivot) and custom-axis sorting. The important principle is that render ordering uses an authored render sort point, not collider radius. https://docs.unity3d.com/6000.0/Documentation/Manual/2d-renderer-sorting.html
- Unity's sprite docs also describe Y-axis sorting as a standard top-down 2D technique. https://docs.unity3d.com/2021.1/Documentation/Manual/Sprites.html
- Community evidence shows the opposite failure mode clearly: tall tree/wall sprites can pop in front/behind a feet-pivot character when pivots/bounds are poorly chosen, so merely switching to a different sort coordinate is not automatically sufficient. https://www.reddit.com/r/Unity2D/comments/15oou4a/
- Counterevidence: collider-based overlap can be intentionally cheaper and may be good enough when props have generous occlusion bounds. Therefore this should be measured before replacing every overlap test with full visual AABB logic.

### HYPOTHESIS
Use the existing avatar presentation contract only for presentation/depth candidate selection while keeping physics collision unchanged. For hero actors, prop overlap eligibility should compare the prop's occlusion/visual bounds against the avatar's visual AABB, and base-Y ordering should use `depthRootY` (which is currently the foot root). Legacy actors without `KELO_AVATAR_PRESENTATION` can retain collider fallback. This should make 1.15x/1.20x visual scaling consistent with occlusion without changing movement or collision.

### PROPOSED_CHANGE
Do not refactor production blindly. First add a helper local to the existing prop owner (or a reusable presentation-query helper only if an owner already exists) that returns `{visualBounds, depthRootY}` from `KELO_AVATAR_PRESENTATION.get(actor, face)` when available, otherwise collider-derived fallback. Instrument baseline misses before changing behavior. Candidate B changes only occlusion candidate overlap to presentation bounds. Candidate C, tested separately, changes only the base-Y comparison from `actor.y` to presentation `depthRootY`. Do not combine B and C in the first measurement. Do not enlarge `actor.radius`, change collision, or use sprite top/bottom as the depth key.

### DO_NOT_ASSUME
- Do not assume every prop should use full visual AABB overlap; measure false positives around large/tall sprites.
- Do not assume `depthRootY` should change with avatar scale; it should remain foot/ground anchored.
- Do not enlarge collision radius to solve a render-depth problem.
- Do not move nameplates, shadows, aura or camera in the same experiment.
- Do not add another `renderAvatar` wrapper; `KeloAvatar` owns avatar composition.
- Do not remove the existing redraw strategy until baseline/candidate traces prove a replacement is better.

Only if both independently improve metrics, test B+C. Repeat winning candidate at 1.20x and at mobile/desktop viewports; physics/camera traces must remain identical.

### RISKS
Visual AABBs are larger than colliders and can create extra redraw candidates even when only transparent corners overlap a prop. Repeated `renderAvatar()` calls can duplicate avatar-attached effects if middleware is not idempotent/depth-aware. A single `depthRootY` works well for ground-standing actors but may need different semantics for flying/elevated actors later. Nameplate visibility is not identical to body occlusion and should be measured separately rather than forced to follow every prop mask. Larger 1.20x sprites amplify any existing occlusion mismatch but do not prove that scale itself is wrong.
