### PROBLEM
The current follow-camera deadzone is derived from CSS viewport dimensions (`screenW * deadXRatio`, `screenH * deadYRatio`) but compared directly against world-coordinate deltas. Rendering then applies `CONFIG.zoom`. The camera world-edge clamp similarly uses `screenW/2` and `screenH/2` as world half-extents even though the visible world half-extents under the actual render transform are `screenW/(2*zoom)` and `screenH/(2*zoom)`. Therefore camera feel and edge framing can vary with zoom/device even when player movement is identical.

### CONFIRMED_IN_GEMINI
Current `engine-a.js::updateCamera(dt)` computes `deadW=screenW*CONFIG.deadXRatio` and `deadH=screenH*CONFIG.deadYRatio`, compares those values to `(localPlayer + lookOffset) - camera.target`, then clamps camera.x/y with `halfW=screenW/2`, `halfH=screenH/2`. `engine-c.js::render()` applies `translate(screen center) -> scale(CONFIG.zoom) -> translate(-camera)`. `engine-c.js::screenToWorld()` correctly divides screen displacement by zoom, which makes the camera path inconsistent with its own coordinate conversion. `engine-z.js` is a later zoom owner and sets zoom to `clamp(screenW/(targetTiles*32), 1.05, 1.45)`. `engine-h.js` handles DPR backing-store scale separately; DPR does not fix the CSS/world-unit mismatch. `engine-t.js` only applies an earlier zoom clamp and is superseded later by engine-z for normal startup.

With the current defaults `deadXRatio=0.10`, `deadYRatio=0.08`, the deadzone expressed on screen becomes approximately `ratio * zoom` of the viewport, not the declared ratio. Examples from the production zoom formula: 390px wide -> zoom≈1.108 -> horizontal visible deadzone≈11.1% (43.2 CSS px per side-equivalent threshold); 430px -> zoom≈1.222 -> ≈12.2% (52.5 CSS px); 1440px desktop -> zoom=1.45 -> ≈14.5% (208.8 CSS px). For world-edge clamping at 1440px/1.45, current halfW is 720 world px while visible half-width is ≈496.6 world px, over-constraining the camera center by ≈223.4 world px near each horizontal world edge.

### EXTERNAL_EVIDENCE
Godot Camera2D defines drag margins relative to screen size, i.e. the camera deadzone is a viewport-relative presentation contract rather than raw world distance. Phaser likewise defines camera deadzone as a region relative to the viewport while zoom separately changes the amount of scene visible. These APIs reinforce keeping the chosen deadzone space explicit and internally consistent. Community reports also show that deadzone/follow damping and camera update mismatches can create visible jitter or uncomfortable snapping, so changing camera math should be benchmarked rather than assumed better.

Sources reviewed: Godot Camera2D 4.6 documentation (drag margins relative to screen size); Phaser camera documentation (deadzone relative to viewport, zoom separate); recent Unity2D/IndieDev community reports on deadzone/damping/jitter. No external source proves Kelo World currently exhibits a visible defect; the code-space mismatch is confirmed, the perceptual impact is not.

### HYPOTHESIS
Keeping deadzone intent in screen space while converting the threshold to world units (`deadWorld = screenCss * ratio / zoom`) will make lateral camera onset consistent across phone/desktop zoom levels. Correcting camera edge clamps to visible world half-extents (`screen/(2*zoom)`) should preserve intended framing near world boundaries. This may improve premium lateral motion because the avatar-to-camera relationship stops changing merely because engine-z selected a different zoom.

### PROPOSED_CHANGE
Do not refactor camera ownership yet. Instrument first. Candidate B changes only unit conversion inside the current camera function: use `z=Math.max(epsilon, CONFIG.zoom||1)`, `deadWWorld=(screenW*deadXRatio)/z`, `deadHWorld=(screenH*deadYRatio)/z`, `halfWWorld=screenW/(2*z)`, `halfHWorld=screenH/(2*z)`. Preserve lookAhead, damping equations, target semantics, physics, stride, collider and render transform. Candidate C may instead define an explicitly world-space deadzone if visual testing shows a viewport-relative deadzone is undesirable; do not mix spaces.

### DO_NOT_ASSUME
Do not assume the current camera feels bad just because units are mixed. Do not change `CONFIG.zoom`, `lookAheadDist`, damping, player physics or pixel rounding in the same experiment. Do not combine this with avatar 1.15x/1.25x until baseline camera metrics are captured. Do not delete engine-h/t/z wrappers before tracing final ownership. Do not claim edge framing is fixed until same traces are run near all four world boundaries.

### RISKS
A screen-consistent deadzone can feel too tight on large displays if the old accidental larger deadzone was aesthetically preferred. Correcting world-edge half-extents changes camera positions near boundaries and may reveal environment regions previously less visible. Camera movement with fractional coordinates can expose existing pixel-art shimmer; do not solve that in the same patch. Look-ahead is in world units and may then become proportionally different on-screen across zoom; measure it separately after this experiment rather than changing it simultaneously.
