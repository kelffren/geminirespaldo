### PROBLEM
The live hero renderer still applies heuristic source cropping and an asynchronous near-white knockout pass to `assets/hero.PNG`, but previous rounds could not inspect the PNG bytes through the GitHub connector. Without measurements, removing the pass or changing the crop would be speculative and could damage legitimate authored pixels. This blocks safe LEFT/contact-frame and 1.15x scale work.

### CONFIRMED_IN_GEMINI
- Current main at the start of the round was `db517faff946f025af45bf1ed2d7b36c4f414f1f`; `index.html` declares V6.23.
- `engine-ab.js` is the live visible hero renderer and still assumes a 4x4 sheet, lateral row 2, LEFT mirrored, 5% horizontal / 4% vertical crop, `footRoot=p.y+10`, side display width 48, front/back width 54.
- `engine-ac.js` remains the gait owner and advances stride from actual world distance; this round does not change gait, frame selection, speed, collider, camera or stop logic.
- `GROK_TO_CHATGPT.md` still has no locomotion feedback newer than `GC-20260831-003`.
- The PNG blob SHA exposed by GitHub is `8319a9046f5dd874f44d1f420d227fa97a005490`, but binary bytes are not available through the connector's UTF-8 file path, so source-pixel conclusions cannot be asserted from connector inspection alone.

### EXTERNAL_EVIDENCE
- MDN documents that preload places the referenced resource in cache for later reuse and that static assets can be versioned/hashed for cache management. That supports deterministic asset experiments, but this round deliberately does not change hero URLs yet because preload/runtime parity must be handled together.
- Counterevidence: pixel statistics alone cannot establish animation semantics such as CONTACT or LEFT; they can only expose crop/knockout behavior and provide evidence for a later visual/manual decision.

### HYPOTHESIS
A zero-output-change runtime audit inside the existing one-time preprocessing pass is the safest next increment. Since `engine-ab.js` already calls `getImageData()` once during idle preprocessing, counting affected pixels during that same pass should add negligible steady-state cost while converting unknown crop/knockout behavior into measurable data.

### PROPOSED_CHANGE
Implemented on main in commit `299d0f0e4fd22e46939a5d0eca58f2d018e62336`:
- expose `window.KELO_HERO_SPRITE_AUDIT`;
- record actual sheet/frame dimensions;
- count near-white pixels and opaque pixels affected by `knockWhite()`;
- calculate opaque-loss percentage;
- count opaque pixels excluded by the current crop, total and per frame;
- record whether the idle preprocessing mutates any pixels;
- record preprocessing duration/error state;
- preserve the existing rendered output and all movement/physics behavior.

Decision for production visual behavior: no visual change yet. This is measurement infrastructure only.

### DO_NOT_ASSUME
- Do not interpret `whiteKnockoutAffectedPixelCount > 0` as proof of damage; affected pixels may be intended background.
- Do not interpret crop counts as proof the crop is wrong; the counted pixels require visual/source inspection.
- Do not infer row 1=LEFT or frame 0/2=CONTACT from these counters.
- Do not change collider, movement speed, footRoot, camera, aura, scale or direction mapping in the same evaluation.

### EXPERIMENT
1. Baseline is the pre-change `engine-ab.js` at blob `b07f785fc4e2360fae1c316e383e701a0bef53b5`.

5. Run the same movement trace as before: RIGHT walk -> RIGHT run -> LEFT reversal -> release -> diagonal -> fountain.

7. Use the measured counts to choose exactly one later visual change: crop correction, knockout correction, directional-frame audit, or no change.

### RISKS
- The audit loop is more arithmetic-heavy during the existing one-time `getImageData` pass and can increase one-time preprocessing duration. It does not add per-frame work.
- `sheetMutationAfterIdle` means the preprocessing changed pixels, not that the user saw a visible pop.
- Because `index.html` still references `engine-ab.js?v=240`, an already-cached client may require normal revalidation before receiving the new instrumentation. A later cache-version increment should be paired with the hero asset experiment rather than mixed into this measurement-only commit.
