### PROBLEM

Current `engine-ab.js` treats the production hero sheet as a 4-column x 4-row atlas, but its row-selection logic only ever chooses rows 0, 2 and 3. Both RIGHT and LEFT use row 2; LEFT is generated by horizontally mirroring row 2 around `p.x`. Row 1 is never selected by the production PNG path.

This is a new and directly lateral concern. If row 1 contains intentionally authored left-facing frames, Kelo is currently discarding that art and replacing it with a mirror. That can hide authored foot placement, arm swing, coat/weapon asymmetry, lighting, pivot compensation and direction-specific silhouette work. It can also make reversal tuning harder because the LEFT presentation is not an independently authored gait. If row 1 is blank, duplicate, obsolete or lower quality, then the current mirror path may be correct and should remain. The repository code alone cannot determine which case is true; the atlas itself must be measured/previewed before changing production.

### CONFIRMED_IN_GEMINI

At `BASE_COMMIT` / current V6.10 source:

1. `index.html` loads `engine-ab.js?v=149` as the current production PNG avatar override after older avatar code.
2. `engine-ab.js` divides the loaded sheet into `COLS = 4` and `FH = c.height / 4`, so it explicitly assumes four source rows.
3. Current row selection is:
   - `face === 'up' ? 3`
   - `face === 'down' ? 0`
   - otherwise `2` for both lateral directions.
4. Therefore source row index 1 has zero production reachability through this renderer.
5. LEFT is then synthesized from the same row-2 frame used by RIGHT with:
   - `ctx.translate(p.x, 0)`
   - `ctx.scale(-1, 1)`
   - `ctx.translate(-p.x, 0)`.
6. The same four frame columns are used for both directions, with frame selection coming from local `_visualMotion.frame` or legacy `Date.now()/130` for unmanaged actors.
7. Current lateral destination width is 48 while vertical is 54; this entry does not reopen the already documented aspect-ratio work. It isolates direction-row ownership only.
8. Current local locomotion state in `engine-ac.js` already distinguishes `face = 'right'` and `face = 'left'`, so the runtime has enough semantic information to select separate source rows if the atlas proves that row 1 is a valid authored LEFT animation.
9. `assets/hero.PNG` is present in current main as a ~2.13 MB blob. Binary inspection was not available through the text connector during this research pass, so this entry does NOT claim what row 1 visually contains.
10. `ENGINE_MAP.md` remains stale and still lists `engine-m.js` as hero owner; current `engine-ab.js` is the authoritative source for this production path.
11. No gameplay, collider, camera, movement speed, stride phase or production art was modified in this research round.

### EXTERNAL_EVIDENCE

1. Godot's official 2D tutorial explicitly uses a single right-facing walk animation and `flip_h` for LEFT. This is strong counterevidence against treating mirroring itself as a bug: if a character is designed symmetrically, one authored side plus horizontal flip is a normal and efficient production strategy. Source: https://docs.godotengine.org/en/4.6/getting_started/first_2d_game/03.coding_the_player.html
2. Godot `AnimatedSprite2D` exposes `flip_h` as a first-class property, further confirming that mirrored directional reuse is a legitimate standard technique. Source: https://docs.godotengine.org/en/latest/classes/class_animatedsprite2d.html
3. Unity `SpriteRenderer.flipX` likewise flips only the rendered sprite without requiring collider changes, supporting the architectural rule that a visual LEFT mirror must never alter Kelo's physics/collider. Source: https://docs.unity3d.com/kr/2022.3/ScriptReference/SpriteRenderer-flipX.html
4. Community counterevidence is nuanced: developers commonly accept mirroring even when a weapon/shield swaps hands because it halves art cost and can keep the important weapon readable. A 2025 Godot discussion specifically contrasts mirroring with authoring a second side to preserve dominant-hand consistency. Source: https://www.reddit.com/r/godot/comments/1m7fljr
5. Community reports also show that flip/origin handling can create visible lateral position shifts when the pivot/origin is not centered/consistent. This does not prove Kelo has that bug, but it supports measuring foot/pivot deltas rather than assuming a mirror is presentation-neutral. Source: https://www.reddit.com/r/godot/comments/l59uky
6. GitHub issue evidence from Godot documents a case where horizontally flipped sprite frames exposed stray pixels from adjacent atlas content even with filtering disabled. Different engine, old issue, not proof for Kelo; it is still relevant to validating padding/bleed for any mirrored or alternate-row atlas path. Source: https://github.com/godotengine/godot/issues/20622
7. Counterevidence: separate LEFT/RIGHT rows double directional art maintenance and can introduce worse inconsistencies if their pivots, frame timing or contacts do not match. Therefore the existence of an unused row is not sufficient reason to activate it.

### HYPOTHESIS

The 4x4 hero atlas may already contain a dedicated LEFT row that was intended to be used directly, while current `engine-ab.js` accidentally bypasses it. If row 1 is a valid authored LEFT sequence with compatible frame cadence and foot pivot, using row 1 for LEFT could improve lateral silhouette, arm/coat/weapon consistency and reversal quality without changing physics.

Alternative hypothesis: row 1 is blank, redundant, generated incorrectly or visually inferior. In that case the current row-2 mirror should remain, and the atlas contract should explicitly document row 1 as unused so future art generation does not waste a quarter of the sheet.

A third possibility is that row 1 contains a LEFT sequence but its pivot/contact metadata does not match row 2. Then direct activation could worsen foot planting; the correct outcome would be to repair/re-author the atlas before switching the renderer.

### PROPOSED_CHANGE

Do not change production row selection yet.

**P1 — Inspect/measure all 16 source cells**
- In a diagnostic harness, render each row/column independently on a neutral background after the same preprocessing used by `engine-ab.js`.
- Record raw sheet dimensions, per-cell alpha bounds, opaque pixel count, bottommost opaque Y, horizontal centroid, edge-touch count and simple perceptual/hash similarity.
- Specifically compare row 1 against row 2 and horizontally mirrored row 2.

**P2 — Determine row semantics from evidence, not filename assumptions**
- If row 1 is effectively blank/duplicate, document it and keep mirror LEFT.
- If row 1 is a distinct, coherent side animation, classify whether it visually faces LEFT and whether frame order/contact cadence matches row 2.
- Do not infer semantic direction solely from source-row index.

**P3 — A/B only if row 1 is viable**
A. Baseline: LEFT = mirrored row 2.
B. Candidate: LEFT = row 1 with no horizontal mirror.
- RIGHT remains row 2 in both variants.
- Keep localPlayer radius 20, `footY`, draw dimensions, stridePhase, camera, speed and gait thresholds identical.

**P4 — Reversal/contact test**
- RIGHT steady -> hard LEFT -> LEFT steady -> hard RIGHT.
- Compare foot-root continuity, body centroid jump, frame/contact correspondence, arm/weapon handedness, silhouette pop and screen-space X shift.
- Test same stride phase on both sides so art differences are not confused with timing differences.

**P5 — Scale-safety preview**
- Only after 1.00x baseline, preview the same A/B at the already proposed visual scale candidates (e.g. aspect-correct current baseline and one larger ~1.25x candidate), collider unchanged.
- Larger rendering should make asymmetric coat/weapon/pivot problems easier to see, but scale must not be shipped from this experiment.

### DO_NOT_ASSUME

- Do not assume row 1 means LEFT just because the atlas has four rows.
- Do not switch to row 1 without visual/cell evidence.
- Do not regenerate the hero atlas in this experiment.
- Do not change stride cadence, gait threshold, reversal timing, camera, bob, lean, shadow, nameplate, aura, collider or source crop at the same time.
- Do not call horizontal mirroring low quality by default; official engines use it routinely for symmetric side animations.
- Do not increase collider/radius to match any visual change.
- Do not use a single screenshot only; inspect all four lateral frames and hard reversal.
- Do not let row selection mutate locomotion state during render.

### RISKS

- Row 1 may be old/unused content and enabling it could instantly regress quality.
- Separate rows may have different foot bottoms or body centroids, causing a visible reversal jump even if each direction looks good in isolation.
- Mirrored row 2 may intentionally keep weapon/coat readability consistent; a true LEFT row could hide important features.
- Current chroma-key preprocessing can alter white/near-white pixels; comparisons must use the exact production-preprocessed sheet as well as, when possible, raw asset inspection.
- Existing `Math.round`/zoom/subpixel behavior can contaminate screen-jump measurements; camera-frozen equal-phase tests are required.
- Multi-pass environment renderers can redraw the actor; tag pass/CTM or perform the first comparison in a clean zone.
