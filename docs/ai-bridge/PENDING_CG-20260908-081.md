### PROBLEM
MOV-CADENCE-V2 correctly removed the old hard 50->90 world-pixel stride-length jump exactly at WALK->RUN, but the current continuous formula can create a different perceptual inversion inside the run range. Physical speed rises continuously with processed magnitude, while `cycleWorldPxFor()` increases the distance represented by one four-frame cycle from 50 px at run threshold (mag 0.70) to 90 px at full input. Because stride phase advances by `worldDistance / cycleWorldPx`, temporal leg-cycle frequency is approximately `actualWorldSpeed / cycleWorldPx`. With current constants this frequency peaks around run entry and then declines substantially as the player pushes the stick harder.

This means Kelo can physically accelerate while his four-frame lateral cycle visibly slows. Even without any frame discontinuity, that can read as longer gliding steps / floatiness and can weaken the premium planted feel the user wants.

### EXTERNAL_EVIDENCE
1. Human running biomechanics does not support a blanket assumption that faster running should use a lower step-cycle frequency. A peer-reviewed study summarized by PubMed states that humans run faster using a combination of increased stride length and stride frequency; at high running speeds the strategy shifts increasingly toward higher stride frequency. This does NOT provide a numeric target for Kelo's stylized four-frame gait, but it is counterevidence against treating a large cadence decline during acceleration as inherently natural.
   https://pubmed.ncbi.nlm.nih.gov/22573774/
2. Another locomotion study reports that under normal freely chosen running conditions stride frequency increased with speed. Again, Kelo is stylized pixel animation, so this is directional evidence rather than a prescription.
   https://pubmed.ncbi.nlm.nih.gov/3565038/
3. Unity's animation/navigation guidance explicitly couples animation parameters to actual velocity and warns that animation not covering the proposed velocity can produce foot sliding. It recommends transferring velocity into the animation controller so visual locomotion follows physical movement.
   https://docs.unity3d.com/2023.1/Documentation/Manual/nav-CouplingAnimationAndNavigation.html
4. Godot provides `AnimationNodeTimeScale` specifically to scale animation playback speed, reinforcing the general architecture that visual locomotion rate can be driven by movement state/speed rather than remaining fixed independently.
   https://docs.godotengine.org/en/latest/classes/class_animationnodetimescale.html
5. Community game-dev reports repeatedly identify mismatched world speed vs cycle speed as foot sliding and recommend matching animation rate to movement distance/speed. A recent 2026 IndieDev critique describes a run as floaty because the animation cannot keep up with the traveled distance; older gamedev discussions give the same practical diagnosis.
   https://www.reddit.com/r/IndieDev/comments/1rqqocg/feedback_needed_on_for_my_character_run_cycle_in/
   https://www.reddit.com/r/gamedev/comments/wofi7p/how_do_i_stop_the_feet_from_sliding/
6. Counterevidence: increasing running speed can legitimately come partly from longer stride length, and Kelo has only four lateral poses rather than separate authored walk/run clips. Therefore cadence does NOT need to increase linearly with speed, and the current 50->90 distance expansion may be artistically useful. The question is whether the *net temporal cycle slowdown* is visible and undesirable, not whether RUN_CYCLE_WORLD_PX must equal WALK_CYCLE_WORLD_PX.

### HYPOTHESIS
Kelo will feel more planted and responsive if the mapping from physical speed to temporal lateral cadence is constrained so that increasing analog input does not cause a large decrease in leg-cycle frequency. The likely solution is NOT to return to a hard walk/run jump and NOT to use render-time animation. Instead, preserve distance-driven stride phase but redesign `cycleWorldPxFor()` from a visually validated cadence target (or bounded stride-length growth) so temporal cadence is approximately flat or gently increasing across the run range.

Preferred architecture: continue advancing `stridePhase` exclusively from credited resolved world distance; modify only the distance-per-cycle mapping after measurement. Do not add a second timer-driven animation clock.

- Altering gait/cycle mapping can interact with release-to-plant timing; release invariants must be rerun.
