### PROBLEM
The current movement core preserves floating-point world positions, but the live PNG hero renderer rounds the avatar destination coordinates to whole WORLD pixels before the camera and zoom transforms are applied. The world/camera transform itself remains fractional in the current `engine-c.js` render path. This creates an asymmetric coordinate policy: the environment can move continuously under a fractional camera transform while Kelo's sprite origin advances in discrete one-world-pixel steps.

That is directly relevant to premium lateral movement. At low and medium horizontal speeds, especially at 90/120 Hz, physics may advance less than one world pixel per render. `engine-ab.js` can therefore draw the exact same rounded X for one or more frames and then jump a full world pixel. Since `engine-z.js` later maps one world pixel to roughly 1.05–1.45 CSS pixels depending on viewport, the visible jump can be larger than one CSS pixel. HiDPI then maps that CSS jump to multiple device pixels. A smooth physical trace can therefore look like micro-stutter even while FPS is stable and stride timing is correct.

This is a separate issue from CG-058's lost gait distance threshold. CG-058 concerns whether animation phase consumes small physical travel. CG-062 concerns where the already-moving sprite is actually drawn.

### CONFIRMED_IN_GEMINI
Current `main` audited at `40f988c154a7fae93b8ffdfe5bafb59e148840cc` (`Load Sword Swap planted PvP visual bridge`). The movement/render files relevant to this finding were unchanged by that latest Sword Swap bridge commit.

`index.html` currently declares `Kelo World — V6.36` and loads the relevant owners in this order: `engine-a.js?v=150`, `engine-c.js?v=228`, `engine-h.js?v=151`, `engine-z.js?v=94`, `engine-ab.js?v=240`, then `engine-ac.js?v=222`.

`engine-a.js::updateMovement(dt)` keeps `localPlayer.x/y` as floating-point values and advances them with `localPlayer.vx * dt` / `localPlayer.vy * dt`. There is no whole-pixel rounding of physics position.

The current `engine-c.js` render wrapper builds the world transform as:
`translate(screenW/2, screenH/2) -> scale(CONFIG.zoom) -> translate(-camera.x, -camera.y)`.
It does not round `camera.x/y` before this transform. Therefore fractional camera/world positions are retained in the current world draw path.

`engine-h.js` sets `CONFIG.roundPixels = true`, but that flag belongs to an older render convention. The later/live `engine-c.js` render wrapper shown above does not consult `CONFIG.roundPixels`. `engine-h.js` also creates the HiDPI backing store using `ctx.setTransform(dpr,0,0,dpr,0,0)` and keeps `imageSmoothingEnabled=false`.

`engine-ab.js`, the live PNG hero owner, computes a foot-root presentation layout and then calls `ctx.drawImage(...)` with destination origin:
- X: `Math.round(p.x - dw / 2)`
- Y: `Math.round(footY - dh)`
while `dw`/`dh` are integer visual dimensions.
The nameplate is independently rounded with `Math.round(layout.nameplateAnchorX/Y)`.

Therefore the actor is explicitly world-snapped even though the camera/world transform remains fractional.

`engine-z.js` sets the final responsive zoom from viewport width and clamps it to `1.05..1.45`. For a representative 390 CSS px mobile viewport, current formula gives approximately `390/(11*32) = 1.108`. For a wide desktop it typically reaches the 1.45 clamp.

Consequences of one world-pixel sprite step under the current transform:
- mobile ~390 px profile: ~1.108 CSS px per snapped world-pixel step;
- desktop at zoom 1.45: 1.45 CSS px per snapped world-pixel step;
- on DPR2 backing store these correspond to ~2.216 and ~2.9 device pixels respectively.

Physics/render cadence examples, ignoring collision/camera movement for clarity:
- walk speed 110 world px/s at 120 Hz = ~0.917 world px per render, so whole-world snapping necessarily creates an uneven hold/step pattern;
- 55 world px/s at 120 Hz = ~0.458 world px per render, so the same drawn X can persist for ~2 renders before a ~1-world-pixel jump;
- even full-speed movement can alternate different integer step sizes when physical displacement per render is non-integer.
These are mathematical consequences of the current rounding policy, not yet a claim about perceptual severity on every display.

Code ownership scan: this is not a reason for a broad renderer refactor. `engine-a.js` has an older render path with its own `CONFIG.roundPixels` behavior; `engine-c.js` is the active world-transform wrapper; `engine-h.js` configures DPR/pixel-art policy; `engine-ab.js` performs per-hero destination rounding. The mismatch is distributed across responsibilities, so editing one flag blindly could make background or hero jitter worse.

### EXTERNAL_EVIDENCE
Official Phaser camera documentation exposes `roundPixels` as a deliberate camera/render policy. It explicitly says that setting it true rounds pixel values when rendering game objects and can prevent sub-pixel aliasing in pixel-art games. The important architectural lesson is that snapping should be a coherent camera/render policy, not an accidental per-object rule.

Phaser issue #4664 provides strong counterevidence against blindly enabling rounding everywhere: the reporter observed a stable 60 FPS but visible camera/background stutter, and reported that enabling `roundPixels` made the character stutter more. Phaser issue #6810 similarly documents a trade-off where exact camera follow can make the background jitter while smoothed camera follow can make the player jitter. This closely matches Kelo's need to benchmark actor and world together rather than optimize one in isolation.

Godot's 2D documentation explicitly distinguishes subpixel movement from pixel snapping. Godot documentation/settings guidance also warns that snapping transforms to pixels can produce a crisper result at the cost of less smooth movement, particularly with camera smoothing. This supports treating Kelo's current per-avatar rounding as a measurable trade-off, not an unconditional best practice.

MDN documents that Canvas2D `scale()` changes how canvas units map to output pixels. Therefore Kelo's later world zoom necessarily magnifies any one-world-unit positional quantization. MDN also documents that `drawImage()` accepts destination coordinates directly; there is no requirement that they be integers.

Community evidence is mixed and useful as counterevidence. Developers frequently report that integer snapping fixes texture shimmer in one setup but introduces visible player/camera judder in another. Recent pixel-art discussions also report that removing subpixel movement by rounding positions can itself be the source of jitter. The practical consensus is not “always round” or “never round”; it is to keep the camera, world and actor sampling policy coherent and benchmark the actual target resolutions/zooms.

Sources reviewed:
- Phaser official camera documentation (`roundPixels`).
- Phaser GitHub issue #4664, `Camera causing stutter on tilemap or sprite`.
- Phaser GitHub issue #6810, `Camera shaking`.
- MDN CanvasRenderingContext2D `scale()` and `drawImage()` documentation.
- Godot official 2D documentation on pixel snap/subpixel positioning.
- Reddit r/gamemaker / r/godot / r/raylib discussions on subpixel rounding, camera jitter and pixel-art motion, including counterexamples where snapping worsens smoothness.

### HYPOTHESIS
Kelo's lateral motion will look materially smoother if actor presentation stops applying an isolated whole-WORLD-pixel snap before a fractional camera/zoom transform. However, simply removing `Math.round()` may introduce nearest-neighbor edge shimmer because `imageSmoothingEnabled=false` and the sprite can then land on fractional device pixels.

The likely winning architecture is not known yet. Candidates must compare at least:
1. current actor-only world snap;
2. unsnapped actor with current fractional camera;
3. a coherent SCREEN/DEVICE-space snap policy applied after camera+zoom mathematics (or an equivalent camera/render policy) so actor and environment do not quantize against different grids.

Do not assume Candidate 2 wins just because it is mathematically smoother. Pixel-art temporal sharpness may favor a coherent snap solution.

### PROPOSED_CHANGE
Do not modify production before collecting baseline traces and video/frame captures.

Candidate A — BASELINE:
Keep `Math.round(p.x - dw/2)` / `Math.round(footY-dh)` in `engine-ab.js` with current fractional camera transform.

Candidate B — UNSNAPPED HERO QA-ONLY:
Pass floating destination X/Y to `drawImage()` for the hero only. Change no camera, physics, gait, zoom, filtering, visual scale, sprite frames or collider. This isolates the cost/benefit of actor world snapping.

Candidate C — COHERENT PRESENTATION SNAP QA-ONLY:
Prototype a render-space snap helper that derives actor screen/device position from `(world - camera) * zoom`, snaps at a chosen output grid (CSS pixel or device pixel), then maps back only for drawing. Apply the same policy to any actor-local ground cue/nameplate required by the benchmark. Do not alter physics `p.x/y`.

Candidate D — CAMERA/WORLD COHERENT SNAP only if A/B/C show world-relative shimmer:
Test a camera quantization policy consistent with the actor, inspired by explicit engine `roundPixels` modes. This must be evaluated carefully because prior external evidence shows camera snapping can move the jitter from player to background.

Do not combine any candidate with 1.20x scale, smoothing filter changes, new lean/bob/squash, dead-zone changes or collision changes on the first pass.

- Do not assume removing `Math.round()` is automatically better; nearest-neighbor fractional sampling may shimmer.
- Do not change physics position to integers. Physics/collision must retain subpixel precision.
- Do not round `localPlayer.x/y` in `updateMovement()`.

### RISKS
- Fractional `drawImage` with nearest-neighbor can cause edge shimmer or changing apparent pixel thickness.
- Snapping the camera instead can make the entire background stutter; external Phaser evidence shows exactly that trade-off.
- A screen-space snap helper can become inconsistent across DPR/zoom if it snaps CSS pixels when the desired grid is device pixels, or vice versa.
- Rounding only the sprite while leaving the nameplate/shadow unsnapped can create internal actor wobble; measure all actor presentation anchors together.
- Existing authored environment assets may already rely on their own integer/fractional placement policies; do not globally change them in this first experiment.
- At 1.20x, integer destination width/height plus fractional position can create a different temporal sampling pattern, so scale testing must happen only after coordinate policy is selected.
- Wrapper ownership is already layered (`engine-c`, `engine-h`, `engine-ab` and later visual wrappers). A blind cleanup could break unrelated visuals. Baseline first.
