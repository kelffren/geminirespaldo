### PROBLEM

Kelo's base Canvas2D avatar renderer contains a simple elliptical contact shadow anchored near the physical root, but the production PNG renderer in `engine-ab.js` replaces `renderAvatar()` after `assets/hero.PNG` loads and does not reproduce that shadow. Therefore the visible production hero loses the one cheap visual cue that explicitly connects the body to the floor. This is especially relevant before increasing avatar size or adding bob/lean, because a larger or vertically animated body with no stable ground contact cue will read as more floaty even if physics and foot root are correct.

This round is intentionally separate from previous footRoot, scale, occlusion, subpixel and squash investigations: it concerns the actual ownership and persistence of the ground-contact shadow in the current production render path.

### CONFIRMED_IN_GEMINI

At base commit `fcf3793bbce89ca2f974043cc4391a1f2dc36f57`:

1. `engine-a.js` defines the base `renderAvatar(p,isSelf)` and begins it by drawing an ellipse at approximately `p.x, p.y + 14` with radii `p.radius * 0.9` and `p.radius * 0.45`, fill `rgba(0,0,0,0.4)`.
2. The local player's physical collider radius is still `20`, so the legacy shadow is approximately 36 world px wide x 18 world px tall.
3. `engine-ab.js` stores the previous renderer as `_av = renderAvatar`, then replaces `renderAvatar` with the production PNG path.
4. `_av` is used only as fallback while the sprite is unavailable/not loaded. Once `ok && sheet` are true, `engine-ab.js` draws `assets/hero.PNG` and the nameplate directly and never calls the base renderer.
5. The production PNG path contains no contact-shadow draw before or after `drawImage()`.
6. Therefore the base ellipse can be present during fallback/early load but is absent from the steady-state PNG hero path.
7. `engine-ac.js` now drives distance-based locomotion state but does not own or publish a shadow transform.
8. `engine-z.js` applies zoom approximately in the 1.05-1.45 range depending on viewport, so any world-space contact shadow would naturally scale with the world unless deliberately decoupled.
9. `ENGINE_MAP.md` remains stale about hero ownership (`engine-m.js`), while the current production PNG override is in `engine-ab.js`. Any shadow fix should follow live code ownership rather than the stale map.
10. No production change was made in this research pass.

### EXTERNAL_EVIDENCE

1. Unity's current 2D rendering documentation treats shadow shape/silhouette as an explicit rendering concern rather than a collider concern (`Shadow Caster 2D`). This supports keeping a visual shadow contract separate from physics bounds. Source: Unity Manual, "Create shadows with Shadow Caster 2D in URP" (Unity 6.x docs).
2. Unity's 2D workflow documentation lists shadows as a visual tool that contributes to presentation/polish rather than gameplay physics. Source: Unity Manual, "2D game creation workflow".
3. Community 2D/pixel-art discussions repeatedly use a grounded pivot/feet relationship to avoid characters appearing to sink or float. A Reddit /r/gamedev discussion on feet sinking specifically recommends aligning the pivot toward the bottom/feet while keeping the collider as a separate concern.
4. HD-2D community discussion provides useful counterevidence: physically projected sprite-shaped shadows can expose the flat billboard nature of 2D sprites and become visually awkward. This argues against jumping straight to expensive silhouette-projected dynamic shadows for Kelo. A simple contact/blob shadow may be more appropriate for this Canvas2D top-down presentation.
5. Counterevidence: a contact shadow is not automatically an improvement. If too dark, too large, or allowed to bob/lean with the torso, it can look like a sticker, make the sprite muddy, or visually imply a larger collision footprint than the true radius. Therefore it needs an A/B measurement and should remain anchored to ground contact rather than body deformation.

### HYPOTHESIS

A small, stable, low-cost contact shadow rendered beneath the PNG and anchored to the formal foot/root position will materially improve lateral grounding and make subsequent 1.15x-1.25x avatar scaling safer, provided:

- it does not inherit body bob/lean/squash;
- it does not change collider radius or collision logic;
- its center follows the ground/foot root, not the torso center;
- its dimensions are calibrated visually rather than copied blindly from the legacy `radius*0.9/radius*0.45` ellipse;
- it remains cheap enough that many actors do not materially increase frame time.

### PROPOSED_CHANGE

Do not implement a lighting system or dynamic projected shadow from this entry.

Evaluate these presentation-only candidates with identical gameplay traces:

**A — BASELINE_PNG_NO_SHADOW**
- Current `engine-ab.js` behavior.

**B — LEGACY_CONTACT_SHADOW_RESTORED**
- Reproduce the current legacy ellipse below the PNG, using the same current physical-root relation (`p.y + 14`) only as a benchmark reference.
- Keep collider, movement and camera unchanged.

**C — FOOTROOT_CONTACT_SHADOW**
- Preferred hypothesis.
- Define one explicit `footRootY`/ground anchor for the PNG presentation (compatible with the existing `footY = p.y + 10` contract).
- Draw an ellipse before the sprite around that ground anchor.
- Shadow transform is independent of torso bob/lean/squash.
- Candidate size should be calibrated against visible foot span, not collider size. Start by benchmarking roughly 60-80% of visible shoulder/body width and a shallow vertical radius rather than adopting a final constant blindly.
- Optional very small opacity/width response to gait may be tested later, but baseline C should remain static to isolate grounding benefit.

**D — AUTHORED_SOFT_CONTACT_ASSET**
- Only if Canvas ellipse edges look too synthetic with pixel-art/HD-2D styling.
- A tiny pre-rendered alpha shadow sprite/atlas element can be compared against C.
- Do not introduce per-frame blur/filter operations as the first solution.

Ownership recommendation if implemented: keep the simple contact-shadow draw in the same final avatar presentation owner that draws the PNG, or expose a narrow helper owned by that renderer. Do not create another generic render wrapper solely for this effect.

### DO_NOT_ASSUME

- Do not assume the old ellipse is visually correct simply because it already exists.
- Do not enlarge `localPlayer.radius` to match a larger sprite or larger shadow.
- Do not attach shadow size directly to future body `scaleY`, bob or lean.
- Do not interpret the shadow as a depth/Y-sort key; depth remains based on foot/baseY semantics.
- Do not implement real-time blurred Canvas shadows, normal-map lighting or WebGL shadow projection from this finding.
- Do not call the hero "grounded" from code inspection; visual evidence is required.
- Do not change stride cadence, stop/reversal phase, camera or collision in the same benchmark.

### RISKS

1. A world-space ellipse will scale with camera zoom; if it becomes too large on mobile zoom, a visual-size calibration may be needed.
2. Tying shadow dimensions to collider radius can accidentally make presentation communicate the wrong footprint once avatar scale and collider intentionally diverge.
3. Drawing a dark shadow directly under pixel feet can obscure the very contact frames we are trying to evaluate.
4. If future bob/lean transforms are applied to a parent Canvas transform that also contains the shadow, the shadow may start bobbing with the body. The shadow must be drawn outside/under the body presentation transform.
5. Multi-pass depth correction may redraw the actor multiple times; blindly embedding a shadow in every avatar redraw could darken/duplicate it. Instrument `shadowDrawsPerVisibleActor` and inspect Plaza/Gardens depth passes before final ownership.
6. A soft filter/blur per actor can become unnecessarily expensive in Canvas2D. Start with a primitive or authored alpha asset.
7. Visual scoring is subjective; preserve screenshots/video and objective anchor/performance metrics.
