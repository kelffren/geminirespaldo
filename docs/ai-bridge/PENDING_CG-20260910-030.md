## PROBLEM
Tras restaurar el dodge funcional de 112 px, cliente y servidor alcanzaban el mismo endpoint pero recorrían trayectorias distintas: cliente lineal y server cubic-out. La divergencia temporal máxima determinista era ~43.10 px. Además el cliente mantenía `state.dodge` bloqueando movimiento/ataque durante 150 ms después del endpoint, mientras el server liberaba `_pvpDash` al terminar el recorrido.

## CONFIRMATION_IN_GEMINI
- `src/abilities/kelo-ability-boot.js` era el owner LIVE de `_dash` y usaba interpolación lineal.
- `server/pvp-authority.js` usaba `ease=1-Math.pow(1-k,3)` para `_pvpDash`.
- `src/systems/pvp-world.js` declaraba `recovery:.15` y `movementHook()` ponía scale 0 mientras `state.dodge` existiera.
- El server declaraba también `.15`, pero su step no aplicaba ese recovery después de eliminar `_pvpDash`; por tanto el contrato declarado y la conducta autoritativa no coincidían.
- `pvp-combat-runtime-loader.js` ya contenía el fix anterior de wake de KeloAbilities; no fue rehecho.

## HYPOTHESIS
Alinear la interpolación genérica de `_dash` del cliente con cubic-out del server y eliminar el recovery local no autoritativo debería producir un dodge más decisivo al inicio, cero deuda de trayectoria cliente/server y devolución inmediata del control al endpoint, sin cambiar distancia, duración, iFrames ni cooldown.

## IMPLEMENTED_CHANGE
Winner gameplay commit: `c6fcd1da276fcc420dd3cc09c38351705f7043b5` (`Align PvP dodge trajectory and recovery parity`).

Cambios:
1. `src/abilities/kelo-ability-boot.js`: interpolación `_dash` lineal -> cubic-out `1-(1-k)^3`, igual al server.
2. `src/systems/pvp-world.js`: dodge recovery `.15 -> 0` para no bloquear control después del endpoint.
3. `server/pvp-authority.js`: recovery declarado `.15 -> 0`, alineando contrato con la conducta autoritativa que ya liberaba al endpoint.
4. `scripts/audit-pvp-dodge-timing.js`: convertido en winner-lock de cubic parity, recovery 0 y max trajectory delta <= .001 a 60/90/120 Hz.

No se creó otro engine, movement manager, timer owner ni game loop. Distance sigue 112 px, duration .16 s, iFrames .105 s y cooldown .85 s.

## ERROR_DETECTED_AND_REFINEMENT
El primer intento de browser validation falló por el harness, no por gameplay: el script temporal se escribió en `/tmp` y Node no podía resolver el package `playwright` desde el `node_modules` del repo. Se corrigió el harness para ejecutarse dentro de `scripts/`, se repitió la misma prueba y mobile+desktop pasaron. No se hizo un segundo tweak de gameplay porque el candidato ya ganó paridad exacta y runtime; tocarlo más habría sido tuning sin evidencia.

## RISKS
- `KeloAbilities` posee `_dash` de forma genérica, por lo que cubic-out también afecta localmente otras abilities que usen ese mismo dash primitive. Esto mejora paridad con el server donde este usa cubic-out, pero Wind Dash/otros mobility deliveries deben quedar en la siguiente matriz de regresión visual antes de retocar su feel.
- Eliminar recovery aumenta la capacidad de actuar justo al endpoint respecto al cliente anterior, pero no respecto al server: elimina un handicap exclusivo del cliente.
- Si diseño competitivo futuro quiere recovery real, debe implementarse como timeline compartida y autoritativa en ambos lados, no reintroducirse solo en presentación/cliente.
