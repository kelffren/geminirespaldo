### PROBLEM
Current lateral locomotion is substantially better than earlier rounds, but the remaining premium-feel risk is now at direction release/reversal boundaries, not basic travel. In current load order `engine-ac.js` wraps `updateMovement` before `engine-ah.js`. `engine-ac` computes visual movement and publishes `_visualMotion` immediately after the wrapped physics move; then the later `engine-ah` wrapper hard-zeros velocity when there is no movement input. On the first no-input simulation step, `engine-ac` can therefore still see the previous nonzero speed (`spd > 16`) and keep `visual.on=true`; `engine-ah` zeros velocity only after that visual decision. The next simulation step plants the sprite. This creates a plausible one-simulation-step visual tail after physical release. The existing LIVE audit waits 140 ms before sampling release, so it proves eventual plant but not release-to-plant latency or refresh-rate consistency.

Avatar scale is already 1.15x with a separate `footRoot`, collider and nameplate anchor. The next scale increase should not be bundled with locomotion changes. Current renderer disables `ctx.imageSmoothingEnabled` and rounds destination position, which is correct for testing crisp nearest-neighbor behavior, but the production source frame is much larger than the final on-screen sprite. Therefore the common advice “disable smoothing when enlarging pixel art” does not by itself prove that smoothing-off is optimal for this specific downscaled source at DPR 1/2.

### EXTERNAL_EVIDENCE
1. MDN `requestAnimationFrame()` documents that callbacks generally track display refresh (commonly 60 Hz, also 75/120/144 Hz) and warns that animation progression must use elapsed time/timestamps or it will run at different speeds on high-refresh displays. Source: https://developer.mozilla.org/en-US/docs/Web/API/window/requestAnimationFrame
2. MDN `CanvasRenderingContext2D.imageSmoothingEnabled` documents that smoothing is on by default and that disabling it preserves sharp pixels when scaled, especially for pixel art. This supports keeping smoothing as an explicit tested variable rather than relying on CSS alone. Source: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
3. Aseprite slice documentation supports explicit sprite pivots and exporting pivot/slice metadata in spritesheet JSON. This is a stronger future asset contract than indefinitely inferring feet from alpha bounds. Source: https://www.aseprite.org/docs/slices/
4. Adobe walk-cycle guidance describes contact/passing poses, weight transfer, opposite arm/leg motion, and firm planted-foot contact as key to natural gait. Source: https://www.adobe.com/creativecloud/animation/discover/animation-walk-cycle.html
5. Community/animation references consistently identify contact pose and weight transfer as the main grounding cues; recent Reddit foot-sliding discussion also frames the defect as contact placement inconsistency rather than simply insufficient bob. Counterevidence: adding more vertical bob is not a guaranteed cure and can make a character floatier if feet are not anchored first.

### HYPOTHESIS
H1 — The next measurable movement defect is a one-simulation-step release visual tail caused by wrapper order (`engine-ac` observes pre-hard-stop velocity, `engine-ah` zeros after). Removing or accounting for that tail should make lateral stops feel more planted without changing physics speed.

H2 — Immediate L↔R mirroring while preserving the same stride frame is mathematically continuous in frame index but can still create a perceptual support-foot pop because mirroring swaps screen-side foot support instantly. A short, time-based reversal settle into the authored plant/contact pose (roughly 50–80 ms), presentation-only, may feel more weighted than an instantaneous mirrored phase. This is NOT proven and must be A/B tested because too much hold will feel laggy.

H3 — Scale 1.20x is a reasonable next candidate only after H1/H2 are measured. At the current geometry it is a small visual step (side width roughly 55 px at 1.15x to ~58 px at 1.20x; height roughly low-90s to high-90s), while collider can remain exactly unchanged. However sprite quality must be judged separately at DPR 1 and DPR 2; do not assume nearest-neighbor downscaling is automatically superior.

### EXPERIMENT
E1 Release latency baseline:
1. Start from clean stationary plant.
2. Hold RIGHT long enough to enter stable walk/run cycle.
3. Release at a timestamp captured by the harness.
4. Sample movement/velocity/visual frame/phase every available animation step for 120 ms.
5. Repeat 30 times on mobile viewport DPR2 and desktop DPR1.
6. Repeat LEFT and diagonal releases.

E2 Reversal baseline/candidate:
1. RIGHT 220 ms -> immediate LEFT 220 ms, repeated 30 times.
2. Compare current phase-preserving mirror against 50/65/80-ms presentation-only settle, one candidate at a time.
3. Record physics reversal distance, visible frame sequence, first opposite-facing timestamp, support/contact pose, and accidental idle.
4. Capture short video/trace or sequential screenshots; single still images are insufficient for judging reversal.

E3 Scale baseline/candidate:
1. 1.15x and 1.20x using same spawn, camera, facing, gait frame and viewport.
2. Mobile 390x844 DPR2 and desktop 1280x720 DPR1.
3. Static idle + lateral walk + reversal + behind/in-front occluder + near viewport edge.
4. Measure screen bounds, collider unchanged, footRoot unchanged, nameplate gap/overlap, aura/shadow anchoring, clipping, JS errors, and frame-time percentile.
5. If visual quality is ambiguous, screenshot crops at native device pixels and compare filtering A/B; do not infer from CSS declarations.

### DECIDING_METRICS
Release:
- median and p95 `releaseToStablePlantMs`;
- number of simulation/render samples with zero input but `visualOn=true`;
- post-release world drift (must remain unchanged or improve; target essentially 0 under hard-stop contract);
- final frame/phase exactly plant contract.

Reversal:
- physical direction reversal latency: unchanged from baseline;
- visible-facing reversal latency: target <=80 ms and no obvious lag;
- accidental idle count: 0;
- frame jump >1: 0;
- no extra world displacement caused by presentation settle;
- qualitative trace: no support-foot teleport/popping.

Scale:
- collider radius delta: 0;
- footRoot/depthRoot/shadowAnchor delta from physics contract: 0 except intended visual bounds;
- nameplate collision/overlap regressions: 0 in test scenes;
- clipping/occlusion regressions: 0;
- p95 frame time regression target <5% from 1.15x baseline;
- no new console/network errors;
- screenshot quality at DPR1/DPR2 must not show materially worse aliasing or blur.

### RISKS
- A reversal plant hold can feel like control latency even if physics reverses instantly.
- Moving stop ownership without a trace may accidentally reintroduce deceleration or alter diagonal behavior.
- `engine-ah` and `engine-ac` both wrap `updateMovement`; refactoring them together would make attribution difficult.
- Scale 1.20x may increase occlusion/nameplate crowding even with unchanged collider.
- Pixel filtering preference is art-dependent; automatic sharpness metrics can disagree with human perception.
- Current alpha-derived contact-band evidence measures silhouette support, not anatomical foot identity, so it cannot by itself prove which leg is planted.
