### PROBLEM
The current MOV-CADENCE-V2 correctly removes the old abrupt 50px -> 90px stride-length jump at WALK->RUN, but it does so by growing cycleWorldPx from 50 to 90 across the run range while the renderer continues to reuse the exact same four lateral source frames. As a consequence, increasing physical speed from the run threshold to full input is represented mostly as a longer virtual stride rather than a faster visible leg cycle. This can make Kelo translate much faster while his legs appear to cycle at almost the same rate, a classic foot-slide / treadmill mismatch candidate.

### CONFIRMED_IN_GEMINI
Current main engine-ac.js defines GAIT_RUN_START=0.70, WALK_CYCLE_WORLD_PX=50, RUN_CYCLE_WORLD_PX=90. For gait==='run', cycleWorldPxFor() linearly increases cycle distance from 50 at magnitude 0.70 to 90 at magnitude 1.00. speedFor() meanwhile increases the movement speed cap; targetSpeed published by KELO_MOVEMENT_AUDIT is processedMag*speedCap.

Using the exact LIVE formulas (model values, not a measured trace):
- mag 0.70: targetSpeed ≈97.316 world px/s, cycleWorldPx=50, ≈1.946 cycles/s, ≈7.785 frame-steps/s.
- mag 0.80: targetSpeed ≈128.350, cycleWorldPx≈63.333, ≈2.027 cycles/s, ≈8.106 frame-steps/s.
- mag 0.90: targetSpeed ≈160.199, cycleWorldPx≈76.667, ≈2.090 cycles/s, ≈8.358 frame-steps/s.
- mag 1.00: targetSpeed=185.280, cycleWorldPx=90, ≈2.059 cycles/s, ≈8.235 frame-steps/s.
Thus the model's translation speed rises about 90.4% from mag 0.70 to 1.00 while visible cycle frequency rises only about 5.8%. It is also slightly non-monotonic near the top: the modeled cycle frequency is a little lower at 1.00 than at 0.90 even though physical speed is higher.

engine-ab.js does not select a separate run row or run frames. It consumes _visualMotion.frame and renders the same lateral row/frame set for walk and run. Therefore the extra virtual stride length is not currently backed by visibly longer authored run poses.

ENGINE_MAP.md still names engine-ac.js as LIVE gait/walk-run/cycle-by-distance owner and engine-ab.js + hero.PNG as LIVE visible hero owner. index.html V6.39 loads engine-ab.js before engine-ac.js, so these current definitions are the relevant runtime chain.

GROK_TO_CHATGPT.md has no newer movement feedback after GC-20260831-003, so no newer Grok evidence supersedes this observation.

### EXTERNAL_EVIDENCE
Unity's Blend Tree documentation explicitly couples walk/jog/run thresholds to motion speed/velocity and provides time-scale adjustment so animation speed can correspond to the movement parameter. Godot AnimatedSprite2D exposes speed_scale specifically to speed up or slow down animation playback. Community pixel-art feedback repeatedly identifies translation speed that exceeds foot-cycle speed as visible sliding; recent Godot discussion recommends matching world travel to the distance the feet cover in the authored animation. Counterevidence: keeping cadence relatively stable while increasing stride length is physically plausible for real running, and an authored run can legitimately gain speed through longer stride rather than much higher cadence. But Kelo currently reuses the same four lateral poses, so whether that assumption is visually supported must be measured rather than assumed.

### HYPOTHESIS
For the current four-frame lateral sheet, the 50->90 world-px cycle-distance interpolation overcompensates for run speed. A run cadence policy that preserves continuity at 0.70 but increases visible cycle frequency more meaningfully with actual speed will reduce foot sliding and make full-stick LEFT/RIGHT feel more energetic and premium. The correct mapping should be determined from the sprite's actual support/contact displacement, not from a generic animation-speed rule.

### PROPOSED_CHANGE
Do not change production yet. Add a QA-only cadence candidate that keeps the same stridePhase continuity and same four source frames but changes only cycleWorldPxFor() above GAIT_RUN_START.

Candidate A: current 50 -> 90 world-px interpolation.
Candidate B: a constrained run cycle-distance curve that grows less aggressively, initially benchmark 50 -> 70 world px at full input.
Candidate C: speed-normalized cadence derived from a target visible cycle frequency, with clamp limits chosen from measured support-foot behavior. Example structure only: cycleWorldPx = actualOrTargetSpeed / desiredCyclesPerSecond(mag). Do not ship constants from this entry without measurement.

Do not introduce separate run art, bob, lean, collider changes, camera changes, native-left changes, per-frame foot-pivot correction, or sampling/DPR changes in the same experiment.

### DO_NOT_ASSUME

### EXPERIMENT
Baseline -> candidate -> same trace -> re-measure.

Run open-space lateral traces at processed input magnitudes 0.48, 0.60, 0.69, 0.70, 0.75, 0.80, 0.90, 1.00. Hold each magnitude long enough for at least 8 complete cycles. Repeat RIGHT and LEFT. Then test ramps 0.60->1.00 and 1.00->0.60 plus release and RIGHT<->LEFT reversal.

For every render/update record: timestamp, dt, processedMag, gait, actualSpeed, worldDistanceDelta, cycleWorldPx, stridePhase, sourceFrame, frame-transition timestamp, support centroid/contact estimate when available.

Repeat at 60/90/120 Hz if harness control is available, plus at least 390x844 DPR2 and 1280x720 DPR1. Keep 1.15x avatar scale for the deciding cadence experiment. Only rerun the winner at 1.20x afterward.

### RISKS
With only four frames, raising cadence can expose authored pose discontinuities, mirroring asymmetry, per-frame foot-anchor variance (CG-068), or support-foot teleport on reversal (CG-064). Those are confounders, not reasons to combine fixes. Candidate B's 70px endpoint is only a bounded benchmark point, not a recommended production constant. ActualSpeed may differ from targetSpeed under collisions or other wrappers, so open-space measurement is mandatory. Browser scheduling at 60/90/120 Hz must not change stride distance itself; if it does, that is a separate timing bug.
