### PROBLEM
The modern LIVE hero renderer rounds destination x/y/width/height to whole WORLD units before the world transform is applied. The world is then rendered through a camera transform whose effective zoom can be fractional, especially in landscape. This creates two quantization domains at once: actor destination geometry is snapped in world space, then those snapped units are multiplied by a possibly fractional screen scale. A character moving smoothly in world space can therefore hold one rendered world pixel for several updates and then jump to the next; the resulting CSS/physical-pixel step size varies with zoom, DPR and orientation. Increasing the avatar from 1.15x to 1.20x can make these phase changes easier to see because the silhouette and foot-contact edges become larger while the collider/physics remain continuous.

### CONFIRMED_IN_GEMINI
At current main base commit 23b29517f83f2efbad12ea7eba1d2bd83e85340d:

1. `src/characters/character-appearance.js` computes exact floating-point `scale = targetBodyHeight / metrics.bodyHeight`, but then rounds all destination geometry before drawing: `dx=Math.round(layout.footRootX-anchorX*scale)`, `dy=Math.round(...)`, `dw=Math.round(sw*scale)`, `dh=Math.round(sh*scale)`.
2. The same file uses per-frame authored foot anchors and records the semantic `footRoot` separately in audit data. Thus the semantic foot root may move continuously while the destination rectangle moves only when the rounded integer changes.
3. `engine-c.js` applies the world transform around avatar rendering as `translate(screen center) -> scale(CONFIG.zoom) -> translate(-camera.x,-camera.y)`. The rounded world-space destination rectangle is therefore multiplied by camera zoom afterwards.
4. `engine-h.js` configures the camera/viewport as `pixelPerfect:true`, `roundPixels:true`, `smoothing:false`, `imageRendering:'pixelated'`.
5. `src/core/camera-system.js` derives `effectiveZoom` from base zoom and orientation. Portrait uses the base zoom, while landscape multiplies by `height/width`, which frequently creates a non-integer/fractional effective zoom. DPR is capped but can itself be fractional on real devices. Therefore rounding to integer world units does not guarantee integer CSS pixels or integer physical pixels after the complete transform.
6. Character Appearance also rounds `dw/dh`, so the scale actually presented by `drawImage()` is quantized independently per destination dimension. When target visual height changes from 1.15x to 1.20x, some directions/frames can cross different integer width/height thresholds and receive a small effective scale discontinuity even though the semantic scale changed smoothly.
7. No production code inspected in this pass demonstrates that this quantization is visually bad. The confirmed finding is the mixed quantization contract, not a proven LIVE defect.
8. Ownership is already clear: Character Appearance owns hero destination geometry; KeloCamera owns viewport/zoom; engine-c owns base render orchestration. Do not create another renderer or camera wrapper for this experiment.

### EXTERNAL_EVIDENCE
MDN Canvas 2D documentation for `drawImage()` and `imageSmoothingEnabled` supports the distinction between image filtering and geometric placement: disabling smoothing keeps nearest-neighbor-style scaling but does not by itself make fractional transforms temporally stable. Relevant docs: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage and https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled .

Godot issue #93048 documents a closely related pixel-art constraint: when movement per update does not align with the pixel grid, snapped rendering alternates between different pixel step sizes and can look uneven even though the underlying motion is mathematically smooth. This is supporting evidence for measurement, not proof that Kelo should abandon snapping: https://github.com/godotengine/godot/issues/93048 .

A public Godot smooth-pixel-camera demo explicitly notes the tradeoff between pixel-perfect rendering and smooth camera/player motion, and that some approaches relax snapping during motion and only snap when motion stops: https://github.com/voithos/godot-smooth-pixel-camera-demo .

Community counterevidence is important. Pixel-art developers commonly fix blur by rounding sprite draw positions, and for some games integer snapping is the preferred aesthetic. Other developers report that rounding both player and camera can itself create visible jitter, especially with slow/diagonal motion and moving cameras. Examples: https://www.reddit.com/r/gamemaker/comments/ln2pix and https://www.reddit.com/r/Unity2D/comments/1iwjstv . Therefore this entry does not assume that removing rounding is better; it asks for an A/B measurement of quantization policy.

PixiJS has also had real-world scaling issues on fractional device-pixel ratios, reinforcing that fractional DPR/scale must be part of the device matrix rather than assuming DPR is always 1/2/3: https://github.com/pixijs/pixijs/issues/4866 .

### HYPOTHESIS
Kelo will look more temporally stable if avatar snapping is defined in one deliberate domain instead of implicitly mixing world-space integer rounding with a fractional camera/DPR transform. The most likely viable policies are either: (a) keep world-space integer snapping and deliberately accept/measure the resulting screen cadence, or (b) preserve floating-point avatar geometry through the world transform and quantize only the final screen/physical placement when a pixel-perfect mode actually requires it. A third possibility is hybrid: allow subpixel motion while moving, then snap only at plant/idle so feet finish cleanly.

### PROPOSED_CHANGE
Do not modify production before measuring.

A — baseline: current integer rounding of `dx/dy/dw/dh` in Character Appearance.

B — float-position candidate: keep `dx/dy` as floats while preserving current integer `dw/dh`, smoothing=false. This isolates temporal position quantization from size quantization.

C — float-position + float-size candidate: preserve all destination values as floats and rely on nearest-neighbor filtering. This tests whether destination-size rounding is creating visible silhouette breathing or scale error.

D — plant-snap hybrid: use float destination position during movement, but on idle/plant quantize the final visual foot contact to the chosen pixel grid. This is relevant only if B/C improve motion but make the stationary sprite look soft/misaligned.

E — explicit screen/physical-grid snap: derive the final desired snap unit from effective zoom and DPR so the anchor lands on a consistent output pixel grid rather than rounding arbitrary world units. This is the most invasive candidate and should be tested only if A-D establish that the mixed domain is a real problem.

Keep physics, collider, movement vectors, stride, facing, camera trajectory and authored foot anchors unchanged. Do not change the global camera snapping policy in the same experiment.

### DO_NOT_ASSUME
- Do not assume `imageSmoothingEnabled=false` eliminates temporal jitter; it only changes filtering.
- Do not assume integer world coordinates are pixel-perfect after a fractional camera scale or fractional DPR.
- Do not remove rounding globally from props/world/UI based on this finding.
- Do not enlarge the collider when testing 1.20x.
- Do not combine this benchmark with cadence, hysteresis, bob, lean, shadow or camera follow changes.
- Do not call A a bug until LIVE traces/screenshots show perceptible uneven motion or anchor phase jumps.
- Do not optimize with per-frame `getImageData()` or allocate canvases in the hot path.

### EXPERIMENT
1. Add debug-only telemetry around Character Appearance draw geometry: semantic `footRootX/Y`, raw floating `dx/dy/dw/dh` before rounding, rounded destination geometry, face/frame, effective zoom, DPR and world->screen foot position.
2. Replay the exact same deterministic RIGHT and LEFT movement traces at steady resolved speeds covering low walk, walk/run threshold and max run. Include diagonal motion because unequal x/y phase advancement often exposes pixel cadence problems more clearly.
3. Run A/B/C on the exact same recorded world/camera trace. Production physics/camera must not be recomputed differently between candidates; render from the same trace if possible.
4. Test 60/90/120 Hz render cadences and at least 390x844 DPR2, 844x390 DPR2, 1440x900 DPR1, plus one real or emulated fractional-DPR case such as 2.625 if browser tooling permits it.
5. For each frame, project the semantic foot root and visible destination anchor to CSS and physical pixels. Measure per-frame displacement sequence rather than only average speed.
6. Capture high-contrast crops of the feet/head silhouette during LEFT/RIGHT steady motion, release-to-plant and RIGHT<->LEFT reversal. Compare temporal edge stability frame-by-frame.
7. Repeat the winning policy at current 1.15x and proposed 1.20x visual scale with unchanged collider/camera.
8. If B/C look smoother but stationary placement is visibly less crisp, test D. Only consider E if a single output-grid snap demonstrably improves both motion and stationary clarity.

### RISKS
- Float positioning with nearest-neighbor rendering can create shimmering/mixels depending on browser, DPR and fractional zoom.
- Snapping in both actor and camera domains can create beat-frequency jitter; snapping neither can look soft.
- A 1.20x avatar can amplify edge instability and overdraw, so scale must be tested after the render policy is chosen, not used to hide the problem.
- Changing `dw/dh` rounding can subtly change apparent sprite proportions by a pixel and must be compared per face because RIGHT uses very different source body metrics from LEFT/UP/DOWN.
- Fractional-DPR emulation may not perfectly reproduce device compositing; real-device capture remains valuable.
