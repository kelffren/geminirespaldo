### PROBLEM
The LIVE browser movement profile and the authoritative PvP server do not currently share one canonical speed mapping. `engine-ac.js` owns the client gait/speed curve with `BASE_SPEED = 220` plus nonlinear magnitude/gait caps, while `server/pvp-authority.js` independently declares `BASE_SPEED = 320` and applies server-side PvP movement restrictions. This is not merely a 100 px/s constant difference: the client curve is nonlinear, so identical movement intent can produce semantically different requested velocities between offline/client prediction and authoritative simulation. Once prediction/reconciliation becomes strict, that creates a high-risk path for correction snaps, rubberbanding, and an online combat feel different from offline.

### CONFIRMED_IN_GEMINI
- Current `main` baseline for this research is `b746daf8e2d694b17ff38474d44d51b7ac318218`.
- `KeloMovement` remains the single Foundation wrapper/extension owner for `updateMovement`; do not add another movement wrapper.
- `engine-ac.js` remains LIVE support for gait/speed/stride and currently defines client `BASE_SPEED = 220` with analog/gait-dependent speed-cap logic.
- `server/pvp-authority.js` independently defines authoritative `BASE_SPEED = 320` and has its own PvP phase/death/respawn movement policy.
- The server base constant is 45.45% larger than the client base constant (`320/220 - 1`), but actual target-speed mismatch cannot be reduced to that percentage because the client applies a nonlinear magnitude/gait curve.
- Recent `main` has already added PvP aim-facing and light-basic recovery mobility improvements, so this parity issue matters more now: a better local feel should not diverge when server authority is enabled.
- Existing client stride logic remains distance-resolved; this proposal must not alter stride, facing, collision, camera or foot-anchor contracts.

### EXTERNAL_EVIDENCE
- Unity Multiplayer documentation describes client prediction/anticipation as local simulation followed by correction to authoritative server state when the prediction differs. Divergent movement semantics therefore directly increase the correction work the presentation layer must hide.
- Unity's latency guidance explicitly notes that a client can update movement immediately from input while remaining server authoritative, but incorrect predictions must later be corrected.
- Recent GitHub reports show visible stutter/rubberbanding when client and server process movement under inconsistent movement/collision semantics; this is supporting evidence, not proof that Kelo currently rubberbands.
- Community networking discussions consistently recommend instrumenting the exact client-sent/server-received input and comparing deterministic simulation traces before blaming latency alone.
- Counterevidence: exact shared runtime code is not mandatory. A canonical data profile plus separate client/server adapters and a parity contract test can be safer if browser and Node module systems make one shared JS module awkward. Numeric parity also does not eliminate corrections caused by latency, collision ordering, remote CC, tick-rate differences or nondeterministic simulation.

### HYPOTHESIS
The safest long-term path is one canonical, pure movement-speed profile consumed or generated into both client and server, while keeping server-only PvP phase/death restrictions outside that profile. Preserve the current client feel numerically first; make the authoritative server produce the same pre-collision target velocity for the same sanitized intent, then apply independent server policy scales. This should reduce future reconciliation error without changing offline movement feel.

### PROPOSED_CHANGE
Benchmark three candidates before implementation:
A. Change only server `BASE_SPEED 320 -> 220`. Lowest code cost, but likely insufficient because it does not reproduce the client's nonlinear analog/gait mapping.
B. Copy the client curve into server code. Better behavior but still leaves two sources of truth and future drift.
C. Preferred if module compatibility is clean: extract only pure movement-profile data/functions into an owner-neutral shared module (or canonical data profile with thin browser/Node adapters). Client `engine-ac.js` and server `pvp-authority.js` consume the same profile. The shared layer may own magnitude-to-speed-cap/target-speed mapping only; it must NOT own input parsing, collision, stride, facing, camera, animation, PvP phase rules, death/respawn restrictions or server authority.

Do not introduce a new engine or wrapper. If a dual-runtime shared module increases boot/build complexity, prefer canonical data + parity tests over forced runtime sharing.

### DO_NOT_ASSUME
- Do not assume the server's `320` is wrong merely because it differs. Measure intended/current traces first.
- Do not assume matching base constants alone gives parity.
- Do not assume client and server receive identically normalized analog input; compare sanitized intent contracts first.
- Do not move server-only phase/death restrictions into client/shared profile.
- Do not claim this fixes network rubberbanding until an online reconciliation trace is measured.
- Do not alter current client feel, collider, camera, stride cadence or avatar presentation as part of this pass.

### RISKS
- Browser and Node module-system incompatibility could turn a small parity fix into boot complexity.
- Moving too much logic into a shared module could blur Foundation ownership.
- If the server intentionally used `320` to compensate for a different input contract, blindly adopting the client curve could slow authoritative movement.
- Shared numbers do not guarantee deterministic collision/order/tick behavior.
- Changing server movement semantics can affect anti-cheat/validation tolerances, PvP spacing, dash ranges relative to run speed and existing network tests.
