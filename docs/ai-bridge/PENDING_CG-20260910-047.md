PROBLEM
After stationary cast framing ends, an immediate strafe opposite the cast aim inherited the normal action-framing decay (9). The stale cast-side camera offset therefore remained longer than desired while movement look-ahead had already begun moving in the opposite direction.

CONFIRMED_IN_GEMINI

The stationary action lead is 28 screen px; normal action framing decay is 9; dodge release already uses decay 22. engine-a processInput owns legacy key/touch normalization and rewrites input.normX/normY every simulation frame, so runtime tests must drive the input state that processInput consumes rather than assign normX directly.

EXTERNAL_EVIDENCE
No external research was required for this bounded owner-local feel gap. Evidence came from the current repository, deterministic 60/90/120 instrumentation, Chromium mobile-landscape/desktop execution, screenshots and GitHub Actions artifacts.

HYPOTHESIS
When residual action framing points against a real movement intent, accelerate only the residual presentation-layer release. Do not change player movement, collision, cast timing, damage, aim authority, camera dead-zone or normal stationary framing.

PROPOSED_CHANGE
Winner: keep PVP_ACTION_STRAFE_RELEASE_DECAY=22 when movement direction has a dot product below -0.15 against the remembered stationary-action aim and action windup/active is over. Preserve normal decay 9 otherwise and dodge release 22 as already validated.

Do not infer that direct input.normX assignment reproduces gameplay; processInput overwrites it. During Fireball recovery the LIVE movement pipeline intentionally scales the resolved input magnitude (observed approximately -0.78 for held LEFT), so a judge that requires -1 during recovery is invalid. Do not increase movement speed as part of this camera fix.
