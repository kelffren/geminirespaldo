### PROBLEM

The local player now owns update-side visual locomotion in `engine-ac.js`, but simulated players/NPC-like actors without `_visualMotion` still fall back to `engine-ab.js::legacyMovingOf()` during rendering. That fallback is not read-only: every `renderAvatar()` call can mutate `_lx`, `_ly`, `_mdx`, `_mdy` and `_walkHold`. Because the current world has multiple render/depth wrappers capable of redrawing actors in the same RAF, the number of render passes can change the NPC locomotion state even when the NPC simulation trace is identical.

This is a different issue from CG-20260903-001. CG-001 concerns duplicated render ownership/draw work. CG-002 concerns a gameplay-presentation state machine being advanced/decremented by those draws. It means adding an occluder or another actor pass can alter how long an NPC appears to keep walking after stopping.

### CONFIRMED_IN_GEMINI

At base commit `33fc28a13d111a3ee12e2b081a148f2cf0cc738c` / visible build V6.10:

1. `engine-a.js::gameLoop()` executes `processInput(); updateMovement(dt); updateCamera(dt); updateSimulation(dt); render();` once per `requestAnimationFrame` callback, with `dt` derived from the RAF timestamp and clamped to 0.1 s.
2. `engine-a.js::updateSimulation(dt)` moves each simulated player toward its target at approximately `80 * dt` world px per update. Their world motion is therefore update/delta driven.
3. Local Kelo differs: `engine-ac.js` creates `_visualMotion` and advances local `stridePhase` from actual world displacement on the update side.
4. `engine-ab.js::motionOf(p)` uses `_visualMotion` only when one already exists. Otherwise it calls `legacyMovingOf(p)`.
5. `legacyMovingOf(p)` is called from the render path and mutates actor state. It writes `p._lx`, `p._ly`, `p._mdx`, `p._mdy` and `p._walkHold`.
6. When legacy motion is detected, `_walkHold` is set to the integer `10`; when movement/target conditions no longer qualify, `legacyMovingOf()` decrements `_walkHold` by one per invocation, not by elapsed seconds or simulated distance.
7. `stepCol()` for these legacy actors uses `Math.floor(Date.now() / 130) % 4`, so pose cadence is wall-clock based while movement-hold lifetime is render-invocation based. The two parts of the same NPC visual state therefore use different clocks.
8. A legacy actor with one `renderAvatar()` invocation per RAF can retain `_walkHold=10` for roughly 10 presented frames after the stop condition becomes false: ~166.7 ms at 60 Hz, ~111.1 ms at 90 Hz, ~83.3 ms at 120 Hz.
9. If the same actor is rendered 2 or 3 times in a RAF by depth/occlusion composition, `_walkHold` can be decremented 2 or 3 times in that same presented frame. Approximate hold duration can then shrink toward ~83/56 ms at 60 Hz, ~56/37 ms at 90 Hz, or ~42/28 ms at 120 Hz, depending on actual pass count and overlap state.
10. Current `plaza-depth.js`, `plaza-nature.js` and `gardens-landmark.js` are exactly the class of environment systems that can create additional actor rendering passes. CG-20260903-001 already identified the growing wrapper/multipass architecture; this entry identifies a concrete state-mutation consequence of that architecture.
11. The resulting problem is not merely performance. Two otherwise identical NPC simulation traces can end with different visible locomotion-hold durations if their render pass count differs by location/occlusion state.
12. `ENGINE_MAP.md` is still stale versus the live runtime and labels old ownership; current `engine-ab.js` source is the authority for this fallback path.

### EXTERNAL_EVIDENCE

1. MDN `requestAnimationFrame` documentation states that callback frequency generally follows display refresh rate, including common 60/75/120/144 Hz displays, and explicitly warns that animation progression should use timestamp/time rather than callback count because otherwise animation speed changes on high-refresh displays: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame
2. Epic/Unreal Engine 5.8 Distance Matching documentation describes advancing locomotion animation from distance traveled and matching animation playback to in-game motion specifically to reduce foot sliding. For cycle locomotion, Epic also documents matching play rate to movement speed: https://dev.epicgames.com/documentation/en-us/unreal-engine/distance-matching-in-unreal-engine and https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/AnimationLocomotionLibraryRuntim-/UAnimDistanceMatchingLibrary/SetPlayrateToMat-
3. Unreal's `AdvanceTimeByDistanceMatching` API explicitly advances the sequence by distance traveled since the previous animation update, reinforcing update-side locomotion progression rather than render-call progression: https://dev.epicgames.com/documentation/en-us/unreal-engine/BlueprintAPI/DistanceMatching/AdvanceTimebyDistanceMatching
4. GitHub issue SardineFish/raindrop-fx #17 documents a real web-animation bug where a fixed per-frame progression made animation speed depend on refresh rate; it is not Kelo's code, but it supports treating frame-count lifetimes as refresh-sensitive: https://github.com/SardineFish/raindrop-fx/issues/17
5. Community engine-design discussion strongly favors render being free of state mutation when possible because render and update may execute at different rates or multiple times; this is community guidance, not a normative spec: https://www.reddit.com/r/gameenginedevs/comments/1ep07bb/
6. Community counterevidence: a tiny game can safely combine update/render when one render call is guaranteed per simulation step. Kelo no longer has that guarantee because authored depth systems can redraw the same actor multiple times inside one RAF. Therefore the issue is the combination of mutable render fallback + variable render multiplicity, not merely that code lives inside a function named render.

### HYPOTHESIS

NPC visual locomotion should become update-owned just like local Kelo. Rendering should consume an already-resolved immutable visual snapshot for the actor during that RAF. At minimum, `_walkHold` must be expressed in elapsed time or distance on the update side, not decremented by `renderAvatar()` calls. Ideally simulated players get a compact `_visualMotion` state containing last world position, travel vector/facing, on/off state, gait/phase and optional stop timer. Then every duplicate render of the actor within the same RAF reads the same state and cannot alter it.

This should make NPC movement presentation invariant to refresh rate and depth-pass count, and it creates a safer foundation for scaling all characters, adding shadows/aura, and eventually using the same 8-WALK/8-RUN atlas contract across local and remote actors.

### PROPOSED_CHANGE

Do not refactor all rendering first. Use the smallest measurable sequence:

P1 — Instrument current legacy mutation without changing output.
- Add `frameId`/`simulationTickId` telemetry.
- For each actor, count `renderAvatarCallsThisRAF`, `legacyMovingOfCallsThisRAF`, `_walkHoldBefore/After`, target distance, world distance moved and resulting displayed column.
- Record pass tag if available (`base`, plaza tree/fountain, gardens fountain, aura, etc.).

P2 — Reproduce pass-count dependence.
- Put a simulated player in a simple 1-draw location and in a known multi-pass occlusion location.
- Give both the same deterministic world trace and stop event.
- No visual change yet.

P3 — Introduce update-side visual state for simulated players only.
- During `updateSimulation(dt)`, after each bot world-position update, update a bot visual state from actual displacement and elapsed time.
- The first implementation does NOT need a new atlas or sophisticated gait. It only needs to reproduce current direction/on/off behavior while removing render-side mutation.
- `renderAvatar()` becomes read-only for actors with this state.

P4 — Preserve legacy fallback only for truly unmanaged external actors if necessary.
- If a network/temporary actor still lacks update ownership, keep fallback behind an explicit legacy path, but do not let normal simulated players use it.
- Do not delete legacy code until call telemetry proves no required actor depends on it.

P5 — After invariance is proven, align NPC stride semantics with local Kelo.
- Prefer actual-distance progression so a slower/faster NPC does not treadmill at the same 130 ms frame cadence.
- This is a later visual-tuning step; do not combine it with P3 if that would prevent same-output verification.

### DO_NOT_ASSUME

- Do not assume every `renderAvatar()` call decrements `_walkHold`; while a bot is still far from its target, `toTarget > 14` can reset the hold to 10. Reproduce the final stop/near-target period where the decrement path actually occurs.
- Do not assume current multipass counts from prior commits remain exact; instrument current main because environment wrappers are evolving.
- Do not assume `Date.now()/130` itself is refresh-rate dependent; it is wall-clock based. The problematic refresh/pass dependence is `_walkHold` and the render-side state mutation. The fixed 130 ms cadence has a separate speed-matching problem, but that should be measured later.
- Do not change NPC world speed, target selection, collider/radius, camera, local-player locomotion or depth behavior in P1-P3.
- Do not replace all actor animation systems in one commit.
- Do not claim a visible bug from code inspection alone; measure the same deterministic stop trace and render pass count.

### EXPERIMENT

Baseline trace for one simulated player:
1. Freeze random target changes and provide a deterministic straight RIGHT travel segment at the existing 80 px/s.
2. Stop the actor at an exact target and hold world position for 500 ms.
3. Repeat in a location/pass configuration producing one actor draw per RAF and in a known multi-pass depth location.
4. Run/replay dt sequences approximating 60, 90 and 120 Hz.
5. Log each simulation update and every renderAvatar/legacyMovingOf invocation with `rafId`, `simulationTickId`, actor id, position, target distance, `_walkHold`, motion on/off and displayed frame.
6. Baseline expectation if the current fallback is active: stop-hold duration in milliseconds decreases as RAF frequency or render calls per RAF increase.
7. Candidate P3: update visual state once per simulation update, then rerun the identical world trace and identical render-pass topology.
8. Require the candidate's visible on/off stop timing and chosen pose to remain invariant when the actor is rendered once, twice or three times during the same RAF.
9. Repeat with actor offscreen/onscreen boundaries and representative mobile/desktop viewports to ensure culling/depth changes do not mutate locomotion state.

### RISKS

- Moving NPC visual-state ownership into `updateSimulation()` can alter the exact legacy look even if world motion is unchanged; first reproduce current direction/on/off semantics before improving cadence.
- Simulated players currently choose random targets. Deterministic testing must temporarily control that randomness without shipping deterministic behavior accidentally.
- Some actors may be created by networking or other systems and not pass through the same updateSimulation loop; keep a narrow fallback until actor ownership is mapped.
- If multipass rendering is later removed by CG-001 work, this mutation bug becomes less visible but still remains refresh-rate dependent and architecturally unsafe.
- Updating all NPC stride by distance immediately could expose limitations of the current 4-frame sheet; separate state-purity work from art-quality work.
