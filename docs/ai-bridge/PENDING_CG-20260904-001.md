### PROBLEM
The production hero renderer anchors the body to `footY = p.y + 10`, but it does not draw a dedicated contact/blob shadow for the actor. The late Armor Aura wrapper draws a ring near the ground, but that ring is gameplay/VFX feedback: it exists only when aura rank > 0, pulses, changes radius/alpha by rank, and is derived from `p.radius`. It therefore cannot serve as a stable grounding cue for locomotion, foot planting, avatar scale, or characters with Aura 0.

This matters most during lateral motion. A small, stable contact shadow can provide a fixed ground reference while the body changes pose, leans or bobs. Without that independent reference, future bob/lean/scale work risks making the character look like it floats even when stride timing is correct.

### CONFIRMED_IN_GEMINI
- `engine-ab.js` production body uses a visual foot anchor of `footY = p.y + 10` and draws the 48-world-px lateral body above that anchor. No dedicated contact-shadow draw exists in this renderer.
- `engine-ac.js` owns movement/stride state but publishes no ground-contact/shadow presentation metric.
- `armor-aura.js` draws `drawRing()` only for aura rank > 0. Its center is `p.y + (p.radius||20)*0.72`, i.e. with the current radius 20 it is approximately `p.y + 14.4`, about 4.4 world px below the hero renderer's current `footY`. Its radius, pulse, alpha and second ring all vary with Aura rank/time. `drawBodyGlow` and particles are also rank-driven. Thus Aura is not a neutral contact shadow.
- `docs/VISUAL_DIRECTION_MEMORY.md` explicitly lists useful shadows, a `shadows` asset family and reusable shadow tiles as part of the visual quality direction.
- Current `index.html` is V6.20 and now loads `performance-governor.js` after Aura/illumination; no current production code inspected here converts Aura into a contact shadow.

### EXTERNAL_EVIDENCE
- Godot's official 2D lighting/shadow documentation treats shadows as a dedicated visual/depth system rather than collider geometry; shadow receivers/casters and sprite presentation are separate concepts.
- PixiJS documents anchor as a normalized, size-independent presentation origin, supporting a stable bottom/foot anchor when texture size changes.
- Community top-down 2D practice commonly uses a separate low-alpha blob/contact shadow, positioned at a named bottom-of-sprite/foot point and rendered beneath the character. This is cheap and predictable compared with duplicating/dynamically warping the whole character.
- Counterevidence: elaborate dynamic projected shadows can cost FPS or visually fight pixel art. Therefore this proposal is intentionally a simple contact shadow first, not real-time silhouette projection or light-dependent shadow casting.

### HYPOTHESIS
A small, low-alpha, non-pulsing contact shadow anchored to the actor's presentation `footRoot` will make lateral movement, stops and reversals look more planted, especially once the avatar is 1.15x–1.25x and gains bob/lean. It should improve grounding without changing physics, stride, depth root, camera or Aura semantics.

### PROPOSED_CHANGE
Do not implement blindly. Benchmark a presentation-only `contactShadow` layer with these rules:
1. Anchor to the same explicit `footRoot` used by body/depth work, not `p.radius`.
2. Render behind the body and below front Aura/VFX; keep it independent from Aura rank.
3. Start with a simple ellipse/blob in Canvas2D or a tiny authored shadow sprite. No blur/filter in baseline candidate.
4. Shadow width may follow `presentationScale`/visual body width, but physics collider remains `radius=20`.
5. Keep center stable during normal walk/run. If bob is later added, body may bob while shadow stays on the ground; only scale/alpha should change if a deliberate jump/airborne state exists.
6. Do not let depth redraws multiply alpha; contact shadow should contribute once to the final actor composite per snapshot.

Candidate A: current no-shadow baseline.
Candidate B: fixed low-alpha ellipse anchored at footRoot.
Candidate C: small authored pixel-art blob shadow anchored at footRoot if B looks too vector/soft beside the sprite.

### DO_NOT_ASSUME
- Do not assume Aura ring can simply be recolored and reused; it has rank, pulse, radius and front/back semantics.
- Do not assume larger avatar means larger collider.
- Do not tie contact shadow center to `p.radius` if `footRoot/depthRoot` becomes explicit.
- Do not add blur, dynamic light direction, silhouette projection, normal maps or WebGL filters in the first experiment.
- Do not refactor all render wrappers in the same change.

### EXPERIMENT
Baseline -> candidate -> same trace -> measurement.

1. Freeze camera and use open ground first. Aura rank 0 to isolate grounding.
2. Run mirrored traces: idle -> RIGHT walk -> stop -> RIGHT run -> hard LEFT reversal -> stop, then LEFT -> RIGHT.
3. Test 60/90/120 Hz-equivalent runs with the same world trajectory and stride state.
4. Capture 1.00x body, then 1.15x and 1.25x presentation scale with collider unchanged.
5. Repeat near Plaza fountain and Gardens landmark to ensure shadow depth/composite behavior stays correct.
6. Stress 1/10/25/50 visible actors; compare ellipse vs authored blob if both are viable.
7. If no live measurement harness is available, implement only instrumentation/design and leave production unchanged.

Instrumentation should record: `footRootWorldX/Y`, `shadowCenterWorldX/Y`, projected foot/shadow CSS position, body visual bounds, presentationScale, renderAvatarCallsPerActorPerRAF, contactShadowDrawsPerActorPerRAF, frameCpuMsP95/P99.

### DECIDING_METRICS
- `shadowFootRootOffsetWorldPx`: target stable and authored; once chosen, variance <= 0.25 world px during flat-ground lateral movement.
- `shadowFootRootOffsetCssPxP95`: no refresh-rate-dependent drift.
- `contactShadowDrawsPerActorPerRAF`: one final visual contribution per actor snapshot.
- `shadowAlphaVarianceAtConstantState`: approximately zero; no Aura-style pulse.
- `plantedFootSlipCssPxP95`: should improve or remain neutral versus baseline when judged on contact frames.
- `groundingPreferenceBlindAorB`: candidate should win human visual comparison without harming readability.
- `frameCpuMsP95/P99`: no material regression; define acceptance from baseline device measurements, not guessed milliseconds.
- Invariants: world trace identical, camera trace identical, collider=20, collision outcomes identical, stridePhase identical.

### RISKS
- A generic ellipse may look too smooth/vector-like beside crisp pixel art.
- Too dark/wide a blob can make the sprite look glued to the floor or add clutter with 25–50 actors.
- Drawing it inside every depth redraw can accidentally darken it multiple times, repeating the Aura compositing problem identified earlier.
- If anchored to the wrong Y, the shadow can amplify foot sliding rather than hide it.
- Scaling shadow linearly with avatar size may be visually excessive; width/alpha must be benchmarked separately.
