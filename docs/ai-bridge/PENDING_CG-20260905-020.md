### PROBLEM
The current movement code already avoids frame-count-driven stride and current DIRECT release does not justify a stop-ownership change. The next unresolved premium lateral defects are more specific: (1) left/right reversal can preserve the same frame index while the mirrored pose changes the apparent support side instantly; (2) the live zoom chain currently contains conflicting ownership that can reintroduce fractional device-space scaling after an earlier module deliberately quantizes zoom for pixel-art stability; and (3) increasing avatar scale from 1.15x to 1.20x before measuring sampling stability risks blaming animation or sprite art for a camera/scale sampling artifact.

The important new code finding is the zoom conflict. `engine-h.js` deliberately computes `pixelPerfectZoom(target)` as an integer physical scale divided by active DPR and sets `CONFIG.roundPixels=true`. However, later-loaded `engine-z.js` recomputes `CONFIG.zoom = screenW / (targetTiles * 32)` clamped to 1.05..1.45 and reapplies it on resize. For common viewport widths this is fractional and therefore overrides the earlier integer-physical-scale policy. `engine-t.js` also clamps zoom before `engine-z`, but `engine-z` is later and wins. This creates three modules participating in zoom ownership.

### CONFIRMED_IN_GEMINI
- Live `main` at this round's source-of-truth check is `51056c703e4898422713e2c9265085675f36f710`.
- `index.html` currently loads `engine-h.js`, then later `engine-t.js`, then later `engine-z.js`, followed by `engine-ab.js`, `engine-ac.js`, and `engine-ah.js`. Therefore the last zoom assignment/resizer in `engine-z.js` has live precedence over the earlier default zoom decisions.
- `engine-h.js` uses active DPR (capped by the mobile performance contract) and `pixelPerfectZoom(target) = round(target * dpr) / dpr`, sets `CONFIG.roundPixels=true`, creates a DPR backing store, and disables canvas image smoothing.
- `engine-z.js` later computes target framing from 11 tiles on screens below 500 CSS px and 14 otherwise, then sets `CONFIG.zoom = clamp(screenW / (targetTiles * 32), 1.05, 1.45)` and reapplies on resize. It does not quantize to physical pixel multiples.
- `engine-t.js` clamps zoom to <=1.05 at its own load point, but it is not final authority because `engine-z.js` follows it.
- `engine-ac.js` advances lateral stride from real world distance (`lastStepDistancePx / cycleWorldPx`) rather than render count. That remains the correct baseline for 60/90/120 Hz independence.
- `engine-ac.js` detects lateral reversals and records frame continuity, accidental idle, and >1-frame jumps, but it does not measure visual support-point continuity after the renderer mirrors the same frame.
- `engine-ab.js` renders right/left from the same lateral row 2, mirroring the canvas horizontally for left. It already computes per-frame bottom-band contact evidence including `supportCentroidX`, `supportWidthPx`, and `lowestOpaqueY`.
- Because a mirrored frame negates its horizontal support offset relative to frame center, preserving the same frame index can still cause an apparent support point jump even when `reversalFrameJumpCount===0`.
- `engine-ab.js` already separates visual presentation from physics: `AVATAR_VISUAL_SCALE=1.15`, collider remains `p.radius`, foot root remains `p.y+10`, and depth/shadow/nameplate anchors derive from that presentation contract. This makes a later 1.20x A/B feasible without changing collision.

- `scripts/live-hero-audit.mjs` already verifies contact evidence, 1.15x visual-scale/collider invariants, RIGHT→LEFT movement, diagonal movement, release plant, reversal count, no accidental idle and no >1-frame jump on mobile DPR2 and desktop DPR1. It does not currently record zoom/DPR physical scale, screen-space edge stability, or support-centroid discontinuity across reversal.

### EXTERNAL_EVIDENCE
1. MDN `requestAnimationFrame()` states callback frequency generally matches display refresh and explicitly warns to advance animation using elapsed time/timestamps so behavior does not speed up on high-refresh screens. This supports retaining distance/dt-based locomotion rather than frame-count cadence. https://developer.mozilla.org/en-US/docs/Web/API/window/requestAnimationFrame
2. MDN `imageSmoothingEnabled` confirms that smoothing controls scaled image filtering and that disabling it keeps pixel-art pixels sharp when enlarged. Counterpoint: the documentation's clearest guarantee is enlargement; it does not prove that arbitrary fractional down/up sampling at Kelo's current source-to-screen ratio will be visually stable. https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
3. Godot issue #86634 documents visible 2D player/screen jitter when camera smoothing is combined with fractional scale. This is not Kelo-specific proof, but it is strong cross-engine evidence that fractional camera/render scale can manifest as motion instability. https://github.com/godotengine/godot/issues/86634
4. Godot issue #76457 discusses pixel-art scaling that looks acceptable until movement/zoom and references sub-pixel-aware filtering approaches. This is counterevidence against assuming nearest-neighbor plus integer-rounded sprite coordinates alone solves moving pixel stability. https://github.com/godotengine/godot/issues/76457
5. Community reports in r/godot describe a recurring tradeoff: snapping everything can itself look jittery during smooth/diagonal movement, while keeping motion smooth and snapping only stable/static presentation can reduce stop shimmer. Another thread reports that nearest filtering plus non-integer scale can still produce jagged/uneven pixels. These are community observations, not authoritative engine rules.

### HYPOTHESIS
H1 — The late `engine-z.js` fractional zoom override is a measurable contributor to lateral sprite shimmer/uneven pixel cadence on some mobile/desktop DPR combinations. Quantizing only the final zoom to an integer physical scale, while leaving player physics and float camera motion unchanged, may improve visual stability with less risk than snapping the camera or player.

H2 — Current reversal metrics are insufficient. A same-frame RIGHT→LEFT mirror can cause a support-point displacement approximately equal to twice the frame's horizontal support offset from frame center. Measuring this with existing `lateralContactFrames[].supportCentroidX` can reveal whether the perceived weight transfer problem is real before inventing a 50–80 ms settle.

H3 — If H1 is stabilized first and H2 is measured, 1.20x remains the next low-risk visual-scale candidate because collider/foot/depth/nameplate contracts are already separate. Scale must not be bundled with a zoom or reversal behavior change.

### PROPOSED_CHANGE
Do not modify production locomotion or scale in this research round.

Phase A — extend instrumentation:

Phase B — zoom A/B only:
- Baseline: current `engine-z` width-derived fractional zoom.
- Candidate: preserve the same target framing formula, then quantize the resulting zoom to a physically integer scale using current DPR, e.g. `round(targetZoom*dpr)/dpr`, choosing floor/round only after comparing field-of-view deviation.
- Keep float camera position, camera damping/deadzone/look-ahead, player physics, stride phase and sprite draw code unchanged.
- Do NOT globally snap camera/player transforms in this experiment because external evidence shows snapping can create its own motion jitter.

Phase C — reversal decision:
- If support-jump metric and sequential video show a real pop, first test a contact-preserving frame/phase remap chosen from the four authored lateral frames using the measured support centroids.
- Only if remap fails or looks worse should the prior 50/65/80 ms presentation-only settle candidates be tested.
- Physical direction reversal remains immediate in all candidates.

Phase D — avatar scale A/B:
- After zoom/reversal baseline is settled, compare current 1.15x against 1.20x only.
- Keep collider radius, footRoot offset, camera, speed and collision unchanged.
- Let current presentation contract move visual top/nameplate naturally, then explicitly measure clipping, front-occlusion, aura/shadow anchoring and crowding.

### DECIDING_METRICS
Zoom/sampling:
- `physicalZoomIntegerError = abs(zoom*dpr - round(zoom*dpr))` baseline vs candidate;
- screen-space edge/raster-step variance at constant world velocity: lower is better without introducing visible stepping;
- camera/player world trajectories: exactly unchanged;
- field-of-view/tile-coverage deviation: target <=5% from current framing unless visual gain is compelling;
- p95 frame time regression <5%;
- no new console/network failures.

Reversal:
- physical reversal latency/displacement unchanged;
- accidental idle count 0;
- frame jump >1 count 0 unless an explicitly tested contact-preserving remap proves better;
- support-jump screen px baseline vs candidate: minimize, but validate with video because bottom-band centroid is a silhouette proxy rather than anatomical foot identity;
- no added visible-direction latency unless a timed candidate is explicitly being tested; if timed, <=80 ms ceiling.

Scale:
- collider radius delta 0;
- footRoot/depthRoot/shadowAnchor contract delta 0;
- nameplate/occlusion/clipping regressions 0 in test scenes;
- p95 frame-time regression <5%;
- no materially worse aliasing/shimmer at DPR1/2/3.

### RISKS
- Quantizing zoom changes framing slightly; at low DPR the nearest integer physical scale may be too coarse, so field-of-view deviation must be reported.
- Fractional zoom may not be the dominant source of visible shimmer on every device; do not ship the candidate if video/metrics show no meaningful gain.
- Hard pixel snapping could improve static crispness but worsen smooth lateral/diagonal motion; that is why this proposal quantizes scale first and leaves float camera motion alone.
- Bottom-band support centroid cannot identify anatomical left/right foot with certainty; use it as a measurable proxy combined with video.
- A support-preserving frame remap can disturb stride cadence even if it improves planting; distance-driven phase must resume cleanly afterward.
- 1.20x may mainly increase occlusion/nameplate crowding rather than GPU cost.
- Zoom ownership is spread across three wrappers/modules; refactoring ownership before proving behavior would make attribution harder.
