### PROBLEM
Kelo's modern renderer correctly uses authored per-frame foot anchors so every sprite frame is registered to the semantic footRoot. However the authored lateral anchor trajectories are very different between LEFT and RIGHT. Because Character Appearance repositions the whole 256x384 source frame by `footRoot - footAnchor * scale`, the destination rectangle itself shifts substantially across the four-frame cycle even when footRoot is perfectly stable. This may be legitimate foot locking if the anchor follows the intended support foot, but it can also create excessive torso/silhouette sway, unequal perceived speed, or frame-to-frame snapping if the selected anchor is not a stable locomotion root. The asymmetry is large enough to benchmark before adding procedural bob/lean or increasing avatar scale to 1.20x.

### CONFIRMED_IN_GEMINI
1. `src/characters/character-appearance.js` defines LEFT footX `[132,108,91,77]`, footY `[344,346,347,348]`, bodyHeight 302; RIGHT footX `[145,135,121,113]`, footY `[384,384,384,384]`, bodyHeight 369.
2. Rendering uses `scale = targetBodyHeight / bodyHeight`, then `dx = round(footRootX - footX[col] * scale)` and `dy = round(footRootY - footY[col] * scale)`. Therefore per-frame anchor changes translate the entire destination rectangle relative to the actor root.
3. At the current ~93 world-px target body height, LEFT scale is ~0.30795 and its footX range of 55 source px produces ~16.94 world px of destination-origin compensation across the cycle. RIGHT scale is ~0.25203 and its footX range of 32 source px produces ~8.06 world px. The raw lateral compensation envelope is therefore roughly 2.1x larger on LEFT than RIGHT.
4. LEFT footY changes by 4 source px (~1.23 world px at current scale); RIGHT footY is constant. So vertical registration policy is also direction-dependent even before any future bob is added.
5. `engine-ac.js` advances stride from resolved world distance and preserves shared stridePhase; this should remain unchanged. The issue is registration of authored frames around footRoot, not cadence or physics.
6. `engine-ab.js` already separates presentation footRoot/depthRoot from collider geometry. Do not solve this by moving actor.x/y or changing collider.
7. The code does not expose whether each footX value tracks the same anatomical foot, the currently planted support foot, or a manually chosen visual pivot. That semantic is the missing contract.
8. Because Character Appearance rounds destination geometry after applying the anchor offset, larger per-frame compensation can interact with CG-005 pixel-phase quantization and become more visible at fractional zoom/DPR.

### EXTERNAL_EVIDENCE
- Unity Root Motion documentation separates body/root transforms and explicitly offers a Feet-based root-height mode so transitions remain grounded around the feet; this supports treating the ground/root reference as a deliberate animation contract rather than an incidental sprite center: https://docs.unity3d.com/Manual/RootMotion.html
- Aseprite issue #1357 proposes per-frame pivot/tagged points specifically so frame-by-frame characters can share a stable root anchor while also exposing other attachment points such as feet/hands/head: https://github.com/aseprite/aseprite/issues/1357
- Godot issue #27328 requests per-frame SpriteFrames offsets because a single constant offset cannot correctly register animations whose authored frames need different origins: https://github.com/godotengine/godot/issues/27328
- Godot proposal #14824 (2026) argues that correct sprite pivot data is fundamental for Y-sorting and animation transforms, reinforcing that pivot/root metadata should be explicit and reusable: https://github.com/godotengine/godot-proposals/issues/14824
- Community evidence is mixed: developers commonly fix jitter by aligning all frames to a consistent bottom/root point, while others deliberately use per-frame offsets tied to a foot when the artwork requires it. That is counterevidence against replacing Kelo's current anchors with one constant pivot without measuring: https://www.reddit.com/r/godot/comments/1gcp4rp/

### HYPOTHESIS
The premium solution is not necessarily smaller anchor motion; it is a semantically correct, direction-consistent registration contract. If the current anchors represent the actual support-contact foot, their compensation should reduce support-foot slip and may be worth asymmetric body motion. If they are effectively hand-tuned visual pivots, LEFT's ~17 world-px origin travel may be overcompensating and causing visible sway. The benchmark should identify the support-foot centroid in each frame and compare it with the published anchor/root before changing any anchor values.

### PROPOSED_CHANGE
Do not modify production yet.
A. Baseline: current per-frame footX/footY arrays.
B. Instrumented baseline: preserve rendering exactly, but publish per-frame destination origin, source anchor, footRoot and visual silhouette/torso centroid measurements.
C. Support-foot-authored candidate: only if image inspection proves current anchors do not track the contacting foot, recalibrate anchors from the actual support foot for each frame/direction while keeping footRoot and stridePhase unchanged.
D. Stable-root candidate: only as a control, derive one conservative locomotion root per direction (or symmetric LEFT/RIGHT root policy) and measure whether body jitter improves at the cost of foot slip.
E. Do not add procedural bob/lean until A-D establish how much body displacement is already encoded by frame registration; otherwise procedural motion can double-count authored sway.

### DO_NOT_ASSUME
- Do not assume per-frame anchors are wrong because their numbers differ; differing offsets can be exactly what correct foot locking requires.
- Do not assume LEFT and RIGHT must have numerically mirrored anchors; the source artwork/bodyHeight differs substantially.
- Do not change physics, collider, camera, stridePhase or world speed to hide a registration problem.
- Do not use destination-rectangle origin alone as the visual quality metric; inspect support-foot and torso/silhouette motion.
- Do not add another animation/root manager; keep KeloCharacterAppearance + KELO_AVATAR_PRESENTATION as owners.
- Do not introduce bob/lean in the same experiment.

Compare A against C/D only after B establishes a measurable problem. Repeat the winning registration policy at avatar visual scale 1.20x.

### RISKS
1. Replacing per-frame anchors with a stable pivot can make the body look smoother while making the feet skate; foot contact wins over cosmetic centroid smoothness.
2. Measuring the wrong anatomical foot can invalidate the benchmark when support changes between frames; annotate support/contact state explicitly.
3. LEFT/RIGHT source art may intentionally be asymmetric rather than mirrored; normalize measurements in rendered world/CSS space, not source pixels alone.
4. At 1.20x every anchor error and silhouette jump becomes more visible.
5. CG-005 rounding can alias small differences; keep the render quantization policy identical across candidates.
6. Future equipment/hair layers must inherit the same semantic root; do not calibrate only the naked base sprite if layered content changes the apparent torso centroid.
