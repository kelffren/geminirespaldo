### PROBLEM
CG-20260905-021 identified per-frame foot anchoring as the next high-value grounding experiment. Re-reading current main reveals an architectural issue underneath that experiment: Kelo now has two overlapping avatar rendering systems. `engine-ab.js` owns the player hero load/preprocess/contact audit/draw/nameplate path, while `src/characters/character-appearance.js` wraps `renderAvatar` later and independently owns non-player appearance loading, alpha cleanup, face/frame selection, per-frame foot anchors, draw transform, nameplate and audit. The player is registered in the appearance system but explicitly delegates back to the legacy hero renderer.

This duplication makes the planned 1.20x scale-up harder to validate because player and bot visual grounding use different source-anchor semantics. It also means future character PNGs risk accumulating bespoke renderer logic even though the project now has a generalized appearance layer.

### EXTERNAL_EVIDENCE
- Aseprite officially supports per-slice pivots and can export slice information to sprite-sheet JSON. This is directly relevant to Kelo because a foot/base pivot can be authored with the art instead of inferred or hardcoded in renderer code: https://www.aseprite.org/docs/slices/
- Aseprite animation frames have explicit per-frame duration, reinforcing that art metadata belongs with animation data rather than being hidden in unrelated movement timing code: https://www.aseprite.org/docs/sprite/ and https://www.aseprite.org/api/frame
- MDN confirms `CanvasRenderingContext2D.imageSmoothingEnabled=false` preserves hard pixel edges when scaling pixel art, but that flag alone does not solve transform-origin/contact consistency across frames: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
- MDN warns `requestAnimationFrame()` frequency follows display refresh and can commonly be 60/75/120/144 Hz; progression must use elapsed time. Kelo's distance-driven stride should therefore remain untouched while renderer-origin work is isolated: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame
- Godot issue #86634 and godot-docs issue #7774 document camera/pixel-art jitter under smoothing/fractional transforms, while issue #98764 shows that aggressive transform snapping can itself introduce jitter. These are counterevidence against solving grounding by globally snapping all simulation/render transforms: https://github.com/godotengine/godot/issues/86634 https://github.com/godotengine/godot-docs/issues/7774 https://github.com/godotengine/godot/issues/98764
- Community reports similarly show a tradeoff: snapping can make rest poses stable while creating visible stepwise motion during movement/diagonals. Treat these as anecdotal, not proof for Kelo, but they support isolating sprite-origin correction from camera/physics changes.

### HYPOTHESIS
H1 — The best next implementation target is not a new timing trick but a shared per-frame appearance-anchor contract. If the player and bots use the same `sourceFootAnchor -> semantic footRoot` transform, Kelo can improve foot planting and later scale characters without changing collision/camera/physics.

H2 — The player should eventually stop using a bespoke final draw path in `engine-ab.js`; however, directly flipping `delegateToLegacyHero` to false would be a blind refactor because the hero path has unique white-knockout/contact-audit behavior. First create a parity candidate and prove identical or improved output under the same trace.

H3 — Runtime silhouette-derived `supportCentroidX/lowestOpaqueY` should remain measurement evidence, not permanent artistic truth. The durable contract should accept authored per-frame pivot metadata. For current PNGs, validated hardcoded metadata is acceptable as an intermediate step; for future authored assets, Aseprite slice-pivot/JSON export or equivalent asset-side metadata should populate the contract.

H4 — Once source anchors are normalized, testing 1.15x -> 1.20x becomes a clean presentation-only experiment: anchor coordinates scale with the sprite, while footRoot/collider/camera remain invariant. If scale-up still looks ungrounded after that, the defect is less likely to be origin drift and can be investigated separately (pose art, cadence, reversal support, sampling).

### PROPOSED_CHANGE
Do not refactor production renderer in this research pass.

Phase A — add parity instrumentation to the existing live hero audit:
1. For each lateral frame 0..3 and both right/left facing, record the CURRENT hero draw destination rect and the projected visible contact position produced by `supportCentroidX/lowestOpaqueY`.
2. Add a pure function or audit-only candidate transform that maps a proposed source foot anchor to the existing `KELO_AVATAR_PRESENTATION.footRoot`, without changing the live draw.
3. Report delta between legacy draw and candidate in CSS pixels and physical pixels for mobile DPR2 and desktop DPR1.
4. Capture all four lateral frames plus RIGHT->LEFT and LEFT->RIGHT reversal screenshots/traces.

Phase B — define a small shared appearance anchor schema before renderer migration. Recommended fields per appearance/facing/frame: source frame rect, `footX`, `footY`, optional authored visual/body bounds, optional nameplate offset. Keep world-facing physics data out of this schema.

Phase C — implement player candidate behind an explicit query/debug flag, not as default:
1. Reuse hero preprocessing output or provide the processed hero canvas as an appearance runtime source.
2. Render `player_hero_v1` through the same source-foot-anchor transform used by crimson bot.
3. Keep `engine-ac` stride/frame output unchanged.
4. Keep `KELO_AVATAR_PRESENTATION`, collider, footRoot, depth, shadow and camera unchanged.
5. Compare baseline vs shared-renderer candidate using the exact same movement trace.

Phase D — only if parity/grounding improves and no regression appears, make the shared appearance path the player owner and reduce duplicated draw/nameplate/motion-fallback responsibilities in `engine-ab.js`. Preserve hero-specific preprocessing/audit as a source-preparation module if still needed.

Phase E — after shared anchor ownership is proven, run isolated 1.15x vs 1.20x visual scale A/B with no other behavior changes.

### DO_NOT_ASSUME
- Do not assume the bottom-band centroid equals the anatomical weight-bearing foot.
- Do not assume the crimson bot's numerical foot anchors can be reused for hero.PNG; each asset needs its own pivots.
- Do not remove `engine-ab.js` simply because responsibilities overlap; first preserve preprocessing, audits, presentation contract and fallback behavior.
- Do not alter `engine-ac.js` cadence/stride while testing anchor ownership.
- Do not enlarge collider or modify camera merely because visual scale increases.
- Do not globally snap camera/player transforms to integers as a substitute for correct sprite-origin mapping.
- Do not mark the shared renderer superior from static screenshots only; movement/reversal traces and frame-time/error checks are required.

### DECIDING_METRICS
For B to beat A:
- `visibleFootToFootRootErrorY`: median and max should materially decrease; target <= 0.75 CSS px median and <= 1.5 CSS px max if authored source anchor can support it.
- `visibleSupportJumpX` at frame changes/reversals: must not worsen; report p50/p95/max in CSS and physical pixels.
- `footRootDriftWorldPx`: exactly 0 from renderer changes.
- `colliderRadiusDelta`: exactly 0.
- `playerWorldTraceDelta` against baseline under identical inputs: within harness timing tolerance; renderer must not change simulation.
- no new accidental idle/frame jumps from existing movement audit.
- no new nameplate overlap, shadow detachment, depth/occlusion regression in screenshots.
- no JS/network errors.
- p95 frame time should not regress >5%; renderer consolidation should ideally be neutral or better.

For C (1.20x) to be accepted after B:
- same zero physics/footRoot drift requirements;
- no clipping at common viewport edges;
- nameplate remains readable and separated from sprite;
- occlusion/depth remains anchored to footRoot rather than top/bottom of enlarged art;
- sprite detail judged equal/better in motion, not only still frame;
- p95 frame time regression <=5% versus accepted 1.15x shared-renderer baseline.

### RISKS
- A silhouette-derived anchor can jump between left/right shoe or include coat pixels; hand validation is necessary.
- Migrating player into `character-appearance.js` too early can lose hero-specific white cleanup or audit semantics.
- Two active preprocessors could duplicate memory/canvas work if the shared runtime reloads hero.PNG instead of reusing the processed source.
- A shared renderer can become another monolith unless source preparation, appearance metadata and presentation geometry remain distinct responsibilities.
- 1.20x may expose downscale shimmer even with perfect foot anchoring; that would require a separate sampling experiment, not rollback of the anchor contract by default.
