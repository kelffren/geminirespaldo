### PROBLEM
Current layered landmark renderers decide whether an actor participates in the corrective actor redraw using `actor.radius || 20`, while the production PNG is much taller than that collider and is anchored above a foot root. This creates a geometric blind band below/front of a landmark: the actor's circle can be outside the `near/overlap` test even while the upper body (and nameplate) still overlaps the landmark's front layer. Because the landmark front layer is painted after the base render, an actor in that band is not redrawn and can therefore have its upper body painted over even though its feet/baseY classify it as being in front. Enlarging the avatar increases this blind band without changing collider 20.

This round does NOT claim an opaque-pixel artifact has been observed on Pages. The blind band is confirmed from current rectangles/order; actual visible severity depends on alpha content in the front-layer PNG/SVG and must be measured.

### EXTERNAL_EVIDENCE
1. Unity 6 `Renderer.bounds` explicitly defines a world-space AABB fully enclosing the rendered object, while `Collider2D.bounds` separately defines the collider's world-space area. This is direct precedent for keeping visual/render bounds and collision bounds as different contracts rather than reusing the collider as a render broadphase. Sources: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Renderer-bounds.html and https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Collider2D-bounds.html
2. Godot's TileMap/TileSet documentation exposes `Y Sort Origin` separately from collision and texture origin, supporting a semantic base/feet point for top-down draw order that is independent of the collider. Source: https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html
3. PixiJS's official Culler uses renderer/screen bounds to decide whether a visual object intersects the viewport. It is disabled by default because bounds checks also cost CPU. This is useful counterevidence: visual bounds are the correct kind of information for visual broadphase, but they should be cheap/precomputed and measured rather than recomputed expensively for every object every frame. Source: https://pixijs.com/8.x/guides/components/application/culler-plugin
4. Godot issue #72322 documents incorrect/ambiguous Y-sort behavior with large sprites/tiles, reinforcing that larger visual extents expose sorting assumptions that can be hidden at small scale. Source: https://github.com/godotengine/godot/issues/72322
5. Community top-down practice commonly anchors Y-sort at character feet and offsets tall artwork above that root; a Godot discussion specifically describes a tall player with its scene/sprite origin at the feet and props with Y-sort origins near their base. Source: https://www.reddit.com/r/godot/comments/1gh58zx
6. Counterevidence: using the full visual AABB as the final depth key would be wrong. Tall crowns/hair should not move the actor's sort base. The proposed use of visual bounds here is only broadphase/intersection eligibility; final front/behind decision should still use foot/baseY semantics.

### HYPOTHESIS
The current occlusion system conflates two different questions:

A) `Could this actor's rendered pixels intersect this occluder?` — broadphase, which should use a visual envelope/bounds.
B) `Should the actor be in front or behind at the contact plane?` — depth decision, which should use footRoot/baseY.

Keeping collider radius for A makes the broadphase increasingly incomplete as Kelo becomes taller. The likely safe architecture is a lightweight actor `visualEnvelope` derived from the actual draw rectangle/pivot (not alpha per frame, and not collider), while preserving `footRootY` for B and collider radius 20 for physics.

### PROPOSED_CHANGE
P0 — Instrument only; no production visual change yet.
- For every actor/landmark pair in Plaza fountain, Gardens fountain and Plaza trees, log collider-overlap result, visual-envelope-overlap result, front/behind result, and whether the actor is redrawn after the front layer.
- Add a diagnostic overlay flag that outlines collider (circle), visual envelope (rect), footRoot, prop/landmark front destination and baseY.

P1 — Define a presentation-only actor envelope contract in/near the actual avatar renderer owner.
Candidate fields/functions:
- `footRootX = p.x`
- `footRootY = p.y + 10`
- `visualWidth = current draw width`
- `visualHeight = current draw height`
- `visualBounds = {left: footRootX-w/2, right: ..., top: footRootY-h, bottom: footRootY}`
- optional `nameplateBounds` tracked separately; do not force labels to share world occlusion policy.
Do NOT put these fields on the collider or change `radius`.

P2 — A/B only the broadphase gate.
A = current `radius||20` overlap gate.
B = actor visual-envelope rectangle against the landmark/prop visual/front rectangle (optionally with a small fixed padding).
Keep `actorInFront()/baseY` unchanged for final depth decision.

P3 — Test avatar scale ladder with identical world trace.
Evaluate current ~48x81 and visual-only 1.15x / 1.25x / 1.30x candidates while collider remains 20. Recompute visual envelope from draw size for each candidate; do not enlarge collision.

P4 — Nameplate policy as a separate decision.
Because `renderAvatar()` currently draws body + nameplate atomically, measure whether labels should:
- remain world-occluded with the body;
- always render in a final UI/nameplate pass;
- or use a hybrid fade/visibility policy.
Do not decide this solely from depth math; mobile legibility and clutter are product/UX concerns.

P5 — Only after B proves visually correct, consider consolidating duplicated overlap helpers (`overlapsFountain`, Gardens `overlaps`, Plaza Nature `overlapActor`) into one presentation-bounds helper. Do not refactor first. Baseline -> one gate change -> same trace -> remeasure.

### DO_NOT_ASSUME
- Do not treat the calculated 15/23/35/43px blind bands as measured opaque-pixel corruption. They are geometric regions where the current broadphase can miss a possible sprite/front-layer intersection.
- Do not derive visual envelope from collider radius.
- Do not derive collision from visual envelope.
- Do not use the top of the sprite as the Y-sort key; keep foot/baseY semantics.
- Do not assume full visual bounds must be recomputed from alpha every frame. Start from authored/draw-rectangle bounds for predictable cost.
- Do not change camera, stride, subpixel snap, WALK/RUN cadence, reversal or collider in the first A/B.
- Do not globally refactor the three render wrappers before measuring; CG-20260903-001 already covers wrapper consolidation.
- Do not make nameplate always-on-top without testing mobile readability/clutter and PvP information rules.

### RISKS
- Draw-rectangle visual bounds include transparent padding, so they can over-trigger redraws. If cost/pop becomes material, use a stable authored per-atlas envelope inset, not per-frame alpha scanning.
- A giant visual envelope can overlap multiple nearby props, increasing redraws. Instrument first and keep only local occluders.
- Nameplate and body may need different layer policies; keeping them atomic can preserve current behavior but limit readability.
- A front-layer PNG may contain transparent regions in the mathematically overlapping area, so geometry-only tests can overestimate visible severity. Pixel-diff/video must decide.
- Consolidating wrappers too early would confound this narrow broadphase test with renderer architecture changes.
