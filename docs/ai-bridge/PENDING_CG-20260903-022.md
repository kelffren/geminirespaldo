### PROBLEM

The current authored landmark depth wrappers decide whether an actor participates in back/actor/front recomposition using the actor physics radius (`actor.radius || 20`), while the production PNG body is much taller/wider than that collider and its visible foot is intentionally drawn at `p.y + 10`. The wrappers then sort actors and decide front/behind using `p.y`, not the visible foot/depth root. This couples three independent concepts: physics collider, visual overlap bounds, and depth-sort root. The coupling can already produce edge cases at the current avatar size and becomes more likely when the user increases Kelo to 1.15–1.25x.

### CONFIRMED_IN_GEMINI

At `main` baseline `574e4ab99059eeb8877ecae418938b84514ad5ab` / `Kelo World — V6.19`:

1. `engine-a.js` still defines `localPlayer.radius = 20`; this is the physics collider and must remain unchanged for presentation-only scaling experiments.
2. `engine-ab.js` is the production hero renderer and draws the side sprite at `dw=48` world px and `dh = round(54*(FH/FW))`. With the current declared sheet frame geometry `FW=256`, `FH=384`, this is ~48×81 world px.
3. `engine-ab.js` defines the visible foot baseline as `footY = p.y + 10`; side visual bounds are therefore approximately x=[p.x-24,p.x+24], y=[p.y-71,p.y+10] before any future scale increase.
4. `plaza-depth.js::overlapsFountain(actor)` uses only `actor.radius || 20` plus hardcoded landmark margins to determine whether an actor is included in depth recomposition. It does not use sprite width/height, footY, opaque bounds, or future presentationScale.
5. `plaza-depth.js::actorInFront(actor)` compares `(actor.y||0) > FOUNTAIN.baseY`; actors are sorted with `(a.y||0)-(b.y||0)`.
6. `gardens-landmark.js::overlaps(p)` also uses only `p.radius || 20`; `inFront(p)` compares `p.y` to `landmark.baseY`; near actors are sorted by `p.y`.
7. Both wrappers call base render first, then add their authored back/front layers and selectively redraw only actors considered `near`. Therefore a sprite can visually overlap a landmark while its collider-derived overlap test says it is not near, allowing the late landmark layer to cover pixels that should have participated in the composite.
8. The risk grows asymmetrically with avatar scaling because body height extends mostly upward from the foot root. A 1.25x side body would be roughly 60×101 world px if scaled proportionally while collider remains 20.
9. Example from below the Plaza fountain: current body top extends ~71 px above p.y, while a 1.25x body would extend ~91 px above p.y. The collider-based eligibility below the fountain extends only by collider+hardcoded margin; there can therefore be a band where the upper body still visually overlaps the fountain/front art but the actor is no longer selected for recomposition. Exact live band depends on final scaled dimensions and opaque pixels, so it must be measured rather than assumed from the rectangular estimate.
10. The depth threshold itself is offset from the visible foot by 10 world px (`p.y` vs `footY=p.y+10`). That can make front/behind transitions occur before the visible ground-contact point crosses the landmark base line.
11. This is separate from CG-015/016: even if `renderAvatar()` becomes render-pure and Aura redraw becomes idempotent, the actor must first be selected for the correct depth pass. It is also separate from collider scaling: the collider should remain 20.

### EXTERNAL_EVIDENCE

1. Phaser official Game Object documentation separates origin, displayed/scaled bounds, and depth. It explicitly provides scaled bounds formulas based on displayWidth/displayHeight + origin, and separately allows depth to be tied to y. This supports independent `visualBounds` and `depthRootY` contracts instead of reusing physics radius: https://docs.phaser.io/phaser/concepts/gameobjects and https://docs.phaser.io/phaser/concepts/gameobjects/components
2. PixiJS official sprite documentation treats anchor/pivot as presentation transforms and notes anchors remain stable when texture dimensions change. This supports a foot-root anchor that survives avatar scaling independently of collider size: https://pixijs.com/7.x/guides/components/sprites
3. Godot proposal #13428 documents a real top-down 2D pain point where Sprite2D's position/pivot used for Y sorting becomes inconvenient when the texture offset/presentation changes, reinforcing that sort root is a separate semantic from image geometry: https://github.com/godotengine/godot-proposals/issues/13428
4. Godot issue #69261 demonstrates that 2D y-sorting can fail when sprites/tilemaps do not share a compatible sorting structure, showing that correct visual overlap requires an explicit render-order contract, not just collision geometry: https://github.com/godotengine/godot/issues/69261
5. Community counterevidence: bottom-foot pivots/Y sorting solve many simple top-down overlaps but are not sufficient for every wide or multi-level object (stairs/bridges/wide blockers often need zones, layers, or custom rules). Therefore the proposal does not replace Plaza/Gardens authored front/back layers with generic y-sort; it only supplies those authored systems with correct visual bounds and depth root. Examples: https://www.reddit.com/r/gamedev/comments/nvazsy and https://www.reddit.com/r/gamedev/comments/13yaq56

### HYPOTHESIS

Kelo can be enlarged safely without changing collision if the engine explicitly separates:

- `physicsBounds` / collider: gameplay only, radius 20;
- `footRoot` / `depthRootY`: world contact and front/behind sorting;
- `visualBounds`: current displayed sprite footprint used for overlap/culling/recomposition eligibility;
- optional `opaqueBounds`: tighter art-derived bounds if rectangular visual bounds cause too many redraws.

For the current renderer, the minimal contract can be computed from the same values used to draw the sprite. At 1.00x this should preserve current physics while fixing missed depth participation near landmark edges; at 1.15/1.25x it should prevent the enlarged body from escaping the authored occlusion passes.

### PROPOSED_CHANGE

**P1 — Instrument baseline before behavior change**
- For Plaza and Gardens, log per actor: colliderBounds, calculated current sprite visualBounds, visible footRootY, depthRootY currently used, overlapFountain/overlaps result, and whether the actor's visual rectangle actually intersects the landmark front/back rectangle.
- Capture cases approaching each landmark from top, bottom, left and right.

**P2 — Add a presentation-bounds helper, without touching collider**
- Candidate API: `getActorPresentationMetrics(p)` returning `{footX, footY, depthY, left, right, top, bottom, width, height, scale}`.
- The helper should derive dimensions from the production renderer's actual side/front dimensions and future presentation scale, not `p.radius`.
- Do not mutate p.x/p.y/radius.

**P3 — Use visual bounds only for recomposition eligibility**
- Replace collider-radius overlap as the primary `near` selector with visualBounds-vs-landmarkBounds (plus a small measured safety margin if needed).
- Keep collision using radius 20.
- If rectangular visual bounds increase redraws too much, test opaqueBounds or a conservative body envelope rather than reverting to collider radius.

**P4 — Use foot/depth root for ordering**
- Compare current `p.y` threshold/sort to `depthY = footY` (currently p.y+10 for hero.PNG) while preserving authored landmark baseY.
- Do not assume +10 is final metadata; future atlas should publish a semantic footRoot per frame/row if necessary.

**P5 — Scale stress only after 1.00x baseline**
- Repeat exact traces at 1.15x and 1.25x presentation scale with collider still 20.
- Test Plaza and Gardens separately because their margins/baseY differ.

**P6 — Do not generalize authored occlusion away**
- Keep the existing back/front authored landmark architecture for complex objects.
- This round only repairs actor eligibility and depth-root semantics; it does not replace landmark-specific layering with global y-sort.

### DO_NOT_ASSUME

- Do not enlarge `actor.radius` to make overlap tests pass; that changes gameplay and violates the user's requirement.
- Do not assume the sprite's full rectangular draw bounds equal opaque body bounds; audit transparent padding/processed hero first.
- Do not assume `footY=p.y+10` is universally correct for all future rows/frames/actors.
- Do not change Plaza/Gardens baseY values in the same experiment.
- Do not refactor all depth wrappers at once before baseline traces exist.
- Do not interpret fewer depth artifacts from a screenshot as sufficient; test movement through the threshold and landmark edges.

### RISKS

- Full rectangular visual bounds can be conservative and increase actor redraw count around landmarks.
- If hero.PNG has substantial transparent padding, draw-rectangle bounds may overestimate meaningful overlap; opaque/body envelope may be preferable after measurement.
- Using footY for depth can expose existing landmark baseY tuning that was visually compensated around p.y; compare A/B before changing authored constants.
- Multiple actors with very large presentation bounds could increase Canvas2D redraw work; measure before shipping.
- Complex landmarks may need polygonal/zone-specific occlusion even after bounds are correct; this proposal is not a universal y-sort solution.
