### PROBLEM
The newest LIVE `main` hardened collision ownership and inside-AABB recovery. That is a good physics correction, but the lateral gait currently derives stride distance from the player's final world-position delta after the entire core movement/collision pass. This means a depenetration/recovery push is indistinguishable from locomotor travel to `engine-ac.js`.

A recovery push can therefore advance `strideDistancePx`, `stridePhase`, and the rendered source frame even when part—or in an overlap-recovery case most—of the world delta came from collision correction rather than a planted step. The current hero harness intentionally stays near spawn so environment collision differences do not dominate; it therefore does not test this boundary.

This round does NOT claim that visible popping already occurs in normal LIVE play. The code path that can contaminate gait distance is confirmed; perceptual severity and frequency require a controlled collision trace.

### CONFIRMED_IN_GEMINI
At BASE_COMMIT `b96c9325d8e247e3709dc3120ac1e3ba7181beee`:

1. `index.html` now loads `src/physics/collision-utils.js?v=1` before `engine-a.js?v=150`, so the new collision helper is part of the LIVE load order.
2. `engine-a.js::updateMovement(dt)` first applies intended X movement (`localPlayer.x += vx*dt`), then loops movement-blocking obstacles and adds `res.pushX`; it then applies intended Y movement and adds `res.pushY`; finally it clamps to world bounds.
3. `src/physics/collision-utils.js::resolveCircleAABB()` has a new `distSq===0` branch for a player center inside an AABB. It chooses the nearest side and returns a depenetration vector large enough to move the circle fully outside that side (`distance-to-side + radius`). This correction can be much larger than one normal locomotor frame.
4. `engine-ac.js` wraps core `updateMovement`. It snapshots no pre-collision locomotor delta. After `_move(dt)` returns, `updateVisualMotion()` computes `dx = p.x - v.lastX`, `dy = p.y - v.lastY`, `dist = hypot(dx,dy)` from the FINAL corrected world position.
5. If `dist > MIN_VISUAL_MOVE_PX`, that entire final distance becomes `lastStepDistancePx` and is added to `strideDistancePx`; `stridePhase += lastStepDistancePx / cycleWorldPx`; `frame = floor(stridePhase*4)%4`.
6. Therefore collision recovery, world-bound correction, and intended locomotion currently share one visual-distance channel. The gait cannot tell which portion of `dist` came from player-driven travel versus solver correction.
7. With the current walk cycle of 50 world px, an isolated 10 px correction advances phase by 0.20 cycle; 20 px advances 0.40 cycle. These are mathematical consequences of the current formula, not measurements of a real LIVE collision event.
8. A deep inside-AABB recovery can exceed those example values because the correction is `nearest-side distance + radius` (radius currently 20 for Kelo). The exact maximum depends on obstacle dimensions and spawn/ability geometry.
9. The current `scripts/live-hero-audit.mjs` says its short holds keep the run close to spawn so environment collision differences do not dominate the hero contract. It records final movement snapshots but does not log collision correction vectors, requested delta, recovered delta, or stride contamination.
10. `engine-ah.js` is not the source of this issue: it runs after the wrapped movement and only hard-zeros velocity when no movement input exists. The collision/gait coupling already occurred inside the `engine-ac` wrapper around core movement.

Redundancy/ownership observation: physics correction belongs to `engine-a.js` + `KELO_COLLISION`, while gait ownership belongs to `engine-ac.js`, but there is no explicit movement-result contract between them. `engine-ac.js` infers locomotor distance indirectly from final positions. This is compact, but it collapses intended motion, collision sliding/depenetration, teleports/warps, and world-bound clamps into one number.

### EXTERNAL_EVIDENCE
- Godot `PhysicsBody2D.move_and_collide` explicitly distinguishes requested `motion` from the collision recovery phase. Its API even has `recovery_as_collision` to decide whether depenetration from recovery is reported as collision, demonstrating that recovery is a distinct phase rather than ordinary requested travel: https://docs.godotengine.org/en/latest/classes/class_physicsbody2d.html
- Godot `CharacterBody2D.safe_margin` states that collision recovery can push a body away BEFORE performing the actual motion. This is directly relevant to Kelo's new inside-AABB recovery and supports instrumenting recovery separately from locomotor displacement: https://docs.godotengine.org/en/4.3/classes/class_characterbody2d.html
- Unity `CharacterController.Move` takes an explicit requested movement delta and constrains that move via collisions; Unity also exposes `enableOverlapRecovery` separately on CharacterController to depenetrate from static overlaps. That separation is useful architectural precedent for not treating overlap recovery as authored walking distance: https://docs.unity3d.com/2022.3/Documentation/ScriptReference/CharacterController.Move.html and https://docs.unity3d.com/2022.3/Documentation/ScriptReference/CharacterController.html
- Community/GitHub controller implementations commonly name depenetration as its own controller responsibility rather than input travel. Example: `kurtdekker/Unity-Kinematic-Body` explicitly lists depenetration from moving obstacles as a controller feature alongside interpolation/collision detection: https://github.com/kurtdekker/Unity-Kinematic-Body

Counterevidence / caution:
- For ordinary wall sliding, using actual post-collision displacement for animation is often desirable: if Kelo presses diagonally into a wall and physically slides 3 px along it, the gait should generally advance by the 3 px he actually traveled, not by the larger unconstrained requested vector.
- Therefore the proposed fix must NOT switch gait blindly to `speed*dt` or raw input distance. That would reintroduce foot sliding against walls. We need to subtract only non-locomotor correction/recovery components while retaining real constrained travel.

### HYPOTHESIS
Rare or repeated depenetration corrections can produce a visible lateral cadence artifact: the player's world body is solver-corrected, then the gait interprets the same correction as a planted stride and may advance one or more source frames. At 1.20x avatar scale, any abrupt frame/support change may be easier to notice.

The correct architecture is likely a small movement-result contract from physics to presentation that distinguishes:
- requested/player-driven displacement;
- actual constrained locomotor displacement after collision sliding;
- recovery/depenetration displacement;
- clamp/teleport displacement.

Gait should continue to be distance-driven from ACTUAL locomotor travel, but recovery-only displacement should not automatically advance stride.

### PROPOSED_CHANGE
Do not change production first.

Candidate A — instrumentation only:
- instrument one movement update with `startX/Y`, requested delta (`vx*dt`,`vy*dt`), final X/Y, accumulated collision push X/Y, world-bound clamp correction, and derived actual locomotor delta;
- publish this as QA telemetry without changing positions or gait;
- extend the hero audit with deterministic collision cases.

Candidate B — only if A confirms meaningful stride contamination:
- add a minimal movement-result contract owned by the physics/core path, e.g. last-frame `requestedDelta`, `collisionRecoveryDelta`, `clampDelta`, `finalDelta`;
- let `engine-ac.js` derive stride from final displacement minus explicitly classified recovery/clamp corrections, while retaining legitimate wall-slide displacement;
- preserve current facing logic and world/camera/collider traces.

Candidate C — if classifying solver components is too invasive:
- gate only large anomalous non-intent-aligned one-frame displacement from stride progression, with explicit telemetry and a conservative threshold derived from maximum legal locomotor delta;
- this is less architecturally clean and should be considered only if B adds unacceptable coupling.

Do NOT replace actual-distance gait with target speed or input magnitude. That would animate walking while physically blocked and is worse than the current issue.

### DO_NOT_ASSUME
- Do not assume the new `resolveCircleAABB` recovery algorithm is wrong; its inside-overlap correction fixed a real collision contract gap.
- Do not assume every collision push must be excluded from gait. Normal constrained/sliding movement is real travel and should still advance cadence.
- Do not change collision geometry, collider radius, joystick, gait cadence, camera, avatar scale, filtering, shadow, stop transition or footRoot in the same experiment.
- Do not refactor `engine-a.js`/`engine-ac.js` wrappers before baseline traces prove the data contract needed.
- Do not use velocity magnitude alone as stride distance while against walls.
- Do not call this a visible bug until the deterministic collision test records a measurable frame/support discontinuity or contaminated stride distance.

Control/quality:

- diagonal wall-slide cadence must remain tied to actual tangential travel.
- `worldTraceDelta = 0` for Candidate B relative to baseline physics.
- `cameraTraceDelta = 0`.
- `colliderDelta = 0`.
- `footRootDelta = 0`.
- collision outcome and final resolved position must be identical.
- no new allocation/GC pressure in the hot movement loop; prefer reused scalar telemetry/object storage.

Initial experimental decision targets, not product requirements:
- recovery-only stride contribution -> approximately 0 px;
- free movement and legitimate wall-slide stride error -> <=1% versus actual intended constrained travel;
- no additional frame jump caused by recovery classification;
- zero physics/collision outcome difference.

### RISKS
- Subtracting all collision push can under-count legitimate movement around/along obstacles.
- A naïve `finalDelta - pushDelta` decomposition may be wrong when X/Y sequential resolution redirects motion; telemetry must be verified against controlled cases.
- Dynamic obstacles/abilities can create legitimate external displacement that may need a future animation policy separate from both locomotion and recovery.
- Adding movement-result data in a hot loop can create GC if implemented with fresh objects every update.
- Existing tests validate collision correctness but not animation/collision coupling.
- At 60/90/120 Hz the size/frequency of penetration and correction can differ, so results should be compared under equivalent deterministic traces.
- 1.20x can magnify the visual symptom but must remain independent from the collision/gait contract change.
