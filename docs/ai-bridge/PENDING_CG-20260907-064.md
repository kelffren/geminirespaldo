### PROBLEM
The current reversal audit treats “same/adjacent source frame after LEFT↔RIGHT reversal” as continuity, but Kelo’s left-facing lateral sprite is produced by horizontally mirroring the exact same authored row/frame used for right-facing movement. If a given lateral frame has an off-center visible support foot, mirroring the frame around the actor center moves that support point to the opposite side instantly even when `v.frame` and `stridePhase` do not jump.

That means the existing `reversalFrameJumpCount === 0` invariant can pass while the visible planted foot still teleports across the body on the first rendered reversal frame. This is specifically relevant to the user’s priority of premium, planted lateral movement and will become more noticeable at larger avatar visual scale.

### CONFIRMED_IN_GEMINI
- Current `main` audited: `70e45c8603c8ab3f235b6a22cf44535e6aed3221` (`Append pending ChatGPT bridge research`). `index.html` declares `Kelo World — V6.37` and loads `engine-ab.js?v=240` before `engine-ac.js?v=222`.
- `engine-ab.js` uses one authored lateral row (`row = 2`) for both LEFT and RIGHT. LEFT is generated at render time by:
  - translate to `p.x`
  - `scale(-1, 1)`
  - translate back from `p.x`
  - draw the same `col` / `row` frame.
- `engine-ab.js` already preprocesses each lateral frame and records visible bottom-band support evidence: `supportMinX`, `supportMaxX`, `supportWidthPx`, `supportCentroidX`, and `lowestOpaqueY` in `KELO_HERO_SPRITE_AUDIT.lateralContactFrames`.
- Because LEFT mirrors the raster around the actor X center, a source-frame support centroid that is not exactly centered maps to the symmetric point on the other side of the rendered actor. The potential reversal support displacement is therefore determined by the source-frame centroid’s signed distance from the cropped-frame center, scaled into destination/world pixels.
- `engine-ac.js` detects lateral reversal from horizontal intent sign and intentionally preserves the existing gait phase/frame unless normal distance advancement changes it. It audits `reversalCount`, `reversalAccidentalIdleCount`, and `reversalFrameJumpCount`.
- The LIVE harness `scripts/live-hero-audit.mjs` performs a RIGHT→LEFT reversal and currently fails only if reversal introduces accidental idle or a source-frame jump. It does not calculate the screen/world position of the visible bottom support centroid before and after the mirror.
- The same harness already validates that lateral support centroids exist for all four frames, so the necessary authored evidence is already present; the missing part is transforming that evidence through LEFT/RIGHT render geometry and sampling the first reversal render(s).
- `AVATAR_VISUAL_SCALE` remains 1.15. If the avatar later moves to 1.20x, any support-point discontinuity caused by mirroring scales up proportionally in screen space.
- `GROK_TO_CHATGPT.md` still has no feedback newer than `GC-20260831-003`; no Grok measurement supersedes this finding.

### EXTERNAL_EVIDENCE
Official / primary:
1. Godot’s official 2D player tutorial uses one right-facing walk animation and `flip_h` for left movement. This validates runtime horizontal mirroring as a normal technique, but it does not guarantee contact-foot continuity across a direction reversal; that remains the game’s responsibility.
   https://docs.godotengine.org/en/4.2/getting_started/first_2d_game/03.coding_the_player.html
2. Unity `SpriteRenderer.flipX` explicitly states that horizontal flip changes rendering only. This supports keeping collision/physics invariant while evaluating the visual support-foot consequence separately.
   https://docs.unity3d.com/2022.3/Documentation/ScriptReference/SpriteRenderer-flipX.html
3. Unity’s 2D directional blending documentation treats directional motion selection as animation-state policy rather than physics. This reinforces separating reversal presentation from the physical movement trace.
   https://docs.unity3d.com/Manual/BlendTree-2DBlending.html

GitHub/issues / counterevidence:
4. Godot issue #117610 documents a real class of problems where mirrored parent transforms invalidate downstream directional assumptions in animation/secondary-motion systems. The exact subsystem differs, but it is direct evidence that mirroring can require explicit handling of dependent spatial features.
   https://github.com/godotengine/godot/issues/117610
5. GB Studio issue #1185 reports mirrored right→left sprites while collision bounds remain unmirrored. Kelo intentionally wants physics unchanged, so this is counterevidence against mirroring collider/physics just to follow the sprite; support-foot continuity should be solved in presentation, not physics.
   https://github.com/chrismaltby/gb-studio/issues/1185

Community / counterevidence:
6. r/gamedev foot-sliding discussions repeatedly reduce the perceptual goal to keeping the contact foot stationary relative to the floor while the body advances. This supports measuring the visible support point rather than only animation-frame indices.
   https://www.reddit.com/r/gamedev/comments/wofi7p/
7. GameMaker discussions on turn/reversal animation show that direction changes interrupted mid-cycle can look wrong even when movement code itself is functioning; state/phase handling matters at reversal.
   https://www.reddit.com/r/gamemaker/comments/gbbfna/
8. Counterevidence: simple `image_xscale=-1` / horizontal flip is widely used and often looks perfectly fine. If Kelo’s authored support centroid is close enough to center in all lateral frames, no special reversal treatment is justified.

### HYPOTHESIS
Kelo may have a first-frame LEFT↔RIGHT support-foot discontinuity that is invisible to the current audit because the audit only checks source-frame continuity. The discontinuity should be approximately zero for frames whose visible bottom support centroid lies on the cropped frame center, and larger for frames with clearly off-center support.

If measured support teleport is perceptible, a presentation-only reversal policy that chooses or remaps the first mirrored pose by contact-foot compatibility should look more planted than blindly mirroring the same frame at identical phase.

### DO_NOT_ASSUME

- Do not assume frame 2 is always the planted frame during reversal; release planting and reversal contact are separate problems.
- Do not reset stride phase to zero on reversal without measurement; that can create a cadence pop larger than the mirror discontinuity.
- Do not change collider, physics root, footRoot, movement speed or camera to solve a presentation-only support mismatch.
- Do not add a general animation state machine/refactor before the benchmark.
- Do not combine the first test with 1.20x scale, smoothing changes, hero subpixel snapping changes, camera deadzone changes, lean, bob or squash.

### EXPERIMENT
First, derive authored support geometry from `KELO_HERO_SPRITE_AUDIT.lateralContactFrames`:
- determine cropped source center X for the lateral frame;
- calculate each frame’s signed `supportCentroidOffsetFromCenterSourcePx`;
- transform that offset to rendered/world pixels using the exact source-crop→destination scale;
- predicted RIGHT support X = actor center + rendered offset;
- predicted LEFT support X = actor center - rendered offset;
- therefore calculate `sameFrameMirrorSupportDeltaWorldPx` and CSS/device-pixel equivalents for each frame at current zoom/DPR.

Then extend the LIVE reversal harness to capture the last rendered RIGHT sample and first 1–4 rendered LEFT samples, not a single snapshot 220 ms later.

Run deterministic reversals forced from each authored lateral source frame 0/1/2/3:
1. RIGHT movement until target source frame is active.
2. Capture actor/world/camera/zoom/frame/support point.
3. Reverse immediately to LEFT without release/idle.
4. Capture first four render/update samples.
5. Repeat LEFT→RIGHT.

Run on:
- 390x844 DPR2
- 1280x720 DPR1
- desktop DPR2 when available
- 60/90/120 Hz when harness control is available.

A/B must use the identical physical trace and identical `stridePhase` entering reversal.

### RISKS
- Contact-compatible frame remapping could trade a foot jump for a body/arm pose jump; therefore body silhouette/bounds must be measured too.
- Picking a non-adjacent frame can create a cadence discontinuity even if contact is improved. Prefer same/adjacent frame candidates first.
- A larger avatar scale will amplify both the benefit and any new pose jump; do not use scale increase to decide the baseline fix.
- The current bottom-band support centroid is a raster heuristic, not semantic left/right foot labeling. If both feet occupy the bottom band, centroid may sit between them and understate a true contact-foot switch.
- A future authored turn pose may outperform frame remap but costs asset work and must preserve sprite clarity/filtering.
- Current source-position rounding / camera sampling issues from CG-062 can contaminate screen-space support measurements; log raw world support geometry as well as screen pixels.
