### PROBLEM
The current live directional selector uses a single instantaneous boundary between lateral and vertical-facing animation rows. In engine-ac.js, after choosing movement direction from resolved displacement/velocity/intent, facing is lateral when `abs(v.dx) * 1.15 >= abs(v.dy)` and vertical otherwise. engine-ab.js repeats the same 1.15 rule as legacy fallback. This creates a hard boundary at approximately `abs(dy/dx) = 1.15`, i.e. about 49 degrees from horizontal. There is no directional hysteresis, dwell, angular deadband, or previous-facing bias around that boundary.

On touch input, engine-a.js updates `input.currentX/currentY` directly from every pointermove and derives normX/normY from the current joystick vector. Near the lateral/vertical boundary, small finger tremor or pointer sampling noise can therefore alternate the classification between `left/right` and `up/down` even if physical speed and trajectory change only slightly. Because engine-ab.js maps lateral to spritesheet row 2, down to row 0 and up to row 3, crossing the threshold swaps an entire authored row, not just a subtle blend weight. This can create a visible torso/feet pop that the current audit does not detect.

### CONFIRMED_IN_GEMINI
- Current main at the start of this round: `86c771f6ba871b4811fc2a8d9b9dfc9ff779ebba`. The only commit after the previous bridge append touches `src/systems/nobility.js`; movement/hero files are unchanged.
- `engine-ac.js` currently sets `CONFIG.joystickDeadzone = 0.045`, `joystickCurve = 'LINEAR'`, `movementType = 'DIRECT'` and computes processed magnitude from hypot(normX,normY).
- In `updateVisualMotion`, facing is selected with `const side = Math.abs(v.dx) * 1.15 >= Math.abs(v.dy);` followed by lateral right/left or vertical down/up. No hysteresis state exists.
- `engine-ab.js::faceOf()` contains the same 1.15 instantaneous classification as fallback.
- `engine-ab.js` renders row 2 for both left/right (left is mirrored), row 0 for down and row 3 for up. Therefore one threshold crossing can replace the entire source row.
- `engine-a.js::processInput()` normalizes keyboard diagonals exactly, but touch uses every current pointer vector directly after radial deadzone remapping. There is no angular smoothing/hysteresis in core input.
- The current live hero audit performs only one keyboard down-right diagonal hold and checks that both physical axes moved. It does not sweep angle around the lateral/vertical boundary, emulate noisy touch angles, count facing changes, or compare world-path change against sprite-row changes.
- Existing stride/cadence remains distance-driven; this finding is about facing-row stability and does not require changing world velocity, collider, camera, stride phase, or asset scale.

### EXTERNAL_EVIDENCE
1. Unity's 2D directional blend-tree documentation treats directional locomotion as a 2D parameter space rather than a binary axis dominance switch. `2D Simple Directional` is specifically intended for forward/back/left/right directional motion. This does not require Kelo to adopt Unity-style blending, but it demonstrates that direction selection can be modeled continuously rather than as a single hard comparator.
   https://docs.unity3d.com/Manual/BlendTree-2DBlending.html
2. Godot's `AnimationNodeBlendSpace2D` similarly represents animation selection in a 2D directional space and blends among adjacent animation points. Again, Kelo's pixel-art renderer may prefer discrete rows, but the external pattern supports treating directional boundaries as stateful/continuous rather than a stateless sign test.
   https://docs.godotengine.org/en/stable/classes/class_animationnodeblendspace2d.html
3. Community reports reproduce the practical failure mode: diagonal directional animation can snap between cardinal directions when tiny differences in axis release or joystick values alter the chosen direction. A July 2026 Godot thread specifically describes right/left-to-diagonal inputs choosing an unwanted facing and asks for behavior that preserves the previous meaningful direction through the diagonal. Another June 2026 joystick case notes that analog axes return arbitrary values rather than exact cardinal values.
   https://www.reddit.com/r/godot/comments/1va7aqp/help_with_diagonal_animations/
   https://www.reddit.com/r/godot/comments/1ui2yag/hello_im_new_to_godot_and_programing_and_i_have/
4. Counterevidence: discrete four-direction sprite games often intentionally prioritize one axis on diagonals. A stable bias can be desirable and cheaper than full 8-way animation. Therefore the proposal is NOT to add diagonal sprites or continuous blend trees blindly; it is to measure whether Kelo's current stateless boundary causes perceptible row thrashing on real/noisy input and, only if confirmed, stabilize that boundary.

### HYPOTHESIS
Kelo can preserve its current four-direction authored art and current physical movement while feeling more premium if facing selection gains a small angular hysteresis / previous-facing retention zone around the current 1.15 boundary. The highest-value effect should be on touch/mobile, where pointer vectors naturally fluctuate. A correct change should substantially reduce lateral↔vertical row flips caused by small angular noise without making intentional turns feel delayed.

### PROPOSED_CHANGE
Do not change production before measuring. Benchmark these candidates with the same input traces:

A — BASELINE: current stateless `abs(dx)*1.15 >= abs(dy)` classification.

B — PREVIOUS-FACE HYSTERESIS: use two thresholds. Example QA-only starting point, not production constants: if currently lateral, remain lateral until `abs(dy) > abs(dx)*1.25`; if currently vertical, remain vertical until `abs(dx)*1.25 > abs(dy)`. Direction sign inside the retained family still updates immediately. Tune from data, not intuition.

C — ANGULAR DWELL: require the candidate family (lateral vs vertical) to remain across the boundary for a very small interval such as 25–50 ms before swapping rows. This is a diagnostic alternative; at 60 Hz even one extra render can be visible, so it must be compared against B.

D — INPUT ANGLE LOW-PASS BEFORE FACING ONLY: smooth only the vector used for presentation facing, while physics continues using raw processed input. This can reduce jitter but risks perceptual lag and should be considered only if B fails.

Preferred architecture if a change is validated: keep physics intent untouched; create one presentation-level `selectFacingFamily(dx,dy,previousFace,dt)` owner in engine-ac.js; engine-ab.js should consume `_visualMotion.face` and retain its local classifier only for true legacy/non-_visualMotion actors. Avoid duplicating a new hysteresis algorithm in both files.

### DO_NOT_ASSUME
- Do not assume the 1.15 bias is wrong; it may already be aesthetically good away from the threshold.
- Do not assume every diagonal should show a diagonal sprite; no new diagonal art is proposed.
- Do not smooth or delay physical `input.normX/normY`, velocity, collision response, or camera as part of this experiment.
- Do not use a long timer that makes deliberate 90-degree turns feel sticky.
- Do not refactor both engine-ac.js and engine-ab.js before baseline traces prove a defect.
- Do not judge success only by reduced face changes; intentional direction-change latency must remain low.

### EXPERIMENT
Extend the live hero audit with a presentation-facing trace that can inject deterministic input vectors without altering movement math. Run at least:

1. ANGLE SWEEP around the current boundary at fixed magnitude 0.25, 0.50 and 1.00. Suggested ratios around `dy/dx`: 1.00, 1.08, 1.12, 1.14, 1.15, 1.16, 1.18, 1.22, 1.30 and back down.
2. NOISE TRACE: hold a nominal diagonal near the boundary for >=2 s while alternating deterministic angle noise of roughly +/-1, +/-2, +/-3 and +/-5 degrees. Do not use randomness unless the seed is fixed.
3. INTENTIONAL TURN: horizontal -> diagonal -> vertical and vertical -> diagonal -> horizontal, measuring time/distance until facing changes.
4. RELEASE FROM DIAGONAL and re-engage, verifying previous-facing policy does not leave stale facing across idle unless explicitly intended.
5. TOUCH-LIKE TRACE using analog magnitudes rather than keyboard-only unit vectors.
6. Repeat at 60/90/120 Hz (or deterministic dt equivalents), mobile 390x844 DPR2 and desktop 1280x720 DPR1.
7. After baseline 1.15 passes, repeat the winning candidate at QA-only 1.20 because larger presentation makes row pops easier to notice.

Record each update/render: raw input vector, processed magnitude, input angle deg, resolved dx/dy, selected face, selected spritesheet row, stridePhase, source frame, player world x/y, and whether the change was an intentional threshold crossing or injected noise sample.

### RISKS
- Excessive hysteresis can make the avatar look like it is facing sideways while moving visibly vertical, creating a different form of foot sliding.
- Time-based dwell can become refresh-rate sensitive if implemented as render-count rather than accumulated dt.
- Duplicating logic in engine-ac.js and engine-ab.js would deepen existing ownership debt.
- Changing face family changes visual width (lateral base width 48 versus non-lateral 54), so row thrash can also create width/nameplate/occlusion jitter; measurement should include presentation bounds transitions.
- A 1.20x avatar can magnify the perceived pop, but scale should remain a second-stage variable so the facing experiment stays isolated.
