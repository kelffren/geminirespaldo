### PROBLEM
Kelo's locomotion physics supports continuous 2D vectors, including normalized keyboard diagonals and arbitrary touch/gamepad diagonals, but the LIVE hero has only four directional sprite rows. The visual classifier uses `abs(dx) * 1.15 >= abs(dy)` to choose lateral vs vertical. This means a trajectory can be almost 49 degrees away from horizontal and still render a pure LEFT/RIGHT walk cycle. The stride phase remains distance-correct, but the authored feet/body are representing a cardinal lateral gait while the foot root translates strongly diagonally. This can read as skating/side-slip and can become more visible when the avatar is enlarged to 1.20x. This is different from CG-004: that entry concerns chatter near the angular boundary; this entry concerns the representational error even when the face classification is perfectly stable.

### CONFIRMED_IN_GEMINI
1. `engine-a.js` keyboard input normalizes simultaneous X/Y keys: W+D, S+D, W+A and S+A resolve to a unit vector at 45 degrees rather than disabling diagonal travel or slowing it incorrectly.
2. Touch input preserves arbitrary analog direction outside the radial deadzone; therefore physical movement is genuinely continuous in angle.
3. `engine-ac.js` advances stride from actual Euclidean resolved distance, which is correct and should be preserved. It then classifies face with `side = abs(v.dx) * 1.15 >= abs(v.dy)` and chooses only `left/right/down/up`.
4. The lateral/vertical boundary is `atan(1.15) ~= 48.99 degrees` from the horizontal axis. Therefore a motion vector up to ~48.99 degrees away from pure horizontal can still use a pure LEFT/RIGHT row. Immediately above that boundary the renderer switches to UP/DOWN, whose directional error starts around ~41 degrees from vertical.
5. Exact keyboard diagonal is 45 degrees and always satisfies the lateral test because `1.15 * |x| >= |y|`. Therefore all four WASD diagonals currently choose LEFT/RIGHT rows, never UP/DOWN rows, while the actor travels diagonally.
6. `src/characters/character-appearance.js` confirms the LIVE hero has only four authored rows (`down`, `left`, `right`, `up`) and no diagonal clips. LEFT and RIGHT use direction-specific frame metrics/foot anchors, so the row is not a neutral generic locomotion cycle.
7. The appearance fallback path duplicates the same 1.15 cardinal classifier for actors without `_visualMotion`; do not add a third direction owner. For the local player, `engine-ac.js` through KeloMovement remains the presentation owner.
8. This is not a physics normalization bug. World speed/distance can be correct while animation direction is visually mismatched.

### EXTERNAL_EVIDENCE
- Unity's official 2D Blend Tree documentation treats directional locomotion as a 2D velocity problem and specifically describes directional clips positioned by velocity X/Y. This supports measuring motion-direction representation rather than treating speed alone as sufficient: https://docs.unity3d.com/Manual/BlendTree-2DBlending.html
- Godot's official 2D movement documentation treats 8-way movement as a distinct top-down movement mode, reinforcing that diagonal travel is a first-class state even when the physics vector is normalized: https://docs.godotengine.org/en/latest/tutorials/2d/2d_movement.html
- Godot issue #100009 is relevant implementation evidence for discrete pixel-art directional animation: maintaining phase/timing while changing cardinal run direction matters because resetting/switching clips can cause rapid repeated footstep events. Kelo should preserve its shared stride phase if/when diagonal presentation changes: https://github.com/godotengine/godot/issues/100009
- Godot issue #41028 is counterevidence against blindly adopting generic BlendSpace-style carry/blending for frame-by-frame art: discrete directional blend/carry can freeze or mis-handle animation position in real engines. Kelo should not introduce a complex blend tree just to solve a four-row spritesheet limitation: https://github.com/godotengine/godot/issues/41028
- Community discussion shows a common four-direction-art compromise: keep the previously dominant/last-pressed cardinal animation while moving diagonally, rather than continuously flipping cardinal rows. This can reduce chatter but does not remove the underlying movement-vs-art directional mismatch: https://www.reddit.com/r/gamemaker/comments/dve1dp/
- Another current community report notes diagonal jitter can also come from sprite hotspots/anchors and camera/pixel stepping, so any diagonal benchmark must separate directional-art mismatch from CG-005 pixel-phase issues: https://www.reddit.com/r/clickteam/comments/1uh590w/

### HYPOTHESIS
The premium path is to keep continuous diagonal physics and shared distance-driven stride, but make diagonal presentation an explicit contract instead of an accidental by-product of a 1.15 threshold. In the short term, a stable dominant-axis/entry-direction policy may reduce visible row snapping and make 45-degree travel read more intentionally. In the long term, true authored diagonal rows (8-direction locomotion) are likely to produce the lowest motion-to-facing error if the art quality is high enough. We should not synthesize diagonal sprites or rotate the existing raster hero without a benchmark because those shortcuts can distort silhouette, foot anchors and pixel-art quality.

### PROPOSED_CHANGE
Do not modify production blindly. Benchmark these policies with the same world trace:
A. Baseline: current four-row classifier with 1.15 threshold.
B. Dominant-history four-row policy: preserve the cardinal row that was already active when a second axis is introduced, and only switch when the new axis becomes decisively dominant. This is presentation-only and should share the existing stridePhase.
C. Closest-cardinal policy: choose the cardinal direction with smallest angular error, with the CG-004 hysteresis band if needed. At exact 45 degrees use a deterministic tie rule based on previous face/last intentional axis, not a hardcoded lateral bias.
D. Authored 8-direction prototype: only if art exists or can be produced at production quality. Add diagonal face IDs/rows through the existing Character Appearance contract while preserving footRoot, shared stride phase, collider and physics. This is the architectural target if A/B/C cannot reach the visual gate.
E. Do NOT rotate/shear the existing 4-direction raster sprite as the default solution. Test only as an explicit negative/control if desired; rotation changes pixel phase, foot contact and silhouette and can look worse than stable cardinal art.

Do not change movement normalization, gameplay speed, collision, camera or joystick to make the animation appear correct. Do not restart stridePhase when face changes; phase continuity is already valuable.

### DO_NOT_ASSUME
- Do not assume four-direction art is automatically unacceptable; many top-down games intentionally use cardinal art during diagonal movement.
- Do not assume 8-direction art is automatically better; poor diagonal frames can reduce clarity and increase asset/memory cost.
- Do not use CG-004 hysteresis alone as proof this problem is solved. Hysteresis can stop chatter while leaving a stable 45-degree motion-to-facing mismatch.
- Do not snap physical movement to four directions; that would change gameplay/PvP and violate the current user priority of preserving responsive movement.
- Do not restart the animation at frame 0 on a diagonal/cardinal row change.
- Do not create a new movement or animation manager; reuse KeloMovement + KeloCharacterAppearance/KeloAvatar.

### RISKS
1. A last-direction/dominant-history policy can keep a cardinal row too long after the player clearly changes trajectory; measure commit latency.
2. Closest-cardinal without hysteresis can recreate CG-004 boundary chatter.
3. Eight-direction art doubles directional locomotion content and per-appearance metadata; keep the schema data-driven so future appearances can opt into 4 or 8 directions.
4. New diagonal frames need authored foot anchors; otherwise better facing direction can still produce worse planting.
5. At 1.20x any cross-axis foot slip and frame-to-frame silhouette jump becomes more visible.
6. Do not conflate pixel-phase jitter (CG-005) with directional-art error; run the same render policy for every candidate.
