PROBLEM
Current production locomotion forces CONFIG.movementType='DIRECT' from engine-ac.js. In engine-a.js DIRECT assigns localPlayer.vx/vy directly to targetVx/targetVy every update. A full RIGHT->LEFT reversal can therefore change physical velocity from +V to -V in one simulation callback with no braking/cross-zero interval. This maximizes responsiveness but gives the body no physical turnaround interval to support premium planted reversal animation. engine-ac simultaneously sets accelDecay=32 and decelDecay=18, but those parameters are not consumed while movementType remains DIRECT.

CONFIRMED_IN_GEMINI
- engine-ac.js is a KeloMovement consumer and explicitly sets CONFIG.movementType='DIRECT', CONFIG.accelDecay=32, CONFIG.decelDecay=18.
- engine-a.js implements two existing paths: DIRECT sets vx/vy immediately to target velocity; the non-DIRECT path exponentially approaches target velocity with factor 1-exp(-decay*dt).
- Under non-DIRECT movement, reversal while input remains nonzero uses accelDecay (currently 32), while release uses decelDecay (currently 18).
- With k=32, an idealized symmetric +V -> -V exponential reversal crosses zero after ln(2)/32 ~= 21.7 ms. This is a very short micro-brake, not a long inertia model, and is approximately time-based because dt is in the exponential.
- Foundation already owns movement extension through KeloMovement; engine-ac/engine-ah consume hooks. Do not add another updateMovement wrapper.
- engine-ac visual stride is distance-driven, so any candidate must be re-measured rather than assuming animation stays correct when physical displacement changes during reversal.
- The current code therefore contains a dormant/unused tuning surface: accelDecay/decelDecay are assigned by engine-ac but DIRECT bypasses them.

EXTERNAL_EVIDENCE
- Unity Vector3.SmoothDamp officially describes time-based gradual convergence toward a desired target and exposes smoothTime/deltaTime; this supports testing a bounded response instead of assuming instantaneous target velocity is the only responsive option: https://docs.unity3d.com/ja/current/ScriptReference/Vector3.SmoothDamp.html
- Roblox creator documentation exposes GroundController AccelerationTime and DecelerationTime separately, demonstrating that character-control systems commonly treat acceleration/braking as explicit tunable properties: https://github.com/Roblox/creator-docs/blob/main/content/en-us/characters/character-controller-library/controllers.md
- GitHub character-controller examples expose acceleration, deceleration, and even separate counter-acceleration when changing direction, supporting the idea that reversal response can be tuned independently rather than coupled blindly to ordinary acceleration: https://github.com/pmndrs/BVHEcctrl
- Community evidence is mixed by design. Top-down developers report that subtle acceleration/deceleration can add weight, while too much makes movement glide; precision-heavy genres may deliberately prefer instantaneous movement. Therefore external evidence supports benchmarking, not blindly enabling inertia.

HYPOTHESIS
A very short, dt-aware braking/cross-zero interval during LEFT<->RIGHT reversal may make Kelo look more planted and give reversal pose/foot-support logic a real physical interval to communicate weight, while preserving responsive control. The already-existing MICRO_ACC path with current 32/18 constants is the lowest-complexity first candidate. It may still be worse than DIRECT; that outcome is acceptable.

RISKS
- Added smoothing can feel slippery, especially on keyboard and precision combat.
- The non-DIRECT path currently uses accelDecay whenever target velocity is nonzero, including counter-steering; its response may be too uniform for starts vs reversals.
- Collision resolution changes position after velocity integration but does not automatically zero blocked velocity; under inertia this must be tested for wall-release slingshot behavior.
- A short physical reversal interval can expose existing CG-089/CG-090 presentation issues rather than solve them.
- At high refresh rates poor test methodology can confuse sample count with time response; compare real milliseconds and distance, not callback count.
