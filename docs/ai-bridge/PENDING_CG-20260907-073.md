PROBLEM
Current MOV-STOP-V2 correctly avoids freezing Kelo forever on an arbitrary walk frame after release, but it solves that by setting visual motion off immediately and resetting the lateral gait to the fixed authored plant frame 2 in the same movement update. Therefore releasing from lateral frames 0, 1 or 3 can change the source sprite column instantly while world velocity has already become zero. Releasing from frame 0 can jump two columns in a single update (0 -> 2). The current LIVE audit waits 140 ms after key release and only asserts that the final state is planted; it does not sample the first render/update after release, so a visible stop pop can pass all current stop tests. This is separate from CG-068 per-frame vertical foot pivots and CG-064 reversal support continuity: it is specifically walk/run -> idle/release transition timing and pose selection.

- Current `main` at research start is `dc4431007ec071a16622b0253d8b70df40d50e26`; `index.html` declares Kelo World V6.47. The movement files were re-read from current main rather than assumed from previous rounds.
- Compared with the previous CG-072 base (`d4aea85c...`), main is 26 commits ahead; the compare shows changes dominated by combat architecture, builder/UI and `index.html`. `engine-a.js`, `engine-ab.js`, `engine-ac.js`, `engine-ah.js` and `scripts/live-hero-audit.mjs` are not listed as changed in that compare, so the release logic inspected here remains the actual current code.
- `engine-ac.js` defines `DEFAULT_PLANT_FRAME = 2`, `PLANT_PHASE = 0.5`, `MOV_STOP_V2` enabled unless `?movStopV2=0`, and comments that release should not freeze an arbitrary stride pose.
- In `updateVisualMotion()`, when `hasIntent` is false and `physicallyMoving` is false, MOV_STOP_V2 sets `v.stopElapsed = VISUAL_STOP_HOLD_SEC`, `v.on = false`, `unsupportedPoseFreezeMs = 0` and `releaseToStablePlantMs = 0` immediately.
- Later in that same call, `else if (!v.on)` unconditionally assigns `v.stridePhase = PLANT_PHASE`, `v.strideDistancePx = 0`, and `v.frame = PLANT_FRAME`. There is no stop-transition state, no adjacent-frame path, no frame-duration budget and no support-foot continuity criterion.
- With four lateral columns and fixed plant frame 2, the source-column distance to the target is: frame 0 -> 2 = two-column jump; frame 1 -> 2 = one; frame 2 -> 2 = zero; frame 3 -> 2 = one. If releases were uniformly distributed by frame, only 25% would already be on the target and 25% would experience the maximum two-column source-frame jump. Actual release distribution must be measured; uniformity is NOT assumed.
- `engine-a.js` is in DIRECT movement because `engine-ac.js` forces `CONFIG.movementType='DIRECT'`. On release, zero input makes target velocity zero inside the core movement update before `updateVisualMotion()` runs, so unobstructed release can satisfy `physicallyMoving=false` immediately and trigger the plant snap in the first update.
- `engine-ah.js` wraps `updateMovement()` after `engine-ac.js` and also zeros velocity when there is no move input. It does not add any presentation settle or change the source frame. It is therefore not a hidden smoothing layer for this problem.
- `engine-ab.js` renders the source column supplied by `_visualMotion.frame`; it does not blend/crossfade frames. Thus a frame change generated by MOV-STOP-V2 becomes an immediate PNG pose change.
- `scripts/live-hero-audit.mjs` executes RIGHT, then immediate LEFT reversal, releases LEFT, waits 140 ms, and snapshots `release`. `assertPlantedRelease()` checks only `visualOn=false`, `visualFrame===plantFrame`, `stridePhase===plantPhase`, and zero retained stride distance. It does not capture the last moving render, first post-release render, source-column jump magnitude, visible support-foot displacement, silhouette area change, or time history during 0..140 ms.
- The audit's existing `lastReleaseFromFrame`/`lastReleaseFromPhase` telemetry records where release came from, but there is no `lastReleaseToFrame`, `releaseFrameJumpCount`, or first-render release metric. Therefore the audit has enough state to identify the source pose but currently does not evaluate continuity to the destination pose.
- `engine-ab.js` already publishes lateral bottom-contact evidence per frame (`lowestOpaqueY`, `supportMinX`, `supportMaxX`, `supportWidthPx`, `supportCentroidX`), which can be used later to judge whether a stop transition preserves support continuity without inventing semantic foot labels.

EXTERNAL_EVIDENCE
- Unity's current Animator transition API explicitly supports exit timing and transition duration rather than forcing every state change to be an instantaneous source-pose reset. `exitTime` allows a transition to become eligible at a selected normalized phase, while transition duration controls the blend timing: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Animations.AnimatorStateTransition-exitTime.html and https://docs.unity3d.com/6000.0/Documentation/Manual/class-Transition.html
- Godot's AnimationTree state-machine transitions expose `Immediate`, `Sync`, and `At End` switch modes plus cross-fade time. This is evidence that stop/idle transition timing is normally an explicit design variable, not necessarily a hard reset: https://docs.godotengine.org/en/stable/tutorials/animation/animation_tree.html
- A Godot community report specifically describes visible flicker/abrupt switching when walk input is released at certain animation phases. The author found that waiting for frame progress near the end helped somewhat but harmed responsiveness/fluidity, which is useful counterevidence against simply waiting for a whole walk cycle: https://www.reddit.com/r/godot/comments/1dhb02v/
- Pixel-art community feedback consistently emphasizes that a contacting foot should remain stable relative to the ground; sudden support-foot relocation is read as sliding/popping even when the character root stops: https://www.reddit.com/r/PixelArt/comments/1hgne5y/
- Counterevidence: immediate idle switching is common and can be preferable when sprites are tiny, the idle frame is visually close to all gait frames, or input responsiveness matters more than transition polish. A phase-aware settle must therefore prove perceptual improvement and cannot add gameplay latency or a conspicuous in-place extra step.

HYPOTHESIS
MOV-STOP-V2 likely solved the previous arbitrary-pose freeze but can still produce a release pop whose severity depends on the current source frame. A presentation-only, bounded phase-aware stop policy can reduce first-frame silhouette/support discontinuity while keeping physics stop immediate. The best policy may be as simple as choosing a release target/adjacent pose that is geometrically closest to the current support configuration; a timed settle should be used only if measurements show it beats immediate switching without looking like Kelo takes an extra step in place.

PROPOSED_CHANGE
Do not change production first. Extend QA to compare:
A) baseline current MOV-STOP-V2: immediate fixed frame 2;
B) nearest-stable-pose immediate: on release choose among authored lateral frames a stable stop candidate whose measured bottom support/silhouette is closest to the current frame, with no timed animation. This tests whether fixed frame 2 is the main problem;
C) bounded adjacent-frame settle: physics stops immediately, but BODY_LOCAL presentation may traverse at most one adjacent authored pose before reaching the configured plant frame, under a strict ~40-80 ms cap and interruptible immediately by new input. Do not advance world-distance stride while settling;
D) phase-window control: allow an immediate plant only when current phase is already near a stable plant window; otherwise use candidate B or C. Do NOT wait for completion of the whole gait loop.
All candidates are presentation-only. Preserve collider, world trace, camera, input, footRoot/depthRoot, movement speed and source art. Do not combine with per-frame vertical anchor correction, native-left row, body lean/squash, DPR changes, cadence changes or 1.20x scale in the same experiment.

DO_NOT_ASSUME
- Do not assume fixed plant frame 2 is visually wrong; it may be the best authored stop pose. The issue is transition continuity, not the existence of a designated plant frame.
- Do not assume release phases are uniformly distributed; record real source-frame/phase histograms.
- Do not wait for a full animation loop before visually stopping; community evidence and input-response principles suggest this can feel laggy.
- Do not continue normal stride advancement after physics stops just to reach plant; that creates an obvious in-place walking step.
- Do not alter physics velocity, collider or release timing to hide a presentation problem.
- Do not crossfade pixel art by default; alpha blending between two nearest-neighbor poses can create ghost limbs. If a crossfade is tested at all, keep it a diagnostic separate candidate.
- Do not let a stop settle block a new LEFT/RIGHT/reversal input. New movement must interrupt presentation settling on the next update.

RISKS
- A timed settle can look like an extra step after the player has stopped if it contains a swing/contact pose rather than a true recovery pose.
- Choosing a different idle frame per release can reduce pop but create inconsistent idle silhouettes unless the policy converges quickly and predictably.
- Support-centroid heuristics are not semantic foot tracking; two feet or stray pixels can bias the centroid. Use silhouette/support geometry as evidence, not ground truth.
- Pixel-art crossfades can blur/ghost limbs and should not be the default solution.
- More stop-state branches can interact with reversal and low-speed threshold research, so experiments must preserve same input/world trace and isolate one variable.
- At 120 Hz a frame-count-based settle would be half as long as at 60 Hz; all timing must be expressed in seconds/ms.
- Larger avatar scale will magnify any release pop, but 1.20x should be tested only after the 1.15x baseline policy is selected.
