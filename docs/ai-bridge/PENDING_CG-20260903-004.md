### PROBLEM
Current local-player presentation deliberately advances stride only from actual post-collision world displacement, which prevents treadmill animation into a wall. However, the ON/OFF state of locomotion is still driven by intent OR nominal velocity. When Kelo reaches a solid wall while the player continues holding LEFT/RIGHT, actual post-collision displacement can become zero while `localPlayer.vx/vy` remains nonzero and intent remains active. `engine-ac.js` therefore keeps `_visualMotion.on = true` indefinitely but cannot advance `stridePhase`; the currently displayed walk/run frame is frozen for as long as the wall is held.

If contact occurs during an arbitrary part of the 4-frame cycle, Kelo can remain visually stuck in that arbitrary mid-stride pose instead of settling into a planted/blocked stance. This is distinct from the already-researched treadmill issue (phase must not advance while blocked), the 0.12 px refresh-rate stride gate, and the release-to-idle settle. Here the problem exists specifically while input remains held and physical progress is persistently suppressed by collision.

### CONFIRMED_IN_GEMINI
At live `main` base commit `7f32446abd3b8286d1fb6486d7e9256d985dd60b` / visible build V6.10:

1. `index.html` still loads `engine-a.js?v=149`, `engine-ab.js?v=149`, `engine-ac.js?v=220`, then `engine-ah.js?v=94`; current movement behavior must therefore be derived from those live files rather than stale ENGINE_MAP ownership text.
2. `engine-ac.js` defines `hasIntent = gait !== 'idle'` and `physicallyMoving = dist > MIN_VISUAL_MOVE_PX || spd > 16`.
3. If either `hasIntent` or `physicallyMoving` is true, it resets `v.stopElapsed=0` and forces `v.on=true`. Thus any sustained processed input above the idle gait threshold can keep visual locomotion ON even if world displacement is zero.
4. `engine-a.js` DIRECT movement sets `localPlayer.vx = input.normX * CONFIG.speed` / `vy = input.normY * CONFIG.speed`, advances position, then resolves axis-separated circle-vs-AABB overlap by pushing the position back out. The collision solver does not zero the corresponding velocity after the push-out.
5. Therefore when already flush against a vertical wall and holding pure RIGHT/LEFT, one update can end with approximately `postCollisionDx=0` while `abs(localPlayer.vx)` remains the requested movement speed and `hasIntent=true`.
6. In that state `engine-ac.js` chooses direction from velocity when `dist <= 0.12 && spd > 16`, so facing remains meaningful, but `v.lastStepDistancePx = dist > 0.12 ? dist : 0` becomes zero.
7. Stride phase/frame advances only when `v.on && v.lastStepDistancePx > 0`. With zero post-collision displacement, phase does not advance.
8. Because `v.on` remains true while the button/stick remains held, the `else if (!v.on)` reset path is never reached. The current `v.frame` can therefore remain unchanged indefinitely while pressing into a wall.
9. `engine-ab.js` consumes `_visualMotion.frame` directly when present; this frozen frame reaches the production PNG avatar.
10. On eventual input release, DIRECT movement makes nominal velocity zero, `engine-ac.js` starts its 75 ms visual stop hold, and only after `v.on` becomes false does it reset stride/frame to zero. That release behavior is a separate already-researched settle issue; it does not solve the indefinite held-wall pose.
11. `engine-ah.js` only hard-stops after the wrapped movement when it believes there is no movement input. While the player is still holding against the wall, `hasMoveInput()` remains true and the wrapper does nothing.
12. The failure does not require a specific refresh rate. 60/90/120 Hz affect how quickly the character reaches the wall and sampling of the final contact frame, but once fully blocked the frozen-pose duration is bounded only by how long input remains held.
13. `docs/IMPLEMENTATION_ROADMAP.md` already states that blocked movement must not treadmill. The current code satisfies the no-treadmill phase invariant but does not specify what presentation pose should be used during sustained blockage. This entry fills that missing presentation contract rather than contradicting MOV-004.
14. `ENGINE_MAP.md` is stale (V5.15 and old hero ownership), so it is not used as authority for the current renderer/movement chain.
15. No production code was modified during this research round.

### EXTERNAL_EVIDENCE
1. Unity's official NavMesh Agent + Animator guidance recommends one-way information flow and, in the common “animation follows agent” setup, feeding agent velocity into the Animator to roughly match animation to actual movement. Unity explicitly notes foot sliding occurs when animation cannot match physical velocity. This supports distinguishing requested input from achieved travel when deciding whether a locomotion cycle should continue: https://docs.unity3d.com/2019.4/Documentation/Manual/nav-MixingComponents.html
2. Godot's official `CharacterBody2D` documentation exposes requested `velocity`, `get_position_delta()` and `get_real_velocity()` as separate concepts after collision. `get_position_delta()` returns actual travel from the last move, while real velocity represents achieved movement direction. This is directly analogous to Kelo needing both intent/requested speed and actual post-collision progress: https://docs.godotengine.org/en/4.3/classes/class_characterbody2d.html
3. Godot issue #75428 describes expected wall behavior where the horizontal velocity is zero when running into a wall in representative cases, illustrating why downstream animation code often treats collision-resolved motion as distinct from requested velocity: https://github.com/godotengine/godot/issues/75428
4. Godot issue #69130 and related wall-slide reports show that wall contact itself can create abrupt/sticky movement behavior depending on solver semantics. These are not evidence of Kelo's exact bug; they are a warning that animation logic should measure actual post-collision travel rather than infer it from requested velocity alone: https://github.com/godotengine/godot/issues/69130
5. Community guidance is not unanimous. A June 2026 r/gamedev discussion on movement→idle argues that player intent can be a useful animation-state signal because pure velocity can misclassify externally pushed/sliding characters. That is valid counterevidence: Kelo should not simply define “moving animation = actual speed > 0” universally. Instead it should represent sustained `intent-but-blocked` as its own presentation condition or settle policy: https://www.reddit.com/r/gamedev/comments/1u7a41y/whats_the_industry_standard_condition_for_going/
6. Community foot-slide discussions commonly recommend scaling locomotion animation to actual movement speed to avoid a moonwalk/treadmill appearance. This supports keeping phase tied to actual travel, which Kelo already does; the new issue is what stable pose to show when actual travel remains zero under continued intent: https://www.reddit.com/r/Unity2D/comments/d5dczo

### HYPOTHESIS
Kelo needs a presentation distinction between:
- `intentActive`: player is asking for movement;
- `travelActive`: post-collision world progress is meaningfully occurring;
- `blocked`: intent remains meaningful but progress along intent is persistently near zero because collision suppresses it;
- `visualLocomoting`: whether the walk/run cycle should actively present as locomotion.

The likely premium behavior is not to treadmill and not to freeze forever in an arbitrary swing frame. After a short, time-based blocked confirmation window, the body should settle to a stable planted/blocked pose while retaining the intended facing. With the current 4-frame asset, the safest production pose is not known yet because contact-foot semantics have not been validated. Therefore the first experiment should identify the blocked condition and compare pose policies without changing physics.

A dedicated “push/brace” animation could eventually be superior, but it is unnecessary for the first benchmark. A stable nearest-contact pose or a deliberate idle/neutral frame may be sufficient if visually validated.

### PROPOSED_CHANGE
Do not change collision, speed, collider or stride cadence in the first pass.

P1 — Instrument blocked travel only.
Add read-only telemetry after `_move(dt)` for:
- `intentMag` and intent vector;
- requested/nominal velocity;
- post-collision `dx/dy`;
- `travelSpeed = dist / max(dt,epsilon)`;
- progress along normalized intent (`dot(actualDelta, intentDir)/dt`);
- current visual frame/phase;
- `blockedCandidateMs`;
- collision-contact evidence if a minimal flag can be surfaced safely.

P2 — Detect sustained blockage from progress, not one tiny frame.
Candidate detector should require meaningful movement intent and requested speed while achieved progress along intent remains a small fraction of requested speed for a short elapsed-time window. Benchmark confirmation windows around 60/90/120 ms; do not use render-frame counts. Reset/relax the detector as soon as meaningful travel resumes.

P3 — Compare presentation policies after detection.
A. Baseline: hold arbitrary current frame forever.
B. `blocked -> visual idle/neutral`: keep facing, settle to a deliberately chosen neutral frame after the blocked dwell.
C. `blocked -> nearest contact`: if frame inspection can identify left/right planted-contact frames, remap to the nearest contact-compatible pose without resetting physics/stride distance.
D. Future only: dedicated one/two-frame brace/push pose if A-C are inadequate.

P4 — Keep stride distance contract intact.
While fully blocked, phase advance must remain zero. Do not animate feet in place merely to make the wall interaction look alive.

P5 — Do not combine this with CG-20260902-021 buffered stride, WALK→RUN cadence smoothing, reversal, avatar scaling, shadow or camera changes. First prove the held-wall presentation behavior in isolation.

### DO_NOT_ASSUME
- Do not assume frame 0 is a valid planted/neutral pose; inspect the current lateral frames or use a diagnostic comparison before choosing it.
- Do not classify a normal very-slow walk as blocked merely because a single update moves less than 0.12 px. Use elapsed progress/travel speed over a window, especially because CG-20260902-021 already identified refresh-rate-sensitive microdistance behavior.
- Do not use nominal `localPlayer.vx/vy` alone as achieved travel; current collision resolution can leave nominal velocity nonzero after position is pushed back.
- Do not stop or alter physics when the presentation becomes blocked.
- Do not advance stride while blocked.
- Do not change collider radius 20.
- Do not infer a dedicated push animation is required before testing a stable contact/neutral pose.
- Do not let a brief corner touch or wall scrape force idle if Kelo is still making substantial travel along the wall.
- Do not mark the issue fixed from code inspection; reproduce a mid-stride wall contact and measure the held frame duration.

### RISKS
1. A blocked detector based on a single-frame displacement threshold would repeat the refresh-rate bug already documented by CG-20260902-021. Use elapsed/cumulative progress.
2. Settling too quickly can make Kelo visibly pop to neutral on every small obstacle touch and feel less responsive.
3. Settling too slowly preserves the arbitrary frozen pose long enough to remain noticeable, especially after avatar enlargement.
4. Using frame 0 without inspecting current art can replace one bad pose with another.
5. A dedicated brace pose can look premium but increases art/state complexity and should not be introduced until the simpler contract is measured.
6. Against a diagonal wall slide, one axis being blocked is normal. Detector must distinguish “no progress” from “one-axis suppression while still traveling.”
7. Future network reconciliation or external movement can create intent/travel mismatches for reasons other than walls. Keep this first detector scoped to local collision presentation rather than turning it into a universal state machine.
