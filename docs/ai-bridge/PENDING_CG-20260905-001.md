### PROBLEM
The current lateral pipeline has improved cadence, hard stop and foot-root separation, but two remaining assumptions prevent us from claiming real foot planting: (1) `engine-ab.js` renders both LEFT and RIGHT from source row 2 and mirrors LEFT, leaving source row 1 unused; (2) MOV-STOP-V2 in `engine-ac.js` immediately resets every true release to frame 0 / stridePhase 0 without evidence that frame 0 is an authored contact pose. Before adding lean, bob, shadow polish or larger avatar scale, verify the actual semantics and contact frames of the 4x4 hero sheet.

This entry complements the zoom/refresh investigation in CG-20260904-025; it does not supersede it. Screen/camera artifacts can amplify perceived sliding, but the source animation semantics should first be made explicit so later A/B tests know what they are measuring.

### EXTERNAL_EVIDENCE
- Common animation/game-dev guidance is to match visible foot travel and ground/world travel rather than advancing locomotion purely by display frames. This agrees with Kelo's current distance-driven stride phase and argues for keeping that architecture.
- Community discussions on foot sliding repeatedly recommend measuring how far a planted foot moves through the authored cycle and synchronizing world displacement/animation speed to it; this is useful as a measurement principle, not as proof of Kelo's specific frame semantics.
- Godot issue #35606 documents 2D sprite jitter that becomes especially visible with camera smoothing; therefore perceived lateral instability must be split into animation/contact error vs screen-space camera/render jitter.
- Godot proposal #6995 explains that nearest-neighbor can still visibly jump when smoothly moving sprites land between display pixels. This is counterevidence against blaming every visible slide on source animation.
- Godot issue #57221 shows rotation + float motion can introduce pixel jitter in pixel-perfect setups. If lean is later added, rotation should not be bundled into this contact-frame experiment.
- A smooth-pixel-camera demo by voithos notes the tradeoff between whole-pixel sprite motion and smooth camera motion; again, camera/render cadence remains a separate later axis.

External references reviewed: Reddit r/gamedev discussions on foot sliding / matching animation footspeed to groundspeed; Godot GitHub issue #35606; godot-proposals #6995; Godot issue #57221; voithos/godot-smooth-pixel-camera-demo.

### HYPOTHESIS
The next high-value improvement is not more procedural bob/lean. It is making authored direction/contact semantics explicit. If row 1 is a genuine authored LEFT row, using it instead of mirroring RIGHT should improve directional asymmetry and may improve arm/leg readability. If the left/right rows are phase-aligned, preserving stride phase across reversals should remain smooth. If they are not phase-aligned, an explicit 4-entry phase/frame mapping is safer than resetting to idle.

Separately, if frame 0 is not a true contact pose, MOV-STOP-V2 can still produce a visible stop pop despite its audit reporting zero freeze. Choosing the nearest verified contact column for a very short visual-only settle may improve planting while physics remains stopped immediately.

These are hypotheses. Do not infer row semantics or contact columns from row number alone.

### PROPOSED_CHANGE
Do not alter production movement yet. First build/enable a small diagnostic path or feature flag that:
1. exposes the exact source row, source column, face and stride phase in `KELO_MOVEMENT_AUDIT`;
2. allows A/B selection of current lateral policy (`LEFT = mirrored row 2`) versus an authored-left candidate only after row 1 is visually/pixel-verified as LEFT;
3. captures all four lateral source columns at a fixed footRoot to label real contact/passing poses;
4. records a `contactFrameSet` only from observed authored frames;
5. if left/right columns are not phase-aligned, defines an explicit phase mapping table for hard reversals instead of inserting idle;
6. only after contact frames are proven, tests a visual-only release settle to the nearest contact pose. Physics stop remains immediate and input/reversal must never wait for settle.

Do not combine this with avatar scale, shadow, lean, bob, camera tuning or zoom changes in the same implementation commit.

### DO_NOT_ASSUME
- Do not assume source row 1 is LEFT merely because the sheet has four rows.
- Do not assume frame 0 is a contact/plant pose.
- Do not assume the same column means the same planted foot in the left and right authored rows.
- Do not assume mirrored RIGHT is inferior; it may be intentional if row 1 is duplicate/unused/bad art.
- Do not interpret zero `releaseToStablePlantMs` as proof of good foot planting; current metric is structurally zero under MOV-STOP-V2.
- Do not change collider radius 20, movement speed, world geometry, camera, combat, economy or networking.

### EXPERIMENT
Baseline first, then one visual-semantic change at a time.

A. SOURCE SEMANTICS BASELINE
- Render/capture the 16 source cells or at minimum the 8 lateral cells with a common origin/footRoot.
- Compare row 1 vs row 2 pixel content and silhouette. Determine whether row 1 is unique and whether it is plausibly authored LEFT.
- Label each lateral column by observed foot state: contact/plant, passing, opposite contact/plant, passing, or UNKNOWN. UNKNOWN is acceptable.

B. DIRECTIONAL-ROW A/B (only if A verifies row 1)
- Baseline: current RIGHT=row2, LEFT=mirrored row2.
- Candidate: RIGHT=row2, LEFT=row1 without mirror (or the verified authored orientation).
- Same trace: LEFT walk, LEFT run, RIGHT walk, RIGHT run, hard R->L, hard L->R, diagonal transitions.
- Preserve all world movement values.

C. RELEASE CONTACT A/B (only after contactFrameSet exists)
- Baseline: current MOV-STOP-V2 immediate frame0.
- Candidate: physics stops immediately; visual chooses nearest verified contact phase and settles for the minimum visually useful duration. Suggested test window <=80 ms, not a required value.
- Release from each of the 4 phase quadrants at walk and run.
- Reversal is explicitly excluded from release settle.

D. DISPLAY VALIDATION
- Repeat representative traces at observed 60/90/120Hz where hardware allows.
- Record screen-space jitter separately from world/phase metrics so camera/zoom artifacts do not contaminate contact conclusions.
- Mobile + desktop screenshots/video if available; follow Visual Direction Memory requirement that meaningful visual changes need LIVE mobile inspection before being called complete.

Accept a directional-row change only if authored semantics are proven and reversal/leg continuity is no worse. Accept a release-settle change only if visual planting improves without delaying physics, causing accidental idle, or moving footRoot/world trace.

### RISKS
- Row 1 may be intentionally unused or visually worse; switching blindly could regress the hero.
- Authored LEFT and RIGHT frames may use different phase ordering, causing a hard reversal pop if the same column is reused without mapping.
- A settle can accidentally become input latency if implemented in physics rather than presentation; keep it visual-only.
- Mirroring can currently hide source-sheet asymmetry inconsistencies; using a distinct row may expose them.
- Camera/zoom/subpixel behavior can mimic foot slip. Keep screen-space jitter as a separate metric and do not refactor camera in this experiment.
- Future lean/rotation on pixel art can introduce new jitter; do not add rotation here.
