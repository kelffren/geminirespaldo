### PROBLEM
The live gait is distance-driven, which is the correct direction for foot planting, but `engine-ac.js` uses a fixed `MIN_VISUAL_MOVE_PX = 0.12` per update. `updateVisualMotion()` computes `dist = hypot(p.x-lastX,p.y-lastY)`, advances stride only when `dist > 0.12`, and then unconditionally writes `lastX/lastY = p.x/p.y`. Therefore any sub-threshold displacement is not accumulated for the next update: it is permanently omitted from stride distance. If update frequency changes with browser/display cadence, the same world speed can advance the gait at 60 Hz but fail to advance it at 120 Hz. This is especially relevant to slow analog joystick motion and premium lateral foot planting.

### CONFIRMED_IN_GEMINI
1. Current `main` at the start of the round is `74dc892c8883dff1c8fd6ed07ed9cb2b8880d3c5` (`Append pending ChatGPT bridge research`).
2. `index.html` still declares `Kelo World — V6.33`, loads `engine-a.js` first and `engine-ac.js` later; therefore engine-ac wraps the live `updateMovement` path.
3. `engine-ac.js` defines `MIN_VISUAL_MOVE_PX = 0.12`, `WALK_SPEED = 110`, `GAIT_IDLE_MAX = 0.03`, and uses DIRECT physics.
4. For magnitudes <= `SPEED_BLEND_START=0.48`, `speedFor()` returns 110. Because base movement multiplies normalized input by `CONFIG.speed`, actual slow-walk speed is approximately `110 * magnitude` world px/s.
5. `updateVisualMotion()` advances `strideDistancePx`, `stridePhase` and frame only when `dist > MIN_VISUAL_MOVE_PX`; afterward it always stores the current `p.x/p.y` as `lastX/lastY`, even when the movement was below the threshold. Sub-threshold displacement therefore does not accumulate across updates.
6. If update cadence is 60/90/120 Hz, the speed needed to exceed 0.12 world px in one update is approximately 7.2/10.8/14.4 world px/s. In the linear slow-walk range that corresponds to joystick magnitudes about 0.065/0.098/0.131.
7. Consequently a magnitude around 0.08 (~8.8 px/s) can exceed 0.12 px per update at 60 Hz but not at 90/120 Hz; magnitude 0.10 (~11 px/s) can exceed it at 60/90 Hz but not 120 Hz. Since `GAIT_IDLE_MAX` is only 0.03, all of these values are classified as walk while stride advancement can differ by update cadence.
8. `hasIntent` keeps `visual.on=true`, so the symptom is not necessarily idle; it can be a visually frozen or under-advancing walk pose while the world position continues to move.
9. The current `scripts/live-hero-audit.mjs` tests mobile DPR2 and desktop DPR1 but does not force/measure 60/90/120 update cadence, does not synthesize low analog magnitudes, and samples mainly after 220ms holds. It cannot detect discarded sub-epsilon stride distance.
10. `ENGINE_MAP.md` identifies `engine-a.js` as core loop/movement owner with `engine-ac.js` as gait/visual-distance owner. The map is older than current code (`V6.16` vs live `V6.33`), so code/load order remains authority.

### EXTERNAL_EVIDENCE
- MDN documents that `requestAnimationFrame()` callback frequency generally follows display refresh rate and explicitly notes common 60 Hz plus widely used 75/120/144 Hz displays. MDN warns animation progression must use elapsed time rather than a fixed per-frame amount on high-refresh screens: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame
- Godot documentation explains that per-frame `_process(delta)` cadence varies with hardware/render rate and that `delta` exists so motion can remain frame-rate independent; fixed physics processing is a separate contract: https://docs.godotengine.org/en/stable/getting_started/step_by_step/scripting_first_script.html
- Unity's current time-management documentation likewise treats per-frame duration as variable and uses delta-time/maximum-delta contracts to avoid frame-dependent simulation: https://docs.unity3d.com/ja/current/Manual/time-handling-variations.html
- Community counterevidence: a fixed epsilon is not inherently wrong. It can suppress tiny collision/subpixel noise and prevent animation jitter. The defect is specifically using a per-update displacement threshold while discarding below-threshold distance, if update cadence is variable. If Kelo's movement scheduler is proven fixed-rate independent of render refresh, the 60/90/120 severity is reduced, though discarded low-speed distance still needs measurement.

### HYPOTHESIS
The premium lateral gait should use a frame-rate-independent contact-distance accumulator. Keep the noise threshold if it is useful for direction/facing decisions, but do not discard legitimate world displacement from stride accumulation. Accumulate achieved distance continuously (or accumulate residual sub-threshold distance) and apply a time-/speed-aware noise policy separately. This should make a given joystick magnitude produce the same stride phase per world meter at 60/90/120 Hz without touching world physics.

### PROPOSED_CHANGE
Do not change production before baseline.

Candidate A — residual distance accumulator (lowest-risk):
- Continue computing achieved `dist` each update.
- Add all finite non-negative achieved distance to a `strideResidualPx`/stride accumulator.
- Use `MIN_VISUAL_MOVE_PX` only to decide whether to update directional evidence (`v.dx/v.dy`) or reject collision jitter, not whether real distance counts toward stride.
- Advance `stridePhase` from accumulated achieved distance; retain exact current `cycleWorldPxFor()` cadence contract.

Candidate B — threshold expressed as speed/time rather than per-update distance:
- Define a minimum visual speed or noise velocity and evaluate `dist / max(dt,epsilon)`.
- Still preserve residual distance so legitimate sub-threshold updates are not lost.

Do not introduce a fixed 60 Hz animation timer merely to hide the issue. Distance-driven gait is valuable and should remain distance-driven.

### RISKS
- Counting every tiny displacement can reintroduce animation twitch from collision resolution or floating-point noise.
- A residual accumulator can produce a small burst after several tiny movements if the implementation waits to consume it; prefer continuous phase accumulation once legitimate intent/movement is established, with noise classified separately.
- If actual simulation is already fixed-rate, browser refresh alone may not reproduce the predicted thresholds; still measure low-speed discarded distance because the unconditional `lastX/lastY` update remains real.
- Slow analog animation may look too busy if the authored four-frame cycle is not suitable for extremely low speeds. If Candidate A is mathematically correct but aesthetically poor, solve that later with slow-walk pose/cadence policy rather than discarding distance based on refresh-dependent frame steps.
