### PROBLEM
Current main has a real client/server movement-semantics divergence during ability casts. The authoritative server creates a cast timeline (windup -> active -> recovery) from `abilityData.action` and applies the ability's `movementScale` to requested movement on every server step. The LIVE client PvP movement hook, however, only applies dodge, melee-basic phase scaling and status multipliers. It does not apply `abilityData.action.movementScale` during local predicted casts. `KeloAbilities` dispatches/delivers the predicted/local ability but does not own a movement hook or cast movement timeline.

Result: while an ability is casting online, the local client can visually/simulated-move at full ordinary speed while the server advances that same input at a reduced ability-specific scale. This is exactly the kind of deterministic prediction mismatch that produces reconciliation corrections even with the already-shared canonical base movement profile.

### CONFIRMED_IN_GEMINI
1. Current LIVE `src/systems/pvp-world.js` installs exactly one `KeloMovement.before('pvp-world:movement-scale', movementHook, 70)`. `movementHook()` computes `s = dodge ? 0 : basicAttack ? KeloMeleeEngine.movementScaleFor(...) : 1`, multiplies `input.normX/normY` by `s`, then applies `KeloStatusEffects.movementMultiplier()`. No cast/ability movementScale is included.
2. `castArmed()` calls `KeloAbilities.engine.predict()` online (or `.cast()` offline), clears `armedSlot`, then sends the ability intent. KeloPvPWorld does not retain a local cast object/timeline analogous to `state.basicAttack`.
3. Current `src/abilities/kelo-ability-boot.js` owns ability validation/delivery/effects/cooldowns/projectiles/dash/blink/etc., but the inspected LIVE runtime has no KeloMovement hook and does not consume `def.action.movementScale` for actor locomotion.
4. `server/pvp-authority.js` imports the exact shared `abilityData.js`. `actionOf(def)` extracts `windup`, `active`, `recovery` and `movementScale`; `startAbility()` creates `_pvpCast`; server `step()` applies cast movement scale before calling `movementProfile.requestedVelocity()` displacement: when `_pvpCast` exists, `scale = min(scale, cast movementScale for current phase/scalar)`. Server also applies melee movementScale through the shared `KeloMeleeEngine`.
5. Therefore CG-021's server-risk question is partly answered: melee phase movement semantics already consume the exact shared melee profiles on both client and server. Changing `sword_light_follow.recovery` in the shared profile would naturally affect both. The more urgent mismatch is abilities: server honors `abilityData.action.movementScale`, client movement does not.
6. Current ability movementScale values are: fireball .78, ice_nova .64, chain_lightning .72, wind_dash 1.00, stone_shield .55, fire_tornado .38, ice_wall .56, shadow_step .90, poison_trap .70, light_aura .60, swap_sword .72.

At full canonical movement speed 185.28 px/s, if client remains at 1.0 while server applies one scalar over the whole action timeline, theoretical unobstructed extra client travel by cast end is approximately: fireball 11.41 px; ice_nova 22.68 px; chain_lightning 16.60 px; wind_dash 0 px from scale; stone_shield 27.51 px; fire_tornado 65.48 px; ice_wall 35.05 px; shadow_step 4.35 px; poison_trap 16.68 px; light_aura 26.68 px; swap_sword 16.60 px. These are upper-bound deterministic semantic deltas before collision/dash/blink/snapshot correction effects, not measured browser reconciliation distances.
8. `index.html` V6.54 currently loads KeloRuntimeBootstrap early and lazy-loads Combat/Effects/Status/Melee on first use; pvp-world and ability boot remain LIVE. Any audit must reproduce this current lazy boot rather than assuming old eager combat load order.

- Engine-agnostic/public authoritative networking examples converge on the same principle: the same simulation semantics should run on client prediction and server authority. One concrete reference: https://github.com/SlateGitOrg/netcode-arena

Counterevidence / constraint: action combat does not imply `movementScale=1` for every cast. Deliberate cast commitment can be desirable for telegraph readability and balance. The defect here is not that scales are below 1; it is that client and server currently do not predict the same scale/timeline.

### HYPOTHESIS
H1: The dominant online cast-movement problem is prediction parity, not the numerical values themselves.
H2: Adding one client-side cast presentation/prediction state that consumes the SAME `abilityData.action` contract can eliminate most deterministic cast-position divergence without changing server authority.
H3: The correct owner is likely KeloPvPWorld's existing combat orchestration + movement hook, consuming published ability action state from KeloAbilities or a minimal reusable cast-state contract; do NOT add a second movement manager.
H4: A quick fix that merely checks `armedSlot` is wrong because `armedSlot` is cleared immediately after cast and does not represent windup/active/recovery.
H5: A quick fix that scales input for a fixed timeout is also wrong because action timings differ per ability and future sources (weapon/mount) should reuse the same timeline semantics.
H6: Once parity exists, individual ability movement scales can be tuned for feel separately. Do not flatten the numbers during the parity pass.

### PROPOSED_CHANGE
Do not retune ability values yet. First build a deterministic client-vs-server cast-movement parity audit using current production sources.

Preferred architecture if the audit confirms the mismatch:
1. Reuse the existing ability `action` data as canonical timing/movement semantics.
2. Expose a minimal local predicted cast lifecycle from the existing ability/PvP owner boundary (cast id, ability key, phase, phase time/remaining, movementScale). Do not create a new engine/manager.
3. Let the existing `pvp-world:movement-scale` hook combine movement permissions/scales from dodge, melee attack, predicted cast and status effects using the same composition rule as server authority (`min` for simultaneous action commitments, multiplicative status movement multiplier).
4. Keep server authoritative. Client cast state is prediction/presentation and must be reconciled/cleared by authoritative snapshots/events where available.
5. Preserve mobility deliveries (`wind_dash`, `shadow_step`, swap) as their own movement/delivery contracts; do not make ordinary locomotion fight the dash/blink owner.

### RISKS

- Local ability delivery is currently immediate/predicted in KeloAbilities while server has windup/active/recovery state. Movement parity may expose a broader cast-timeline presentation mismatch; do not silently refactor all ability delivery in the same pass unless the audit proves it is inseparable.

- Simultaneous status slow + cast + melee/dodge composition must match server ordering (`min` action commitment, then status multiplier), otherwise a second mismatch replaces the first.
- Browser 90/120 Hz presentation vs server fixed 60 Hz requires dt-aware phase prediction and deterministic boundaries.
- Current ENGINE_MAP load-order prose is stale relative to V6.54 lazy bootstrap; tests must follow index/runtime, not documentation alone.
