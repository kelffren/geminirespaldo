### PROBLEM
The LIVE lateral start transition has a presentation discontinuity that is separate from steady-state cadence. `engine-ac.js` initializes/settles visual locomotion at authored `PLANT_FRAME=2` / `PLANT_PHASE=0.5`, while `src/characters/character-appearance.js::frameColumn()` renders column 0 whenever `motion.moving === false`. When movement begins, `motion.moving` becomes true and the renderer immediately consumes `visual.frame`, which is still frame 2. Therefore the visible transition is currently idle column 0 -> locomotion column 2 on the first moving render, skipping the intermediate authored pose. Because stride is distance-driven, frame 2 then remains selected until phase reaches 0.75. That requires 0.25 of a cycle: 12.5 world px with the 50px walk cycle and 22.5 world px with the 90px max-run cycle. With DIRECT movement, this can create a visually planted frame that translates for ~0.12–0.24s before the next pose, depending on analog magnitude. This can read as a start-slide even if steady-state stride cadence is acceptable.

### CONFIRMED_IN_GEMINI
Current `main` at the baseline above:
- `engine-ac.js`: `DEFAULT_PLANT_FRAME=2`, `PLANT_PHASE=PLANT_FRAME/4`, new `_visualMotion` starts at frame 2 / phase 0.5, and non-moving state resets to frame 2 / phase 0.5.
- `engine-ac.js`: stride phase advances only from actual resolved world distance; next frame from phase 0.5 is frame 3 at phase >=0.75.
- `engine-ac.js`: `RUN_CYCLE_WORLD_PX=90`, `WALK_CYCLE_WORLD_PX=50`.
- `engine-a.js`: `CONFIG.movementType='DIRECT'` is set by engine-ac and the base movement owner then assigns `localPlayer.vx=targetVx`, `vy=targetVy` immediately, with no acceleration ramp in DIRECT mode.
- `src/characters/character-appearance.js`: `frameColumn()` first executes `if (!motion.moving) return 0;`, and only then uses `motion.frame`. Thus idle visibly uses frame 0 even though the movement owner says the semantic plant pose is frame 2.
- On movement start, `motion.moving` switches true and the same renderer can immediately jump from visible frame 0 to semantic frame 2.
- At analog magnitude 0.48: target speed is about 52.8 world px/s (`mag * speedCap`, speedCap=110), 12.5px to frame 3 is ~237ms.
- At magnitude 0.70: cycle is still ~50px at the run threshold and the first quarter-cycle is 12.5px; target speed is roughly ~97px/s, ~129ms.
- At magnitude 1.0: target speed is ~185.28px/s and cycle is 90px; 22.5px to frame 3 is ~121ms.
These durations are distance-derived, so the intended phase timing is mostly refresh-rate independent; render sampling at 60/90/120Hz can still change the first visible-frame boundary.

### EXTERNAL_EVIDENCE
- Epic Games' Unreal Engine locomotion documentation describes movement and animation playback as a synchronized system and specifically provides Distance Matching to select animation poses based on distance rather than time, including XY locomotion transitions such as start/stop/pivot. This supports Kelo's existing distance-driven stride approach but also implies start/stop transitions should deliberately map displacement to appropriate poses rather than rely on an incidental idle->cycle phase jump.
- Epic's Distance Matching documentation states animation playback can be advanced by distance traveled and that this reduces disruption when character speed changes. This is conceptually close to Kelo's current stridePhase-by-distance design.
- Epic's Pose/Stride Warping documentation explicitly targets matching animated stride to capsule/root movement speed to reduce foot sliding.
- Community evidence from r/godot (2026-03-18) on pixel-animated sprites converges on matching how far the feet move in the animation to how far the character moves in-game, potentially per frame; users note otherwise the character appears to skate. Another r/gamemaker case describes direction tapping causing a character to slide in idle because the walking animation does not enter an appropriate first walk frame immediately.
- Counterevidence: a dedicated start animation or forced first-step pose can add input latency or make rapid PvP tapping look sticky. Kelo must not delay physical response simply to satisfy animation. The visual transition must remain presentation-only unless testing proves otherwise.

### HYPOTHESIS
The premium-feel issue at movement onset is not primarily that Kelo needs acceleration. It is that the renderer and movement owner disagree on idle pose ownership, causing visible frame 0 -> 2 discontinuity, followed by a relatively long first translated hold of frame 2. A small start-phase policy, still distance-driven and presentation-only, may improve lateral weight without changing physics. The best policy may be different for touch walk and keyboard/full-run.

### RISKS
- Resetting phase on every noisy intent edge can create pose chatter; only true stable off->on transitions should be eligible.
- Forcing a visually active start pose may look worse during tiny analog movement.
- Unifying idle to frame2 may expose that frame2 was authored as a walk contact pose rather than a comfortable sustained idle.
- A dedicated start clip increases art/logic complexity and should be deferred unless the four-frame loop cannot cover the transition.
- Changing movement acceleration would alter PvP responsiveness and is outside this proposal.
