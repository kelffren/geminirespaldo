### PROBLEM
The shared appearance renderer now has per-frame foot anchors, but its presentation bounds and its actual draw transform are not governed by the same contract. Before increasing the player to 1.20x or migrating the player off the legacy renderer, we need to prove that visualWidth/visualHeight, source-foot anchors, destination rect, shadow/nameplate/occlusion bounds and collision remain coherent across facing changes and appearances.

### CONFIRMED_IN_GEMINI
1. Current main was re-read. The locomotion owners remain engine-a.js + engine-ac.js and the local hero remains engine-ab.js; the newest commits inspected during this round touched visual/world reset and legacy plaza decoration rather than these locomotion owners.
2. engine-ab.js exposes KELO_AVATAR_PRESENTATION with a nominal side visualWidth of round(48*1.15)=55 px and visualHeight about 93 px. Its local player draw uses those destination dimensions directly, with colliderRadius remaining p.radius and footRootY=p.y+10.
3. src/characters/character-appearance.js does NOT use layout.visualWidth to determine the generic actor draw width. It computes one scale from targetBodyHeight/layout.visualHeight divided by metrics.bodyHeight, then draws the full 256x384 source frame at dw=256*scale and dh=384*scale.
4. For bot_crimson_v1, authored bodyHeight differs strongly by face: down 303, left 302, right 369, up 307. At targetBodyHeight 93 this produces full-frame destination widths of about 78.6 px (down), 78.8 px (left), 64.5 px (right), 77.6 px (up), while the presentation contract still reports a side visualWidth around 55 px. These are destination-canvas rectangles, not guaranteed opaque silhouette widths, but they prove the declared presentation width is not the actual draw width.
5. The generic renderer correctly uses per-frame footX/footY anchors and keeps the world footRoot stable, but audit.lastDraw currently exposes destinationRect and sourceFootAnchor without validating that the declared presentation bounds contain the pixels actually drawn.
6. scripts/live-hero-audit.mjs validates local-player visualScale, collider, footRoot and 1.15x enlargement. It does not currently validate a generic actor's actual destination rectangle against presentation visual bounds, nor direction-to-direction bound stability.
7. engine-ac.js remains distance-driven for the local player's stride and should not be altered by this experiment.

### EXTERNAL_EVIDENCE
- Unity's 2D Pixel Perfect guidance recommends a consistent Pixels Per Unit value for sprites and per-sprite pivots in pixel units. This supports separating a stable world-space scale contract from per-frame pivot metadata rather than deriving unrelated display scales ad hoc per pose. Source: Unity Manual, 2D Pixel Perfect sprite preparation.
- Godot Sprite2D exposes frame/region, offset and get_rect(), reflecting the common separation between source region/pivot/offset and the render-space rectangle that downstream systems can query.
- A Godot community report on animation jitter identifies changing sprite dimensions between poses as a visible source of outline jitter; another Unity2D community example resolved moving feet by correcting per-frame pivots. These are community observations, not engine guarantees, but they align with the need to measure both anchors and visible bounds.
- Counterevidence: different animation poses can legitimately have different source extents/aspect ratios. Therefore the experiment must not force every frame into an identical rectangle or distort art merely to satisfy a numeric width target. A stable pixels-per-world scale plus explicit pivot/bounds metadata is preferable to per-frame stretching.

### HYPOTHESIS
Kelo's next renderer contract should use one stable appearance-level pixels-to-world scale (or equivalent nominal body scale) and explicit per-frame pivot + visible bounds. presentation.visualWidth/visualHeight should describe or be derived from the actual rendered visible bounds, not coexist as nominal numbers that generic draw code ignores. This will make 1.20x scaling, nameplates, shadows, occlusion/culling and future online actors predictable while preserving collider size.

### PROPOSED_CHANGE
Do not change production scale yet. First add a pure measurement path for generic appearances:
- appearanceScale: stable per appearance (candidate), independent of current face;
- sourceRect per frame;
- sourceFootAnchor per frame;
- sourceVisibleBounds per frame (opaque bounds or authored metadata);
- destinationVisibleBounds derived from scale + anchor;
- declaredPresentationBounds from the current presentation contract.

Then compare current per-face bodyHeight normalization against a candidate stable appearance-scale mode without changing physics, input, gait, camera or collider. If stable scale makes authored left/right size mismatch visually worse, preserve per-face normalization but make presentation bounds truthful and measure reversal silhouette continuity explicitly.

### DO_NOT_ASSUME
- Do not assume the full destination canvas rectangle equals the opaque character silhouette.
- Do not assume bot_crimson's left/right bodyHeight difference is an art bug; it may include perspective or authored cropping differences.
- Do not force visualWidth=55 by stretching source art horizontally.
- Do not migrate player_hero_v1 away from delegateToLegacyHero until the same trace proves parity.
- Do not change colliderRadius, footRoot, camera, speed, cadence or network state in this experiment.

### EXPERIMENT
Baseline A (current renderer):
1. Add a synthetic/generic actor to the existing Playwright harness without altering local-player physics.
2. For down/left/right/up and frames 0..3 record: layout.visualWidth/visualHeight, scale, sourceFootAnchor, destinationRect, derived destination visible bounds, footRoot and colliderRadius.
3. Run 30 left<->right reversals at walk and run visual cadence; record screen-space top/left/right/bottom of visible silhouette and footRoot.
4. Repeat mobile 390x844 DPR2 and desktop 1280x720 DPR1.

Candidate B:
5. Hold one appearance-level scale constant across faces; preserve the same per-frame foot anchors.
6. Run the identical trace and compare silhouette size continuity, pivot error and bounds truthfulness.
7. Do not ship B unless screenshots and metrics both improve. If B worsens perspective/art fidelity, reject stable-scale rendering and instead keep face-specific scaling while deriving truthful bounds from actual transformed visible pixels.

Only after A/B is understood should a player 1.15x -> 1.20x trial run, with the same collider and world trace.

### RISKS
- Opaque-bound scanning in runtime can be expensive if repeated; preprocess once or author metadata, never scan every frame.
- A single appearance-wide scale could expose genuine source-art inconsistencies that per-face normalization currently hides.
- Tight bounds can cause nameplate/occlusion jitter if they change every frame; downstream systems may need an appearance-level conservative envelope plus per-frame pivot.
- Increasing to 1.20x before this contract is coherent can magnify bound mismatches and unexpected occlusion.
