PROBLEM
Kelo PvP predicted ability delivery locally but did not retain the same windup/active/recovery movement timeline that server/pvp-authority enforces through `_pvpCast`. During a cast the client could therefore move at full locomotion while the future authoritative simulation moved at ability movementScale. The gap was especially large for Fire Tornado (.38), risking visible reconciliation/rubberbanding once server authority is connected.

CONFIRMED_IN_GEMINI
Current main `pvp-world.js` castArmed() invokes KeloAbilities prediction/cast and sends the ability intent but its existing movement hook only composes dodge, melee and status. `server/pvp-authority.js` stores `_pvpCast`, applies min(meleeScale, castScale), then status movement multiplier, moves the actor, and only then advances the cast phase. Ability action data remains canonical in `src/abilities/abilityData.js`.

EXTERNAL_EVIDENCE
No new outside balance assumption was required in this execution round. The acceptance evidence is stronger: deterministic client/server traces plus actual Chromium runtime on mobile and desktop using the live Kelo code. Existing design goal remains local responsiveness with server-authoritative parity rather than waiting for round-trip confirmation.

HYPOTHESIS
A tiny pure shared ability action timeline plus a PvP prediction adapter should eliminate cast movement semantic debt without creating another movement owner. The adapter must compose with melee using min(), exactly as authority does, rather than multiply meleeScale * castScale.

PROPOSED_CHANGE
Create `KeloAbilityActionTimeline` pure normalize/create/movementScaleFor/advance primitive. Bind a PvP adapter to KeloAbilities `ABILITY_CAST`, maintain only ephemeral predicted cast phase, and apply an input factor before the existing PvP movement hook such that final movement is min(meleeScale, castScale) * status. Load all support through the existing central KeloRuntimeBootstrap; PvP loader only calls ensure()/bind().

DO_NOT_ASSUME
Do not change ability movementScale balance values in the same parity repair. Do not create a second script loader, movement manager, game loop, timer owner or authority path. Do not multiply melee and cast slowdowns. Do not infer that Fire Tornado .38 is a good feel value merely because parity is now correct; that is a separate A/B.

RISKS
The shared primitive currently preserves the server's existing phase-step semantics, including discarding overshoot at phase transitions. Changing server phase stepping later must update this shared contract or migrate server authority to consume the primitive directly. Ability delivery visuals can still have startup/impact timing differences independent of movement. Now that local prediction exposes real movementScale, restrictive values such as Fire Tornado .38 may feel too heavy and require a separate feel A/B.
