### PROBLEM
The live PNG avatar already exposes a presentation contract with separate visual bounds, footRoot, depthRoot and colliderRadius, but generic prop occlusion does not consume that contract. It still tests actor overlap using actor.x/actor.y and actor.radius, and depth decisions use actor.y directly. This means enlarging the avatar from 1.15x toward 1.20x can increase visible sprite coverage without expanding the spatial region that triggers occlusion/redraw. The result can be a visually larger character whose head/shoulders/side silhouette intersect foliage or props while the occlusion system still believes the actor is outside the prop interaction area.

### CONFIRMED_IN_GEMINI
At BASE_COMMIT, index.html declares Kelo World V6.52 and loads engine-ab.js before generic-props consumers and plaza-depth.js later.

engine-ab.js defines AVATAR_VISUAL_SCALE=1.15 and presentationOf(). For lateral facing it uses baseVisualWidth=48 and baseVisualHeight=round(54*(FH/FW)); with the current nominal frame ratio 384/256 this is 81. Therefore the live lateral destination is approximately 55x93 world px at 1.15x. presentationOf() separately publishes colliderRadius=p.radius, footRoot, depthRoot, shadowAnchor, visualLeft/Top/Right/Bottom, and nameplateAnchor.

src/environment/generic-props.js does not call KELO_AVATAR_PRESENTATION. Its overlaps(actor,bounds) uses actor.radius (default fallback 20) around actor.x/actor.y. For actor-base-y-clip-v1 it decides occlusion with actor.y < prop.occlusion.baseY and redraws the prop only when the radius-based overlap test passes. For actor-base-y-redraw-v1 it similarly decides using actor.y > baseY and radius-based overlap, then redraws renderAvatar(actor).

At radius 20, the generic occlusion overlap region is about 40 world px wide while the current lateral visible sprite is about 55 world px wide. At a QA-only 1.20x, lateral width would be about 58 world px while the overlap radius remains 20 unless physics is changed. The visual top also extends far above actor.y: current footRoot is actor.y+10 and current visual height is about 93, giving visualTop around actor.y-83, whereas overlap Y still uses actor.y +/- radius.

src/environment/prop-contract.js currently applies actor-base-y-clip-v1 to plaza nature and actor-base-y-redraw-v1 to the 720x720 plaza fountain. plaza-depth.js reports fountain depth from localPlayer.y relative to baseY=1505, not from the exported depthRootY.

This is not a claim that current occlusion is visibly broken everywhere. It is a confirmed mismatch between visual presentation bounds/depthRoot and the generic occlusion contract.

### EXTERNAL_EVIDENCE
Unity 6 2D sorting documentation explicitly supports a Sprite Sort Point based on a sprite Pivot rather than only its geometric center, and 2D Y sorting commonly uses a deliberate position/pivot contract for depth. Source: https://docs.unity3d.com/6000.0/Documentation/Manual/2d-renderer-sorting.html

Unity SpriteAlignment exposes BottomCenter and Custom pivots, reinforcing that the render/depth reference can be separated from the sprite rectangle and collider. Source: https://docs.unity3d.com/6000.0/Documentation/ScriptReference/SpriteAlignment.html

Community counterexample: large/tall 2D sprites can pop in front/behind long props when sorting is driven by an unsuitable pivot; a Unity2D discussion documents exactly this class of issue with a character pivot at the feet and large tree-wall sprites. Source: https://www.reddit.com/r/Unity2D/comments/15oou4a/

Counterevidence: physics collider bounds should NOT automatically grow with visual scale. Keeping a smaller collider is often intentional for movement feel. Therefore the proposed research does not couple collision radius to visual size; it tests a separate presentation/occlusion bounds contract.

### HYPOTHESIS
A dedicated actor presentation/depth query for occlusion can preserve the current collider while making foliage/prop occlusion robust to avatar scale. The likely correct split is:

- physics overlap/collision continues using p.radius and physicsRoot;
- depth ordering uses KELO_AVATAR_PRESENTATION.depthRootY (or a deliberately measured equivalent);
- visual occlusion eligibility uses visualBounds or a smaller authored occlusionBounds derived from the presentation contract, not the physics collider;
- clip/redraw regions remain independently tunable so a huge full-sprite rectangle does not cause excessive redraw work.

At current constants depthRootY = actor.y+10, so blindly swapping actor.y to depthRootY would shift the fountain threshold by 10 world px. That must be benchmarked rather than assumed correct.

### PROPOSED_CHANGE
Do not change production yet. Add QA-only instrumentation and compare:

A — baseline: radius-based overlaps + actor.y depth decisions.

B — visual-overlap diagnostic: use KELO_AVATAR_PRESENTATION visual bounds only for deciding whether the actor visually intersects a prop; keep actor.y for depth decision.

C — ground/depth-root diagnostic: use a compact occlusionBounds centered on footRoot/depthRoot (for example width derived from visual width but vertical extent biased upward) and use depthRootY for front/behind threshold.

D — hybrid candidate: keep physics radius for collision, use visual/occlusion bounds for eligibility, and preserve an explicit per-prop baseY contract for front/behind sorting. This is the preferred architecture only if measurements show B/C improve real overlap errors without causing excess redraws.

Do not enlarge p.radius just because the sprite is enlarged.

### DO_NOT_ASSUME

Do not assume depthRootY=footRootY is automatically the perfect Y-sort reference for every prop.
Do not assume the existing fountain baseY should be shifted by +10.

### RISKS
Using the full visual rectangle can over-trigger occlusion because transparent/head/nameplate regions do not necessarily need cover. Larger eligibility bounds can increase redraw work. Switching depth comparison from actor.y to footRoot/depthRoot may move existing tuned thresholds by 10 world px and break fountain ordering. A presentation query in a hot loop can add overhead if implemented carelessly, although the arithmetic itself is small. Different facings have different visual widths, so an occlusion bound tied directly to sprite width may chatter on LEFT/RIGHT vs UP/DOWN transitions unless hysteresis or a stable authored occlusion footprint is used.
