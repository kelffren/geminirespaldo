PROBLEM
`engine-a.js::updateMovement()` continuously computes `localPlayer.squashX` and `squashY` from `currentSpeed / CONFIG.speed`, but the current production `engine-ab.js` PNG hero renderer does not consume those values. This is latent/dead presentation state in the movement owner. More importantly, connecting it directly to the sprite would be unsafe for the current premium-foot-planting goal: a center-based scale would move the visible foot/root, and the source signal is velocity magnitude rather than actual resolved world displacement, so Kelo can remain visually stretched while pushing against a blocking collider.

CONFIRMED_IN_GEMINI
- Current `main` title is Kelo World V6.43. `index.html` loads `engine-a.js?v=150`, `engine-ab.js?v=240`, `character-appearance.js?v=2`, and `engine-ac.js?v=222`; current code supersedes older ENGINE_MAP snapshots.
- `engine-a.js` initializes `localPlayer.squashX=1`, `squashY=1` and every movement update eases toward `1 + (currentSpeed/CONFIG.speed)*0.08` on X and `1 - (currentSpeed/CONFIG.speed)*0.06` on Y with exponential decay 15.
- `engine-ac.js` forces `CONFIG.movementType='DIRECT'` and wraps `updateMovement()` after setting `CONFIG.speed=speedCap`. In unobstructed motion, `currentSpeed/CONFIG.speed` therefore approximately equals processed joystick magnitude; it is not a measurement of authored foot motion.
- Collision resolution in `engine-a.js` corrects `localPlayer.x/y` after velocity has already been set, but does not zero/recompute `vx/vy` from the resolved displacement. Therefore `currentSpeed` can stay high while actual world displacement is near zero against an obstacle.
- `engine-ab.js::renderAvatar()` derives `footRoot`, `visualWidth`, and `visualHeight`, then draws the PNG directly with fixed width/height; no `squashX`, `squashY`, body lean, or body-local bob transform is applied there.
- `KELO_AVATAR_PRESENTATION` already publishes `footRoot`, `depthRoot`, `shadowAnchor`, and visual bounds, giving the correct semantic anchor around which a QA-only presentation transform can be tested without changing physics.
- `src/systems/armor-aura.js` wraps the final `renderAvatar`; aura ground/body effects are drawn outside the PNG draw call. Any future body-local transform must not accidentally rotate/scale the ground ring or shadow anchor.

EXTERNAL_EVIDENCE
- Godot's current cutout-animation documentation explicitly treats pivot placement as the basis for safe rotation/translation of 2D sprite parts; it recommends adjusting the Sprite2D pivot/offset so transforms occur around the intended point: https://docs.godotengine.org/en/4.x/tutorials/animation/cutout_animation.html
- Unity SpriteRenderer documentation separates visual sprite pivot/sort point from other object semantics, supporting the same principle: presentation transforms should be authored around an intentional pivot rather than the texture rectangle center: https://docs.unity3d.com/2023.1/Documentation/Manual/class-SpriteRenderer.html
- Community counterevidence: squash/stretch on direction changes can add responsiveness, but practical implementations frequently suffer from scale not returning correctly or remaining distorted while input is held, showing that a continuously input/velocity-driven scale can easily become visually persistent rather than a short secondary-motion accent: https://www.reddit.com/r/gamemaker/comments/12i1l95/
- Counterevidence to adding any transform: the authored four-frame sprite may already encode sufficient body motion. If QA-only lean/squash does not improve perceived weight or introduces shimmer/foot drift, leave the live renderer untransformed and remove/deprecate the unused core squash state later in a separate refactor.

HYPOTHESIS
A small, presentation-only BODY_LOCAL transform can improve lateral weight and acceleration/reversal readability, but it should be anchored at `footRoot`, driven from actual resolved displacement/intent transitions rather than raw velocity magnitude alone, and kept separate from GROUND_LOCAL elements such as shadow/aura/depth. The existing `squashX/Y` values should not simply be wired into the PNG renderer.

PROPOSED_CHANGE
Do not change production first. Add QA telemetry and compare:
A) baseline: current PNG renderer with no body-local transform;
B) naive control: consume existing `squashX/Y` around the current sprite center only to demonstrate whether it causes foot-root drift or blocked-wall distortion; do not ship this candidate;
C) foot-root-anchored micro-transform: apply only to the sprite body, not ground effects/nameplate. Start conservatively with lateral lean/scale caps small enough to remain visually subordinate to authored frames (for example <=2-3 degrees lean and <=2-3% scale deviation) and derive activation from actual resolved lateral displacement plus acceleration/reversal events. Exact values must come from measurement.
D) foot-root-anchored lean-only control with no squash, to determine whether scale deformation adds value beyond directional body tilt.
Implement candidates only behind QA/query flags. Keep physics, collider, world position, stride phase, source-frame sequence, camera, depthRoot, shadowAnchor and aura ring world geometry unchanged.

DO_NOT_ASSUME
- Do not assume squash/stretch is desirable merely because the core already computes it; current PNG art may look better untouched.
- Do not drive the final transform only from `vx/vy`; blocked collisions can preserve velocity while resolved displacement is zero.
- Do not transform around sprite center. The feet/ground anchor must remain invariant for a planted look.
- Do not transform nameplate, shadow/contact ring, depth root, collider, hitbox, aura ground ellipse, or camera.
- Do not combine this benchmark with 1.20x avatar scale, native LEFT row, per-frame foot pivots, cadence changes, DPR changes, facing hysteresis, contact shadow changes, or subpixel snapping.
- Do not refactor the duplicated movement/presentation ownership in the same patch. First baseline -> isolated transform -> same trace -> re-measure.

RISKS
- Even tiny non-integer rotation/scale with nearest-neighbor rendering can increase edge shimmer, especially under non-integer zoom/DPR.
- Lean can make the character appear to float if pivot anchoring is wrong by even a few pixels.
- Squash can alter apparent limb proportions and reduce authored sprite quality when Kelo is enlarged later.
- Driving from resolved displacement can become noisy at collision boundaries; signal design may require low-pass filtering, but filtering must be frame-rate independent and benchmarked at 60/90/120 Hz.
- Existing `squashX/Y` state is updated in the physics owner even though it is presentation data; eventual cleanup may be warranted, but removing/moving it now would be an attribution-breaking refactor.
- Aura/body glow wrappers may visually disagree with a transformed body if their body-local vs ground-local responsibilities are not separated explicitly.
