### PROBLEM
The current camera follow computes `deadW = screenW * CONFIG.deadXRatio` and `deadH = screenH * CONFIG.deadYRatio`, then compares those values directly against world-space deltas `(localPlayer + lookOffset) - camera.target`. The renderer later applies `CONFIG.zoom`. Therefore a nominal 10% horizontal dead-zone is not 10% of the visible screen after zoom; its visible fraction is approximately `deadXRatio * effectiveZoom`. `lookAheadDist` is also a world-space distance, so its visible lead in CSS pixels varies with effective zoom/orientation.

### CONFIRMED_IN_GEMINI
- `engine-a.js` camera follow computes dead-zone dimensions from CSS viewport dimensions (`screenW`, `screenH`) but compares them with world coordinates before render zoom.
- `engine-c.js` renders the world with `ctx.scale(CONFIG.zoom, CONFIG.zoom)` around screen center.
- `src/core/camera-system.js` owns effective zoom and, in landscape, uses `effectiveZoom = baseZoom * (innerHeight / innerWidth)` to preserve vertical world span.
- `engine-z.js` keeps base zoom orientation-invariant and reduces look-ahead to 36 world px when it exceeds 40.
- Existing camera browser CI verifies viewport/DPR, screen↔world round-trip, base/effective zoom and orientation/FOV invariants, but does not measure the on-screen dead-zone or on-screen look-ahead distance.
- Current default camera tuning inherited from `engine-a.js` is `deadXRatio=0.10`, `deadYRatio=0.08`, `dampX=dampY=8`, while `engine-z.js` caps lookAheadDist to 36 world px.

Representative math from current formulas (not a LIVE measurement):
- 390×844 portrait: base/effective zoom ≈ 390/(11*32)=1.108. Horizontal dead-zone visual fraction ≈ 10%*1.108 = 11.08%; 36-world-px look-ahead ≈ 39.9 CSS px.
- Same device 844×390 landscape: base remains ≈1.108, effective zoom ≈1.108*(390/844)=0.512. Horizontal dead-zone visual fraction ≈5.12%; 36-world-px look-ahead ≈18.4 CSS px.
Thus rotating the same phone can approximately halve both the visible horizontal dead-zone fraction and visible look-ahead despite preserving vertical FOV.

### EXTERNAL_EVIDENCE
- Unity Cinemachine documentation defines Dead Zone Width/Height as a screen region in which target motion is ignored, and Screen X/Y as screen positions. This is evidence that a composition dead-zone is commonly treated as screen-space behavior rather than unscaled world distance: https://docs.unity3d.com/ja/Packages/com.unity.cinemachine@2.6/manual/CinemachineAimComposer.html
- Godot Camera2D defines drag margins as normalized screen margins; a margin value of 1 means waiting until the corresponding screen edge is reached: https://docs.godotengine.org/en/4.2/classes/class_camera2d.html
- Godot docs issue #7774 notes that small camera drag margins can materially affect perceived pixel-perfect camera jitter, showing that dead-zone sizing is a perceptual camera-control parameter, not merely geometry: https://github.com/godotengine/godot-docs/issues/7774
- Community counterevidence: dead-zones can intentionally create delay/lag before the camera follows, and some developers prefer disabling them for immediate camera movement. Therefore no assumption is made that a normalized dead-zone is automatically better: https://www.reddit.com/r/godot/comments/bp34ze/

### HYPOTHESIS
Part of the inconsistent lateral camera feel between portrait, landscape and desktop may come from mixing screen-derived dead-zone values with world-space comparison and from keeping look-ahead in fixed world pixels. If the intended product behavior is compositionally consistent framing, converting screen-space targets into world-space using effective zoom before comparison should reduce orientation/zoom variance without changing player physics. However, the current world-space behavior may be intentional and could feel better; this must be benchmarked.

### PROPOSED_CHANGE

B) Screen-consistent dead-zone only: compute world dead-zone as `(screenW * ratio) / effectiveZoom` and `(screenH * ratio) / effectiveZoom` (or equivalent KeloCamera helper), keeping look-ahead unchanged.
C) Screen-consistent look-ahead only: define a desired CSS-pixel lead and convert to world units through effective zoom, keeping dead-zone baseline.
D) B+C only if each isolated candidate improves the same reproduction.
All tuning ownership should remain in `KeloCamera`; do not add another camera wrapper or write CONFIG.zoom directly.

### RISKS
- A normalized screen dead-zone can feel too loose when zoomed out or too restrictive in some combat contexts.
- Converting look-ahead to screen-space may expose more world in one orientation and change anticipation around hazards/props even without changing camera FOV.
- Camera edge clamps can mask results near world boundaries; run tests away from edges.
- `roundPixels=true` plus fractional effective zoom can create visible jitter that is orthogonal to dead-zone composition; record it but do not conflate with this experiment.
- PvP/ability focus paths may temporarily command camera targets; isolate normal locomotion first.
