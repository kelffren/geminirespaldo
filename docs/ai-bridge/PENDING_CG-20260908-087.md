### PROBLEM
The live PNG hero path has a semantic `shadowAnchor` at the foot root, but the PNG renderer itself does not draw a ground/contact shadow. The older/base `renderAvatar` path does draw an oval shadow before drawing the procedural body, yet `engine-ab.js` replaces the hero render path when `assets/hero.PNG` is ready and does not call that base renderer on successful PNG draws. The final visual integration wrapper only applies BODY_LOCAL transform/FX and calls the definitive renderer; it does not add a ground shadow. Therefore the current live PNG hero can have a published shadow contract without a confirmed shadow consumer. This matters directly to lateral foot planting: a stable ground-local contact cue can make a large sprite feel planted, while tying a shadow to body bob/lean can recreate the old floating failure documented in engine-ah.js.

### EXTERNAL_EVIDENCE
- Perception research by Ni, Braunstein & Andersen (Perception, 2004, “Perception of Scene Layout from Optical Contact, Shadows, and Motion”) found that shadow motion can materially affect perceived object position/depth, supporting the use of a correctly coupled contact cue rather than treating it as decorative only: https://journals.sagepub.com/doi/10.1068/p5288
- A 2021 review of Gibson's ground theory emphasizes perceived contact with the ground as foundational to spatial layout judgments: https://doi.org/10.1177/20416695211021111
- Current game-dev community practice commonly uses a cheap circular/blob shadow directly under characters as the simplest 2D grounding solution; a 2026 IndieDev comparison reported that added foot/contact shadows made the character read as more grounded, including on low-spec targets: https://www.reddit.com/r/IndieDev/comments/1qoriji/i_didnt_realize_how_much_of_a_difference/
- Counterevidence: a gamedev ground-shadow example received feedback that even attractive shadows make characters look like they float when the shadow's ground position detaches from the character. This supports measuring contact alignment, not simply adding more shadow detail: https://www.reddit.com/r/gamedev/comments/c70xht
- Counterevidence/performance-quality risk: Godot issue #35606 and related pixel-snap issues demonstrate that camera smoothing/subpixel transforms can create one-pixel jitter in 2D sprites. Kelo should not assume a vector ellipse and a nearest-neighbor sprite will remain visually phase-locked under fractional zoom: https://github.com/godotengine/godot/issues/35606 and https://github.com/godotengine/godot/issues/71074

### HYPOTHESIS
A small, stable GROUND_LOCAL contact shadow centered on the existing semantic shadow/foot anchor will improve lateral grounding and make 1.20x avatar scale safer perceptually, provided it is not transformed by BODY_LOCAL bob/lean and does not introduce relative sprite-shadow jitter under fractional zoom. The shadow should represent contact/physical footprint rather than define collider size, and its dimensions should not automatically scale one-to-one with avatar visual scale.

QA B minimal contact-shadow candidate: draw one low-alpha ellipse in a dedicated GROUND_LOCAL stage using the existing `shadowAnchor`/`foot` anchor before BODY_LOCAL transforms. Start from the old base-renderer dimensions as a reference, but do not copy them blindly; tune via measurements and screenshots.
QA C phase-alignment candidate: same B shadow, but compare continuous world-coordinate anchor versus a shadow anchor snapped to the same effective visual/device-pixel phase as the PNG destination. Choose only if B shows measurable relative jitter.
QA D scale behavior: compare keeping shadow footprint constant from avatar 1.15x→1.20x versus very modest visual scaling. Collider remains unchanged in both cases. Do not let shadow dimensions redefine physics or occlusion bounds.
Architecture guardrail: avoid putting the shadow inside `visual-integration.js`'s BODY_LOCAL transform scope, because rotation/squash/bob would move/deform the ground cue with the body and recreate the failure described in engine-ah.js. If a shared owner is eventually warranted, place it before BODY_LOCAL transform or in a dedicated ground FX layer and prove no double-draw first.

### RISKS
- Static code inspection can miss a shadow baked into `hero.PNG`, a map-level effect, or a dynamically installed runtime owner; LIVE screenshot/pixel verification is mandatory before implementation.
- A generic oval can look cheap or overly dark. The goal is contact grounding, not a large dramatic projected shadow.
- Drawing a smooth Canvas vector ellipse under a nearest-neighbor sprite may make relative subpixel phase differences more visible under fractional zoom. Candidate C exists only for measured evidence of this.
- Scaling the blob with avatar visual size can accidentally imply a larger physical footprint even though collider remains fixed; test constant/very modest footprint scaling.
- Incorrect render order can cause the blob to paint over foreground props or appear through occluders.
- Reusing the final actor transform wrapper for the shadow would couple ground and body again and could recreate the exact floating problem already documented in engine-ah.js.
