### PROBLEM
The runtime hero preprocessing audit introduced in CG-20260905-003 had one semantic false-positive: `sheetMutationAfterIdle` was derived from every RGB>232 match (`affected > 0`), including pixels whose source alpha was already zero. Setting alpha 0 -> 0 is not a visible alpha mutation. Using that boolean to decide whether `knockWhite()` changes Kelo could therefore produce a false positive. Separately, the existing LIVE Playwright harness did not collect `KELO_HERO_SPRITE_AUDIT`, so the new counters were not automatically captured as evidence.

### EXTERNAL_EVIDENCE
- MDN documents `ImageData.data` as RGBA pixel data and `getImageData()`/`putImageData()` as reading and writing those underlying values. A visible knockout mutation requires a source pixel with non-zero alpha to become zero-alpha; an already transparent pixel matching the RGB threshold is not a visible alpha change.
- MDN also warns that get/put image data can be subject to representation details such as premultiplied-alpha conversion, reinforcing that this audit should be treated as a focused diagnostic rather than semantic proof of CONTACT/LEFT frame meaning.

References reviewed: MDN `getImageData()`, `putImageData()`, `ImageData.data`, pixel manipulation guide. Counterevidence retained: pixel statistics cannot determine animation semantics or prove a visually important difference without inspection.
