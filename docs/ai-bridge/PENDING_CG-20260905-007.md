### PROBLEM
The live hero renderer now exposes useful v3 sprite diagnostics (crop loss, white-knockout loss and row1/row2 lateral similarity), but those diagnostics were not part of the repository's production LIVE audit pipeline. `tests/kelo-live.spec.js` could read them, yet `.github/workflows/live-audit.yml` did not trigger on `engine-ab.js` or `assets/hero.PNG`, and it did not run a hero-specific mobile+desktop check. That meant a future LEFT/RIGHT, foot-planting, crop or 1.15x scale commit could pass normal CI without automatically proving that Pages served the intended hero renderer/asset on both target classes.

- Unrelated environment/depth commits continued landing during this round, so the implementation intentionally touched only hero QA files and did not refactor renderer ownership.

### EXTERNAL_EVIDENCE
- Playwright's official screenshot API supports device-pixel screenshots and high-DPI contexts; this is appropriate for comparing mobile DPR behavior separately from desktop rather than treating one viewport as representative of both.
- Aseprite's official sprite-sheet/tag documentation reinforces that matrix row position is not semantic proof of direction; authored tags/metadata are preferable when available, so the live audit measures row similarity but does not declare row 1 to be LEFT.
- Community pixel-art discussion provides counterevidence to blind mirroring: mirroring is a valid production shortcut for symmetric characters, while asymmetric details can make it visibly wrong. Therefore the audit must preserve the current mirror policy until source evidence or visual evidence justifies changing it.

### HYPOTHESIS
Making hero diagnostics a first-class LIVE gate will reduce false conclusions and let the next round make a real LEFT/crop/knockout/scale decision from deployed data. A cache-busted hero-only audit in both mobile and desktop should add strong evidence without changing gameplay output, physics, frame cadence or visual presentation.
