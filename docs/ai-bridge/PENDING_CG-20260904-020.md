### PROBLEM
The current movement mapping keeps physical target speed continuous across the walk/run threshold, but animation distance-per-cycle changes discontinuously from 50 world px to 90 world px exactly when gait changes at processed magnitude 0.70. Because the same four-column lateral atlas is used for both walk and run, this can make the visible leg cycle slow down sharply at the moment the player transitions into RUN even though world speed is increasing. That inversion can read as floaty/skating and directly conflicts with the priority of premium lateral movement and foot planting.

### CONFIRMED_IN_GEMINI
Current `main` at BASE_COMMIT loads `engine-ab.js` before `engine-ac.js`; `engine-ac.js` owns local gait/stride state and `engine-ab.js` consumes `_visualMotion.frame` directly as one of four atlas columns.

`engine-ac.js` currently defines:
- `GAIT_RUN_START = 0.70`
- `WALK_CYCLE_WORLD_PX = 50`
- `RUN_CYCLE_WORLD_PX = 90`
- `v.stridePhase += lastStepDistancePx / cyclePx`
- `v.frame = floor(stridePhase * 4) % 4`

The physical speed map is continuous. At processed magnitude 0.699, the current formula produces about 97.03 world px/s and gait WALK. Animation cycle frequency is therefore about 97.03 / 50 = 1.94 cycles/s, or ~7.76 frame-column changes/s for a four-column cycle. At magnitude 0.700, speed is about 97.32 world px/s and gait switches to RUN, but the cycle denominator becomes 90 world px, giving about 1.08 cycles/s or ~4.33 frame-column changes/s. Thus a ~0.3% rise in physical speed can produce roughly a 44% drop in visual cycle frequency at the threshold.

At full processed magnitude 1.0, physical speed is ~185.28 world px/s and RUN cadence rises back to ~2.06 cycles/s (~8.23 column changes/s). This means the run cadence has a valley immediately after entering RUN.

`engine-ab.js` does not select a distinct run row or run atlas. LEFT/RIGHT both use lateral row 2 (LEFT mirrored), and `stepCol()` uses the frame provided by `_visualMotion`. Therefore the only current walk-vs-run visual timing distinction for local movement is chiefly the cycle-distance denominator; there is no separate authored run animation compensating for the 50→90 jump.

The current movement owner also sets `CONFIG.movementType='DIRECT'`, so `accelDecay/decelDecay` values in `engine-ac.js` are not what smooth this threshold. This finding is about visual cadence, not acceleration physics.

Code responsibility scan: `engine-ac.js` is appropriately the owner of local distance-based stride; `engine-ab.js` should remain a consumer. Do not duplicate cadence logic into the renderer. `engine-ab.js` still contains a separate legacy time-based fallback for actors without `_visualMotion`; that is related debt but not part of this experiment unless visible fallback actors are used in the same capture.

### EXTERNAL_EVIDENCE
External locomotion guidance consistently couples animation playback/cycle rate to actual movement speed to avoid foot sliding. Unity documentation exposes animation/blend thresholds based on Speed/Velocity and allows state playback speed to be parameterized; its navigation/animation guidance similarly recommends matching movement speed to animation motion. Community practice in Unreal/game-dev discussions describes the same observable failure: when the ground speed increases without a corresponding animation-rate increase, feet slide and the character reads as skating.

A Godot issue on BlendSpace synchronization is useful counter-context: two locomotion animations with different lengths can look wrong if their phases are not synchronized, which supports preserving normalized stride phase across gait changes rather than blindly restarting the cycle.

Counterevidence: a longer world-distance run cycle is not inherently wrong. A real run usually has a longer stride than a walk, so RUN_CYCLE_WORLD_PX > WALK_CYCLE_WORLD_PX can be artistically correct. The defect candidate is the abrupt ratio change at the threshold combined with the same four authored frames, not the existence of a longer run stride by itself. If asset inspection shows row 2 intentionally depicts a long-stride run at those timings, the current numbers may be defensible.

### HYPOTHESIS
The 50→90 world-px denominator jump at `GAIT_RUN_START=0.70` creates a perceptible cadence inversion: near the joystick threshold, Kelo moves faster but his lateral leg animation suddenly slows, increasing foot-slide/float perception. A continuous or calibrated distance-per-cycle mapping should reduce that inversion while preserving the same physical movement trace and normalized stride phase.

### PROPOSED_CHANGE
Do not change production yet. Instrument first.

Compare four presentation-only candidates while keeping physical speed mapping identical:

A — CURRENT_STEP_BASELINE
- WALK cycle = 50 world px.
- RUN cycle = 90 world px at mag >= 0.70.

B — CONTINUOUS_CYCLE_DISTANCE
- Interpolate cycle world distance continuously over a magnitude band instead of switching 50→90 in one frame.
- Preserve `stridePhase`; never reset on gait change.
- Initial diagnostic band only, e.g. mag 0.60→0.85, with exact endpoints chosen after measurement.

C — CADENCE-MATCHED_THRESHOLD
- Choose the first RUN cycle distance so cycles/s does not fall at the 0.70 boundary, then gradually approach the authored run distance as speed rises.
- Do not assume 90 is wrong at full run.

D — SINGLE_DISTANCE_CONTROL
- Diagnostic only: one fixed cycle world distance across walk/run to isolate whether the threshold discontinuity itself causes the visual defect.

Do not introduce a separate run row, extra frames, body lean, bob, shadow changes, camera changes, or physics changes in this experiment. Those would confound attribution.

### RISKS
- Smoothing the cycle-distance transition can hide an authored semantic boundary if the four frames are intended to represent distinct walk/run timing despite sharing the same row.
- Increasing cadence near run entry can make a four-frame sprite look frantic if the pose set cannot support it.
- A continuous denominator that changes while phase advances can still alter instantaneous frame timing; therefore compare normalized phase and contact events, not only average cycles/s.
- Touch magnitude itself may jitter around 0.70 and cause repeated gait labels. That is separate from directional hysteresis CG-015 and should be logged, not silently solved in this experiment.
- Fixing cadence without classifying the actual contact frame can reduce one kind of sliding while worsening another.
