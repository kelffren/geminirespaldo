### PROBLEM

The current main loop performs exactly one simulation update per `requestAnimationFrame`, with a variable `dt` clamped to 100 ms. Normal movement multiplies physical displacement by `dt`, but `updateSimulation()` still contains gameplay/AI random decisions expressed as fixed probabilities per update (`Math.random()<0.005` for wandering retarget and `Math.random()<0.02` for rival projectile attempts). Because update count follows render refresh, these events occur substantially more often on 90/120 Hz displays than at 60 Hz. This also means a tempting future fix for long-frame locomotion/collision hitches — subdividing one frame into multiple update calls — would silently multiply those random decision opportunities unless the RNG contract is fixed first.

This is a dependency gate for the user's requested 60/90/120 Hz movement work. It is not a proposal to refactor the entire game loop now.

### CONFIRMED_IN_GEMINI

At live `main` baseline `baa237baab3d410294c9e58a1dd8a45e2e08cab1` / visible title `Kelo World — V6.12`:

1. `engine-b.js::gameLoop(currentTime)` computes `dt = Math.min((currentTime-lastTime)/1000, 0.1)`, then executes exactly once per RAF: `processInput(); updateMovement(dt); updateCamera(dt); updateSimulation(dt); render();`.
2. Therefore at a steady 60/90/120 Hz display the main simulation is normally called approximately 60/90/120 times per second, not at a fixed independent tick rate.
3. `engine-a.js::updateSimulation(dt)` moves wandering simulated players with time-scaled displacement (`80*dt`), but their random target reselection includes `Math.random()<0.005` once per update.
4. The same `updateSimulation(dt)` gives an active PvP rival a projectile opportunity with `Math.random()<0.02` once per update.
5. Those two probabilities are not multiplied by `dt` and are not expressed as a per-second hazard or timer.
6. At 60 Hz, a per-update probability `p=0.005` has an expected 0.30 random successes/s and about 25.97% probability of at least one success in one second. At 90 Hz this becomes 0.45 expected/s and ~36.31%; at 120 Hz 0.60 expected/s and ~45.20%.
7. At 60 Hz, `p=0.02` has an expected 1.20 successes/s and ~70.24% probability of at least one success in one second. At 90 Hz this becomes 1.80 expected/s and ~83.77%; at 120 Hz 2.40 expected/s and ~91.15%.
8. Thus the 120 Hz client gets approximately 2x as many RNG trials per second as the 60 Hz client for these systems. This is a code-level consequence, not a measured live frequency yet.
9. Current local movement is `DIRECT` because `engine-ac.js` overwrites the config. At max processed magnitude, current speed cap is `178 + (1-0.74)*28 = 185.28 world px/s`.
10. A single legal 100 ms clamped long frame can therefore request ~18.53 world px of full-run movement in one update. At normal full-run cadence this is ~3.09 px/update at 60 Hz, ~2.06 at 90 Hz, and ~1.54 at 120 Hz.
11. The current run stride cycle is 90 world px, so 18.53 px advances internal stride phase by ~0.206 cycles in one update. With the current four equal frame bins, that is ~0.82 of one pose-bin width. Near the top of WALK (processed magnitude ~0.69), a 100 ms step is ~9.45 px and ~0.189 of the 50 px WALK cycle (~0.76 pose-bin width).
12. `engine-a.js` collision resolution is positional circle-vs-AABB after X movement and then Y movement. There is no swept collision or explicit bounded substep inside that movement function.
13. `engine-ac.js` consumes actual post-movement displacement once per wrapped movement call to advance stride phase. This is correct in principle for distance matching, but its state granularity follows the number of movement updates supplied by the loop.
14. `engine-ah.js` adds another movement wrapper but does not create fixed updates; it only forces zero velocity when input is absent.
15. Any elapsed frame gap above 100 ms is truncated to 100 ms by the game loop rather than accumulated/caught up. This protects against enormous background-tab jumps but deliberately discards simulation time.
16. `ENGINE_MAP.md` remains stale (V5.15/v66 and outdated ownership), so it is not evidence that the current loop or hero renderer has a different timing owner.
17. `GROK_TO_CHATGPT.md` still has no feedback newer than GC-20260831-003, so no Grok evidence currently closes this 60/90/120 RNG/timestep question.

### EXTERNAL_EVIDENCE

1. MDN documents that `requestAnimationFrame()` callback frequency generally follows display refresh rate and commonly runs at 60, 75, 120, or 144 Hz; it also notes callbacks are commonly paused in background tabs. This supports treating per-RAF gameplay probabilities as refresh-rate-sensitive unless explicitly normalized by time.
2. MDN's game-loop guidance distinguishes fixed update ticks from rendering cadence; the architectural point is that simulation frequency does not have to equal display refresh frequency.
3. Glenn Fiedler's well-known timestep analysis shows why large variable timesteps can change integration/collision outcomes and describes bounded/semi-fixed subdivision as one mitigation, while explicitly warning about the spiral-of-death/catch-up cost. This supports benchmarking bounded substeps, not blindly installing them.
4. A June 2026 GitHub issue in OloEngineBase reports a similar architecture problem: gameplay simulation on raw variable frame delta plus non-deterministic RNG produces frame-rate-dependent behavior and blocks deterministic rollback work. This is external precedent, not proof that Kelo requires rollback/fixed timestep now.
5. A Godot proposal on timestep-vs-refresh jitter describes the mismatch between render Hz and physics ticks as especially visible on high-refresh displays and discusses interpolation/adaptive timestep as alternatives. This supports testing multiple timing architectures rather than assuming one universal solution.
6. Reddit/game-dev community discussions repeatedly distinguish elapsed-time-scaled state changes from per-frame changes. Counterevidence is equally important: not every input should be multiplied by delta time (for example, already-integrated pointer deltas), so the fix must target only semantics that are intended to represent a rate over real time.
7. Another useful counterexample from community discussion is maximum-delta clamping: engines deliberately cap a giant `deltaTime` after stalls so simulation does not jump by seconds. Kelo's 100 ms cap is therefore not inherently wrong; the unresolved question is what simulation semantics should happen inside that bounded interval.

### HYPOTHESIS

Before changing Kelo's movement loop to fixed or semi-fixed updates, convert refresh-rate-sensitive random event opportunities to a time-based contract or isolate them from movement substeps. For an event historically tuned as probability `p60` per 60 Hz frame, a time-invariant hazard can be defined as `lambda = -60 * ln(1-p60)` per second and evaluated each update as `p(dt) = 1 - exp(-lambda*dt)`.

Using that mapping:
- wandering `p60=0.005` corresponds to `lambda≈0.30075/s`; equivalent per-update probabilities are ~0.005000 at 60 Hz, ~0.003336 at 90 Hz and ~0.002503 at 120 Hz.
- rival fire `p60=0.02` corresponds to `lambda≈1.21216/s`; equivalents are ~0.020000 at 60 Hz, ~0.013378 at 90 Hz and ~0.010051 at 120 Hz.

This should preserve statistical event rate across refresh/substep frequency. It will not make exact RNG sequences deterministic across different step counts; deterministic replay/network authority would require a stronger RNG/event-clock contract and is outside this proposal.

After that dependency is measured, a separate bounded-substep experiment can decide whether long-frame collision/camera/locomotion state materially improves. Visual locomotion should NOT artificially replay every pose missed during an actual dropped render frame; if the browser did not present those frames, forcing presentation to lag behind physical distance would reintroduce foot sliding.

### PROPOSED_CHANGE

**P0 — Instrument before changing timing**
- Add test-only counters/timestamps for actual RAF `dt`, long-frame counts, update count, wandering RNG trials/successes, rival-fire trials/successes, and rendered frame count.
- Measure representative mobile and desktop traces including 60/90/120 Hz where controllable.

**P1 — Pure deterministic RNG-rate harness**
- Without changing production behavior, run seeded/statistical simulations for 60/90/120 update rates over long virtual intervals using the current fixed-per-frame probabilities.
- Confirm observed event rates converge to the mathematical baseline above.

**P2 — Time-based probability candidate behind a narrow flag**
- Preserve the existing 60 Hz tuning as the reference distribution.
- Convert only the two confirmed per-update random opportunities to `p(dt)=1-exp(-lambda*dt)`.
- Do not change target ranges, movement speeds, projectile speed/damage, AI decisions, or rendering.

**P3 — Same-duration 60/90/120 remeasurement**
- With a seeded harness and identical elapsed duration, compare event counts/distribution under baseline vs time-based candidate.
- Statistical target: no systematic rate scaling with refresh. Exact sample-by-sample identity is not required.

**P4 — Only then benchmark bounded movement/simulation subdivision**
- Reproduce a 100 ms long-frame interval as A: one 100 ms update, B: 6x16.667 ms updates, and C: 12x8.333 ms updates.
- First run movement/collision/camera/visual-state in a deterministic harness.
- If testing a production substep loop, do not simply call all of `updateSimulation()` N times until per-update RNG and any other per-update side effects are audited.
- Prefer a maximum bounded step count/headroom to avoid catch-up spiral.

**P5 — Keep presentation semantics honest**
- Render once after the simulated long frame in the hitch harness.
- Do not slow or cap stride phase merely to display missed animation frames; compare foot/root state against actual traveled distance.
- The goal is state consistency, not fake slow-motion recovery.

### DO_NOT_ASSUME

- Do not assume `speed*dt` alone makes the whole game frame-rate independent; per-update RNG is confirmed counterevidence.
- Do not wrap the current entire loop in 6-12 substeps without auditing per-update side effects.
- Do not remove the 100 ms clamp simply to preserve wall-clock time after a long stall.
- Do not assume fixed timestep is automatically superior for local input latency; rendering/interpolation policy matters.
- Do not require exact identical RNG sequences from the time-hazard candidate; this proposal targets statistical rate invariance.
- Do not change collider radius, movement speed, gait thresholds, stride distances, camera settings or avatar scale during this experiment.
- Do not use a presentation-phase clamp that makes feet lag behind actual distance traveled after a hitch.

### RISKS

- Calling `updateSimulation()` multiple times per rendered frame before normalizing its per-update RNG would increase wandering/fire opportunities and create a false regression attributed to fixed timestep.
- A time-based hazard preserves rates statistically but changes exact random sequences and may affect tests that accidentally depend on frame-specific RNG calls.
- Fixed/semi-fixed stepping can increase CPU cost after long frames and enter a catch-up spiral if the step budget is not bounded.
- Interpolating local player presentation between fixed ticks can add latency if implemented blindly; this round does not prescribe interpolation yet.
- A 100 ms `dt` clamp intentionally discards time after very long stalls; changing this policy can produce large catch-up bursts or gameplay jumps.
- Substeps cannot recreate visual frames that the browser never displayed. Trying to replay missed poses can make animation lag behind physics and harm foot planting.
- Current NPC target selection also has a distance-to-target condition, so the p=.005 analysis isolates only the random branch; live aggregate retarget frequency also depends on path geometry and target arrival.
