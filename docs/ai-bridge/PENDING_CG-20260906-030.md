### PROBLEM
Kelo's current visual-motion state distinguishes intent/commanded speed from actual displacement, but the `physicallyMoving` decision still treats high commanded velocity as movement even when collision resolution has reduced net world displacement to ~0. When the player holds directly into a wall or blocked prop, the stride phase stops advancing because it is distance-driven, yet `visualOn` can remain true because `localPlayer.vx/vy` remain high. The visible result can therefore be a stationary character frozen on whichever walk/run frame happened to be active at contact instead of settling into the authored planted pose. This is specifically a foot-planting/collision presentation issue; it is not evidence that DIRECT physics or collision response should be changed.

### CONFIRMED_IN_GEMINI
- Current `main` inspected for this pass is `5d764e365707361690fc099681f52afcb6367bf3`. The latest commit touched `.github/workflows/visual-system-live.yml`, not locomotion owners.
- `index.html` currently declares V6.33 and loads `engine-a.js?v=149`, `engine-ab.js?v=240`, `character-appearance.js?v=2`, `engine-ac.js?v=222`, then later `engine-ah.js?v=94`; therefore `engine-ac` wraps core movement and `engine-ah` wraps the resulting movement function again.
- `engine-ac.js` forces `CONFIG.movementType='DIRECT'`. In `engine-a.js::updateMovement`, DIRECT sets `localPlayer.vx/vy` to the requested target velocity before moving/colliding.
- `engine-a.js` resolves X and Y collisions by moving the player, applying overlap push-out, and preserving the commanded `localPlayer.vx/vy`; the collision branch does not rewrite velocity to the net displacement achieved.
- `engine-ac.js::updateVisualMotion` computes actual `dist = hypot(p.x-lastX,p.y-lastY)` but separately computes `spd = hypot(p.vx,p.vy)`. `physicallyMoving` is true when `dist > 0.12` OR `spd > 16`.
- While movement input remains held, `hasIntent` is also true. Therefore a player pressing directly into a blocking wall can remain `v.on=true` even when actual displacement is zero or near zero.
- Stride advancement itself is correctly based on actual distance only: `lastStepDistancePx = dist > 0.12 ? dist : 0`, and `stridePhase` advances only when `lastStepDistancePx > 0`. Thus a blocked actor does not treadmill through frames; instead it can freeze indefinitely on the current arbitrary frame.
- When `v.on=false`, the authored planted state is explicit: `stridePhase=PLANT_PHASE`, `strideDistancePx=0`, `frame=PLANT_FRAME` (default lateral plant frame 2). The blocked-contact path currently does not reach that state while input/commanded speed persist.
- `engine-ah.js` hard-stops velocity only when there is no move input. It does not help when the input is deliberately held against a wall.
- `scripts/live-hero-audit.mjs` currently exercises RIGHT, immediate LEFT reversal, release and diagonal near spawn, but has no head-on wall press / blocked-displacement case, so this failure mode can pass all current hero movement assertions.
- The wrapper scan also confirms duplicated movement-state responsibility: core `engine-a` owns requested velocity/collision, `engine-ac` infers visual movement from both displacement and requested velocity, and `engine-ah` separately infers whether movement input exists for hard-stop. Do not merge/refactor these owners as part of the blocked-motion experiment; instrument first.

### EXTERNAL_EVIDENCE
- Godot `CharacterBody2D` explicitly distinguishes requested `velocity` from `get_real_velocity()` and `get_position_delta()`: `get_real_velocity()` reports the actual movement after `move_and_slide`, whereas `velocity` is the requested velocity. This is directly analogous to Kelo's commanded `vx/vy` versus measured world displacement and supports using achieved motion for gait presentation. https://docs.godotengine.org/en/4.3/classes/class_characterbody2d.html
- Unity's `CharacterController` documentation likewise describes requested movement being constrained by collisions and exposes collision flags after the move. This reinforces that command velocity and achieved locomotion are separate semantics. https://docs.unity3d.com/kr/530/ScriptReference/CharacterController.html
- Godot issue #69130 documents the practical distinction between trying to run against a wall and actual body motion after collision, showing why collision-constrained movement needs explicit treatment rather than assuming input velocity equals travel. https://github.com/godotengine/godot/issues/69130
- Community examples repeatedly hit animation-state bugs when animation is chosen from input/request vectors while collision prevents actual travel. A Godot discussion notes that `move_and_slide` can return zero motion on an axis against a flat wall, which changes what should be considered actual movement. https://www.reddit.com/r/godot/comments/y1jtbm/
- Counterevidence: some games intentionally keep a push/run pose while the player presses into a wall for responsiveness or style. Therefore Kelo should not blindly switch to generic idle on the first blocked frame. The correct candidate is a short blocked-motion settle into the authored planted/contact pose, with sliding tangential motion still animating by actual distance.

### HYPOTHESIS
A small presentation-only `blockedMotion` state derived from sustained intent + high requested speed + negligible actual displacement will improve lateral grounding at walls/props without changing physics. After a short grace period, the body should settle to the authored planted frame while preserving facing and input. If the collision allows tangential sliding and actual distance remains above the visual threshold, stride must continue normally. The state must clear immediately when real displacement resumes. This should reduce arbitrary frozen-stride poses and become even more important if the avatar is enlarged to 1.20x.

### PROPOSED_CHANGE
Do not change production in this research pass. First extend telemetry/harness. Candidate implementation, feature-flagged only after baseline measurement:
1. Track `blockedElapsedSec` in `_visualMotion` when all are true: movement intent exists, requested speed is above a meaningful threshold, and achieved displacement remains below `MIN_VISUAL_MOVE_PX` (or a dt-normalized achieved-speed threshold).
2. Use a short grace candidate such as 50/75/100 ms for A/B; do not hardcode a final number before measurement.
3. After the grace, set presentation to a planted blocked-contact state: `v.on=false` or an explicit `v.blocked=true` with `frame=PLANT_FRAME`, `stridePhase=PLANT_PHASE`, while preserving `face` from intent/last motion. Do not zero physics velocity/input.
4. Reset blocked timer immediately when achieved displacement resumes.
5. Tangential wall slide must remain gait-active because actual displacement is non-zero; never classify all collisions as blocked.
6. Keep shadow/footRoot/collider/camera unchanged. If a later dedicated push animation exists, the same semantic `blocked` state can select it instead of plant frame.
7. Publish audit fields: `blockedMotion`, `blockedElapsedMs`, `requestedSpeed`, `achievedStepDistancePx`, `achievedSpeedPxPerSec`, `blockedSettleCount`, `lastBlockedFromFrame`.

### DO_NOT_ASSUME
- Do not change DIRECT movement, collision resolution, velocity, camera, joystick deadzone, gait thresholds or avatar scale in this experiment.
- Do not treat `input held` as proof that the actor is visually locomoting.
- Do not treat `vx/vy != 0` as achieved movement after collision.
- Do not settle immediately on the first low-displacement frame; tiny dt, raster thresholds or transient collision correction could create false blocked states.
- Do not stop animation during a legitimate wall slide where tangential world displacement continues.
- Do not reset facing to down/idle when blocked; preserve the direction of the push.
- Do not refactor the `engine-ac` / `engine-ah` wrapper chain until baseline traces establish which wrapper produces each state.
- Do not add a new push animation asset in the same benchmark; first prove the semantic state with the existing plant frame.

### RISKS
An overly aggressive blocked detector could plant the sprite during very slow analog walking, micro-collision corrections, frame stalls or narrow passages. A pure per-frame distance threshold is refresh-sensitive unless interpreted carefully; achieved speed (`dist/dt`) or a time-integrated blocked condition may be safer. Resetting stride distance on blocked settle may make resumption visibly restart the walk cycle; preserving phase while displaying the plant frame is an alternate candidate that should be compared if restart pops are visible. Some players may prefer a dedicated braced/push pose rather than neutral plant, but adding art before validating the state would confound the experiment. Enlarging the avatar will magnify any frozen-stride or restart pop, so this should be settled before 1.20x.
