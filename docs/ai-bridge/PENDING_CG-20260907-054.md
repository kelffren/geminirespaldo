### PROBLEM
The current live hero path always sets `ctx.imageSmoothingEnabled = false` around `drawImage()`. That policy is commonly correct when enlarging deliberate pixel art, but Kelo's current hero renderer is not simply a 1:1 or integer-upscale path: `engine-ab.js` crops a source frame and draws it into a much smaller presentation rectangle (`~55x93 world px` laterally at the current 1.15 visual scale). The live audit already exposes `sheetWidth/sheetHeight/frameWidth/frameHeight`, but it does not calculate source-to-destination reduction ratio or compare filtering modes temporally while the player moves.

This matters to the user's current priorities in two ways. First, increasing the avatar from 1.15x to 1.20x is not automatically a resolution-risk operation if the source frame is still substantially larger than the destination; it can actually reduce the amount of downscaling. Second, future 1–2% squash/lean scale experiments may look worse not because the authored animation is wrong, but because nearest-neighbor sampling of a heavily reduced source can select different source texels as destination size/position changes, creating edge crawl or silhouette thickness changes.

The correct question is therefore not `nearest is sharp, so keep nearest` versus `linear is smooth, so use linear`. The correct question is which sampling strategy preserves Kelo's authored silhouette and temporal stability at the ACTUAL runtime source/destination ratios on mobile and desktop.

### EXTERNAL_EVIDENCE
- MDN documents `imageSmoothingEnabled=false` primarily as useful for pixel art when ENLARGING images, where browser smoothing would blur pixels. It does not say that nearest-neighbor is universally best for large reductions: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
- MDN documents `imageSmoothingQuality` (`low|medium|high`) only when smoothing is enabled, but also notes that this property is not Baseline across all major browsers. That means it can be a benchmark candidate, not a compatibility assumption: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingQuality
- Godot's current rendering documentation explicitly recommends mipmapped filtering for non-pixel-art textures shown at low scale because source pixels become smaller than screen pixels. This is evidence that downscale quality is a different problem from integer pixel-art enlargement: https://docs.godotengine.org/en/stable/classes/class_renderingserver.html
- Godot CanvasItem texture-filter documentation likewise distinguishes nearest from linear+mipmaps and specifically calls out low-scale rendering/Camera2D zoom as a mipmap use case: https://docs.godotengine.org/en/4.0/classes/class_canvasitem.html
- Community evidence is mixed but relevant. Developers downscaling high-resolution 2D art report better control from precomputed lower-resolution/mipmap assets rather than depending only on runtime downscale; conversely, deliberate pixel art often looks crisper with nearest. Example: https://www.reddit.com/r/godot/comments/1jbxbz1/
- Community reports also show the opposite failure mode: nearest plus non-integer scaling can create distorted or jittery pixel widths during motion. Example: https://www.reddit.com/r/godot/comments/1php1x7/

COUNTEREVIDENCE:
- If `hero.PNG` is intentionally authored as pixel art whose pixel grid is itself part of the style, linear filtering may blur the exact look the user wants even during downscale.
- Canvas2D does not expose true GPU mipmap control for `drawImage()` in the same way WebGL/WebGPU texture sampling does; switching engine technologies solely for this issue would be unjustified.
- A pre-generated lower-resolution hero atlas may be visually superior but increases asset-pipeline complexity and memory/HTTP variants; do not add it unless A/B evidence beats the current single asset.
- Some apparent shimmer may actually come from fractional world zoom/camera placement identified in earlier rounds, not source filtering. The benchmark must hold camera/zoom trace constant.

### HYPOTHESIS
The current hero may be temporally less stable than necessary because it combines a relatively large authored source frame, a much smaller runtime destination, nearest-neighbor source resampling, fractional world zoom and integer-rounded destination placement. A 1.20x avatar does not inherently reduce sprite quality; if the hero remains downscaled, 1.20x may preserve slightly more source information. The best presentation may be one of three strategies:

A. current nearest-neighbor;
B. smoothing enabled for the hero draw only (default/portable mode; optionally quality hint where supported);
C. an authored/precomputed presentation-resolution atlas chosen for Kelo's target on-screen size, still rendered nearest at approximately 1:1.

No strategy should be selected by still-image sharpness alone. Temporal edge stability while walking/reversing is the deciding factor.
