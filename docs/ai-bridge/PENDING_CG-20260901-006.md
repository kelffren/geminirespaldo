## EXTERNAL_EVIDENCE

1. MDN documents `imageSmoothingEnabled=false` as the standard way to preserve sharp pixel-art edges, but its newer crisp-pixel-art guidance explicitly warns that non-integer CSS/device-pixel mappings can make some pixels wider than others when devicePixelRatio or page zoom is non-integer. This is counterevidence against assuming smoothing-off alone guarantees stable pixel quality.
2. MDN further notes that when `drawImage()` performs a non-integer image-to-canvas scale, source pixels cannot map uniformly; integer-aligned source/canvas/device relationships are the cleanest case. Kelo's current 256-ish source frame down to 48/54 CSS-world pixels is strongly non-integer before camera zoom/DPR are considered.
3. Recent top-down 2D community debugging converges on using the bottom/feet/ground-contact origin as the Y-sort key. Sorting from the sprite center/head causes characters to pop in front/behind objects at visually incorrect times. This directly supports Kelo's existing foot-root direction rather than sorting by visual rectangle center.
4. A recent August 2026 Godot Y-sort thread reports a concrete fix by moving the sort origin to the bottom of the sprite. Other 2025-2026 threads similarly recommend feet/base origins for tall top-down characters and props.
5. A public top-down renderer example (`ti.game`) describes Y-sorting by bottom edge/feet/trunk base within the same depth layer. This is consistent with the same physical-world illusion but is architectural evidence only; Kelo should not migrate engines just to copy this feature.
6. Counterevidence: global Y-sort is not automatically correct for roofs, canopies, UI/nameplates, projectiles, or deliberately separated render layers. The correct experiment is actor/occluder-specific foot-root sorting after the existing layer chain is measured, not blindly sorting every draw call by Y.

## HYPOTHESIS

The larger 8-frame character should use one stable ground-contact key (`sortY` derived from the foot/root) for actor depth, while its visual top, nameplate, bob and shadow remain presentation-only. If Kelo first makes actor state render-pure, then sorts only comparable world actors/occluders by foot-root Y inside a single actor layer, a 1.15-1.30 larger avatar can preserve collision and look more spatially correct. Separately, final sprite size should be chosen from a small set of destination-size buckets that minimize unstable non-integer sampling at common zoom/DPR combinations, rather than one arbitrary continuous scale factor.

P3 — Prototype actor-only foot-root Y-sort behind a flag after CG-005 render-pure state.

- Keep nameplates attached to their actor after sorting; do not sort nameplates independently.
- Do not include ground, UI, skill indicators, particles, roofs or unrelated overlays in the same sort list without a measured reason.

P4 — Treat buildings/occluders as explicit depth participants, not full-image rectangles by default.
- For tall props/buildings that should occlude the player only near their base, define a ground-contact sort line/key separate from their full visual height.
- Preserve roof/canopy overlays as separate layers when needed rather than forcing a single global Y-sort.

P5 — Add pixel-quality scale buckets.
- Candidate visual scales remain 1.15/1.25/1.30, but record actual destination `dw/dh` after zoom and DPR for common desktop/mobile cases.
- Compare nearest-neighbor direct draw at integer-rounded destination dimensions against current continuous scaling.
- Prefer a small set of visually approved destination sizes/mini-atlas variants if that measurably reduces shimmer without excessive memory.
- Do not rely on `imageSmoothingQuality='high'` as a required path because browser support is incomplete.

P6 — Nameplate and shadow contracts for larger sprites.
- Shadow center follows foot root; body bob/lean must not move the sort key.
- Nameplate follows a stable visual envelope/top anchor, not raw bob every frame.
- Measure nameplate overlap and occlusion separately from actor depth correctness.

P7 — Architecture cleanup only after equivalent layering is proven.
- `engine-i.js` currently redraws actors to restore them above the plaza floor; actor sorting must not be implemented twice independently in base and redraw paths.
- Preferred end state is one actor presentation list consumed once at the correct layer point, but only after baseline→change→same-trace proof.
