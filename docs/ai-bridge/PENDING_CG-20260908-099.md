### PROBLEM
Current main changed the default player rendering path materially. `player_hero_v1` in `src/characters/character-appearance.js` now uses independent authored rows for LEFT and RIGHT (`left:1`, `right:2`) with no mirroring and explicit per-frame foot anchors. Therefore the old default-player hypothesis in CG-20260908-089 (same frame mirrored across RIGHT↔LEFT swaps the visible support foot) is no longer the correct LIVE baseline. CG-20260908-095's visible raw→white-knockout sprite swap is also no longer the default-player draw path because Character Appearance middleware priority 200 handles `player_hero_v1` before `engine-ab` priority 100; engine-ab remains fallback/background work and may still have startup cost, but it is not the primary visible player renderer when Character Appearance is ready.

The new LIVE renderer solves an important anchoring problem but introduces a different measurement requirement before increasing avatar scale: the semantic presentation contract from `engine-ab` still reports one constant side `visualWidth`/`visualHeight`, while Character Appearance scales each direction from different authored `bodyHeight` metrics and draws the full 256×384 source frame around a per-frame foot anchor. At current 1.15 visual scale, target body height is 93 world px. LEFT uses bodyHeight=302 => scale≈0.30795 and full destination rect≈79×118 px; RIGHT uses bodyHeight=369 => scale≈0.25203 and full destination rect≈65×97 px. The semantic side visual width remains ≈55 px for both. Full destination rectangle is not the same thing as opaque bounds because transparent padding may account for the difference, so this is NOT yet proof of an occlusion/bounds bug. It is a strong reason to measure actual post-cleanup opaque bounds per face/frame and compare them to `KELO_AVATAR_PRESENTATION` before 1.20×.

### CONFIRMED_IN_GEMINI
- `index.html` now declares Kelo World V6.54 and loads `engine-ab.js` before `src/characters/character-appearance.js`; `KeloAvatar` remains the avatar composition owner.
- `src/characters/character-appearance.js` default player is `player_hero_v1` using `assets/hero.PNG?hero=deeab966`.
- `HERO_FACE_ROWS = {down:0,left:1,right:2,up:3}` and all `HERO_MIRROR_FACES` are false.
- Per-frame foot anchors are authored separately for every direction. LEFT footX=[132,108,91,77], footY=[344,346,347,348]; RIGHT footX=[145,135,121,113], footY=[384,384,384,384].
- Character Appearance calls `presentationOf(actor,face)` and consumes `KELO_AVATAR_PRESENTATION.get(...)` when available.
- It computes `targetBodyHeight = layout.visualHeight`, `scale = targetBodyHeight / metrics.bodyHeight`, then anchors every frame using `dx = footRootX - anchorX*scale`, `dy = footRootY - anchorY*scale`.
- The current semantic presentation in `engine-ab.js` uses AVATAR_VISUAL_SCALE=1.15, side baseVisualWidth=48 and baseVisualHeight=round(54*(384/256))=81, yielding side visualWidth≈55 and visualHeight≈93.
- LEFT and RIGHT therefore intentionally receive different raster scale factors because their authored bodyHeight differs, despite sharing the same semantic target body height.
- Character Appearance middleware is registered at KeloAvatar priority 200, while engine-ab production hero is priority 100. A ready Character Appearance render does not call `next()`, so engine-ab is fallback, not the normal visible player draw.
- `engine-ac.js` still provides frame/stride/facing state and remains unchanged in the relevant path; CG-20260908-090's classifier wedge remains independently relevant because it concerns movement classification, not mirroring.

### EXTERNAL_EVIDENCE
- Unity's 2D Pixel Perfect sprite preparation documentation explicitly says that when a texture contains multiple sprite elements, pivot points may need to be set for each sprite element, and recommends pixel-unit pivots/snapping for consistent pixel movement. This supports Kelo's new per-frame foot-anchor direction rather than returning to a single center pivot.
- Unity Sprite Editor documentation treats pivot as an explicit alignment point for each sprite graphic rectangle, and Godot documents adjusting Sprite2D offset/pivot when the visual rotation/placement pivot is wrong.
- Aseprite issue #1357 describes the practical game-development need for per-frame pivots/root anchors, specifically noting humanoid feet and Y-sorting as examples.
- MDN documents that `drawImage()` destination width/height perform scaling and that disabling `imageSmoothingEnabled` preserves sharp pixel edges when enlarging pixel-art-like images. Character Appearance already disables smoothing, so the next quality question is not whether smoothing is enabled; it is whether the chosen fractional source→destination scales and integer-rounded destination rectangles keep the opaque silhouette stable at 1.15× and 1.20×.
- Counterevidence: a full frame destination rectangle larger than the semantic visual bounds is not automatically wrong. Transparent padding can make the true opaque footprint fit the semantic contract. Do not infer a bug from destination rect dimensions alone.

### HYPOTHESIS
The new per-frame foot anchors should materially improve root stability and make CG-089 obsolete for the default LIVE player. However, because LEFT and RIGHT are authored with substantially different body-height metrics and therefore substantially different raster scale factors, the actual opaque bounds may differ from the constant semantic `visualWidth`/`visualHeight` enough to affect occlusion candidates, nameplate clearance, sprite-edge shimmer and perceived body size when changing direction. Increasing AVATAR_VISUAL_SCALE to 1.20 could amplify any mismatch.

A second hypothesis is that integer rounding of `dx/dy/dw/dh` keeps the foot root stable but may introduce face/frame-dependent silhouette quantization because LEFT (~0.308 source scale) and RIGHT (~0.252 source scale) land on different rounded destination sizes. This must be measured in screen CSS pixels under effective zoom/DPR rather than assumed.

First extend/audit Character Appearance with measurement-only opaque-bound telemetry (prefer test/offline instrumentation, not permanent per-frame `getImageData()`):

### RISKS
- Direction-aware semantic bounds add complexity if transparent padding already makes current constants good enough; reject the change if measured benefit is negligible.
- Measuring alpha bounds after cleanup but rendering from a different source would invalidate the audit; use the exact `runtime.source` semantics.
- Per-frame bounds can cause occlusion flicker if consumers switch thresholds every animation frame. If frame-aware bounds are needed, consider conservative union bounds per direction for occlusion while keeping exact per-frame anchors for rendering.
- Scaling to 1.20× can make non-integer source→destination ratios more visible. `imageSmoothingEnabled=false` keeps edges sharp but does not guarantee temporal stability when rounded dimensions/positions vary.
- Existing modular clothes/appearance layers may have their own anchors. Do not solve the base-body audit in a way that breaks Character Customization/Appearance Foundation.
