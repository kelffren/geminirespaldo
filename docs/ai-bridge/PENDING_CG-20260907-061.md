### PROBLEM
Kelo's current presentation contract already publishes a semantic `shadowAnchorX/Y` equal to `footRootX/Y`, which is the correct architectural place to anchor future lateral lean/bob/squash without making the ground cue float. However, the live PNG hero path in `engine-ab.js` does not consume that anchor and does not draw the legacy contact shadow at all when `assets/hero.PNG` is loaded successfully. Meanwhile Armor Aura computes `footRootY` in `visualMetrics()` but its actual ground ring ignores that value and draws at `p.y + physicsRadius * 0.72` instead. We therefore have three different ground-contact concepts in the code: the semantic foot/shadow root at `p.y + 10`, the old procedural shadow at `p.y + 14`, and the Aura ground ring at `p.y + 14.4` for the current radius 20.

This matters before adding premium secondary motion or increasing avatar scale. A body can lean, bob or scale around the foot root only if the visual ground cue remains independently anchored to that same ground contract. Otherwise Kelo can look like the body and its shadow/ring belong to different planes, especially when the avatar occupies more screen space.

### CONFIRMED_IN_GEMINI
Current `main` audited at `2bab5cb7a296a39a7c0eb224fff479ce0f2ea89e`.

`ENGINE_MAP.md` still identifies `engine-ab.js + assets/hero.PNG` as OWNER LIVE for the visible hero and `engine-ac.js` as the gait owner. `index.html` currently declares Kelo World V6.34 and loads `engine-ab.js?v=240` after the legacy core render definitions.

`engine-a.js` base `renderAvatar()` draws a procedural contact shadow first:
- center X: `p.x`
- center Y: `p.y + 14`
- radius X: `p.radius * 0.9`
- radius Y: `p.radius * 0.45`
- alpha: 0.4

But `engine-ab.js` later captures the previous renderer as `_av` and replaces `renderAvatar()`. In the normal successful PNG path (`ok && p && sheet`) it draws only the authored sprite and nameplate. `_av()` is called only on the fallback branch when the PNG/sheet is unavailable. Therefore the old ellipse shadow is bypassed by the live PNG hero path.

The same `engine-ab.js` presentation contract explicitly publishes:
- `FOOT_ROOT_OFFSET_Y = 10`
- `footRootY = p.y + 10`
- `depthRootY = footRootY`
- `shadowAnchorY = footRootY`
- `visualBottom = footRootY`

So the renderer has already declared the semantic ground anchor but does not consume it for a visible contact shadow.

`src/systems/armor-aura.js` calls `KELO_AVATAR_PRESENTATION.get()` and its `visualMetrics()` returns `footRootY`. However `drawRing()` does not use `m.footRootY`; it draws both ring halves at `p.y + m.physicsRadius * 0.72`. With the current radius 20 this is `p.y + 14.4`, i.e. 4.4 world px below the declared foot/shadow root (`p.y + 10`). That is structurally close to the old procedural shadow (`p.y + 14`) rather than the new presentation contract.

`engine-z.js` still sets responsive zoom from viewport width and clamps it to 1.05–1.45, so any world-space disagreement is magnified differently on mobile and desktop. Do not use a hardcoded CSS-pixel interpretation; measure the rendered separation per profile.

### EXTERNAL_EVIDENCE
Official Godot 2D lighting/shadow documentation separates the object that receives/draws the sprite from shadow occluders and lighting masks, reinforcing that shadow behavior is an independent rendering responsibility rather than something that should accidentally inherit every body transform. Godot's stable 2D lights and shadows documentation explicitly requires separate LightOccluder2D geometry for cast shadows.

General 2D sprite/pivot documentation across engines consistently treats bottom-center/feet as the useful character ground pivot. This aligns with Kelo's existing `footRoot`/`shadowAnchor` contract and supports keeping lean/scale around the feet rather than around the physics center.

Community evidence is useful but not authoritative: 2D developers commonly implement the small contact shadow as a separate object/layer following the player and, when animated, control its subtle size/shape separately from the character animator. That pattern avoids redrawing or deforming the shadow with every sprite frame. A recent Godot discussion about sprite-sheet shadows also illustrates the exact failure mode when the shadow origin is not connected to the feet.

Counterevidence: a perfectly static oval can itself look cheap or disconnected during strong poses, jumps, attacks or stylized HD-2D lighting. The goal is not to freeze the shadow forever. The first contract should keep its WORLD POSITION tied to `shadowAnchor/footRoot`; subtle opacity/ellipse-size changes may later follow speed/support state if benchmarked. Also, Kelo may eventually use directional cast shadows from the lighting system, so a contact shadow should remain cheap, subtle and composable rather than becoming a second full lighting solution.

Sources reviewed:
- Godot stable `2D lights and shadows` / `LightOccluder2D` documentation.
- Unity/Godot-style 2D sprite pivot guidance for bottom-center/feet anchoring.
- Reddit r/IndieDev discussion on independent animated contact shadows for moving 2D characters.
- Reddit r/godot discussion on adjusting shadow origin for sprite-sheet characters whose feet and shadow origin do not align.

### HYPOTHESIS
Restoring a subtle contact shadow as a separate ground-local element at the already-declared `shadowAnchor`, and making Armor Aura's ground ring consume the same anchor, will improve perceived planting and create a stable foundation for future lateral lean/bob/squash and 1.20x avatar tests without touching collision, world movement or camera.

The premium contract should be:
`physicsRoot` = collision/gameplay center;
`footRoot/depthRoot` = actor-ground/depth ordering;
`shadowAnchor` = ground cue position, currently same as footRoot;
`BODY_LOCAL` = sprite transformations such as lean/bob/squash;
`GROUND_LOCAL` = contact shadow / aura ring base, position not inherited from body lean/bob.

This is a contract hypothesis, not approval to add a large or stylized shadow.

### DO_NOT_ASSUME
- Do not assume the absence of the legacy ellipse is automatically a bug; it may have been intentionally removed for the authored PNG look. Benchmark visual quality first.
- Do not assume the old `p.y + 14` shadow offset is correct. The current semantic contract says `p.y + 10`.
- Do not scale or rotate the contact shadow with BODY_LOCAL transforms by default.
- Do not make the contact shadow a large dark blob; HD-2D depth can be harmed by excessive AO-like darkness.
- Do not migrate to WebGL/WebGPU or dynamic light casting for this single ground-contact issue.
- Do not touch collider radius, camera, world speed, gait phase, source frames, footRoot or depthRoot in this experiment.
- Do not change Armor Aura rank thresholds/particle budgets while measuring ground anchoring.

### RISKS
- Reintroducing the old-looking oval unchanged could make the authored PNG look cheaper rather than more premium.
- A shadow too dark/large can muddy authored Plaza art and fake excessive ambient occlusion.
- Moving Aura's ring upward by ~4.4 world px may expose assumptions in effects tuned around the old physics-center offset.
- If a later lighting system adds proper cast shadows, an over-strong contact shadow could double-darken the character.
- If BODY_LOCAL and GROUND_LOCAL are split by another wrapper without clear ownership, wrapper depth/redundancy could worsen. Avoid refactor until benchmark proves the contract.
- Large avatar scale will make ground-anchor errors easier to see, so 1.20x should be tested after—not simultaneously with—the anchor change.
