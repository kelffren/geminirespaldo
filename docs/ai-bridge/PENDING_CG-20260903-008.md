### PROBLEM

The current local-player locomotion uses distance-driven animation phase, which is directionally correct, but it changes the distance represented by one visual cycle discontinuously at the gait boundary. `engine-ac.js` uses `WALK_CYCLE_WORLD_PX = 50`, `RUN_CYCLE_WORLD_PX = 90`, and selects RUN as soon as processed input magnitude reaches `GAIT_RUN_START = 0.70`.

The physical speed curve is continuous across 0.70. The visual cycle distance is not. Therefore increasing the stick from just below 0.70 to exactly 0.70 can make Kelo move slightly faster in the world while the visible four-frame leg cycle suddenly advances much more slowly per second. This is the opposite perceptual response expected from a walk→run transition and can make the lateral gait feel heavy, disconnected, or as if the animation "drops gear" when the player pushes harder.

This is distinct from earlier refresh-rate/stride-capture findings: even with perfect distance capture and identical 60/90/120 Hz traces, the current WALK→RUN boundary itself creates a cadence discontinuity.

### CONFIRMED_IN_GEMINI

At current `main` baseline `0bd3f5cea328cf004703121ce8215b63e3f5c5f9`, visible title `Kelo World — V6.12`:

1. `engine-ac.js` defines `GAIT_RUN_START = 0.70`, `WALK_CYCLE_WORLD_PX = 50`, and `RUN_CYCLE_WORLD_PX = 90`.
2. `gaitFrom(mag)` returns `walk` for `mag < 0.70` and `run` for `mag >= 0.70`.
3. `speedFor(mag)` is continuous through 0.70. At magnitudes above 0.48 it smoothly increases the speed cap; there is no physical-speed step at the gait boundary.
4. `updateVisualMotion()` preserves `stridePhase` when gait changes. It advances phase by `lastStepDistancePx / cyclePx`, where `cyclePx` is selected from the current gait each update.
5. Consequently, exactly at the gait switch the denominator changes from 50 to 90 world px/cycle, a factor of 1.8, while world speed changes only marginally.
6. Using the current speed function, at processed magnitude 0.699 the target speed is approximately 97.03 world px/s. Because the gait is WALK, visual cycle rate is about `97.03/50 = 1.94 cycles/s` or about `7.76 four-frame pose changes/s` in the ideal continuous-distance approximation.
7. At processed magnitude 0.700 the target speed is approximately 97.32 world px/s. Because the gait becomes RUN, cycle rate falls to about `97.32/90 = 1.08 cycles/s` or about `4.33 four-frame pose changes/s`.
8. Therefore crossing 0.699→0.700 increases target world speed by only ~0.30%, while ideal visual cycle frequency drops by roughly 44.3%.
9. The implied visual cycle period jumps from about 515 ms just below the threshold to about 925 ms at the threshold.
10. At full magnitude 1.0, target speed is about 185.28 world px/s; with the 90 px run cycle the animation reaches about 2.06 cycles/s (~8.23 pose changes/s). So the RUN cadence eventually recovers as speed rises, creating a non-monotonic cadence-vs-input curve around gait entry.
11. `engine-ab.js` consumes the four-state `v.frame` directly and does not use `v.gait` to select a separate WALK versus RUN art sequence. Both gaits currently use the same directional row and the same four source columns; only the phase distance changes in `engine-ac.js`.
12. Therefore the 50→90 switch currently does not select an authored run cycle with a demonstrably longer physical stride. It only changes how quickly the same four lateral poses are traversed.
13. No Grok feedback newer than GC-20260831-003 exists, so there is no implementation evidence closing this gait-cadence issue.
14. `ENGINE_MAP.md` remains stale relative to runtime and still labels `engine-m.js` as the hero sprite owner even though current production PNG frame selection is in `engine-ab.js`; any implementation must follow current code, not the map alone.

### EXTERNAL_EVIDENCE

1. Epic Games' current Animation Locomotion Library documentation describes Distance Matching as driving animation using distance metrics and notes that cycle animations such as walk/jog typically adjust play rate to match in-game movement speed. This supports the principle that visual cadence should track travel speed rather than jump discontinuously due solely to a state label. Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Plugins/AnimationLocomotionLibraryRuntim-/UAnimDistanceMatchingLibrary
2. Epic's `Set Playrate to Match Speed` documentation says cycle animation play rate is commonly adjusted to match current in-game movement speed, often with clamps to avoid implausibly slow/fast playback. Source: https://dev.epicgames.com/documentation/unreal-engine/BlueprintAPI/DistanceMatching/SetPlayratetoMatchSpeed
3. Epic's Stride Warping documentation explicitly frames the problem as matching animated stride spacing to capsule movement speed, reducing dependence on hard blend-space transitions. Source: https://dev.epicgames.com/documentation/en-us/unreal-engine/pose-warping-in-unreal-engine
4. Unity's 1D Blend Tree documentation recommends locating walk/jog/run thresholds from the authored clips' speeds (for example 1.5, 2.3 and 4 units/s), and blends between motions based on a continuous speed parameter. This is evidence against treating an arbitrary input threshold as sufficient proof that a different stride length is appropriate. Source: https://docs.unity3d.com/cn/2018.3/Manual/BlendTree-1DBlending.html
5. GitHub issue `ywmaa/Advanced-Movement-System-Godot#10` groups stride warping/distance matching specifically around changing stride pace to match actual speed and foot locking. This is community/project evidence, not a normative specification. Source: https://github.com/ywmaa/Advanced-Movement-System-Godot/issues/10
6. Reddit/gamedev discussions on foot sliding repeatedly converge on matching character travel speed and animation cadence/stride. One concrete thread notes that visible foot sliding appears when movement speed and gait do not correspond. Source: https://www.reddit.com/r/gamedev/comments/wofi7p
7. Counterevidence: a real RUN animation can legitimately have a longer world-space stride than WALK, and at the same translational speed its cycle frequency may be lower. A 50→90 px cycle is not inherently wrong if the source art represents a longer run stride.
8. Counterevidence specific to Gemini: current `engine-ab.js` does not select separate run art, so the present code does not provide evidence that the four-frame source sequence at RUN should represent 1.8x the world distance. If a future atlas adds distinct walk/run clips, separate calibrated cycle distances may become correct again.

### HYPOTHESIS

The lateral movement will feel more coherent if displayed pose cadence is monotonic or at least perceptually continuous with actual travel speed across the WALK→RUN boundary. With the current single four-frame source sequence, using an abrupt 50→90 world-px cycle switch is likely inferior to either one calibrated continuous cycle-distance model or a smoothly blended effective cycle distance.

Candidates to test without altering physics:

A — BASELINE_STEP
- WALK: 50 world px/cycle.
- RUN: 90 world px/cycle immediately at mag 0.70.

B — SINGLE_CALIBRATED_DISTANCE
- Keep one cycle distance for the existing four-frame sequence until a separate authored RUN clip exists.
- Calibrate the distance empirically from foot-contact quality rather than choosing 50 or 90 by assumption.

C — CONTINUOUS_CYCLE_DISTANCE_BLEND
- Keep current nominal WALK and RUN distances, but derive an `effectiveCyclePx` continuously from actual/target travel speed or from a bounded blend region around gait transition instead of switching on a single frame.
- Preserve stride phase continuously.

D — SEPARATE_AUTHORED_WALK_RUN
- Future option: if the atlas is expanded to distinct WALK and RUN sequences, calibrate each clip's world distance from its actual foot contacts and transition/blend without a cadence reversal.

B/C are candidates for the current asset; D is the longer-term premium solution.

### RISKS

1. A visually faster cadence can look cartoonish if the four-frame sheet lacks enough intermediate poses. Fixing monotonicity may expose the need for more authored frames rather than justify arbitrarily high playback.
2. A single cycle distance may improve continuity but make high-speed RUN look like short rapid steps. That outcome would argue for separate run art, not for reinstating an arbitrary hard switch.
3. Blending cycle distance by input magnitude instead of actual travel can misbehave against collisions or external pushes. Prefer actual/target travel semantics consistent with the existing distance-driven design.
4. Testing only frame counts without identifying real foot-contact poses can optimize a metric while worsening planting. Cadence metrics are a gate; visual/contact inspection remains required.
5. The current source sequence may itself not contain a true RUN pose. Do not infer premium run quality from timing alone.
