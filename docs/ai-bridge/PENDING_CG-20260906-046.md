### PROBLEM
The live hero renderer draws the player's nameplate inside the same world transform as the map and avatar. The world transform in engine-c.js is `translate(screen center) -> scale(CONFIG.zoom) -> translate(-camera)`, and engine-ab.js then draws the name with `ctx.font = 'bold 11px sans-serif'` and `fillText()` at rounded world coordinates. Therefore the label is not screen UI: camera zoom scales its font/gap, integer world rounding quantizes its motion before zoom, and increasing avatar visual height changes the world-space anchor. This can make the label change apparent size between mobile/desktop, step during slow lateral motion, and move farther when the avatar is increased to 1.20x even though gameplay physics is unchanged.

### CONFIRMED_IN_GEMINI
1. Current `main` at the start of this round is commit `2400329f61d65a3351a0683b12983d9b86c3b4a0` (latest commit message: `Append pending ChatGPT bridge research`).
2. `index.html` still declares `Kelo World — V6.33` and loads `engine-c.js` before `engine-ab.js`, then `engine-z.js` before `engine-ab.js`.
3. `engine-c.js::render()` applies `ctx.translate(screenW/2, screenH/2); ctx.scale(z,z); ctx.translate(-camera.x,-camera.y)` and calls `renderAvatar(localPlayer,true)` before restoring the context. Thus actor text drawn inside `renderAvatar` inherits world zoom.
4. `engine-ab.js::presentationOf()` defines `nameplateAnchorX = footRootX` and `nameplateAnchorY = footRootY - visualHeight - 6`. With the current 256x384 frame aspect, `baseVisualHeight = round(54 * 1.5) = 81`. At 1.15x, `visualHeight = round(81*1.15)=93`, so the name anchor is `p.y + 10 - 93 - 6 = p.y - 89`. At a QA-only 1.20x it would be `round(81*1.20)=97`, moving the anchor to about `p.y - 93`, 4 world px higher while collider/physics stay unchanged.
5. `engine-ab.js::renderAvatar()` draws the name with `ctx.font='bold 11px sans-serif'` and `ctx.fillText(..., Math.round(layout.nameplateAnchorX), Math.round(layout.nameplateAnchorY))`. The label position is therefore quantized to whole world units before camera zoom.
6. `engine-z.js` currently sets zoom from viewport width. Representative existing audit profiles imply approximately `390/(11*32)=1.10795x` on 390px mobile and the clamp `1.45x` on 1280px desktop.
7. Because Canvas2D transforms apply to painted text, the authored 11px font becomes approximately 12.19 CSS px at mobile zoom 1.10795 and 15.95 CSS px at desktop zoom 1.45: about 30.8% larger on desktop solely from world zoom. The authored 6-world-px name gap similarly becomes ~6.65 CSS px vs 8.70 CSS px.
8. Integer world rounding can produce label steps of one full world pixel. At 1.45x desktop that is a 1.45 CSS-px position jump; at 1.10795x mobile it is ~1.11 CSS px. Slow analog movement can therefore hold the label for multiple frames and then jump, even if the camera/player world state changes fractionally each frame.
9. `engine-h.js` keeps a DPR-scaled backing store (`ctx.setTransform(dpr,...)`). Therefore a screen-space label drawn after the world `ctx.restore()` can still use device resolution while avoiding camera zoom.
10. `scripts/live-hero-audit.mjs` currently records avatar presentation, DPR and movement state but does not measure nameplate screen position, text bounds, text scale, overlap, or temporal jitter.
11. A legacy wrapper in `engine-c.js` also contains a title text draw (`Caballero`) based on `p.radius`, but because `engine-ab.js` later replaces `renderAvatar` and does not call its captured fallback when the hero sheet is ready, this title path is not a reliable live authority for the production hero. Do not refactor it blindly; treat it as duplicated/legacy responsibility requiring separate cleanup after behavior is benchmarked.

### EXTERNAL_EVIDENCE
- MDN CanvasRenderingContext2D documentation states that the current transformation matrix is applied when painting text, and `scale()` changes the size of canvas units. Therefore `ctx.font='11px ...'` inside a scaled world context is not guaranteed to stay 11 CSS px on screen. Sources: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D and https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/scale
- Godot Camera2D documentation explicitly warns that camera zoom can make bitmap/rasterized text blurry or pixelated unless the font is placed in a CanvasLayer that ignores camera zoom (or uses MSDF). Source: https://docs.godotengine.org/en/4.3/classes/class_camera2d.html
- Current Godot issue #117679 reports text becoming blurry when zoomed with Camera2D, confirming that world-space text quality under camera zoom remains a real rendering problem in modern engines. Source: https://github.com/godotengine/godot/issues/117679
- PlayCanvas issue #3088 documents world-layer text pixelisation under rendering effects/zoom conditions. Source: https://github.com/playcanvas/engine/issues/3088
- Community evidence: raylib developers recommend drawing text after exiting the 2D camera transform when the text must keep a stable screen size; Unity developers similarly recommend screen-space UI for labels that must remain crisp and constant-size while still following world objects. Sources: https://www.reddit.com/r/raylib/comments/ul72te/ and https://www.reddit.com/r/Unity3D/comments/id90m2/
- Counterevidence: world-space labels are legitimate when intentional perspective/zoom scaling is part of the design. Moving every label to screen space can increase overlap, make distant actors visually noisy, and remove natural occlusion. Therefore this is not an automatic refactor; Kelo World needs an A/B with readability, overlap and performance metrics.

### HYPOTHESIS
For Kelo World's social/MMORPG nameplates, separating the actor's world-space anchor from the text's screen-space raster will improve premium lateral presentation and readability: the anchor still follows `visualTop/footRoot`, but the label can be rendered after the world transform at a fixed CSS-pixel font/gap. This should eliminate zoom-dependent font-size drift and pre-transform whole-world-pixel stepping without changing physics, camera, stride, depth root or avatar scale. A hybrid policy may be preferable for many actors: fixed-size screen labels only inside a distance/visibility budget, with fade/culling/priority to control overlap.

### PROPOSED_CHANGE
Do not change production yet. Add QA instrumentation first.

Candidate A (baseline): keep the existing name inside `engine-ab.js` world-space render.

Candidate B (QA-only screen-space label):
1. `engine-ab.js` (or a small dedicated owner) publishes a world anchor only, e.g. `{nameplateWorldX, nameplateWorldY}` derived from avatar presentation.
2. Do not round the world anchor before projection.
3. After `engine-c.js` restores the world camera transform, project the anchor to screen coordinates using the same camera/zoom contract: `sx = screenW/2 + (worldX-camera.x)*zoom`, `sy = screenH/2 + (worldY-camera.y)*zoom`.
4. Draw the name at a fixed CSS-pixel font size (benchmark 11/12/13px) under the existing DPR transform from engine-h.js, optionally final-rounding only the screen coordinate if that proves visually cleaner.
5. Keep the visual gap authored in screen pixels (candidate 6-8 CSS px) rather than world pixels.
6. For multiple actors, add view culling and later evaluate overlap/priority rather than drawing all labels unconditionally.

Candidate C (lower-change alternative): retain world-space drawing but inverse-scale font/gap by `1/zoom`. This may normalize apparent size but still leaves text inside world rasterization and may preserve/introduce fractional rendering artifacts; benchmark it only if Candidate B has architecture cost.

### RISKS
- Screen-space labels can overlap more because they no longer shrink with zoom.
- Labels drawn after world restore will no longer be naturally occluded by foreground props; this may be desirable for social readability or undesirable for immersion. Treat it as a product decision and measure both policies (always visible vs actor-visibility/fade mask).
- A fixed CSS font can dominate very small/mobile viewports if too large.
- Moving nameplate drawing out of `renderAvatar` introduces a new render responsibility; avoid creating another wrapper chain. Prefer one explicit label pass if Candidate B wins.
- Screen-space projection must use the exact same camera/zoom values as the world render or labels can lag one frame.
- If the world camera itself has subpixel jitter, Candidate B will expose it; do not mask camera defects inside label smoothing.
