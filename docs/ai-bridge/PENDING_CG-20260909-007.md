### PROBLEM
The LIVE camera follow math currently mixes two coordinate conventions. `engine-a.js::updateCamera()` computes `deadW = screenW * CONFIG.deadXRatio` and `deadH = screenH * CONFIG.deadYRatio`, but compares those values directly against `(localPlayer + lookOffset) - camera.target`, which is in world units. It also treats `CONFIG.lookAheadDist` as world units. `KeloCamera` then applies an orientation-dependent `effectiveZoom`, especially in landscape (`baseZoom * height / width`). Therefore the actual screen-space size of the horizontal dead zone and the visible look-ahead distance are not explicit composition constants; they vary as a side effect of zoom/viewport policy. This can make the same LEFT/RIGHT movement feel differently framed on portrait phone, landscape phone, and desktop even when physics and input traces are identical.

### CONFIRMED_IN_GEMINI
Current `main` at the baseline above:
- `index.html` declares Kelo World V6.54 and loads `engine-a.js`, then the Foundation `src/core/camera-system.js`; `KeloCamera` deliberately preserves legacy follow math rather than replacing it.
- `engine-a.js` initializes `CONFIG.deadXRatio=0.10`, `deadYRatio=0.08`, `lookAheadDist=60`, `lookAheadDecay=4.0`.
- `engine-ac.js` changes gait/speed/input constants but does not replace those camera tuning values.
- `engine-a.js::updateCamera(dt)` uses exponential dt-invariant smoothing for look-ahead and camera damping, which is good: `1-exp(-decay*dt)`.
- The same function computes `deadW=screenW*CONFIG.deadXRatio` / `deadH=screenH*CONFIG.deadYRatio`, then compares world-space player/target deltas against those values without dividing by camera zoom.
- `camera.lookOffsetX/Y` approaches `input.normX/Y * CONFIG.lookAheadDist`, so `lookAheadDist=60` is also effectively a world-space distance.
- `src/core/camera-system.js::effectiveZoomFor(base,mode)` returns `base` in portrait and `base*(height/width)` in landscape.
- With baseZoom 0.82, the same 60-world-px horizontal look-ahead is approximately 49.2 CSS px on 390x844 portrait, 22.7 CSS px on 844x390 landscape, and 27.7 CSS px on 1280x720 desktop.
- With `deadXRatio=0.10`, the current horizontal dead-zone half/threshold value becomes 39 world px on 390x844, 84.4 world px on 844x390, and 128 world px on 1280x720. After effective zoom, that is approximately 32.0 CSS px portrait, 32.0 CSS px landscape, and 59.0 CSS px desktop. As a fraction of screen width, that is about 8.2%, 3.8%, and 4.6% respectively, despite the property being named `deadXRatio=0.10`.
- The portrait/landscape equality of ~32 CSS px on the same 390x844 device is an incidental result of the current landscape zoom formula; the look-ahead does NOT get the same cancellation and visibly shrinks by ~54% when rotating that device.
- `KeloCamera` already owns viewport/zoom/screen↔world conversion, so any correction belongs at that owner/legacy-follow boundary; do not create another camera engine.

### EXTERNAL_EVIDENCE
- Godot Camera2D documents drag margins as values relative to screen size; a margin of 1 corresponds to the screen edge. This is an explicit screen-composition contract rather than an implicit world-unit threshold.
- Current Godot 4.x documentation likewise exposes drag_left/right/top/bottom_margin as normalized screen-region controls and distinguishes camera screen position from the Camera2D node position when smoothing/limits apply.
- Unity Cinemachine describes Dead Zone Width/Height as regions of the screen/frame within which target motion is ignored, with Screen Position controlling where that zone sits. Cinemachine Position Composer documentation states a value of 1 means full screen width/height and defines dead/soft zones in camera-frame space.
- Unity Cinemachine also treats lookahead as prediction from target motion and warns that noisy prediction can amplify jitter, which supports benchmarking camera look-ahead independently from player sprite gait noise.
- Community reports around 2D camera jitter show that camera smoothing/snap/update policy can be perceived independently from player motion, especially during deceleration/settle. This is evidence for measuring camera screen traces directly rather than judging only player world traces.
- Counterevidence: world-space dead zones/look-ahead are not inherently wrong. They can be a deliberate design choice if the goal is constant world context rather than constant screen composition. Kelo's current constants may have been tuned empirically. The issue is not 'world units are invalid'; it is that current names (`deadXRatio`) and mixed formulas make the design intent ambiguous and device-dependent.

### HYPOTHESIS
For premium lateral feel, Kelo should define camera composition deliberately in one of two coherent spaces: either (A) screen-normalized composition for dead-zone/look-ahead, or (B) world-space composition with explicit world-unit names and acceptance of viewport-dependent screen feel. Because the user prioritizes consistent premium LEFT/RIGHT feel across mobile portrait/landscape and desktop, a screen-normalized horizontal composition candidate is likely worth benchmarking. However, changing look-ahead too aggressively can reduce situational awareness or make PvP camera movement feel busy.

### PROPOSED_CHANGE
Do NOT alter production before baseline measurement. Keep the existing owner and compare isolated policies:
A) BASELINE: current mixed behavior (`deadW=screenW*ratio` compared in world units; 60-world-px lookahead).
B) SCREEN-DEADZONE ONLY: convert desired screen dead-zone width into world units using `deadWorld = screenCss * ratio / effectiveZoom`; keep existing 60-world-px look-ahead unchanged. This isolates the dead-zone coordinate-space question.
C) SCREEN-LOOKAHEAD ONLY: keep baseline dead-zone; define a desired horizontal look-ahead in CSS/screen-normalized units and convert through `KeloCamera.getEffectiveZoom()` to world units before feeding legacy follow math. Do not change lookAheadDecay.
D) COHERENT SCREEN COMPOSITION: both dead-zone and look-ahead are derived from screen/reference-frame targets, converted once into world units at the camera owner boundary.
E) COHERENT WORLD COMPOSITION CONTROL: retain world units but rename/document semantics and tune separate portrait/landscape/desktop presets only if measurements show that device-dependent screen feel is actually desirable.
Do not change player speed, gait, collider, sprite scale, camera damping, or render pixel policy in the first A/B/C/D pass.

### DO_NOT_ASSUME
- Do not assume `deadXRatio=0.10` was intended to mean exactly 10% of CSS width; verify historical intent and live feel.
- Do not assume identical screen-space look-ahead on every viewport is automatically best for gameplay; landscape may intentionally need less camera lead because it already shows more horizontal world context.
- Do not combine this with sprite 1.20x, cadence, plant-frame, or pixel-phase changes in the first causal benchmark.
- Do not replace the exponential damping math; it is already dt-aware.
- Do not introduce another camera manager or write `CONFIG.zoom` directly from a feature.

### RISKS
- Normalizing look-ahead to CSS pixels can make landscape camera lead too large in world units because effective zoom is small, causing the camera to travel farther through the world and potentially reveal more map/occlusion work.
- A larger world-space camera excursion can increase culling/render load even if the screen offset is unchanged.
- Too-small dead zones can make the camera chase tiny joystick noise; too-large screen-normalized zones can make starts feel disconnected.
- PvP may prefer direction-dependent or velocity-based look-ahead rather than a fixed screen offset; do not add this complexity until the simple coordinate-space benchmark is measured.
- Camera composition changes can visually interact with CG-20260909-005 pixel-phase jitter, so use the same render policy across A/B/C/D.
