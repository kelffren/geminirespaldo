### PROBLEM
Current live Kelo movement contains two incompatible response models. `engine-a.js` defines a MICRO_ACC path with exponential acceleration/deceleration (`accelDecay`, `decelDecay`) and even computes speed-dependent `squashX/squashY`, but late-loaded `engine-ac.js` explicitly sets `CONFIG.movementType = 'DIRECT'`. As a result, `engine-a.js::updateMovement()` assigns target velocity immediately while input is active. Later, `engine-ah.js` wraps movement again and forces `localPlayer.vx/vy = 0` whenever move input is absent. The final production response is therefore effectively instant start + hard stop, not the acceleration/deceleration behavior still present in the core/config vocabulary.

This matters for the user's current lateral-polish goal because an abrupt physical velocity edge can make idle→walk/run and reversal look mechanically binary. However, blindly re-enabling physical acceleration is risky: keyboard/mobile responsiveness can become mushy, stopping distance can change collisions/camera, and gait currently derives from processed input magnitude rather than actual achieved speed. A physical ramp would therefore also create a temporary mismatch where gait can say `run` before world speed has ramped to run speed.

There is a second unused presentation signal: `engine-a.js` continuously computes `localPlayer.squashX/squashY` from speed, but the current live `engine-ab.js` hero renderer sizes the sprite from `KELO_AVATAR_PRESENTATION` and draws fixed `dw/dh`; it does not consume `squashX/squashY`. Therefore the code pays the conceptual cost of secondary-motion state without the live hero receiving that effect.

`engine-a.js` currently defines:
- PRESET B/C with `movementType: 'MICRO_ACC'`;
- default CONFIG `movementType: 'MICRO_ACC', speed: 320, accelDecay: 18, decelDecay: 35`;
- MICRO_ACC implementation using `factor = 1 - exp(-decay*dt)` and velocity convergence toward `targetV`;
- speed-dependent `squashX` and `squashY` updated every movement step;
- DIRECT implementation that sets `localPlayer.vx = targetVx`, `vy = targetVy` immediately.

`engine-ac.js` then overrides the live contract:
- `CONFIG.speed = WALK_SPEED`;
- `CONFIG.movementType = 'DIRECT'`;
- assigns `CONFIG.accelDecay = 32` and `CONFIG.decelDecay = 18`, but those values are inert while movementType is DIRECT;
- wraps `updateMovement()` to derive gait and speed cap from processed input magnitude before calling the earlier movement function;
- keyboard magnitude 1 therefore targets the current maximum speed immediately (MAX_SPEED = 178 + 0.26*28 = 185.28 world px/s);
- gait is derived from input magnitude (`idle < .03`, `walk < .70`, else run), not from achieved physical speed.

`engine-ah.js` later wraps `updateMovement()` again and after the underlying movement call sets `localPlayer.vx = 0`, `vy = 0`, `input.normX = 0`, `normY = 0` whenever there is no movement input. Thus even if a future change merely switched `movementType` back to MICRO_ACC, this later hard-stop would still suppress release deceleration unless explicitly accounted for.

`engine-ab.js` live hero renderer reads `_visualMotion`, face/frame and `KELO_AVATAR_PRESENTATION`, then draws fixed `dw = layout.visualWidth`, `dh = layout.visualHeight`. It does not apply `localPlayer.squashX/squashY`. Therefore the speed-dependent squash state from engine-a is not currently a live-hero presentation effect.

`scripts/live-hero-audit.mjs` samples positions/velocity after 220ms holds and verifies direction/release/planting, but it does not capture the first 100-150ms of start/stop, time-to-speed, braking distance, reversal zero-crossing, or any presentation response envelope. It cannot distinguish an immediate velocity edge from a short ramp, nor does it prove whether a presentation-only onset improves feel.

### EXTERNAL_EVIDENCE
Godot's official demo project includes a movement model with explicit acceleration force and a stronger stop force rather than only assigning target speed. This confirms acceleration/deceleration is a normal design tool, but not that it is automatically right for Kelo.

Unity's official Blend Tree documentation independently supports driving walk/run/strafe animation from velocity/speed parameters, including separate directional velocity components. The relevant lesson is that animation state can be authored from motion measurements rather than raw input alone.

Community evidence is mixed, which is important here. A recent r/gamedev-style Godot discussion notes that acceleration creates momentum by changing velocity over time, while another high-engagement movement-feedback thread specifically recommends near-instant response with only a small amount of ramp/inertia or an animation windup, because too much physical acceleration makes controls feel floaty/sluggish. The same thread repeatedly identifies foot sliding and movement-animation speed mismatch as more damaging than lack of inertia, and suggests lean/bob/transition juice as presentation improvements.

A recent Godot discussion about smoothing individual velocity axes also reports undesirable diagonal/oscillation artifacts during starts/stops/reversals and recommends treating velocity as a vector. This is direct counterevidence against casually reactivating the existing per-component exponential smoothing without a deterministic reversal benchmark.

### HYPOTHESIS
The safest first improvement is NOT to re-enable physical inertia. Preserve current DIRECT world response as the control baseline, and add/measure a separate presentation-response envelope that rises/falls over a very short time window while stride phase continues to advance from achieved world distance.

A presentation envelope can drive future lateral lean, tiny body bob amplitude, arm-swing intensity, shadow compression/expansion and idle↔locomotion pose settling without changing collision, camera target path or input latency. This would let Kelo look like he gathers/settles weight while still moving immediately when the player commands it.

Only after that baseline should a QA-only physical-ramp candidate be tested. If physical ramp is tested, gait/presentation must be checked against achieved speed so Kelo does not visually sprint while still physically accelerating.

### RISKS
A physical acceleration ramp can improve weight but make keyboard controls mushy, especially because desktop WASD already jumps directly to magnitude 1. It can also alter camera/depth/collision traces and therefore contaminate the separate camera and 1.20-scale experiments.

Reusing `squashX/squashY` from engine-a can break foot planting if scaling occurs around the sprite center rather than footRoot. It can also distort pixel art under fractional zoom, worsening CG-033 shimmer.

Presentation-only smoothing can still feel laggy if it controls facing, frame selection or actor translation. Restrict it to secondary motion/intensity first.

Hard-stop in engine-ah is currently intentional according to its comment (`Solo freno al soltar`). Removing it without a stop-distance benchmark would reopen a previously chosen behavior.

If gait remains input-based while a physical ramp is introduced, Kelo may enter run immediately even while actual speed is still low. Conversely, switching gait entirely to actual speed can cause collision-induced gait flicker. Test a stable measured signal rather than swapping sources blindly.

Dead/inert movement configuration creates maintenance ambiguity, but cleanup is secondary to measured behavior. Do not refactor wrappers just because responsibilities overlap.
