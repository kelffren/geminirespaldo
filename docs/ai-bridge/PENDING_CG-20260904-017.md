### PROBLEM
The production hero path does an asynchronous full-atlas pixel rewrite after the PNG loads. `engine-ab.js` first uses the raw image, then schedules `knockWhite()` with `requestIdleCallback(...,{timeout:900})` or `setTimeout(0)`. `knockWhite()` creates a second full-size canvas, draws the full hero atlas, calls `getImageData()` for every pixel, loops over the entire RGBA buffer, sets alpha to zero for any pixel whose R/G/B are all >232, calls `putImageData()`, and swaps `sheet` from the raw image to that processed canvas. This is a runtime transparency repair inside the hot visual asset path, not an authored-asset contract.

It matters to current priorities because enlarging the hero to 1.15x/1.25x makes silhouette/highlight damage more visible, while mobile browsers are the environment where full-atlas readback/allocation and delayed sheet replacement are least desirable. The delayed swap can also make the first visible hero frames come from one source bitmap and later frames from another.

### CONFIRMED_IN_GEMINI
1. `index.html` preloads `assets/hero.PNG` at high priority and loads `engine-ab.js` as the current production hero renderer.
2. `engine-ab.js` sets `sheet=raw` immediately on `raw.onload`, computes frame size from the loaded image, and sets `ok=true`.
3. The same `raw.onload` then schedules `knockWhite()` through `requestIdleCallback` with a 900 ms timeout, or `setTimeout(0)` as fallback.
4. `knockWhite()` allocates an offscreen canvas equal to `raw.width x raw.height`, requests a 2D context with `{willReadFrequently:true}`, draws the whole atlas, calls `getImageData(0,0,width,height)`, iterates every pixel, makes every pixel with all RGB channels >232 fully transparent, writes the whole buffer back with `putImageData()`, and replaces `sheet` with that canvas.
5. The threshold is color-only; it does not check whether a near-white pixel belongs to the background versus authored hero content. Therefore near-white highlights, eyes, fabric/specular accents or other intended pixels are eligible for deletion if they satisfy the threshold.
6. The production renderer then draws from whichever `sheet` is current, so the source can change after the hero has already begun rendering.
7. `src/systems/performance-governor.js` contains texture-memory accounting APIs (`registerTexture`) but the reviewed hero loader does not register either the raw image or the processed canvas there, so current `textureMB` telemetry does not prove the cost of this duplicate atlas representation.
8. Current GitHub connector access confirms the hero blob exists but does not expose its decoded dimensions in this run; exact atlas pixel count/memory therefore must be measured in-browser rather than assumed from fallback constants.

### EXTERNAL_EVIDENCE
- MDN documents that `getImageData()` returns an `ImageData` object containing the underlying pixel data for the requested rectangle, so a full-atlas call materializes a full pixel buffer. https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/getImageData
- The Canvas2D `willReadFrequently` explainer states that direct readback via `getImageData()` can be particularly slow when Canvas2D is GPU-backed and that the hint exists so browsers can optimize for repeated read access, often by avoiding GPU acceleration for that canvas. https://github.com/fserb/canvas2D/blob/master/spec/will-read-frequently.md
- Community mobile-canvas reports show large `getImageData()` buffers can create substantial memory/GC pressure on weaker devices. This is anecdotal and scale-dependent, so it supports measurement rather than proving Kelo's atlas is currently a bottleneck. https://www.reddit.com/r/webdev/comments/loqdys/
- Counterevidence: this preprocessing happens only once per hero load, not every frame, and the code already marks the temporary canvas `willReadFrequently`. If the atlas is small and processing occurs outside an active frame budget, runtime cost may be negligible. The benchmark must distinguish visual correctness from performance cost.

### HYPOTHESIS
The runtime white-knockout is likely technical debt from an earlier non-transparent hero asset. If `assets/hero.PNG` can be authored/exported with correct alpha, removing runtime color-keying should preserve more artwork, eliminate a delayed source swap, remove one full-atlas readback/rewrite, and make presentation scaling safer. If the existing asset still genuinely contains a white matte, the correct short-term fallback may be a one-time preprocessing step outside runtime (asset pipeline/build) rather than color-threshold deletion in the browser.

### PROPOSED_CHANGE
Do not remove `knockWhite()` blindly. Benchmark and inspect first.

A — `RUNTIME_KNOCKOUT_BASELINE`
Keep current code exactly.

B — `RAW_ALPHA_DIAGNOSTIC`
Render directly from `raw` for the entire session and disable the later sheet swap only in an experiment build. Capture every direction/frame against dark and light backgrounds. If a white matte is visible, B is not production-viable.

C — `AUTHORED_ALPHA_ASSET`
If the raw asset has a matte, create/export a corrected `hero.PNG` (or versioned replacement) with explicit alpha offline, preserving authored near-white pixels. Runtime renderer uses only that asset; no `getImageData`, color threshold or delayed source swap.

D — `OFFLINE_EXACT_MASK`
If the source cannot be re-authored immediately, preprocess it once outside the browser with an exact/edge-aware mask and commit the output. Do not keep heuristic `RGB>232 => alpha 0` as the long-term runtime contract.

Only after B/C/D visual equivalence or improvement is established should 1.15x/1.25x presentation-scale tests use the winner.
