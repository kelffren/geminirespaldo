### PROBLEM
The live camera controller mixes screen-pixel dimensions and world-space positions without compensating for the final world zoom. `engine-a.js::updateCamera()` computes the horizontal/vertical dead-zone as `screenW * CONFIG.deadXRatio` and `screenH * CONFIG.deadYRatio`, compares those values directly against world-space deltas, and clamps `camera.x/y` using `screenW/2` and `screenH/2` as if the visible world half-extents were equal to the viewport half-extents. Later, `engine-c.js::render()` applies `ctx.scale(CONFIG.zoom, CONFIG.zoom)` around the camera. Therefore the actual visible world half-extents are `screenW/(2*zoom)` and `screenH/(2*zoom)`, not `screenW/2` and `screenH/2` when zoom != 1.

`engine-z.js` then sets viewport-dependent zoom after the earlier camera/core definitions. At the current mobile audit viewport 390px wide, `zoom = 390/(11*32) ~= 1.10795`. At desktop 1280px wide, the computed value exceeds the clamp and final `zoom = 1.45`. This means lateral camera framing, dead-zone size in screen pixels, look-ahead in screen pixels, and world-edge reach all change materially between mobile and desktop even though the camera ratios/constants are nominally the same.

This is particularly relevant before increasing avatar scale or adding lateral lean/bob: a larger Kelo makes the character occupy more of the frame, so inconsistent lateral camera space can be mistaken for an avatar-animation problem.

### CONFIRMED_IN_GEMINI
Current `main` at round start is `1150cb039d767ec38fe408c8c82f66efb0c70038`. `index.html` is Kelo World V6.33 and loads `engine-a.js` first, `engine-c.js` early, `engine-h.js`, then the late `engine-z.js` zoom override before the live hero/gait engines.

`engine-a.js::updateCamera(dt)` currently:
- smooths `camera.lookOffsetX/Y` toward `input.normX/Y * CONFIG.lookAheadDist`;
- computes `deadW = screenW * CONFIG.deadXRatio` and `deadH = screenH * CONFIG.deadYRatio`;
- compares `(localPlayer.x + lookOffsetX) - camera.targetX` (world units) to `deadW` (raw viewport pixels);
- clamps `camera.x` to `[screenW/2, worldWidth-screenW/2]` and `camera.y` analogously.

`engine-c.js::render()` later establishes the actual camera transform with:
`translate(screenW/2, screenH/2) -> scale(z,z) -> translate(-camera.x,-camera.y)`.
It also defines `screenToWorld()` correctly as `(screen - screenCenter) / z + camera`, which is direct evidence elsewhere in current Gemini that screen/world conversion is expected to divide by zoom.

`engine-z.js::applyZoom()` sets `targetTiles = 11` for widths below 500 and 14 otherwise, computes `z = screenW / (targetTiles * 32)`, clamps to 1.05..1.45, and reduces `lookAheadDist` to 36 if it was above 40. It does not adjust camera dead-zone or camera world-bound half-extents for that zoom.

Current default `CONFIG.deadXRatio = 0.10`, `deadYRatio = 0.08`; `engine-ac.js` changes speed/deadzone/gait properties but does not replace these camera ratios. With current final zoom:
- mobile 390x844: zoom ~= 1.10795; nominal horizontal dead-zone 39 world units becomes ~43.2 screen px, ~11.08% of viewport width rather than 10%; lookAheadDist 36 becomes ~39.9 screen px;
- desktop 1280x720: zoom = 1.45; nominal horizontal dead-zone 128 world units becomes 185.6 screen px, 14.5% of viewport width rather than 10%; lookAheadDist 36 becomes 52.2 screen px.

The edge clamp mismatch is larger. At desktop zoom 1.45, the true visible half-width is `1280/(2*1.45) ~= 441.38` world px, but `updateCamera()` clamps the camera center to at least 640. Therefore the leftmost visible world x at the minimum camera position is approximately `640 - 441.38 = 198.62`, so roughly the first 199 world px cannot be brought to the viewport edge by the camera. Symmetrically the right edge has the same inaccessible framing band. At mobile 390 wide / zoom 1.10795, the mismatch is about `195 - 176 ~= 19` world px.

The current `scripts/live-hero-audit.mjs` validates hero scale, footRoot, gait/reversal/release and movement distances but does not sample `camera.x/y`, `camera.targetX/Y`, lookOffset, final zoom, screen-space player position, dead-zone screen fraction, or camera-world edge coverage. Therefore this mismatch is currently invisible to the locomotion audit.

### EXTERNAL_EVIDENCE
Godot Camera2D documentation treats camera zoom, drag margins, smoothing and camera limits as explicit camera properties, and documents that zoom changes how much of the scene is visible in the viewport. Its API also distinguishes target position from actual smoothed screen-center position. The relevant principle for Kelo is that camera bounds/dead zones must be interpreted in a consistent coordinate space after zoom.

Godot's current Camera2D docs state that a zoom of `(2,2)` doubles the size seen in the viewport. Community examples solving zoom-aware camera bounds compute visible camera size as `viewport_size / zoom`, then use half of that world-space size for edge calculations. A Raylib community answer similarly notes that camera corner distances must compensate for camera zoom when clamping to world bounds.

Unity Cinemachine documentation independently separates dead/soft zones, damping and look-ahead. It warns that look-ahead can amplify noisy target motion, reinforcing that framing parameters should be intentionally defined in presentation/screen space rather than accidentally changing with render scale.

Counterevidence / design caveat: it is not universally correct that dead-zone and look-ahead must be fixed percentages/pixels across every viewport. Deliberately giving desktop a larger dead-zone or more look-ahead can be a valid composition choice. The bug here is not that desktop differs; it is that the difference currently emerges implicitly from mixing units. If a different desktop framing is desired, it should be authored explicitly after a zoom-aware baseline.

Relevant external references reviewed:
- Godot 4.x Camera2D documentation (zoom, drag margins, target vs smoothed position).
- Unity Cinemachine Composer/Using Cinemachine documentation (dead zone, soft zone, damping, look-ahead and jitter warning).
- Reddit r/godot discussion deriving visible camera size as `viewport_size / zoom` for zoom-aware bounds.
- Reddit r/raylib discussion noting camera bound corners/distances must compensate for zoom.

### HYPOTHESIS
Converting viewport-derived camera quantities into world units before comparing/clamping will make lateral camera behavior consistent and measurable across mobile/desktop while leaving player physics untouched.

For a screen-space-authored camera contract:
- `viewWorldW = screenW / zoom`, `viewWorldH = screenH / zoom`;
- `halfWorldW = viewWorldW / 2`, `halfWorldH = viewWorldH / 2` for world-edge clamps;
- if `deadXRatio/deadYRatio` are intended as viewport fractions, `deadWWorld = (screenW * deadXRatio) / zoom`, `deadHWorld = (screenH * deadYRatio) / zoom`;
- if look-ahead is intended to be a fixed screen-pixel distance, `lookAheadWorld = desiredLookAheadScreenPx / zoom`; alternatively keep it in world units but then explicitly accept that screen-space look-ahead grows with zoom.

Do not assume all three quantities should use the same policy. Edge clamp is mathematically required to use the visible world half-extents. Dead-zone and look-ahead are design choices that require A/B after the unit mismatch is exposed.

### RISKS
Changing edge clamps can reveal portions of map borders/decoration that have not previously been visible on desktop because the over-conservative clamp hid them. That is valuable evidence but may expose art seams; do not hide the camera math bug again to conceal an environment seam.
A smaller world-space dead-zone at zoom 1.45 will make the camera react sooner on desktop. That may be mathematically screen-consistent but aesthetically worse; measure before deciding.
Converting look-ahead to screen-consistent units may reduce desktop anticipation too much in a top-down world. Treat look-ahead policy separately from edge correctness.
Zoom can change on resize; any cached camera world extents must be recomputed or derived live without per-frame allocations.
Current camera damping is exponential and already dt-aware; do not replace it with frame-count interpolation while fixing units.
Camera rounding/rasterization concerns from CG-033 remain separate; a zoom-aware camera can still exhibit pixel shimmer if final presentation snapping is inconsistent.
