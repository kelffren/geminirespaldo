### PROBLEM
The LIVE production hero begins rendering from the raw `assets/hero.PNG` as soon as `raw.onload` runs, then `engine-ab.js` asynchronously executes `knockWhite()` and replaces the rendered `sheet` with a processed Canvas. The preprocessing removes alpha from every pixel whose RGB channels are all >232, regardless of whether that near-white pixel is connected to an unwanted background or is a legitimate white/highlight detail inside the character. Because the mutation is deferred with `requestIdleCallback(...,{timeout:900})` when available and falls back to `setTimeout(...,0)` otherwise, the exact time at which the visible hero changes can differ by browser/device/load conditions. This is directly relevant to lateral premium feel and avatar upscaling: a silhouette/detail pop after first render can be misdiagnosed as frame instability, filtering shimmer, or scale quality.

### CONFIRMED_IN_GEMINI
- Current main at research time: `92a258c95e19229a69dfe9ae07d69b9e2640ec1a`.
- `index.html` is still Kelo World V6.53 and loads `engine-ab.js?v=240` in the LIVE legacy/support block.
- `assets/hero.PNG` on current main has blob SHA `deeab9669886b0c8dc4bc233cb1907429f14e041`, size 1,789,777 bytes.
- `engine-ab.js` defines nominal source frames `FW=256`, `FH=384`, 4 columns × 4 rows, implying a 1024×1536 source sheet (1,572,864 pixels) when the expected asset contract holds.
- `raw.onload` first calls `useRawSheet()`, which assigns `sheet = raw`, sets `ok=true`, and therefore permits the raw PNG to render immediately.
- Only after that, it schedules `knockWhite()` using `requestIdleCallback(later,{timeout:900})` when available, else `setTimeout(later,0)`.
- `knockWhite()` draws the complete sheet into a Canvas, calls `getImageData()` for the complete bitmap, scans all pixels, and sets alpha to zero whenever `R>232 && G>232 && B>232`; it then assigns `sheet = c`.
- The code already publishes audit fields `whiteKnockoutOpaquePixelCount`, `whiteKnockoutOpaqueLossPct`, `visibleAlphaMutationAfterIdle`, `sheetMutationAfterIdle`, `preprocessMs`, and per-frame crop/contact metrics. This proves the runtime itself recognizes that preprocessing can mutate visible opaque pixels.
- The preprocessing is not merely metadata. Once `sheet = c`, subsequent `drawImage()` calls use the mutated bitmap in the same gameplay session.
- With the nominal 1024×1536 sheet, the main knockout pass alone visits ~1.57M pixels. `compareLateralRows()` and `measureLateralContactFrames()` add substantial additional per-pixel work before/around the knockout. This is a one-time operation but it happens on the main thread.
- No new Grok bridge feedback exists after GC-20260831-003; nothing in current feedback closes this issue.

### EXTERNAL_EVIDENCE
1. MDN documents `requestIdleCallback()` as limited-availability/non-Baseline and states that callbacks run during idle periods; a timeout can force execution even if doing so risks performance impact. Therefore its execution timing is intentionally nondeterministic relative to first paint/gameplay.
2. MDN's Background Tasks guidance states idle work still executes on the browser main thread and should not overrun its available budget because doing so can cause animation/input stutter.
3. MDN documents `getImageData()` as a full pixel readback and `putImageData()`/ImageData as CPU-side pixel manipulation. ImageData is also available in workers, which means offline/worker preprocessing is technically possible if ever needed.
4. A June 23, 2026 GitHub issue in `intro-skipper/segment-editor` documents Safari desktop/iOS lacking `window.requestIdleCallback`, while Chrome/Firefox/Edge used it. Kelo guards the API, so it does not crash, but it takes a materially different fallback path (`setTimeout(0)`) on those browsers.
5. GitHub issue `konvajs/konva#293` reports severe browser-dependent performance from `getImageData()` on large canvases and a large improvement after caching/reducing readback. This is not proof Kelo's one-time pass is slow, but it is counterevidence against assuming the cost is negligible on every device.
6. GitHub issue `bokeh/bokeh#14469` records browser warnings around repeated Canvas2D readbacks and `willReadFrequently`; Kelo already requests `{willReadFrequently:true}`, which is good, but the issue still supports measuring the readback rather than assuming zero cost.
7. Community sprite workflows consistently recommend authoring/exporting transparency in the asset itself (PNG alpha) rather than treating all white as transparent at runtime. Reddit examples also show the opposite failure: white intended as visible art can disappear when white is designated as the transparent color. Community evidence is anecdotal and should not substitute for Kelo's own pixel audit.

### HYPOTHESIS
The current two-stage raw→processed hero pipeline can create two independent quality problems:
A) VISUAL MUTATION: legitimate near-white opaque pixels inside Kelo may disappear after the first visible frames, producing a one-time silhouette/detail pop whose timing differs by browser/device.
B) STARTUP JANK: the 1024×1536 full-image readback plus multiple scans can create a long frame or input hitch, especially on mobile or on browsers taking the `setTimeout(0)` fallback.
The preferred architecture, if measurements confirm either problem, is to make the production sprite immutable during gameplay: transparency should be baked/validated before runtime, or the processed representation should be fully prepared before the hero is ever exposed to rendering. Do not assume the white knockout can simply be deleted; it may currently be compensating for a real white background in the source asset.

### PROPOSED_CHANGE
No production change yet.
Candidate A — BASELINE: keep current raw→idle knockout pipeline and instrument first render + mutation timing.
Candidate B — PREPROCESS-BEFORE-PUBLISH: run the existing processing first, but keep `ok=false` / do not publish the hero renderer until the final sheet is ready; compare startup blank/fallback duration and frame-time cost. This removes mid-session mutation but may delay hero availability.
Candidate C — AUTHORITATIVE TRANSPARENT ASSET: only if pixel evidence proves the source can be exported with correct alpha, bake transparency into `hero.PNG` (or a generated runtime asset) and remove the color-key mutation from gameplay. Keep the audit as an offline/CI validator, not a render-time modifier.
Candidate D — CONNECTED-BACKGROUND KNOCKOUT: only if white background genuinely remains and legitimate white details exist. Remove only near-white regions connected to frame borders/background, not every near-white pixel. This is more complex and should lose to C if the art pipeline can produce correct alpha.
Do not move the current 1.57M-pixel mutation into a per-frame path. Do not add another renderer wrapper.

### RISKS
- Baking transparency incorrectly can permanently erase legitimate highlights/white clothing/accessories, which is worse than the current runtime workaround.
- Waiting for processed hero before first draw can briefly hide the player or fall back to a legacy avatar; that transition must be benchmarked.
- Border-connected flood-fill can fail when background color touches intentional white regions through antialiasing gaps.
- A replacement PNG changes asset integrity hashes/CI and must be audited visually at all 16 frames.
- Performance results from desktop cannot be generalized to iPhone/Safari; schedule path and CPU/GPU behavior differ.
