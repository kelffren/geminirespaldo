### PROBLEM
Current main contains two incompatible zoom policies in load order. engine-h.js intentionally defines pixelPerfectZoom(target) so the effective physical world scale is an integer: physicalScale = round(target * activeDpr), CONFIG.zoom = physicalScale / activeDpr. It also sets CONFIG.roundPixels=true and disables Canvas2D image smoothing. But index.html loads engine-z.js later, and engine-z.js rewrites CONFIG.zoom from viewport width using screenW/(targetTiles*TILE), clamped 1.05..1.45, without re-quantizing through the DPR-aware integer policy. The final live zoom can therefore make zoom*DPR fractional despite engine-h.js explicitly trying to prevent that. The live hero renderer then uses nearest-neighbor (ctx.imageSmoothingEnabled=false) and rounds its destination X/Y in world space before the world transform. This combination can produce uneven physical pixel replication and phase-dependent stepping/shimmer during lateral movement. It is especially relevant before increasing the avatar from 1.15x to 1.20x, because larger nearest-neighbor presentation does not fix a fractional world-to-physical scale and can make unstable edges more salient.

### CONFIRMED_IN_GEMINI
At BASE_COMMIT, index.html declares Kelo World V6.33 and loads mobile-performance-contract.js before engine-h.js; engine-h.js before engine-z.js; and engine-z.js before engine-ab.js. mobile-performance-contract.js caps DPR to 2 on normal mobile, 1.5 on low-memory mobile, and 3 on desktop. engine-h.js computes activeDpr() from that cap and pixelPerfectZoom(target) = round(target*dpr)/dpr, sets CONFIG.zoom=pixelPerfectZoom(1), CONFIG.roundPixels=true, creates a DPR-sized backing canvas, applies ctx.setTransform(dpr,...), and keeps imageSmoothingEnabled=false. This establishes an explicit contract that zoom*dpr should be integer for authored pixel-art rendering.

engine-z.js then runs later and overwrites CONFIG.zoom in applyZoom(): targetTiles=11 below 500 CSS px, otherwise 14; z=screenW/(targetTiles*32); CONFIG.zoom=clamp(z,1.05,1.45). It does not call or replicate pixelPerfectZoom(). For the audit mobile viewport 390 CSS px at DPR2, final z is 390/(11*32)=1.1079545, so effective physical scale z*dpr is ~2.215909 rather than integer 2. For a low-memory mobile DPR cap 1.5 it is ~1.661932. For the audit desktop viewport 1280 CSS px at DPR1, the clamp produces z=1.45, so effective physical scale is 1.45; at desktop DPR2 it would be 2.9, and DPR3 4.35.

engine-c.js applies the world transform as translate(screen center) -> scale(CONFIG.zoom) -> translate(-camera), while engine-h.js has already made one Canvas unit equal to activeDpr backing pixels through ctx.setTransform(dpr,...). Therefore the physical device-pixel scale of world units is directly activeDpr*CONFIG.zoom. engine-ab.js then draws the hero with ctx.imageSmoothingEnabled=false and destination coordinates Math.round(p.x-dw/2), Math.round(footY-dh), using integer world destination width/height. At current lateral 1.15x presentation dw is 55 world px and dh about 93; at 390/DPR2 those map to roughly 121.875 x 206.08 device px. A QA 1.20x candidate would be about 58 x 97 world px, mapping to ~128.52 x 214.94 device px. On 1280/DPR1 current 55 x 93 maps to 79.75 x 134.85 device px. These are not integer physical extents despite nearest-neighbor rendering.

A responsibility scan confirms redundant/conflicting zoom ownership: engine-c.js initializes CONFIG.zoom=0.82 and exposes old zoom steps; engine-t.js later clamps CONFIG.zoom to <=1.05; engine-h.js replaces it with a DPR-aware pixel-perfect policy; engine-z.js then replaces the final value again with viewport-derived fractional zoom. ENGINE_MAP already marks zoom ownership NEEDS_AUDIT and warns not to edit one of engine-h/engine-t/engine-z in isolation. This is exactly such a conflict. No refactor is proposed until the visual/performance trace is measured.

scripts/live-hero-audit.mjs currently captures mobile 390x844 DPR2 and desktop 1280x720 DPR1 and validates avatar scale/collider/footRoot/contact evidence, but it does not record CONFIG.zoom, active DPR cap, zoom*DPR integrality, destination device-pixel rects, camera fractional phase, or frame-to-frame edge stability. It therefore cannot detect this rendering contract violation today.

### EXTERNAL_EVIDENCE
MDN documents that CanvasRenderingContext2D.imageSmoothingEnabled=false is intended to retain sharp pixel-art pixels when images are enlarged, but it does not itself guarantee even pixel sizes under arbitrary fractional transforms: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled . MDN also documents that CanvasRenderingContext2D.scale() changes the physical size represented by each canvas unit; a non-integer transform therefore directly creates non-integer device-pixel coverage before rasterization: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/scale .

Godot's current multiple-resolution documentation provides strong directly relevant evidence: fractional scale factors such as ~2.133 cause pixel-art pixels/line widths to become uneven because displays only have whole pixels, while integer scaling keeps the checkerboard/pixel widths consistent. Godot explicitly recommends integer stretch scaling for pixel art to prevent distortion: https://docs.godotengine.org/en/4.4/tutorials/rendering/multiple_resolutions.html . Unity's Pixel Perfect package describes its purpose as keeping 2D pixel art crisp, clear across resolutions, and stable in motion: https://docs.unity3d.com/6000.0/Documentation/Manual/com.unity.2d.pixel-perfect.html .

GitHub counterexamples show the issue is not solved simply by enabling pixel snap. Godot issue #71074 reports transform-to-pixel snapping removing camera jitter but introducing visible sprite jitter/vibration, while issue #54974 reports some sprite pixels stretching when the screen is scaled by a non-perfect-integer factor. Issue #7774 aggregates multiple Camera2D pixel-perfect jitter cases and recommends careful snapping/drag-margin handling rather than assuming one switch fixes all subpixel problems. Relevant sources: https://github.com/godotengine/godot/issues/71074 , https://github.com/godotengine/godot/issues/54974 , https://github.com/godotengine/godot-docs/issues/7774 . Community evidence is mixed: developers frequently report fractional camera zoom causing pixel-art stutter, but some prefer smooth fractional rendering and even disable transform pixel snap because strict snapping can itself look worse during smooth camera motion. Representative discussion: https://www.reddit.com/r/godot/comments/1ocipqi/ . Therefore integer scaling must be A/B tested against Kelo World's desired HD-2D look rather than imposed dogmatically.

### HYPOTHESIS
Part of Kelo's lateral visual roughness may be raster cadence rather than animation cadence: with nearest-neighbor sprites, a fractional physical world scale plus rounded world destination positions can cause visible edges to advance in uneven device-pixel patterns as actor/camera phases change. Restoring a coherent DPR-aware zoom policy, or otherwise making the hero's final device-space presentation stable, should reduce pixel-width variation/shimmer without altering world physics, stride or input. This may also let 1.20x look cleaner than the same scale under today's fractional raster contract.

The strongest first hypothesis is not 'force integer zoom everywhere'. It is: quantify whether the current final zoom violates the intended engine-h contract and whether this correlates with measurable edge instability. If yes, compare at least two presentation-only candidates: A) quantize final viewport-derived zoom through the existing DPR-aware integer physical-scale rule; B) retain fractional camera/world zoom but render the hero through a separately stabilized device-pixel presentation path or subpixel-aware filter, preserving smooth camera composition. Candidate B exists because strict integer world zoom can change field of view too much on arbitrary phones and can create visible bars/composition jumps; the benchmark must decide.

2) Run deterministic sustained RIGHT and LEFT at magnitudes 0.50, 0.70, 1.00 for >=2 seconds, plus RIGHT->LEFT reversal. 3) Capture a tight hero crop every frame. Compare stable opaque edge landmarks and compute frame-to-frame edge displacement versus expected world/camera displacement. 4) Candidate A: quantize final z through DPR-aware integer physical scale, then replay the exact input/world trace. Do not alter authored target-tile intent beyond the quantization itself. Measure both visual stability and framing/FOV delta.
5) If A reduces shimmer but the FOV/composition delta is unacceptable, test Candidate B separately with fractional world zoom but a stabilized hero raster path. Do not proceed to B if A already meets visual and composition goals.
6) Repeat winning candidate at 60/90/120 Hz and 1.15x vs QA-only 1.20x. Then test 1/8/16/32 actors to make sure any intermediate-render or extra transform path does not create meaningful CPU/GC/draw overhead.

Negative controls: idle actor while camera is static; idle actor while camera moves; moving actor with locked camera; world tile/architecture crop next to hero; and UI/text outside world transform. These separate actor rounding, camera phase and global fractional-scale artifacts.

### RISKS
Quantizing zoom can change field of view abruptly across resize/orientation breakpoints and may expose/hide more world, interact with CG-040 camera bounds, or make mobile composition feel too tight/loose. A separate intermediate hero raster can add memory, extra draws and complexity, especially with 32 actors. Removing Math.round from hero destination coordinates under nearest-neighbor/fractional zoom can reduce one kind of stepping but worsen blur/edge crawl depending on browser rasterization. Different browsers/GPUs may rasterize fractional nearest-neighbor transforms differently enough that Chrome-only results are insufficient for universal claims. DPR caps on low-memory devices mean the same CSS viewport can have materially different physical scale. Aura/nameplates/depth redraw can visually confound crop differences, so the benchmark should be able to disable or separately account for them in QA without changing production.
