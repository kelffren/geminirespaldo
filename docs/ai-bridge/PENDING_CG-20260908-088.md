### PROBLEM
The live HD renderer establishes a DPR-aware integer physical zoom policy in `engine-h.js` (`pixelPerfectZoom()` chooses a target whose `zoom * activeDpr` is an integer), sets the backing store to the capped DPR, disables Canvas2D image smoothing and marks the canvas `image-rendering: pixelated`. However, `engine-z.js` is loaded later and unconditionally overwrites `CONFIG.zoom` with `screenW / (targetTiles * 32)` clamped to 1.05..1.45. This makes the final world-to-device scale fractional on common mobile/desktop configurations, defeating the earlier pixel-perfect physical-scale invariant. The hero renderer then rounds destination world coordinates/sizes before the global fractional world transform. The result can be crisp but uneven nearest-neighbor sampling, especially during lateral motion/camera movement and when testing avatar 1.15x vs 1.20x.

### CONFIRMED_IN_GEMINI
1. Current main baseline for this entry is `37b194f7e1bb25e11c515743054ce4eea8a9a875`; `index.html` declares Kelo World V6.53.
2. Load order is authoritative: `engine-h.js` loads early and `engine-z.js` loads much later, before `engine-ab.js`. Therefore the final zoom used by the hero is the later `engine-z.js` value unless another later owner changes it.
3. `engine-h.js` defines `pixelPerfectZoom(target)` as `round(target * activeDpr) / activeDpr`, explicitly comments that this is Pixel-art HD mode, sets `CONFIG.roundPixels=true`, configures the canvas backing store to `screenW/H * activeDpr`, sets CSS `imageRendering='pixelated'`, and forces `ctx.imageSmoothingEnabled=false`.
4. `engine-z.js` later calculates `z = screenW / (targetTiles * TILE)` with targetTiles 11 below 500px width and 14 otherwise, then clamps 1.05..1.45 and assigns that directly to `CONFIG.zoom`. It does not call `pixelPerfectZoom()` or otherwise quantize `zoom * DPR`.
5. With the current mobile performance contract, ordinary mobile DPR is capped at 2 (1.5 on <=2 GB reported device memory), desktop DPR at 3. At the existing audited 390px-wide DPR2 mobile viewport, final `engine-z` zoom is about 1.10795 and final world-to-device scale is about 2.21591, not an integer. At 430px DPR2 it is about 2.44318 device pixels per world pixel. At 1280px desktop the zoom clamps to 1.45, yielding physical scale 1.45 at DPR1, 2.9 at DPR2, or 4.35 at DPR3.
6. `engine-c.js` applies the global world transform as `translate(screen center) -> scale(CONFIG.zoom) -> translate(-camera)`, so the fractional final zoom affects avatar, environment, camera-relative movement, shadows and world FX.
7. `engine-ab.js` disables image smoothing for the hero draw and rounds the hero destination X/Y in world coordinates before it is multiplied by the global zoom. A one-world-pixel destination step therefore becomes about 1.108 CSS px on the 390px mobile configuration and 1.45 CSS px on the 1280px desktop clamp, while device-pixel coverage is fractional as above.
8. `engine-ab.js` currently renders the lateral avatar at 55x93 world px for 1.15x. A QA-only 1.20x candidate would become approximately 58x97 world px. The source frame is nominally 256x384 before crop; after current 5%/4% per-frame crop, the source is still roughly 230x353 px. Therefore 1.15x and 1.20x are both heavy DOWNSAMPLES of the source, not resolution-starved upscales. Source sprite resolution is not the immediate blocker to trying 1.20x; temporal/downsampling quality and fractional display mapping are the real risks.
9. `scripts/live-hero-audit.mjs` currently verifies 390x844 DPR2 and 1280x720 DPR1, asserts 1.15x presentation/collider/foot-root contracts and captures screenshots, but it does not record final `CONFIG.zoom`, effective `zoom * cappedDpr`, device-pixel phase, per-frame silhouette stability, or 1.15x/1.20x resampling comparisons.
10. This is not a request to switch the whole game blindly to fixed integer viewport scaling. The current camera/world design intentionally shows a target number of tiles and supports multiple aspect ratios. The identified defect is specifically that the earlier HD policy and later zoom owner contradict each other, leaving no single explicit contract for the final sampling mode.

### EXTERNAL_EVIDENCE
- MDN documents that `CanvasRenderingContext2D.imageSmoothingEnabled=false` preserves hard pixel edges when scaling, but it does not guarantee uniform device-pixel coverage under a fractional final mapping: https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled
- MDN's current crisp-pixel-art guidance explicitly warns that when CSS pixels do not align with device pixels, some source pixels can be rendered larger than others and edges can look uneven; it notes that arbitrary/fractional canvas scaling adds another mapping stage: https://developer.mozilla.org/en-US/docs/Games/Techniques/Crisp_pixel_art_look
- Godot 4.x documents integer stretch scaling specifically to prevent uneven pixel scaling/distorted pixel-art line widths; its fractional example (2.133x) shows uneven pixels, while integer scale keeps widths consistent: https://docs.godotengine.org/en/4.3/tutorials/rendering/multiple_resolutions.html
- Counterevidence: Godot also notes that fractional/canvas-style scaling is appropriate when smooth subpixel sprite/camera motion is desired, and MDN allows arbitrary canvas scale factors. Kelo therefore should not adopt global integer scaling solely from pixel-art doctrine; it must benchmark visual stability against field-of-view/composition and smooth-camera behavior.
- Community counterevidence is mixed: developers of smooth-camera top-down pixel-art games report that strict snapping can trade shimmer for visible camera/object stepping. This supports an A/B/C benchmark rather than a categorical integer-only rule: https://www.reddit.com/r/godot/comments/1et31wd

### HYPOTHESIS
The current contradiction between an early DPR-aware integer-scale policy and a later arbitrary fractional zoom is contributing to temporal edge shimmer/uneven silhouette sampling more than the avatar's intrinsic source resolution. For the 1.15x->1.20x decision, preserving a coherent final device-pixel sampling contract should improve apparent sprite quality without changing collider, world speed or source art. The best solution may be quantizing only the final zoom to DPR-compatible steps near the composition target, or keeping fractional camera/world composition while rendering the hero to a dedicated quantized presentation path; which one wins must be measured.

Architecture guardrail: choose one final owner for zoom/sampling policy. `engine-h` and `engine-z` should not independently claim incompatible pixel-perfect/fractional contracts. Baseline -> one change -> same trace -> remeasurement; no broad renderer refactor.

### DO_NOT_ASSUME
- Do not assume integer scaling is universally better; smooth camera and target-tile composition may justify fractional world scaling.
- Do not assume `imageSmoothingEnabled=false` solves fractional device-pixel mapping; it only selects the image sampling behavior inside Canvas2D.
- Do not assume 1.20x lacks sprite resolution. The current source frame is far larger than the destination and both 1.15x/1.20x downsample it substantially.
- Do not couple visual zoom quantization to collider/world speed.
- Do not modify camera semantics simultaneously with the sampling experiment; if B changes zoom, apply CG-084's zoom-aware camera math only as a separately measured follow-up or hold camera traces constant for comparison.

### RISKS
- Quantizing final zoom changes field of view. On narrow mobile screens, a large quantization jump can be worse UX than mild pixel unevenness.
- Hero-only offscreen rendering can add architecture and memory/GC overhead; avoid unless global quantization fails.
- Nearest-neighbor is desirable for crisp authored pixel edges when enlarging, but Kelo's source is heavily downsampled; hero-only smoothing may improve static detail while making movement look soft. It must remain a diagnostic until visual evidence supports it.
- Rounding avatar destination in world space plus fractional camera/global zoom can interact with camera subpixels; changing only one snap can transfer jitter from sprite to world/background.
- DPR can change with browser zoom/display movement. Any final quantization policy must re-evaluate on resize/DPR change without thrashing zoom.
- `engine-h.js` and `engine-z.js` currently duplicate zoom responsibility. A cleanup is justified only after a measured winner is known.
