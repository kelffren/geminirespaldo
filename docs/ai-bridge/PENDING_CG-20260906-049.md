### PROBLEM
The current LIVE reversal audit proves only that a RIGHT↔LEFT reversal does not introduce an idle and does not jump more than one animation-frame index. It does not prove that the visible support foot remains planted. `engine-ac.js` preserves the same stride phase/frame through a reversal, while `engine-ab.js` renders LEFT by horizontally mirroring the same lateral row around `p.x`. If the current frame's visible contact/support point is not exactly centered on `p.x`, mirroring changes its world-side instantaneously. A reversal can therefore pass `reversalFrameJumpCount === 0` and still create a visible shoe/contact jump.

### CONFIRMED_IN_GEMINI
Current `main` at the start of this round is `13709bdf4e641f9f3240b3d7e24f81bbb743bd21`.

`index.html` still loads `engine-ab.js?v=240`, then `src/characters/character-appearance.js?v=2`, then `engine-ac.js?v=222`; the player appearance delegates back to the legacy/current hero renderer in `engine-ab.js`.

In `engine-ac.js::updateVisualMotion()` a lateral reversal increments audit counters but does not remap `stridePhase` or `frame`. The current check only flags a reversal frame jump if the cyclic frame distance exceeds one. Therefore same-frame reversal is considered clean by the present audit.

In `engine-ab.js`, both RIGHT and LEFT use spritesheet row 2. LEFT is produced by:
- translating to `p.x`;
- `scale(-1, 1)`;
- translating back from `p.x`;
- drawing the same source frame.

The draw rectangle itself is centered on `p.x`, not on a frame-specific visible support-foot anchor. The preprocessing audit already computes `lateralContactFrames[].supportCentroidX` for all four lateral frames, but those values are not consumed by the player renderer.

Therefore, for a frame whose visible support point is offset by `o` world pixels from the mirror axis, an instantaneous mirror changes that point from `+o` to `-o`, producing a theoretical contact displacement of `2*|o|` before camera/zoom. This is a geometric consequence of the current transform; the actual `o` for LIVE must be measured from the processed sprite rather than assumed.

`src/characters/character-appearance.js` contains a non-player/retired appearance path with per-frame `footX[]/footY[]` anchors and draws the sprite relative to `footRoot`. This is evidence that the repository already recognizes per-frame foot anchoring as a useful rendering contract, but those legacy metrics must NOT be copied blindly to the player because `player_hero_v1` currently delegates to `engine-ab.js`.

`scripts/live-hero-audit.mjs` currently executes RIGHT -> LEFT reversal and asserts `reversalFrameJumpDelta === 0`, but it samples only state snapshots and never computes the visible support point before and after the mirror. Thus the existing audit can produce a false sense of reversal continuity.

### EXTERNAL_EVIDENCE
- Unity's current Blend Tree documentation states that mirrored locomotion is not treated as a naively symmetric operation: Unity adds offsets so mirrored walk/run cycles align foot cycles correctly with surrounding motions. In the example, the corresponding foot must contact the ground at the same cycle time after mirroring. This directly supports testing contact-phase continuity rather than frame-number continuity alone: https://docs.unity3d.com/Manual/BlendTree-AdditionalOptions.html
- Unity's Blend Tree documentation also recommends aligning locomotion clips at normalized foot-contact landmarks (for example left-foot and right-foot contacts), reinforcing that support/contact phase is the invariant that matters when changing locomotion presentation: https://docs.unity3d.com/Manual/class-BlendTree.html
- Unity's Timeline humanoid workflow documents foot sliding caused by transitions between different foot positions and recommends positional/root offsets to reduce the discontinuity. The engine differs from Kelo World, but the principle is relevant: pose continuity alone does not guarantee foot continuity: https://docs.unity3d.com/Manual/TimelineWorkflowHumanoidAnimation.html
- Community evidence from a top-down Godot case reports a visible moonwalk/glitch specifically when switching left/right while reusing a right-facing animation with horizontal flip, showing that mirror transitions can expose timing/contact problems even when the underlying frames are valid: https://www.reddit.com/r/godot/comments/udmg88/
- Additional community discussion notes that top-down projects often choose either explicit left/right clips or controlled `flip_h` state; mirroring is a storage/pipeline choice, not proof that transition/contact semantics are automatically correct: https://www.reddit.com/r/godot/comments/1akrggm/

Counterevidence: mirroring one lateral cycle is a standard and often correct optimization. If the authored frames are centered around the support point, or if reversal happens during a flight/pass phase where no foot is intended to remain planted, the visible jump may be negligible or even desirable. The benchmark must therefore identify support/contact phases before applying any reversal-specific phase remap or anchor compensation.

### RISKS
- Bottom-band support detection may select the wrong shoe or both shoes.
- Forcing support continuity during a flight/pass phase can make the animation less natural.
- Moving the mirror axis per frame can cause body-center wobble if the art is not authored symmetrically.
- A phase remap can create a larger pose pop than the contact jump it fixes.
- At fractional zoom/DPR, raster shimmer can contaminate screen-pixel measurements; retain world-space support metrics as the primary geometric signal and use screen-space as perceptual evidence.
- Future dedicated left/right sprites could supersede mirror compensation entirely.
