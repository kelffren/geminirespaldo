### PROBLEM
The live locomotion code uses two different angular rules for concepts that are expected to describe the same visual state. `engine-ac.js` classifies the rendered facing as lateral when `abs(dx) * 1.15 >= abs(dy)`, but it classifies horizontal intent for reversal detection only when `abs(intentX) >= abs(intentY)`. Therefore there is a wedge where Kelo is visibly rendered LEFT/RIGHT while the reversal detector says the intent is not horizontal. Numerically, the facing rule remains lateral until roughly 48.99° from the horizontal axis, while the reversal detector stops treating the input as horizontal above 45°. Any future support-foot phase remap or reversal polish wired to the current `lateralReversal` flag can silently miss reversals in that ~4° sector.

### CONFIRMED_IN_GEMINI
Current `main` still loads Foundation movement ownership and `engine-ac.js` as a `KeloMovement` consumer. The current `engine-ac.js` computes `horizontalIntentSign` with `abs(intentX) >= abs(intentY)` but later computes `v.face` using `abs(v.dx) * 1.15 >= abs(v.dy)`. The PNG renderer in `engine-ab.js` consumes `v.face`, so the visual row/mirror decision follows the wider 1.15 rule while reversal telemetry follows the narrower 1.0 rule. `engine-ab.js` also retains the same 1.15 rule as legacy fallback. No production change in the latest fullscreen/Foundation commits removes this mismatch.

### EXTERNAL_EVIDENCE
Unity's official 2D directional blending documentation treats direction selection as one coherent 2D parameter space for left/right/up/down rather than separate incompatible angular tests for adjacent animation decisions. Godot/joystick issue reports show that noisy analog axes can flicker around direction thresholds, and a 2026 Reddit case demonstrates that analog joystick direction logic commonly breaks when code assumes exact/cardinal values rather than treating the continuous axis consistently. Community discussions on 8-way/diagonal top-down animation also recommend preserving direction history or using a separate facing decision to avoid last-frame/diagonal state errors. Counterevidence: using different sectors for different purposes can be valid if intentional; the mismatch is not automatically a gameplay bug. It becomes a problem only if reversal behavior is supposed to apply whenever the avatar is visually lateral.

### HYPOTHESIS
If reversal-specific presentation logic is keyed from the current `lateralReversal`, then inputs around 45°–49° can produce LEFT↔RIGHT visual reversals without triggering the reversal path. This can make support-foot continuity, reversal metrics, or future phase remapping work for pure horizontal input but fail near diagonals. A single authored `facingFamily`/sector decision shared by both visual facing and reversal classification should reduce this inconsistency without changing physical velocity.
