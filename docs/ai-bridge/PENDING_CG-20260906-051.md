### PROBLEM
The live hero now exposes explicit presentation geometry (`visualLeft/Top/Right/Bottom`, `footRoot`, `depthRoot`) independently from the physics collider, but generic prop occlusion still tests actors using only `actor.radius` around `actor.x/y` and makes front/behind decisions using `actor.y`. This is already geometrically different from the rendered hero at 1.15x and becomes slightly more divergent if the visual avatar is increased to 1.20x. The likely consequence is not collision failure; it is visual depth/occlusion switching that can happen too late, too early, or only after a tall/wide sprite is already visibly intersecting a prop.

### CONFIRMED_IN_GEMINI
Current `main` at base commit 7ff0bbd5eaeffbf0af4c1ef5a355c28db5395f51 still declares Kelo World V6.33 in `index.html` and loads `engine-ab.js` before `engine-ac.js`, then environment depth/prop systems later.

`engine-a.js` defines the local player with `radius: 20`; physics collision and world clamping use that radius.

`engine-ab.js` defines `FOOT_ROOT_OFFSET_Y = 10` and `AVATAR_VISUAL_SCALE = 1.15`. For lateral facing it uses base width 48 and base height 81, yielding current rounded visual dimensions about 55x93 world px. Its presentation contract publishes:
- physicsRoot = p.x/p.y
- colliderRadius = p.radius
- footRoot = p.x, p.y + 10
- depthRoot = footRoot
- visual bounds from footRoot and visual dimensions

Therefore at current lateral 1.15x the rendered body extends about 27.5 world px horizontally from center while the collider extends only 20; the visual top is about p.y-83 while collider top is p.y-20. This separation is intentional and should not be removed by blindly enlarging the collider.

At QA-only 1.20x, the same formulas would round to roughly 58x97 world px: horizontal visual half-width ~29 px, still versus a 20 px collider; visual top becomes roughly p.y-87. The extra scale therefore increases the visual-vs-collider horizontal overhang from ~7.5 to ~9 world px per side and the top overhang beyond collider-top from ~63 to ~67 world px.

`src/environment/generic-props.js` currently defines `overlaps(actor,b)` using a circle-like AABB based on `actor.radius || 20`, not the hero presentation visual bounds. For `actor-base-y-clip-v1`, it requires `overlaps(actor,p.visualBounds)` and then compares `actor.y >= p.occlusion.baseY`. For `actor-base-y-redraw-v1`, it also gates with radius-based overlap and compares `actor.y <= p.occlusion.baseY` before deciding whether to redraw the actor.

`src/environment/prop-contract.js` assigns Plaza nature props `actor-base-y-clip-v1` and the fountain `actor-base-y-redraw-v1`. Fountain baseY is 1505. `src/environment/plaza-depth.js` likewise reports local depth from `(localPlayer.y||0)>baseY`, not the hero's published `depthRootY`.

Because `depthRootY = p.y + 10`, the current generic prop depth decision is displaced by 10 world px from the hero presentation's own declared ground/depth root. Example: at p.y=1496, the foot/depth root is 1506, already beyond fountain baseY 1505, while the current fountain decision still treats actor.y as behind until physics-center Y crosses 1505.

This is a responsibility mismatch: `engine-ab.js` already owns actor presentation geometry, but `generic-props.js` reconstructs actor spatial extent from physics radius and physics-center Y.

### EXTERNAL_EVIDENCE
Official Godot CanvasItem documentation states that Y-sorting orders CanvasItems according to Y position. Its TileMapLayer documentation exposes `y_sort_origin` specifically to alter the point used for top-down depth ordering. This supports treating depth as a ground/origin-point problem rather than as full sprite height.

Godot proposal issue #9222 explicitly describes center-bottom pivots as a common need for tilted top-down/Y-sorted sprites, because the desired sorting point is typically the bottom of the sprite.

Recent Godot community reports repeatedly resolve top-down occlusion problems by placing the character/root origin at the feet and setting prop/tile Y-sort origins at their ground/base point. This is consistent with Kelo's existing `footRoot/depthRoot` contract.

Counterevidence: full visual bounds should NOT replace the depth root as the ordering key. Tall sprites intentionally extend upward while still belonging to the ground position of their feet. Using `visualTop`, sprite center, or entire rectangle to choose front/behind would make tall characters switch depth too early. Visual bounds are appropriate for determining whether two images can visibly overlap; ground/depth roots are appropriate for deciding which should be in front.

### HYPOTHESIS
Kelo's occlusion logic should consume two separate actor spatial concepts:
1. presentation/visual bounds for broad-phase visible-overlap gating;
2. `depthRootY` (normally footRootY) for front/behind decisions.

This should improve tall-avatar and 1.20x behavior without modifying physics, collision radius, movement trace, camera, or sprite scale. The current 10 px physics-center-vs-depth-root discrepancy is a stronger immediate defect candidate than the modest additional 1.15x→1.20x width difference.

### PROPOSED_CHANGE
Do not change production yet.

Candidate A (instrumentation only): add a QA spatial profile for actors. If `KELO_AVATAR_PRESENTATION.get(actor, face)` is available, record `visualLeft/Top/Right/Bottom`, `depthRootY`, `footRootY`, and collider radius. In generic prop audit, record both current radius-overlap/depth decisions and candidate presentation-aware decisions without changing rendering.

Candidate B (only after baseline proves mismatches): for prop occlusion broad-phase, use actor presentation visual bounds when available; retain radius fallback for actors without a presentation profile. For front/behind, compare prop `baseY` against `depthRootY`, falling back to `actor.y` for actors without a presentation profile.

Candidate C (only if B is verified and API duplication becomes a maintenance issue): centralize a tiny read-only `actorSpatialProfile(actor)` adapter so generic props do not directly depend on hero-specific renderer internals. Do not refactor renderer/physics ownership as part of the first fix.

### DO_NOT_ASSUME
- Do not enlarge `localPlayer.radius` to match the sprite. That would alter navigation, collision feel, passability and world trace and is not required for a visual occlusion fix.
- Do not use the full visual rectangle as the depth ordering key. Sorting should remain ground-contact based.
- Do not assume every actor has `KELO_AVATAR_PRESENTATION`; preserve radius/Y fallback for NPCs or legacy appearances until audited.
- Do not assume 1.20x is approved. Test 1.15x baseline first, then 1.20x QA-only.
- Do not refactor `generic-props.js`, `engine-ab.js`, or environment wrappers before same-trace measurement.

### EXPERIMENT
Baseline instrumentation on current 1.15x:
1. Choose props using both occlusion modes: at least one Plaza nature prop (`actor-base-y-clip-v1`) and fountain (`actor-base-y-redraw-v1`).
2. Move RIGHT/LEFT and vertical/diagonal paths through prop visual bounds while sampling every update/render.
3. For each sample record actor physics center, collider radius, presentation visual bounds, footRoot/depthRoot, prop bounds/baseY, current overlap result, candidate visual-overlap result, current front/behind result, candidate depthRoot result, and actual actor redraw/clip counts.
4. Specifically traverse ±20 world px around each prop baseY at slow and normal speeds.
5. Capture identical traces at 60/90/120-equivalent sampling where practical.
6. Repeat unchanged with 1.20x QA-only visual scale, without changing collider or physics.
7. If baseline shows discrepancies, apply Candidate B and replay the exact same traces.

Suggested deterministic edge cases:
- `depthRootY = baseY - 1 / baseY / baseY + 1` while physics center remains 10 px above those values;
- actor visual rectangle intersects a prop while the radius-based overlap still returns false;
- left/right reversal near a prop edge;
- diagonal motion crossing prop edge and baseY in the same short interval.

### DECIDING_METRICS
- `depthDecisionRootErrorWorldPx`: current `actor.y` decision point vs published `depthRootY`; baseline expected structural offset = 10 px for current hero.
- `visibleOverlapMissCount`: candidate visual bounds overlap true while current radius overlap false.
- `visibleOverlapMissDurationMs` and `visibleOverlapMissDistancePx`.
- `occlusionSwitchOffsetFromDepthRootPx`: distance between actual layer switch and depthRoot crossing baseY.
- `wrongFrontBehindFrameCount` from instrumented expected decision, before/after.
- `propActorRedrawCountDelta` to detect excess redraw work.
- `renderFrameTimeP95Ms` / `renderFrameTimeP99Ms` with 1/8/16/32 actors if presentation-aware bounds are generalized.
- invariants: `worldTraceDelta=0`, `cameraTraceDelta=0`, `colliderDelta=0`, `footRootDelta=0`, `stridePhaseDelta=0`, `collisionOutcomeDiff=0`.

A strong Candidate B result would reduce `occlusionSwitchOffsetFromDepthRootPx` toward 0 and eliminate measured visible-overlap misses without changing any gameplay invariant or materially increasing actor redraw/frame cost.

### RISKS
- Visual bounds are much taller than collider bounds, so naively using them can increase broad-phase prop checks/redraw opportunities. Keep the broad-phase cheap and measure 1/8/16/32 actors.
- Some actors may not use the hero renderer/presentation contract; fallback behavior is mandatory.
- Some authored prop visual bounds may themselves be generous rectangles containing transparent space, creating false-positive overlap. If measured, the next step should improve prop occlusion bounds, not shrink actor bounds blindly.
- The fountain's very large 720x720 bounds may make overlap-gate changes irrelevant there; its primary likely issue is the 10 px depth-root mismatch. Nature props are more useful for measuring overlap gating.
- If future bob/lean modifies only body presentation, depthRoot must remain stable; otherwise this fix could reintroduce depth chatter.
